# 类型安全和接口真实返回不一致怎么办？

## 核心回答

1. 类型声明只是前端对数据的约定，不是接口内容的证明。编译过了，读字段时照样可能炸。比如声明商品价格是数字，服务端却给了字符串，乘法可能被悄悄转换，后面金额格式化也可能直接失败。

2. 请求边界上，解析出来的数据先当未知值。看对象是不是空的、字段在不在、嵌套内容合不合要求。过了检查再做成内部的成功状态。别直接断言成成功类型，断言既补不上缺的字段，也不会把错数据转对。

3. 网络失败、业务拒绝、数据格式不对，分开记。处理办法不一样，格式问题反复重试通常也好不了。要兼容字符串价格，在接口转换层明确转，并验证数值范围，别让每个页面自己猜接口什么意思。

4. 接口变了，先对实际响应和约定，再一起改校验、模拟数据和相关用例，别只改类型把报错消掉。线上排查可以记字段路径和接口版本，完整用户数据别直接写进日志。

## 追问：后端多返回一个字段应该让整个请求失败吗？

1. 不一定。多出来的字段允不允许，看接口兼容约定。页面不用它，通常只取自己需要的字段就行。所有新增字段都强制拒绝，后端正常扩展也会把旧页面打挂，严到什么程度跟业务目的走。

2. 必填字段缺了，或者类型变了，要更小心，直接影响计算和展示。商品名称旁边多一个附加字段，可以忽略；价格从数字变成任意文本，不能默默收下，边界上明确报错，或者按已经约定好的规则转换。

3. 转成内部对象时，只复制经过校验的字段，外部扩展和内部模型隔开。用例分别覆盖：多了字段、缺了必填、未知枚举值。兼容策略是故意选的，不是某个断言碰巧放过去了。

## 追问：一次返回的商品列表只有一项不合法怎么办？

1. 先看这个列表干什么用。别默认把坏数据滤掉就算成功。账单汇总少一项，总额可能就错了。推荐列表允许部分展示，可以把异常项隔开，但先确认这种降级产品同不同意。

2. 走部分成功的话，记下异常项位置和字段问题，只把通过校验的记录交给展示。页面要不要提示「有一部分不可用」，也得有约定。别一边展示过滤后的条数，一边还把服务端总数当成完全对得上。

3. 要求结果完整，整次解析就进格式错误状态，留下重试或反馈入口。单项错误、全部错误、分页中间出错都要测。尤其看过滤之后会不会误判已经到最后一页，别把数据问题弄成分页问题。
