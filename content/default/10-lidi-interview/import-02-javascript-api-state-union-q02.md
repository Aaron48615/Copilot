# 类型安全和接口真实返回不一致怎么办？

## 核心回答

1. 我会先明确类型声明只是前端对数据的约定，不是对接口内容的证明，编译通过也可能在读取字段时出错。比如声明商品价格是数字，服务端却返回字符串，代码里的乘法可能发生隐式转换，后续金额格式化也可能直接失败。

2. 在请求边界我会先把解析出的数据作为未知值处理，检查对象是否为空、字段是否存在以及嵌套内容是否符合要求。通过检查以后再构造内部成功状态，而不是直接断言成成功类型，因为断言并不会补上缺失字段或转换错误数据。

3. 我会把网络失败、业务拒绝和数据格式不符分开记录，因为对应的解决方式不一样，格式问题反复重试通常也不会好。如果需要兼容字符串价格，会在接口转换层显式处理并验证数值范围，不能让每个页面自行猜测接口的含义。

4. 遇到接口变更，我会先核对实际响应和约定，再同步调整校验、模拟数据与相关用例，不会只修改类型让报错消失。如果要补充线上排查信息，可以记录字段路径和接口版本，但应避免把完整用户数据直接写进日志，这属于改进方案。

## 追问：后端多返回一个字段应该让整个请求失败吗？

1. 不一定，多余字段是否允许取决于接口兼容约定，如果页面不依赖它，通常可以只提取自己需要的字段。强制拒绝所有新增字段会让后端正常扩展也破坏旧页面，所以严格程度需要结合业务目的确定。

2. 对必需字段缺失或字段类型改变，我会更谨慎，因为它们直接影响页面计算和展示。例如商品名称增加附加字段可以忽略，但价格从数值变成任意文本不能默默接受，应在边界明确报错或执行已约定的转换。

3. 转换到内部对象时只复制经过校验的字段，可以把外部扩展和内部模型隔开。验证用例需要分别包含额外字段、缺少必填字段和未知枚举值，确保兼容策略是有意识选择的，而不是某个断言偶然放行。

## 追问：一次返回的商品列表只有一项不合法怎么办？

1. 先看列表的业务用途，不能默认过滤坏数据就算成功，如果是账单汇总，少一项可能导致总额错误。对于允许部分展示的推荐列表，可以考虑隔离异常项，但要先明确这种降级是否符合产品要求。

2. 如果采用部分成功方案，我会记录异常项位置和字段问题，只把通过校验的记录交给展示层。页面是否提示部分内容不可用也应有约定，不能一边展示过滤后的数量，一边仍把服务端总数当作完全一致的结果。

3. 如果要求结果完整，就让整次解析进入格式错误状态，保留重试或反馈入口。测试要覆盖单项错误、全部错误和分页中的错误，特别检查过滤后是否误判已经到最后一页，避免把数据问题变成分页问题。
