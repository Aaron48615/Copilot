# 哪些状态不该放 Redux？

## 核心回答

1. 我不会按“用了 Redux 就把状态全放进去”来组织页面。只在一个组件中使用的展开状态、输入焦点或临时悬停，通常留在本地；把它们全局化会增加 action 和订阅，也让其他页面有机会依赖无关的细节。

2. 可以从已有状态算出的数据一般也不再保存一份，例如商品列表的总价、已选数量或过滤结果。通过 selector 计算能减少同步负担，否则修改商品后忘记更新总价，store 本身就会同时存在两个不同答案。

3. DOM 节点、图表实例、Promise、定时器句柄等通常不适合进入 Redux state。它们不是便于序列化和回放的业务数据，可以放在 ref 或外部资源管理逻辑中；state 只保存驱动界面需要的状态，比如是否加载成功。

4. 服务端数据要考虑缓存和失效机制，而不是每个接口都手写普通 slice。若项目已使用 RTK Query，可以利用它管理服务端缓存；Redux 并非不能存接口结果，关键是不要让多个系统同时维护同一份数据又没有明确归属。

5. 我会给每份状态问两个问题：谁需要读它，离开当前界面后是否还应存在。比如上传进度可能只属于当前任务面板，已经上传成功的附件编号却需要后续提交使用；先确定这些差异，再选择本地或共享存储，比按数据大小或变量数量判断更可靠。

## 追问：搜索词应该放本地、URL 还是 Redux？

1. 如果只是当前输入框的未提交文字，放本地 state 通常最直接。按键无需通知整个应用，也可以让用户修改到一半而不立即改变已展示的列表条件，这有助于区分草稿和已执行的搜索。

2. 如果搜索结果需要分享、刷新恢复或浏览器后退还原，已确认的筛选条件适合体现在 URL 中。组件从 URL 解析条件，并校验页码等参数，不能直接信任任意 query 字符串就是有效业务值。

3. 多个相距较远的组件需要同时编辑共享条件，且 URL 不适合承担全部交互状态时，再考虑全局 store。仍应确定一个主要来源，避免本地、URL 和 Redux 各存一份，每次更新还要互相写回。

## 追问：为什么把整个接口响应放进 store 也可能有问题？

1. 接口响应可能包含页面不需要的内部字段或很大的嵌套结构，完整保存会扩大订阅和调试成本。应先明确页面要用的数据，避免把临时请求对象、错误实例和非序列化句柄一起塞入 state。

2. 同一个实体可能在列表和详情里各出现一份，分别更新容易不同步。可以按业务 id 组织实体，或使用已有查询缓存管理它们的失效关系，不能只靠复制接口返回的形状就认为状态设计完成。

3. 还要约定何时清理，特别是退出登录和切换账号。缓存并不只是“以后不用再请求”，个人数据需要按身份隔离；否则下一位用户可能短暂看到上一位用户的内容，即使后续请求最终覆盖了它。
