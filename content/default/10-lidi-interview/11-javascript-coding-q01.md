# 手写一个防抖函数。

## 核心回答

1. 先写尾部触发：连续调用就重新计时，停够等待时间才跑最后一次。比如输入框连打三个字，安静下来才去查，打字过程中不承诺也会定期查。

2. 定时器放在外层闭包里，返回普通函数，才能接到调用时的 `this` 和参数。下面带取消能力，假设 `fn` 是函数、`delay` 是合理的非负等待时间。

    ```js
    function debounce(fn, delay) {
      let timer = null;
      function debounced(...args) {
        if (timer !== null) clearTimeout(timer);
        timer = setTimeout(() => {
          timer = null;
          fn.apply(this, args);
        }, delay);
      }
      debounced.cancel = () => {
        if (timer !== null) clearTimeout(timer);
        timer = null;
      };
      return debounced;
    }
    ```

3. 每次调用先清旧定时器，新回调留下这次的参数，所以真正跑的是最后一次那组数据。回调里先把 `timer` 置空再跑 `fn`，这样就算 `fn` 里面又调了防抖，也不会把刚建好的定时器记录盖掉。

4. `cancel` 用来丢掉还没执行的那次。组件卸掉时可以调它，同时把事件监听也摘了。防抖函数要在合适的初始化位置建一次；每次输入都重新跑 `debounce`，多个独立闭包就对不上上一次的等待。

5. 这段没有首部触发、最大等待，也没有立刻执行待处理任务。也不会同步把 `fn` 的返回值交出来。`fn` 要是返回 Promise，拒绝得它自己或专门的异步封装去处理，外层这次调用的 `try/catch` 抓不到以后才发生的错误。

## 追问：防抖已经减少请求，为什么还可能出现旧结果覆盖新结果？

1. 防抖取消的是还没开始的定时器，已经发出去的请求它管不着。用户先停一下触发查询，随后又输入另一个词，两个请求都可能在路上，旧的如果后回来，就把新结果盖掉了。

2. 新查询开始时记一个递增序号，只允许当前最新序号往页面上写；请求能取消的话再配上 `AbortController`。取消请求和检查结果还有效，可以一起用，别的异步步骤才不会继续交过期数据。

3. 清空输入时也得让旧请求失效，不能只清列表、取消计时器。组件已经离开页面，回调同样不该再改它的状态。这些是查询生命周期的事，不能全塞进防抖函数本身。

## 追问：怎样验证防抖的参数、上下文和取消行为？

1. 用可控的假定时器推等待过程：零时刻调一次，等待结束前再调一次，确认原来那个触发点没跑，最后一次满等待时间后只执行一次。不用靠真实计时误差来判断对不对。

2. 让对象以方法形式调这个防抖函数，连续传入不同参数，看最终函数读到的是原对象的 `this` 和最后一组参数。再造两个独立防抖实例，确认其中一个重置定时器不会取消另一个的任务。

3. 再看调用后立刻 `cancel`、重复取消、取消后再调用，必要时加上函数内部再次触发自身。这些都能对着代码跑；只演示一次正常输入，清不掉、重入对不对都看不出来。
