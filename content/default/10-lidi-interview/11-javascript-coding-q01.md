# 手写一个防抖函数。

## 核心回答

1. 我先实现尾部触发的防抖：连续调用时重新计时，停止调用达到等待时间后，只执行最后一次。比如输入框连续输入三个字符，只在最后一次输入后的安静期结束时触发查询，不承诺用户持续输入期间也定期执行。

2. 定时器要放在外层闭包里，返回普通函数以接收调用时的 `this` 和参数。下面是带取消能力的教学实现，假设 `fn` 是函数、`delay` 是合理的非负等待时间。

    ```js
    function debounce(fn, delay) {
      let timer = null;
      function debounced(...args) {
        if (timer !== null) clearTimeout(timer);
        timer = setTimeout(() => {
          timer = null;
          fn.apply(this, args);
        }, delay);
      }
      debounced.cancel = () => {
        if (timer !== null) clearTimeout(timer);
        timer = null;
      };
      return debounced;
    }
    ```

3. 每次调用清理旧定时器，新回调保留本次参数，因此实际执行的是最后一次调用的数据。回调中先把 `timer` 清空再运行 `fn`，这样即使 `fn` 内再次调用防抖函数，也不会把新建立的定时器记录覆盖掉。

4. `cancel` 负责放弃尚未执行的调用，组件卸载时可以调用它，并同时移除事件监听。防抖函数应该在合适的初始化位置创建一次，如果每次输入都重新执行 `debounce`，多个独立闭包就无法共同取消前一次等待。

5. 这段实现没有首部触发、最大等待时间或立即执行待处理任务的功能，也不会同步返回 `fn` 的执行结果。若 `fn` 返回 Promise，需要它自身或专门的异步封装处理拒绝，不能以为外层调用的 `try/catch` 会捕获未来的错误。

## 追问：防抖已经减少请求，为什么还可能出现旧结果覆盖新结果？

1. 防抖取消的是还没开始的定时器，无法自动取消已经发出的请求。用户输入一个词并等待触发查询，随后又输入另一个词，两个请求都可能在途，较旧的请求如果最后返回就可能覆盖新结果。

2. 我会在新查询开始时记录递增序号，只允许当前最新序号写入页面；能够取消的请求也可以配合 `AbortController`。取消请求和检查结果是否仍有效可以一起使用，避免其他异步步骤继续提交过期数据。

3. 清空输入时也需要让旧请求失效，而不能只清空列表和取消计时器。如果组件已经离开页面，回调同样不应再更新它的状态；这些属于查询生命周期处理，不能全部归到防抖函数本身的职责里。

## 追问：怎样验证防抖的参数、上下文和取消行为？

1. 我会用可控的假定时器推演等待过程：在零时刻调用一次，等待时间结束前再调用一次，确认原来的触发点没有执行，最后一次调用满等待时间后只执行一次。这样不需要依赖真实计时误差判断正确性。

2. 让对象以方法形式调用防抖函数，并连续传入不同参数，检查最终函数读到原对象的 `this` 和最后一组参数。再创建两个独立防抖实例，确认其中一个重置定时器不会取消另一个的任务。

3. 我还会检查调用后立即 `cancel`、重复取消和取消后再次调用的行为，必要时加上函数内部再次触发自身的场景。这些是可以针对代码执行的验证项，不能只演示一次正常输入就认为清理和重入都正确。
