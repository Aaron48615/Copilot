# 为什么不直接用对象？

## 核心回答

1. 普通对象可以实现某些限定键类型的缓存，但单靠对象属性顺序不适合直接表达 LRU。LRU 要同时完成按键查询和记录最近访问顺序，Map 提供现成的键值操作和插入顺序，手写时更容易把这两个要求对应起来。

2. 我不会说对象完全无序，因为普通对象的自有属性有明确的枚举规则，其中整数索引键优先按数值排列。比如先写键“10”再写“2”，枚举时可能先得到“2”，这与写入先后不同，直接删除枚举的第一项可能淘汰错对象。

3. 对象属性键主要是字符串和 Symbol，把普通对象作为键会发生键转换，不适合按对象身份区分缓存项。Map 可以直接保存对象键，也能区分数字 1 和字符串“1”；但两个内容相同的新对象仍是不同键，不能把它当成按内容查询。

4. 普通对象还要处理继承属性和特殊键，例如用 `key in cache` 可能把原型上的字段误判成命中。`Object.create(null)` 配合自有属性判断可以减少这类问题，但不会自动提供最近使用顺序和 size，仍然需要维护额外结构。

5. Map 的已有键直接 set 不会自动变成最新，所以命中和更新时仍要先 delete 再 set。若题目要求经典算法结构，我会使用哈希表加双向链表；这里选择 Map 是实现简洁，不能进一步宣称标准保证它每一次操作都是严格 O(1)。

## 追问：Object.create(null) 能不能代替 Map？

1. 如果键确定都是字符串，它可以作为无原型字典，避免继承到 `toString` 之类的属性。判断命中仍应该使用明确的自有属性检查，不根据值的真假判断，因为缓存值可能合法地是 0、false 或 undefined。

2. 不过它仍遵循对象属性键规则，数字键会变为字符串，整数索引键的枚举顺序也不是任意插入顺序。要实现可靠 LRU，我还需要单独维护双向链表或其他访问顺序结构，并维护条目数量，不能只靠遍历属性找最旧项。

3. 所以“能不能实现”和“是否更适合这道题”是两回事，限定输入下当然能实现。面试中我会说明额外代码的责任，再选择较容易验证的 Map；如果已有系统固定使用字符串字典，也可以在其上增加链表，不必为了形式强行替换。

## 追问：用对象作为 Map 键，会不会导致相同请求无法命中？

1. 会，假如每次查询都新建 `{ page: 1 }`，这些对象内容相同但引用不同，在 Map 里就是不同键。缓存不会自动比较字段，所以我会先确定业务需要的是对象身份缓存，还是相同查询条件复用结果。

2. 对请求参数缓存，我会从影响结果的字段生成稳定键，例如用户作用域、关键词、页码和排序方式。不能随便漏掉一个条件，也不能默认任意对象 JSON 字符串化都能得到可靠规范键，因为字段顺序和特殊值处理需要约定。

3. 如果本来就是给同一个对象附加计算结果，按对象身份缓存才符合目标。还要记住 Map 强持有对象键和值，LRU 容量只限制条目数，不限制单条数据体积；注销或切换作用域时是否清理，也要按业务隔离要求处理。
