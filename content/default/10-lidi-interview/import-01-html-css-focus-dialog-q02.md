# ARIA 能解决所有问题吗？

## 核心回答

1. ARIA 解决不了所有可访问性问题。它主要让辅助技术知道元素的名称、角色、状态和关系。普通 DOM 行为不会自动改，视觉反馈也不会自动补。一个 `div` 被宣布成按钮，不代表已经能 Tab 访问、用空格激活，或者正确处理禁用。

2. 所以先用原生语义：动作用 `button`，跳转用带 `href` 的链接，表单用 `label` 关联控件。原生元素已经带上的行为通常更完整，再按需要补图标名称或错误描述，比从一个空白 `div` 开始模拟所有交互靠谱。

3. 自定义组件要把语义、键盘、焦点和真实状态一起做。给弹窗标 `aria-modal`，不会自动禁止背景点击，也不会限制 Tab。给展开按钮写 `aria-expanded`，面板开合时也得跟着改。错误或过期的 ARIA 会让用户听到跟界面相反的信息。

4. 验证也不能只靠自动检查没有报错。工具能发现缺名称这类问题，流程顺不顺、读屏会不会重复、焦点回不回合理位置，得人工把任务走完才看得出来。从打开、操作、报错到关闭走一遍，问题落到具体使用过程上，别只统计属性数量。

5. 视觉上还要有足够清楚的焦点和错误提示，比如校验失败别只把边框改成红色。辅助技术能读到状态，普通用户也得看见原因。语义补充和可见反馈应对上，别做成两套互不相干的界面。

## 追问：给 div 加 role="button" 后还缺什么？

1. 首先是键盘够不够得到、怎么激活。要有合适的 `tabindex`，并处理用户预期的 Enter 和空格。空格还涉及默认页面滚动，以及按下、抬起时机。随便监听一次 `keydown`，可能跟原生按钮体验不同，也可能重复触发。

2. 其次是清楚的可访问名称、可见焦点和禁用状态。`aria-disabled` 只声明状态，不自动拦截点击。代码仍要拦住业务动作，视觉提示和实际状态也得一致，别看起来灰了却还能提交。

3. 没有特殊结构限制，直接改成 `button`，再用 CSS 调外观。手动代码少了，不同输入方式之间也不容易行为不一致。自定义角色得有明确理由，别只是因为 `div` 更好写样式。

## 追问：自动化可访问性检查通过，为什么还要人工测试？

1. 自动工具通常检查能静态判断的条件，比如名称缺不缺、属性值合不合法，但理解不了业务目标。按钮虽然有名称，名称写成错误动作，或者点完焦点消失，页面仍可能通过一部分规则。

2. 用键盘完成一次实际任务，看顺序、焦点轮廓和错误恢复；再用读屏听宣布的名称、状态和上下文。提交失败后知不知道哪个字段有问题，得连续操作，单张页面快照不够。

3. 人工测试也不是随便点一遍。围着典型任务固定步骤，空状态、异步变化、关闭返回都要覆盖。自动检查尽早发现常见遗漏，人工检查确认人能理解并做完流程，两边提供的证据不一样。
