# ARIA 能解决所有问题吗？

## 核心回答

1. ARIA 不能解决所有可访问性问题，它主要让辅助技术知道元素的名称、角色、状态和关系。它不会自动改变普通 DOM 行为，也不会补齐视觉反馈；一个 div 被宣布为按钮，不代表它已经能被 Tab 访问、用空格激活或正确处理禁用。

2. 所以我会先使用原生语义，例如动作使用 button、跳转使用带 href 的链接、表单用 label 关联控件。原生元素已经提供的行为通常更完整，再根据需要补充图标名称或错误描述，比从一个空白 div 开始模拟所有交互更可靠。

3. 自定义组件需要语义、键盘、焦点和真实状态一起实现。比如给弹窗标 aria-modal，并不会自动禁止背景点击或限制 Tab；给展开按钮写 aria-expanded，也必须随着面板开合更新。错误或过期的 ARIA 会让用户得到与界面相反的信息。

4. 验证也不能只靠自动检查没有报错。工具能发现缺少名称等一部分问题，但流程顺不顺、读屏是否重复、焦点是否回到合理位置，需要人工完成任务才能看出来。我会从打开、操作、报错到关闭走一遍，把问题落到具体使用过程，而不是只统计属性数量。

5. 视觉上还需要足够清晰的焦点与错误提示，例如不能只把边框改成红色表达校验失败。即使辅助技术能读到状态，普通用户也需要看到原因，语义补充与可见反馈应该相互对应，而不是服务于两套互不相干的界面。

## 追问：给 div 加 role="button" 后还缺什么？

1. 首先是键盘可达性和激活行为，要有合适的 tabindex，并处理用户预期的 Enter 和空格操作。空格还涉及默认页面滚动以及按下、抬起时机，随便监听一次 keydown 可能与原生按钮体验不同或导致重复触发。

2. 其次是清楚的可访问名称、可见焦点和禁用状态。aria-disabled 只声明状态，不自动拦截点击；代码仍需要阻止业务动作，同时让视觉提示与实际状态一致，避免看起来灰了却还能提交。

3. 因此如果没有特殊结构限制，我会直接改成 button，再用 CSS 调整外观。它不仅减少手动代码，也降低不同输入方式之间行为不一致的风险；自定义角色应有明确理由，不能只是因为 div 更容易写样式。

## 追问：自动化可访问性检查通过，为什么还要人工测试？

1. 自动工具通常检查可静态判断的条件，例如名称是否缺失、属性值是否有效，但无法完全理解业务目标。一个按钮虽然有名称，如果名称写成错误动作，或点击后焦点消失，页面仍可能通过部分规则检查。

2. 我会用键盘完成一次实际任务，观察顺序、焦点轮廓和错误恢复，再用读屏检查宣布的名称、状态和上下文。比如提交失败后是否知道哪个字段有问题，这需要连续操作，单张页面快照不够。

3. 人工测试也不是随便点一遍，可以围绕典型任务固定步骤，并覆盖空状态、异步变化和关闭返回。自动检查负责尽早发现常见遗漏，人工检查负责确认人能理解并完成流程，两者提供不同的证据。
