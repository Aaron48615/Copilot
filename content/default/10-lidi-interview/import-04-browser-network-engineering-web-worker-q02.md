# SharedWorker 和普通 Worker 有什么区别？

## 核心回答

1. 普通 Dedicated Worker 通常由一个页面上下文创建并与它通信，适合这个页面自己的数据处理。SharedWorker 可以被符合共享条件的多个上下文连接，通过多个 MessagePort 接收消息，适合确实需要跨标签共享计算或连接的场景。

2. 创建 SharedWorker 不代表所有网页都可以访问，同源以及脚本身份等条件需要匹配，浏览器的存储分区和兼容策略也可能影响共享。不能只说域名一样就永远共用同一实例，应按目标浏览器实际验证。

3. 通信方式上，Dedicated Worker 常直接使用 worker.postMessage，SharedWorker 则处理 connect 事件并通过端口通信。页面采用事件监听方式时要正确启动端口，协议还应包含请求标识和来源范围，才能把结果返回给正确的调用方。

4. 共享状态会增加管理成本，例如两个标签同时更新同一任务、一个退出登录而另一个仍连接、某个标签关闭后端口如何释放。SharedWorker 也不是永久服务，浏览器可能结束它，关键数据仍要有合适持久存储与恢复方式。

5. 我会先确认是否真的需要共享。如果只是广播设置变化，BroadcastChannel 等方式可能更简单；需要共享任务再考虑 SharedWorker，并提供支持检测与降级，不能为了减少一个实例就让普通功能依赖不确定的后台寿命。

## 追问：多个标签共享连接，怎样把响应发回正确标签？

1. 我会为每个连接端口维护有限的客户端信息，消息带请求标识，Worker 保存请求与端口的对应关系。服务端回复后只发给相应端口，需要广播的通知再按明确规则分发，不能默认所有页面都应该收到所有结果。

2. 页面关闭或不再需要服务时应释放端口和订阅，超时请求也要清理映射。否则长时间使用会积累失效客户端，或者把旧请求结果发到已经切换账号的页面，产生内存和数据隔离问题。

3. 验证时同时开两个标签执行不同任务，再关闭其中一个并重连。结果归属、退出登录和未完成请求的处理都应正确；减少网络连接只是收益之一，不能因此忽略多客户端协议带来的复杂性。

## 追问：不支持 SharedWorker 时，怎样降级？

1. 先做能力检测，确认当前浏览器和上下文允许使用，再选择方案。若共享只是性能优化，可以每个页面使用自己的 Dedicated Worker 或连接；若涉及业务唯一任务，就不能直接多开实例而不考虑重复执行。

2. 可以让服务端按任务标识幂等处理，页面之间用支持的消息机制协调显示，但这些机制也有各自生命周期限制。降级方案应从业务正确性出发，不能用 localStorage 的一个布尔值冒充可靠的跨标签分布式锁。

3. 我会测试支持与不支持两种路径，确保功能、取消和账号隔离保持一致。若某项能力确实无法可靠降级，就给出明确限制，而不是悄悄失败后留下一个永远等待共享实例返回结果的界面。
