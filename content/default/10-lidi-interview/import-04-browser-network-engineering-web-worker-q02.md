# SharedWorker 和普通 Worker 有什么区别？

## 核心回答

1. 普通 Dedicated Worker 通常由一个页面上下文创建，跟它通信，适合这个页面自己的数据处理。SharedWorker 可以被符合共享条件的多个上下文连接，通过多个 MessagePort 收消息，适合确实需要跨标签共享计算或连接的场景。

2. 创建 SharedWorker 不代表所有网页都能访问。同源、脚本身份这些条件要匹配，浏览器的存储分区和兼容策略也可能影响共享。域名一样就永远共用同一实例，这话不稳，按目标浏览器实际验证。

3. Dedicated Worker 常直接 `worker.postMessage`。SharedWorker 则处理 `connect` 事件，通过端口通信。页面用事件监听时要正确启动端口。协议里带请求标识和来源范围，结果才能回到正确的调用方。

4. 共享状态管理成本更高。两个标签同时更新同一任务、一个退出登录另一个还连着、某个标签关掉后端口怎么释放，都要设计。SharedWorker 也不是永久服务，浏览器可能结束它。关键数据仍要有合适的持久存储和恢复方式。

5. 是不是真的需要共享，先确认。只是广播设置变化，BroadcastChannel 这类方式可能更简单。需要共享任务再考虑 SharedWorker，并提供支持检测和降级。为了少一个实例，让普通功能依赖不确定的后台寿命，不划算。

## 追问：多个标签共享连接，怎样把响应发回正确标签？

1. 每个连接端口维护有限的客户端信息，消息带请求标识，Worker 保存请求和端口的对应关系。服务端回复后只发给相应端口。需要广播的通知再按明确规则分发。默认所有页面都该收到所有结果，会串。

2. 页面关闭或不再需要服务时，释放端口和订阅，超时请求也要清映射。长时间用会攒失效客户端，或者把旧请求结果发到已经切了账号的页面，内存和数据隔离都会出问题。

3. 同时开两个标签执行不同任务，再关掉其中一个并重连。结果归属、退出登录、未完成请求的处理都要对。少一条网络连接只是收益之一，多客户端协议带来的复杂性不能忽略。

## 追问：不支持 SharedWorker 时，怎样降级？

1. 先做能力检测，确认当前浏览器和上下文允许使用，再选方案。共享只是性能优化，每个页面可以用自己的 Dedicated Worker 或连接。涉及业务唯一任务，就不能直接多开实例、不考虑重复执行。

2. 可以让服务端按任务标识做幂等，页面之间用支持的消息机制协调显示。这些机制也有各自的生命周期限制。降级从业务正确性出发。`localStorage` 里一个布尔值，当不了可靠的跨标签分布式锁。

3. 支持和不支持两条路径都测，功能、取消、账号隔离保持一致。某项能力确实无法可靠降级，就把限制说清楚。悄悄失败后留下一个永远等待共享实例返回结果的界面，用户会卡住。
