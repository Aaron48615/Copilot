# 如何验证没有超出上限？

## 核心回答

1. 看任务执行过程，别只看最后结果数组，因为最终成功看不出中间是不是同时启动过太多任务。任务真正开始时增加 active，结束时减少，记下 peak。下面的包装把同步抛错和异步拒绝都放在 finally 的清理范围内。

   ```js
   let active = 0, peak = 0;
   const wrap = task => async () => {
     active++;
     peak = Math.max(peak, active);
     try { return await task(); }
     finally { active--; }
   };
   ```

2. 准备五个可手动完成的任务，limit 设成二，任何任务完成前确认只启动了两个。然后只释放其中一个，等第三个的启动信号，确认新任务及时补位且 active 仍为二。真实延迟不适合承担这个时序控制。

3. peak 不超过上限之外，还要确认有任务可执行时确实用了允许的并发度。永远串行的错误实现也能满足 peak 小于等于二，所以初始启动数量、空位出现后的补位、每个任务只执行一次，都要检查。

4. 打乱完成顺序，看返回结果仍对应输入下标，并测空输入、上限一、上限大于任务数、非法上限。错误用例按接口约定检查继续执行还是停止取任务，「收集所有失败」和「遇错立即返回」别混在同一套预期里。

5. 全部已启动任务结束后 active 回到零，没有遗留拒绝或等待；支持取消的话，还要确认取消后不再启动排队任务。测试包装必须覆盖任务的完整 Promise 生命周期，否则任务提前返回、内部请求还在跑时，计数只是表面正确。

## 追问：怎样证明任务完成后会立即补位，而不是整批等待？

1. 让最先启动的 A 保持 pending，只完成同批的 B，再等 C 的启动信号。C 能在 A 完成之前启动，说明空位被用上了；一定要等 A 完成才启动 C，就暴露了按整批等待的实现。

2. 这个测试不靠「C 应在十毫秒内启动」这种真实时间判断，而是用可控 Promise 和事件记录表达先后关系。启动信号由任务函数实际执行时产生，不能由测试自己假装通知，否则证明不了调度器真的调了任务。

3. 观察完补位后，释放剩余任务并等池子结束，再核对记录里没有重复启动，也没有超过上限。等待信号本身应有测试框架的超时限制，避免实现不补位时永久挂住，但这个超时只是失败保护，不是用来制造完成顺序。

## 追问：任务失败时，计数归零就代表实现正确吗？

1. 不代表。计数归零只说明被统计的任务结束了，还要看失败策略有没有履行。采用收集结果时，一项失败后其他排队任务应继续执行，返回结果在对应下标记下拒绝原因；直接把失败项弄丢，计数仍可能完全正常。

2. 采用停止取任务时，先让一个任务失败，再检查新的任务没有启动，并按约定等待或取消已运行任务。同步 throw 和返回拒绝 Promise 都要覆盖，因为只在 then 的成功回调里释放空位，失败就可能让整个队列卡住。

3. 再看调用方收到失败的时刻和 active 的关系。接口约定立即拒绝，返回时 active 可能仍大于零，并不自动算错；但后台任务仍要有人处理结果和清理资源，别把外层 Promise 结束误当成所有任务都已停止。
