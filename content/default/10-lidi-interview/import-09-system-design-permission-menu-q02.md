# 权限矩阵怎么测试？

## 核心回答

1. 我会先把业务规则写成明确的权限矩阵，列出角色、资源、操作和预期结果。比如查看者能读但不能编辑，编辑者只能修改指定范围的记录；预期结果要由规则独立确定，不能直接调用被测权限函数来生成答案。

2. 测试维度不只角色，还要覆盖资源归属、租户和状态。同样是编辑者，自己的草稿、别人的草稿和已归档记录可能权限不同；如果只拿一个管理员和一个普通用户测试，很容易漏掉同级用户之间的越权。

3. 前端测试检查菜单是否出现、按钮是否可用，以及直接输入受保护 URL 时的结果。还要覆盖刷新页面时权限未加载、加载失败和未知路由，确保不会短暂展示敏感内容，也不会把所有错误都跳回登录页。

4. 接口测试直接发起读取、更新和删除请求，验证拒绝操作没有实际副作用。不能因为 E2E 看不到按钮就认定接口安全，也不能只检查状态码；批量操作、导出和附件下载都可能走不同入口，需要按范围覆盖。

5. 最后测试状态变化，包括会话过期、角色撤销、切换账号和切换租户，确认旧权限及业务缓存不会继续复用。规则变更后，我会把新增情况加入回归用例，并记录覆盖范围和执行结果。比如撤销角色后再次访问旧链接，前端提示和服务端拒绝都应符合新的权限规则。

## 追问：角色和页面很多，怎么控制测试组合数量？

1. 我会先按权限行为归类，例如多个只读角色若在某类资源上规则完全一致，可以选代表用例。归类依据是具体规则，而不是角色名字相似；一旦某个角色有额外数据范围，就需要拆开验证。

2. 高风险的写入、删除、跨租户和批量接口保留明确的允许与拒绝用例，不能为了减少组合全部抽样。对于重复的展示逻辑，可以用参数化测试复用执行过程，同时保留每一行独立的预期结果和失败说明。

3. 新增规则优先增加受影响边界，例如从全量可读改为仅本人可读，就补同角色不同拥有者的用例。组合测试可以辅助发现交互问题，但不能取代必须拒绝的关键案例，也不能仅凭覆盖率数字判断权限正确。

## 追问：怎样测试权限在页面打开期间被撤销？

1. 先让用户以有效权限打开页面，再通过测试环境中的权限管理能力撤销对应权限，保持页面不刷新。之后点击原来显示的操作，确认服务端按新规则拒绝，而不是继续相信页面加载时获得的权限快照。

2. 检查前端收到拒绝后是否更新按钮、菜单和当前页面状态，并确认没有把原请求无限重试。若产品依赖权限版本轮询或推送，还要分别覆盖通知正常到达和通知暂时丢失，授权正确性不能依赖通知必达。

3. 撤销已经发生后，再检查业务数据、缓存和其他标签页的表现，明确失效时间的约定。如果服务端使用有有效期的权限缓存或令牌，需要验证实际撤销窗口，不能未经确认就承诺权限变化在所有位置立即生效。
