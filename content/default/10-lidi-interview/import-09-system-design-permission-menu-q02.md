# 权限矩阵怎么测试？

## 核心回答

1. 业务规则写成明确的权限矩阵：角色、资源、操作、预期结果。查看者能读但不能编辑，编辑者只能改指定范围的记录。预期结果由规则独立确定，别直接调被测权限函数来生成答案。

2. 测试维度不只角色，还要覆盖资源归属、租户、状态。同样是编辑者，自己的草稿、别人的草稿、已归档记录，权限可能不同。只拿一个管理员和一个普通用户测，同级用户之间的越权很容易漏。

3. 前端测试查菜单出不出现、按钮能不能用，以及直接输入受保护 URL 时的结果。刷新页面时权限未加载、加载失败、未知路由也要覆盖。别短暂展示敏感内容，也别把所有错误都跳回登录页。

4. 接口测试直接发读取、更新、删除请求，验证拒绝操作没有实际副作用。E2E 看不到按钮，认定不了接口安全。只查状态码也不够。批量操作、导出、附件下载可能走不同入口，按范围覆盖。

5. 最后测状态变化：会话过期、角色撤销、切换账号、切换租户，旧权限和业务缓存别继续复用。规则变更后，新增情况加进回归用例，覆盖范围和执行结果记下来。撤销角色后再访问旧链接，前端提示和服务端拒绝都该符合新规则。

## 追问：角色和页面很多，怎么控制测试组合数量？

1. 先按权限行为归类。多个只读角色在某类资源上规则完全一致，可以选代表用例。归类依据是具体规则，不是角色名字像。某个角色有额外数据范围，就拆开验。

2. 高风险的写入、删除、跨租户、批量接口，保留明确的允许和拒绝用例。别为了减少组合全部抽样。重复的展示逻辑可以用参数化测试复用执行过程，每一行独立的预期结果和失败说明还是要留。

3. 新增规则优先加受影响的边界。比如从全量可读改成仅本人可读，就补同角色、不同拥有者的用例。组合测试能帮忙发现交互问题，替不了必须拒绝的关键案例。覆盖率数字也判断不了权限对不对。

## 追问：怎样测试权限在页面打开期间被撤销？

1. 先让用户以有效权限打开页面，再通过测试环境里的权限管理能力撤销对应权限，页面不刷新。之后点原来显示的操作，确认服务端按新规则拒绝，别继续相信页面加载时拿到的权限快照。

2. 前端收到拒绝后，按钮、菜单、当前页面状态有没有更新，原来的请求有没有被无限重试。产品依赖权限版本轮询或推送，通知正常到达和暂时丢失都要覆盖。授权对不对，不能依赖通知必达。

3. 撤销已经发生后，再查业务数据、缓存、其他标签页，失效时间的约定说清楚。服务端如果用有有效期的权限缓存或令牌，要验实际撤销窗口。未经确认，别承诺权限变化在所有位置立即生效。
