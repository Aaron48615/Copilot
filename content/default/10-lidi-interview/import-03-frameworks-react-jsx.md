# JSX 是什么？浏览器能直接运行吗？

## 核心回答

1. JSX 是 JavaScript 的语法扩展，用类似 HTML 的形式描述界面，不是浏览器原生支持的 HTML 模板。项目需要通过 Babel、TypeScript 或构建工具配置的转换器，把它转换成普通 JavaScript 后再运行。

2. 经典转换会生成 React.createElement 调用，自动 JSX 转换使用 jsx-runtime 提供的函数。是否需要手动引入 React 取决于转换配置，不能只按 React 版本断言；这些调用产生元素描述，真正修改 DOM 由渲染器完成。

3. 花括号里放表达式，比如三元条件或数组 map；if 和 for 这类语句可以先在函数体执行，再返回 JSX。小写标签通常表示原生元素，大写标识符表示组件；需要成组返回时可以使用 Fragment，不必为了语法增加多余 div。

4. JSX 采用 JavaScript 的属性约定，例如 className 和事件函数 onClick，也要求标签正确闭合。普通文本插值会被转义，富文本则需要显式的 HTML 插入方式；这能减少误把文本当标签执行，但不意味着所有动态 URL 或第三方 HTML 都自动安全。

5. 列表和条件最终也只是表达式结果，返回数组时仍需给业务项稳定身份。比如搜索结果从多个条目中生成按钮，可以把筛选逻辑先写清楚再映射元素；不要为了把所有代码塞进花括号而写很长的嵌套条件，否则结构虽然能编译，维护时却不容易判断每种状态显示什么。

## 追问：JSX 编译后是对象，为什么不能直接当 DOM 操作？

1. 元素描述记录类型、props 和子元素等信息，本身不是浏览器中的节点。创建 `<button />` 不代表按钮已经插入页面，因此不能直接对这个描述调用 focus 或读取 getBoundingClientRect。

2. React 根据元素描述计算需要提交的变化，完成提交后真实节点才可通过 ref 获取。需要点击后聚焦输入框时，我会操作 inputRef.current，而不是试图保存一份 JSX 并把它当 HTMLInputElement 使用。

3. 这种区分也解释了为什么渲染应保持纯粹：构造描述可能重复发生，而用户能看到的 DOM 变化在提交阶段完成。请求、订阅或第三方实例创建不应混在普通 JSX 计算中随意执行。比如先构造一段输入框描述再隐藏它，浏览器可能从未创建对应节点，描述存在不代表节点已经可访问。

## 追问：为什么 count && <Badge /> 在 count 为零时会显示 0？

1. JavaScript 的 && 返回某个操作数，不会自动转换成布尔结果。count 为 0 时表达式结果就是数字 0，而 React 会把数字作为可显示内容，所以屏幕上出现 0 并不是 Badge 被渲染出来了。

2. 如果业务意思是有数量才显示，可以写 `count > 0 && <Badge />`，或者使用明确的三元表达式。这样条件结果是布尔值，隐藏分支不会把原始数字意外带入界面，代码意图也更容易理解。

3. 我会同时考虑负数、未加载和空值的含义，而不是统一套 `!!count`。例如数量尚未返回时可能需要骨架，数量为零时需要“暂无消息”，这时三元分支或提前返回通常比一个 && 更清楚。同时要让空状态和加载状态有明确差别，避免用户分不清正在等待还是已经确认没有消息。
