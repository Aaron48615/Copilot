# 虚拟列表有什么代价？

## 核心回答

1. 虚拟列表只渲染看得见的那一段，外加一点缓冲，节点会少很多。屏幕外的项没有真实 DOM。页面查找、复制全部内容、有些读屏方式都会受影响。它不是把普通列表换皮，体验完全一样。

2. 高度是实际难点。行高固定还好办；带图片、折叠说明、多行文字，就要测量、修正偏移。估矮了，滚动会跳、会空一截、定位会偏。图片加载完、窗口变窄，以前量的高度也可能作废。

3. 行被复用或卸掉以后，里面的草稿、展开状态、输入焦点可能丢，也可能错位到另一行。要留的业务状态按稳定编号放在合适的地方，别只靠行组件自己的局部变量。提交表单也不能只读当前看得见的那几个输入框。

4. 键盘导航、滚到出错字段、选中后再定位，都要跟虚拟列表自己的接口配合。先让目标项进可渲染范围，再处理焦点，别对屏幕外节点直接 `focus`。有的场景分页更简单，阅读和填表也更稳。

5. 先确认瓶颈真是节点太多，再用虚拟化。用真实行内容测快滚、改尺寸、回到原来位置。已经下载的大数组、排序计算不会因为少画几行就自动变少。数据怎么取、怎么算，还是要单独看。

## 追问：动态高度列表怎样减少滚动跳动？

1. 还没量过的行给一个接近实际的估高，图片这些资源加载后再更新测量。估得太矮，补测时整段列表不停往下撑，滚动条和位置一直变，人没法稳定看同一条。

2. 更新高度时尽量锚住当前看得见的那一块，前面某行变高，别把正在看的行顶走。用现成列表工具，要搞清它的测量缓存、重新计算、滚动定位接口。自己改 DOM 高度，别指望内部偏移自动对。

3. 窄屏换行、图片慢加载、展开详情这些会改行高的情况都要测。行结构特别复杂、精确恢复很贵，也可以分页，或限制展开区域。不必为了用上虚拟列表，接受一套很难维护的定位。

## 追问：虚拟列表的键盘焦点应该怎么管理？

1. 屏幕外没有真实节点，不能从完整数据的下标推断一定能聚焦。先用列表的滚动或定位接口把目标项滚进渲染范围，等节点出来再移焦点，并用稳定业务编号确认目标没变。

2. 正在输入的那一行滚出可见区域，也要有策略。有的组件会把正在编辑的行留着，有的把草稿存外层、回来再恢复。不管哪种，按一下方向键不该突然丢输入位置，或把字写到另一项上。

3. 纯键盘走首项、末项、跨窗口移动、错误定位，读屏能不能说清项目位置。任务主要是长表单编辑，分页或分组可能更合适。性能方案要撑得住真实操作，别只追滚动帧率。
