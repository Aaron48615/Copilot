# 虚拟列表有什么代价？

## 核心回答

1. 虚拟列表只渲染可视区域和少量缓冲项，能显著减少节点数量，但代价是屏幕外项目不再持续保有真实 DOM。浏览器页面查找、复制全部内容和某些无障碍阅读方式会受到影响，不能把它理解成完全没有体验差异的列表替换。

2. 高度计算是一个实际难点。固定行高比较简单，包含图片、折叠说明或多行文字时需要测量和修正偏移；高度估算不准可能出现滚动跳动、空白或定位偏差，图片加载和窗口宽度改变也会让之前测量失效。

3. 行实例被复用或卸载后，内部草稿、展开状态和输入焦点可能丢失或错位。需要保留的业务状态应按稳定编号存在合适位置，不能只依赖行内局部变量；表单提交也不能只读取当前可见的几个 DOM 输入框。

4. 键盘导航、滚动到错误字段和选中后定位都需要与虚拟列表接口配合。先让目标项进入可渲染范围，再处理焦点，不能对屏幕外节点直接调用 focus；有些场景分页反而更简单，也更适合稳定阅读和表单操作。

5. 我会先确认瓶颈来自节点体量，再采用虚拟化，并用真实行内容测试快滚、尺寸变化和回到原位置。它不会自动减少已经下载的大数组或排序计算，数据获取和计算仍要分别优化，不能因为渲染行数减少就认为整个页面所有性能问题都解决了。

## 追问：动态高度列表怎样减少滚动跳动？

1. 可以给尚未测量的行合理估算高度，并在图片等资源加载后更新测量结果。估算应接近实际内容，明显过小会在补测时不断扩展整段列表，用户看到滚动条和位置连续变化，而不是稳定地浏览同一条记录。

2. 更新高度时尽量保持当前可见内容的锚点，避免前面某行变高就把用户正在看的行推走。使用成熟列表工具时，应了解它的测量缓存、重新计算和滚动定位接口，而不是直接修改 DOM 高度后期待内部偏移自动正确。

3. 我会测试窄屏换行、图片慢加载和展开详情等会改变行高的情况。若行结构特别复杂、精确恢复成本很高，也可以选择分页或限制展开区域，不必为了使用虚拟列表而接受难以维护的定位逻辑。

## 追问：虚拟列表的键盘焦点应该怎么管理？

1. 屏幕外项目没有真实节点，不能直接从完整数据索引推断一定能聚焦。需要先通过列表的滚动或定位接口让目标项进入渲染范围，等相应节点出现，再执行焦点移动，并使用稳定业务编号确认目标没有变化。

2. 当前输入行滚出可见区域时，也要有明确策略。有的组件会保留正在编辑的行，有的把草稿存到外层并在返回时恢复；无论采用哪种，都不能让用户按一次方向键就突然失去输入位置或把内容写到另一项。

3. 我会用纯键盘测试首项、末项、跨窗口移动和错误定位，检查读屏语义是否能说明项目位置。若任务主要是长表单编辑，分页或分组可能更适合，性能方案应支持实际操作方式，而不是只追求滚动帧率。
