# INP 高时先查什么？

## 核心回答

1. INP 高时，先找到具体哪次点击、触摸或键盘交互响应慢，别把页面上所有动画和接口都列成原因。INP 关注的是交互到下一次呈现的响应，通常取最慢的那次。交互很多时按规则排除少量极端值，它不是请求耗时的平均数。

2. 一次慢交互可以拆成输入延迟、事件处理、呈现延迟。输入延迟高，说明用户操作时主线程可能正忙。事件处理长，看回调里的计算和同步工作。呈现延迟高，继续查样式、布局、绘制。三段对应不同的修复位置。

3. 性能面板里定位长任务和调用栈，看大循环、同步布局、重复组件更新、第三方代码。网络请求本身通常是异步的，但请求前大量处理、响应后一次渲染大量数据，都可能占住主线程。只盯接口时间会漏。

4. 处理时先让用户拿到必要反馈，再减少这次交互必须完成的工作。能延后的统计和计算分到后续任务，大计算适合时丢给 Worker，长列表缩小渲染范围。简单包成 Promise 微任务，不一定让浏览器获得绘制机会。

5. 改完重复同一次交互，再看整体页面数据和其他操作有没有变差。先显示 loading、后面异步处理很久，下一次绘制可能变快，但业务完成仍慢，两个目标都要盯。本地测试记下交互路径和设备条件，再结合真实访问数据，看最慢操作有没有改善。

## 追问：把重计算放进 Promise.then，为什么可能还是卡？

1. `then` 回调当微任务执行，浏览器通常要在适当检查点把微任务队列清完，再继续别的工作。不断追加微任务，或里面有很长的计算，仍可能挡住下一次绘制。计算不会自动跑到后台线程。

2. 按工作性质选方式。必须在主线程但可以拆开的任务，适当让出执行机会。不需要 DOM 的大量计算，考虑 Worker。拆分也要控制每段工作量。整个大循环只是挪到另一个回调里，仍然是一段长任务。

3. 看用户点击后的时间线，是不是真的更早出现绘制，计算总量有没有变。代码用了异步关键字，不代表不卡。关键是浏览器何时能处理输入、提交新画面，不是函数返回什么类型。

## 追问：点击后立即显示 loading，就等于解决 INP 了吗？

1. 它可能帮下一次绘制更早出现，让用户知道操作被接受了。前提是后续同步工作没有在绘制前继续占住主线程。设完状态立刻跑大循环，浏览器仍可能等循环结束，才把 loading 真正画出来。

2. 必要反馈和重工作在调度上分开，同时减少计算或更新范围。业务完成时间也要测。用户看到加载状态后仍等很久，不算完整改善。只优化一个测量点，任务本身还在无效耗时，用户感知还在。

3. 测试既记首次反馈，也记内容完成、可以继续操作的时间。取消或重复点击还要有状态保护，别为了快速反馈启动多个重复任务，让接下来几秒更难用。
