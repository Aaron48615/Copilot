# INP 高时先查什么？

## 核心回答

1. INP 高时，我会先找到具体哪次点击、触摸或键盘交互响应慢，不直接把页面所有动画和接口都列为原因。INP 关注交互到下一次呈现的响应，通常取最慢交互；交互很多时按规则排除少量极端值，并不是请求耗时的平均数。

2. 一次慢交互可以分输入延迟、事件处理和呈现延迟。输入延迟高说明用户操作时主线程可能正忙，事件处理长则看回调里的计算和同步工作，呈现延迟高则继续检查样式、布局和绘制，三段对应不同修复位置。

3. 我会在性能面板定位长任务及调用栈，检查大循环、同步布局、重复组件更新和第三方代码。网络请求本身通常异步，但请求前的大量处理和响应后一次渲染大量数据都可能占住主线程，不能只盯着接口时间。

4. 处理时先让用户得到必要反馈，再减少当前交互必须完成的工作。可延后的统计和计算分到后续任务，大计算适合时用 Worker，长列表减少渲染范围；简单包成 Promise 微任务不一定让浏览器获得绘制机会。

5. 改完重复同一交互，并观察整体页面数据与其他操作有没有退化。如果先显示 loading 后异步处理很久，下一次绘制可能变快，但业务完成仍慢，两个目标都要关注；本地测试要记录交互路径和设备条件，再结合真实访问数据检查最慢操作是否改善。

## 追问：把重计算放进 Promise.then，为什么可能还是卡？

1. then 回调作为微任务执行，浏览器通常要在适当检查点清空微任务队列后再继续其他工作。如果不断追加微任务，或者其中有很长的计算，仍可能阻碍下一次绘制，并不会自动让计算跑到后台线程。

2. 我会按工作性质选择方式：必须在主线程但可拆分的任务适当让出执行机会，不需要 DOM 的大量计算考虑 Worker。拆分也要控制每段工作量，只把整个大循环挪到另一个回调里，仍然是一段长任务。

3. 验证时看用户点击后的时间线是否真的出现更早绘制，以及计算总量是否变化。不能只因为代码用了异步关键字就认为不卡，关键是浏览器何时能处理输入和提交新画面，而不是函数返回什么类型。

## 追问：点击后立即显示 loading，就等于解决 INP 了吗？

1. 它可能帮助下一次绘制更早出现，让用户知道操作被接受，但前提是后续同步工作没有在绘制前继续占住主线程。设置状态后立刻执行大循环，浏览器仍可能等循环结束才把 loading 真正画出来。

2. 我会把必要反馈与重工作在调度上合理分开，同时减少计算或更新范围。还要测业务完成时间，用户看到加载状态后仍等很久并不是完整改善，不能只优化一个测量点而放任任务本身无效地耗时。

3. 测试时既记录首次反馈，也记录内容完成和可继续操作的时间。对于取消或重复点击，还需状态保护，避免为了快速反馈启动多个重复任务，让页面在接下来的几秒变得更难使用。
