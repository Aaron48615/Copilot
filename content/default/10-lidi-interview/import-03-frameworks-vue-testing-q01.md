# Vue 2 的 nextTick 怎么在测试里用？

## 核心回答

1. Vue 2 更新响应式数据后，DOM 通常要等异步更新队列刷新。测试如果修改数据就立即断言文本，可能读到旧界面；可以 await Vue.nextTick 或实例的 $nextTick，再检查由那次修改产生的 DOM，而不是增加固定毫秒数的等待。

2. Vue Test Utils 对应 Vue 2 的版本里，trigger、setValue、setProps 等会触发更新的方法通常可以直接 await。比如点击加一按钮后等待 trigger，再断言数字变化，既模拟了用户行为，也明确等待相关视图更新，比直接调用内部方法更接近组件契约。

3. nextTick 不能自动完成未结束的接口 Promise。如果点击后先请求再设置列表，要先让模拟请求完成，推进相应 Promise 回调，再等待必要的 Vue 更新；只重复 nextTick，不能使一个仍未解决的网络任务凭空返回数据。

4. 涉及 debounce 或轮询时，还要分别管理定时器。使用测试框架的假时钟推进延时，再处理 Promise 与视图更新，并在用例后恢复时钟；不能把定时器、请求和 Vue 调度当作同一种等待，否则测试可能偶尔通过却无法稳定复现。

5. Vue 2 自身的响应式限制也不能靠 nextTick 修好。直接给对象新增属性或改数组下标没有触发更新时，应先按 Vue 2 规则使用 $set、splice 等正确修改；等待只负责已经安排的更新，不是强制重新发现所有数据变化。

## 追问：为什么 await trigger 之后，接口结果仍然没有显示？

1. trigger 的等待主要覆盖相关 Vue 更新，不承诺等待事件处理器里所有外部异步任务。点击产生请求后，加载提示可能已经出现，但模拟接口还没完成，列表自然没有结果，测试应分阶段断言这种过程。

2. 我会显式完成模拟 Promise，或使用适合测试环境的 Promise 队列推进工具，再等待结果赋值引起的视图更新。flushPromises 也不能替一个真实永不完成的请求造出响应，请求返回值仍需要由测试控制。

3. 可以先断言按钮忙碌和加载内容，再完成请求检查结果，失败时检查错误与重试。这样等待顺序对应实际业务过程，不会为了让最后一个文本出现就连续加许多无法解释的 nextTick。

## 追问：Vue 2 测试直接改数组下标，再等待为什么还是失败？

1. Vue 2 对数组下标直接赋值存在检测限制，这次变化可能根本没有通知视图更新。nextTick 只是等待已安排的更新队列，不会自动扫描数组寻找遗漏，因此多等几轮仍不等于正确触发响应式变化。

2. 应通过 Vue.set、实例 $set 或 splice 更新相应位置，再等待 Vue 刷新。测试最好走组件实际对外的用户操作，若业务代码本身使用错误的下标修改方式，应修复业务逻辑，而不是在测试里强制更新来让断言通过。

3. 我会保留一个能暴露原问题的操作验证，并检查其他已有项没有被误改。区分“数据没通知”和“通知后还没刷新”，才能决定修复赋值方式还是等待时机，不能把所有失败都归为测试跑得太快。
