# Transferable 为什么会让原数据失效？

## 核心回答

1. 转移会让原数据失效，是因为它把底层资源交给接收方，不是让两边各留一份副本。以普通二进制缓冲区为例，成功转移后发送端的原缓冲区会分离。原对象还在，但已经不能再访问那块原来的字节数据。

2. 主线程把一段图片像素交给工作线程处理，转移能够避免为这块缓冲区再复制全部内容。使用前必须确定发送方后续不再需要读取它，否则预览、重试或者其他处理逻辑可能继续访问已经失效的旧引用。

3. 类型化数组是观察缓冲区的视图。转移时应把其底层缓冲区放进转移列表，不是把视图本身当成可转移资源。同一个缓冲区上的其他视图也会受到影响，所以不能只检查当前变量还会不会用，还要检查共享它的对象。

4. 转移列表只说明哪些资源需要转移，不会自动把资源加进返回结果或发送的消息里。调用时还应让消息内容能访问到这些资源，比如把缓冲区或对应视图放进消息对象。否则原端可能失效，接收方却拿不到想处理的数据。

5. 两边都需要保留原始数据，就选择复制，或者先保留必要副本再转移剩余数据，并把额外内存成本算进去。共享内存是另一套机制，需要考虑并发读写与环境限制。转移不是双方仍可随意读写的共享方案。

## 追问：只转移一个视图用到的部分，会影响其他视图吗？

1. 会。转移针对的是整个底层缓冲区，不是某个视图看到的那一段范围。两个视图分别观察同一缓冲区的前半段和后半段，转移其中一个视图引用的缓冲区后，发送端的另一个视图也无法继续正常访问原字节。

2. 只想交出其中一段，同时保留其他数据，就先为这一段创建独立缓冲区，再把它转移出去。这样会产生一次有意的复制，但资源边界更清楚。别为了说没有复制，就让无关功能共享的内存一起失效。

3. 设计接口时应说明调用后谁持有缓冲区，以及调用方是否还允许保留视图继续使用。验证也要覆盖多个视图共用缓冲区的情况，不能只检查接收方处理成功，还要确认发送方的预览或缓存没有继续依赖旧数据。

## 追问：工作线程处理失败后，发送方怎样重试？

1. 成功转移以后，发送方不能直接拿原来的缓冲区重新发送，因为它已经分离。处理任务失败，需要从文件、网络响应或事先保留的副本重新取得输入，或者在协议允许时让工作线程把仍持有的资源转移回来。

2. 任务协议里区分已收到、处理中和处理完成，并用任务标识关联结果，避免超时后新旧任务结果混在一起。工作线程异常退出时，原资源不一定还能取回，所以重试方案必须有可恢复的数据来源，不能只保存旧引用。

3. 要不要保留副本，取决于恢复成本和内存预算。大文件全量备份可能抵消转移的收益。可以考虑保留原始文件引用、分块读取或限制并发任务数，但这些都是针对场景的设计选择。转移本身不带可靠重试。
