# 为什么 emit 时要复制集合？

## 核心回答

1. 复制监听集合，是为了在一次 emit 开始时固定本轮要通知哪些订阅者。回调本身可能订阅新监听器或取消其他监听器，如果直接遍历正在被改的集合，当前派发就会被这些操作带着走，调用方很难只根据开始时的状态理解结果。

2. 比如原来有 A、B，A 执行时新增 C，遍历原 Set 可能在本轮继续访问 C。先做 `[...listeners]` 后再遍历，外层这一轮只通知 A、B，C 等后续派发。这里固定的是监听器引用，不需要深拷贝函数或业务参数。

3. 删除的语义也要说清楚：采用开始时快照，A 在回调里移除 B，B 仍在本轮快照中，通常还会执行，之后的 emit 才不包含它。Node.js EventEmitter 的普通监听器也有这种行为，所以快照不是「取消一定立刻阻止本轮执行」的保证。

4. 直接遍历 Set 并不是没有规则，也不是删除自己就一定跳过后一个元素，它有明确的动态遍历语义。真正要避开的是新增元素被本轮访问、尚未访问的元素删除后被略过，以及删除后重新加入造成再次访问，这些和预期的派发规则可能对不上。

5. 快照需要与监听器数量成正比的额外时间和空间，用这个换规则清楚。高频事件确实出现分配压力，再依据测量考虑稳定数组或版本机制。同时 once 还需要独立的已触发标记，快照本身解决不了嵌套 emit 的重复执行。

## 追问：A 移除了 B，为什么本轮还允许 B 执行？

1. 这是「本轮名单在开始时确定」的约定，取消订阅只改后续派发的名单。好处是调用结果不依赖前一个回调是否恰好删了别人，订阅者能据此理解顺序。但这个选择必须写清楚，别让使用者误以为退订能撤销已排队通知。

2. 业务需要立刻跳过还未执行的 B，可以在每次调用前检查订阅记录是否仍然有效。这样会变成另一套合理规则，和直接遍历快照不同。给记录加 active 状态，别临时混用几种判断导致行为不一致。

3. 组件卸掉后的状态更新，即使 emitter 用快照，也可以在回调内部检查组件是否仍有效。这个检查保护业务状态，退订负责去掉后续监听，两层作用不同。正在执行的同步回调也无法靠删除集合成员倒退停止。

## 追问：快照能阻止回调里再次 emit 引发的问题吗？

1. 不能。嵌套 emit 是一次新的派发，会读当时的监听集合，所以可能看到外层开始后新加的监听器。外层快照只约束外层这一轮，不能把所有嵌套派发都冻在同一份名单上，除非额外设计队列语义。

2. 对 once，调用之前就要移除并标记已触发；如果等调用结束才移除，回调里再次 emit 会重新触发自己。还存在前面的普通监听器先嵌套派发的情况，所以外层快照后来走到同一个 once 记录时也要检查已触发标记。

3. 普通监听器无条件再次触发同名事件，仍可能无限递归，这不是复制集合能消掉的。先检查业务该不该产生新事件；若需要排队处理，再明确改成异步或队列调度，因为这会改变同步顺序和异常传播方式。
