# 为什么不把完整 source map 放公网？

## 核心回答

1. 完整 source map 可能把压缩代码对应回源码，并包含原始内容、注释和内部路径。它不一定是机密，但会增加外部可分析的信息，所以我会按项目公开范围和调试需求决定，不默认把所有生产 map 与静态资源一起公开。

2. 对于不希望公开源码的应用，可以生成生产 map 后上传到受限的错误平台，用于还原堆栈，再从公开部署产物中排除。这样保留定位能力，同时让访问源码的人和访问普通页面的人拥有不同权限。

3. hidden source map 只是不在脚本末尾提供自动关联注释，并不自动禁止别人下载 map 文件。若它仍在静态目录，知道或猜到 URL 的人可能直接访问，所以还需要实际检查部署清单和公网访问结果。

4. 上传时必须关联准确的发布版本、文件路径或平台要求的标识。新旧 map 搞错会把堆栈指到不相关代码，可能比没有 map 更误导；构建、上传和发布之间应保证来自同一份产物，而不是事后重新构建一份猜测匹配。

5. 我会限制调试平台权限和保留时间，并确认源码中本就没有密钥。关闭 source map 不是保护前端秘密的办法，因为浏览器仍需执行 JS；服务端密钥不能进入客户端产物，无论是否提供 map 都一样。

## 追问：hidden-source-map 和 nosources-source-map 怎么区分？

1. hidden 的重点是生成映射文件但不在产物里自动引用它，适合由受控平台自行关联。它可能仍包含源码，且如果被部署到公开目录，地址可访问时仍会暴露内容，不能把 hidden 理解成服务器访问权限。

2. nosources 的重点是映射里不携带源内容，但仍可能暴露文件名、目录或符号信息。它对定位能力也有影响，错误平台可能还需要其他方式获得源码，因此要按平台流程和隐私需求选择，而不是只追求名字更安全。

3. 我会检查实际生成的文件字段和部署结果，并用一个已知错误验证映射。配置名称只是工具选项，最终要确认外部能获得哪些信息、内部能否还原堆栈，不能只看配置文件就认定目标达成。

## 追问：线上堆栈映射到错误行，先检查什么？

1. 先检查错误事件的发布版本与所用 map 是否一致，尤其是旧用户仍运行上一版代码时，平台不能总拿最新 map 来解释。随后核对脚本 URL、文件名和上传标识，确认平台关联的是实际执行的那份文件。

2. 再看产物是否被 CDN、服务器或其他步骤二次压缩、拼接或注入内容。source map 对应的是生成时的代码位置，后续修改如果没有同步更新映射，行列就可能偏移，即使文件名仍然看起来正确。

3. 我会用固定可复现的异常在发布产物中验证，还原到明确源码位置。修复上传流程后再确认旧版本记录没有被覆盖，不能为了一次定位方便把所有历史文件都归到同一个 release 名称下。
