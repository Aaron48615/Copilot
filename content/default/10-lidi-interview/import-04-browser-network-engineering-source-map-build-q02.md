# 为什么不把完整 source map 放公网？

## 核心回答

1. 完整 source map 可能把压缩代码对应回源码，里面还有原始内容、注释、内部路径。它不一定算机密，但会增加外部可分析的信息。按项目公开范围和调试需求来定，不默认把所有生产 map 跟静态资源一起公开。

2. 不希望公开源码的应用，可以生成生产 map 后上传到受限的错误平台，用来还原堆栈，再从公开部署产物里排除。定位能力还在，访问源码的人和访问普通页面的人权限不一样。

3. hidden source map 只是不在脚本末尾提供自动关联注释，并不自动禁止别人下载 map 文件。它还在静态目录里，知道或猜到 URL 的人可能直接访问。部署清单和公网访问结果要实际查。

4. 上传时必须关联准确的发布版本、文件路径，或平台要求的标识。新旧 map 搞错，堆栈会指到不相关代码，可能比没有 map 更误导。构建、上传、发布之间应对同一份产物，别事后重新构建一份再猜着匹配。

5. 调试平台权限和保留时间要限制，并确认源码里本来就没有密钥。关掉 source map 不是保护前端秘密的办法，因为浏览器仍要执行 JS。服务端密钥不能进客户端产物，有没有 map 都一样。

## 追问：hidden-source-map 和 nosources-source-map 怎么区分？

1. hidden 的重点是生成映射文件，但不在产物里自动引用它，适合由受控平台自己关联。它可能仍包含源码。被部署到公开目录、地址能访问时，内容照样会暴露。hidden 不是服务器访问权限。

2. nosources 的重点是映射里不携带源内容，但仍可能露出文件名、目录或符号信息。定位能力也会受影响，错误平台可能还需要别的方式拿到源码。按平台流程和隐私需求选，别只追求名字听起来更安全。

3. 看实际生成的文件字段和部署结果，再用一个已知错误验证映射。配置名称只是工具选项。外部能获得哪些信息、内部能不能还原堆栈，这两边都要确认。只看配置文件认定目标达成，不够。

## 追问：线上堆栈映射到错误行，先检查什么？

1. 错误事件的发布版本和所用 map 是否一致，尤其是旧用户还在跑上一版代码时，平台不能总拿最新 map 来解释。随后核对脚本 URL、文件名、上传标识，确认平台关联的是实际执行的那份文件。

2. 再看产物有没有被 CDN、服务器或其他步骤二次压缩、拼接或注入内容。source map 对应的是生成时的代码位置，后续改了却没同步更新映射，行列就可能偏，即使文件名看起来还对。

3. 用一个固定可复现的异常，在发布产物里验证，还原到明确的源码位置。上传流程修好之后，旧版本记录不能被覆盖。为了一次定位方便，把所有历史文件都归到同一个 release 名称下，后面会更乱。
