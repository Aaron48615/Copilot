# 如何用可辨识联合描述请求状态？

## 核心回答

1. 我会把请求状态写成几个对象类型组成的联合，每个分支都有一个取值明确的标签。比如空闲、加载中、成功和失败分别对应不同标签，成功分支必须携带数据，失败分支必须携带错误原因，让状态本身说明现在能读到哪些信息。

2. 渲染时先判断 `status`，TypeScript 就能根据标签缩小当前对象的类型，在成功分支允许读取数据。这里要求各分支的标签是具体字面量；如果所有分支都写成宽泛的字符串，编译器就无法据此排除其他情况，检查效果会变差。

3. 相比独立维护加载标记、可选数据和可选错误，这种写法能排除一部分不合理组合。比如初次加载成功时漏传数据会报类型错误，但有旧数据的刷新状态也可能完全合理，因此要按页面实际需要定义，不能机械地认为加载和数据不能共存。

4. 我会在分支处理末尾用 `never` 做穷尽检查，新增状态后让遗漏的处理位置暴露出来。它只能帮助检查类型覆盖情况，不会自动验证接口数据或请求先后顺序，所以外部响应校验和过期请求判断仍然需要在运行时完成。

## 追问：新增一个取消状态，怎样让遗漏的渲染分支报错？

1. 可以在按标签逐一处理的分支末尾，把剩余状态赋给一个 `never` 类型变量。所有情况都处理完时，理论上没有状态能到这里；新增取消状态却没处理时，剩余类型就不再是空的，赋值会报错。

2. 检查要放在真实的分支处理代码里，而不是单独写一个永远不会使用的类型声明。这样增加状态时，错误会指向需要更新的地方，开发者可以明确决定取消后展示空闲页、保留旧数据还是给出提示。

3. 这也不能保证线上永远不会进到兜底，因为外部数据可能违反声明，或者有人用了断言绕过检查。运行时仍应有合理的异常处理，编译期穷尽检查负责提醒代码遗漏，两者解决的问题并不相同。

## 追问：刷新时继续显示旧列表，应该怎样设计状态？

1. 我会先确认交互是不是允许旧数据继续可见，再决定增加带数据的刷新状态。这样初次加载表示没有可展示内容，刷新表示已有数据但正在更新，组件不必通过多个松散的布尔值猜测两者区别。

2. 刷新失败也不一定要把整个列表清空，可以设计保留旧数据并附带刷新错误的分支。页面能继续展示现有内容，同时明确提示更新失败，让用户知道看到的是旧结果，而不是误以为本次请求已经成功。

3. 状态数量增加是为了表达真实的界面差异，不需要把所有字段组合都建成独立状态。假设某个页面刷新时本来就清空内容，简单的四种状态可能已经足够，设计应跟随需求，而不是追求类型写得复杂。
