# 如何用可辨识联合描述请求状态？

## 核心回答

1. 请求状态写成几个对象类型组成的联合，每个分支有一个取值明确的标签。空闲、加载中、成功、失败各用不同标签。成功那一支必须带数据，失败那一支必须带错误原因，看状态就知道现在能读到什么。

2. 渲染时先判断 `status`，TypeScript 就能按标签把当前对象收窄，成功分支允许读数据。各分支的标签得是具体字面量。所有分支都写成宽泛的字符串，编译器没法据此排除其他情况，检查就弱了。

3. 比起单独维护加载标记、可选数据、可选错误，这种写法能排除一部分不合理组合。初次加载成功却漏传数据，会报类型错误。但刷新时还有旧数据，完全可能合理，按页面实际需要定义，别机械地认为加载和数据不能共存。

4. 分支处理末尾用 `never` 做穷尽检查，新增状态后，漏掉的处理位置会暴露出来。它只能帮着看类型覆盖全不全，不会自动验证接口数据，也不会管请求谁先谁后。外部响应校验和过期请求判断，还是运行时的事。

## 追问：新增一个取消状态，怎样让遗漏的渲染分支报错？

1. 按标签逐一处理的分支末尾，把剩余状态赋给一个 `never` 类型变量。情况都处理完，理论上没有状态能走到这里；新增取消状态却没处理，剩余类型就不是空的，赋值会报错。

2. 检查要放在真实的分支处理代码里，别单独写一个永远不用的类型声明。加状态时，错误会指到需要更新的地方，再决定取消后是展示空闲页、留着旧数据，还是给个提示。

3. 这保证不了线上永远走不到兜底。外部数据可能违反声明，也可能有人用断言绕过检查。运行时仍要有合理的异常处理。编译期穷尽检查管的是代码漏没漏，跟运行时不是一回事。

## 追问：刷新时继续显示旧列表，应该怎样设计状态？

1. 先确认交互允不允许旧数据继续可见，再决定要不要增加「带着数据的刷新」状态。初次加载表示没有可展示内容，刷新表示已有数据但正在更新，组件不必靠几个松散的布尔值去猜两者区别。

2. 刷新失败也不一定要把整个列表清空。可以设计成：旧数据还在，另外附带刷新错误。页面继续展示现有内容，同时明确提示更新失败，用户知道看到的是旧结果，不会误以为这次已经成功。

3. 状态变多是为了表达真实的界面差异，不必把所有字段组合都建成独立状态。某个页面刷新时本来就清空内容，简单四种状态可能已经够。设计跟着需求走，别为了类型好看把状态写复杂。
