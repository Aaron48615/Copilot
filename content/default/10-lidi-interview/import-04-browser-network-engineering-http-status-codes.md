# 常见的 HTTP 状态码有哪些？

## 核心回答

1. 状态码按类别理解，具体接口还得单独看。2xx 表示请求成功：200 返回结果，201 常用于创建资源，204 没有响应体。不能无条件对所有成功响应调用 JSON 解析，还是看接口约定。

2. 3xx 跟重定向或缓存验证有关。301 和 302 分别表达永久和临时重定向。304 是条件请求验证后继续用缓存，不是一次普通页面跳转。需要保留请求方法和请求体时，还要考虑 307、308 的语义。

3. 4xx 常见有参数错误、认证失败、权限不足和资源冲突。401 表示缺少有效认证，403 表示服务端拒绝访问，不该一律清登录态。409 可以表达版本冲突，比如两个人同时编辑记录，后来的更新需要先刷新状态。

4. 429 表示请求过多，应结合 Retry-After 这类信息把频率降下来。5xx 里 500 是内部错误，502 是网关收到无效上游响应，504 是等待上游超时。前端要留脱敏请求标识，但不能只凭状态码确定后端哪一行代码出错。

5. 请求库的行为也要分清。比如 `fetch` 收到错误状态通常仍返回 Response。页面应区分可重试查询和写操作。超时或服务错误，不一定意味着业务没执行。提示和重试要符合具体场景，别把所有异常都处理成请重新登录。

## 追问：401 和 403 分别应该怎样展示？

1. 401 通常进入恢复认证或重新登录流程，但先确认它确实来自受保护业务接口，不是其他独立服务。多个请求同时失效时应统一处理，避免连续跳转或重复弹窗，并保存合理的返回位置。

2. 403 应提示当前操作被拒绝，必要时说明可以联系管理员或回到其他页面，不该默认删掉正常会话。它也可能涉及风控或策略限制。前端要结合服务端的安全业务码，不能只凭登录状态猜具体原因。

3. 无论页面怎么展示，后端都要真正拒绝未授权的数据访问。隐藏按钮只改善体验，用户仍可直接发请求。验证时包含普通账号访问管理接口，确认失败后不会泄露敏感响应，也不会残留上一页数据。

## 追问：收到 409 后，能不能自动覆盖提交？

1. 如果 409 表示乐观锁版本对不上，自动覆盖会丢掉别人刚提交的内容，跟冲突检测的目的相反。前端应先读最新记录，告诉用户数据已经变了，别只把 version 改成新的再无条件重发。

2. 把用户本地输入留下来，展示哪些字段发生冲突。简单场景可以让用户重新确认后再提交。互不影响的字段能不能合并，由业务约定。前端不能凭字段名自行决定别人改的内容不重要。

3. 服务端更新时仍要原子校验版本，避免读到最新值后又发生竞争。测试用两个会话先读同一版本，再分别提交，确认后一次得到明确冲突，并且用户输入没有因为弹出错误提示而全部丢掉。
