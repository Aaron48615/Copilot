# 常见的 HTTP 状态码有哪些？

## 核心回答

1. 我会按状态码类别理解，但会结合具体接口处理。2xx 表示请求成功，例如 200 返回结果、201 常用于创建资源、204 没有响应体；不能无条件对所有成功响应调用 JSON 解析，仍要看接口约定。

2. 3xx 与重定向或缓存验证有关，301 和 302 分别表达永久与临时重定向，304 是条件请求验证后继续使用缓存，并不是一次普通页面跳转。需要保留请求方法和请求体时还要考虑 307、308 的语义。

3. 4xx 常见有参数错误、认证失败、权限不足和资源冲突。401 表示缺少有效认证，403 表示服务端拒绝访问，不应一律清登录态；409 可以表达版本冲突，例如两个人同时编辑记录，后来的更新需要先刷新状态。

4. 429 表示请求过多，应结合 Retry-After 等信息减少频率。5xx 里 500 是内部错误，502 是网关收到无效上游响应，504 是等待上游超时；前端要保留脱敏请求标识，但不能只凭状态码确定后端哪一行代码出错。

5. 请求库的行为也要分清，例如 fetch 收到错误状态通常仍返回 Response。页面应区分可重试查询和写操作，超时或服务错误不一定意味着业务未执行；我会让提示和重试符合具体场景，不把所有异常都处理成请重新登录。

## 追问：401 和 403 分别应该怎样展示？

1. 401 通常进入恢复认证或重新登录流程，但先确认它确实来自受保护业务接口，而不是其他独立服务。多个请求同时失效时应统一处理，避免连续跳转或重复弹窗，并保存合理的返回位置。

2. 403 应提示当前操作被拒绝，必要时说明可以联系管理员或返回其他页面，不应默认删除正常会话。它也可能涉及风控或策略限制，前端需要结合服务端的安全业务码，不能只凭登录状态猜出具体原因。

3. 无论页面如何展示，后端都要真正拒绝未授权的数据访问。隐藏按钮只改善体验，用户仍可直接发请求；验证时要包含普通账号访问管理接口，确认失败后不会泄露敏感响应或残留上一页数据。

## 追问：收到 409 后，能不能自动覆盖提交？

1. 如果 409 表示乐观锁版本不匹配，自动覆盖会丢掉他人刚提交的内容，违背冲突检测的目的。前端应先读取最新记录，并告诉用户数据已经变化，而不是只把 version 改成新的再无条件重发。

2. 我会保留用户本地输入，展示哪些字段发生冲突，简单场景可以让用户重新确认后提交。互不影响的字段是否允许合并要由业务约定，不能让前端凭字段名自行决定别人修改的内容不重要。

3. 服务端更新时仍要原子校验版本，避免读取最新值后又发生竞争。测试用两个会话先读同一版本再分别提交，确认后一次得到明确冲突，并且用户输入没有因为弹出错误提示而全部丢失。
