# 和 enum 有什么关系？

## 核心回答

1. 我会先区分枚举和可辨识联合各自表达的内容：枚举给一组值起名字，可辨识联合描述不同情况分别携带哪些字段。比如枚举能列出加载中、成功、失败，却不能单靠这些名字保证成功时一定有数据、失败时一定有错误原因。

2. 两者可以一起使用，把枚举成员作为每个对象分支的标签即可。成功分支的标签固定为成功成员并携带数据，失败分支固定为失败成员并携带错误；判断标签后，编译器才能据此缩小整个对象的类型，允许访问对应字段。

3. 如果状态只在一小段页面逻辑中使用，我倾向于直接用字符串字面量作为标签，阅读时不必跳到另一个定义。普通枚举通常还会生成运行时对象，而字符串联合只参与类型检查，因此是否需要运行时访问也是选择时要考虑的因素。

4. 如果多个模块已经统一使用某个枚举，我会优先保持现有约定，再通过联合类型补上标签与数据的关系。无论选择哪种写法，接口返回值都不会因为类型声明自动合法，外部数据仍要检查，不能把声明为某个枚举当作完成了校验。

## 追问：把 status 定义成枚举，再把 data 写成可选字段够不够？

1. 这样只能限制状态有哪些名字，不能限制字段与状态的组合。即使 `status` 是成功，`data` 仍可能缺失；失败对象也可以意外带着成功数据，编译器没有足够的信息认定这些情况不合法。

2. 我会将成功和失败分别写成对象类型，再用联合连接。每个对象的标签必须足够具体，成功分支要求数据字段，失败分支要求错误字段，这样构造对象和读取对象时都能检查到状态与字段的关联。

3. 需要保留旧数据时，也应该明确说明它属于刷新中状态或缓存字段，而不是随便把所有属性都改成可选。类型的目标是表达允许出现的组合，不能为了暂时消除报错，就让错误状态也变得容易创建。

## 追问：接口返回数字状态码时，页面也必须使用数字枚举吗？

1. 不必须，服务端协议和页面内部状态可以分别表达。假设接口约定数字代表处理结果，我会在读取响应时先判断数字是否在已知范围，再映射成页面能理解的成功、失败等状态，避免组件到处比较数字。

2. 数字枚举有自动递增等语言特性，但这不能替代对接口值的明确约定。如果服务端把某个数字改成另一种含义，前端类型检查并不会发现，因此协议字段应有固定定义，不能依赖声明顺序碰巧一致。

3. 对未知状态码，我会保留原始值供排查，并给页面一个明确的异常分支。直接断言成枚举只是让编译器相信调用方，不会检查真实数据，也不能保证后面按成功响应读取字段时一定安全。
