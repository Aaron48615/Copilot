# 和 enum 有什么关系？

## 核心回答

1. 枚举给一组值起名字；可辨识联合描述不同情况分别带着哪些字段。枚举能列出加载中、成功、失败，单靠这些名字保证不了：成功时一定有数据、失败时一定有错误原因。

2. 两者可以一起用：把枚举成员当每个对象分支的标签。成功分支的标签固定为成功成员并带着数据，失败分支固定为失败成员并带着错误。判断标签后，编译器才能把整个对象收窄，允许访问对应字段。

3. 状态只在一小段页面逻辑里用，直接用字符串字面量当标签更省事，阅读时不必跳到另一个定义。普通枚举通常还会生成运行时对象，字符串联合只参与类型检查。要不要运行时访问，也是选型时要看的。

4. 多个模块已经统一用某个枚举，就先保持现有约定，再用联合类型补上标签和数据的关系。不管哪种写法，接口返回值不会因为类型声明自动合法。外部数据仍要检查，声明成某个枚举不等于已经校验过。

## 追问：把 status 定义成枚举，再把 data 写成可选字段够不够？

1. 这样只能限制状态有哪些名字，限制不了字段跟状态怎么组合。就算 `status` 是成功，`data` 仍可能缺失；失败对象也可以意外带着成功数据。编译器没有足够信息认定这些不合法。

2. 成功和失败分别写成对象类型，再用联合接起来。每个对象的标签必须够具体：成功分支要求数据字段，失败分支要求错误字段。构造对象、读取对象时，都能检查到状态和字段的关联。

3. 需要留旧数据时，也该写明它属于刷新中状态或缓存字段，别随便把所有属性都改成可选。类型要表达允许出现的组合，别为了暂时消报错，让错误状态也变得很好造。

## 追问：接口返回数字状态码时，页面也必须使用数字枚举吗？

1. 不必。服务端协议和页面内部状态可以分开表达。接口约定数字代表处理结果，读响应时先看数字在不在已知范围，再映射成页面能懂的成功、失败，组件里别到处比较数字。

2. 数字枚举有自动递增这类语言特性，替不了对接口值的明确约定。服务端把某个数字改成另一种含义，前端类型检查发现不了。协议字段应有固定定义，不能靠声明顺序碰巧一致。

3. 未知状态码，留下原始值方便排查，页面给一个明确的异常分支。直接断言成枚举，只是让编译器相信调用方，不会检查真实数据，后面按成功响应读字段也不一定安全。
