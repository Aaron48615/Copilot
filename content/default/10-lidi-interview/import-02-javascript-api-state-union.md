# 如何用联合类型表达请求状态和错误？

## 核心回答

1. 页面真正要分的状态先列出来，比如未开始、加载中、成功、失败，再用同一个状态字段的不同字面量做成联合。成功那一支带着数据，失败那一支带着错误描述，其余分支别假装已经有结果。字段跟状态绑在一起，才知道现在能读什么。

2. 渲染时按状态字段分支，编译器会把对象收窄到对应类型，不必到处写非空断言。成功就展示商品列表，失败就展示重试按钮。所有分支都处理完，还可以用不可达类型检查：后来新增一种状态却漏了处理，编译会报出来。

3. 错误还能再拆：网络不通、业务拒绝、响应格式不对，用户能做的事不一样。网络问题可以提示重试，权限不足可能要重新登录，字段对不上得去查接口。别一律弹一句「请求失败」。

4. 状态模型跟着真实交互走。成功但列表为空，通常仍是成功；后台刷新时还留着旧数据，也得单独表达清楚。它能减少字段乱组合，但验不了服务器真返回了什么，也挡不住旧请求盖住新状态。边界校验和轮次判断还是两件独立的事。

## 追问：如何让新增状态时编译器提醒遗漏分支？

1. 分支判断的最后，把剩下的状态交给一个参数类型是 `never` 的函数，也就是穷尽检查。原来那些状态都处理完，剩下应当是空的；新增了取消状态却没处理，这里就过不去。

2. 这套检查要求状态字段是明确的字面量联合。随手扩成普通字符串，就没法一项一项列。也不能用断言把剩余分支强行说成 `never`，报错被压掉了，检查就没意义。

3. 临时加一个新分支做类型检查，确认提示真会响，再给这个状态补上界面。运行时外部数据仍可能是未知状态，类型检查只发生在编译阶段，服务端乱发一个值，这关拦不住。

## 追问：空列表应该建成 empty 状态还是 success？

1. 接口正常完成，只是没有符合条件的商品，一般仍算成功，数据是空数组。页面在成功分支里看长度，展示「没有匹配结果」和改筛选的入口。正常查完没货，别当成要重试的故障。

2. 空结果要是对应另一套流程，比如第一次进来要引导去创建内容，也可以单独建成空状态。看它有没有不同的行为和字段要求。别只因为画面上有一张空白插图，就把所有空数组都拆成新状态。

3. 还没请求，和请求完是空的，是两件事。前者可能在等用户输入，后者已经有明确查询结论。初始页、成功空数组、请求失败，三条路径分开看，别一进页面就显示无结果，让人以为已经查过了。
