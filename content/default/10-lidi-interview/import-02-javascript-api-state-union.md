# 如何用联合类型表达请求状态和错误？

## 核心回答

1. 我会先列出页面真正需要区分的状态，例如未开始、加载中、成功和失败，再用同一个状态字段的不同字面量把它们组成联合。成功分支携带数据，失败分支携带错误描述，其余分支不假装拥有结果，让字段与状态之间的关系写清楚。

2. 渲染时根据状态字段进行分支判断，编译器就能把对象缩小到对应类型，不必到处使用非空断言。比如成功状态下展示商品列表，失败状态下展示重试按钮；如果所有分支都处理完，还可以通过不可达类型检查发现后来新增而遗漏的分支。

3. 错误本身也可以继续区分网络不可达、业务拒绝和响应格式异常，因为用户能够采取的操作不同。网络问题可以提示重试，权限不足可能需要重新登录，字段不符则需要排查接口，不能都只给一个笼统的请求失败提示。

4. 状态模型应配合实际交互调整，例如成功但列表为空通常仍是成功，后台刷新时保留旧数据也需要明确表达。它能减少字段组合错误，却不能验证服务器真实响应，也不能阻止旧请求覆盖新状态，这两部分还要分别做边界校验和轮次判断。

## 追问：如何让新增状态时编译器提醒遗漏分支？

1. 我会在分支判断的最后，把剩余状态交给参数类型为不可达类型的函数，也就是常见的穷尽检查。原来的所有状态处理完后，剩余类型应当为空；新增取消状态却没有处理时，就无法再满足这个要求。

2. 这种检查依赖状态字段保持明确的字面量联合，如果把它随意扩大成普通字符串，就失去了逐项列举的基础。也不能用类型断言把剩余分支强行变成不可达，否则报错被压掉了，检查便没有实际作用。

3. 我会用一个临时新增分支的类型检查用例确认提示确实生效，再给该状态补上合理界面。运行时仍需处理外部未知数据，因为类型检查发生在编译阶段，服务端发来的未知状态不会自动被这个检查拦住。

## 追问：空列表应该建成 empty 状态还是 success？

1. 如果接口正常完成，只是没有符合条件的商品，我通常让它保持成功状态，数据是空数组。页面在成功分支里判断长度，展示没有匹配结果和调整筛选入口，这样不会把正常查询误当成需要重试的故障。

2. 如果空结果对应独立流程，例如首次进入需要引导创建内容，也可以单独建模为空状态。关键是它是否有不同的行为和字段要求，不能只因为视觉上有一张空白插图，就把所有空数组都拆成新状态。

3. 我会特别区分尚未请求和请求后为空，前者可能等待用户输入，后者已经有明确查询结论。测试时分别检查初始页、成功空数组和请求失败，防止初始化时就显示无结果，让用户误以为系统已经查过。
