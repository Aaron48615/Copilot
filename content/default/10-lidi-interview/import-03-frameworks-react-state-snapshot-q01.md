# React 为什么要批处理？

## 核心回答

1. 批处理是把合适范围内的多次状态更新合并处理，减少中间渲染和提交。比如点击一次同时改变筛选条件、页码和错误提示，通常不需要让用户先看到条件变了、页码还没重置的半完成状态，也能减少重复计算。

2. setter 提交的是更新请求，不会立刻改掉当前函数里的 state 变量。同一个事件里连续读取 count，拿到的仍是这次渲染的快照；因此连续三次 setCount(count + 1) 通常都是要求写入相同结果，不能理解成执行了三次即时自增。

3. 需要连续基于前一个结果更新时，使用函数式更新。三个 `c => c + 1` 会依次进入更新队列，后一个拿到前一个的结果；批处理并没有丢掉更新规则，只是把处理和最终显示安排得更集中。

4. React 18 的新根 API 扩展了自动批处理范围，包括许多 Promise 和定时器里的更新，但不同独立交互不会无限合并。具体表现还要看 React 版本和根的创建方式，不能用老项目的某次日志作为所有版本的统一结论。

5. 我不会把批处理当作可靠的业务事务接口。请求失败、两个独立事件和外部系统修改仍需要自己的状态设计；确实要求同步提交 DOM 时有 flushSync，但它会增加同步工作和相关限制，只适合明确的第三方集成需求。

## 追问：连续三次函数式更新为什么能得到加三？

1. 每个 updater 表达的是“接到前一状态后如何得到下一状态”，而不是提前算好的数字。React 处理队列时按顺序应用，初始零经过三次加一得到三，后一次不再固定读取事件闭包中的零。

2. 相比之下，三次传入 count + 1 会在事件执行时都算出一，队列收到的是相同替换值。两种写法在只更新一次时常常结果相同，所以问题容易在连点、组合更新或异步场景中才暴露出来。

3. updater 必须保持纯粹，不能在其中发请求或记录一次性业务事件。开发检查可能重复调用它来发现不纯计算，真正的用户行为应在事件处理器表达，避免把状态计算次数误当成操作次数。

## 追问：为什么不为了拿到新 DOM，经常使用 flushSync？

1. flushSync 强制 React 尽快把相关更新同步提交，会打断原本能够合并和调度的工作。大量使用可能增加主线程阻塞，还可能使待处理的其他工作一起被刷新，不是普通状态更新的常规写法。

2. 很多需求其实不依赖同步 DOM。例如提交下一页参数可以直接使用已计算的新页码，不必先更新 state 再从 DOM 读取；测量布局可以在合适的提交后时机处理，先明确目的再选择 API。

3. 只有外部浏览器或第三方接口要求某个回调返回前 DOM 已更新，才考虑局部使用，并测量实际影响。不能为了让 console.log 看见新值使用它，因为当前函数的闭包快照仍不会因此变成另一轮渲染的变量。
