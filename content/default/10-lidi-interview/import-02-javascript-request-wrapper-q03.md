# 为什么不把所有逻辑都塞进 Axios 拦截器？

## 核心回答

1. 不该把所有逻辑都放进拦截器，因为调用方很难从一个请求看出背后还有刷新登录、重试甚至轮询。拦截器本身没有问题，问题是把接口差异藏起来以后，排查重复请求和加载状态会变得很困难。

2. 通用且稳定的处理适合放在专用请求实例里，例如为允许的目标地址补充身份凭据、附加请求标识。响应也可以统一转换错误结构，但下载文件和普通数据接口返回形式不同，不能无条件按同一格式解包。

3. 超时预算、可重试条件和取消信号，更适合作为请求函数的明确参数，让调用处能看出策略。商品查询可以重试，创建订单却没有幂等保证，这种差异应该在接口定义附近看得见，别藏在全局条件分支里。

4. 登录失效可以统一协调，但要防止多个失败请求同时刷新凭据，也要防止刷新接口再次触发自己。重放原请求前还要检查它是否已取消、是否允许重发。失败时统一结束等待，不能把调用方永久挂住。

5. 页面提示和轮询生命周期通常留在业务层。后台预取失败未必需要弹窗，弹窗关闭后轮询也应该停止。实例职责保持简单，再用少量明确的策略组合功能，避免一个拦截器依赖所有页面状态。

## 追问：多个请求同时返回登录失效时怎么处理？

1. 用一个共享的刷新任务，让同一登录会话中后续失败请求等待它，而不是各自发刷新请求。刷新完成后更新凭据，再决定哪些请求可以重放，避免旧凭据与新凭据互相覆盖，登录状态来回变。

2. 刷新接口需要跳过这段刷新逻辑，原请求也要标记已经尝试过恢复，防止无限循环。等待期间如果用户退出登录或切换账号，就不能把旧任务的结果写回新会话，应通过会话标识检查结果是否仍然有效。

3. 刷新失败后，所有等待者都应拿到明确失败，业务层再统一安排登录提示。恢复成功也不意味着所有写请求都能盲目重发，仍要看接口是否保证未执行或具备幂等能力，确认不会重复产生业务结果。

## 追问：为什么统一错误弹窗容易造成体验问题？

1. 同一个接口可能既用于用户主动保存，也用于后台预加载，失败时用户的预期不同。保存失败需要清楚提示，后台预加载失败可能保留旧内容即可。全局弹窗不知道请求目的，容易制造与当前操作无关的打扰。

2. 页面同时发多个请求时，每个拦截器都弹一次会出现重复通知，也可能和组件的错误提示叠在一起。底层提供统一错误类别和必要上下文，由页面或约定的提示层决定展示位置、合并方式与是否可重试。

3. 主动取消应和真正失败分开处理。用户切换筛选条件后取消旧查询，不需要显示网络故障。具体接口也可以明确选择静默处理，但仍保留适当诊断信息。不弹窗和吞掉异常是两件事。
