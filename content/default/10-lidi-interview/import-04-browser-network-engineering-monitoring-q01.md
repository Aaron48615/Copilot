# 怎样避免日志泄露隐私？

## 核心回答

1. 允许上报的字段要事先定好，别先把整个错误对象传上去再事后删。通常留错误类型、发布版本、路由模板、脱敏后的请求标识，就够定位。用户填的内容默认不收。

2. URL、请求头、异常消息里都可能带敏感信息。`Authorization`、Cookie、手机号、地址、聊天正文要排除，查询参数按名单挑。页面地址还可能把订单号嵌在路径里，只过滤 query 不够。

3. 脱敏在客户端采集出口做一遍，服务端接收处再查一遍。散列后的用户标识如果还能对上个人，也不是完全匿名。截图和回放更要额外控，输入框遮罩之外，页面上展示的个人资料也可能入镜。

4. 传输走安全通道，服务端限制谁能看、保存多久。开发环境那套很细的调试日志，不能原样带到生产。临时提高诊断信息，要限定范围、时限和用途，别为了一个问题永久收集所有请求体。

5. 用带测试手机号和假 Token 的错误走一遍，看真正发出去的载荷和平台上展示什么，新增字段也覆盖到。监控是为了解释问题，收得越多不一定越有用。没必要的信息不采，泄露风险和维护成本都会低一些。

## 追问：只把手机号中间四位替换掉，是否足够？

1. 要看这条日志拿来干什么，以及其他字段能不能拼出个人。手机号只遮一部分，旁边还有姓名、地址或订单，照样可能认出是谁。一种字符替换认定整条已经匿名，不够。不必要的字段先少收。

2. 日常面板用关联编号，不直接暴露联系方式。账号映射单独存，查询权限收紧。它仍能关联到个人，不是真正匿名。普通错误面板只展示编号，真要定位账号再走受控流程，日常暴露会少很多。

3. 测的时候看字段组合，也看自由文本，异常消息里也可能嵌了原始输入。服务端对不符合约定的字段拒绝或清掉，防止新版客户端漏过滤。数据结构一变，脱敏规则也要跟着改，查一次不够。

## 追问：前端报错时直接上传整个 error 对象有什么问题？

1. 错误对象上可能挂着请求配置、响应体、自定义上下文，里面有 Token 和用户输入。直接序列化还可能漏掉不可枚举的 `message`、`stack`，结果是该有的定位信息不完整，不该有的敏感内容却发出去了。

2. 允许字段显式抽出来，比如规范化后的错误名、消息、堆栈、请求路径模板，再做长度限制。业务异常约定安全的错误码，别让服务端把完整 SQL、内部地址或个人资料当错误文本返回，再被上报。

3. 序列化失败、循环引用也要测，别让监控 SDK 自己再触发一轮新的异常上报。采集失败要限流、有保护，同时留一句能诊断的短状态。为了记一个错误把页面主流程卡住，不值得。
