# 怎样避免日志泄露隐私？

## 核心回答

1. 避免日志泄露隐私，我会先定义允许上报的字段，而不是先把整个错误对象上传再事后删除。通常保留错误类型、发布版本、路由模板和脱敏请求标识就能帮助定位，不需要默认收集用户填写的全部内容。

2. URL、请求头和异常消息都可能含敏感信息。Authorization、Cookie、手机号、地址和聊天正文应排除，查询参数按名单选择；页面地址还可能把订单标识嵌在路径里，所以只过滤 query 不一定够。

3. 脱敏尽量在客户端采集出口和服务端接收处分别检查。散列后的用户标识如果仍能关联到个人，也不能当成完全匿名；截图和回放尤其需要额外控制，输入框遮罩之外还要考虑页面中显示的个人资料。

4. 传输使用安全通道，服务端限制访问权限和保存时间，开发环境的详细调试日志不能直接原样带到生产。如果需要临时提高诊断信息，应限定范围、时限和用途，不能为了一个问题永久收集所有请求体。

5. 验证时我会构造含测试手机号和假 Token 的错误，检查真正发送的载荷和平台展示，再覆盖新增字段。监控数据的价值是解释问题，收集越多未必越有帮助；没有必要的信息不采集，能同时降低泄露风险和维护成本。

## 追问：只把手机号中间四位替换掉，是否足够？

1. 要看日志用途和其他字段是否能关联到个人。手机号只遮一部分，配合姓名、地址或订单信息仍可能识别用户，因此不能只通过一种字符替换就认定整条日志已经匿名，应该先减少不必要字段。

2. 我会使用不直接暴露联系方式的关联编号，把账号映射单独保存并限制查询权限。它仍是可关联个人的数据，不是真正匿名；普通错误面板只展示编号，需要定位账号时再通过受控流程查询，减少日常暴露范围。

3. 测试要看字段组合和自由文本，异常消息里也可能嵌入原始输入。服务端还应拒绝或清理不符合约定的字段，防止新版客户端漏过滤；脱敏规则需要随数据结构变化更新，不能只检查一次。

## 追问：前端报错时直接上传整个 error 对象有什么问题？

1. 错误对象可能附带请求配置、响应体或自定义上下文，里面包含 Token 和用户输入。直接序列化还可能遗漏不可枚举的 message、stack，结果是该有的定位信息不完整，不该有的敏感内容却被发出去。

2. 我会显式提取允许字段，例如规范化后的错误名、消息、堆栈和请求路径模板，再做长度限制。业务异常需要约定安全的错误码，避免让服务端把完整 SQL、内部地址或个人资料作为错误文本返回并被上报。

3. 最后验证序列化失败和循环引用等情况，不让监控 SDK 自己触发一轮新的异常上报。采集失败应受到限流和保护，同时保留可诊断的简短状态，不能为了记录一个错误把页面主流程也阻塞。
