# 怎么写一个类型守卫？

## 核心回答

1. 类型守卫就是通过运行时条件缩小值的可能类型。先明确这个检查究竟要保证哪些字段。用户类型要求字符串编号和名称，守卫接收 `unknown`，返回类型标注为 `value is User`，函数内部检查字段并返回布尔值。返回 `true` 时，调用方就可以在对应分支中按用户类型读取属性。

2. 检查顺序通常是先确认它是非空对象，再确认字段存在，最后判断字段值的类型。只检查对象上有 `name` 还不够，因为它可能存的是数字。直接对空值使用属性判断也会出错，前面的条件需要真正保护后面的访问。

3. 守卫承诺的类型要和检查范围一致。用户还有必填的角色列表，就不能只检查名称后当成完整用户有效。嵌套字段也要继续验证，数组还要判断元素。业务只需要编号，就定义更小的输入结构，不必假装已经验证整个用户模型。

4. 编译器会相信显式类型谓词，但不会证明函数里的逻辑足以支持这个承诺，所以写出谓词不等于校验正确。只检查编号就返回真，调用方仍可能在名称缺失时出错。这类问题要靠认真核对声明和测试异常输入发现。

5. 用合法对象、空值、缺字段和字段类型错误的例子验证守卫，并明确可选字段的规则。字段缺失可能允许，字段存在但类型错误通常不能放过。希望自动转换输入，更适合返回转换结果，别让一个看似只判断的函数偷偷修改数据。

## 追问：为什么只检查 name 存在，不能宣称输入是完整 User？

1. 属性存在只证明有这个名字，不证明值的类型，也不证明其他必填字段齐全。`name` 是数字而编号不存在的对象仍能通过简单的存在检查，随后调用字符串方法就会失败。问题出在守卫承诺大于实际验证。

2. 对照目标类型逐个列出必要条件：字符串字段检查类型，列表检查容器和成员，可选字段检查允许缺失的情况。如果只需要用户名，就把返回类型限制为这个最小结构，让调用方无法误以为其他用户资料也已被检查。

3. 另外，`in` 可以检查到原型链上的属性。接口约定要求对象自身提供字段，还需要确认自有属性。该要求要和输入来源匹配。普通 JSON 对象与任意脚本对象的边界不同，不能盲目把一种检查当成适合所有来源。

## 追问：守卫返回 false 时，也必须保证类型含义正确吗？

1. 必须考虑。类型谓词同时影响成功和失败分支，不能只保证返回真时看起来合理。输入是字符串或数字，却把「数字且大于零」写成数字守卫，返回假时仍可能是负数，但编译器可能按排除数字来理解。

2. 这时把类型识别和业务条件拆开：先确认数字，再单独判断是否大于零。这样失败可以明确区分不是数字和数字不符合范围，不会借助过强的谓词让另一条分支得到错误结论，后续调用也更容易读懂。

3. 测试不能只放正常数据，还应加入零、负数和空字符串等边界，分别观察两个分支是否符合声明。检查本来只表示业务资格，可以返回普通布尔值或具体结果对象，不必为了得到收窄效果强行写类型谓词。
