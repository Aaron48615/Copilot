# 了解哪些设计模式？说说单例和观察者

## 核心回答

1. 我会把设计模式理解成处理常见代码关系的办法，重点是说明它解决了什么重复问题。单例负责共享同一实例，工厂集中创建过程，代理在访问目标时增加控制，装饰器则在原有能力外组合新功能，不需要为了用模式而先写很多类。

2. 单例常见的实现是把实例保存在闭包或模块中，第一次获取时创建，后面直接返回缓存。假设页面需要统一控制一个提示窗口，这样能避免各处重复创建，但共享状态也会影响测试，所以实例里不应该随意堆放所有页面的数据。

3. 观察者模式是目标维护订阅者，状态变化时直接通知它们；发布订阅通常多一个事件中心，发送者和接收者通过事件约定联系。比如一个对象直接通知监听函数偏向观察者，而多个独立模块向公共事件中心登记消息则更像发布订阅。

4. 我会根据变化点选择模式，而不是把框架中的所有代码都贴上模式名称。模块顶层导出的实例通常能在同一模块加载环境内共享，但不同运行环境或不同模块身份可能产生多份实例，所以不能说用了 ESM 就保证整个系统只有一个对象。

## 追问：事件中心实现了订阅，为什么还要设计取消订阅？

1. 事件中心会持有监听函数，而监听函数可能通过闭包引用页面数据。如果页面卸载后没有取消订阅，它仍可能收到消息，也可能让已经无用的数据继续被引用，造成重复执行和内存占用。

2. 假设我要实现一个简单事件中心，会让订阅方法返回取消函数，由使用者在离开页面时调用。取消应针对本次注册的监听记录，避免只按事件名删除全部监听，误伤其他仍在使用该事件的页面。

3. 还要约定通知过程中的行为，例如一个监听抛错是否继续通知其他人，监听期间新增的函数是否本次执行。可以先复制监听列表再遍历，让规则更清楚，但异常是否隔离仍要根据业务要求决定。

## 追问：共享请求实例适合放用户登录状态吗？

1. 在单个浏览器页面内，共享基础地址和通用请求配置通常比较方便。但令牌会变化，若创建实例时把它固定在闭包里，退出或切换账号后可能继续使用旧值，因此需要明确读取和更新的位置。

2. 如果是假设的服务端渲染场景，进程中的模块实例可能服务多个用户。把某个用户的凭据写进全局共享对象就存在串用风险，此时应按请求传入凭据，或为每次请求创建独立的上下文对象。

3. 测试也需要考虑实例中的状态是否残留，例如前一个用例添加的拦截器影响后一个用例。可以让创建函数接收配置，测试时获得独立实例；单例带来的方便不能替代对状态归属和生命周期的判断。
