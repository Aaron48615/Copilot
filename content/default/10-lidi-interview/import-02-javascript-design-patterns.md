# 了解哪些设计模式？说说单例和观察者

## 核心回答

1. 设计模式是处理常见代码关系的办法，重点是它解决了哪类重复问题。单例：大家共用同一个实例。工厂：创建过程集中在一处。代理：访问目标时加一层控制。装饰器：在原有能力外面再组合新功能。不必为了用模式先写一堆类。

2. 单例常见写法是把实例放在闭包或模块里，第一次获取时创建，后面直接返回缓存。页面要统一控制一个提示窗口，就能避免各处重复创建。共享状态也会拖累测试，实例里别随意堆所有页面的数据。

3. 观察者：目标自己维护订阅者，状态变了直接通知它们。发布订阅：中间多一个事件中心，发送方和接收方靠事件名约定。一个对象直接通知监听函数，更像观察者；多个独立模块往公共事件中心登记消息，更像发布订阅。

4. 按真正会变的那一点来选模式，别给框架里每段代码都贴模式名。模块顶层导出的实例，同一模块加载环境里通常能共享；换一个运行环境，或模块身份不一样，可能出现多份。用了 ESM，不保证整个系统只有一个对象。

## 追问：事件中心实现了订阅，为什么还要设计取消订阅？

1. 事件中心握着监听函数，监听函数又可能通过闭包引用页面数据。页面卸了却没取消订阅，它仍可能收到消息，已经没用的数据也卸不掉，既会重复执行，也会占内存。

2. 简单事件中心可以让订阅方法返回取消函数，离开页面时由使用者调用。取消应对准这一次注册的那条记录，别只按事件名把全部监听删掉，误伤还在用这个事件的其他页面。

3. 通知过程中的规则也要定：一个监听抛错，后面的还通不通知；通知过程中新加的函数，这一轮算不算。可以先复制监听列表再遍历，规则更清楚。异常隔不隔离，还是跟业务要求走。

## 追问：共享请求实例适合放用户登录状态吗？

1. 单个浏览器页面里，共享基础地址和通用请求配置通常方便。但令牌会变，创建实例时把它固定在闭包里，退出或切账号后可能还在用旧值。读和更新令牌的位置要说清楚。

2. 服务端渲染的话，进程里的模块实例可能服务多个用户。某个用户的凭据写进全局共享对象，有串用风险。应按请求传入凭据，或给每次请求单独一份上下文。

3. 测试还要看实例里的状态会不会残留，比如前一个用例加的拦截器影响后一个用例。创建函数接收配置，测试时拿到独立实例。单例图方便，替不了把状态归属和生命周期想清楚。
