# `useMemo` 和 `useCallback` 有什么区别？

## 核心回答

1. `useMemo` 保存一次计算的结果，`useCallback` 保存函数引用，两者都会根据依赖是否变化决定是否复用。前者会在渲染阶段执行计算函数，后者不会替我执行传入的业务函数，只是把函数返回给组件使用。两者都不能代替正常的状态管理。

2. 比如一个较大的商品列表需要筛选和排序，可以用 useMemo 保存计算结果，依赖列表和筛选条件。这样输入无关的表单字段时有机会跳过重复计算，但首次计算的成本并不会消失。

3. useCallback 常见的用途是给经过 `memo` 包装的子组件传事件回调。如果父组件每次都传新函数，子组件的 prop 就发生了变化；稳定回调引用才可能让这部分比较发挥作用。

4. 依赖必须写完整，否则缓存可能返回基于旧条件的结果或旧闭包。即使函数引用稳定，子组件自己的 state、使用的 context 或其他 props 变化，仍然可能让它重新渲染。

5. 我会先确认重复计算或渲染是否真的慢，再决定要不要缓存，因为依赖维护和比较也有成本。缓存是性能优化，不能用来保证业务正确性；是否启用 React Compiler 也要看项目配置，不能仅凭 React 版本判断。

## 追问：用了 useCallback，子组件为什么还是重新渲染？

1. 我会先确认子组件是否使用了 memo，普通子组件不会因为一个函数稳定就自动跳过父组件触发的渲染。useCallback 控制的是引用，不是一个阻止渲染的指令。排查时我会用组件分析工具确认具体是哪项输入导致更新。

2. 再看其他 props，例如父组件每次创建的 options 对象、数组或 JSX，都可能发生引用变化。也要检查回调自己的依赖，依赖频繁变化时返回新函数本来就是正确行为。

3. 最后区分父组件传参变化与子组件自身状态、context 更新，后两者并不由这一个回调控制。如果页面没有可感知的卡顿，我不会为了让渲染次数变成零而不断增加比较逻辑。

## 追问：useMemo 里面能发请求或者修改原数组吗？

1. 我不会在里面发请求，因为它运行在渲染阶段，计算应该保持纯粹。开发环境可能额外调用计算函数来检查问题，而某次渲染也未必提交，网络请求不该依赖这种调用次数。

2. 如果需要排序，我会先复制输入数组再排序，例如 `[...items].sort(compare)`。直接对 props 或 state 数组调用 sort 会修改原数据，其他组件可能因此看到未经正常状态更新的变化。

3. 请求应放在合适的数据获取机制、事件处理或 Effect 中，再根据请求结果做纯计算。useMemo 里的局部新对象可以构建和修改，关键是不改变组件外部已有的数据，也不产生可观察的外部副作用。相同输入下，计算应给出可预测的结果。
