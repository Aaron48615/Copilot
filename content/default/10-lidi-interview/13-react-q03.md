# `useMemo` 和 `useCallback` 有什么区别？

## 核心回答

1. `useMemo` 保存一次计算的结果，`useCallback` 保存函数引用。两者都看依赖变没变，决定复不复用。前者会在渲染阶段执行计算函数，后者不会替你执行传入的业务函数，只是把函数还给组件用。两者都不能代替正常的状态管理。

2. 比如一个比较大的商品列表要筛选、排序，用 `useMemo` 存计算结果，依赖列表和筛选条件。输入无关的表单字段时，有机会跳过重复计算。但第一次计算的成本不会消失。

3. `useCallback` 常见用法是给经过 `memo` 包装的子组件传事件回调。父组件每次都传新函数，子组件的 prop 就变了。回调引用稳住，这部分比较才可能起作用。

4. 依赖必须写全，不然缓存可能返回基于旧条件的结果或旧闭包。就算函数引用稳了，子组件自己的 state、用到的 context 或其他 props 变了，仍可能重渲染。

5. 先确认重复计算或渲染是不是真的慢，再决定要不要缓存。依赖维护和比较本身也有成本。缓存是性能优化，不能拿来保证业务正确。有没有启用 React Compiler，看项目配置，别只凭 React 版本判断。

## 追问：用了 useCallback，子组件为什么还是重新渲染？

1. 先看子组件有没有用 `memo`。普通子组件不会因为一个函数稳住，就自动跳过父组件触发的渲染。`useCallback` 管的是引用，不是阻止渲染的指令。用组件分析工具看，具体是哪项输入导致更新。

2. 再看其他 props。父组件每次新建的 options 对象、数组或 JSX，都可能引用变了。回调自己的依赖频繁变化时，返回新函数本来就是对的。

3. 最后分清是父组件传参变了，还是子组件自身状态、context 更新。后两者不由这一个回调控制。页面没有可感知的卡顿，不必为了让渲染次数变成零，越加越多比较逻辑。

## 追问：useMemo 里面能发请求或者修改原数组吗？

1. 别在里面发请求。它跑在渲染阶段，计算应该保持纯粹。开发环境可能额外调用计算函数来检查问题，某次渲染也未必提交。网络请求不该依赖这种调用次数。

2. 需要排序，先复制输入数组再排，比如 `[...items].sort(compare)`。直接对 props 或 state 数组调 `sort` 会改原数据，别的组件可能因此看到未经正常状态更新的变化。

3. 请求放在合适的数据获取机制、事件处理或 Effect 里，再根据请求结果做纯计算。`useMemo` 里的局部新对象可以构建、可以改，关键是别改组件外部已有的数据，也别产生可观察的外部副作用。同样输入，计算该给出可预测的结果。
