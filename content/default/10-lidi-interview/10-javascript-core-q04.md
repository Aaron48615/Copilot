# `==` 和 `===` 有什么区别？

## 核心回答

1. `===` 是严格相等，类型不同就返回假，不会为比较主动转换类型。`==` 是宽松相等，会按双方类型执行特定转换，例如数字一与字符串 `'1'` 宽松相等，但严格比较不相等。

2. 我不会把宽松相等概括成“全部转成字符串”或“全部转成数字”。例如 `null == undefined` 是专门的规则，`null == 0` 却是假；对象与基本值比较还可能触发对象转基本值，因此结果需要按规则判断。

3. 对象之间两种比较通常都看是否为同一引用，而不会逐个比较字段。两个分别创建的 `{ id: 1 }` 即使内容一致，严格相等仍是假；如果要判断是不是同一商品，应该按约定比较商品 ID，并先确认接口里的标识类型一致；只有确实需要比较全部内容时，才进一步定义字段级的相等规则。

4. 严格相等也有要记住的数字边界：`NaN === NaN` 是假，正零和负零严格相等。判断一个值是不是 `NaN` 可以用 `Number.isNaN`，需要区分正负零等特殊值时再考虑 `Object.is`。

5. 业务中我优先用严格相等，在接口或表单入口统一类型，并单独校验非法输入。`value == null` 可以用于合并判断空值，但要遵守项目规范，也要知道浏览器历史对象 `document.all` 存在特殊兼容行为。

## 追问：为什么空数组与 false 宽松相等，但放进 if 又为真？

1. `if ([])` 只需要做布尔转换，对象包括空数组都属于真值。这里不会因为数组没有元素就变成假，所以判断数组是否为空应该查看 `length`，不能只判断数组对象本身。

2. `[] == false` 执行的是宽松相等算法，布尔值先变成数字零，数组再转成基本值。空数组通常得到空字符串，继续与数字比较会转成零，所以这个表达式是真，两种场景用的转换过程不同。

3. 我不会在业务条件里依赖这种结果，例如需要判断“没有选中商品”时就明确判断选中数组长度。遇到输入既可能是数组又可能是布尔值的接口，还应先规范数据结构，避免一个判断同时承担类型猜测和业务判断。

## 追问：表单里的数字字符串应该先转数字再比较吗？

1. 如果字段业务含义确实是数量，我会先检查空字符串，再转换并验证结果。直接 `Number('')` 会得到零，而“没有填写”和“填写零”可能有不同含义，转换成功不等于输入符合要求。

2. 转换后还要按字段要求检查有限数、整数和允许范围。例如购买数量一般不能是负数或小数，`Number.isFinite` 与 `Number.isInteger` 解决的是不同问题，不能只依靠和零做一次比较。

3. 如果字段是商品编号或订单编号，即使看起来全是数字，也可能需要保留前导零，或者超过安全整数范围。这种数据更适合保留字符串，统一双方类型后再比较，而不是为了让严格相等通过就强行转成数字。
