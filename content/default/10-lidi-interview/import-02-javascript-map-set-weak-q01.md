# WeakMap 为什么不能遍历？

## 核心回答

1. WeakMap 不能遍历，是因为它不把键强行保活，而键何时被垃圾回收又不是业务可以控制的。如果提供完整键列表，程序就可能通过列表变化观察回收时机，同一段逻辑的结果也会受内存压力等运行环境因素影响。

2. 所以它只支持拿着已知键进行读写、判断和删除，没有 `keys()`、普通迭代入口或 `size`。这里的限制是不能枚举未知条目，并不是数据写进去后就不能读取；只要仍然持有合法键，就能按这个键查询对应信息。

3. 例如假设要给页面节点保存一次计算结果，可以用节点作为键，结果作为值。节点从页面移除且其他强引用也消失后，这张表不会仅仅因为保存了键就阻止回收，省去了为每个失效节点维护缓存索引的负担。

4. 但移除节点不等于它立即不可达，闭包、数组或事件订阅仍可能保存引用。而且值在键仍存活时也可能占用很多内存，因此我不会把弱映射描述成自动管理所有缓存的方案，更不会承诺某个时刻一定释放。

5. 如果需求包含展示全部缓存、统计数量或按最近使用情况淘汰，我会选择 Map 并明确清理策略。当前规范允许弱映射使用对象和未注册的 Symbol 作为键，不能再简单背成只允许对象，但字符串业务编号仍不适合直接放进去。

## 追问：额外用数组保存全部键能弥补不能遍历吗？

1. 数组如果直接保存每个对象键，就建立了新的强引用。即使 WeakMap 本身不保活这些键，数组仍让它们可达，结果是遍历能力补上了，原本希望随对象生命周期释放的效果却被另一个容器破坏。

2. 假设这些键是已经离开页面的节点，长期保存它们的调试数组也可能让相关对象一直留下。排查时应检查整个引用链，而不是看到用了弱映射就排除缓存问题；一个辅助索引同样属于需要管理的业务状态。

3. 如果确实要列出全部条目，我会直接使用 Map，并在组件销毁或容量到限时删除对应记录。这样数量与清理行为都可解释，也比同时维护一份强引用列表和一张弱映射更容易验证，避免两份数据更新不同步。

## 追问：WeakMap 的值引用自己的键会导致永远不能回收吗？

1. 仅有条目内部的值回指键，不会自动让这一对数据永久存活。弱映射的回收语义会考虑键是否能从外部强引用路径到达，因此不能把它简单画成普通对象的相互引用，再据此断定必然泄漏。

2. 但如果外部另外保存了这个值，而值又保存着键，就形成了真实的外部强引用路径。假设全局数组保存元数据，元数据包含节点，节点就仍然可达，问题出在这条外部路径，弱映射无法替其他对象解除引用。

3. 所以分析内存时，我会先找谁仍持有对象，再判断缓存结构是否合适。清理方案应针对全局数组、订阅或闭包等实际持有者，不能只把 Map 换成 WeakMap 就宣布解决，也不应通过固定延时断言回收已经发生。
