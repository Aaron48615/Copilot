# 为什么不把 Token 都放 localStorage？

## 核心回答

1. 我不会把所有 Token 都放 localStorage，因为它能被当前源里的 JavaScript 读取。只要发生 XSS，或者引入的同源执行脚本被污染，令牌就可能被拿走；存进去之前做前端加密也不能阻止能执行代码的攻击者使用它。

2. 它的优势是接入简单、刷新后仍存在，但长期保留也意味着共享设备和退出清理的问题。sessionStorage 生命周期更短，IndexedDB 读取异步，但它们同样不是隔离同源恶意脚本的保险箱，换一个存储 API 不自动解决 XSS。

3. 如果后端方案允许，可以把短期访问令牌放内存，把刷新凭据放受限的 HttpOnly Cookie。HttpOnly 限制脚本读取，Secure 限制安全传输条件，SameSite 减少某些跨站携带，但仍要配合 CSRF 与服务端会话设计。

4. 具体方案要看应用是否需要刷新恢复、多标签共享和跨站登录。Cookie 自动携带与 Authorization 手动携带有不同边界，我会先明确凭据如何发送、如何过期和撤销，再选存储，而不是只给一个所有项目通用的答案。

5. 若现有项目仍用 localStorage，我会如实说明，并优先控制令牌权限和有效期、修复注入点、退出清理。如果继续完善再与后端调整认证流程，不能单靠前端把数据搬到内存，就宣称已经实现完整的安全会话。

## 追问：Token 放内存，刷新页面后怎样保持登录？

1. 内存状态会随页面上下文销毁，刷新后需要重新建立会话。常见设计是浏览器携带受限的刷新 Cookie 调用服务端，换取新的短期访问令牌；这需要后端接口支持，不是前端变量自己恢复出来的。

2. 初始化期间界面要有明确的认证检查状态，避免先把用户跳到登录页，再因为刷新成功闪回业务页。刷新失败则清理当前会话，不能不断循环尝试；多个请求需要等待同一次认证初始化结果。

3. 我会把用户资料缓存和真实登录状态分开，本地保存的头像或用户名只能用于展示，不能证明已登录。还要验证页面刷新、Cookie 过期和服务端撤销三种情况，确认都能得到一致的访问结果。

## 追问：换成 HttpOnly Cookie 后，XSS 就没有影响了吗？

1. 没有。HttpOnly 阻止 JavaScript 直接读取该 Cookie，但浏览器仍可能为同源请求自动携带它。恶意脚本可以利用当前页面身份调用接口、读取响应或修改界面，即使不知道 Cookie 的具体字符串。

2. 因此防护重点仍包括输出编码、富文本清洗和减少危险脚本执行，Cookie 属性只是限制某一类令牌盗取方式。敏感操作还应在服务端重新校验权限，必要时要求额外确认，不能信任前端已经隐藏按钮。

3. 我会用受控测试确认 Cookie 确实不能被 document.cookie 读到，同时验证业务请求和 CSRF 防护。不能把这项测试通过等同于整个站点不存在 XSS，也不能因此在页面里随意放其他敏感数据。
