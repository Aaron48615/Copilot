# 为什么不把 Token 都放 localStorage？

## 核心回答

1. Token 不该都放 `localStorage`，因为它能被当前源里的 JavaScript 读到。只要发生 XSS，或者引入的同源执行脚本被污染，令牌就可能被拿走。存进去之前做前端加密，也挡不住能执行代码的攻击者去用它。

2. 它的好处是接入简单，刷新后还在，但长期保留也意味着共享设备和退出清理的问题。`sessionStorage` 生命周期更短，IndexedDB 读取是异步的，但它们同样不是隔离同源恶意脚本的保险箱。换一个存储 API，不会自动解决 XSS。

3. 如果后端方案允许，可以把短期访问令牌放内存，把刷新凭据放受限的 HttpOnly Cookie。HttpOnly 限制脚本读取，Secure 限制安全传输条件，SameSite 减少某些跨站携带。但这仍要配合 CSRF 和服务端会话设计。

4. 具体方案看应用要不要刷新恢复、多标签共享、跨站登录。Cookie 自动携带，和 Authorization 手动携带，边界不一样。先明确凭据怎么发送、怎么过期和撤销，再选存储。没有一个所有项目通用的答案。

5. 若现有项目仍用 `localStorage`，如实说，并优先控制令牌权限和有效期、修注入点、退出时清掉。再跟后端调整认证流程。不能单靠前端把数据搬到内存，就宣称已经做成完整的安全会话。

## 追问：Token 放内存，刷新页面后怎样保持登录？

1. 内存状态会随页面上下文销毁，刷新后需要重新建立会话。常见设计是浏览器带着受限的刷新 Cookie 调服务端，换取新的短期访问令牌。这需要后端接口支持，不是前端变量自己恢复出来的。

2. 初始化期间界面要有明确的认证检查状态，避免先把用户跳到登录页，再因为刷新成功闪回业务页。刷新失败就清当前会话，不能不停循环尝试。多个请求要等同一次认证初始化的结果。

3. 用户资料缓存和真实登录状态要分开。本地保存的头像或用户名只能用于展示，不能证明已经登录。还要验证页面刷新、Cookie 过期、服务端撤销这三种情况，确认访问结果一致。

## 追问：换成 HttpOnly Cookie 后，XSS 就没有影响了吗？

1. 没有。HttpOnly 拦住 JavaScript 直接读这个 Cookie，但浏览器仍可能为同源请求自动带上它。恶意脚本可以利用当前页面身份调接口、读响应或改界面，即使不知道 Cookie 的具体字符串。

2. 所以防护重点仍包括输出编码、富文本清洗、减少危险脚本执行。Cookie 属性只是限制某一类令牌盗取方式。敏感操作还应在服务端重新校验权限，必要时要求额外确认。不能信任前端已经把按钮藏起来了。

3. 用受控测试确认 Cookie 确实不能被 `document.cookie` 读到，同时验证业务请求和 CSRF 防护。这项测试通过，不等于整个站点不存在 XSS，也不能因此在页面里随便放其他敏感数据。
