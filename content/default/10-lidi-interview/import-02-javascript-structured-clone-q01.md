# 和 JSON 深拷贝相比好在哪里？

## 核心回答

1. 我理解它最大的优势是保留更多数据类型和对象之间的关系，而不只是把对象变成文本再解析回来。比如日期、映射集合和包含循环引用的数据，用结构化克隆能按支持的类型恢复，普通的字符串化再解析则会丢信息或失败。

2. JSON 适合表达约定好的文本数据，但用来深拷贝时有一些容易被忽略的变化，例如日期变成字符串，非有限数字变成空值。对象里的未定义值属性会被省略，数组里的对应位置却变成空值，结果可能改变后续判断的含义。

3. 结构化克隆还能保留同一份数据内部的共享引用，两个字段原本指向同一个子对象，克隆后仍指向同一个新子对象。它们通常不再指向原对象，这与把相同内容各复制一次不同，对缓存关系和循环结构尤其重要。

4. 不过它不是完整复制任何对象的方法，函数和弱引用集合不能直接克隆，自定义类的原型行为也不会原样恢复。即使没有报错，克隆后的值也可能失去原来的方法，因此我会先确认数据主要是状态还是带行为的实例。

5. 如果只是改列表中的一个条目，我通常会沿修改路径浅复制，让未修改部分继续共享，而不是整份深拷贝。若确实需要独立快照，再根据数据类型选择结构化克隆，并用真实数据规模测量成本，不会直接宣称它一定更快。

## 追问：两个字段指向同一个对象，克隆后还相等吗？

1. 假设原对象的作者和审核人都指向同一个用户对象，结构化克隆会记录已经访问过的对象关系。克隆结果里的这两个字段仍然严格相等，但一般不再等于原来的用户对象，所以关系被保留，普通对象本身则被重新创建。

2. 这点会影响修改结果，例如修改克隆结果里作者的名称，审核人名称也会随之变化，因为它们仍是同一个对象。若业务实际要求两份独立人物快照，就需要显式分别构造，不能以为一次深拷贝会自动拆开全部共享关系。

3. 循环引用也用类似的关系记录来处理，原对象指向自己时，结果会指向克隆后的自身，而不是无限递归。验证时除了比较字段值，我会检查这些引用关系以及修改结果是否影响原数据，避免只看打印内容得出错误结论。

## 追问：纯接口数据能继续用 JSON 复制吗？

1. 如果数据约定明确只有普通对象、数组和允许的基本值，而且需要的就是文本序列化结果，使用 JSON 可以成立。关键是清楚知道它的限制，而不是把任意运行时对象传进去后，默认所有类型与引用关系都能还原。

2. 假设接口返回的日期本来就是字符串，字符串化并不会额外破坏日期对象，因为此时根本没有日期实例。但如果应用已经把它转换成日期或加入未定义值，再沿用同一复制方式就可能改变数据，边界应以当前实际值为准。

3. 对于只想避免误改状态的场景，我会先考虑局部浅复制，通常没有必要绕一圈文本转换。若必须保留快照，我会为约定内的数据准备样例，检查空值、特殊数字和共享引用，并把性能比较放在具体数据上进行。
