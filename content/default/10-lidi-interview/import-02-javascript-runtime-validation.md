# TypeScript 项目为什么还需要运行时校验？

## 核心回答

1. TypeScript 检查的是开发时的代码关系，接口真正返回什么要等程序运行后才知道，类型声明不会替服务器检查响应。即使把结果断言成用户对象，缺少名称的实际数据也不会自动补齐，调用字符串方法时仍可能报错。

2. 我会把接口、地址参数、浏览器缓存和上传内容视为外部输入，在确认结构前按未知数据处理。先检查它是不是预期的对象，再检查必要字段和取值范围，只有通过这些判断后，才交给依赖具体类型的业务代码。

3. 规则少时可以手写判断，结构复杂或多个入口复用时可以使用校验库，让字段路径和失败原因更一致。选工具之前仍要想清楚哪些字段必填、空值代表什么、额外字段是否允许，否则写了规则也未必表达了真实约定。

4. 结构合法和业务可用还需要分开，例如订单金额是有限数字不代表价格正确，订单状态属于枚举也不代表允许退款。业务规则应在对应层判断，服务端继续承担权威校验，前端主要保护交互并尽早发现接口不一致。

5. 校验失败后的处理也是设计的一部分，可选头像可以用占位图，关键标识错误就应该停止操作。如果让我接入这套流程，我会让接口模块返回可信结果或明确错误，并准备缺字段、错误类型和旧缓存等样例验证降级行为。

## 追问：把响应写成泛型或类型断言为什么还不够？

1. 泛型和类型断言描述的是编译器应该如何看待一个值，不会在响应到达时执行字段检查。假设请求函数允许调用方写任意结果类型，那么同一份响应既能被声明成用户也能被声明成订单，实际数据却没有发生变化。

2. 我会让未知响应经过真正执行的检查，例如确认用户编号是非空字符串，名称缺失时按约定报错。成功分支再返回用户类型，这样类型信息才有运行时判断作为依据，而不是靠调用方的期待直接跨过数据边界。

3. 手写类型守卫也可能写错，例如只检查对象存在就声称所有字段都正确，因此不能只看函数签名。验证时应喂入空值、数组、缺失字段和错误类型，确认失败样例确实被拒绝，关键规则再与接口约定保持同步。

## 追问：数字字符串应该自动转成数字吗？

1. 我会先看接口有没有允许两种表示，而不是为了让校验通过就全部转换。地址参数天然是文本，把合法的页码字符串转成整数通常合理；如果接口约定金额必须是数字，突然返回字符串可能是需要暴露的约定变更。

2. 转换前要检查空白、格式和范围，因为某些宽松转换会把空字符串变成零，或者只读出前半段数字。分页可以明确接受正整数文本，再检查上限；金额则还要考虑精度和单位，不能复用一个没有边界的万能转换函数。

3. 转换规则应集中且可观察，成功后输出应用内部统一的类型，失败则说明是格式不符还是超出范围。假设为了兼容旧接口临时接受两种表示，我会明确记录兼容条件和退出计划，避免坏数据长期被悄悄修饰成正常结果。
