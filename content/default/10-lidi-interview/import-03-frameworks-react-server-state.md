# React 里的服务端数据和 UI 状态怎么分？

## 核心回答

1. 服务端数据的最终来源在服务器，例如商品列表、订单和用户资料；前端持有的是某次获取的副本。它需要考虑加载、错误、缓存新鲜度和重新获取，不能因为已经放进 state 就认为前端可以永久决定它的真实内容。

2. 界面状态由当前交互决定，例如弹窗开关、排序面板是否展开和未提交的表单草稿。这类数据通常放在最靠近使用者的组件，跨组件确实需要同步时再提升，不必跟着接口数据一起全部进入全局状态库。

3. 查询条件介于两者的使用关系中：条件是用户选择的，结果由服务器返回。需要分享和后退恢复的条件可以进入 URL，查询缓存按条件组织；输入框正在编辑的文字和已经发起查询的条件也可以有意区分，避免每个按键都触发请求。

4. 我会避免重复保存可推导的值，例如列表条目数和已选数量直接计算。服务端数据可以使用专门的查询管理方案，也能在简单页面手动请求；选择库不是关键，关键是明确取消、过期、重试和修改后的同步规则。

5. 例如编辑商品时，服务器商品、编辑草稿和保存状态应分开。保存失败保留草稿，成功后使用服务端确认的结果刷新缓存；退出登录时处理个人数据范围，不能把旧缓存当成无条件可复用的公共数据，这些边界比仅按变量名分类更重要。

## 追问：接口数据已经在查询缓存里，还要复制到 Redux 吗？

1. 通常不需要再复制一份相同结果，否则查询刷新和 Redux 更新可能先后不一致。若两个地方都可以修改商品名称，组件究竟读哪一份会越来越难解释，也会重复实现加载、错误和失效处理。

2. 可以由查询缓存保存服务端结果，Redux 或本地状态保存选中编号、操作面板等界面信息。需要组合展示时通过选择和计算得到结果，不必为了让一个组件读取方便就把完整接口数据搬到另一个容器。

3. 若确有独立用途，例如离线编辑草稿或提交快照，应明确那是另一种业务数据，并说明何时创建和合并。复制行为可以有理由，但不能只因为“项目已经使用 Redux”就让两套系统都承担同一缓存职责。

## 追问：用户退出后，只删除 token 够不够？

1. 不够，页面内存和查询缓存里可能仍有个人订单、地址和资料。删除 token 只影响后续认证方式，已经获取的数据不会自动消失，应让身份变化同时触发相关缓存、界面状态和未完成请求的处理。

2. 请求结果也要与身份对应。退出后旧请求才返回，如果仍然写入缓存，就可能重新把个人数据放回界面；可以取消请求并判断账号或请求版本，确保旧身份的数据不再提交到新会话中。

3. 公共数据不一定要全部清空，例如不含个人信息的商品分类可以保留。重点是根据数据范围区分清理，并验证连续登录两个账号时没有短暂串用，不能只检查登录按钮已经变成未登录状态。
