# 为什么不把所有数据都放进 Redux？

## 核心回答

1. 我按使用范围与生命周期决定状态放哪里。城市视图的登录用户、Token 和主题会被多个页面读取，放 Redux Toolkit 便于统一更新与恢复；某张图表的加载状态或一个弹窗开关只服务本页，放组件内部通常更直接。

2. auth 和 app 会持久化，分别包含身份与主题相关内容。持久化只是恢复前端状态，不代表 Token 仍有效，也不意味着所有临时数据都应该保存，接口失效后仍要清理并重新确认身份。

3. 图表 option 通常可以由业务数据与配置计算得到，不一定需要再存成另一份全局对象。否则筛选变化既要改原数据又要改 option，容易漏同步；ECharts 实例、DOM 与观察器更适合放 ref，不属于可序列化业务状态。

4. 把数据放 Redux 也不表示每次更新一定让所有组件重新渲染，实际还取决于订阅、selector 与相等判断。但大量无必要全局字段会增加更新来源和选择器维护成本，让一个简单交互更难追踪，这才是我控制范围的主要理由。

5. 若多个页面需要共享某组筛选，可以再集中管理或用 URL 表达可恢复条件。服务端数据缓存、界面状态和持久偏好需求不同，不能因为项目已有 Store 就全往里放；我会先明确谁修改、谁读取以及什么时候失效。

## 追问：为什么 ECharts 实例不适合放 Redux？

1. 图表实例包含方法、DOM 引用与内部资源，不是普通可序列化数据。放进 Store 后，持久化、调试快照与状态回放都难以处理，也可能让已经卸载的容器被长时间引用，增加清理负担。

2. 组件用 ref 保存实例更符合生命周期：挂载创建，数据变化调用 setOption，卸载 dispose。Redux 可以保存用户选择的图表配置，但实际运行中的实例应由渲染组件管理，这两者不需要共用存储位置。

3. 如果别的组件需要操作图表，可以通过明确的组件接口或共享配置触发更新，而不是让所有页面随意拿全局实例调用方法。这样主题切换或实例重建时，旧引用不会散落在多个业务模块里。

## 追问：筛选条件应该放 URL、局部状态还是 Redux？

1. 希望复制链接后复现的条件，例如城市与日期范围，适合考虑 URL。输入中的临时草稿则可以先留在组件，点击查询后再更新正式条件，避免每输入一个字符都改变页面地址和请求。

2. 多个页面共同使用且不适合放 URL 的偏好，可以进入 Store，但仍要决定退出登录是否清理、刷新是否恢复。仅一个页面使用的筛选无需为了“统一”而全局化，否则离开页面后还可能影响无关入口。

3. 我会检查同一条件是否出现两份可写来源，如果 URL 和 Redux 都保存城市，就明确谁是主来源以及如何同步。测试刷新、返回、复制链接和切换账号，能帮助验证选择的位置是否满足真实使用方式。
