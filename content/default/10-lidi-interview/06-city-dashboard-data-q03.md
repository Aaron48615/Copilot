# 为什么不把所有数据都放进 Redux？

## 核心回答

1. 看谁要用、用多久。城市视图的登录用户、Token、主题，好几个页面都会读，放 Redux Toolkit 方便一起更新、一起恢复。某张图的加载状态、一个弹窗开关只服务本页，放组件里更直接。

2. `auth` 和 `app` 会持久化，分别装着身份和主题相关内容。持久化只是把前端状态找回来，不代表 Token 还有效，也不等于临时数据都该存。接口失效了还得清掉，再重新确认身份。

3. 图表 `option` 通常能从业务数据和配置算出来，不一定再存一份全局对象。不然筛选一变，原数据和 `option` 都得改，容易漏同步。ECharts 实例、DOM、观察器更适合放 ref，不是能序列化的业务状态。

4. 数据进了 Redux，也不等于每次更新所有组件都重渲染，还看订阅、selector 和相等判断。但没必要的全局字段一多，更新来源和选择器都更难跟。一个简单交互就不好追，范围才要收住。

5. 好几个页面要共享一组筛选，可以再集中管，或者用 URL 把能恢复的条件写出来。服务端数据缓存、界面状态、持久偏好不是一回事。项目已经有 Store，也不用什么都往里塞。谁改、谁读、什么时候失效，先说清楚。

## 追问：为什么 ECharts 实例不适合放 Redux？

1. 图表实例带着方法、DOM 引用和内部资源，不是普通可序列化数据。塞进 Store，持久化、调试快照、状态回放都不好办，卸载掉的容器也可能被一直握着，清理更麻烦。

2. 组件用 ref 存实例更对得上生命周期：挂载时创建，数据变了调 `setOption`，卸载 `dispose`。Redux 可以存用户选的图表配置，真正跑着的实例由渲染组件管。这两样不用放同一个地方。

3. 别的组件要操作图表，走明确的组件接口或共享配置去触发更新，别让所有页面随便拿全局实例调方法。主题切换或实例重建时，旧引用就不会散落在好几个业务模块里。

## 追问：筛选条件应该放 URL、局部状态还是 Redux？

1. 复制链接还想复现的，比如城市和日期范围，适合考虑 URL。输入过程中的临时草稿可以先留在组件，点查询再更新正式条件，别每敲一个字就改地址、发请求。

2. 多个页面共用、又不适合放 URL 的偏好，可以进 Store，但退出登录清不清、刷新恢不恢复，得定下来。只有一页用的筛选，不必为了「统一」做成全局，离开页面后还可能影响无关入口。

3. 同一条件别出现两份可写来源。URL 和 Redux 都存城市，就要说清谁是主来源、怎么同步。刷新、返回、复制链接、切换账号都测一遍，看放的位置是不是真能这么用。
