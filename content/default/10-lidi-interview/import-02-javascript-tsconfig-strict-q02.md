# noUncheckedIndexedAccess 会带来什么变化？

## 核心回答

1. noUncheckedIndexedAccess 主要提醒我，下标或动态键对应的位置不一定真的有值。例如字符串数组的普通数字下标访问，结果会包含 undefined，这更接近空数组和越界时的运行行为，而不是默认任何位置都存在字符串。

2. 对带索引签名的对象也是类似的，动态读取一个没有明确声明存在的键，需要考虑缺失。已经声明为必填的属性仍按原类型读取，所以不能概括成开启以后所有对象属性都会变成可选，固定结构和开放字典要分开看。

3. 使用结果前，我倾向于先存到局部变量，再判断是否为 undefined，随后使用收窄后的值。这样既容易理解，也避免重复读取；如果合法值可能是零或空字符串，就不能简单用真假判断代替缺失判断，否则零库存也可能被误判为没有记录。

4. 遍历数组时，能直接拿元素就优先用 for...of 或数组迭代方法，减少不必要的下标读取。确实需要相邻元素或按位置配对时，仍要处理边界，不能因为循环条件比较了长度，就认为编译器一定能证明每次访问都安全。

5. 这个选项需要单独配置，strict 并不会自动打开它，实践中通常配合严格空值检查使用。假如要在旧项目启用，我会先处理字典查询和数组边界，再评估确实有保证的访问，避免用批量非空断言抵消它的作用。

## 追问：已经判断数组长度大于零，为什么首项仍可能提示为空？

1. 普通数组的类型主要描述元素类型，没有把每一个运行时长度条件都编码进结构。即使代码判断了长度，编译器也不一定把数组自动转换成首项必定存在的类型，所以提示并不意味着那个判断完全没有运行时价值。

2. 对只需要首项的逻辑，我会先读取首项并保存，再检查这个局部值是否为 undefined。这个写法直接证明了后续要用的值存在，比为了消除提示给整个数组强行加断言更明确，也少依赖复杂的推断规则。

3. 如果函数本身要求非空数组，可以用非空元组表达这个输入前提，但调用方必须先建立保证。来自接口的数组仍要检查，不能把可能为空的普通数组直接断言成非空元组，否则只是把未处理的情况藏进类型里。

## 追问：动态字典查不到键时，应该返回默认值还是让调用方处理？

1. 我会看缺失是否属于正常情况，例如缓存查询未命中就应该让调用方知道没有数据。若在字典工具里直接返回空对象，调用方反而分不清缓存没找到和确实存了一个空对象，后续处理容易混在一起。

2. 对展示用途的映射表，可以在明确约定下给默认标签，比如未知状态显示“未知”。但这个标签只负责界面兜底，不能据此认为状态合法，更不能自动把未知状态转换成可提交的正常状态。

3. 如果某些键按设计必须存在，我会把它们写成必填属性，或在初始化时验证完整性。开放的字符串索引适合数量和名称不固定的数据，不该为了写起来方便，把本来固定的配置也变成处处需要猜测的字典。
