# 怎么用 DevTools 排查？

## 核心回答

1. 用 DevTools 排查层级时，我会先选中目标元素，确认它实际存在、尺寸不为零、没有被 display 或 visibility 隐藏。再看计算后的 position、display 和 z-index，确认声明有效且参与当前布局，避免把元素没渲染误判成被其他元素盖住。

2. 下一步确定遮挡它的是哪个元素，并分别沿祖先查看层叠上下文创建条件。常见的是父容器有 transform、opacity 或明确层级，让子元素只能在内部比较；我会找到双方共同的外层比较位置，记录真正决定前后顺序的两个上下文。

3. 同时检查 overflow、clip-path 等裁剪条件，以及 fixed 的包含块。临时禁用一条可疑声明，看是覆盖关系恢复还是位置发生变化，能帮助区分问题。操作时一次验证一个因素，不能连续改十条 CSS 后只知道“好了”，却说不清哪条是原因。

4. Layers 面板可以辅助了解合成层和绘制情况，但合成层不等同于 CSS 层叠上下文，不能看见一层就直接推导 z-index 顺序。最终修复要落到实际样式或挂载结构，并重新验证滚动、动画和弹层开关，开发者工具里的临时修改本身不算完成。

5. 如果问题只在悬浮或打开动画时出现，我会固定对应状态再检查，而不是移开鼠标后读取已经恢复的样式。动态添加的类和内联值可能才是上下文来源，确认触发条件能避免把正常静态样式当成原因去修改。

## 追问：怎样区分菜单是被覆盖还是被父元素裁掉？

1. 观察消失边界是第一步。若菜单恰好沿父容器边缘被截断，裁剪的可能性较大；若另一个有明确背景的组件盖在上面，则更像层叠问题。但外观只能提供线索，还需要通过样式和边界进行验证。

2. 我会临时关闭相关祖先的 overflow 裁剪，或给菜单加轮廓显示实际盒子范围。如果内容恢复且前后顺序本来正确，就优先处理裁剪；若禁用裁剪仍被兄弟区域盖住，再继续查双方层叠上下文，可能两种问题同时存在。

3. 修复时不一定直接删除 overflow，因为父容器可能需要裁圆角图片或内部滚动。可以把装饰裁剪与菜单挂载分开，让图片留在裁剪区、菜单进入合适外层，避免为修复菜单又让卡片内容全部溢出。

## 追问：为什么 Layers 面板不能代替层叠上下文分析？

1. Layers 展示的重点是浏览器为绘制与合成采用的分层，CSS 层叠上下文则规定元素的前后顺序，两者目的不同。浏览器可能因为性能策略建立或合并图层，不能把图层数量直接当成上下文数量。

2. 我会用计算样式和祖先关系解释层叠，再用 Layers 查看某些变换、绘制区域和资源代价。比如发现一个大层可以提示检查动画成本，但仅凭它是独立层，不能证明里面的菜单可以超越所有外部元素。

3. 最终结论要能对应一条具体规则，例如父级建立上下文限制了子项，或 overflow 把超出部分裁掉。工具面板是证据来源，不是替代解释的术语；如果无法说清楚比较发生在哪两层，就还需要继续缩小例子。
