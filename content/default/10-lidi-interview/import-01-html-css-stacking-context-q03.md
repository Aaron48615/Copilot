# 怎么用 DevTools 排查？

## 核心回答

1. 用 DevTools 排层级，先选中目标元素，确认它确实在、尺寸不是零、没有被 `display` 或 `visibility` 藏起来。再看计算后的 `position`、`display` 和 `z-index`，确认声明有效、参与当前布局。别把元素没渲染，误判成被别的元素盖住。

2. 下一步确定挡住它的是哪个元素，分别沿祖先查看层叠上下文是怎么建出来的。常见是父容器有 `transform`、`opacity` 或明确层级，子元素只能在内部比。找到双方共同的外层比较位置，记下真正决定前后顺序的两个上下文。

3. 同时查 `overflow`、`clip-path` 这类裁剪，以及 `fixed` 的包含块。临时禁用一条可疑声明，看是覆盖关系恢复了，还是位置变了，能把问题分开。一次验一个因素。连续改十条 CSS 以后只知道「好了」，却说不清哪条是原因，下次还会栽。

4. Layers 面板能辅助看合成层和绘制情况，但合成层不等于 CSS 层叠上下文。看见一层，推不出 `z-index` 顺序。最终修复落到实际样式或挂载结构，再重新验滚动、动画和弹层开关。开发者工具里的临时修改，本身不算做完。

5. 问题只在悬浮或打开动画时出现，就把对应状态固定住再查，别移开鼠标以后去读已经恢复的样式。动态加上的类和内联值，才可能是上下文来源。确认触发条件，避免把正常静态样式当成原因去改。

## 追问：怎样区分菜单是被覆盖还是被父元素裁掉？

1. 先看消失边界。菜单刚好沿父容器边缘被截断，裁剪的可能性更大；另一个有明确背景的组件盖在上面，更像层叠问题。外观只提供线索，还得用样式和边界验证。

2. 临时关掉相关祖先的 `overflow` 裁剪，或给菜单加轮廓看实际盒子范围。内容回来了，前后顺序本来也正确，就优先处理裁剪。禁用裁剪仍被兄弟区域盖住，再查双方层叠上下文。两种问题也可能同时在。

3. 修复时不一定直接删 `overflow`，父容器可能要裁圆角图片或内部滚动。装饰裁剪和菜单挂载可以分开：图片留在裁剪区，菜单进合适外层。别为了修菜单又让卡片内容全部溢出来。

## 追问：为什么 Layers 面板不能代替层叠上下文分析？

1. Layers 看的是浏览器为绘制和合成采用的分层，CSS 层叠上下文规定元素前后顺序，目的不同。浏览器可能因为性能策略建立或合并图层，图层数量不能直接当上下文数量。

2. 用计算样式和祖先关系解释层叠，再用 Layers 看某些变换、绘制区域和资源代价。发现一个大层，可以提示去查动画成本。但它是独立层，证明不了里面的菜单能盖过所有外部元素。

3. 最终结论要能对上一条具体规则，比如父级建立上下文限制了子项，或 `overflow` 把超出部分裁掉。工具面板是证据来源，替代不了解释。说不清比较发生在哪两层，例子还得再缩小。
