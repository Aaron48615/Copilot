# 设计一个支持流式回答的聊天页面

## 核心回答

1. 我会先把一次提问拆成用户消息和一次助手生成，两者都有稳定 id，并关联会话。发送时先显示本地待发送状态，服务端确认后替换为正式记录；请求重试带同一个幂等键，避免重复点击产生两条用户消息。

2. 传输方式上，可以先 POST 创建生成任务，再用 EventSource 订阅服务端事件；也可以用 fetch POST 直接读取响应流。原生 EventSource 不能任意设置请求方法和请求头，需要自定义鉴权头或请求体时，fetch 方案更方便，但要自己负责解析与重连。

3. 我会约定 text、status、error、done 等业务事件，携带生成 id 和递增序号，前端据此更新对应助手消息。fetch 读到的是字节块，不是一条完整事件，要增量解码、保留未完成的行和事件，解析完整后才能消费。

4. 界面状态包括等待、生成中、完成、失败、中断和主动停止，只有收到业务完成事件或核对到服务端完成状态才显示完成。网络流的 done 只代表读完了传输，不能据此认定答案正常结束；切换会话也要隔离旧任务的迟到事件。

5. 收到文本后可以按帧批量追加，减少高频组件更新，并在完成时提交剩余缓冲。只有用户仍在底部附近才自动跟随，向上阅读后显示新内容提示；Markdown 渲染限制原始 HTML 和危险链接，不把模型输出当作可信页面代码。

6. 如果落地这个方案，我会把模型密钥、会话鉴权、生成超时和输出限制放在服务端，前端提供停止和重试入口。历史消息与生成状态需要持久化，断线后才能查询或恢复。还要区分只是重新连接，还是重新生成答案，避免一次断网让用户重复消耗生成次数。

## 追问：一个网络 chunk 不是一条事件，解析时怎么避免乱码和丢数据？

1. 中文字符的 UTF-8 字节可能跨两个 chunk，我会复用同一个 TextDecoder，并在分块解码时传 `stream: true`。正常读到流结束后再执行最终解码，把解码器缓冲交给文本解析层，而不是每块单独创建解码器。

2. 字符完整之后，事件仍可能不完整：一个 chunk 里可能有半行，也可能有多条事件。SSE 解析按行保存状态、遇到空行提交，支持多行 data 合并、注释以及不同换行形式，不能直接对每个 chunk 做 JSON.parse。

3. EOF 也不能强行把没有终止空行的 SSE 残片当作完成事件。只有完整帧才进入业务层，残留异常应记录为协议或中断问题；为防止一直收不到边界，我还会限制缓冲大小和等待时间，避免内存持续增长。

## 追问：流式回答时怎样兼顾滚动体验和渲染开销？

1. 我会把接收频率与绘制频率分开，先缓存短文本，再在一次渲染机会里合并更新。完成或停止时要处理尚未显示的缓冲；如果每个小片段都重新解析整段 Markdown，长回答的计算成本会不断增加。

2. 自动滚动只在用户处于底部附近时开启，判断要在内容增长之前记录用户意图。用户主动向上滚动后暂停跟随，显示“有新内容”的按钮，点击才回到底部，避免一边阅读历史一边被新增文字拉走。

3. 图片加载、代码块展开和容器变化也会改变高度，所以不能只监听文本追加。读屏提示则适合播报生成开始、完成或错误等状态，不必每个 token 都放进实时播报区，否则视觉流畅了，听觉交互反而很难使用。
