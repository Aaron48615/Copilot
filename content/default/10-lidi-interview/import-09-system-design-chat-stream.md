# 设计一个支持流式回答的聊天页面

## 核心回答

1. 一次提问拆成用户消息和一次助手生成，两边都有稳定 id，并挂到会话上。发送时先显示本地待发送状态，服务端确认后再换成正式记录。请求重试带同一个幂等键，避免连点产生两条用户消息。

2. 传输可以先 POST 创建生成任务，再用 EventSource 订服务端事件；也可以用 fetch POST 直接读响应流。原生 EventSource 不能随便设请求方法和请求头，需要自定义鉴权头或请求体时，fetch 更方便，解析和重连得自己做。

3. 约定 `text`、`status`、`error`、`done` 这类业务事件，带上生成 id 和递增序号，前端据此更新对应助手消息。fetch 读到的是字节块，不是一条完整事件。要增量解码，留下没完成的行和事件，解析完整了才能消费。

4. 界面状态有等待、生成中、完成、失败、中断、主动停止。只有收到业务完成事件，或者核对到服务端完成状态，才显示完成。网络流的 done 只代表传输读完了，答案不一定正常结束。切会话也要把旧任务迟到的事件隔开。

5. 收到文本可以按帧批量追加，少做高频组件更新，完成时把剩余缓冲交出去。用户还在底部附近才自动跟随，往上读了就出新内容提示。Markdown 渲染限制原始 HTML 和危险链接，模型输出不当成可信页面代码。

6. 落地的话，模型密钥、会话鉴权、生成超时、输出限制放在服务端，前端提供停止和重试入口。历史消息和生成状态要持久化，断线之后才能查询或恢复。还要分清只是重新连接，还是重新生成答案，一次断网别让用户重复消耗生成次数。

## 追问：一个网络 chunk 不是一条事件，解析时怎么避免乱码和丢数据？

1. 中文字符的 UTF-8 字节可能跨两个 chunk。复用同一个 `TextDecoder`，分块解码时传 `stream: true`。正常读到流结束，再做最终解码，把解码器缓冲交给文本解析层。别每块单独新建解码器。

2. 字符完整了，事件仍可能不完整：一个 chunk 里可能有半行，也可能有多条事件。SSE 按行保存状态，碰到空行再提交，支持多行 data 合并、注释、不同换行。别直接对每个 chunk 做 `JSON.parse`。

3. 到了 EOF，也不能硬把没有终止空行的 SSE 残片当成完成事件。只有完整帧才进业务层，残留异常记成协议问题或中断。为防止一直收不到边界，还要限制缓冲大小和等待时间，内存别一直涨。

## 追问：流式回答时怎样兼顾滚动体验和渲染开销？

1. 接收频率和绘制频率分开，先缓存短文本，再在一次渲染机会里合并更新。完成或停止时，还没显示的缓冲要处理掉。每个小片段都重新解析整段 Markdown，长回答的计算成本会越来越高。

2. 自动滚动只在用户处于底部附近时开，判断要在内容增长之前记下用户意图。人主动往上滚就暂停跟随，显示「有新内容」按钮，点了才回底部。别一边读历史一边被新增文字拽走。

3. 图片加载、代码块展开、容器变化也会改高度，不能只监听文本追加。读屏适合播报生成开始、完成或错误，不必每个 token 都进实时播报区。视觉顺了，听觉交互反而可能很难用。
