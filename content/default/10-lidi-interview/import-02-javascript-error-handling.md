# 前端异步错误应该怎么分层处理？

## 核心回答

1. 按错误含义分开处理：输入不合法、业务规则拒绝、网络或程序异常，用户该做的事不一样。字段缺了，在输入旁边提示；业务不允许，把原因讲清楚；网络失败，留着当前内容并给出下一步。别一律弹出「请求失败」。

2. 请求层把通信相关信息整理清楚：状态码、解析失败、超时、主动取消，原始原因留下来排查。这里不该直接决定每个页面怎么跳转、清不清数据。同一个接口失败，不同页面可能要完全不同的交互。

3. 页面或业务层最清楚这次操作想干什么，决定错误能不能恢复、展示什么、能不能重试。`await` 时要保证异步任务进得了捕获范围。捕获之后没法恢复，就继续把失败传出去。别只打日志再返回空值，后面误走进成功分支。

4. 全局监听和框架边界用来发现漏网错误、记下上下文、展示最后的兜底，各自能抓住的范围不一样。完善流程时，先查重复提示、错误被吞、过期请求改状态这些路径，再考虑上报。取消请求不等于撤销了服务端写入。

## 追问：请求层已经 catch，页面为什么还需要处理错误？

1. 请求层能统一认出通信问题，却不一定知道用户是在刷新列表还是提交重要表单。前者可能留着旧列表给个轻提示，后者要留着输入、确认处理结果。页面仍得按操作含义决定怎么反馈。

2. 底层捕获可以补上接口路径、错误类别，再把失败继续传给调用方。也可以按约定返回明确的失败结果。既把异常吞掉又不给失败标记，页面就分不清请求失败和真的没有数据。

3. 谁负责展示提示要说清楚，别拦截器弹一次、页面再弹一次。从用户操作走完整条路径：错误既没消失，也没被重复展示；表单内容、加载状态、重试入口也对得上预期。

## 追问：用户取消请求，应该显示失败提示并自动重试吗？

1. 主动取消通常不是故障。用户换了搜索条件，旧请求的结果已经不需要了。这是预期行为，一般不必弹错误，也不必自动重试，不然页面会不断把用户已经放弃的任务拉回来，还可能干扰新查询。

2. 取消来源还要再分：用户主动取消、页面卸载、超时策略触发，含义可能不同。可以根据控制器和取消原因记下类别。看见拒绝就当网络故障，或者只靠某一个错误名字覆盖所有取消方式，都会判错。

3. 写入操作里，客户端停止等待，不代表服务端撤销执行。取消时服务端可能已经接住请求，后面仍可能完成。按接口约定去查结果，或走幂等。别直接告诉用户操作已撤销，更不该无条件重发。
