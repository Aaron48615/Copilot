# 前端异步错误应该怎么分层处理？

## 核心回答

1. 我会先按错误含义区分处理方式：输入不合法、业务规则拒绝，以及网络或程序异常，需要的用户动作不同。假设字段缺失就在输入旁提示，业务不允许则解释原因，网络失败可以保留当前内容并提供下一步，而不是统一弹出一句请求失败。

2. 请求层负责把通信相关信息整理清楚，包括状态码、解析失败、超时和主动取消，同时保留原始原因供排查。这里不应该直接决定每个页面怎么跳转或清空数据，因为同一个接口失败在不同页面可能需要完全不同的交互处理。

3. 页面或业务层最了解操作目的，负责决定错误是否可恢复、展示什么，以及能否重试。使用 `await` 时要确保异步任务进入捕获范围；如果捕获后无法恢复，就继续传递失败，不能只打印日志再返回空值，让后续误走成功分支。

4. 全局监听和框架边界用于发现漏网错误、记录上下文及展示最后的兜底，但各自都有捕获范围。若假设要完善处理流程，我会先检查重复提示、错误被吞和过期请求更新状态这些路径，再考虑增加上报，不能把取消请求说成撤销了服务端写入。

## 追问：请求层已经 catch，页面为什么还需要处理错误？

1. 请求层能统一识别通信问题，却不一定知道用户是在刷新列表还是提交重要表单。前者可能保留旧列表并显示轻提示，后者需要保留输入和确认处理结果，所以页面仍要根据操作含义决定如何反馈。

2. 底层的捕获可以补充接口路径、错误类别等信息，再把失败继续传给调用方。它也可以按约定返回明确的失败结果，但不能既吞掉异常又不给失败标记，否则页面根本无法区分请求失败和真正没有数据。

3. 我会明确谁负责展示提示，避免请求拦截器弹一次、页面再弹一次。验证时从用户操作走完整条路径，确认错误既没有消失，也没有被重复展示，并检查表单内容、加载状态和重试入口是否符合预期。

## 追问：用户取消请求，应该显示失败提示并自动重试吗？

1. 主动取消通常不同于故障，例如用户切换搜索条件后，不再需要旧请求的结果。如果这是预期行为，一般不必弹错误或自动重试，否则页面会不断恢复用户已经放弃的任务，甚至干扰新的查询。

2. 仍要区分取消来源：用户主动取消、页面卸载以及超时策略触发，含义可能不同。可以根据控制器和取消原因记录类别，不能只看到拒绝就认为网络故障，也不能只靠某一个错误名字覆盖所有取消方式。

3. 对写入操作，客户端停止等待不代表服务端撤销执行。假设取消时服务端已经接收请求，后续可能仍然完成，因此应按接口约定查询结果或使用幂等机制；不能直接告诉用户操作已撤销，更不应无条件重发。
