# Reflect.set 为什么要返回布尔值？

## 核心回答

1. Reflect.set 返回布尔值，是为了表达这次属性写入有没有被接受，不是返回赋进去的值。Proxy 的 set 拦截结果也按真假表示成功与否，所以最直接的写法是返回 Reflect.set 的结果，让调用方拿到真实的写入结论。

2. 拦截器忘了 `return`，默认返回 `undefined`，会被当成失败。就算前面已经改了数据，严格模式下对代理赋值仍会抛 TypeError。非严格模式下这种失败通常不会因为返回假而抛错，所以不能靠没有异常判断写入一定成功。

3. 写只读字段时，Reflect.set 可以返回 false，让调用方自己决定怎么处理，但它不是保证永远不抛错的安全包装。目标的 setter 本身抛出异常，异常仍然会往外传。业务代码需要分清写入拒绝和执行异常。

4. 第四个参数 `receiver` 决定访问器里的 `this`，也参与普通数据属性最终写到哪个对象的规则。通过代理转发时把它留下来，可以维持继承场景下的行为。只写 `target[key] = value`，可能让 setter 把数据写到错误对象上。

5. 要在写入后通知更新，先拿到操作结果，再结合是不是真的变化决定要不要触发，而不是无条件通知。返回 true 也不能证明值一定改了，比如 setter 可以接受调用却不保存参数。代理还必须遵守目标不可配置属性的约束。

## 追问：set 拦截器直接返回 true 会有什么问题？

1. 直接返回 true 只是向调用方报告成功，不会替你执行写入。漏了实际赋值，数据可能完全没变。表单把姓名更新成新值，界面逻辑以为写入完成，重新读却还是旧值，这种静默失败比明确拒绝更难查。

2. 还有一些属性约束不能靠返回 true 绕过。比如目标自身的不可配置且不可写数据属性，不能谎称已经改成不同值。代理会检查这些约束并可能抛异常，拦截器不是可以任意改语言规则的后门。

3. 优先把操作交给 Reflect.set 并透传结果。需要字段校验，就在不满足条件时明确拒绝，或抛业务能识别的错误。记日志和触发更新也要尊重这个结果，写入被拒绝后别再显示保存成功，也别继续通知依赖。

## 追问：receiver 怎样影响原型上的 setter？

1. 父对象定义了 `name` 的 setter，内部通过 `this._name` 保存值，子对象继承父对象后给 `name` 赋值。正常情况下 setter 的 `this` 应该是子对象，实际数据写入子对象，而不是把所有子对象的姓名都存到父对象上。

2. 父对象被代理时，set 拦截器拿到的 `receiver` 可以是这个子对象，转发时把它留下来就能维持原来的行为。直接对目标赋值，却可能让 `this` 变成父对象，两个子对象意外共享同一份状态。问题来自 `this` 被换掉了。

3. 验证时创建两个子对象分别赋值，检查各自的自身属性以及父对象有没有被污染，别只看 setter 有没有执行。setter 内部再次写字段，还可能触发其他拦截。通知更新应按实际字段关系处理，避免重复执行副作用。
