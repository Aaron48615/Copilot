# Reflect.set 为什么要返回布尔值？

## 核心回答

1. Reflect.set 返回布尔值，是为了表达这次属性写入操作是否被接受，而不是返回赋进去的值。Proxy 的 set 拦截结果也按真假表示成功与否，所以最直接的写法是返回 Reflect.set 的结果，让调用方得到真实的写入结论。

2. 如果拦截器忘记 return，默认返回 undefined，会被当成失败；即使前面已经修改了数据，严格模式下对代理赋值仍会抛 TypeError。非严格模式下这种失败通常不会因返回假而抛错，因此不能靠没有异常判断写入一定成功。

3. 写只读字段时，Reflect.set 可以返回 false，让调用方自己决定如何处理，但它不是保证永远不抛错的安全包装。如果目标的 setter 本身抛出异常，异常仍然会向外传播，业务代码需要区分写入拒绝与执行异常。

4. 第四个参数 receiver 决定访问器中的 this，也参与普通数据属性最终写到哪个对象的规则。通过代理转发时保留它，可以维持继承场景下的行为；只写 target[key] = value 可能让 setter 把数据写到错误对象上。

5. 如果要在写入后通知更新，我会先得到操作结果，再结合是否真的变化决定是否触发，而不是无条件通知。返回 true 也不能证明值一定改变，例如 setter 可以接受调用却不保存参数，代理还必须遵守目标不可配置属性的约束。

## 追问：set 拦截器直接返回 true 会有什么问题？

1. 直接返回 true 只是向调用方报告成功，不会替你执行写入，遗漏实际赋值时数据可能完全没变。假设表单把姓名更新为新值，界面逻辑以为写入完成，重新读取却仍是旧值，这种静默失败比明确拒绝更难排查。

2. 还有一些属性约束不能靠返回 true 绕过，例如目标自身的不可配置且不可写数据属性，不能谎称已经改成不同值。代理会检查这些约束并可能抛出异常，所以拦截器并不是可以任意改变语言规则的后门。

3. 我会优先把操作交给 Reflect.set 并透传结果，如果需要字段校验，就在不满足条件时明确拒绝或抛业务可识别的错误。记录日志和触发更新也应尊重这个结果，不能在写入被拒绝后还显示保存成功或继续通知依赖。

## 追问：receiver 怎样影响原型上的 setter？

1. 假设父对象定义 name 的 setter，内部通过 this._name 保存值，子对象继承父对象后给 name 赋值。正常情况下 setter 的 this 应该是子对象，因此实际数据写入子对象，而不是把所有子对象的姓名都存到父对象上。

2. 如果父对象被代理，set 拦截器拿到的 receiver 可以是这个子对象，转发时保留它就能维持原来的行为。直接对目标赋值却可能让 this 变成父对象，使两个子对象意外共享同一份状态，问题来自接收者被换掉。

3. 验证时我会创建两个子对象分别赋值，检查各自的自身属性以及父对象是否被污染，而不仅是查看 setter 有没有执行。还要留意 setter 内部再次写字段可能触发其他拦截，通知更新时应按实际字段关系处理，避免重复执行副作用。
