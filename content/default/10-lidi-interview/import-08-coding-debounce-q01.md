# 为什么要保存 this 和参数？

## 核心回答

1. 防抖包装函数现在被调用，原函数要等一段时间才执行，所以得记住这次调用的上下文和入参。比如把对象的搜索方法包装后，方法内部仍要读对象上的配置，不能因为延迟执行就把调用时的 `this` 丢掉。

2. 用普通函数接收调用，通过 `lastThis = this`、`lastArgs = args` 保存信息，到点再用 `fn.apply(lastThis, lastArgs)` 执行。定时器回调可以用箭头函数，但对外的包装函数不能用箭头函数拿动态 `this`，因为箭头函数的绑定来自定义位置。

3. 连续调用时要同时覆盖上下文和参数，保证它们属于最后一次调用。比如先执行 `search.call(a, '手')`，再执行 `search.call(b, '手机')`，尾部执行就应该用对象 b 和「手机」，不能把第一次的对象和最后一次参数拼起来。

4. 保存参数只是保存引用，不会自动生成数据快照。传入对象后又改它，执行时读到的可能是新内容。搜索框一般直接传当前字符串，避免延后读事件对象或 DOM，也避免没必要地深拷贝整个输入对象。

5. 执行时先取出本次上下文和参数，再清空闭包里的待执行状态，最后调用原函数。这样可以放开不再需要的引用，也能避免原函数内部再次触发防抖时，新保存的数据被旧调用的清理逻辑删掉。取消操作同样要清掉这些引用。

## 追问：把包装函数改成箭头函数会出什么问题？

1. 箭头函数没有自己的动态 `this`，所以即使写成 `obj.search()`，也不会拿到这里的 obj。防抖要是在模块作用域创建的，保存到的上下文可能就是外层的 `undefined`，原方法读实例属性时就会报错。

2. 外层返回普通函数，在它里面读 `this` 和剩余参数；内部负责等待的回调可以用箭头函数。这两个位置得分开看，「箭头函数能保存外层 this」不等于所有包装位置都适合箭头函数。

3. 如果原函数本来就是箭头函数，或者已经通过 `bind` 固定了上下文，`apply` 不能再改它的绑定。这时包装器仍然能传参数，但没法替调用方修好原函数的上下文设计，得在定义或绑定方法时处理。

## 追问：为什么不直接把输入事件对象保存到定时器里？

1. 搜索通常只需要输入值，在事件处理函数里读 `event.target.value`，把字符串传给防抖函数。这样保存的是本次输入内容，不用等定时器执行时再去访问可能已经变了的输入框状态。

2. 即使事件对象没有被回收，事件里的 DOM 引用也不等于当时的数据快照。输入框可能已被清空或卸掉，延后读取会增加理解和清理成本。只抽出业务需要的字段，更容易判断最终搜索的是哪个关键词。

3. 这不是说所有对象参数都不能传，而是先约定用调用时的值还是执行时的值。确实需要多个字段的快照，就构造一个只包含必要基本类型的对象，执行或取消后释放引用，不默认保存整棵组件状态。
