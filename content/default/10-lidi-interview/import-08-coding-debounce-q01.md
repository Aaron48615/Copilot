# 为什么要保存 this 和参数？

## 核心回答

1. 防抖包装函数现在被调用，原函数要等一段时间才执行，所以需要记住这次调用的上下文和入参。比如把对象的搜索方法包装后，方法内部仍要读取对象上的配置，不能因为延迟执行就丢掉调用时的 `this`。

2. 我会用普通函数接收调用，通过 `lastThis = this`、`lastArgs = args` 保存信息，到点再用 `fn.apply(lastThis, lastArgs)` 执行。定时器回调可以用箭头函数，但对外的包装函数不能用箭头函数获取动态 `this`，因为箭头函数的绑定来自定义位置。

3. 连续调用时要同时覆盖上下文和参数，保证它们属于最后一次调用。比如先执行 `search.call(a, '手')`，再执行 `search.call(b, '手机')`，尾部执行就应该使用对象 b 和“手机”，不能把第一次的对象与最后一次参数拼起来。

4. 保存参数只是保存引用，不会自动生成数据快照。如果传入对象后又修改它，执行时读到的可能是新内容；搜索框一般直接传当前字符串，避免延后读取事件对象或 DOM，也避免无必要地深拷贝整个输入对象。

5. 执行时我会先取出本次上下文和参数，再清空闭包中的待执行状态，最后调用原函数。这样可以释放不再需要的引用，也能避免原函数内部再次触发防抖时，新保存的数据被旧调用的清理逻辑删除；取消操作同样要清掉这些引用。

## 追问：把包装函数改成箭头函数会出什么问题？

1. 箭头函数没有自己的动态 `this`，所以即使写成 `obj.search()`，也不会获得这里的 obj。若防抖是在模块作用域创建的，保存到的上下文可能就是外层的 `undefined`，原方法读取实例属性时就会报错。

2. 我会让外层返回普通函数，在它里面读取 `this` 和剩余参数；内部负责等待的回调可以使用箭头函数。区分这两个位置很重要，不能把“箭头函数能保存外层 this”理解成所有包装位置都适合箭头函数。

3. 如果原函数本来就是箭头函数，或者已经通过 `bind` 固定了上下文，`apply` 不能再改变它的绑定。这时包装器仍然能传递参数，但无法替调用方修复原函数的上下文设计，需要在定义或绑定方法时处理。

## 追问：为什么不直接把输入事件对象保存到定时器里？

1. 搜索通常只需要输入值，我会在事件处理函数中读取 `event.target.value`，把字符串传给防抖函数。这样保存的是本次输入内容，不需要等定时器执行时再访问可能已经变化的输入框状态。

2. 即使事件对象没有被回收，事件中的 DOM 引用也不等于当时的数据快照。输入框可能已被清空或卸载，延后读取会增加理解和清理成本；只提取业务需要的字段，更容易判断最终搜索的是哪个关键词。

3. 这不是说所有对象参数都不能传，而是要先约定使用调用时值还是执行时值。如果确实需要多个字段的快照，我会构造一个只包含必要基本类型的对象，并在执行或取消后释放引用，不默认保存整棵组件状态。
