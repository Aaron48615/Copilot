# 怎么定位 CSP 报错？

## 核心回答

1. 定位 CSP 报错时，我先读控制台里的被阻止地址和生效指令，例如 script-src、style-src 或 connect-src。先确认这是实际阻断还是 Report-Only 警告，再看对应功能是否受影响，不会一看到红字就添加通配符。

2. 随后检查 HTML 响应头以及页面中的 meta 策略，确认配置到底从哪里发出。网关、应用和 CDN 可能同时添加策略，多条执行策略通常共同限制资源，不能以为后加的一条宽松策略会覆盖前面的严格规则。

3. 针对资源类型核对实际 URL、协议、重定向和 nonce。比如接口被 connect-src 限制，应核对 API 来源；内联脚本失败则检查每次响应的 nonce 是否和标签一致，不能用放开所有内联脚本代替修正生成过程。

4. 我会先判断该资源是否属于正常业务，再修改最小范围的规则。修复后覆盖登录、主页面、动态加载和异常上报，并检查策略在真实响应中生效；违规也可能来自浏览器扩展或错误注入，不能把所有报告都当成需要信任的新来源。

5. 例如生产中某个弹窗被拦，而首页正常，我会复现打开弹窗的步骤，查看新增脚本或接口的完整地址。这样可以精准确认哪个功能遗漏了配置，避免把整页策略永久放宽，也便于把这条路径加入下一次发布回归。

## 追问：配置里已经允许域名，为什么浏览器还是拦？

1. 我会对照实际地址检查协议、端口、子域和资源类型。允许脚本来源不等于允许连接来源，允许一个主域也不必然包含所有子域；如果资源重定向到另一个地址，还需要核对最终请求。

2. 再检查是否有多份 CSP 同时存在，例如源站和 CDN 各发一条。多条策略不是简单选择最宽松的一条，资源必须符合生效限制，所以只修改应用配置可能没有改变网关加上的那份策略。

3. 最后看浏览器是否仍在使用旧 HTML 响应，或页面受 Service Worker 影响。把完整响应头与构建版本对应起来，才能判断是配置没部署、缓存未更新，还是规则本身写错，而不靠连续添加白名单试运气。

## 追问：Report-Only 没有明显报错，可以直接开启强制策略吗？

1. 我会先确认报告通道确实工作过，而不是接收地址错误导致一条数据都没有。可以主动加入一个受控的违规请求，验证浏览器产生报告、接收服务收到数据以及平台能区分策略版本。

2. 接着覆盖关键业务，尤其是只在登录后、支付回调或懒加载页面里出现的资源。短时间看首页没有违规不能代表所有路径都安全，第三方脚本也可能按地区或功能动态加载额外资源。

3. 证据足够后再逐步启用执行策略，并关注功能错误率及用户反馈。若发现遗漏，应确认来源用途再精准调整；Report-Only 的价值是帮助找缺口，不是证明策略能阻止所有攻击。
