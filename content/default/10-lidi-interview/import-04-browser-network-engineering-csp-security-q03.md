# 怎么定位 CSP 报错？

## 核心回答

1. 定位 CSP 报错，先读控制台里被拦住的地址和生效指令，比如 `script-src`、`style-src`、`connect-src`。先确认这是实际阻断还是 Report-Only 警告，再看对应功能有没有受影响。看见红字就加通配符，不行。

2. 随后查 HTML 响应头，以及页面里的 meta 策略，确认配置到底从哪发出。网关、应用和 CDN 可能同时加策略。多条执行策略通常一起限制资源，后加的一条宽松策略，覆盖不掉前面的严格规则。

3. 按资源类型核对实际 URL、协议、重定向和 nonce。比如接口被 `connect-src` 限制，就核对 API 来源；内联脚本失败，就看每次响应的 nonce 和标签是不是一致。别用放开所有内联脚本代替修正生成过程。

4. 先判断这个资源是不是正常业务，再改最小范围的规则。修好之后覆盖登录、主页面、动态加载和异常上报，并确认策略在真实响应里生效。违规也可能来自浏览器扩展或错误注入，不是所有报告都该当成需要信任的新来源。

5. 比如生产里某个弹窗被拦、首页却正常，就复现打开弹窗的步骤，看新增脚本或接口的完整地址。这样能确认哪个功能漏了配置，不必把整页策略永久放宽，这条路径也可以加进下一次发布回归。

## 追问：配置里已经允许域名，为什么浏览器还是拦？

1. 对照实际地址检查协议、端口、子域和资源类型。允许脚本来源，不等于允许连接来源；允许一个主域，也不必然包含所有子域。资源如果重定向到另一个地址，还要核对最终请求。

2. 再查是不是有多份 CSP 同时存在，比如源站和 CDN 各发一条。多条策略不是简单选最宽松的那条，资源必须符合生效限制。只改应用配置，可能根本没动到网关加上的那份。

3. 最后看浏览器是不是还在用旧 HTML 响应，或者页面受 Service Worker 影响。把完整响应头和构建版本对上，才能判断是配置没部署、缓存没更新，还是规则本身写错。连续往白名单里加域名碰运气，不靠谱。

## 追问：Report-Only 没有明显报错，可以直接开启强制策略吗？

1. 先确认报告通道确实工作过，不是接收地址写错导致一条数据都没有。可以主动加一个受控的违规请求，验证浏览器会产生报告、接收服务能收到、平台能区分策略版本。

2. 接着覆盖关键业务，尤其是只在登录后、支付回调或懒加载页面里才出现的资源。短时间看首页没有违规，代表不了所有路径都安全。第三方脚本也可能按地区或功能动态再加载额外资源。

3. 证据够了再逐步打开执行策略，同时看功能错误率和用户反馈。发现遗漏，确认来源用途后再精准调整。Report-Only 的价值是帮着找缺口，证明不了策略能挡住所有攻击。
