# 为什么不直接用 Object.defineProperty？

## 核心回答

1. 我会先纠正一个说法：Object.defineProperty 可以定义新属性，也可以修改已有属性的描述符，并不只支持已有字段。它的限制是要明确指定属性名，给某几个字段安装访问器，并不会自动拦截以后任意新增的键。

2. 如果用它观察一个普通对象，需要逐个设置 getter 和 setter，嵌套对象也要递归处理。后续直接新增字段或删除字段，不会因为其他属性装了访问器就自动通知更新，所以通常还要约定专门的新增和删除入口。

3. Proxy 拦截的是经由代理发生的对象操作，可以分别处理读取、赋值、删除和枚举，因此动态字段更容易统一覆盖。数组下标也属于属性，但数组长度变化有自己的规则，不能只写一个普通字段的监听就认为数组已经处理完整。

4. 不过代理并不等于把原对象全面变成可观察数据，直接修改原对象仍然会绕过代理，嵌套对象也需要另行包装。代理与目标不是同一个引用，集合方法和私有字段还可能遇到接收者问题，这些都是实现时要付出的成本。

5. 所以我会按目标选择：只控制几个稳定字段，用描述符就很直接；设计支持动态键的响应式能力，代理更合适。Proxy 也不是不能撤销，Proxy.revocable 提供撤销能力，但撤销只让代理失效，不会回滚已经写入的对象。

## 追问：用 defineProperty 观察数组为什么容易漏更新？

1. 给已有下标安装访问器，只覆盖那些具体位置，向数组尾部新增下标时并不会自动为新位置安装同样的访问器。假设最初只有两个元素，直接给第三个位置赋值就可能漏掉通知，这与普通对象新增未知键的问题相似。

2. 数组的 length 又不是可随意改成访问器的普通字段，缩短长度会按数组自身规则删除超出范围的元素。逐项监听已有下标，不能因此保证捕获所有长度变化和元素删除，所以只测试读取与覆盖已有元素是不够的。

3. 一种补充方案是包装 push、splice 等变更方法，并要求调用方通过约定入口操作数组，但直接写下标仍可能绕过约定。如果需求允许任意原生数组操作，采用代理通常更自然，不过仍要专门验证长度与下标依赖的触发关系。

## 追问：什么情况下继续使用属性描述符更合适？

1. 假设一个配置对象只有少量稳定字段，需要把其中的派生字段写成 getter，或者限制某个字段不可写，属性描述符已经能直接表达需求。此时没有必要为了拦截所有操作再引入代理身份、缓存和调试方面的额外问题。

2. 描述符也能控制可枚举、可配置等属性特征，而代理只是拦截操作，最终仍要遵守目标对象上的约束。比如真正希望某字段不可修改，可以通过描述符定义规则，不能只靠 set 中打印警告，却让其他引用继续随意写入。

3. 选择之前我会列出需要观察的操作范围，再核对访问方式是否受控，如果未来会大量新增未知字段，逐个维护访问器就容易遗漏。兼容性也应以目标运行环境为准，不能承诺用一段通用补丁完整模拟代理对任意键的拦截能力。
