# 为什么数组跨 iframe 的 instanceof 可能失败？

## 核心回答

1. 不同窗口有各自的全局环境，也有各自的数组构造函数和原型对象。父页面直接拿到同源子页面创建的数组，它的原型链通常连的是子页面的数组原型，不是父页面的。两边对象名字看起来一样，比的是内存里的对象身份。相同名称、相同用途，代替不了同一个引用。

2. 普通的 `instanceof Array` 比的是当前所用构造函数的原型，在不在对象原型链上，不是检查对象有没有数组能力。跨窗口数组跟当前窗口数组原型对不上，会返回假，那不表示那个对象已经不是数组。

3. 目标只是判断数组，用 `Array.isArray(value)`。它根据数组自身的内部特征判断，不依赖当前窗口的构造函数身份。能认出另一环境中的数组，也不会把仅仅有长度和数字下标的普通对象当成数组。

4. 通用的对象标签方法可以辅助观察类型，但标签可能受 `Symbol.toStringTag` 影响，当不了可靠的数组验证替代品。同源直接访问，和跨窗口消息传递，要分开讨论。消息里的数组经过克隆后，不能直接套「还留着源窗口对象引用」的结论。

## 追问：Object.prototype.toString 为什么也不能作为绝对可靠的类型判断？

1. 它返回的标签对观察内建对象有帮助，但对象可以提供自定义的类型标签属性。一个普通对象也可能让结果显示成数组标签。看到标签像数组，只能说明显示结果如此，证明不了它有真实的数组内部特征。

2. 只设置标签，不会让对象自动拥有数组的长度更新规则，也不会让数组专用判断认可它。后面的代码要依赖真实数组语义，标签判断就可能放过不满足要求的数据，错误发生得更晚、更难定位。

3. 按实际操作选判断方式：必须收数组时用数组判断；需要可迭代数据时检查相应协议；需要业务字段时检查字段结构。一个万能标签函数往往把不同问题混在一起，给不了同等强度的保证。

## 追问：跨 iframe 传来的对象都应该用 instanceof 判断吗？

1. 先确定对象是直接引用，还是通过消息传来的数据。同源窗口可能共享引用；跨源窗口通常不能直接读彼此对象；消息传递还有自己的复制规则。这些情形不能都当成同一个原型链问题。

2. 对业务数据，通常更关心字段和取值合不合约定，比如消息有没有正确的类别、编号、内容。实例判断成功，也证明不了字段完整或可信。接收窗口消息时，还应按通信约定核对来源和发送窗口。

3. 对内建对象，优先找符合目标的专用检查，别依赖本地构造函数身份。只是希望遍历一组值，也可以按协议接收可迭代对象，但那跟要求数组不同。允许不允许集合或生成器这类输入，提前说清楚。
