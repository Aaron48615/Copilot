# 为什么数组跨 iframe 的 instanceof 可能失败？

## 核心回答

1. 不同窗口有各自的全局环境，也有各自的数组构造函数和原型对象。假设父页面直接拿到同源子页面创建的数组，它的原型链通常连接子页面的数组原型，而不是父页面的数组原型，即使两边对象名字看起来一样。这里比较的是内存中的对象身份，相同名称和相同用途都不能代替同一个引用。

2. 普通的 `instanceof Array` 比较的是当前所用构造函数的原型是否在对象原型链上，不是检查对象是否具有数组能力。因此跨窗口数组与当前窗口数组原型不匹配时会返回假值，这并不表示那个对象已经不再是数组。

3. 如果目标只是判断数组，我会使用 `Array.isArray(value)`，它根据数组自身的内部特征判断，不依赖当前窗口的构造函数身份。它能识别另一环境中的数组，也不会把仅仅有长度和数字下标的普通对象当成数组。

4. 通用的对象标签方法可辅助观察类型，但标签可能受 `Symbol.toStringTag` 影响，不能作为可靠的数组验证替代品。另外，同源直接访问和跨窗口消息传递要分开讨论；消息中的数组经过克隆后，不能直接套用保留源窗口对象引用的结论。

## 追问：Object.prototype.toString 为什么也不能作为绝对可靠的类型判断？

1. 它返回的标签对观察内建对象有帮助，但对象可以提供自定义的类型标签属性。一个普通对象也可能让结果显示为数组标签，所以看到标签像数组，只能说明显示结果如此，不能证明它有真实的数组内部特征。

2. 举例来说，只设置标签不会让对象自动拥有数组的长度更新规则，也不会让数组专用判断认可它。如果代码随后依赖真实数组语义，标签判断就可能放过不满足要求的数据，引出更晚发生且更难定位的错误。

3. 我会按实际操作选择判断方式：必须接收数组时使用数组判断，需要可迭代数据时检查相应协议，需要业务字段时检查字段结构。一个万能标签函数往往把不同问题混在一起，并不能提供同等强度的保证。

## 追问：跨 iframe 传来的对象都应该用 instanceof 判断吗？

1. 我会先确定对象是直接引用还是通过消息传来的数据。同源窗口可能共享引用，跨源窗口通常不能直接读取彼此对象，消息传递还有自己的复制规则，不能把这些情形都当成同一个原型链问题。

2. 对业务数据，通常更关心字段和取值是否符合约定，例如消息是否有正确的类别、编号和内容。即使实例判断成功，也不能证明字段完整或可信，接收窗口消息时还应按通信约定核对来源和发送窗口。

3. 对内建对象则优先寻找符合目标的专用检查，避免依赖本地构造函数身份。如果只是希望遍历一组值，也可以按协议接收可迭代对象，但那与要求数组不同，需要提前说明是否允许集合或生成器这样的输入。
