# 什么时候不该深拷贝？

## 核心回答

1. 别为了避免改原数据就对任何对象做整份深拷贝，先看实际要改哪里。比如只改一条列表记录的选中状态，复制数组、复制那条记录就行，没变的记录继续共享引用，遍历和分配更少，引用比较的意义也更好留住。

2. 对象代表运行中的资源，通常不会去复制它。DOM 节点、网络连接、函数闭包或带私有字段的类实例，不是把可枚举属性递归一遍就能复制出同等行为。更合理的是传标识、抽出数据，或者通过明确的构造方法创建新实例。

3. 大对象在高频交互里反复深拷贝也不合适，因为要遍历对象图并分配副本，还可能加重垃圾回收。比如输入一次就复制整份大型表格，先缩小更新范围。有没有性能问题要测量，别只凭对象看起来大就编造耗时。

4. 跨线程处理二进制数据时，复制和转移所有权要分开。支持 transfer 的 ArrayBuffer 可以转给另一侧，原 buffer 会被分离，原有视图不能继续按原方式用。两边都还需要独立数据，才选择复制，别把转移当成没有行为变化的优化。

5. 深拷贝比较适合明确的数据快照或独立编辑草稿，但仍要检查类型支持和数据边界。接口返回的新对象也不天然不可变，`Object.freeze` 默认只冻一层。「不允许谁修改哪些字段」得说清楚，别靠频繁复制掩盖共享状态的责任问题。

## 追问：只做浅拷贝，怎样避免修改到原来的嵌套对象？

1. 浅拷贝只换当前容器，嵌套对象还是同一引用。比如 `{ ...state }` 之后直接改 `next.user.name`，仍可能改到原来的 user。沿着实际修改路径，把经过的每一层都建成新对象，再替换目标字段。

2. 对列表可以用 `map`，只对目标记录返回 `{ ...item, selected: true }`，其他记录原样返回。改的是记录里的 address，还要复制 address。关键是复制到发生变化的那一层，不是复制了数组就够安全。

3. 这种方式的前提是共享的其余对象不会被后续原地修改，所以要和状态更新约定一起用。特别深的结构，可以考虑扁平化或采用明确的不可变更新工具，减少漏复制某一层的机会，别盲目加更多展开运算符。

## 追问：编辑表单草稿时，深拷贝是否就是最合适的选择？

1. 表单需要取消后恢复原数据，独立草稿通常合理，但先挑选允许编辑的字段。把完整服务响应都复制进去，可能连只读状态和无关列表也一起存，提交时反而容易带上不该改的字段。

2. 以基本类型为主的小表单，按字段建草稿往往比通用深拷贝清楚；包含支持的嵌套数据，可以用 structuredClone。文件、日期和自定义实例则分别确认处理方式，别默认 JSON 转换后仍保留相同类型。

3. 草稿只解决本地隔离，不解决编辑期间服务端数据已变化的冲突。继续完善时根据接口能力加入版本检查，提交时明确覆盖规则。别把保存一份旧快照当成并发编辑控制，也别声称取消草稿能撤销已提交请求。
