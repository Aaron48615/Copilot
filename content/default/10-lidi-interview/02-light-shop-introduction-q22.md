# 商品详情使用 v-html 有什么风险？

## 核心回答

1. 详情页的 product.content 是商品富文本，v-html 能保留段落、图片和排版，满足商品介绍的展示需要。普通插值会把标签当文本显示，因此两者能力不同，不能为了保留样式就忽略输入内容的可信程度。

2. v-html 会把内容交给浏览器按 HTML 解释，未经清洗的事件属性、危险链接等可能造成 XSS。例如带 onerror 的图片可能触发脚本；风险不只在 script 标签，所以简单删除某一种标签并不能覆盖所有危险内容。

3. 当前商品详情直接使用 v-html，前端还没有加富文本清洗，这一块需要补上。即使内容由商城后台返回，后台账号、编辑器或导入数据也可能有问题，接口是自己的不等于里面所有 HTML 都安全。

4. 如果继续完善，我会和后端约定允许的标签、属性和资源地址，由成熟清洗机制处理，前端只展示约定格式。无需富文本的 AI 卖点和搜索建议使用文本渲染，避免为了文案效果增加不必要的 HTML 解释入口。

5. 展示层还要限制图片宽度并保留合适比例，检查长文本与链接是否破坏移动端布局。CSP 等措施可以进一步限制影响，但不能代替内容清洗；也不能把“页面没有弹窗”当成所有 XSS 风险已经消失的证明。

## 追问：为什么不自己写一个正则删除危险标签？

1. HTML 的结构和浏览器解析规则比较复杂，危险行为可以藏在属性、URL 协议和不规范标记里。只匹配 script 标签容易漏掉图片事件，自己逐条补黑名单也难以证明覆盖了所有浏览器实际会解释的形式。

2. 更合适的是按业务需要保留少量安全标签与属性，再使用维护成熟的清洗实现。商品详情可能只需要段落、列表和图片，不必允许任意样式、事件或嵌入页面，范围越明确，验证也越具体。

3. 清洗后还要检查合法商品内容是否受损，例如图片和必要段落能否展示。安全处理不能只验证恶意样例被删除，也要验证正常内容仍可用；例如检查正常图片是否保留、合法链接是否可点击，以及商品段落在手机上是否仍有清楚的层次。

## 追问：用了 HttpOnly Cookie，XSS 就没影响了吗？

1. HttpOnly 可以阻止页面脚本直接读取对应 Cookie，降低凭据被拿走的风险，但恶意脚本仍运行在当前页面环境里。它可能读取页面上的用户信息、修改操作界面，或利用浏览器的登录状态发请求。

2. 所以凭据存储与输出安全解决的问题不同。即使以后把当前 localStorage Token 改成 Cookie，商品富文本依然需要清洗，重要操作也需要服务端校验，不能因为换了存储方式就继续信任任意 HTML。

3. 验证时除了观察能否读取凭据，还要检查是否能插入危险链接、触发带登录态的操作或窃取页面数据。防护应减少脚本执行入口和后果，而不是只拿“读不到 Cookie”作为整个页面安全的结论。
