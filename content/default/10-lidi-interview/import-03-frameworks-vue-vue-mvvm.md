# MVVM 和 MVC 有什么区别？

## 核心回答

1. MVC 和 MVVM 都是在讨论界面与数据如何分工，但不同框架有不同实现。MVC 中 Model 表达数据和业务，View 展示内容，Controller 协调输入与处理；不能简单说 Controller 必然直接操作所有 DOM，或者这种模式天然难维护，责任划分方式才是关键。

2. MVVM 增加 ViewModel 来提供视图需要的状态和行为，通过绑定机制让视图与状态关联。开发者更多描述“当前数据应该显示什么”，而不是在每个事件里分别找到文本、按钮和错误区域逐个修改，常规交互的数据关系更明确。

3. Vue 的响应式系统与模板渲染体现了这种数据驱动思路，但不必把每个 Vue 概念硬对应到经典 MVVM 的一个框。比如组件状态改变后依赖它的展示自动更新，模板中的事件则调用明确的处理逻辑，这能解释实际工作方式，不只是背缩写。

4. 表单双向绑定也不是所有数据任意双向修改。v-model 将值传递和输入事件回写组合起来，组件 props 仍强调父级传入、子级报告变化；如果子组件直接修改共享对象，让变化来源不清楚，反而破坏了原本希望获得的可理解数据流。

5. 我会用搜索页面说明：状态保存输入和请求结果，模板展示列表与加载提示，事件或监听触发查询。请求失败和竞态仍由业务逻辑处理，框架不会因为采用数据驱动就自动解决；架构模式帮助划分责任，但不能代替缓存、权限和错误恢复的具体设计。

## 追问：数据驱动之后，还需要理解 DOM 吗？

1. 需要，框架最终仍在浏览器中展示内容，聚焦、布局、滚动和原生事件都有具体 DOM 行为。数据驱动减少日常手动更新，并不意味着可以忽略节点何时存在、元素语义或浏览器如何计算尺寸。

2. 我会优先用模板绑定表达显示，确实需要 DOM 能力时通过 ref 和合适生命周期访问。例如打开弹窗后聚焦输入框，需要等待节点挂载；直接改变 state 不会自动替我们完成所有焦点管理和键盘体验。

3. 第三方图表或编辑器也需要明确操作边界，Vue 管容器和配置，库管理自己的内部节点。双方都修改同一块内容会互相覆盖，所以理解 DOM 反而有助于在声明式界面中安全地接入外部能力。

## 追问：双向绑定会不会让数据变化来源难以追踪？

1. 简单输入的双向绑定通常很清楚，因为它对应一个值和一个更新事件。问题更多出现在多层组件共享同一可变对象、许多监听互相写回，或者输入和已保存数据不区分，这时来源确实会变得难找。

2. 我会保持单一状态拥有者，子组件通过明确事件报告修改，复杂编辑使用草稿与提交动作。这样即使模板写的是 v-model，也能解释底层是谁传值、谁发出事件，不能把语法简写理解成取消组件边界。

3. 若字段之间互相派生，优先用 computed 或单次更新规则表达，而不是建立两个 watch 互相赋值。可追踪性来自清楚的数据归属和转换，不是简单禁用所有双向绑定就能获得，合理使用工具同样可以保持透明。
