# WebSocket 和 SSE 怎么选择？

## 核心回答

1. WebSocket 支持连接建立后的双向消息通信，适合双方频繁交互，例如协同编辑或实时游戏。SSE 是服务端持续向客户端推送文本事件，客户端其他操作可以走普通 HTTP，适合进度、通知和逐步生成的文字内容。

2. 浏览器 EventSource 提供 SSE 解析与重连等能力，使用相对直接。需要自定义头、POST 或更细控制时也可以用 fetch 读取流，但这样需要自己处理字符解码、事件边界和恢复，不能把 EventSource 的能力自动算到 fetch 实现上。

3. WebSocket 可以传文本与二进制，但应用要设计消息格式、心跳、重连和权限。SSE 也需要服务端及时刷新输出、代理不长时间缓冲，连接超时与部署配置同样重要；单向并不代表连接保持与资源管理没有成本。

4. 选择时我会先看消息方向、频率、数据格式和已有基础设施。客户端偶尔提交一次指令、服务端持续返回进度，用 SSE 加普通请求就可能足够，不必因为叫实时功能就默认 WebSocket；二者都不保证业务消息只处理一次。

5. 无论哪种，我都会让组件卸载时关闭连接，事件带稳定标识，并校验订阅权限。自行管理重连时采用退避，原生 EventSource 则由浏览器及服务端 retry 字段控制重连等待。遇到网络切换或登录失效要有明确状态，验证消息重复和缺口；真正可靠的是完整恢复过程，而不是界面出现了已连接三个字。

## 追问：SSE 接口在命令行逐条输出，浏览器却最后一起出现，查什么？

1. 先检查服务端和中间代理是否缓冲响应，内容类型是否为 text/event-stream，以及是否及时刷新输出。压缩、网关缓冲和超时设置都可能改变到达节奏，命令行直连正常不代表经过生产代理也一样。

2. 再看浏览器读取代码是否持续消费 body，还是用了 text 等方式等待完整响应才处理。手动解析还要正确识别事件空行边界，服务端缺少分隔符时，客户端即使收到字节也可能一直等不到一个完整事件。

3. 我会沿服务端、代理和浏览器分段记录安全的时间信息，用少量测试事件判断哪里开始聚合。修复后覆盖空闲心跳和长时间连接，不能只把缓冲关闭就忽略代理稍后仍会因超时切断的问题。

## 追问：怎样选择实时连接的心跳和重连策略？

1. 先看服务端及代理的空闲超时，心跳用于及时发现失联或保持必要活跃，不是越频繁越好。SSE 可以用注释行保持流活动，浏览器 WebSocket 的协议级 ping 不能像普通消息那样由页面任意控制，应用心跳需双方约定。

2. 手动管理 WebSocket 或 fetch 流时，可以用退避和随机扰动减少同时重连。原生 EventSource 没有自定义退避算法的接口，由浏览器及 retry 字段安排；若主动关闭并定时创建新实例，新实例不会继承旧 Last-Event-ID，需要保存恢复位置并通过服务端约定重新传入。

3. 恢复后还要确认消息位置和当前订阅，不只是重新亮起连接状态。测试断网、服务端重启和大量重复事件，验证用户看到的数据完整且不会重复提交，心跳正常也不能代替业务层的进度确认。
