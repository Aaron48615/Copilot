# WebSocket 和 SSE 怎么选择？

## 核心回答

1. WebSocket 支持连接建立后的双向消息，适合双方频繁交互，比如协同编辑、实时游戏。SSE 是服务端持续向客户端推送文本事件，客户端其他操作可以走普通 HTTP，适合进度、通知、逐步生成的文字内容。

2. 浏览器 `EventSource` 提供 SSE 解析和重连这些能力，用起来相对直接。需要自定义头、POST 或更细控制时，也可以用 `fetch` 读流，但字符解码、事件边界、恢复都要自己做。`EventSource` 的能力不能自动算到 `fetch` 实现上。

3. WebSocket 可以传文本和二进制，但应用要设计消息格式、心跳、重连、权限。SSE 也需要服务端及时刷新输出，代理别长时间缓冲。连接超时和部署配置同样重要。单向并不代表连接保持和资源管理没有成本。

4. 看消息方向、频率、数据格式、已有基础设施。客户端偶尔提交一次指令、服务端持续返回进度，用 SSE 加普通请求就可能够。因为叫实时功能就默认 WebSocket，常常过重。两者都不保证业务消息只处理一次。

5. 不管哪种，组件卸载时关掉连接，事件带稳定标识，订阅权限要校验。自行管理重连时用退避。原生 `EventSource` 由浏览器和服务端 `retry` 字段控制重连等待。网络切换或登录失效要有明确状态，消息重复和缺口都要验证。真正可靠的是完整恢复过程，界面出现「已连接」三个字不够。

## 追问：SSE 接口在命令行逐条输出，浏览器却最后一起出现，查什么？

1. 先查服务端和中间代理有没有缓冲响应，内容类型是不是 `text/event-stream`，输出有没有及时刷新。压缩、网关缓冲、超时设置都可能改到达节奏。命令行直连正常，不代表经过生产代理也一样。

2. 再看浏览器读取代码是不是持续消费 `body`，还是用了 `text()` 这类方式等完整响应才处理。手动解析还要正确识别事件空行边界。服务端缺分隔符时，客户端就算收到字节，也可能一直等不到一个完整事件。

3. 沿服务端、代理、浏览器分段记下安全的时间信息，用少量测试事件判断从哪开始聚合。修好后覆盖空闲心跳和长时间连接。只把缓冲关掉，忽略代理稍后仍会因超时切断，问题会换一种方式出现。

## 追问：怎样选择实时连接的心跳和重连策略？

1. 先看服务端和代理的空闲超时。心跳用来及时发现失联，或保持必要活跃，不是越频繁越好。SSE 可以用注释行保持流活动。浏览器 WebSocket 的协议级 ping，不能像普通消息那样由页面任意控制，应用心跳要双方约定。

2. 手动管理 WebSocket 或 `fetch` 流时，可以用退避和随机扰动，减少同时重连。原生 `EventSource` 没有自定义退避算法的接口，由浏览器及 `retry` 字段安排。若主动关闭再定时创建新实例，新实例不会继承旧 `Last-Event-ID`，要自己保存恢复位置，并通过服务端约定重新传入。

3. 恢复后还要确认消息位置和当前订阅，不只是重新亮起连接状态。测断网、服务端重启、大量重复事件，验证用户看到的数据完整、不会重复提交。心跳正常，也代替不了业务层的进度确认。
