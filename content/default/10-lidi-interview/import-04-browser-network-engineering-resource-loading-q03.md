# 模块脚本默认是什么行为？

## 核心回答

1. type=module 的脚本按 JavaScript 模块处理，浏览器会解析静态 import 并获取依赖。它默认具有类似 defer 的延后执行行为，不会像普通无属性经典脚本那样在下载时一直阻塞 HTML 解析，所以通常不需要再加 defer。

2. 模块有自己的作用域，顶层变量不会像普通脚本某些声明那样自动挂到全局对象，代码默认严格模式。模块导入导出明确依赖关系，依赖的同步求值通常先于导入它的代码，但循环依赖和顶层 await 需要额外理解。

3. 模块加载也有约束，例如跨源模块请求需要符合 CORS，服务器要返回合适的 JavaScript MIME。直接通过 file 地址打开或把模块路径错误回退到 HTML，可能在开发服务器正常的情况下仍加载失败，部署验证不能省。

4. 模块脚本可以设置 async，让它及依赖就绪后尽快执行，这时不能继续假定按文档顺序运行。动态 import 则是在代码执行到相应位置才触发，返回 Promise，需要处理下载失败、解析错误及发布后旧文件缺失。

5. 我会把模块化和按需加载分开：用了 module 不代表所有依赖都延迟到需要时才下载，静态依赖仍会被发现和加载。首屏优化要看实际依赖图和请求时机，不能只加一个 type 属性就承诺显著减少初始体积。

## 追问：模块顶层变量为什么在控制台 window 上找不到？

1. 模块有独立作用域，顶层声明不自动成为 window 的属性，这样可以减少多个文件之间的全局命名冲突。另一个模块需要访问某个值，应通过 export 和 import 表达依赖，而不是默认从全局对象读取。

2. 如果确实要接入依赖全局变量的旧脚本，可以明确设置一个受控的全局入口，但应避免把整个模块状态都暴露出去。混合经典脚本与模块时还要确认初始化顺序，否则旧脚本可能比模块更早读取这个入口。

3. 我会优先改成清楚的接口调用，并通过开发工具的模块断点观察实际状态。调试方便不应成为把 Token 或内部对象全部挂到 window 的理由，公开全局数据会增加意外修改和敏感信息暴露机会。

## 追问：静态 import 与动态 import 的失败处理有什么区别？

1. 静态 import 属于模块依赖，关键依赖无法加载或求值时，入口模块可能无法正常执行，不能指望入口后面的 try/catch 自动捕获加载前就发生的问题。需要页面级加载错误处理和明确的部署资源策略。

2. 动态 import 返回 Promise，可以在触发功能时捕获失败并展示重试。它适合路由或大型可选功能，但重试要有限；如果旧 chunk 已被删除，反复请求相同地址不会突然成功，应提示获取新版本并保护用户输入。

3. 我会分别测试网络中断、文件缺失和模块内部抛错，给出不同诊断信息。不能所有失败都归成网速慢，也不能把普通重试按钮当成解决入口文件版本不兼容的完整办法。
