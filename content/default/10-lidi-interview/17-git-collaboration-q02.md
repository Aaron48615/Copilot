# 遇到 Git 冲突怎么处理？

## 核心回答

1. 遇到冲突我会先停下来用 git status 确认当前是在 merge、rebase 还是其他操作，并查看哪些文件未合并。再看工作树是否有原本就存在的修改，避免把自己的冲突处理和别人未提交的内容混在一起。

2. 我会读取冲突区附近的完整逻辑，并结合双方提交说明理解各自在解决什么问题。冲突不只可能是同一行文本，还可能涉及删除与修改、文件重命名，不能只机械地去掉冲突标记。

3. 例如一边给提交函数增加参数校验，另一边调整了请求字段，最终可能需要同时保留两种行为。解决方案应依据最新接口和业务要求判断，无法确定的业务选择需要找相关修改者确认，不能直接用最后修改时间决定。

4. 修改后先看 diff，再按文件执行 git add 标记已解决；如果是 rebase，就在确认后继续当前操作。使用编辑器的“接受当前”或“接受传入”之前，我会核对对应内容，尤其不能在 rebase 时凭标签直觉选择整份文件。

5. Git 不再显示冲突只是文本层面处理完成，还要运行与改动相关的类型检查、测试或页面验证。重点检查双方功能组合后的行为，例如新校验是否阻断正常请求、重命名后引用是否完整，并再次确认没有误带无关改动。

## 追问：Git 没有标记冲突，为什么合并后功能仍然坏了？

1. Git 主要按照文本和历史关系合并，不理解完整的业务约束。比如一边把接口返回字段从 name 改成 title，另一边在不同文件新增了读取 name 的代码，文本上不冲突，运行时却可能拿不到数据。

2. 我会检查跨文件接口、类型和调用关系，结合两边变更的目的分析，而不是只看发生冲突的那几个文件。类型检查可以发现一部分问题，但动态数据或不准确的类型声明仍可能让错误通过。

3. 验证要覆盖组合后的实际流程，尤其是权限、表单提交和数据转换这些依赖上下文的行为。如果无法跑通需要的环境，要明确记录未验证部分，不能把合并命令成功当成业务验收通过。

## 追问：rebase 中的 ours 和 theirs 应该怎么理解？

1. 我不会简单地把 ours 永远理解为“我原来分支上的版本”。在 rebase 中，Git 正把提交重放到新基点上，ours 通常是新基点及已重放的结果，theirs 是当前正在重放的那次提交。

2. 这与普通 merge 中对当前分支和传入分支的直观理解容易不同。操作前我会查看当前重放的提交、冲突内容和两边差异，必要时逐段处理，而不是对整个文件直接接受某一边。

3. 特别是删除与修改冲突，选一边可能让整份新功能消失。解决后还要检查最终文件是否包含需要保留的双方行为，只有确实理解另一边应被舍弃的原因，才使用整份文件替换方式。
