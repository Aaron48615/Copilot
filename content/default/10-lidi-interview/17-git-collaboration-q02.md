# 遇到 Git 冲突怎么处理？

## 核心回答

1. 遇到冲突先停下来，用 `git status` 看当前是 merge、rebase 还是别的操作，哪些文件还没合完。再看工作树里有没有自己本来就改着的东西，别把冲突处理和没提交的修改搅在一起。

2. 冲突标记附近的完整逻辑都要读，两边提交说明也看一下，搞清楚各自在解决什么。冲突不一定是同一行打架，删了对方改的文件、文件改名，都可能冲突，把标记删掉不算完。

3. 比如一边给提交函数加了参数校验，另一边改了请求字段，最后可能两种都得留。按最新接口和业务来合，拿不准就找改过这块的人问，别按谁最后改的时间来选。

4. 改完先看 diff，再按文件 `git add`，标记已经解决。如果是 rebase，确认后再 continue。编辑器上的「接受当前」「接受传入」，点之前要对一下内容。rebase 时两边的标签跟直觉可能反着，别凭标签整份覆盖。

5. Git 不再显示冲突，只说明文本合完了。跟这次改动相关的类型检查、测试、页面还要跑一下。重点看两边功能叠在一起之后对不对，比如新校验会不会把正常请求拦了、改名之后引用还在不在。别把无关改动一起带进去。

## 追问：Git 没有标记冲突，为什么合并后功能仍然坏了？

1. Git 按文本和历史合，不懂业务。一边把返回字段从 `name` 改成 `title`，另一边在别的文件里还在读 `name`，文本上不打架，跑起来却拿不到数据。

2. 跨文件的接口、类型、调用都要看，不只看当时标了冲突的那几个文件。类型检查能抓住一部分，动态数据、类型写得不准的，还是可能漏。

3. 合完要按真实流程验，权限、表单提交、数据转换这些特别容易出问题。环境跑不起来，就把没验到的说清楚，merge 命令成功不等于业务过了。

## 追问：rebase 中的 ours 和 theirs 应该怎么理解？

1. rebase 里 ours 不是「我原来分支上那个」。Git 正把提交往新基点上重放，ours 一般是新基点加上已经重放过的结果，theirs 是当前正在重放的那次提交。

2. 这跟普通 merge 里「当前分支 / 进来的分支」不是一回事。先看正在重放哪次提交、冲突内容、两边 diff，能一段段合就一段段合，别整份文件直接收一边。

3. 删和改撞上了，选一边可能把整段新功能弄没。合完再看最终文件，两边该留的行为都在不在。真搞清楚另一边该丢掉，再用整份替换。
