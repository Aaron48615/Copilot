# 和 Promise.all 有什么关系？

## 核心回答

1. Promise.all 负责汇总一组输入的结果，并发池负责控制任务什么时候启动，两者解决的问题不同。all 可以接收 Promise 和普通值，但不会自动调用传进去的任务函数，也没有并发上限这个参数。

2. 常见写法是 urls.map 里直接调用 fetch，再把返回的数组交给 all，此时请求在遍历阶段就已经发出了。如果想限制并发，应保存返回 Promise 的函数，等调度器拿到名额才调用，不能对已经启动的请求事后排队。

3. 一种实现方式是只启动固定数量的 worker，每个 worker 连续取任务并等待完成，再取下一项。外层可以用 all 等待这些 worker 结束，因此使用并发池并不意味着不能使用 all，关键在于汇总的对象和启动时机。

4. 失败策略仍然需要单独决定，独立任务可以在 worker 内捕获并记录，再继续派发；必须停止的批次则需要显式更新停止状态。即使外层 all 因某个 worker 拒绝而结束，其他 worker 也不会因此自动停止运行。

5. 如果只加载少量独立数据，而且服务端能承受，直接组合请求往往更清楚；批量上传或大量查询才更需要排队。并发池也不等于每秒限流，请求完成很快时仍可能在短时间发出很多次，固定频率要求还需要另设规则。

## 追问：把任务函数直接交给 Promise.all 会执行吗？

1. 不会，普通函数会被当作一个值参与汇总，最后得到的数组里仍然是函数本身。比如把两个返回请求的函数放入数组，再 await all，并不代表已经发出了两次请求，必须有明确调用这些函数的步骤。

2. 如果改成先遍历并调用所有函数，虽然请求会执行，但也丢失了延迟启动的意义。真正的并发限制应由 worker 每次只取一个函数调用，其他函数继续留在队列里，所以检查实现时要先找调用发生的位置。

3. 我会用一个启动计数器做最小验证：入队后计数应不变，调度开始后最多增加到上限。只有释放一个名额才允许再增加一次，这比只看最终返回数组更能证明实现确实控制了开始时间，而不是仅仅延迟收集结果。

## 追问：每五个请求用一次 Promise.all 算并发池吗？

1. 如果每批五个，并且等本批全部结束后才启动下一批，就能把同时运行数量限制在五个，但会产生批次之间的等待。假设前四个很快完成，第五个很慢，下一批仍然不能开始，虽然当前只剩一个请求在运行，其余可用名额也会空着。另外，Promise.all 遇到拒绝会提前返回；如果失败后还要继续下一批，应使用 allSettled，或逐个捕获错误再等待全部结束，否则上一批的剩余请求可能和下一批重叠。

2. 持续补位的池会在任意一项结束后马上取下一项，因此更适合任务耗时差异明显的场景。实现也要多处理游标、错误和取消，不过不需要为了追求吞吐而把所有需求都复杂化，少量任务分批已经可能够用。

3. 如果业务要求上一批完成校验后才能开始下一批，等待反而是正确约束，不应擅自改成持续补位。比如假设后续请求依赖前一批生成的标识，就要先处理数据依赖，再讨论并发数，单纯补满名额可能发送无效请求。
