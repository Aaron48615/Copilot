# 声明合并什么时候会带来风险？

## 核心回答

1. 声明合并的风险首先取决于作用范围。同一作用域里的同名接口可以合并，两个独立模块各自导出的同名接口，不会只因为名字相同就自动合并。真正要留意的是全局声明、同一模块内的重复声明，以及明确针对模块做的类型增强。

2. 合并有时是有意设计的扩展方式，比如给已有库的对象类型补充实际存在的能力。字段分散在多个声明文件里，阅读某个接口时可能看不到完整要求。新增一个必填字段，还可能影响原来能正常创建对象的代码。

3. 不同声明里的同名普通属性，不能随便写成不一致的类型，这种冲突会报错，不是后声明的字段直接盖住前面的。方法成员还可能形成重载，后续增加的签名会影响调用匹配。合并也不只是把字段拼起来这么简单。

4. 需要扩展的接口和普通业务类型分开。业务代码优先通过显式导入和组合表达关系。发现项目依赖隐藏的类型增强，先查清声明来源和运行时实现，再考虑集中说明或调整。别只删声明文件来消掉看起来重复的类型。

## 追问：新增一个全局声明文件，为什么其他文件也开始报错？

1. 声明文件如果处于全局作用域，其中的接口可能与原有全局接口合并。新增必填属性后，原先创建的对象就可能不再满足接口要求。错误虽然出现在别处，根因是整体类型约定被扩大了。

2. 先看这个文件有没有模块标记，有没有显式做全局增强，再看编译配置实际包含哪些声明文件。不能只凭文件后缀判断它一定只影响本目录。编译器会按项目范围把相关声明一起处理。

3. 声明本来只为一个模块服务，应通过模块导出和明确导入限制使用范围。确实是全局增强，就保留真实的全局语义。修改前还要确认运行时有没有对应能力，不然只是把编译错误转成使用时错误。

## 追问：第三方库升级后，原来的类型增强可能出现哪些问题？

1. 库的新版本可能已经增加同名属性，但类型跟本地补充声明不同，于是发生冲突。也可能库调整了导出位置，旧的增强目标不再对应实际使用的类型，本地声明还在，却没按预期生效。

2. 更隐蔽的是编译通过，但增强所描述的运行时方法已经改名或被移除。类型声明不会替库创建方法。把增强声明和实际调用放在一起核对。跳过声明检查，证明不了升级兼容。

3. 要维护这类增强，记下它针对的库版本和补充原因，升级时检查能不能删或改。还可以用最小调用样例验证真实行为。这是一种维护方式，补齐声明本身不等于完成了功能适配。
