# 声明合并什么时候会带来风险？

## 核心回答

1. 声明合并的风险首先取决于作用范围，同一作用域里的同名接口可以合并，但两个独立模块各自导出的同名接口不会仅因为名字相同就自动合并。真正需要留意的是全局声明、同一模块内的重复声明，以及明确针对模块做的类型增强。

2. 合并有时是有意设计的扩展方式，例如给已有库的对象类型补充实际存在的能力。但如果字段分散在多个声明文件中，阅读某个接口时可能看不到它的完整要求，新增一个必填字段还可能影响原来能正常创建对象的代码。

3. 不同声明里的同名普通属性不能随便写成不一致的类型，这种冲突会报错，不是后声明的字段直接覆盖前面的字段。方法成员还可能形成重载，后续增加的签名会影响调用匹配，因此合并也不只是把字段拼接起来这么简单。

4. 我会把需要扩展的接口和普通业务类型区分清楚，业务代码优先通过显式导入和组合表达关系。如果发现项目依赖隐藏的类型增强，我会先查清声明来源和运行时实现，再考虑集中说明或调整，不能仅删除声明文件来消除看起来重复的类型。

## 追问：新增一个全局声明文件，为什么其他文件也开始报错？

1. 声明文件如果处于全局作用域，其中的接口可能与原有全局接口合并。新增必填属性后，原先创建的对象就可能不再满足接口要求，错误虽然出现在别处，根因却是整体类型约定被扩大了。

2. 我会先检查这个文件是否包含模块标记，以及是否显式使用了全局增强，再查看编译配置实际包含哪些声明文件。不能仅凭文件后缀判断它一定只影响本目录，编译器会按项目范围把相关声明一起处理。

3. 如果声明本来只为一个模块服务，应通过模块导出和明确导入限制使用范围；如果确实是全局增强，则需要保留真实的全局语义。修改前还要确认运行时是否存在对应能力，否则只是把编译错误转成使用时错误。

## 追问：第三方库升级后，原来的类型增强可能出现哪些问题？

1. 库的新版本可能已经增加同名属性，但类型与本地补充声明不同，于是发生冲突。也可能库调整了导出位置，旧的增强目标不再对应实际使用的类型，导致本地声明仍存在却没有按预期生效。

2. 更隐蔽的情况是编译通过，但增强所描述的运行时方法已经改名或被移除。类型声明不会替库创建方法，所以我会把增强声明和实际调用放在一起核对，不能用跳过声明检查来证明升级兼容。

3. 假如需要维护这类增强，我会记录它针对的库版本和补充原因，升级时检查能否删除或修改。还可以用最小调用样例验证真实行为；这是一种拟采用的维护方式，不能把补齐声明本身当成完成了功能适配。
