# call、apply、bind 有什么区别？

## 核心回答

1. 对普通函数，这三个方法都能指定调用时 `this` 指向谁，但时机不一样。`call` 和 `apply` 马上调用并返回结果；`bind` 先造一个新函数，以后再调这个新函数，原来的逻辑才跑。`call` 的参数一个一个传，`apply` 传一组类数组。

2. 写成代码就是 `fn.call(obj, a, b)` 和 `fn.apply(obj, [a, b])`。`apply` 第二个参数不必是真数组，够格的类数组也行。`bind` 还能先塞一部分参数，之后传入的接在后面，适合把通用函数收成某个回调。

3. 箭头函数没有自己的 `this`，沿用外层那个，`call`、`apply`、`bind` 改不了。已经 `bind` 过的函数，再指定别的对象也不会改绑。原函数能当构造函数的话，`new` 那个绑定函数时，绑上去的对象会被忽略，还是新实例。

4. 对象方法要当事件回调，先把绑定后的函数存下来，注册和移除监听都用同一个引用。手写时把函数临时挂到对象上，只能演示一部分原理。碰到冻结对象、严格模式、`new` 这些语义就不完整，那不是原生方法的等价实现。

## 追问：为什么每次 bind 后都无法移除原来的监听？

1. 每次 `bind` 都会造一个新的函数对象。就算传入的对象和预置参数完全一样，引用也不同。移除监听要比对当初注册的那个函数，现场再 `bind` 一次，拿到的不是当初那份。

2. 初始化时把绑定结果存下来，注册和清理都用这个引用，捕获选项也保持一致。这样对象方法的 `this` 是固定的，页面离开时也能摘掉监听，事件不会再去跑已经失效的逻辑。

3. 改用箭头函数包一层对象方法，同样要保存那个包装函数，移除时不能再写一个新的箭头函数。核对时真去触发清理之后的事件，确认回调没再跑，别只看清理函数被调用过就算完。

## 追问：为什么把函数临时挂到对象上不等价于原生 call？

1. 这种写法靠对象方法调用来传 `this`，首先得能改目标对象。对象冻住了，或者不允许扩展，就可能失败。就算用独一无二的属性名避免盖住原字段，对象本身不许加属性，还是过不去。

2. 严格模式下，`this` 可以是 `null`、`undefined` 或者原始值。简化实现要是统一换成全局对象或者包装对象，原函数看到的值就变了。非严格函数又有自己的转换规则，一套手工处理概括不了全部情况。

3. 原生 `call` 并不真的往目标对象上写属性，简化实现还可能触发代理的拦截。手写时先讲清只覆盖普通可扩展对象，异常之后把临时属性清掉，把边界说清楚。
