# call、apply、bind 有什么区别？

## 核心回答

1. 对普通函数来说，这三个方法都能指定调用时的接收者，但执行时机不同，前两个会立即调用函数并返回结果。`call` 接收逐个列出的参数，`apply` 接收一组类数组参数；`bind` 则先生成新函数，之后调用新函数才执行原来的逻辑。

2. 写成代码就是 `fn.call(obj, a, b)` 与 `fn.apply(obj, [a, b])`，后者不要求第二个参数必须是真数组，符合要求的类数组也可以。绑定还能预先放入一部分参数，之后传入的参数接在它们后面，适合把通用函数调整为特定回调。

3. 我会注意普通调用、箭头函数和构造调用的区别，箭头函数的接收者来自定义环境，不能被这些方法重新指定。已绑定函数再被指定其他接收者也不会改绑；但如果原函数能被构造，使用 `new` 调用绑定函数时，绑定的接收者会被忽略。

4. 例如对象方法需要作为事件回调时，可以先保存绑定后的函数，再用同一个引用注册和移除监听。手写时把函数临时挂到对象上只能说明部分原理，遇到冻结对象、严格模式和构造语义就不完整，我不会把这种简化版本说成原生方法的等价实现。

## 追问：为什么每次 bind 后都无法移除原来的监听？

1. 每次绑定都会创建一个新的函数对象，即使传入的接收者和预置参数完全一样，它们的引用也不同。移除事件监听时需要匹配原先注册的回调，因此现场重新绑定一次，拿到的并不是此前注册的那个函数。

2. 我会在初始化时把绑定结果保存下来，注册与清理时都使用这个引用，同时保持捕获选项一致。这样既能固定对象方法的接收者，又能在页面离开时解除监听，避免事件继续触发已经失效的业务逻辑。

3. 如果改用箭头函数包装对象方法，同样需要保存包装函数，不能在移除时重新写一个新的箭头函数。验证时应实际触发清理后的事件，确认回调没有再次执行，而不是只看清理函数已经被调用过。

## 追问：为什么把函数临时挂到对象上不等价于原生 call？

1. 这种写法利用对象方法调用来传递接收者，但它首先要求能够修改目标对象，冻结或禁止扩展的对象就可能失败。即使使用唯一属性名避免覆盖原字段，也没有解决目标对象本身不允许新增属性的问题。

2. 严格模式下接收者可以保留为空值或原始值，简化实现若统一换成全局对象或者包装对象，就改变了原函数观察到的值。非严格函数又有自己的转换规则，所以不能用一个统一的手工处理概括全部情况。

3. 原生调用并不需要真的向目标对象写属性，简化实现还可能触发代理对象的拦截逻辑。如果面试要求手写，我会先说明支持普通可扩展对象的范围，并用异常后清理临时属性说明实现边界。
