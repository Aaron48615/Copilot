# `useEffect` 的依赖数组怎么理解？

## 核心回答

1. 我把依赖数组理解为这个 Effect 需要跟随哪些响应式值重新同步，比如 props、state 和组件内声明的变量。它不是随意选择执行时机的开关，读到了会变化的值却故意不写进去，容易让回调一直使用旧数据。

2. React 在组件提交后运行 Effect，依赖变化时先执行上一次清理，再执行新的设置逻辑。依赖逐项用 `Object.is` 比较，所以每次渲染新建的对象即使内容一样，也可能让 Effect 再运行。

3. 不传数组会在每次提交后执行，空数组表示没有响应式依赖，有依赖数组则在首次挂载及依赖变化后执行。空数组不能保证整个应用生命周期只执行一次，重新挂载会执行，开发环境的 Strict Mode 还会额外检查设置和清理。

4. 比如根据商品 ID 拉取详情，我会把 ID 放进依赖，并在清理时取消或作废旧请求。这样从商品 A 切到 B 时，新页面不会一直保留 A 的请求逻辑，晚回来的 A 结果也不能覆盖 B。

5. 如果只是从列表计算筛选结果，我会优先在渲染时计算，而不是用 Effect 再设置一个状态。图表这类外部实例才适合用 Effect 同步，同时区分实例创建和数据更新，避免筛选变化就销毁重建。

## 追问：依赖里放了对象，为什么 Effect 一直执行？

1. 组件函数每次执行都会重新创建对象，例如 `const options = { id }`。即使两次的 id 相同，对象引用仍然不同，依赖比较就会认为需要重新同步，不能按对象内容相等来理解。开发时可以对照前后两次引用，确认究竟是哪项依赖变化。

2. 我会先看 Effect 是否只需要 id，如果是，就在 Effect 内创建 options，并直接依赖 id。这样依赖对应实际业务输入，也减少为了稳定引用而额外引入缓存的复杂度。

3. 如果执行后又更新了状态，更新导致渲染、渲染又创建对象，就可能出现循环。排查时要同时找出触发渲染的状态更新和每次变化的依赖，不能只删掉依赖或关掉检查提示。

## 追问：定时器读到旧 state，应该怎么改？

1. 假设空依赖的定时器里写 `setCount(count + 1)`，回调捕获的是创建时的 count。后续渲染产生的新值不会自动替换旧闭包，因此显示可能加到一之后就不再增长。这不是定时器停止了，而是它反复提交了同一个值。

2. 如果只是基于上一个值递增，我会写 `setCount(c => c + 1)`，并在清理时调用 `clearInterval`。函数式更新表达的是状态转换，不需要为了读取 count 而每次重新建立定时器。

3. 如果回调确实依赖当前用户选择，比如轮询不同商品，就应该把商品 ID 放入依赖并重新订阅。不能把所有变量都藏到 ref 里省事，否则商品切换了，旧定时任务仍可能在请求错误的资源。
