# `useEffect` 的依赖数组怎么理解？

## 核心回答

1. 依赖数组是这个 Effect 要跟着哪些响应式值重新同步，比如 props、state、组件里声明的变量。它不是随便选执行时机的开关。读到了会变的值却故意不写进去，回调就容易一直用旧数据。

2. React 在组件提交后跑 Effect。依赖变了，先执行上一次清理，再跑新的设置逻辑。依赖逐项用 `Object.is` 比，所以每次渲染新建的对象，哪怕内容一样，也可能让 Effect 再跑一遍。

3. 不传数组，每次提交后都执行。空数组表示没有响应式依赖，有依赖数组则在首次挂载以及依赖变化后执行。空数组不能保证整个应用生命周期只执行一次，重新挂载会执行，开发环境 Strict Mode 还会额外检查设置和清理。

4. 比如按商品 ID 拉详情，把 ID 放进依赖，清理时取消或作废旧请求。从商品 A 切到 B，新页面就不会一直留着 A 的请求逻辑，晚回来的 A 结果也不能盖住 B。

5. 只是从列表算出筛选结果，优先在渲染时算，别用 Effect 再设一份状态。图表这类外部实例才适合用 Effect 同步，同时分清实例创建和数据更新，别一改筛选就销毁重建。

## 追问：依赖里放了对象，为什么 Effect 一直执行？

1. 组件函数每次执行都会重新创建对象，比如 `const options = { id }`。两次的 `id` 相同，对象引用仍不同，依赖比较就会认为要重新同步。别按对象内容相等来理解。开发时对照前后两次引用，看究竟是哪项变了。

2. Effect 如果只需要 `id`，就在 Effect 里面创建 `options`，直接依赖 `id`。依赖对上实际业务输入，也为了稳引用去额外缓存的复杂度会少一些。

3. 执行完又更新状态，更新导致渲染，渲染又创建对象，就可能转起来。排查时把触发渲染的状态更新、每次都在变的依赖一起找出来。别只删依赖，也别只关检查提示。

## 追问：定时器读到旧 state，应该怎么改？

1. 空依赖的定时器里写 `setCount(count + 1)`，回调抓住的是创建时的 `count`。后面渲染产生的新值，不会自动换进旧闭包。所以显示可能加到 1 就不再涨。不是定时器停了，是它反复提交同一个值。

2. 只是基于上一个值递增，写 `setCount(c => c + 1)`，清理时 `clearInterval`。函数式更新表达的是状态转换，不必为了读 `count` 每次重建定时器。

3. 回调确实依赖当前用户选择，比如轮询不同商品，就把商品 ID 放进依赖并重新订阅。别把所有变量都藏进 ref 图省事。商品切了，旧定时任务仍可能在请求错的资源。
