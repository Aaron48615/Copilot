# preload 为什么可能造成警告？

## 核心回答

1. preload 是提示浏览器尽早获取当前页面很快会用到的资源，不负责真正使用它。控制台出现预加载后未使用的警告，通常意味着资源在预期时间里没有被消费，但具体观察窗口是浏览器行为，不应背成统一固定秒数。

2. 我会先核对资源是否确实属于首屏。例如把只有进入弹窗才用到的图片全部 preload，用户根本没打开弹窗时自然不会消费，还会与主图、字体等关键内容竞争带宽，提醒本身可能暴露了优先级设计问题。

3. 其次检查 URL、as、类型和凭据模式是否与后续请求一致。字体预加载通常需要正确的 crossorigin，图片响应式选择也可能让浏览器最后用另一张图；请求参数不匹配时，提前下载的内容可能没被复用，甚至重复下载。

4. JavaScript 模块通常考虑 modulepreload，它更符合模块获取和准备的语义。普通 preload 脚本也不会因为下载完成就执行，仍需实际 script 或模块导入；不能只放一个 link 就认为业务代码已经开始工作。

5. 修正时我会查看 Network 中请求的发起原因、优先级和使用时机，删除无价值提示并验证关键资源是否更早完成。警告不是越少越好看这么简单，真正目标是让需要的内容及时可用，同时避免增加首次访问负担。

## 追问：字体 preload 为什么常需要 crossorigin？

1. 字体的实际获取使用相应的跨源请求模式，预加载也需要与最终请求的模式匹配，常见写法会配 crossorigin。即使字体地址看起来同源，也不能只凭域名省略匹配检查，否则浏览器可能没有复用预加载结果。

2. 还要确认预加载的是页面实际使用的字体文件和字重。只用了常规字重，却预先加载多个粗体和不需要的语言子集，会增加传输成本；跨源字体本身也需要服务端满足相应的 CORS 条件。

3. 我会在 Network 看是否同一字体出现重复获取，再检查 CSS 中的 font-family、font-weight 和实际命中字体。验证应覆盖冷缓存，缓存热起来后重复下载现象可能不明显，容易让错误配置被掩盖。

## 追问：响应式图片怎样避免预加载错版本？

1. 使用 srcset、sizes 时，浏览器会根据视口和像素密度选择图片，固定 preload 某个大图地址可能与实际候选不同。我会让预加载的响应式提示与图片元素的选择条件对应，而不是另写一套不一致的尺寸逻辑。

2. 还需要确认它真的可能成为当前视口的 LCP 图片。桌面首图在移动端可能不展示，全部预加载只会占用带宽；如果 HTML 已能很早发现图片，额外提示的收益也可能很小，要通过时间线判断。

3. 我会在不同视口和设备像素比例下检查实际请求地址，确认没有下载两份候选。优化后比较图片发现延迟和首屏完成时间，而不是只因为新增了 preload 标签就认为主图一定更早出现。
