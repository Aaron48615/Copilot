# preload 为什么可能造成警告？

## 核心回答

1. `preload` 是提示浏览器尽早去拿当前页面很快会用到的资源，不负责真正用它。控制台出现预加载后未使用的警告，通常是这份资源在预期时间里没被消费。观察窗口是浏览器自己的行为，别背成统一固定秒数。

2. 资源是不是真属于首屏，先对一下。只有进弹窗才用到的图片全部 `preload`，用户根本没打开弹窗，自然不会消费，还会跟主图、字体抢带宽。这条提醒本身往往说明优先级没设计好。

3. URL、`as`、类型、凭据模式要跟后续那次请求一致。字体预加载通常要配对的 `crossorigin`。图片走响应式，浏览器最后可能用另一张图。请求参数对不上，提前下的那份可能没被复用，甚至下两遍。

4. JavaScript 模块通常考虑 `modulepreload`，更贴近模块获取和准备的语义。普通 `preload` 脚本也不会因为下完就执行，还得有实际的 `script` 或模块导入。只放一个 `link`，业务代码并没有开始工作。

5. 看 Network 里请求的发起原因、优先级、什么时候真正被用。没价值的提示删掉，关键资源是不是更早完成再验证。警告越少越好看，不是目标。真正要的是该用的内容及时可用，首次访问别因此更重。

## 追问：字体 preload 为什么常需要 crossorigin？

1. 字体实际获取用的是相应的跨源请求模式，预加载也要跟最终请求的模式匹配，常见写法会配 `crossorigin`。字体地址看起来同源，也不能只凭域名就省略匹配。对不上，浏览器可能复用不了预加载结果。

2. 预加载的得是页面实际在用的字体文件和字重。只用了常规字重，却预先加载好几个粗体、不需要的语言子集，传输会变重。跨源字体本身也要服务端满足相应的 CORS 条件。

3. Network 里看同一字体有没有重复获取，再对 CSS 里的 `font-family`、`font-weight` 和实际命中的字体。验证覆盖冷缓存。缓存热了之后重复下载可能看不出来，错误配置容易被盖住。

## 追问：响应式图片怎样避免预加载错版本？

1. 用了 `srcset`、`sizes`，浏览器会按视口和像素密度选图。固定 `preload` 某个大图地址，可能跟实际选中的那张不一样。预加载的响应式提示要跟图片元素的选择条件对上，别另写一套尺寸逻辑。

2. 它得真的可能成为当前视口的 LCP 图片。桌面首图在移动端可能不展示，全部预加载只会占带宽。HTML 已经能很早发现这张图，额外提示的收益也可能很小，看时间线再判断。

3. 不同视口、不同设备像素比例下，看实际请求地址，确认没有下两份候选。优化后比较图片发现延迟和首屏完成时间。新增了 `preload` 标签，主图不一定更早出现。
