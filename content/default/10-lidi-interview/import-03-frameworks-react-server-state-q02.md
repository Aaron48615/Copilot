# 请求失败后缓存怎么处理？

## 核心回答

1. 请求失败后不应该统一清空缓存，先区分首次加载失败和已有数据的后台刷新失败。首次没有可展示结果，可以显示错误与重试；已经有旧数据时，通常可以保留并提示刷新失败，让用户知道内容可能不是最新，而不是突然变成空白页。

2. 还要区分失败原因。短暂网络故障可以有限重试，参数错误应让用户修正，明确的权限失效则需要停止展示不再允许访问的数据；不能因为“保留旧缓存体验好”就继续把上一账号的个人内容留在界面上。

3. 缓存应按完整查询条件和身份范围组织，例如商品类别、页码和用户编号。一次查询失败只能影响对应的条目，不能把另一页或另一位用户的数据作为默认替代；空数组也不能同时表达“确实没有结果”和“接口失败”。

4. 修改请求如果使用乐观更新，需要保存回滚依据，失败后恢复或重新获取服务端结果。并发修改同一对象时，简单整体回滚可能覆盖后来的成功操作，所以要按请求范围处理，或采用失效后重新查询的保守方式。

5. 我会让界面分别表达数据是否存在、是否正在刷新和最近一次错误，并提供明确重试入口。重试次数与间隔应有上限，取消请求通常不展示为普通失败；测试时也要覆盖离线、权限变化和恢复联网，而不只测正常成功路径。

## 追问：接口失败和接口返回空列表，为什么不能显示同一句话？

1. 空列表说明请求完成且确实没有匹配结果，用户可以调整筛选或创建内容；请求失败说明结果未知，用户应该重试或检查连接。两者都显示“暂无数据”，会让用户误以为记录已经被删除或条件没有匹配项。

2. 我会根据请求状态和数据来源区分展示。首次失败显示错误区域，成功且为空显示空状态，有旧数据但刷新失败则继续展示旧内容并说明刷新问题，不需要把整个页面统一替换成一个错误图标。

3. 这种区分也有利于排查问题。记录错误类型、查询条件和重试结果，可以知道是后端异常还是正常无结果；不能只把 catch 分支设为 `data=[]`，否则界面和后续分析都失去了失败信息。

## 追问：乐观删除失败时，直接把旧数组放回去安全吗？

1. 如果等待期间没有其他变化，恢复旧数组可能可行，但并发场景中容易覆盖新操作。比如删除 A 后又成功新增 B，A 失败时回填请求前的整个数组，B 也可能被一起删掉，回滚反而制造新的错误。

2. 可以按业务编号恢复受影响项目，或者将相关查询标为失效并重新获取，具体取决于排序、分页和一致性要求。复杂情况下宁愿等待服务端确认再删除，也不要为了即时反馈引入难以解释的状态冲突。

3. 我会让删除中的项目有明确反馈，并避免用户对同一项连续执行冲突操作。测试中安排两个请求交错完成，确认失败恢复只影响它负责的内容；只模拟单次请求失败，发现不了整体快照回滚的问题。
