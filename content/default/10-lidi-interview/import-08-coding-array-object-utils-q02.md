# 分页和后端分页有什么不同？

## 核心回答

1. 前端分页的前提是完整候选数据已经在浏览器里，切页只是取其中一段；后端分页则每次按查询条件取部分数据。比如只有几十条且变化不频繁的配置列表，可以本地分页，数据多或需要及时更新时则更适合按需请求。

2. 本地分页先约定页码从一开始、页大小为正整数，非法输入直接报错，超出范围返回空数组。下面是普通数组的简化实现，slice 不改变原数组，但元素如果是对象仍然共享引用；这不是深拷贝，也没有解决数据加载成本。

   ```js
   function pageOf(items, page, size) {
     if (![page, size].every(x => Number.isSafeInteger(x) && x > 0)) {
       throw new RangeError('invalid page or size');
     }
     const start = (page - 1) * size;
     return items.slice(start, start + size);
   }
   ```

3. 排序和筛选必须针对完整候选集后再分页，否则只会在当前页里得到局部结果。后端分页时这些条件需要一起发给服务端，权限校验也必须由服务端执行，不能把所有数据先交给浏览器，再靠隐藏某些行保护访问范围。

4. 服务端常见的 offset 方式方便按页跳转，但数据插入或删除可能让下一页重复或漏项；游标方式按稳定排序位置继续读取，更适合连续加载。游标也需要明确排序键和更新规则，不代表任何数据变化下都能天然保证一致。

5. 前端仍要处理切页中的 loading、错误恢复和请求竞态，比如第一页慢响应不能覆盖后来选中的第二页。筛选变化时通常重置页码或游标，删除末页最后一条后也要重新确认有效页，而不是继续显示一个无法操作的空页。

## 追问：为什么在当前页排序，会让用户感觉结果不对？

1. 用户通常把“按价格升序”理解为全部搜索结果从便宜到贵排列，而只排序当前页，第二页仍可能有更便宜的商品。这个操作没有改变跨页分布，所以各页内部看起来有序，合起来却不满足用户选择的排序规则。

2. 完整数据在本地时，我会先复制需要排序的数组，再排序并切片，避免 sort 意外改变共享输入。使用后端分页时则把排序字段、方向和筛选条件作为同一次查询的参数，让服务端先确定顺序，再返回对应页的数据。

3. 相同价格需要稳定的次级排序键，例如记录标识，否则跨次请求的同价记录顺序可能不一致。切换排序时还要清掉旧游标并处理旧请求响应；如果继续沿用上一套顺序的游标，即使每次接口都成功，也可能接出错误的列表。

## 追问：游标分页能保证不重复、不漏数据吗？

1. 不能无条件保证，它首先依赖一个明确且能区分记录的排序，比如创建时间加唯一标识。下一页按上次末条记录的排序位置继续查询；只有创建时间而没有处理同一时间的多条记录，就可能在边界漏掉其中一些。

2. 数据更新还可能改变记录的排序位置，例如按热度排列时，一条记录在两次请求间跳到了前面或后面。若业务需要遍历某一时刻的完整集合，就要考虑快照或版本约定；单纯把页码替换成字符串游标并不会自动提供这种一致性。

3. 前端追加列表时可以按稳定标识去重，但去重只能消除重复展示，无法补回未返回的数据。是否还有下一页应遵循接口的游标或 hasNext 约定，总数也可能不提供；不应拿当前已加载条数冒充服务端全部记录数。
