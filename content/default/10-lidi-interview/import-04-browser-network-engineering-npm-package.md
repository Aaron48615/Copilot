# 发布一个 npm 包，构建上要注意什么？

## 核心回答

1. 我还没有正式发布过 npm 包，按准备流程来说。先明确这个包对外暴露什么、跑在哪：浏览器组件还是通用工具，要不要支持 Node。应用项目那一整份构建产物直接上传，当可复用包，通常不对。

2. 输出格式按消费方需要选。ESM 方便静态分析，确实还有人 `require`，再给对应入口。`package.json` 的 `exports`、类型声明、文件扩展名要对上。双格式还要防同一个包被加载成两份状态。只加 `main` 和 `module`，不保证兼容。

3. 依赖要分类。React 这类得跟宿主共用一份的框架，通常放 `peerDependencies`，构建时外置。普通运行时依赖可以放 `dependencies`，不是所有依赖都绝对不能打包。授权、体积、使用方式说清楚，别无意打进第二份框架。

4. 样式和初始化行为要如实声明。`sideEffects: false` 只适合真的没有相应副作用的文件。用了转译辅助库，消费环境得拿得到。类型文件和样式入口也要进发布范围，不然本地源码能用，别人装完却缺文件。

5. 发布前看 `npm pack` 的实际文件清单，在一个独立示例里安装这个包，测导入、类型、生产构建。密钥、缓存、不必公开的源码排除掉，版本变更说清楚。打包验证和正式发布是两步，正式发布是远端操作，按授权做。

## 追问：为什么组件库要避免打入另一份 React？

1. React 组件得跟宿主的渲染器用兼容的那一份运行时。意外打进另一份 React，Hooks 可能异常，体积也变大。把 React 声明成 `peerDependency`，是告诉宿主要提供它，但构建配置还得真正外置，声明和产物不是一回事。

2. 包声明和实际产物两边都看。写了 `peerDependencies`，打包器仍可能把相关代码打进去。`react-dom`、JSX runtime 这些实际导入路径也要外置，只挡一个精确包名，子路径可能漏。

3. 在干净的消费项目里安装打包结果，看依赖树、组件渲染、Hooks。库仓库自己的开发示例看起来正常不够，本地链接、工作区依赖提升，可能把真正发布后的重复依赖盖掉。

## 追问：npm pack 为什么比只检查 dist 更重要？

1. 用户装到的是发布包里实际包含的文件，不是仓库里整个 dist 或源码目录。`files` 配置、忽略规则、生命周期脚本都可能改结果。dist 在，不代表类型、样式、所有入口都会进最终压缩包。

2. 先看打包清单，`exports` 指向的每个文件都在，测试数据、凭据、本地配置排除掉。然后在独立目录安装这个压缩包，走真实的导入路径。用源码别名绕过包入口，验证的不是用户拿到的那份。

3. 构建后的消费结果也要测，比如按需导入还能否带上所需样式、类型能不能解析。发布范围和接口设计的问题能提前发现，正式发布后才发现用户装到的包跟本地验证的不一样，成本更高。
