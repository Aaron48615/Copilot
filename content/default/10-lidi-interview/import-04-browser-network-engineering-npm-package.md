# 发布一个 npm 包，构建上要注意什么？

## 核心回答

1. 我还没有正式发布 npm 包，这部分会按我理解的准备流程来回答。首先明确包的公共接口和目标环境，是浏览器组件还是通用工具，是否需要支持 Node；不能把应用项目的全部构建产物直接上传就当作一个可复用包。

2. 输出格式按消费需求选择，ESM 有利于静态分析，确实需要 require 的用户再提供相应兼容入口。package.json 的 exports、类型声明和文件扩展名要匹配，双格式还要防止同一个包被加载成两份状态，不能只添加 main 和 module 就保证兼容。

3. 依赖要分类，React 这类需要与宿主共享的框架通常使用 peerDependencies 并在构建中外置。普通运行时依赖可以放 dependencies，不是所有依赖都绝对不能打包；关键是授权、体积和使用方式清楚，避免无意产生重复框架。

4. 样式和初始化行为要准确声明，sideEffects:false 只适合真实没有相应副作用的文件。使用了转译辅助库就确保消费环境能获得它，类型文件和样式入口也要包含在发布范围内，否则本地源码能用，安装后的包却缺文件。

5. 发布前我会检查 npm pack 的实际文件清单，在独立示例里安装包并测试导入、类型和生产构建。还要排除密钥、缓存与不必要源码，明确版本变更；实际发布是远端操作，应按授权执行，不能把打包验证和正式发布混为一谈。

## 追问：为什么组件库要避免打入另一份 React？

1. React 组件需要与宿主渲染器使用兼容的运行时，意外打入另一份 React 可能带来 Hooks 等使用异常，也增加体积。把 React 声明为 peerDependency 是表达宿主依赖关系，但构建配置仍要正确外置它。

2. 我会同时检查包声明和实际产物，因为写了 peerDependencies 不代表打包器一定没有把相关代码打进去。还要关注 react-dom 和 JSX runtime 等实际导入路径，避免只外置一个精确包名却遗漏子路径。

3. 验证时在干净的消费项目中安装打包结果，观察依赖树、组件渲染和 Hooks 行为。不能只在库仓库的开发示例里看起来正常，因为本地链接与工作区依赖提升可能掩盖真正发布后的重复依赖问题。

## 追问：npm pack 为什么比只检查 dist 更重要？

1. 用户安装的是发布包里实际包含的文件，不是仓库中的整个 dist 或源码目录。files 配置、忽略规则和生命周期脚本都可能影响结果，所以 dist 存在不代表类型、样式和所有入口都会进入最终压缩包。

2. 我会先查看打包清单，确认 exports 指向的每个文件都存在，并排除测试数据、凭据和本地配置。然后在独立目录安装这个压缩包，验证真实的导入路径，而不是通过源码别名绕过包的入口规则。

3. 还要测试构建后的消费结果，例如按需导入是否保留所需样式、类型是否可解析。这样能提前发现发布范围和接口设计的问题，避免正式发布后才发现用户装到的包与开发者本地验证的内容不同。
