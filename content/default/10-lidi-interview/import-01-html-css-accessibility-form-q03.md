# 错误提示要不要用 alert？

## 核心回答

1. 我会先区分浏览器的 `window.alert()` 和 ARIA 的 alert 角色。前者会打开阻塞式提示框，通常不适合普通字段校验；后者用于向辅助技术及时宣布重要消息，不会自动弹出窗口，也不会替我们把错误显示在页面上。

2. 普通字段错误可以直接显示在字段附近，用描述关联说明原因，并标记无效状态。比如邮箱少了域名，用户需要看到具体要求、保留原输入并能继续修改，没有必要每敲一个字符都通过强提醒打断当前阅读。

3. 需要立即知道的提交失败，可以考虑 `role="alert"`；不那么紧急的状态，如“正在保存”或“保存完成”，通常更适合温和的 live region。播报区域应在合适时机准备好并更新内容，避免重复挂载造成漏报或多次宣布，实际效果要用读屏验证。

4. 提示也不能只依赖声音。错误要持续可见，必要时提供重试按钮或错误汇总，并根据场景移动焦点。alert 本身不要求拿走焦点；如果同时聚焦相同错误文本又触发强播报，用户可能连续听两遍，反而难以理解下一步。

5. 例如支付表单中某个字段不完整，可以在原位置说明；会话过期导致整次提交无法继续，则需要更明显地告知重新登录的路径。提醒强度应取决于用户是否必须立即改变当前操作，而不是后端统一返回了一个错误码。

## 追问：为什么每个字段都加 role="alert" 可能更难用？

1. 用户提交一张有多个错误的表单时，多个强提醒可能同时触发，播报被打断或排队，听完也未必知道对应哪个字段。字段越多，逐个强制宣布越容易让错误之间失去上下文。

2. 我会把字段说明稳定放在对应输入框附近，通过名称和描述关联提供局部信息。表单级别再给一条汇总，例如说明有几处待修改，并提供跳转入口，用户可以按自己的节奏逐项处理。

3. 修正过程中只更新发生变化的错误状态，不要每次渲染都重写全部提示。验证时关注实际听到的内容、顺序和重复次数，而不是仅仅检查 DOM 里有几个 ARIA 属性，属性存在并不等于播报体验合适。

## 追问：提交失败和网络断开应该给相同的错误提示吗？

1. 不应该。字段不符合要求需要用户修改输入，网络断开需要恢复连接或重试；如果统一写成“提交失败，请检查表单”，用户可能反复修改正确的信息，也不知道已经输入的数据是否还在。

2. 我会保留表单内容，并用明确文案说明这次请求没有确认成功。对于可能已经到达服务端的提交，还要按业务检查结果或使用防重复机制，不能让用户多点几次就产生多条重复记录。

3. 网络状态提示可以通过温和播报让用户知道恢复情况，只有确实紧急时才用强提醒。重试按钮应有清晰状态，等待时避免重复触发，失败后重新可操作，并保持焦点在合理位置，便于连续尝试。
