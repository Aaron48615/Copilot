# 错误提示要不要用 alert？

## 核心回答

1. 先分清浏览器的 `window.alert()` 和 ARIA 的 alert 角色。前者会弹出阻塞框，普通字段校验一般别用。后者是给辅助技术及时宣布重要消息，不会自己弹窗，也不会替你把错误画到页面上。

2. 普通字段错误直接显示在字段旁边，用描述关联说明原因，并标上无效状态。比如邮箱少了域名，人要看到具体要求、原来填的还在、能接着改。每敲一个字符就强提醒打断阅读，没必要。

3. 提交失败这种得马上知道的，可以考虑 `role="alert"`。「正在保存」「保存完成」这类不那么急的，用温和一点的 live region 就够。播报区域要在合适时机准备好再改内容，别反复挂卸载，漏报或连念好几遍都常见，实际效果得用读屏听。

4. 提示也不能只靠声音。错误要一直看得见，该给重试按钮或错误汇总就给，该移焦点就移。alert 本身不要求把焦点拿走；要是同时又聚焦同一段错误文本、又强播报，人可能连听两遍，下一步更不清楚。

5. 支付表单某个字段没填完，在原位置说明就行。会话过期导致整次提交走不下去，得更明显地告诉人怎么重新登录。提醒有多冲，看用户是不是必须马上改当前操作，别看后端统一回了一个错误码。

## 追问：为什么每个字段都加 role="alert" 可能更难用？

1. 一张表提交后好几个字段都错，多个强提醒可能一起响，播报被打断或排队，听完也不一定知道对应哪个框。字段越多，一个个强制宣布，错误之间更容易没了上下文。

2. 字段说明稳稳放在对应输入框旁边，用名称和描述关联提供局部信息。表单顶上再给一条汇总，比如有几处要改，并提供跳转入口，人可以按自己的节奏一项项处理。

3. 修正过程中只更新真正变了的错误，别每次渲染都把全部提示重写一遍。听实际念了什么、什么顺序、重复了几次，别只数 DOM 里有几个 ARIA 属性。属性在，不等于播报好用。

## 追问：提交失败和网络断开应该给相同的错误提示吗？

1. 不该。字段不符合要求，人得改输入；网络断了，人得连上或重试。统一写成「提交失败，请检查表单」，人可能对着本来没错的内容反复改，也不知道已经填的还在不在。

2. 表单内容先留着，文案说清楚这次请求没有确认成功。请求可能已经到了服务端，还得按业务查结果，或者做防重复。别让人多点几次就多出几条记录。

3. 网络状态可以用温和播报让人知道恢复了没，真紧急再用强提醒。重试按钮状态要清楚：等的时候别重复点，失败了再能点，焦点留在好接着试的位置。
