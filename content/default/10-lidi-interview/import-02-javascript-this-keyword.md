# this 的指向怎么判断？

## 核心回答

1. 我会先区分普通函数和箭头函数，再看实际的调用表达式。普通函数作为 `obj.fn()` 执行时，接收者是 obj；把方法赋给另一个变量后再直接调用，原来的对象关系就没有了，不能因为函数写在对象里就认定它永远属于这个对象。

2. 普通函数直接调用时，严格模式里的 this 是 undefined，非严格模式下，直接调用通常会使用全局对象。这里不能一律说成 window，因为运行环境可能是 Node.js，而且模块顶层的 this 和函数内部的 this 也不是同一个问题。

3. `call` 和 `apply` 会在这次调用中传入 this，`bind` 则返回一个绑定后的函数，暂时不执行原函数。对可构造的绑定函数使用 new 时，绑定的 this 会被忽略，所以我不会把 new 和显式绑定简单说成完全相同的优先级。

4. 箭头函数没有自己的 this，会沿外层作用域查找，给它调用 call 或 bind 也改不了这个值。例如对象方法内部创建一个箭头回调，可以沿用这次方法调用的 this，但对象字面量本身不会给箭头函数提供一个 this。

5. 实际排查时，我会找到函数最终在哪里、以什么形式被执行，再看是否经过绑定或包装。定时器和事件回调还要看宿主接口的约定，不能把所有回调都当成严格模式下的直接调用，也不能仅凭函数定义位置下结论。

## 追问：把对象方法传给定时器后，怎样保留原来的 this？

1. 直接传入 `obj.run` 只交出了函数值，并没有一起传入方法调用的接收者。定时器怎样调用它由运行环境决定，因此即使原来 `obj.run()` 正常，回调里读取对象属性也可能得不到预期结果。

2. 可以传入 `() => obj.run()`，让回调执行时重新完成一次对象方法调用。这里真正保证接收者的是内部的调用表达式；如果 obj 变量之后被重新赋值，执行时读到的也会是新的对象，需要考虑是否符合预期。

3. 也可以事先保存 `obj.run.bind(obj)`，把原对象固定下来，再把绑定函数交给定时器。两种写法都能用，但绑定函数会固定当时的方法和对象，包装函数则会在执行时读取方法，选择时要看是否需要反映后续变化。

## 追问：对象里的箭头方法为什么不能自动访问这个对象？

1. 对象字面量只是创建对象，不会像普通函数调用一样建立 this 绑定。因此 `run: () => this.name` 里的 this 来自外层作用域，即便通过对象属性调用，箭头函数也不会改为读取这个对象的 name。

2. 如果方法需要根据调用对象工作，我会写成普通方法，再在方法内部用箭头函数处理需要继承 this 的回调。这样内外职责比较清楚，也能通过借用方法的方式，让同一个函数为不同对象读取各自的数据。

3. 类的实例箭头字段是另一种情况，字段初始化时可以捕获该实例的 this，所以传出去后通常仍能访问实例。代价是每个实例都会创建自己的函数，不能把它和原型上共享的普通方法当成存储方式完全一样的写法。
