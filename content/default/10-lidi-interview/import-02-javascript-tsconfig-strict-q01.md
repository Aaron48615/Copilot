# strictNullChecks 为什么有用？

## 核心回答

1. strictNullChecks 的作用，是让 null 和 undefined 在类型上被认真区分出来。一个变量如果声明为用户对象，就不能随便把空值塞进去；可能查不到用户时，类型应该如实写成对象与空值的联合，而不是让调用方猜测。

2. 最直接的例子是数组的 find，它即使面对非空数组，也可能找不到符合条件的元素。开启检查后，我需要先处理查找失败，再访问结果的属性，这会把原本藏在运行时的报错提前变成开发时的提示。

3. 处理空值时，我会先确定业务含义，再决定提前返回、显示空状态还是提供默认值。比如没有昵称可以展示“未填写”，但缺少订单编号就不能随便补一个空字符串继续提交，否则只是把错误推迟到更难定位的位置。

4. 可选链能避免空值上的属性访问，结果却仍可能是 undefined，并不代表业务已经完成处理。使用空值合并给默认值时，也要确认默认值合理；它保留零和空字符串，与按真假判断的逻辑或并不一样。

5. 这个选项不会检查服务器实际返回的数据，也不会独自覆盖所有数组下标越界情况。外部数据还需要运行时校验，下标访问可以另外启用对应选项；非空断言只消除提示，不能把一个不存在的值变成真实对象。

## 追问：为什么判断用户存在后，还要单独判断用户的可选字段？

1. 用户对象存在，只能证明最外层不是空值，不能证明里面每个字段都存在。例如昵称本来就是可选字段，那么登录成功取得用户对象以后，昵称仍然可能缺失，这是两个不同层次的条件。

2. 我会根据字段用途选择处理方式，展示昵称可以用占位文案，发送通知需要的地址则要明确检查。不能因为用户已经登录，就通过非空断言认为所有资料齐全，否则资料未完善的用户仍会触发异常。

3. 如果很多地方都要求某些字段完整，可以在检查通过后返回一个描述完整资料的新类型。这样后续函数接收的前提更清楚，但转换函数必须真的验证字段，不能只换一个类型名称来假装资料已经补全。

## 追问：什么时候用空值合并，什么时候应该直接报错？

1. 空值合并适用于缺失后有明确合理替代值的场景，例如可选说明没有填写时显示提示文字。我会先确认空字符串是不是用户有意填写的值，因为空值合并不会像逻辑或那样把它也替换掉。

2. 如果缺失的是流程必须依赖的信息，例如准备跳转详情却没有资源编号，我会停止这一步并展示错误。补成零或空字符串虽然容易通过类型检查，却可能发出错误请求，让用户看见另一种更难理解的失败。

3. 还有些空值代表正常业务结果，例如搜索确实没有找到记录，这时应显示空状态而不是技术错误。选择默认值、空状态还是报错，需要跟接口约定和页面用途一致，类型系统本身无法替我作出这个业务判断。
