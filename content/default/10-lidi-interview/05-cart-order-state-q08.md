# 轻购的订单提交、取消支付和支付失败怎么处理？

## 核心回答

1. 先调用 submitOrder 创建订单，成功后取返回的 orderNumbers 或 orderNumber。没有拿到订单号时不能继续盲目支付，应提示创建结果需要确认；字段兼容处理也要明确数组与单号的约定，不能把任何非空响应都当作支付标识。

2. 拿到订单号后删除 sessionStorage 的 confirmOrder，因为购买意图已经变成服务端订单。后续取消支付或支付失败都不应该回到“订单从未创建”的状态，否则刷新旧确认页可能再次提交相同商品。

3. 然后弹出确认支付对话框，用户取消时按暂不支付处理，订单保持待付款并回到“我的”入口。关闭支付弹窗不是取消订单，不应该把订单从列表删除，也不应显示提交失败这种不符合实际阶段的文案。

4. 用户确认后调用 payOrder，携带订单号与 payType: 1，异常或业务失败时提示，没有成功就不执行成功跳转。当前是模拟支付流程，成功后 replace 到我的页面，真实订单状态仍可从订单列表重新获取。

5. 真正第三方支付还需要服务端支付单、通知校验和幂等处理。特别是超时只表示没拿到响应，不足以判断未付款；如果继续完善，我会先查询已创建订单，再允许安全重试，不能自动重新创建订单或承诺真实扣款已经完成。

## 追问：订单提交成功但没有订单号，可以直接再提交吗？

1. 不能根据前端缺字段就断言服务端没创建。可能只是响应字段变化、解析错误或部分响应丢失，再提交可能生成第二张订单，所以应先把它当结果需要确认，而不是普通校验失败。

2. 如果继续完善，我会利用服务端支持的请求标识查询结果，或者引导到订单列表核对本次订单。没有查询协议时至少明确提示勿连续提交，不能前端猜一个订单号，也不能拿支付流水号与订单号混用。

3. 测试模拟成功响应缺号、单号与多号结构，以及请求已完成但响应超时，检查不会自动重放创建。前端按钮保护只限制本页点击，真正避免重复创建还需要后端幂等约定与事务验证。

## 追问：支付失败后为什么优先回到订单状态？

1. 订单是已经保存的业务对象，支付失败只影响它是否付款，不会让选购与地址确认都重新开始。用户应该能找到同一订单继续处理，而不是被迫回购物车再选一遍并创建另一单。

2. 失败还可能是结果未知，查询订单能区分已支付、待支付或其他状态。特别是网络中断，浏览器报错并不意味着后端动作没有完成，页面文案应避免把未知结果写成确定未付款。

3. 当前模拟支付可通过订单列表回读状态，真实支付还要与平台结果核对。如果继续完善，我会给继续支付、查看订单和刷新状态清楚入口，并限制无依据的自动重试，让用户知道操作针对的始终是同一张订单。
