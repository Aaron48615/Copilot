# 缓存列表页会不会拿到旧数据？

## 核心回答

1. 会，KeepAlive 保留的是组件实例和状态，不会自动保证接口结果一直新鲜。列表切走后服务器可能发生新增、删除或状态变化，回来时仍显示上次缓存，这是使用组件缓存需要主动设计的数据更新问题，而不是框架帮我们承诺的实时一致。

2. 我会把需要恢复的界面状态和需要确认的服务端数据分开。筛选条件、展开项和滚动位置通常值得保留，库存、订单状态等则可能要重新获取；不能为了拿新数据就把整页缓存全部丢掉，让用户每次都从列表顶部重新开始。

3. 激活时可以按更新时间、业务失效标记或用户主动刷新决定是否请求。比如详情页成功修改了某项，返回列表时只更新相关项或标记列表需要刷新；不是所有返回都必须重新查，也不能永远只凭已有数组不再确认。

4. 请求中可以保留旧数据并显示轻量刷新提示，失败时说明内容尚未更新。若筛选条件或账号已变化，需要检查缓存身份和请求归属，旧请求不能覆盖新条件；个人数据尤其不能跨登录会话复用。

5. 列表刷新后还要处理记录删除和排序变化对滚动位置的影响。恢复位置应在列表 DOM 更新且相关尺寸条件满足后进行，必要时按记录锚点恢复；nextTick 只能等待 Vue 更新，不能保证图片尺寸或第三方虚拟列表已经稳定。

## 追问：每次 activated 都重新请求，是不是最保险？

1. 它能提高重新确认的机会，但会增加请求和等待，也未必满足所有体验要求。频繁切换页签时，每次都清空列表重新加载，用户会失去连续浏览感，尤其网络差时，即使旧数据仍有价值也完全看不到。

2. 可以结合业务时效使用新鲜度窗口或修改标记。比如详情保存成功后明确标记列表失效，而短时间内单纯查看返回可以先复用；高时效数据则更积极刷新，策略来自数据用途，不是一套间隔适用所有页面。

3. 我会保留手动刷新入口并处理后台刷新失败，不把“发过请求”当成“数据已经正确”。还要验证快速激活、停用和再次激活，旧返回不能改掉后一轮结果，重复激活也不应同时建立多份轮询。

## 追问：返回列表后怎么兼顾新数据和原来的浏览位置？

1. 先保存筛选条件和可识别的位置，例如当前顶部记录编号及偏移，而不只存绝对 scrollTop。若前面新增了几条记录，绝对像素仍相同，但用户看到的内容可能完全换了，按记录锚点更符合继续浏览的意思。

2. 新数据到达后等列表完成更新，再寻找原锚点恢复；锚点被删除时需要有合理退路，如邻近记录或当前页顶部。图片和动态行高会影响位置，必要时等待相应加载或使用列表组件提供的定位接口。

3. 我会避免每次后台刷新都强制滚动，用户正在主动浏览时突然拉回原位置同样令人困惑。通常只在返回激活或明确恢复动作时处理，并测试刷新导致排序变化的情况，保证恢复规则可解释。
