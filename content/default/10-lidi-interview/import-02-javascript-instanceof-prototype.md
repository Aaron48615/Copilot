# instanceof 怎样沿原型链判断？

## 核心回答

1. 对没有自定义判断行为的普通构造函数，`value instanceof Ctor` 会沿着值的原型链寻找构造函数的原型对象。从值的直接原型开始向上查找，遇到相同引用就成立，走到空原型仍未找到就不成立，比较的不是属性是否相似。原型对象上即使没有任何业务方法，只要这条连接关系存在，也可能得到成立的结果。

2. 这也是子类实例通常同时属于子类和父类的原因：它的查找链经过子类原型，再到父类原型。相反，一个普通对象即使拥有与某个类完全一样的字段，只要没有对应的原型联系，也不会因此通过普通的实例判断。

3. 真正的运算符会先考虑右侧对象的 `Symbol.hasInstance` 方法，所以右侧不一定只能是普通函数，自定义方法还可以改变判断规则。若没有可用规则且右侧不满足要求，可能抛出类型错误，不能简单把所有非法输入统一解释为假值。

4. 手写时我会明确只模拟普通原型链查找，并用 `Object.getPrototypeOf` 逐级比较。跨窗口构造函数、绑定函数、自定义判断以及替换原型都会让完整语义更复杂，因此简化实现适合解释原理，不能声称可以无条件替代原生运算符。

## 追问：修改构造函数的 prototype 后，旧实例的判断为什么会变？

1. 普通构造函数创建实例时，实例连接的是当时那个原型对象。如果之后把构造函数的原型属性换成另一个对象，旧实例的连接通常仍然保留，新的实例判断却使用替换后的原型作为目标，所以结果可能变成假值。

2. 这里要区分替换整个原型和修改原型上的方法。只修改原来那个对象上的方法，并没有改变对象身份，旧实例通常仍然通过判断，也能在没有自身同名属性的情况下读到更新后的方法。

3. 因此我不会依靠运行中替换原型来给所有旧实例升级行为，因为它不会自动重连旧实例。以上讨论针对允许替换原型属性的普通构造函数，类构造函数的原型属性不可按同样方式赋值替换，不能混为一谈。

## 追问：手写 instanceof 时只判断右侧是不是函数有什么遗漏？

1. 一个普通对象如果实现了可调用的自定义实例判断方法，也能参与这个运算符。先用函数类型检查拒绝它，就会错过原生运算符允许的情况，因此简化版本应该明确限制输入范围，而不是说完全兼容。

2. 绑定函数也需要额外处理，因为原生判断可以转向它绑定的目标函数，而直接读取绑定函数的原型属性未必能得到目标原型。只写一个沿链循环的版本，无法覆盖这类转发行为，测试时应把这个差别说出来。

3. 还要注意错误行为，右侧没有有效判断能力时可能抛错，箭头函数也不能仅凭函数身份就保证可用。面试中我会先讲普通构造函数的实现，再说明这些边界，避免为了短代码把抛错情况全部吞成假值。
