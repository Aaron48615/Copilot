# instanceof 怎样沿原型链判断？

## 核心回答

1. 对没有自定义判断行为的普通构造函数，`value instanceof Ctor` 会沿着值的原型链找构造函数的原型对象。从值的直接原型开始往上找，碰到相同引用就成立，走到空原型还没找到就不成立。比的不是属性像不像。原型对象上就算没有任何业务方法，只要这条连接在，也可能得到成立的结果。

2. 这也是子类实例通常同时属于子类和父类的原因：查找链经过子类原型，再到父类原型。反过来，一个普通对象即使字段跟某个类完全一样，没有对应的原型联系，普通的实例判断也不会过。

3. 真正的运算符会先看右侧对象有没有 `Symbol.hasInstance` 方法，所以右侧不一定只能是普通函数，自定义方法还可以改判断规则。没有可用规则且右侧不满足要求，可能抛出类型错误。非法输入不能一律解释成假值。

4. 手写时明确只模拟普通原型链查找，用 `Object.getPrototypeOf` 一级一级比。跨窗口构造函数、绑定函数、自定义判断、替换原型，都会让完整语义更复杂。简化实现适合讲原理，不能无条件替代原生运算符。

## 追问：修改构造函数的 prototype 后，旧实例的判断为什么会变？

1. 普通构造函数创建实例时，实例连的是当时那个原型对象。之后把构造函数的原型属性换成另一个对象，旧实例的连接通常还留着，新的实例判断却用替换后的原型当目标，结果可能变成假。

2. 要分清替换整个原型，和修改原型上的方法。只改原来那个对象上的方法，对象身份没变，旧实例通常仍然通过判断，自身没有同名属性时也能读到更新后的方法。

3. 运行中替换原型，不会自动把旧实例重新接上去，别靠这一招给所有旧实例升级行为。以上针对允许替换原型属性的普通构造函数。类构造函数的原型属性不能按同样方式赋值替换，两套不能混谈。

## 追问：手写 instanceof 时只判断右侧是不是函数有什么遗漏？

1. 一个普通对象如果实现了可调用的自定义实例判断方法，也能参与这个运算符。先用函数类型检查拒绝它，就会漏掉原生运算符允许的情况。简化版本应明确限制输入范围，别说完全兼容。

2. 绑定函数也要额外处理。原生判断可以转向它绑定的目标函数，直接读绑定函数的原型属性未必能拿到目标原型。只写一个沿链循环的版本，盖不住这类转发。测试时把这个差别说出来。

3. 右侧没有有效判断能力时可能抛错，箭头函数也不能只凭函数身份就保证可用。普通构造函数这条链能讲清楚，这些边界还在。别为了短代码把抛错情况全部吞成假值。
