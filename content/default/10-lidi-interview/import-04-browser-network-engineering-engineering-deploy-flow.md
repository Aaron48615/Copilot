# 项目是怎么打包上线的？

## 核心回答

1. 前端打包上线，就是把确定版本的源码变成静态产物，再让服务器正确提供这些文件。以 Vite 构建、Nginx 托管为例：先确认构建环境和接口地址，再检查上传的资源齐不齐，最后验证用户从真实域名进来时，页面路由和业务请求都对。

2. 构建前按锁文件装依赖，跑项目已有的检查。接口地址和公开功能开关按环境配，但构建进客户端的变量都可能被看见，API Key 这类服务端密钥放进环境变量，不等于就安全了。

3. 部署时 Nginx 分别处理静态资源、页面路由和接口代理。history 路由要在正确范围回退到入口 HTML，但 `/api` 和不存在的 JS 文件不能也一律回成页面，否则接口解析和模块加载会出现很难懂的错误。

4. 新版资源先上传，再更新入口。HTML 及时验证，带内容 hash 的资源可以合理长缓存。旧产物留一段时间，既方便回滚，也避免还停在旧页面的用户找不到之后才加载的 chunk。

5. 发布后验证首页、深层链接、登录、接口和懒加载页面。预发布尽量接近生产配置，但不必直接连生产数据库。可以逐步放量、看错误，再决定要不要扩大范围。构建成功不等于上线成功。

## 追问：刷新深层路由出现 404，应该查哪里？

1. 先分清应用里点击，和浏览器直接访问。SPA 内部导航由前端路由处理，但刷新 `/orders/123` 时，服务器收到的是这个完整路径。服务器如果只找同名文件，就会 404，前端代码还没机会接手。

2. 给页面路由配入口回退，同时把静态资源和接口路径单独处理。所有不存在的请求都回退到 `index.html`，缺失的 JS 也会变成 200 加 HTML，浏览器反而报模块类型或语法错误，把真实原因盖住。

3. 验证时直接打开一个有效深层地址，再测不存在的资源和接口。页面能恢复、错误资源仍返回正确状态，规则范围才算合适。部署在子目录时，还要核对 `base` 和前端路由前缀。

## 追问：回滚前端版本，为什么还要考虑后端接口？

1. 旧前端可能依赖已经改过的接口字段或业务约定，把旧静态文件恢复回去，不保证它还能正常请求。比如后端删了旧字段，前端回滚后页面能打开，表单提交或数据显示仍可能失败。

2. 接口演进尽量留一段兼容期，发布前说清楚新旧版本能一起用的组合。静态产物按版本保存，同时记下对应配置和接口要求。只留下一个不知道属于哪次发布的 `dist` 目录，不够。

3. 回滚后还是要跑关键业务验证，并注意 CDN 和浏览器入口缓存。出问题时先确认用户实际拿到哪个版本，再判断要不要调接口或配置。连续刷新 CDN，却忽略前后端不兼容，解决不了。
