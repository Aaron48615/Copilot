# 项目是怎么打包上线的？

## 核心回答

1. 我的理解是，前端打包上线要把确定版本的源码变成静态产物，再让服务器正确提供这些文件。以 Vite 构建和 Nginx 托管为例，我会先确认构建环境与接口地址，再检查上传的资源是否完整，最后验证用户从真实域名访问时的页面路由和业务请求。

2. 构建前应按锁文件安装依赖，并运行项目已有检查。接口地址和公开功能开关按环境配置，但构建进入客户端的变量都可能被看到，所以 API Key 等服务端密钥不能因为放在环境变量中就认为安全。

3. 部署时 Nginx 分别处理静态资源、页面路由和接口代理。history 路由需要在正确范围回退到入口 HTML，但 /api 和不存在的 JS 文件不能也一律返回页面，否则接口解析和模块加载会出现难懂的错误。

4. 新版资源要先上传，再更新入口，HTML 及时验证，带内容 hash 的资源合理长缓存。旧产物保留一段时间，既方便回滚，也避免停留在旧页面的用户找不到之后才加载的 chunk。

5. 发布后我会验证首页、深层链接、登录、接口和懒加载页面。预发布应尽量接近生产配置，但不必直接使用生产数据库；如果继续完善，可以逐步发布并观察错误，再决定是否扩大范围，不能只以构建成功作为上线成功。

## 追问：刷新深层路由出现 404，应该查哪里？

1. 先区分应用内点击和浏览器直接访问。SPA 内部导航由前端路由处理，但刷新 /orders/123 时服务器收到的是这个完整路径；若服务器只找同名文件，就会返回 404，前端代码还没有机会接管。

2. 我会给页面路由配置入口回退，同时把静态资源和接口路径单独处理。若把所有不存在的请求都回退到 index.html，缺失的 JS 也会返回 200 和 HTML，浏览器反而报模块类型或语法错误，掩盖真实原因。

3. 验证时直接打开一个有效深层地址，再测试不存在的资源和接口。页面能恢复、错误资源仍返回正确状态，才说明规则范围合适；还要核对部署在子目录时的 base 和前端路由前缀。

## 追问：回滚前端版本，为什么还要考虑后端接口？

1. 旧前端可能依赖已经改变的接口字段或业务约定，恢复旧静态文件并不保证它还能正常请求。比如后端删除了旧字段，前端回滚后即使页面能打开，也可能在表单提交或数据显示时失败。

2. 我会让接口演进尽量保持一段兼容期，发布前明确新旧版本可支持的组合。静态产物按版本保存，同时记录对应配置和接口要求，不能只留下一个不知道属于哪次发布的 dist 目录。

3. 回滚后仍要跑关键业务验证，并注意 CDN 与浏览器入口缓存。发现问题时先确认用户实际拿到哪个版本，再判断是否需要调整接口或配置，而不是连续刷新 CDN 却忽略了前后端不兼容。
