# Axios 拦截器应该放哪些逻辑？

## 核心回答

1. 我会把拦截器用于同一类接口共用的请求和响应规则，通常先创建独立的 Axios 实例。请求阶段可以附加认证头和请求标识，但要限制目标服务范围，避免把自己的 Token 发给不相关的第三方地址。

2. 响应阶段适合按约定识别 HTTP 错误和业务错误，并整理出调用方能处理的错误信息。默认情况下非 2xx 响应进入失败处理，但 validateStatus 可以改变这个判断，因此不能假设所有项目都按同一规则执行。

3. 认证过期可以统一处理，不过是否刷新凭据、是否跳登录页，要遵循具体认证方案。页面自己的表单校验、库存不足提示或列表刷新不适合都写进拦截器，否则一个接口的修改可能影响其他页面。

4. 拦截器要保持 Promise 行为清楚，请求处理返回 config，响应处理返回约定的结果，失败继续抛出或拒绝。不能捕获错误后什么都不返回，让页面把 undefined 当成请求成功，也要避免公共层和页面重复弹提示。

5. 文件上传、下载和公开接口需要支持各自的配置，不能统一强制 JSON 解析或认证头。如果在组件中动态注册拦截器，还要在适当时 eject；全局 loading 使用并发计数，并保证成功、失败和取消都正确扣减。

## 追问：多个请求同时返回 401，怎么避免重复刷新 Token？

1. 如果系统采用刷新机制，我会让同一客户端共享一个正在进行的刷新 Promise。第一个请求发起刷新，其他符合条件的请求等待它，而不是每个请求各自刷新，造成凭据互相覆盖或重复跳转。

2. 刷新成功后再更新认证状态，并为原请求限制重放次数；刷新接口本身应绕开这段重试逻辑。还要区分未认证失败与已经产生副作用的请求，不能对所有请求无限自动重放。

3. 刷新失败时统一结束等待并清理失效会话，错误仍传给各调用方处理。这个方案属于需要实现和验证的设计，不能仅仅写一个 401 判断就声称处理好了并发、退出登录和重试边界。

## 追问：拦截器统一返回 response.data，有什么取舍？

1. 好处是业务调用更简洁，不必每次再取 data；代价是默认拿不到状态码、响应头等信息。比如分页总数在响应头里，或下载需要 Content-Disposition 文件名，只返回 data 就会丢掉必要上下文。

2. 我会先统一返回约定，并给需要原始响应的接口保留明确入口，例如独立实例或专门方法。TypeScript 类型也要与真实返回值一致，不能运行时返回数据，声明却仍然让调用方当成 AxiosResponse。

3. 下载错误还可能以 Blob 形式返回，需要依据响应类型和接口约定解析错误，而不是直接当文件保存。公共层应该提供稳定基础行为，具体文件命名、业务提示和页面更新仍由对应功能决定。
