# Axios 拦截器应该放哪些逻辑？

## 核心回答

1. 拦截器用来放同一类接口共用的请求和响应规则，通常先创建独立的 Axios 实例。请求阶段可以附加认证头和请求标识，但要限制目标服务范围，别把自己的 Token 发给不相关的第三方地址。

2. 响应阶段适合按约定识别 HTTP 错误和业务错误，并整理成调用方能处理的错误信息。默认非 2xx 进入失败处理，但 `validateStatus` 可以改这个判断，别假设所有项目都按同一规则执行。

3. 认证过期可以统一处理，不过要不要刷新凭据、要不要跳登录页，得跟具体认证方案走。页面自己的表单校验、库存不足提示、列表刷新，不适合都写进拦截器。不然一个接口的修改可能影响其他页面。

4. 拦截器要保持 Promise 行为清楚：请求处理返回 `config`，响应处理返回约定的结果，失败继续抛出或拒绝。别捕获错误后什么都不返回，让页面把 `undefined` 当成请求成功。公共层和页面也别重复弹提示。

5. 文件上传、下载和公开接口需要支持各自的配置，别统一强制 JSON 解析或认证头。如果在组件里动态注册拦截器，还要在适当时 `eject`。全局 loading 用并发计数，成功、失败、取消都要正确扣减。

## 追问：多个请求同时返回 401，怎么避免重复刷新 Token？

1. 系统如果采用刷新机制，同一客户端共享一个正在进行的刷新 Promise。第一个请求发起刷新，其他符合条件的请求等它。别每个请求各自刷，凭据互相覆盖或重复跳转。

2. 刷新成功后再更新认证状态，并为原请求限制重放次数。刷新接口本身应绕开这段重试逻辑。还要分清未认证失败，和已经产生副作用的请求，别对所有请求无限自动重放。

3. 刷新失败时统一结束等待并清理失效会话，错误仍传给各调用方处理。这套要真正实现并验证。只写一个 401 判断，处理不了并发、退出登录和重试边界。

## 追问：拦截器统一返回 response.data，有什么取舍？

1. 好处是业务调用更简洁，不必每次再取 `data`。代价是默认拿不到状态码、响应头这些信息。比如分页总数在响应头里，或下载需要 `Content-Disposition` 文件名，只返回 `data` 就会丢掉必要上下文。

2. 先统一返回约定，并给需要原始响应的接口留明确入口，比如独立实例或专门方法。TypeScript 类型也要跟真实返回值一致。运行时返回数据，声明却还让调用方当成 `AxiosResponse`，会对不上。

3. 下载错误还可能以 Blob 形式返回，要依据响应类型和接口约定解析错误，别直接当文件保存。公共层提供稳定基础行为，具体文件命名、业务提示、页面更新仍由对应功能决定。
