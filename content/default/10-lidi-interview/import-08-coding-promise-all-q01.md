# 失败后其他任务会停止吗？

## 核心回答

1. 不会，Promise.all 只组合结果，不负责停止任务。比如同时发三个请求，其中一个先失败，组合 Promise 会以最先使它拒绝的原因结束，但另外两个请求仍可能继续下载和处理，不能把快速失败理解成全部执行都停下来了。

2. 请求通常在调用 fetch 或任务函数时就已经启动，Promise.all 接收的是这些执行结果对应的 Promise。它既不提供并发上限，也不会自动调用传入的普通函数；因此想控制哪些任务开始，应该管理任务函数的调度，而不是只换组合方法。

3. 如果任务支持 AbortSignal，我会为同一组任务传入共享控制器的 signal，在捕获首个失败后调用 abort 通知其余任务停止。各任务仍要实际响应 signal；不支持取消的计算或第三方接口不会因此自动中止，已经完成的工作也不会被撤销。

4. 页面层面还要防止取消后仍有旧结果写入状态，可以使用批次版本或有效标记。取消提示与真实业务失败也应区分，保留触发整组失败的原始原因，不让随后产生的多个取消错误把真正要排查的问题覆盖掉。

5. 对已经被正常纳入 Promise.all 的输入，组合器会注册拒绝处理，并不是其他任务稍后失败就必然成为未处理拒绝。调用者仍要处理组合 Promise，任务内部另起且未返回的 Promise 也要单独负责；如果需要完整清理结果，可以再等待这些任务 settled。

## 追问：怎样在一个请求失败后取消同组的其他 fetch？

1. 我会先创建一个控制器，把同一个 signal 传给这一组 fetch，再用 Promise.all 等待。捕获失败时调用控制器的 abort，并继续向上抛出原始错误；这个控制器只负责当前批次，新一轮任务要新建，不能复用已经中止的 signal。

2. fetch 遇到 HTTP 404 或 500 通常仍会返回 Response，所以请求封装要检查 `response.ok`，不满足业务要求时主动抛错。否则 Promise.all 可能把错误响应当成成功，根本不会进入预期的整组失败和取消逻辑。

3. 取消也可能发生在响应头收到之后、响应体读取完成之前，因此读取过程的拒绝仍要处理。若任务还有自定义异步转换，也要检查 signal 或批次有效性；若服务端已完成写入，浏览器取消请求无法把它自动撤销。

## 追问：多个接口必须全部成功，Promise.all 能保证事务吗？

1. 不能，它只能表达客户端“所有输入成功才得到成功结果”，无法约束服务端提交。比如创建订单成功、扣库存失败，Promise.all 会拒绝，但已创建的订单并不会因此自动消失，客户端看到失败不等于系统恢复到操作前状态。

2. 如果业务要求原子性，我会优先通过一个能保证对应事务边界的后端接口完成，而不是前端随意并行多个写接口。跨服务无法直接放在同一事务时，则需要服务端设计状态和补偿规则，不能由前端组合 Promise 代替。

3. 对客户端可做的部分，我会防止重复提交、保存操作标识，并按接口约定查询最终状态或安全重试。哪些操作可重试、是否幂等都要由真实接口约定确认，不能声称加 abort 或重新调用一次就能保证不产生重复副作用。
