# 为什么接口响应不能直接断言成类型？

## 核心回答

1. 接口响应直接断言成某个类型，只改变编译器怎么看它，不会检查真实数据，也不会补字段或转换值。服务端把编号从数字改成字符串，写 `as User` 仍然可能通过编译，但后续运算和展示已经偏离原先假设，错误只是被往后推了。

2. 这类数据属于程序外部输入，可能遇到版本不一致、错误响应或历史缓存，不能因为接口文档写过就认定每次返回都可靠。先以 `unknown` 接住，在进入业务模型前检查需要的结构，让外部变化在比较容易定位的位置被发现。

3. 校验时需要区分解析、结构和业务约束。JSON 能解析并不代表里面存在用户字段。数量字段除了是数字，可能还要求非负整数。这些规则应来自明确约定，不能随意把非法值改成零，否则会把错误数据当成有效结果继续流转。

4. 简单对象可以手写类型守卫，复杂嵌套结构可以考虑运行时校验工具，这是可选实现方案。关键是成功结果必须确实满足后续函数的输入条件，失败时应有清楚的错误路径，不能捕获后统一返回一个被断言成完整类型的空对象。

5. 如果已经由可信的校验步骤建立了保证，只是类型声明没有准确传递，可以在很小的适配范围内考虑断言。把依据和位置讲清楚，并优先修好声明或返回类型，避免同一个不确定假设沿请求层、状态层一直传到每个组件。

## 追问：校验发现字段类型错误，应该自动转换还是拒绝？

1. 先看接口是否明确允许两种表示。编号约定允许数字和数字字符串，就可以在入口统一成内部格式。但不能看见类型不符就无条件转换，因为空字符串转数字可能变成零，原本缺失的信息反而被包装成正常值。

2. 转换后还要验证结果。数量必须是有限的非负整数，仅调用数字转换函数不够。对于不能解释的内容，返回结构错误，让调用方停止依赖该字段的操作，避免在计算或提交环节才出现更隐蔽的异常。

3. 要兼容某个旧接口，把转换限定在对应入口，并保留可定位的错误原因。这是可能的改进方案。页面内部统一使用转换后的模型，可以减少重复兼容，但不应把临时迁就扩散成整个系统都接受模糊输入。

## 追问：校验失败时，怎样避免把错误伪装成空数据？

1. 空列表通常意味着查询成功但没有记录，结构错误则意味着无法理解响应，两者应采用不同结果。缺少列表字段不能直接补成空数组，否则用户可能误以为原有记录已经消失，刷新或重试也看不出真实原因。

2. 让调用方区分成功、业务失败和数据格式异常，再决定展示空状态、提示重试还是中止后续操作。错误信息要能帮助定位字段问题，但页面提示不需要原样暴露整个响应，更不能为了排查方便记录所有个人信息。

3. 对必须依赖有效数据的提交步骤，应在校验失败时停止，不能带着默认编号继续请求。如果只是非关键展示字段，允许降级也要有明确规则，例如显示缺省说明，同时保留格式异常的处理路径，而不是吞掉所有错误。
