# 接口数据能只靠 TypeScript 类型保证吗？

## 核心回答

1. 接口数据不能只靠 TypeScript 类型保证，因为类型注解和接口声明在运行时不会替代码检查响应内容。把返回值声明成用户对象，服务端仍可能返回错误结构或者缺少昵称，浏览器不会因此自动拒收这些数据。

2. 先把外部结果当成未知值，在接口进入业务代码的地方检查结构。页面需要编号和名称，就先确认对象非空，再检查编号和名称的实际类型。里面还有列表，还要验证元素，不能只确认外层是数组就结束。

3. 结构正确也不一定符合业务要求。数量是数字，但可能为负数或超出允许范围。具体限制应该来自接口约定，不能凭个人感觉追加条件。可选说明缺失可以接受，提交所需的资源编号缺失则应明确中止对应流程。

4. 检查通过后，把结果交给有明确参数类型的业务函数，让内部代码使用稳定结构。检查失败，应返回可区分的错误信息或进入错误页面，而不是用空对象顶替所有情况，否则调用方无法区分没有数据和响应损坏。

5. 对简单结构可以手写守卫，复杂结构可以评估运行时校验工具，但这属于实现选择，不能说项目已经接入。无论采用哪一种，都需要覆盖缺字段、错误类型和合法空列表等情况，确保校验规则真的符合接口，不是只让正常样例通过。

## 追问：HTTP 成功和 JSON 解析成功为什么还不够？

1. HTTP 成功只说明请求在协议层获得了成功响应，不能直接证明业务操作成功。接口可能在响应体里用业务码表达失败，调用方仍需要按接口约定分辨，不是收到成功状态就跳转到完成页面。

2. JSON 解析成功证明文本符合 JSON 语法，并不证明它是目标对象。合法的空值、数组或字符串都可能解析成功。解析之后还要检查业务结构，避免把「可以解析」和「可以访问用户名称」当成同一个条件。

3. 处理时可以区分网络失败、解析失败、结构不符和业务拒绝，让页面采取相应反馈。权限失效与确实没有记录不应共用空列表兜底，否则用户以为数据被清空，排查时也容易把真正原因看漏。

## 追问：接口新增字段或缺少可选字段时，校验要直接拒绝吗？

1. 依据兼容约定决定是否允许额外字段。普通查询接口增加一个页面不用的字段，通常没必要让旧客户端全部失败。某个场景要求字段集合严格固定，就应明确约定并测试，不能靠校验工具默认行为碰运气。

2. 对可选字段，缺失与存在但类型错误需要分开处理。备注没返回可以接受，返回成数组则不符合声明。约定还允许空值，就把空值写入规则，不要把所有异常输入都悄悄转成空字符串来掩盖变化。

3. 要兼容旧版本字段，在入口做明确转换，并让转换后的内部模型保持一致。这样组件不必反复判断两套名称。这种兼容应有依据和结束条件，不能永久接受任何结构，最后失去校验的意义。
