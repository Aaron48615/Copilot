# 什么时候可以用 data-testid？

## 核心回答

1. 需要稳定测试标识、用户可见信息又不适合唯一定位时，用 `data-testid`。比如文案经常换的图表区域。它是显式约定的定位接口，不必一概看成不推荐。但它替不了元素本来该有的可访问名称。

2. 普通按钮和表单还是优先按角色、名称、标签定位，用户找不到控件的问题也能暴露出来。只有图标的删除按钮没有名称，就先补合理的可访问名称。加个测试标识让测试通过，这件事本身没做完。

3. 标识名表达稳定业务含义，比如 `order-summary`，别写成第三个 div 或某个样式类名。布局调整之后，测试还能找到同一块业务区域。标识被删掉或重复用，照样会失败，所以它也要维护。

4. 列表里多个同名操作，先按记录名称或稳定业务标识限定到一行，再在行内找按钮。别对所有「编辑」按钮取第一个，排序一变就可能编到另一条。脚本通过，也不等于目标操作是对的。

5. 定位成功之后还要断言实际行为：目标记录是不是真进了编辑，新值是不是存上了。`data-testid` 只说明找到了约定元素，能不能被键盘操作、文案对不对、读屏能不能理解，这些还要另外验。

## 追问：列表中每一行都叫“删除”，应该怎么定位？

1. 先找到目标记录的容器，再在里面定位删除按钮。比如按行角色和唯一订单号缩小范围。订单号必须来自本条测试准备的数据，别假设环境里第一行永远是同一笔订单，并行造数就会把结果改掉。

2. 行内文字不唯一，可以给行设一个由稳定记录标识构成的测试标识，再用行内的按钮角色去点。测试标识只解决定位歧义。个人敏感信息、临时数组下标当不了稳定身份，页面本身的按钮语义也别丢掉。

3. 点完确认弹窗指向的是目标记录，操作完成后再查这一行消失、其他行还在。定位匹配到多个元素报错，就补足范围。直接追加 `first` 能消掉错误，却可能把真正的数据问题或定位问题藏起来。

## 追问：文案会做多语言切换，还适合按文字定位吗？

1. 可以，但先明确这条测试验什么。验的是中文登录流程，就固定语言，按中文可访问名称操作。一条业务测试要覆盖多种语言，就随语言提供对应名称，或者对稳定业务容器用测试标识，少受无关文案变动影响。

2. 别把所有文字断言都换成测试标识。翻译缺失、占位符泄露，用户也能看见。主要行为用稳定定位完成，再针对每种语言留关键标题、错误信息、控件名称的检查，各自保护什么说清楚。

3. 浏览器语言、账号语言、本地存储都要控住。测试以为是中文环境，页面却沿用了上次存的英文设置。项目没有明确多语言需求，没必要提前做复杂的语言映射。先覆盖实际支持的界面。
