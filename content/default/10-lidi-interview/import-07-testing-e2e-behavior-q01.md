# 什么时候可以用 data-testid？

## 核心回答

1. 我会在需要稳定测试标识、而用户可见信息不适合唯一定位时使用 data-testid，例如文案经常切换的图表区域。它是显式约定的定位接口，不必一概看成不推荐的写法，但也不能代替元素本来应该具备的可访问名称。

2. 普通按钮和表单仍优先按角色、名称或标签定位，因为这也能暴露用户找不到控件的问题。比如一个只有图标的删除按钮，如果没有名称，我会先补合理的可访问名称，而不是加个测试标识让测试通过就算完成。

3. 标识名应表达稳定业务含义，例如 order-summary，不写第三个 div 或某个样式类名。这样布局调整后测试仍能找到同一块业务区域；不过标识被删掉或重复使用时仍可能失败，所以它同样需要维护。

4. 列表里多个同名操作，我会先根据记录名称或稳定业务标识限定到一行，再在行内找按钮。不能直接对所有“编辑”按钮取第一个，否则排序一变就可能编辑另一条记录，脚本通过也没有证明目标操作正确。

5. 定位成功之后还要断言实际行为，比如目标记录真的进入编辑状态或保存了新值。data-testid 只能说明找到了约定元素，不能证明它能被键盘操作、文案正确或者屏幕阅读器能够理解，这些要求需要另外验证。

## 追问：列表中每一行都叫“删除”，应该怎么定位？

1. 我会先找到目标记录的容器，再在其中定位删除按钮，例如按行角色和唯一订单号缩小范围。这里订单号必须来自本条测试准备的数据，不能假设测试环境中第一行一直是同一笔订单，否则并行造数就会改变结果。

2. 如果行内文字不唯一，可以给行设置由稳定记录标识构成的测试标识，再用行内的按钮角色完成操作。测试标识只解决定位歧义，不应该把个人敏感信息或临时数组下标当成稳定身份，更不能忽略页面本身的按钮语义。

3. 点击后我会确认弹窗指向目标记录，完成操作再检查这一行消失、其他行仍在。如果定位匹配多个元素而报错，我会补足范围；直接追加 first 虽然能消除错误，却可能把真正的数据或定位问题隐藏起来。

## 追问：文案会做多语言切换，还适合按文字定位吗？

1. 可以，但要先明确这条测试验证什么。若验证的是中文登录流程，就固定语言并按中文可访问名称操作；如果一条业务测试要覆盖多个语言，随语言提供对应名称，或对稳定业务容器使用测试标识，减少无关文案变动。

2. 我不会把所有文字断言都换成测试标识，因为翻译缺失、占位符泄露也是用户能看到的问题。可以让主要行为用稳定定位完成，再针对每个语言保留关键标题、错误信息和控件名称的检查，分别说明各自保护的要求。

3. 还要控制浏览器语言、账号语言和本地存储，避免测试以为是中文环境，页面却沿用了上次保存的英文设置。若项目没有明确多语言需求，就没有必要提前设计复杂的语言映射工具，先覆盖实际支持的界面即可。
