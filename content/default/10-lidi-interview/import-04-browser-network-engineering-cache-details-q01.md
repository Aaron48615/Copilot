# 为什么带 hash 的 JS 可以长缓存？

## 核心回答

1. 带内容 hash 的 JS 可以长缓存，核心是内容变化会生成新的 URL。例如业务代码由 app.abc.js 变成 app.def.js，新 HTML 引用新地址，浏览器把它当成另一个资源，不必先删除本地的旧文件才能更新。

2. 这里必须是与实际内容关联的版本标识，并保证同一个 URL 对应的内容不被覆盖。可以给这类静态资源设置较长 max-age 并配合 immutable，减少新鲜期内不必要的验证；随手给固定文件名加一个永不改变的 hash 没有这个效果。

3. HTML 是找到新文件的入口，一般要及时验证或使用适合业务的短缓存。否则浏览器一直使用旧 HTML，仍然只认识旧 JS，即使新文件已经上传也不会主动猜出地址；CDN、浏览器和 Service Worker 的策略需要一起检查。

4. 发布时我会先让新资源可用，再切换 HTML，并保留一定时间的旧资源。停留在旧页面的用户可能稍后才触发动态导入，过早删除旧 chunk 会出现加载失败；长缓存解决的是资源复用，不自动解决旧页面的兼容问题。

5. 我还会检查页面实际引用的路径，确保构建生成的 hash 与部署清单一致。资源上传漏文件时，即使 HTML 及时更新也会白屏；回滚时同样要恢复一组彼此匹配的入口与资源，而不是只替换某一个脚本。

## 追问：文件名带 hash，为什么每次构建 vendor 文件也变？

1. 先确认业务构建里用的是内容相关 hash，而不是把整个构建版本统一写进所有文件名。若所有文件都跟随一次发布变化，即使库代码没变，浏览器也会重新下载，长期缓存的收益就变小了。

2. 再比较实际产物，模块标识、运行时代码、依赖图变化或生成顺序都可能影响 vendor 内容。把运行时和稳定依赖合理拆开有时有帮助，但不能只凭文件名推断是浏览器缓存失效，需要确认内容为什么变化。

3. 我会使用同样的锁文件和构建环境重复构建，再只修改一处业务代码观察差异。这样可以区分构建不稳定与合理的依赖变化，不会为了固定 hash 而错误复用本应更新的文件。

## 追问：能不能发布后立即删除全部旧资源？

1. 我不会立即删除，因为在线用户可能还持有旧入口和旧模块图。比如他打开页面后过一段时间再进入报表页，此时需要旧版本的懒加载文件，服务端已删除它就会返回 404，即使新版本本身完全正常。

2. 比较稳妥的是保留若干版本或一定时间窗口，并结合访问日志与部署容量确定清理策略。回滚也依赖旧文件仍然存在，所以资源清理应与版本保留规则一起设计，而不是每次发布先清空目录。

3. 页面可以在 chunk 加载失败时提示刷新，但要防止无限重试，并保护未提交表单。刷新只是让用户重新获取入口，不能代替服务端合理保留资源，更不能承诺所有旧页面都能无感切换。
