# 为什么带 hash 的 JS 可以长缓存？

## 核心回答

1. 带内容 hash 的 JS 可以长缓存，核心是内容一变就会生成新 URL。比如业务代码从 `app.abc.js` 变成 `app.def.js`，新 HTML 引用新地址，浏览器把它当成另一个资源，不必先删本地旧文件才能更新。

2. 这个标识必须跟实际内容挂钩，同一个 URL 对应的内容也不能被覆盖。这类静态资源可以设比较长的 `max-age`，再配上 `immutable`，新鲜期内少做没必要的验证。给固定文件名随手加一个永不改变的 hash，没有这个效果。

3. HTML 是找到新文件的入口，一般要及时验证，或者用适合业务的短缓存。否则浏览器一直用旧 HTML，还只认识旧 JS，新文件就算已经上传，它也不会自己猜出地址。CDN、浏览器和 Service Worker 的策略要一起查。

4. 发布时先让新资源可用，再切 HTML，旧资源再留一段时间。停留在旧页面的用户，可能过一会儿才触发动态导入，旧 chunk 删太早就加载失败。长缓存解决的是资源复用，旧页面兼不兼容是另一回事。

5. 还要核对页面实际引用的路径，构建生成的 hash 和部署清单得一致。资源上传漏文件时，HTML 及时更新也会白屏。回滚时同样要恢复一组彼此匹配的入口和资源，只替换某一个脚本不够。

## 追问：文件名带 hash，为什么每次构建 vendor 文件也变？

1. 先确认业务构建用的是内容相关 hash，不是把整次构建版本统一写进所有文件名。所有文件都跟着一次发布变，库代码没动，浏览器也会重新下，长期缓存的收益就变小了。

2. 再比较实际产物。模块标识、运行时代码、依赖图变化、生成顺序，都可能改到 vendor 内容。把运行时和稳定依赖合理拆开，有时有帮助。不能只凭文件名断定是浏览器缓存失效，得确认内容为什么变。

3. 用同样的锁文件和构建环境重复构建，再只改一处业务代码看差异。这样能分清是构建不稳定，还是依赖本来就该变。别为了 hash 固定，错误复用本该更新的文件。

## 追问：能不能发布后立即删除全部旧资源？

1. 不要马上删。在线用户可能还拿着旧入口和旧模块图。比如他打开页面后过一段时间再进报表页，这时需要旧版本的懒加载文件，服务端已经删了就会 404，新版本本身完全正常也没用。

2. 比较稳妥的是保留若干版本，或者留一个时间窗口，再结合访问日志和部署容量定清理策略。回滚也依赖旧文件还在，资源清理要和版本保留规则一起设计，每次发布先清空目录不行。

3. 页面可以在 chunk 加载失败时提示刷新，但要防止无限重试，也要保护没提交的表单。刷新只是让用户重新拿入口，代替不了服务端合理留资源，更不能承诺所有旧页面都能无感切过去。
