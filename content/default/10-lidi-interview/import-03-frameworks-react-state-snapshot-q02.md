# 怎么在更新后做事？

## 核心回答

1. “更新后做事”要先区分究竟等待什么。如果只是拿下一状态作为参数，直接在事件里算出 nextValue，用它同时更新 state 和执行后续动作即可；没有必要等 React 再渲染一次，只为了重新读回自己刚算出的值。

2. 若要在界面提交后和外部系统同步，可以使用依赖该状态的 Effect。例如选中项改变后通知图表突出显示，Effect 能使用本次已提交渲染对应的状态，并在变化时重新同步，但不应该替代明确的点击提交事件。

3. 需要读取新 DOM 并在绘制前调整布局时，考虑 useLayoutEffect。比如弹出提示框后测量高度再定位；普通请求不需要阻止绘制，不能只为了“更早执行”就把所有副作用都放到布局 Effect 中。

4. useState 的 setter 不返回等待提交完成的 Promise，所以 await setState 并不能提供可靠的更新后时机。setTimeout 也只是排到以后执行，不能表达对某次 React 提交的准确依赖，尤其不适合作为修复状态旧值的固定套路。

5. 我会把“更新数据”和“观察提交结果”分开设计，并防止 Effect 反过来无条件更新其依赖。例如监听 count 后再次增加 count 会循环；一次性提交动作尽量留在事件中，真正随状态变化的外部同步才交给 Effect。

## 追问：提交前先 setForm，再读取 form 发请求为什么可能还是旧值？

1. setter 没有修改当前事件函数捕获的 form，这次事件继续读取的还是原快照。即使界面很快更新，原函数里的变量也不会自动替换，所以请求可能带上修改前的字段，问题与网络快慢无关。

2. 可以在事件中生成 nextForm，并把它分别传给 setter 和请求函数。这样本次提交的数据明确，后续用户继续编辑也不会偷偷改变已经发出的参数；需要基于最新草稿时则应从正确的状态归属处发起操作。

3. 不建议为了绕开旧值加一个“待提交”状态，再由 Effect 监听 form 自动请求。这样重挂载、重复更新或其他编辑也可能触发提交，业务动作变得隐含；点击处理器直接表达提交通常更容易控制。

## 追问：打开弹窗后立刻 focus，为什么有时找不到输入框？

1. 如果输入框由 open 条件决定是否渲染，调用 setOpen 后当前时刻的 DOM 可能还没有新节点，ref.current 因此为空。状态更新请求已经发出，并不表示条件子树已经完成挂载，这两个时机需要区分。

2. 可以在弹窗组件挂载后通过 ref 聚焦，或在合适的 Effect 中根据 open 处理。若组件库提供打开完成回调，要考虑它的动画和焦点管理，使用该接口通常比在外面随意加固定延时更稳妥。

3. 聚焦前还需检查节点可见、未禁用，并尊重弹窗自身的无障碍逻辑。关闭时通常应恢复触发按钮焦点，测试需要覆盖键盘打开和快速开关，不能只确认鼠标点击一次时偶尔能成功聚焦。
