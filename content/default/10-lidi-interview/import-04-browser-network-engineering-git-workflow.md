# Git 是怎么用的？说说分支和提交规范

## 核心回答

1. 先看当前分支、远端和还没提交的修改，确认自己在正确的任务分支上。功能或修复单独开分支，主分支保持能用。多人协作时，不属于当前任务的修改尤其不能覆盖，也不能顺手带走。

2. 开发中按一个清楚的主题组织提交，提交前检查工作区和暂存区差异。提交信息可以用 feat、fix、docs 这些前缀，重点是说明实际变化。比如修复登录回跳丢失查询参数，比只写「更新代码」好追得多。

3. 同步之前先拿远端变化，再按团队约定 merge 或 rebase。自己还没共享的提交可以适当整理，共享分支的历史不随意改写。冲突要结合双方意图解决，再重新验证，不能只把冲突标记删掉。

4. 做完后跑跟改动匹配的检查，再走评审合进目标分支。Fork 场景还要分清 origin 和 upstream 的角色。提交、推送、创建 PR 都按项目授权执行。本地写完，不等于可以直接往远端发。

5. 出问题时，已经共享的提交通常用 revert，把历史留着再撤销。本地 reset 这类操作，要理解它对暂存区和工作区的影响，别随便用会丢掉修改的模式。比起强调提交数量，更关心每次改动是不是容易理解、验证和恢复。

## 追问：一次修改涉及功能和重构，应该怎么拆提交？

1. 如果两者可以独立成立，先把不改变行为的重构作为一项，再加功能。评审就能分别看结构变化和业务变化。前提是每个提交都能构建，并且状态合理。别为了拆分制造一串跑不起来的中间版本。

2. 如果功能必须依赖很小的结构调整，也可以放在一个说清楚原因的提交里。拆分是为了帮助理解和恢复，不是机械限制改动行数。同一工作区里别人的修改，必须保持独立。

3. 提交前用暂存差异确认边界，必要时按片段暂存，并跑相关验证。尤其注意配置、类型和调用方有没有一起进提交。否则本地因为还有未暂存修改而正常，别人检出后却会失败。

## 追问：误把密钥加入提交，删除文件再提交就够了吗？

1. 不够。旧提交里可能仍然保存着密钥。如果已经推送，或者被别人拿到，应先按凭据管理流程撤销或轮换。把文件藏起来、加上 gitignore，不能让已经暴露的凭据重新变安全。

2. 接着确认密钥出现在哪些提交、日志或构建产物里，并跟仓库维护者协调怎么清理。重写共享历史会影响其他协作者，需要明确授权和同步方案。自己立刻强推来抹掉表面记录，不行。

3. 后续把真实凭据挪到受控的服务端配置里，仓库只留没有秘密的示例，提交前检查敏感内容。验证时也别再把密钥打出来。报告时说明类型和处理状态就行，原值不要复制到工单。
