# Git 是怎么用的？说说分支和提交规范

## 核心回答

1. 我会先检查当前分支、远端和未提交修改，确认正在正确的任务分支上工作。功能或修复单独开分支，主分支保持可用；多人协作时尤其不能把不属于当前任务的修改覆盖或顺手带走。

2. 开发中按一个清晰主题组织提交，提交前检查工作区与暂存区差异。提交信息可以使用 feat、fix、docs 等前缀，但重点是说明实际变化，例如修复登录回跳丢失查询参数，比只写更新代码更容易追踪。

3. 同步之前先获取远端变化，再按团队约定 merge 或 rebase。自己的未共享提交可以适当整理，共享分支的历史不随意改写；冲突需要结合双方意图解决，并重新验证，而不是只删除冲突标记。

4. 完成后运行与改动匹配的检查，再通过评审流程合入目标分支。Fork 场景还要明确 origin 与 upstream 的角色，提交、推送和创建 PR 都按项目授权执行，不能认为本地写完就代表可以直接向远端发布。

5. 出问题时，已经共享的提交通常用 revert 保留历史地撤销。本地 reset 等操作也要理解它对暂存区和工作区的影响，不随意使用会丢弃修改的模式；比起强调提交数量，我更关心每次改动是否容易理解、验证和恢复。

## 追问：一次修改涉及功能和重构，应该怎么拆提交？

1. 如果两者可以独立成立，我会先把不改变行为的重构作为一项，再增加功能，这样评审能分别看结构变化和业务变化。前提是每个提交都能构建并保持合理状态，不能为了拆分制造一串不可运行的中间版本。

2. 如果功能必须依赖很小的结构调整，也可以放在一个明确的提交里，把原因说明清楚。拆分目标是帮助理解和恢复，不是机械限制改动行数；同一工作区中其他人的修改则必须保持独立。

3. 提交前使用暂存差异确认边界，必要时按片段暂存，并运行相关验证。尤其注意配置、类型和调用方是否一起进入了提交，否则本地因为存在未暂存修改而正常，别人检出后却会失败。

## 追问：误把密钥加入提交，删除文件再提交就够了吗？

1. 不够，因为旧提交里可能仍然保存密钥。如果已经推送或被他人获取，就应首先按凭据管理流程撤销或轮换，不能把隐藏文件或增加 gitignore 当成让已暴露凭据重新安全的方法。

2. 接着确认密钥出现在哪些提交、日志或构建产物中，并与仓库维护者协调清理方式。重写共享历史会影响其他协作者，需要明确授权和同步方案，不能自己立即强推来抹掉表面记录。

3. 后续把真实凭据移到受控的服务端配置中，仓库只保留没有秘密的示例，并在提交前检查敏感内容。验证也应避免再次打印密钥，报告时说明类型和处理状态即可，不把原值复制到工单。
