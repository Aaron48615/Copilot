# CSS 动画卡顿时怎么排查？

## 核心回答

1. 我会先复现具体卡顿动作，例如打开侧栏或滚动时播放卡片动画，再录制 Performance，而不是看到动画卡就认定 CSS 写得不好。卡顿可能来自脚本长任务、反复布局、大面积绘制或图片处理，需要先知道浏览器时间花在哪里。

2. 然后检查动画修改的属性。transform 和 opacity 通常更有机会只由合成阶段处理，连续改 width、height、top 等则可能引起布局和绘制。比如侧栏滑入可以尝试平移，但如果需求是让旁边正文跟着缩窄，单纯平移并不能替代真实布局变化。

3. 如果记录中反复出现布局，我会检查是否一边改样式一边读取几何信息；如果绘制很重，就看大阴影、滤镜和覆盖面积。一次只移除或替换一个可疑效果，再对比同样的操作，才能判断改善来自哪里，不把偶然流畅当成结论。

4. 最后才考虑有针对性地使用 will-change，而且只在确实需要的元素和阶段使用，不能给整页长期加层。还要提供减少动态效果的方案，在真实目标设备上检查结果；没有采集前后的记录，我不会把“用了 transform”表述成已经完成性能优化。

5. 减少动态效果时，我会保留状态变化本身，例如直接显示已展开的面板，并取消非必要的大幅移动。不能把动画关闭后连加载状态或成功反馈也一起删除，否则性能更轻了，用户却不清楚操作有没有完成。

## 追问：为什么不能给所有动画元素都加 will-change？

1. 它只是提前告知浏览器可能发生的变化，浏览器是否建立合成层仍由实现决定。提前准备可能占用内存和其他资源，尤其很多大图片同时参与时，资源成本可能超过动画开始时节省的工作。

2. 我会先从性能记录中确认某个动画的准备阶段确实有明显停顿，再对该元素试用。需要时在动画开始前提前设置，交互结束后移除，避免无关或不可见的组件长期保留提示。

3. 验证不能只看帧率，还要观察页面整体和重复操作后的资源变化。如果第一次变顺但滚动其他区域更差，就说明代价被转移了；这时应减少动画范围或复杂效果，而不是继续增加 will-change。

## 追问：读写 DOM 交错为什么容易让动画变慢？

1. 修改会影响布局的样式后，再读取 offsetWidth 或位置，浏览器可能必须先完成待处理的布局才能给出准确值。循环中每个节点都这样读一次、写一次，就可能把原本能合并的计算拆成多次。

2. 我会先集中读取本轮需要的尺寸和位置，再集中更新样式。比如列表动画先收集所有初始位置，再统一添加目标状态，避免处理每张卡片时都立即测量下一张，这样更有机会减少强制同步布局。

3. requestAnimationFrame 可以安排更新时机，但不能消除错误的读写顺序。修改后仍要检查记录里布局次数和耗时是否减少，若布局本身涉及巨大列表，还需要缩小参与范围，而不是只把原循环包进回调。
