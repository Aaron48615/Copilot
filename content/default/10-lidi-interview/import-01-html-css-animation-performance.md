# CSS 动画卡顿时怎么排查？

## 核心回答

1. 先复现具体哪一下卡，比如打开侧栏、滚动时卡片在动，再录 Performance。看见动画卡就认定 CSS 写得差，常常不准。卡顿可能来自脚本长任务、反复布局、大面积绘制、图片处理，得先知道浏览器时间花在哪。

2. 再看动画改的是哪些属性。`transform` 和 `opacity` 更有机会只走合成；连续改 `width`、`height`、`top` 则可能带动布局和绘制。侧栏滑进来可以试平移，但旁边正文要跟着变窄，光平移替代不了真实布局变化。

3. 记录里反复出现布局，就看是不是一边改样式一边读几何信息。绘制很重，就看大阴影、滤镜、覆盖面积。一次只拿掉或换掉一个可疑效果，同样操作再对比，才知道改善从哪来。偶然流畅一次，当不了结论。

4. 最后才针对性用 `will-change`，而且只给确实需要的元素、确实需要的那一段时间，别给整页长期加层。还要提供减少动效的方案，在真实目标设备上看结果。没有前后记录，别把「用了 transform」说成性能已经优化完。

5. 减少动效时，状态变化本身还在，比如面板直接显示已展开，大幅移动可以取消。别连加载状态、成功反馈一起删掉，页面是轻了，人却不知道操作做没做完。

## 追问：为什么不能给所有动画元素都加 will-change？

1. 它只是提前告诉浏览器可能要变，建不建合成层还是浏览器自己定。提前准备会占内存和别的资源，很多大图同时参与时，这笔成本可能比动画开始时省下的还多。

2. 先从性能记录里确认某个动画的准备阶段确实有明显停顿，再给那个元素试。需要就在动画开始前设上，交互结束拿掉，别让看不见、不相干的组件长期留着这个提示。

3. 验证别只看帧率，还要看整页、重复操作之后资源有没有变差。第一次顺了，滚别的区域更卡，说明代价被挪走了。这时该缩小动画范围或减弱效果，别继续堆 `will-change`。

## 追问：读写 DOM 交错为什么容易让动画变慢？

1. 改了会影响布局的样式，紧接着读 `offsetWidth` 或位置，浏览器可能必须先把待处理的布局算完才能给准数。循环里每个节点读一次写一次，本来能合并的计算就被拆成很多次。

2. 本轮需要的尺寸、位置先集中读，样式再集中改。列表动画可以先收齐所有初始位置，再统一加上目标状态，别处理一张卡片就立刻去量下一张，强制同步布局会少很多。

3. `requestAnimationFrame` 能把更新安排到合适时机，但读写顺序错了它救不了。改完还得看记录里布局次数和耗时有没有降。布局本身卷进巨大列表，还得缩小参与范围，把原来的循环原样塞进回调不够。
