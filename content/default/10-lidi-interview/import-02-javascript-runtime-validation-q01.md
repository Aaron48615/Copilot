# 哪些数据值得完整校验？

## 核心回答

1. 优先完整校验那些一旦出错就会影响操作结果、权限判断或金额展示的数据，不是给所有字段平均用力。订单编号缺失可能让按钮操作到错误对象，商品说明少一个可选段落通常只影响展示，两者处理强度应不同。

2. 这里的完整，是把接口约定涉及的结构和约束检查清楚，包括必填字段、数组元素、枚举取值以及必要的范围。只验证金额是数字还不够，还要确认有限性、单位和允许范围，否则负数或异常数值仍可能进入后续计算。

3. 外部来源也会影响优先级。接口响应、地址参数、上传文件和浏览器缓存，都不能因为已有类型声明就直接相信。缓存尤其可能由旧版本写入，所以要检查版本和内容，不能把成功解析成对象当成内容已经正确。

4. 普通展示数据可以按风险降级，比如头像地址无效就用占位图，但必要的标识和列表结构仍应验证。默认值应有清楚的业务含义。价格缺失不能默认为零，否则页面看似恢复了，实际却传达了错误的购买信息。

5. 前端检查主要帮助发现约定变化并保护交互。真正的授权、订单价格和支付规则，仍必须由服务端独立校验。落地时先梳理关键操作依赖哪些字段，再补充异常样例。前端校验建不起安全边界。

## 追问：金额字段为什么不能只检查是不是数字？

1. 数字类型里仍可能出现非有限值，接口也可能把以分计价的整数换成以元计价的小数。前端仍按旧单位除以一百，类型检查会全部通过，但展示结果已经错了。金额约定必须同时说明单位和精度。

2. 按约定检查范围与精度。使用最小货币单位整数，还要考虑是否超出安全整数范围。字符串形式的大额金额，应按明确格式解析，不能为了通过校验直接随意转换。空字符串转成零，就可能把数据问题盖住。

3. 前端可以核对用于展示和提交的格式，但最终应付金额要由服务端根据商品、优惠和订单状态重新计算。关键金额校验失败，应阻止继续支付并展示异常，不要补一个默认金额让用户继续操作。

## 追问：一百条列表中一条数据异常，要整页失败吗？

1. 先看这张列表的用途。只是资讯浏览，隔离一条损坏记录可能比整页失败更合适。页面应保留有效条目，并在需要时说明部分内容不可用，避免用户把不完整结果误当成全部数据都已展示。

2. 列表用于对账、总额汇总或批量操作，丢掉一条就可能改变结论，这时不能悄悄过滤。把本次结果标为不完整，停止依赖完整数据的计算或提交，让用户能明确区分数据为空和数据没有通过检查。

3. 实现时可以分别检查外层结构与单条记录，记下失败位置和原因，再按接口约定决定是否局部降级。分页总数也要谨慎处理，不能把过滤后的数量直接当作服务端总数，否则翻页和全选行为都会变得含糊。
