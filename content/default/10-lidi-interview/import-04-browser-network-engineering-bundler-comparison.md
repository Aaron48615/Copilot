# Webpack 和 gulp、Rollup 这类工具有什么区别？

## 核心回答

1. 我会先按职责区分：gulp 更像任务编排工具，把压缩图片、编译样式和复制文件组织成任务；Webpack、Rollup 则主要从模块依赖关系出发，分析入口用到了什么，再生成可部署的产物，两类工具也可以配合使用。

2. Webpack 的模块体系和插件机制比较完整，能处理脚本、样式及各种资源，适合需要较多构建定制的应用。代价是复杂项目的配置和排查成本较高，不过缓存、按需编译等能力也在发展，不能简单认为它一定很慢。

3. Rollup 同样分析依赖图，比较重视模块输出和静态分析，常用于库构建。它可以借助插件处理 CommonJS 等格式，不是只能使用 ESM；tree-shaking 效果还受副作用和依赖写法影响，也不能保证任何库都能被删得很干净。

4. Vite 提供开发服务器和生产构建的组合，应用开发体验通常更直接。旧版常见 esbuild 加 Rollup，Vite 8 改用 Rolldown 统一打包并结合 Oxc 编译，所以选型时我会核对项目版本、插件兼容及部署目标，再比较维护成本，而不是只背一张固定工具排名。

5. 实际比较时，我会选包含样式、图片和懒加载的一小段业务，分别验证开发更新与最终部署。只有冷启动快但发布后资源路径错误的方案并不合适；测试同时覆盖可维护性和功能，才能避免只依据工具宣传作选择。

## 追问：只需要压缩一批图片，还要引入完整打包器吗？

1. 不一定，因为这类任务不必分析 JavaScript 模块依赖。少量文件可以用现有脚本调用图片工具，若还有监听、复制和串并行任务，再考虑 gulp；选择依据是流程复杂度，而不是工具听起来是否更新。

2. 我会明确输入、输出和失败处理，例如原图放一个目录，处理结果放另一个目录，并在某张图片处理失败时返回失败状态。这样可以避免不小心覆盖原文件，也方便把任务放进持续集成执行。

3. 还要验证视觉质量和文件格式，文件越小并不总是越合适。如果项目本来已有图像处理能力，优先复用已有工具，额外增加一套任务系统会带来依赖和维护成本，不应为一次简单操作引入复杂配置。

## 追问：做组件库为什么常考虑 Rollup？

1. 组件库更关注导出结构、外部依赖和不同消费方式，Rollup 提供的模块输出能力比较适合这些需求。例如保留 ESM 便于使用方分析未使用导出，同时把 React 等宿主依赖声明为外部依赖，避免重复打包。

2. 不过工具本身不会替我设计包接口。我仍要配置 exports、类型声明和样式入口，并确认具有初始化行为的文件没有被错误标成无副作用；否则构建成功，使用方仍可能遇到无法导入或样式丢失。

3. 选择前我会做一个小消费示例，验证常见的 import 方式和生产构建结果。若团队已有稳定的其他库构建流程，也没有必要只因为某工具常用于库就迁移，迁移收益需要超过配置和兼容验证的成本。
