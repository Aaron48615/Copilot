# Webpack 和 gulp、Rollup 这类工具有什么区别？

## 核心回答

1. 职责不一样。gulp 更像任务编排，把压缩图片、编译样式、复制文件排成任务。Webpack、Rollup 主要从模块依赖出发，看入口用到了什么，再生成能部署的产物。两类工具也可以一起用。

2. Webpack 的模块体系和插件比较完整，脚本、样式、各种资源都能处理，适合构建定制比较多的应用。代价是复杂项目的配置和排查会重一些。缓存、按需编译这些能力也在发展，不等于它一定很慢。

3. Rollup 同样分析依赖图，比较看重模块输出和静态分析，库构建里常见。它可以靠插件处理 CommonJS 等格式，不是只能用 ESM。tree-shaking 还受副作用和依赖写法影响，不能保证任何库都能删得很干净。

4. Vite 把开发服务器和生产构建放在一起，应用开发体验通常更直接。旧版常见 esbuild 加 Rollup，Vite 8 改用 Rolldown 统一打包，再配合 Oxc 编译。选型要核对本项目版本、插件兼容和部署目标，再比维护成本，别只背一张固定工具排名。

5. 实际比较时，拿一段带样式、图片和懒加载的小业务，分别验证开发更新和最终部署。冷启动很快、发布后资源路径却错了，这种方案不行。可维护性和功能都要测，不能只听工具宣传。

## 追问：只需要压缩一批图片，还要引入完整打包器吗？

1. 不一定。这类任务不必分析 JavaScript 模块依赖。文件不多，现有脚本调图片工具就行；还要监听、复制、串并行任务，再考虑 gulp。看的是流程复杂不复杂，不是工具听起来新不新。

2. 输入、输出和失败处理要说清楚。比如原图一个目录，处理结果另一个目录，某张图失败就让任务失败。这样不容易盖掉原文件，也方便丢进持续集成。

3. 视觉质量和文件格式也要验，文件越小不总是越好。项目里本来就有图像处理能力，优先复用。额外再加一套任务系统会带来依赖和维护成本，一次简单操作不必上复杂配置。

## 追问：做组件库为什么常考虑 Rollup？

1. 组件库更关心导出结构、外部依赖、别人怎么消费。Rollup 的模块输出能力比较对得上这些需求。比如保留 ESM，方便使用方分析没用到的导出；React 这类宿主依赖声明成外部依赖，避免打进去一份重复的。

2. 工具本身不会替你设计包接口。`exports`、类型声明、样式入口还是要自己配，有初始化行为的文件也不能错误标成无副作用。否则构建成功，使用方仍可能导不进来，或者样式丢了。

3. 选之前做一个小的消费示例，验证常见的 `import` 方式和生产构建结果。团队已经有稳定的其他库构建流程，没必要因为某工具常用于库就迁过去。迁移收益得超过配置和兼容验证的成本。
