# Redux Toolkit 解决了什么问题？

## 核心回答

1. Redux Toolkit 主要解决传统 Redux 配置和样板代码较多的问题。`configureStore` 提供常用配置，`createSlice` 把一类状态的初始值、reducer 和生成的 action 放在一起，更容易看清一次状态更新对应什么行为。调试时也能沿着 action 找到状态变化的来源，检查是否由预期的用户操作触发。

2. slice 的 reducer 可以写出像 `state.count += 1` 这样的代码，是因为内部通过 Immer 处理草稿并生成不可变结果。它不代表 Redux 允许在任意地方直接改 store，组件仍然应该通过 dispatch 描述更新。

3. 城市视图的登录信息和角色属于跨页面会使用的状态，可以放在共享状态中管理。页面上只用一次的输入框、弹窗开关则不一定需要进 store，否则简单交互也要跨文件寻找更新逻辑。

4. 异步请求可以用 createAsyncThunk 表达执行过程，但它不会自动替我完成所有缓存策略。RTK Query 更侧重服务端数据获取和缓存，是否采用要看需求。例如多个组件读取同一份商品数据时，我会先明确缓存共享、失效和重新请求的规则，再决定使用哪种方式。

5. redux-persist 是独立的持久化方案，需要选择保存哪些字段及恢复规则。角色缓存只能帮助展示界面，不能代替服务端鉴权；退出登录、账号切换和旧数据版本变化时，也要避免恢复上一个用户的状态。

## 追问：为什么 reducer 看起来可以直接修改 state？

1. 在 createSlice 的这类 reducer 中，state 通常是 Immer 提供的草稿，对它的修改会被记录并转成新结果。没有变化的部分可以继续共享引用，而不是每更新一个字段就深拷贝整个状态树。这也有助于依赖引用比较的订阅判断哪些数据发生变化。

2. 我会选择修改草稿或返回替换状态中的一种方式，避免一边改字段一边又返回另一个新对象。像 `state = action.payload` 只改变局部变量绑定，也不等于替换整个 slice，整体替换应明确 return。

3. reducer 仍然需要可预测，不适合在里面发请求、操作 DOM 或读写本地存储。异步和外部操作应在相应逻辑中处理，再 dispatch 结果，这样重放 action 或定位某次更新时才更清楚。

## 追问：登录信息持久化后，刷新页面就一定能直接使用吗？

1. 不一定，本地恢复出来的信息可能过期，Token 也可能被撤销。我会区分“有缓存”和“当前认证有效”，需要时请求服务端确认身份，不能只因为缓存里有管理员角色就开放真实权限。

2. 页面初始化还要考虑恢复状态的时机，否则未恢复时可能被错误跳转到登录页。可以设计明确的初始化状态，在认证判断完成前显示加载反馈，而不是把暂时没有数据当成已经退出。

3. 保存内容应有明确范围，密码不应进入持久化状态，敏感凭据的存放要按认证方案判断。如果继续完善，我会检查账号切换时的清理和持久化结构迁移，避免旧缓存让新版本页面读取错误字段。
