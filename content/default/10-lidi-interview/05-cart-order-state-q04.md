# 购物车为什么要先把嵌套数据扁平化？

## 核心回答

1. 后端的购物车结构先按店铺分组，再到优惠分组，最后才是商品项。这个结构适合展示店铺名称和活动，但做全选或找选中 ID 时每次都写多层循环，很容易遗漏一层或在不同地方出现不一致的处理。

2. 当前 cartItems 计算属性遍历 shopCartItemDiscounts 和 shopCartItems，把所有商品引用整理成一个数组。之后计算 selectedBasketIds、allChecked 和逐项修改，都可以面对同一层商品集合，逻辑更集中。

3. 原始 cartList 仍保留给页面按组展示，扁平化只是增加一个适合操作的视角。它没有把接口数据永久改成平面结构，也没有丢弃店铺与优惠信息，不能为了方便计算就把模板所需的分组关系一起删除。

4. 扁平数组中放的是原商品对象，没有深拷贝，所以修改 checked 仍会反映到原分组里的商品。若随意用展开语法为每项复制一份，再在复制对象上改状态，就可能出现计算数组选中了、原模板却没变化的问题。

5. 当前一些购物车数据仍使用 any，如果继续完善，我会分别定义店铺、优惠分组与商品项类型，并确认空分组和缺失数组的处理。扁平化让代码容易读，但不能替代接口结构校验，也不能自动解决重复 ID 等数据问题。

## 追问：computed 每次返回新数组，会复制商品对象吗？

1. 不一定，数组容器新建与元素深拷贝是两件事。把原来的 item 放进新数组，两个结构仍引用同一个商品对象，修改 item.checked 会影响同一对象，而不是生成两份互不相干的状态。

2. 但如果遍历时写成复制对象，元素引用就改变了，顶层 checked 可能不再与原商品保持一致。深浅拷贝的区别在这里很实际，不能只看到使用 flatMap 或展开就直接判断所有层级是否共享。

3. 我会通过修改扁平项并观察分组模板验证，同时检查是否有不希望出现的共享修改。需要独立编辑草稿时才考虑复制，当前勾选希望同步，所以共享原商品引用反而符合目的。

## 追问：服务端同一个购物车项重复出现在分组里怎么办？

1. 先确认接口语义，是重复数据，还是同一商品的不同购物车项。prodId 相同不代表 basketId 相同，可能是不同 SKU；不能为了去重简单按商品 ID 合并，否则会丢掉合法的规格与数量。

2. 如果同一个 basketId 重复且违反约定，应在数据边界发现并与后端核对。前端临时去重可以减少重复操作，但要明确保留哪条，不能默默相加数量或任选价格，把异常变成难以追踪的业务变化。

3. 测试可以包含同商品不同 SKU、相同 basketId 重复和空优惠组，检查选中 ID 与删除参数。扁平化只简化遍历，正确识别每一条购物车项仍依赖稳定标识和明确的数据契约，也要与后端逐项核对。
