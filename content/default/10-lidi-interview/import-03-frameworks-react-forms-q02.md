# 表单性能差时怎么查？

## 核心回答

1. 我会先复现具体的卡顿动作，比如输入某个字段、打开下拉列表或提交校验，再用 React Profiler 和浏览器性能面板区分耗时。输入慢可能来自整张表重渲染，也可能是校验计算、布局或同步存储，并不是必然由受控输入造成。

2. 如果每次按键都让大量无关字段执行，我会检查状态是否放得太高，以及是否订阅了整份表单。把字段状态或订阅缩小到真正需要的范围，通常比给所有组件加 memo 更直接；联动字段仍要保留必要的更新关系。

3. 如果耗时来自校验，就把简单格式检查和昂贵检查分开。远程检查可以防抖并处理竞态，复杂计算可以延后或视情况放入 Worker；输入值本身仍应立即更新，不能为了减轻工作让光标和文字反馈明显滞后。

4. 非受控方案能减少逐键 state 更新，但会改变值读取和联动方式，不能只为追求少渲染就盲目切换。我会用接近实际的字段数、错误提示和联动操作重新测量，确认输入响应变好，也没有丢失校验或重置行为。

5. 我也会检查长下拉和错误列表的真实节点数量。即使字段组件更新次数很少，一次打开几千个选项仍可能造成布局和绘制压力，这时分页、虚拟化或更合适的选项检索方式，比继续稳定几个回调引用更接近实际问题。

## 追问：为什么给字段组件套 memo 之后还是每次都渲染？

1. memo 默认浅比较 props。父组件每次传入新的错误对象、内联配置数组或回调函数，即使内容看起来一样，引用变化仍会使比较失败；先查看到底是哪一个 prop 变了，再决定如何调整。

2. 字段自身 state 或读取的 Context 变化，也会触发它更新，memo 不能屏蔽这些来源。若所有字段都消费一整个表单 Context，输入一个字段就改变 value，单独给字段加 memo 并不能解决订阅过大的问题。

3. 我会让字段只接收自己的值、错误和必要事件，昂贵子组件再考虑稳定引用。自定义比较函数必须比较影响显示和事件行为的全部 props，漏掉回调可能让界面看似不更新，点击时却执行旧逻辑。

## 追问：防抖应该加在输入更新上，还是校验和请求上？

1. 受控输入的显示值应及时更新，否则用户按键后要等一段时间才看到内容，输入法组合和光标位置也可能变得难处理。通常把延迟放在搜索请求或昂贵校验上，而不是直接延迟 value 的回写。

2. 可以分别维护即时输入和已确认的查询条件，或者由防抖函数读取本次值安排请求。清空、提交和切换表单时需要取消或立即执行待处理任务，不能留下一个过期定时器稍后修改新表单。

3. 防抖不解决并发返回顺序，延迟后的两次请求依然可能乱序完成。我会用请求编号保护结果，并在最终提交时执行必须的校验，不能因为用户点击过快、最后一次防抖尚未触发就放过检查。
