# 表单性能差时怎么查？

## 核心回答

1. 先复现卡在哪一下：敲某个字段、打开下拉、点提交校验。再用 React Profiler 和浏览器性能面板看时间花在哪。输入慢，可能是整张表都在重渲染，也可能是校验计算、布局、同步往存储里写，不一定就是受控输入的锅。

2. 每次按键都带着大量无关字段跑，看状态是不是放得太高，是不是订了整份表单。把字段状态或订阅收到真正用到的范围，通常比给所有组件加 `memo` 更直接。该联动的字段还是要联动。

3. 时间花在校验上，就把简单格式检查和贵的检查分开。远程检查防抖，还要处理谁先回来；复杂计算可以往后放，必要时丢 Worker。输入框里的字还是要马上跟上，别为了少干活让光标和文字明显慢半拍。

4. 非受控能少掉逐键的 state 更新，但取值和联动方式会变，别为了少渲染就整表切过去。用接近真实的字段数、错误提示、联动再测一遍，确认输入跟手，校验和重置也还在。

5. 长下拉、错误列表的真实节点数也要看。字段组件自己不怎么更新，一打开几千个选项，布局和绘制照样会顶不住。这时分页、虚拟列表、或者先检索再出选项，比再稳住几个回调更对症。

## 追问：为什么给字段组件套 memo 之后还是每次都渲染？

1. `memo` 默认浅比较 props。父组件每次传来新的错误对象、内联配置数组、或者新的回调，内容看着一样，引用不一样比较就失败。先看到底是哪一个 prop 在变，再决定怎么改。

2. 字段自己的 state 变了，或者它读的 Context 变了，也会更新，`memo` 挡不住这些。所有字段都在吃一整份表单 Context，敲一个字 `value` 就变，单独给字段加 `memo` 解决不了订得太大的问题。

3. 字段只收自己的值、错误和必要事件，贵的子组件再考虑把引用稳住。自定义比较函数要把影响显示和点击行为的 props 都比到。漏掉回调，界面像没更新，点下去却跑的是旧逻辑。

## 追问：防抖应该加在输入更新上，还是校验和请求上？

1. 受控输入的显示值要马上跟上。按了键等一会儿才看到字，输入法组合、光标位置都容易乱。延迟通常加在搜索请求或贵的校验上，别直接推迟 `value` 回写。

2. 可以一份是眼前的输入，一份是已经确认要去查的条件；也可以防抖函数读这次的值再安排请求。清空、提交、换表单时，把还没跑的定时器取消或马上执行，别留一个过期定时器回头去改新表单。

3. 防抖不管返回顺序。延迟之后发出的两次请求，照样可能后发的先回来。用请求编号护住结果。最终提交该做的校验还是要做，别因为点得太快、最后一次防抖还没触发，检查就被跳过。
