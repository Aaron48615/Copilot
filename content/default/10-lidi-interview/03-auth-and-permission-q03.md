# 把 Token 放在哪里更安全？

## 核心回答

1. 当前轻购把 accessToken 存在 localStorage，刷新后仍能读取，Axios 请求拦截器再加入 Authorization。这种方式刷新恢复比较直接，但 localStorage 中的数据能被同源脚本访问，不能据此称它最安全。

2. 如果页面出现 XSS，恶意脚本可能读取并带走 Token。改成 sessionStorage 只是缩短保存周期，仍然可被页面脚本读取；存内存能减少持久残留，但刷新恢复与会话续期又需要另外设计，没有只换一个 API 就彻底解决的方案。

3. HttpOnly Cookie 能阻止 JavaScript 直接读取对应凭据，通常可以降低直接盗取的风险。Secure 用来限制安全传输，SameSite 影响跨站携带；但 Cookie 会随符合规则的请求自动发送，因此还要结合业务处理 CSRF 等问题。

4. HttpOnly 也不能消除 XSS，恶意脚本可能借当前页面身份操作接口或读取页面数据。无论使用哪种存储，输出清洗、HTTPS、有效期、退出与服务端身份校验都要考虑，不能把存储方案代替完整会话设计。

5. 如果重新选择，根据前后端是否同站、是否存在第三方客户端和后端协议共同确定。同站 Web 应用可以优先评估 HttpOnly Cookie；需要多种客户端共享认证接口时，再比较 Bearer Token 的存储和续期方式，没有一个选项能省掉全部安全处理。

## 追问：sessionStorage 比 localStorage 安全很多吗？

1. 它主要改变数据保留范围与生命周期，同一标签页刷新仍在，通常关闭后清除。相比长期 localStorage，敏感信息残留时间可能更短，但两者都可被页面脚本读取，所以面对同源 XSS 并没有本质隔离。

2. 对轻购的订单确认参数，sessionStorage 适合临时流程；对登录凭据，还需要考虑刷新、多个标签页和退出策略。不能因为它名字带 session，就以为它自动具备服务端会话校验或 HttpOnly 的保护。

3. 如果继续改，先确定威胁与产品需求，再选择存储，不把“关闭会消失”当安全结论。服务端仍应检查凭据有效期与资源归属，前端也要消除危险 HTML 等脚本入口，这些工作不会因换存储而省掉。

## 追问：HttpOnly Cookie 方案下，前端怎么知道自己登录了？

1. 前端不需要读取凭据本身，可以调用当前用户或会话接口，根据服务端返回的用户信息建立页面登录状态。Cookie 随符合配置的请求发送，身份由后端确认，这与把 Token 文本读进 JavaScript 是不同方式。

2. 页面刷新后会有一次身份确认过程，可以显示短暂加载，再决定进入目标页面还是登录。跨源场景还要按部署方式配置凭据请求与 CORS，不能只让后端加一个 HttpOnly 就期望所有浏览器请求自动正确携带。

3. 退出时应由服务端让会话失效或清除对应 Cookie，前端再清理用户数据。这样的调整涉及前后端协议，当前轻购并未因此自动具备这套流程，这是可选改进，不是现状。
