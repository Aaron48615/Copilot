# 为什么 setTimeout 里的 this 常出问题？

## 核心回答

1. 定时器里的 this 容易出问题，主要是把对象方法作为参数传出去时，只传了函数值，没有保留原来的对象调用关系。假设把计数器的增加方法直接交给定时器，回调执行时就不再等价于通过计数器对象调用这个方法。

2. 普通函数的 this 取决于实际调用方式，定时器由运行环境调用回调，因此不能默认它还是原对象。浏览器与服务端环境的具体表现还可能不同，我会先确认运行环境，而不会把所有定时器回调都说成指向同一个全局对象。

3. 如果想在执行时调用对象的当前方法，可以传入箭头包装，例如 `() => counter.inc()`，这里通过对象完成调用。箭头函数也可以在实例方法中捕获外层 this，但前提是外层方法本身已经拿到了正确实例，否则只是保留了错误值。

4. 另一种方式是提前绑定方法，例如使用 bind 得到固定接收者的回调，并保存这个函数引用。绑定保留的是对象引用，不会冻结对象内部的字段，所以延迟执行时读取到的通常是最新状态，而不是安排定时器时的状态快照。

5. 如果回调其实只需要一个编号，我更愿意显式传入或捕获编号，减少对整个实例的依赖。对于页面离开后不应执行的任务，还要保存定时器标识并清理；绑定解决的是接收者问题，不能顺便解决过期任务或数据时序问题。

## 追问：箭头包装和 bind 在方法被替换后有什么区别？

1. 假设先创建回调，随后把对象的增加方法替换为新实现，箭头包装在执行时再读取对象上的方法，因此通常调用新实现。提前绑定则保存了当时的原函数和接收者，后续属性替换不会让这个已绑定函数自动改用新实现。

2. 两者都可能读取对象的最新字段，因为它们引用的还是同一个对象，而不是完整保存了对象当时的状态。若需要的是安排任务时的数量，我会先把数量保存为单独的值，再让回调使用它，明确区分方法选择与数据快照。

3. 选择时要看任务意图，例如希望尊重运行时替换的方法，可以用延迟查找的包装；希望固定本次提交行为，可以保存具体回调。测试可以在等待期间分别修改字段和替换方法，检查实际变化是否符合预期，而不是只验证回调能运行。

## 追问：用了箭头函数，为什么回调还是拿不到实例？

1. 箭头函数保留的是定义位置外层的 this，并不会自动寻找距离最近的对象。假设把包含定时器的类方法先取出来直接调用，这个外层方法已经丢失实例，里面再定义箭头回调，也只会沿用当前无效的接收者。

2. 对象字面量里的箭头属性也不会把对象字面量当成 this 的作用域，例如把普通对象的方法直接改成箭头，不一定能读取该对象字段。需要对象接收者时可以保留普通方法，并保证入口以对象方法方式调用，或提前绑定入口。

3. 排查时我会从外层调用一路追到回调创建处，分别检查外层的 this 和回调执行时使用的值。这样能区分接收者一开始就错了，还是传递过程中丢失，避免在每一层盲目增加箭头函数却没有修正真正的入口问题。
