# 怎么区分 AI 写的功能已经做好还是只是看起来能用？

## 核心回答

1. 「做好」得变成能检查的条件，不是看 AI 有没有生成一个漂亮页面。导购要能提交需求、展示对应商品、解释匹配情况、进到正确详情。每一项都能从一次操作和实际结果里判断。

2. 正常路径之外也要看，尤其是失败之后用户还能不能继续操作。接口报错、返回空商品、字段缺失是不同场景。全部显示一块空白，页面没崩，交互也不算做完。

3. 异步功能要改操作顺序再验，演示一次成功请求不够。连续提交不同需求，让第一次后回来，页面仍该对应当前这次。顺序返回时正常，碰到慢网络就显示错内容，这种代码很常见。

4. 验推荐系统，把前端展示、规则计算、模型理解分开看。固定响应可以验页面，固定商品和已解析条件可以验规则，真实自然语言要另做模型评估。这是验证方法，不是说项目已经具备全部测试。

5. 最后读差异，看功能之外有没有偷偷加依赖、改公共接口、忽略错误处理。符合当前约定、又有对应验证的部分，才说完成。确认不了的后端实现和真实环境表现，缺什么证据就说什么。

## 追问：演示十次都成功，为什么还不能保证功能可靠？

1. 十次如果都是同一个输入、同样快的网络，其实只反复覆盖了很窄的一条路。这个场景重复成功，能观察得到；空数据、乱序响应、权限过期对不对，它说明不了。

2. 改会影响行为的条件：接口延迟拉长、商品缺可选字段、请求中途离开页面。重点是盖到不同分支，不是单纯加演示次数。这样找到的问题也更容易对上具体原因。

3. 对模型输出，还要留输入、期望约束、实际结果，看不同表达是不是被理解成一样。少量样例通过，只说明这些样例的表现。别据此编总体准确率，更别承诺模型永远不会理解错需求。

## 追问：只剩半天，你会优先检查哪些问题？

1. 优先查直接影响用户决策和操作结果的：商品价格、预算提示、详情标识是不是对得上。样式上的小间距可以后排。推荐内容和原需求矛盾，功能本身就不可信，这个得先确认。

2. 接着查一次成功操作，以及最常见的失败恢复：接口报错后加载能不能结束、能不能重新提交。有重复请求的入口，再补一组乱序返回。普通演示里很难碰到，最终展示却会受影响。

3. 剩下的问题按影响记清楚，交付范围收到已经验过的行为上。还没验的入口必要时先不开放。时间不够可以缩小范围，不能改事实表述。没执行的检查，别写成已经完成来凑一个完整结论。
