# `computed` 和 `watch` 的区别？

## 核心回答

1. `computed` 适合从已有响应式状态推导出一个值，例如按商品价格和数量计算购物车合计。它会基于响应式依赖缓存结果，依赖没有变化时重复读取可以复用结果，因此不需要另外保存一份总价再手动同步。

2. 计算属性的 getter 应保持纯粹，主要负责计算并返回值，不在里面发请求、修改其他状态或操作 DOM。比如 `Date.now()` 本身不是响应式依赖，单独把它放进计算属性也不会让时间自动持续刷新。

3. `watch` 适合在指定数据改变时执行副作用，例如查询条件变化后请求列表，或同步第三方地图实例。默认不会在创建时立刻执行回调，需要初始化就运行可以设置 `immediate`，这和计算属性按读取求值的用途不同。

4. 监听对象属性时，我会传 getter，例如 `watch(() => state.keyword, callback)`，而不是把当下的字符串值传进去。对大对象开启深度监听需要谨慎，嵌套遍历有成本，而且原地修改时新旧值可能仍指向同一个对象。

5. 对异步监听，我会清理旧请求或检查请求序号，避免旧结果覆盖新结果。需要在所属组件 DOM 更新后读取尺寸时可以用 `flush: 'post'`；普通默认回调发生在该组件 DOM 更新前，不能假定任何 watcher 都已经看到最新 DOM。

## 追问：watch 和 watchEffect 应该怎么选？

1. `watch` 把监听源和回调分开，适合明确规定“只有商品 ID 改变才重新请求”的场景。回调里读取其他响应式值，不会自动把它们都加入监听源，这能避免某个辅助字段变化也意外触发请求。

2. `watchEffect` 会立即执行，并自动追踪同步执行期间读取的响应式依赖，适合依赖关系简单的副作用。若回调是异步函数，通常只有第一次 `await` 之前访问到的依赖会被收集，后面读取的值不能指望自动被监听。

3. 我会根据依赖是否需要显式控制来选，而不是只看哪个写得短。计算展示值仍优先使用 `computed`，不能把 `watchEffect` 当成计算属性的替代品，否则会多维护一份状态，也更难判断数据从哪里产生。

## 追问：监听搜索词发请求时，旧请求应该怎样清理？

1. 每次回调创建一个新的 `AbortController`，把它的 `signal` 交给请求，再注册清理函数取消本次请求。清理应在发起异步等待前安排好，避免搜索词已经变化后，旧请求才迟迟登记取消逻辑。

2. Vue 3 的 `watch` 回调第三个参数提供 `onCleanup`；Vue 3.5 起还可以用 `onWatcherCleanup`，但后者必须在同步执行阶段调用，不能放到 `await` 后面。我会核对项目版本再选 API，不假定所有 Vue 3 项目都支持新方法。

3. 主动取消通常不需要显示成网络故障，同时还要保护 loading 和结果更新，只让有效请求修改它们。对于不能可靠取消的异步操作，可以用失效标记或递增序号过滤结果；取消和结果校验解决的是相关但不同的问题。
