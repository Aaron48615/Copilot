# 轻购为什么使用路由懒加载？部署后动态模块加载失败怎么办？

## 核心回答

1. 路由懒加载是等用户需要某个页面时，再加载它对应的代码。轻购里很多业务页面在路由表中写成 `() => import(...)`，比如商品详情、购物车和订单。这样用户刚打开首页时，不必把还没访问的页面代码全部一起下载。

2. 构建工具会根据动态导入组织分包，但一个页面不一定永远只对应一个独立文件，因为公共依赖可能共享。主要收益是推迟暂时用不到的代码加载；具体首屏减少多少，要看构建结果和网络记录，不能凭用了懒加载就给出提升百分比。

3. 部署以后可能遇到一种问题：用户仍然开着旧版本页面，里面记的是旧分包地址，而新部署已经把旧文件删了。这时点一个还没加载过的路由，就可能请求不到那个文件。这和业务接口失败不一样，失败的是页面需要执行的 JavaScript 模块。

4. 项目里的 `deploymentRecovery` 会监听 `vite:preloadError` 和路由中的动态模块加载错误，识别相关情况后记录恢复标记，并通过带 `_app_reload` 的 URL 刷新页面。它限制同一目标的恢复次数，成功进入路由后再清理标记，避免反复刷新却始终进不去。

5. 不过动态加载失败也可能来自断网，刷新并不是所有问题的通用解法。这段逻辑是一次恢复尝试，后续仍要检查入口 HTML 的缓存、旧静态文件是否保留，以及失败后能不能提示用户重试。部署策略处理好，才不需要让用户总靠刷新解决。

## 追问：为什么不能遇到加载错误就一直刷新？

1. 因为错误可能一直存在，比如用户离线，或者服务器确实缺文件。这时每次失败都刷新，只会进循环，用户连错误提示都来不及看到，也没有机会回到可用页面。

2. 恢复前应该记录这次尝试对应的目标，并限制自动恢复。已经试过仍失败时，就停止自动刷新，保留错误信息和手动重试入口。刷新还可能丢掉未保存的输入，因此也要考虑页面里有没有需要提醒用户的内容。

3. 验证时可以分别模拟旧分包返回 404 和网络离线。前者在拿到新入口后可能恢复，后者不能保证恢复。两种情况都不能无限刷新，重新联网后用户还得有可操作的恢复方式。

## 追问：入口 HTML 和带哈希的 JavaScript 文件为什么适合不同的缓存策略？

1. HTML 里包含当前版本资源的引用。如果它长期不更新，用户可能一直拿着旧地址去访问已经失效的文件，所以入口通常要能及时检查有没有新版本，而不是给所有文件统一设很长的缓存时间。

2. 带内容哈希的 JavaScript 文件，内容变了文件名也会变，因此通常更适合长期缓存。浏览器可以复用相同文件，新版本则通过新 HTML 引用新文件，减少重复下载。关键是部署时保证 HTML 引用的文件确实存在。

3. 对于还开着旧页面的用户，还可以保留一段时间的旧分包，减少他们后续导航时找不到文件。这是部署端的配合方案，不代表当前前端的一次刷新逻辑已经把所有缓存问题都解决了。
