# 怎样测组件销毁清理？

## 核心回答

1. 测销毁清理，要看资源是不是真的停了，不只是某个清理方法被调用过。组件建了轮询，先确认挂着的时候会执行；再卸载、把时钟往前拨，请求次数不再涨，才说明人走了没有残留工作。

2. 事件监听要核对摘掉的事件类型、函数引用、相关配置。卸载后再派发一次，确认不再响应。添加和移除用了两个新的匿名函数，方法名都对得上，实际没摘掉。只断言 `removeEventListener` 调了一次，可能漏。

3. 请求还没回来就卸载，再让模拟请求成功或失败，结果不该再动后续界面。支持取消就查 signal，也要查有效性判断。网络已经结束之后的异步转换仍可能继续，调用了取消，不等于所有旧回调都跑不了。

4. `KeepAlive` 下普通切换是停用，不是卸载。停用暂停、激活恢复、缓存淘汰释放，分开测。Vue 2 Test Utils 用 `destroy`，Vue 3 用 `unmount`，跟着项目版本走，两套 API 别混写。

5. 每个用例自己建组件、时钟、替身，结束恢复环境，上一个测试的监听别漏到下一个。重复挂上再卸掉也值得覆盖，重新进入只该有一份资源。第一次离开没报错，发现不了订阅越积越多、第二次启动翻倍。

## 追问：只断言 clearInterval 被调用，为什么还不够？

1. 清掉的可能是错的句柄，或者组件建了两个定时器只清了一个。方法被调用说明尝试清理了，说明不了外面已经停。卸载后再推进足够时间，业务回调或请求次数应保持不变。

2. 先证明挂着的时候定时器确实在工作，再卸载做反向验证。组件根本没启动成功，卸载后当然没有新调用，测试绿了却没盖到清理能力。正向和停了之后的断言要一起有。

3. 测完恢复假时钟、清掉残留任务，别影响后面用例。循环定时器别无条件跑到永远结束，推进一段有限时间，测试可控，也不会被无限重复任务拖死。

## 追问：怎样测试快速挂载后马上卸载的异步初始化？

1. 用一个能手动完成的 Promise 模拟初始化前面的请求，挂上立刻卸掉，再完成这个 Promise。看迟到的逻辑会不会还去创建编辑器、监听、定时器。真实快速切页最容易冒这种没人管的资源。

2. 实现上应检查组件或请求还有效没有，或者让初始化任务能取消。测试里不但看没有更新文本，也看第三方构造、注册方法有没有被迟到回调调到。组件已经没了，界面断言不一定能发现后台泄漏。

3. 初始化已经创建了资源才发现失效，也要马上释放，句柄别留下来给下次误用。再挂一份新组件，新的初始化应正常，旧任务不能碰到新实例。实例边界这样才完整。
