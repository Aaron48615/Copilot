# 怎样测组件销毁清理？

## 核心回答

1. 测组件销毁清理，要验证资源行为确实停止，而不只是看到某个清理方法被调用。比如组件创建轮询后，先确认在挂载期间会执行，再卸载、继续推进时钟，检查请求次数不再增加，这才说明用户离开后没有残留工作。

2. 事件监听需要检查移除的事件类型、函数引用和相关配置，并在卸载后派发事件确认不再响应。若添加和移除使用两个新匿名函数，代码都有对应方法名却没真正清理，单纯断言 removeEventListener 调用一次可能漏掉问题。

3. 请求尚未完成时卸载，再让模拟请求成功或失败，确认结果不会影响后续界面。支持取消时检查信号，也要验证有效性判断，因为网络已经结束后的异步转换仍可能继续，取消调用存在不等于所有旧回调都无法执行。

4. 使用 KeepAlive 时，普通切换是停用而非卸载，应分别测停用暂停、激活恢复和缓存淘汰释放。Vue 2 Test Utils 使用 destroy，Vue 3 使用 unmount 等对应接口，测试代码需要跟随项目实际版本，不能把两个版本 API 混写。

5. 我会让每个用例自行建立组件、时钟和替身，结束后恢复环境，避免前一个测试的监听影响后一个。重复挂载卸载也值得覆盖，确认重新进入只产生一份资源；只测第一次离开没有异常，发现不了累积订阅和第二次启动的问题。

## 追问：只断言 clearInterval 被调用，为什么还不够？

1. 它可能清除的是错误句柄，或者组件同时创建了两个定时器只清掉一个。方法调用本身说明尝试清理，不说明外部行为已停止，因此还应在卸载后推进足够时间，检查业务回调或请求次数保持不变。

2. 我会先证明挂载期间定时器确实工作，再卸载做反向验证。否则组件根本没成功启动，卸载后当然没有新调用，测试看似通过却没有覆盖所声称的清理能力，正向和停止后的断言需要配合。

3. 测试结束还要恢复假时钟和清除残留任务，避免影响后续用例。对于循环定时器不应无条件运行所有任务直到结束，而应推进有限时间窗口，确保测试可控且不会因为无限重复任务一直运行。

## 追问：怎样测试快速挂载后马上卸载的异步初始化？

1. 用一个手动控制完成的 Promise 模拟初始化前置请求，挂载后立即卸载，再完成该 Promise。这样可以观察迟到的逻辑是否仍创建编辑器、监听或定时器，真实快速切页时最容易出现这种无人管理的资源。

2. 正确实现应检查组件或请求是否仍有效，或者让初始化任务能够取消。测试中不仅检查没有更新文本，也要检查第三方构造或注册方法没有被迟到回调调用，因为组件已经消失，界面断言未必能发现后台泄漏。

3. 如果初始化已经创建资源再发现失效，也要立即释放，并验证句柄没有被保存供下次误用。然后重新挂载一份新组件，确认新的初始化正常，旧任务不能影响新实例，这能把实例边界验证得更完整。
