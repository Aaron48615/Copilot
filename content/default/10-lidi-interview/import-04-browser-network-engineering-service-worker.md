# Service Worker 能做什么，更新时有什么坑？

## 核心回答

1. Service Worker 是浏览器在独立上下文运行的脚本，可以在作用范围内处理请求事件，并结合缓存提供离线访问。它不能直接操作页面 DOM，通常要求安全上下文，也不是永远运行的后台进程，浏览器可以随时结束它并在事件到来时重新启动。

2. 常见生命周期包括安装、等待和激活。安装阶段准备必要资源，新版本可能等待旧客户端退出再接管；页面首次注册成功也不一定马上受控制，所以要区分注册完成、worker 激活和当前页面已被控制这几件事。

3. 缓存策略要按资源区分。版本化静态文件适合缓存优先，入口可能需要更及时更新，接口按可容忍的陈旧程度选择网络优先或后台更新；Cache Storage 的管理要自己设计，不能以为响应带了缓存头就自动完成所有规则。

4. 更新最容易出现新旧组合问题。强制跳过等待或立即接管时，旧页面代码可能遇到新资源策略，过早删除旧缓存又会影响旧页面懒加载；我会考虑更新提示、兼容窗口和失败恢复，而不是默认新版本必须马上接管所有页面。

5. 如果继续完善离线能力，我会重点处理缓存上限、私人数据隔离、网络失败和多标签更新，并测试离线保存后的恢复。离线页面能打开不代表提交也能安全执行，界面要明确区分本地已保存与服务端已确认，失败后保留可恢复内容。

## 追问：离线时把所有请求放入队列，联网后重发就可以吗？

1. 不能，读取请求和修改状态的请求需求不同，写操作还可能包含过期凭据、已变化的业务条件或重复提交。把整份请求原样保存也可能泄露私人数据，因此需要按允许的业务操作设计离线记录。

2. 我会记录稳定操作标识、必要参数和版本，联网后由服务端幂等处理，并检查冲突。比如离线编辑的记录已经被别人更新，应该提示合并或重新确认，不能按旧快照直接覆盖服务器最新数据。

3. 界面要区分已在本地保存和已同步到服务器，并允许查看失败项目。浏览器存储可能被清理，后台任务也不保证及时运行，因此重要数据需要可恢复方案，不能把排入队列就显示成永久保存成功。

## 追问：为什么不能把重要状态只放在 worker 的全局变量里？

1. Service Worker 是事件驱动的，浏览器可能在空闲时终止它，下次事件再重新启动。全局变量只在当前执行实例中存在，不具备跨生命周期的持久性，所以不能用它唯一保存待上传任务或用户草稿。

2. 需要跨事件保留的数据应使用合适的持久存储，并在每次处理事件时读取必要状态。处理异步工作还要正确使用 waitUntil 等机制延长事件工作范围，但它也不是让脚本无限运行的承诺。

3. 我会模拟停止 worker 后重新请求，确认任务和版本判断仍然正确。若功能只在开发工具一直保持 worker 活跃时正常，说明可能依赖了偶然生命周期，应先修复状态保存方式再讨论后台能力是否可靠。
