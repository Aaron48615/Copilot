# 普通函数、箭头函数和类方法的 this 怎么判断？

## 核心回答

1. 判断 this 时，我会先看函数种类，再看它最终怎样被调用，而不是只看写在谁的对象里面。对于依赖动态接收者的普通函数，通过 `obj.fn()` 调用通常使用 obj，但把方法取出来交给别处以后，这层调用关系就可能丢失。

2. 普通函数直接调用时，严格模式下 this 是未定义值，非严格模式则会做默认绑定和必要的值转换。显式调用可以用 call 或 apply 提供接收者，bind 则返回保存接收者的新函数；判断时还要注意函数是否早已被绑定。

3. 箭头函数没有自己的 this，会沿定义位置的外层作用域查找，因此换一种调用方式也不能重新指定它的接收者。对象字面量本身不创建这样的 this 作用域，所以把对象方法一律写成箭头函数，并不能保证它指向这个对象。

4. 类的普通方法使用严格模式，也不会因为写在类里就自动绑定实例，脱离实例直接调用时可能读不到字段。可以在构造时绑定需要外传的方法，或使用实例箭头属性；后者会在每个实例上创建函数，需要结合使用方式选择。

5. 通过 new 调用可构造函数时，this 通常参与新实例的初始化，不过构造函数显式返回对象会影响最终结果。如果让我排查问题，我会画清调用入口、函数传递和绑定位置，再用最小例子确认，避免把几条规则背成没有前提的口诀。

## 追问：类方法传给事件监听器后为什么读不到实例字段？

1. 注册监听器时传入的是函数引用，事件系统并不知道这个函数原来属于哪个实例。普通 DOM 监听回调执行时的 this 通常对应当前处理监听的目标，所以直接读取实例字段可能拿到未定义值，即使事件本身已经正常触发。

2. 我会把方法绑定到实例后保存为稳定引用，或者用保存下来的箭头回调转发到实例方法，再用于注册和移除监听。事件目标可以从事件对象读取，不必同时依赖 this 表达实例和页面元素，否则一个变量承担两种含义容易混淆。

3. 清理时不能重新调用一次 bind 后拿新函数去移除，因为那不是注册时的同一个引用，箭头包装临时重建也有同样问题。验证时除了确认点击能更新字段，还要检查注销后确实不再执行，以及反复进入页面没有累积监听器。

## 追问：实例箭头属性和原型方法应该怎样选择？

1. 原型方法由多个实例共享函数，适合通过实例调用且不需要长期外传的行为，方法内部仍可根据接收者操作不同实例。实例箭头属性则固定捕获创建时的实例，用作回调比较直接，但每个实例会拥有各自的函数对象。

2. 这不意味着箭头属性一定造成明显性能问题，也不意味着原型方法永远更好，需要看实例数量和实际使用场景。假设只有少量界面对象，稳定回调带来的清晰度可能更重要；若创建大量短生命周期对象，就应关注分配成本。

3. 我会优先让调用约定清楚，需要共享实现时保留原型方法，仅对确实外传的入口绑定，并保存好回调引用。涉及继承和方法替换时再检查是否依赖原型上的行为，不为省几行绑定代码就把所有方法统一改成实例字段。
