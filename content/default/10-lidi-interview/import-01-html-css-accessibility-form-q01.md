# 什么时候使用 aria？

## 核心回答

1. 我会在原生 HTML 无法充分表达名称、状态或关系时使用 ARIA。比如只有放大镜图标的搜索按钮，可以补一个明确的 `aria-label`；但如果按钮已经有“搜索”文字，一般就不必再写另一套名称，避免显示文字和读屏名称不一致。

2. 表单中的关系也是常见场景。帮助说明或错误文本可以用 `aria-describedby` 关联输入框，校验不通过后用 `aria-invalid` 表达状态。它们不会替用户执行校验，应用仍然要决定什么时候错误成立、什么时候移除错误提示。

3. 对于展开面板的按钮，可以用 `aria-expanded` 反映展开状态，必要时用 `aria-controls` 指向受控区域。状态必须随着界面真实变化更新，不能只是初始化写成 false；否则读屏用户听到的是关闭，眼前的内容却已经打开。

4. 我会优先选择 button、input、select 等原生元素，再考虑自定义角色。给 div 加 `role="button"` 不会自动获得 Tab 焦点、空格触发或禁用行为，这些都得补齐。ARIA 是语义补充，最终还要结合键盘操作和读屏检查来验证。

5. 装饰图标可以对辅助技术隐藏，避免按钮名称中混入没有帮助的图形信息，但不能把仍可聚焦的控件一起隐藏。名称、描述和可见状态需要彼此一致，我会查看实际计算出的可访问名称，而不只确认源码里写过一个标签。

## 追问：aria-label 和 aria-labelledby 怎么选择？

1. 界面已经存在合适的可见标题时，我倾向用 `aria-labelledby` 引用它，例如弹窗名称直接关联标题。这样修改标题后无需同步维护另一份隐藏字符串，更容易保证所有用户得到相同信息。

2. 纯图标按钮没有可引用的可见文字时，可以用简短的 aria-label，例如“删除这条记录”。如果列表中有多个相同按钮，名称还应结合对应条目区分，让用户知道删除的是哪一个对象。

3. 不应为了补充说明而把名称写成一整段帮助文本。名称负责回答“这是什么”，较长的输入要求或限制可以通过描述关联提供；还要检查计算后的可访问名称，避免已有文字被意外覆盖。

## 追问：aria-disabled 和 disabled 有什么区别？

1. 原生 disabled 会让支持它的表单控件不可操作，通常退出 Tab 顺序，并影响表单提交。比如暂不可用的提交按钮，直接使用原生属性时，浏览器会处理一部分行为，不需要从头模拟。

2. aria-disabled 主要向辅助技术说明当前不可用，不会自动阻止点击、键盘触发或提交。如果需要保留控件在焦点顺序中以便用户了解不可用原因，就必须额外拦截操作，并提供清晰说明。

3. 我会根据交互选择，而不是把两个属性视为同义词。无论哪种方式，都要测试键盘、鼠标和代码触发的业务入口；服务端也不能因为前端按钮变灰就省略权限和状态校验。
