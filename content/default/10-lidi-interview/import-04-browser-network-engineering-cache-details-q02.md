# 用户私有接口能不能放 CDN？

## 核心回答

1. 用户私有接口可以经过 CDN 转发，允不允许 CDN 缓存是另一回事。订单、个人资料这类响应带着用户信息，默认禁止共享缓存。不能因为路径都是 `/profile`，就让不同账号共用同一份结果。

2. 浏览器私有缓存和 CDN 共享缓存要分开。`Cache-Control: private` 允许私有缓存存，禁止共享缓存存；`no-store` 要求不存储响应。真正敏感的数据要按业务选，`no-cache` 不等于完全不保存。

3. 如果确实要按用户缓存，读取缓存之前就得做完身份和权限检查，缓存键也要带上可信的用户或租户范围。只按客户端传来的 `userId` 分区不安全，`Vary` 也代替不了鉴权。用户维度一大，命中率会掉，容量也会上去。

4. 先看响应能不能拆成公开信息和个人信息。比如商品介绍可以公共缓存，个人优惠单独请求。测试至少覆盖：两个账号访问同一路径、退出登录、权限变化、缓存失效。隔离没验过之前，速度快了也不能说明方案能上线。

5. 比如同一商品页的公开描述可以复用，收藏状态不能跟着公共 HTML 一起缓存。拆开请求之后，公共内容命中率还在，私人部分也好验。别为一个布尔状态，把整页的用户隔离做得特别复杂。

## 追问：加了 Vary:Cookie 就能安全缓存个人资料吗？

1. 不能单凭这个响应头下结论。`Vary` 告诉缓存按请求头选表示，并没有检查 Cookie 是否有效，也没有确认这个用户能不能看这份资料。CDN 认不认它，还得看实际产品配置和覆盖规则。

2. Cookie 里往往还有统计、偏好这些字段，整串 Cookie 都加进缓存键，会产生大量几乎复用不上的条目。如果只想按会话里的用户分区，得用可信的服务端鉴权结果，不能直接拿没验证过的请求字段当身份。

3. 资料接口优先不进共享缓存，再用两个账号、无 Cookie、伪造参数去验。真要做边缘用户缓存，退出、撤权、过期和日志脱敏都得补上。同一用户第二次访问更快，远远不够。

## 追问：误把私有响应缓存到 CDN，应该怎样处理？

1. 先停掉受影响路径的共享缓存，清掉已经存下来的缓存，确认各节点规则生效。只改源站响应头，已经存着的旧响应不一定马上消失，还得按 CDN 的清理能力做失效。

2. 随后弄清缓存键、存活时间和访问范围，排查哪些账号可能拿到别人的信息。日志查询本身也要限权限，含个人资料的响应别再复制到公开工单里。必要时按团队的安全事件流程处理。

3. 修好之后用不同账号交替访问同一地址，看响应内容，以及 `Age`、缓存命中这些信息。再把这类验证加进发布检查，重点验隔离和撤权。看见一次 MISS，不等于所有节点都已经安全。
