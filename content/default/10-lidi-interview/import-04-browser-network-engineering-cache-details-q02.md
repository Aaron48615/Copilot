# 用户私有接口能不能放 CDN？

## 核心回答

1. 用户私有接口可以经过 CDN 转发，但是否允许 CDN 缓存是另一回事。订单、个人资料这类响应包含用户信息，我会默认禁止共享缓存；不能因为接口路径都是 /profile，就让不同账号共用同一份结果。

2. 浏览器私有缓存和 CDN 共享缓存要区分。Cache-Control:private 允许私有缓存存储，禁止共享缓存存储；no-store 则要求不存储响应。真正敏感的数据需要结合业务选择，不能把 no-cache 当成完全不保存。

3. 如果确实设计按用户缓存，需要在读取缓存之前完成身份与权限检查，并让缓存键包含可信的用户或租户范围。只按客户端传来的 userId 分区并不安全，Vary 也不能代替鉴权；大量用户维度还会降低命中率、增加容量。

4. 我会先看响应是否能拆成公开信息与个人信息，例如商品介绍可以公共缓存，个人优惠单独请求。测试至少覆盖两账号访问同一路径、退出登录、权限变化和缓存失效；未验证隔离之前，速度提升不能证明方案可以上线。

5. 例如同一商品页的公开描述可以复用，但我的收藏状态不能跟着公共 HTML 一起缓存。拆开请求后既能保留公共内容的命中率，也更容易验证私人部分，避免为一个布尔状态把整个页面的用户隔离做得复杂。

## 追问：加了 Vary:Cookie 就能安全缓存个人资料吗？

1. 不能单凭这个响应头下结论。Vary 告诉缓存按请求头选择表示，并没有检查 Cookie 是否有效，也没有确认该用户能访问目标资料；CDN 是否尊重它还要看实际产品配置和覆盖规则。

2. Cookie 往往还包含统计和偏好字段，把整串 Cookie 加入缓存键可能产生大量低复用条目。若希望只按会话中的用户分区，需要可信的服务端鉴权结果，不能直接拿未经验证的请求字段当身份。

3. 我会优先让资料接口不进入共享缓存，再通过两个账号、无 Cookie 和伪造参数进行验证。如果确实要做边缘用户缓存，还要补齐退出、撤权、过期和日志脱敏，不能只验证同一用户第二次访问更快。

## 追问：误把私有响应缓存到 CDN，应该怎样处理？

1. 先停止受影响路径的共享缓存并清理已有缓存，确认各节点规则生效。仅修改源站响应头未必能让已经存储的旧响应立即消失，因此还需要按 CDN 的清理能力执行失效操作。

2. 随后确定缓存键、存活时间和访问范围，排查哪些账号可能拿到别人的信息。日志查询本身也要限制权限，不应把含个人资料的响应再次复制到公开工单中；必要时按团队的安全事件流程处理。

3. 修复后用不同账号交替访问同一地址，检查响应内容以及 Age、缓存命中等信息。再把这类验证加入发布检查，重点验证隔离和撤权，不能看到一次 MISS 就认为所有节点都已经安全。
