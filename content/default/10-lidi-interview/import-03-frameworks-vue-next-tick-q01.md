# 什么时候不该用 nextTick？

## 核心回答

1. 不碰更新后的 DOM，通常就不用 `nextTick`。响应式变量赋完值，JavaScript 里再读已经是新值，只是 Vue 可能还没把视图补丁交出去。拿新页码发请求，直接用新页码，不必等按钮重新画出来。

2. 请求完没完看它自己的 Promise，图片加载听 `load`，动画结束用动画或组件给的完成事件。`nextTick` 只等 Vue 这一轮更新刷新，不会把这些外部过程一起等完。拿它当通用 `sleep`，换个网速就偶发出问题。

3. 能绑在模板上的显示，别改成“等一下再手动改 DOM”。错误提示、按钮类名，直接绑状态。先 `nextTick` 再改文本或样式，Vue 管的界面和手写修改会互相盖，更难查。

4. 从数据派生另一个值，用 `computed`，别在 `watch` 里等一次 `nextTick` 再复制结果。多一份副本就要一直同步。监听确实要读更新后的元素，`flush: 'post'` 已经表达这个时机，不一定再套一层等待。

5. 这次操作到底在等什么完成，再选等待方式。连着放两三个 `nextTick`，保证不了第三方弹窗动画结束；写死延时也证明不了布局已经稳。用对应系统自己的完成信号，快速切换、资源迟到这些场景要测。

## 追问：改完页码就请求接口，为什么不需要先 nextTick？

1. 页码变量已经改完了，接口参数来自数据，不看分页按钮什么时候重绘。按更新后的页码直接请求。等 DOM 只是让网络晚一会儿开始，参数不会因此更正确。

2. 代码里还读到旧页码，多半是存了旧快照、传错参数，或读了另一份数据。`nextTick` 可能碰巧让某个 watcher 先跑，把顺序问题盖住。请求明确接收这次确认过的查询参数，更稳。

3. 改条件和发请求的方式要统一。又手动打一次、又监听页码再打一次，点一下会出两次接口。要等的是请求回来的数据；真要读列表新 DOM 再用 `nextTick`，两段分开。

## 追问：为什么加两个 nextTick 后偶尔正常，仍不算可靠修复？

1. 只说明这台机器、这次顺序多等了一轮，等的不一定是真正依赖。高度靠图片、结果靠网络、结束靠 CSS 动画，跟 Vue 刷新几次没有固定对应。换设备、换网速又可能坏。

2. 先看尺寸什么时候变、资源什么时候完成。图片用 `load`，弹窗用打开完成回调，容器一直变可以用 `ResizeObserver`。别加等待次数加到本机看起来正常为止。

3. 修完用延迟资源和快速开关再测，等的过程中组件可能已经离开。异步完成时节点可能没了，访问还要保护。不能因为前面等过更新，就假定元素一直还在页面上。
