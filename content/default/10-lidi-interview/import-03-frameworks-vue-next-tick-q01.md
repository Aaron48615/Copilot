# 什么时候不该用 nextTick？

## 核心回答

1. 不涉及更新后 DOM 的事情通常不需要 nextTick。响应式数据赋值后，JavaScript 中再读取这个变量已经是新值，只是 Vue 还可能没有把视图补丁提交；为了拿到新页码发请求，直接使用新页码即可，不需要先等待页面渲染。

2. 请求是否完成应等待请求自己的 Promise，图片是否加载应监听加载事件，动画是否结束应使用动画或组件提供的完成事件。nextTick 只等待 Vue 的更新刷新，不会自动把这些外部过程一起等完，把它当通用等待容易产生偶发问题。

3. 能声明式表达的显示也不必改成“等待后手动操作 DOM”。比如根据错误状态显示提示、根据条件改变类名，直接绑定状态即可；先 nextTick 再修改文本或样式，会让 Vue 管理的界面和手写修改互相覆盖，反而更难维护。

4. 依赖数据做派生计算时，应该考虑 computed，而不是 watch 中等一次 nextTick 再复制结果。额外保存副本不仅多一次更新，还要保持同步；如果监听确实需要读取更新后的元素，flush: 'post' 往往已经表达了对应时机，不一定再等待。

5. 我会先问这次操作究竟依赖哪个完成条件，再选择等待方式。连续放两三个 nextTick 并不能保证第三方弹窗动画结束，固定延时也不能证明布局稳定；正确方法是使用对应系统的完成信号，并验证快速切换和资源延迟的场景。

## 追问：改完页码就请求接口，为什么不需要先 nextTick？

1. 页码变量的赋值是已经发生的，接口参数来自数据，不依赖分页按钮何时重新绘制。直接按更新后的页码请求即可；等待 DOM 只会让本来可以立即开始的网络工作晚一点，并没有增加参数正确性。

2. 若代码仍读到旧页码，要检查是否保存了旧快照、传错参数或使用了另一个数据来源。nextTick 可能碰巧让某个 watcher 先执行，从而掩盖顺序问题，但更好的做法是让请求明确接收本次确认的查询参数。

3. 我会把修改查询条件和请求触发方式统一，避免既手动请求又监听页码请求，造成一次点击发两次接口。需要等待的是请求完成后的数据，再在确实要读取列表新 DOM 时使用 nextTick，两个阶段分别处理。

## 追问：为什么加两个 nextTick 后偶尔正常，仍不算可靠修复？

1. 它只说明当前运行顺序下多等待了一轮，不能证明等待的是实际依赖。若真正依赖图片高度、网络结果或 CSS 动画，次数固定的 Vue 刷新与这些过程没有必然对应关系，换设备或网络条件就可能再次失败。

2. 我会先记录尺寸何时变化、资源何时完成，找到决定操作成功的条件。图片使用 load，弹窗使用打开完成回调，容器持续变化可以考虑 ResizeObserver，而不是不断增加等待次数直到本机看起来正常。

3. 修复后用延迟资源和快速开关重复验证，并检查等待期间组件是否已经离开。异步完成时节点可能不存在，仍需保护访问，不能因为之前已经等过更新就假定元素以后始终保持在页面中。
