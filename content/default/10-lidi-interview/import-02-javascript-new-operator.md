# new 一个对象时底层发生了什么？

## 核心回答

1. 我会先限定在普通构造函数上解释：执行 new 时，会创建一个实例，并让它的内部原型关联到构造函数的 prototype 对象。这里建立的是查找关系，不是把原型上的方法复制一份，所以后续修改共享方法可能影响已有实例。

2. 接着以这个新实例作为 this，传入参数执行构造函数，用来初始化姓名等实例属性。比如构造函数里写 this.name，属性属于当前实例；把介绍方法放到原型上，则多个实例可以共享同一个函数。

3. 最后需要检查构造函数的返回值，显式返回对象或函数时，整个 new 表达式采用那个返回值。对于普通基础构造函数，返回数字、字符串、null 或没有返回值，最终仍然得到先前创建的实例。

4. 手写简化版时，我会用 Object.create 建立原型，再用 apply 执行初始化，并正确判断返回值是否为对象。这个实现只是帮助理解，不能因为几个例子通过，就声称完整复现了语言内置的构造机制。

5. 真正的边界还包括 class、绑定函数和内置构造器，单靠普通函数调用不能覆盖它们。箭头函数也没有构造能力；如果业务需要动态传参构造对象，我会优先考虑 Reflect.construct，而不是维护一个不完整的替代品。

## 追问：构造函数返回 null、对象或函数分别得到什么？

1. 假设普通构造函数先设置 this.name，再返回 null，得到的仍然是带 name 的新实例。原因是 null 虽然经过 typeof 会显示 object，但在构造返回值规则中不属于对象，手写判断必须把它排除。

2. 如果改成返回一个带 code 的普通对象，调用者拿到的就是这个对象，先前在 this 上初始化的 name 不会自动合并过去。返回对象也不必继承该构造函数的原型，因此不能保证 instanceof 仍然成立。

3. 如果返回的是函数，也应该采用这个返回值，因为函数同样属于对象。验证简化实现时，我会分别覆盖无返回值、原始值、对象和函数四种情况，并明确这些结论针对普通基础构造函数，不能直接套到派生类上。

## 追问：为什么 Object.create 加 apply 不能完整替代 new？

1. Object.create 只负责创建对象并设置原型，既不会执行构造函数，也不会初始化类的私有字段。即使生成的对象能沿原型找到类方法，调用涉及私有字段的方法仍可能报错，说明原型相同不代表初始化已经完成。

2. apply 走的是普通调用，而 class 构造函数必须通过构造调用进入，所以直接套这个步骤就会抛错。构造函数中的 new.target 也能区分这两种调用，简化实现不能仅靠替换 this 就伪装出完整语义。

3. 如果只是面试展示，我会先说明支持普通函数这个前提，再解释它遗漏了哪些能力。实际需要调用 class 或内置构造器时，可以使用 Reflect.construct，让语言执行构造流程，同时仍需确认传入目标确实可以被构造。
