# 为什么不能只写一个 z-index？

## 核心回答

1. `z-index` 只参与视觉层叠，数值再大，页面行为也不会变成模态。半透明遮罩能挡住鼠标点击，键盘仍可能跳到背景按钮，读屏也可能读到背景内容。看起来盖住了，和实际不能操作，是两件事。

2. 它甚至保证不了弹窗一定显示在所有元素之上，比较还受层叠上下文限制。父元素设了 `transform`，里面的弹窗就可能被另一组内容盖住。先查祖先元素，再决定要不要把弹窗挂到独立容器。

3. 焦点要单独管。打开时进入弹窗，Tab 和反向 Tab 不该跑到背景，关闭后回到合理位置。否则人看见弹窗，键盘操作的位置却还在原页面。长表单里尤其容易不知道自己当前选中了什么。

4. 语义和背景隔离也要补。自定义弹窗需要对话框角色、可访问名称、正确的模态声明。`aria-modal` 本身不会做焦点限制，背景通常还需要 `inert` 这类实际隔离。别把包含弹窗的祖先一起禁用，弹窗自己也操作不了。

5. 还有滚动和清理：背景滚动锁、移动端软键盘遮挡、嵌套弹窗关闭顺序。原生 `dialog` 的 `showModal` 能提供顶层显示和背景惰性，但关闭策略、内容布局、状态恢复还是应用自己定。一个 CSS 属性替不了这些。

## 追问：把弹窗挂到 body 下，就解决所有层级问题了吗？

1. 挂到 `body` 下通常能避开业务容器里的 `overflow` 裁剪，以及部分层叠上下文限制，布局上有用。但它仍在普通文档的层叠体系里，靠把 `z-index` 加大，盖不过浏览器顶层里的模态 `dialog`。

2. 挂载位置变了，依赖父元素的样式、主题变量、定位参照还要查。弹窗原本继承了局部容器的颜色变量，移出去可能丢样式。给弹层容器明确的样式来源，别只检查是不是置顶。

3. Portal 一类机制主要改 DOM 放哪，无障碍行为不会自动有。焦点恢复、背景隔离、关闭事件还是要统一处理。同页有多种弹层，层级约定也说清，别各组件自己去抢最大数值。

## 追问：嵌套两个弹窗时，滚动锁和 Escape 应怎么处理？

1. 记下当前弹窗栈，最上层弹窗接收关闭请求和焦点操作。按一次 Escape 只关最上层。别让多个全局监听器同时响应，把确认框和下面正在编辑的表单一起关掉。

2. 页面滚动锁按仍然打开的模态层数量来管。关上上层，不能马上恢复背景滚动。最后一个弹窗关了，才恢复进入前的样式和滚动位置。恢复的是保存的原值，别假定原来一定允许滚动。

3. 关上上层后，焦点回到下层里打开它的那个按钮，下层此时仍然限制背景交互。页面卸载或异常关闭，监听要摘掉，对应状态要释放。验的时候覆盖连续打开、逆序关闭、触发按钮消失这些情况。
