# 为什么不能只写一个 z-index？

## 核心回答

1. z-index 只参与视觉层叠，数值再大也不代表页面行为变成了模态。一个半透明遮罩能挡住鼠标点击，键盘仍可能跳到背景按钮，读屏器也可能读到背景内容，所以看起来盖住和实际不能操作是两件事。

2. 它甚至不能保证弹窗一定显示在所有元素之上，因为比较还受层叠上下文限制。比如父元素设置了 transform，里面的弹窗就可能被另一组内容盖住；我会先检查祖先元素，再决定是否把弹窗挂到独立容器。

3. 焦点需要单独管理，打开时进入弹窗，Tab 和反向 Tab 不应跑到背景，关闭后回到合理位置。否则用户虽然看见弹窗，键盘操作的位置却还在原页面，尤其在长表单里很容易不知道自己当前选中了什么。

4. 语义和背景隔离也要补齐，自定义弹窗需要对话框角色、可访问名称和正确的模态声明。aria-modal 本身不会实现焦点限制，背景通常还需要 inert 等实际隔离手段；不能把包含弹窗的祖先一起禁用，导致弹窗也无法操作。

5. 最后还有滚动和清理问题，例如背景滚动锁、移动端软键盘遮挡、嵌套弹窗关闭顺序。原生 dialog 的 showModal 能提供顶层显示和背景惰性行为，但应用仍需定义关闭策略、内容布局和状态恢复，不能用一个 CSS 属性代替这些工作。

## 追问：把弹窗挂到 body 下，就解决所有层级问题了吗？

1. 挂到 body 下通常能避开业务容器中的 overflow 裁剪和部分层叠上下文限制，这是有用的布局手段。但它仍处于普通文档的层叠体系里，不能靠增大 z-index 覆盖浏览器顶层中的模态 dialog。

2. 挂载位置变化后，还要检查依赖父元素的样式、主题变量和定位参照。比如弹窗原本继承了局部容器的颜色变量，移出去后可能丢失样式；因此我会给弹层容器明确的样式来源，而不只检查是否置顶。

3. Portal 一类机制主要改变 DOM 放置位置，并不自动实现无障碍行为。焦点恢复、背景隔离和关闭事件仍需统一处理；如果同页存在多种弹层，还应明确它们的层级约定，避免各组件自行争抢最大数值。

## 追问：嵌套两个弹窗时，滚动锁和 Escape 应怎么处理？

1. 我会记录当前弹窗栈，让最上层弹窗接收关闭请求和焦点操作。按一次 Escape 只关闭最上层，不能让多个全局监听器同时响应，把确认框和下面正在编辑的表单一起关掉。

2. 页面滚动锁按仍然打开的模态层数量管理，关闭上层时不能马上恢复背景滚动。最后一个弹窗关闭后，才恢复进入前的样式和滚动位置；恢复的是保存的原值，而不是假定原来一定允许滚动。

3. 关闭上层后，焦点应回到下层里打开它的按钮，下层此时仍然限制背景交互。页面卸载或异常关闭也要移除监听并释放对应状态，验证时我会覆盖连续打开、逆序关闭和触发按钮消失这些情况。
