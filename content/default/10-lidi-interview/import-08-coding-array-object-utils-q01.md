# 为什么不全用 reduce？

## 核心回答

1. 不排斥 reduce，求和、统计数量这种「把多个元素攒成一个结果」的活很适合它。比如下面明确给初始值，空数组也有结果；要转换每个元素或筛条件，用 map、filter 往往更直接，没必要为了写法统一全换成 reduce。

   ```js
   const sum = numbers.reduce((total, value) => total + value, 0);
   ```

2. 有早停需求时，更倾向 find、some 或循环。比如找到第一个不合法的表单字段就返回，reduce 没有正常的 break。虽然能用状态跳过后面的逻辑，回调还是会继续跑，真正的停止条件也更难看出来。

3. 累计器每轮是不是在复制，得看清楚，比如不断用展开语法造新数组。第几轮就复制此前多少元素，总复制量可能变成平方级。函数内部往新建数组 push，并不等于改了调用方输入，没必要为表面的不可变付这种成本。

4. 异步 reduce 还容易让人误会执行顺序，数组遍历本身不会等 async 回调做完。确实可以显式串接 Promise 做成串行，但普通 for...of 加 await 更好讲；要并发或限流，就直接把对应调度规则写出来。

5. 空数组、稀疏数组和初始值约定都得对一下，不能只验证一个正常例子。原生 reduce 会跳过不存在的索引，没给初始值又没有可用元素时会抛错。教学循环要是没处理这些差异，就不能说和原生完全等价。

## 追问：循环里 push 结果，算不算破坏不可变性？

1. 看改的是谁拥有的数据。函数内部刚创建的结果数组还没交给调用方，往里面 push 不会改输入数组。结果产生后按约定用，这种写法通常比每轮复制整个累计器更简单，分配量也好控。

2. 但如果把传入的数组直接当累计器，或者取出输入对象后改它的属性，就可能影响外面。浅拷贝只复制外层容器，内部对象还是共享的，所以即使用展开语法返回新数组，也不能自动证明原始对象没被改。

3. 测试里留住输入的内容和引用关系，调用后再看它们是否符合约定，再看输出顺序和值。要不要深拷贝，取决于调用方会不会改结果对象。别为了说自己用了不可变写法，就默认递归复制所有数据、多出一截开销。

## 追问：用 async 回调写 reduce，会自动串行请求吗？

1. 不会自动串行。reduce 仍然同步调回调，返回值只是在后续迭代里变成累计器。只有每轮先等上一轮 Promise，再启动当前请求，依赖才建得起来；如果先调请求再 await 累计器，前面的等待也挡不住请求提前发出。

2. 更愿意用下面的循环直接表示顺序执行，前一个失败时立刻离开循环，不再发后一个。这是普通异步业务代码，不是 reduce 的实现，也没有同时启动多个任务的能力，吞吐就取决于任务一个个做完。

   ```js
   const results = [];
   for (const item of items) {
     results.push(await request(item));
   }
   ```

3. 任务彼此独立，才考虑并发；服务有并发约束，就交给接收任务函数的并发池。先说清楚要保序的是启动顺序、完成顺序还是结果顺序，因为结果按输入排，并不要求请求一定串行。
