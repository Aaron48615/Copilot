# 为什么不全用 reduce？

## 核心回答

1. 我不会排斥 reduce，求和、统计数量这类“把多个元素累计成一个结果”的任务很适合它。比如下面明确给出初始值，空数组也有结果；如果转换每个元素或筛选条件，用 map、filter 往往更直接，不必为了统一写法都换成 reduce。

   ```js
   const sum = numbers.reduce((total, value) => total + value, 0);
   ```

2. 有早停需求时，我更倾向于 find、some 或循环。比如找到第一个不合法的表单字段就返回，reduce 没有正常的 break 机制，虽然能用状态跳过后续逻辑，但回调仍会继续执行，也更难看出真正的停止条件。

3. 我会特别注意累计器是否在每轮复制，例如不断写展开语法创建新数组。若第几轮就复制此前多少元素，总复制量可能变成平方级；在函数内部往新建数组 push 并不等于修改了调用方输入，没必要为表面的不可变付出这种成本。

4. 异步 reduce 还容易让人误解执行顺序，数组遍历本身不会等待 async 回调完成。确实可以显式串接 Promise 实现串行，但普通 for...of 加 await 更容易解释；要并发或限流时，应直接表达对应调度规则。

5. 最后我会核对空数组、稀疏数组和初始值约定，不能只验证一个正常示例。原生 reduce 会跳过未存在的索引，未提供初始值且没有可用元素时会抛错；教学循环若没有处理这些差异，就不能说是完全等价的原生实现。

## 追问：循环里 push 结果，算不算破坏不可变性？

1. 要看改的是谁拥有的数据。函数内部刚创建的结果数组还没有暴露给调用方，往里面 push 不会修改输入数组；只要结果产生后按约定使用，这种写法通常比每轮复制整个累计器更简单，也更容易控制分配量。

2. 但如果把传入的数组直接当累计器，或者取出输入对象后修改它的属性，就可能影响外部状态。浅拷贝只复制外层容器，内部对象仍然共享，所以即使用展开语法返回新数组，也不能自动证明原始对象没有被改变。

3. 我会用测试保留输入的内容和引用关系，调用后检查它们是否符合约定，再检查输出顺序和值。是否需要深拷贝取决于调用方会不会修改结果对象，不能为了说自己用了不可变写法，就默认递归复制所有数据并增加额外开销。

## 追问：用 async 回调写 reduce，会自动串行请求吗？

1. 不会自动串行，reduce 仍然同步调用回调，返回值只是在后续迭代里成为累计器。只有每轮先等待上一轮 Promise，再启动当前请求，才能建立依赖；如果先调用请求再 await 累计器，前面的等待也挡不住请求提前发出。

2. 我更愿意用下面的循环直接表示顺序执行，前一个失败时会立即离开循环，不再发起后一个。这是普通异步业务代码，不是 reduce 的实现，也没有同时启动多个任务的能力，所以它的吞吐取决于任务逐个完成。

   ```js
   const results = [];
   for (const item of items) {
     results.push(await request(item));
   }
   ```

3. 如果任务彼此独立，才考虑并发执行；如果服务有并发约束，就交给接收任务函数的并发池。面试时我会先说明需要保序的是启动顺序、完成顺序还是结果顺序，因为结果按输入排列并不要求请求一定串行。
