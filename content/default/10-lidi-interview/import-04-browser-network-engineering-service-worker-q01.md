# 新 Service Worker 为什么不立即生效？

## 核心回答

1. 新 Service Worker 不立即接管通常是生命周期的正常设计。浏览器发现脚本更新后会安装新 worker，但旧 worker 仍控制着打开的页面时，新版本通常进入 waiting，让现有页面有机会继续使用原来匹配的缓存和代码。

2. 安装阶段常通过 waitUntil 等待必要资源准备好，安装失败时不应把不完整的新版本替换上去。页面刷新也不一定结束旧客户端的使用关系，尤其还有其他标签页时，所以看到 waiting 不能直接认定更新脚本坏了。

3. skipWaiting 可以让等待中的新 worker 尝试更早进入激活，clients.claim 可以在激活后接管符合范围的客户端，两者职责不同。强行组合使用会让旧页面代码遇到新请求策略，必须考虑接口与资源版本是否兼容。

4. 我会更倾向于发现更新后提示用户，在允许刷新时切换，并保护正在编辑的内容。激活阶段清理缓存也要谨慎，旧标签可能还需要旧资源；不能为了让新版本看起来马上生效就一次删掉所有历史缓存。

5. 验证需要同时打开两个标签页，覆盖安装失败、等待、接受更新和离线状态。Service Worker 的更新不是普通脚本替换，只有页面、worker、缓存和服务端资源的组合都能正常工作，才算真正完成了升级。

## 追问：skipWaiting 和 clients.claim 有什么区别？

1. skipWaiting 处理的是新 worker 的等待阶段，让它不用一直等旧客户端全部离开才尝试激活。clients.claim 则是在 worker 激活后，让它接管自己作用范围内原本未受其控制的客户端，两个调用不是互相替代。

2. 它们也不会自动把页面已经执行的 JavaScript 换成新版。旧页面仍可能持有旧模块和内存状态，只是后续请求由新 worker 处理，因此接管不等于整页更新，版本兼容问题仍然存在。

3. 我会按需要设计更新提示和刷新时机，监听控制者变化时避免重复刷新。测试旧页面操作、懒加载和新页面打开三种情形，确认没有出现循环刷新或新 worker 删除了旧页面仍需要的资源。

## 追问：用户正在填写表单，怎样安排 worker 更新？

1. 我会让新 worker 先等待，并在页面提示有新版本可用，不立即刷新打断输入。页面需要知道当前是否有未保存内容，用户可以完成保存后再更新，或者明确选择暂时继续使用当前版本。

2. 接受更新时可以先保存必要草稿，再通知新 worker 激活，并在合适的控制者变化后刷新。保存步骤必须确认成功，不能只调用一个异步写入就立刻跳走，否则所谓保护草稿可能并没有真正完成。

3. 服务端仍应保留旧资源和必要接口兼容，允许延迟更新的页面继续工作。如果新版本涉及必须立即停止的旧功能，需要单独设计说明和恢复流程，不能把普通静默更新机制当成所有业务情况的统一答案。
