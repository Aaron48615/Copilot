# 新 Service Worker 为什么不立即生效？

## 核心回答

1. 新 Service Worker 不马上接管，常常是生命周期的正常设计。浏览器发现脚本更新会安装新 worker，但旧 worker 还控制着打开的页面时，新版本通常进 waiting。现有页面还能继续用原来匹配的缓存和代码。

2. 安装阶段常用 `waitUntil` 等必要资源准备好。安装失败，不完整的新版本不该替上去。刷新页面也不一定结束旧客户端的使用关系，尤其还有别的标签页。看到 waiting，不能直接认定更新脚本坏了。

3. `skipWaiting` 让等待中的新 worker 尝试更早进入激活，`clients.claim` 是激活后再接管符合范围的客户端，两件事职责不同。硬组合使用，旧页面代码可能碰上新请求策略。接口和资源版本兼不兼容，要一起考虑。

4. 更稳的是发现更新后提示用户，允许刷新时再切，正在编辑的内容要保护。激活阶段清缓存也要谨慎，旧标签可能还需要旧资源。为了让新版本看起来马上生效，一次删掉所有历史缓存，旧页面会出事。

5. 验证要同时开两个标签页，覆盖安装失败、等待、接受更新、离线。Service Worker 的更新不是普通脚本替换。页面、worker、缓存、服务端资源这几边都能正常工作，才算升级完成。

## 追问：skipWaiting 和 clients.claim 有什么区别？

1. `skipWaiting` 处理的是新 worker 的等待阶段，让它不用一直等旧客户端全部离开才尝试激活。`clients.claim` 则是 worker 激活之后，接管作用范围内原本还没受它控制的客户端。两个调用不能互相替代。

2. 它们也不会自动把页面已经执行的 JavaScript 换成新版。旧页面仍可能握着旧模块和内存状态，只是后续请求由新 worker 处理。接管不等于整页更新，版本兼容问题还在。

3. 更新提示和刷新时机按需要设计，监听控制者变化时避免重复刷新。测旧页面操作、懒加载、新页面打开这三种情形，确认没有循环刷新，也没有新 worker 删掉旧页面还需要的资源。

## 追问：用户正在填写表单，怎样安排 worker 更新？

1. 新 worker 先等待，页面提示有新版本可用，不立刻刷新打断输入。页面要知道当前有没有未保存内容。用户可以先保存再更新，也可以明确选择暂时继续用当前版本。

2. 接受更新时可以先存必要草稿，再通知新 worker 激活，在合适的控制者变化后刷新。保存步骤必须确认成功。只调用一个异步写入就立刻跳走，所谓保护草稿可能根本没写完。

3. 服务端仍保留旧资源和必要接口兼容，延迟更新的页面还能继续工作。新版本涉及必须马上停掉的旧功能，要单独做说明和恢复。普通静默更新机制，套不到所有业务情况上。
