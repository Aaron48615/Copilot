# 为什么用 sessionStorage 传购物车到订单确认页？

## 核心回答

1. 购物车和详情页去确认订单时，需要带上本次购买意图。购物车入口主要是 basketIds 与地址 ID，立即购买还有商品、SKU、数量和店铺，把这些对象都放进 URL 会比较零散，项目用 confirmOrder 暂存更直接。

2. sessionStorage 按来源与标签页会话划分，当前标签页刷新后仍能读取，适合确认页中途刷新或去选择地址再返回。它不是长期订单存储，也不是绝对跨标签共享；带 opener 打开的页面可能初始复制，但后续并不持续同步。

3. 写入时将对象序列化，确认页读取并解析，再重新请求地址和订单确认金额。没有参数时提示重新选择并回购物车，不能靠空对象继续提交；格式损坏或字段类型不对也需要安全处理，JSON.parse 本身不会检查业务结构。

4. 创建成功并拿到订单号后删除 confirmOrder，之后支付围绕已存在的订单进行。用户取消付款不等于撤销创建订单，因此不能因为取消弹窗就恢复旧草稿再创建一单，清理时机要与业务阶段一致。

5. 存储内容可以被修改或过期，所以后端仍要检查购物车与地址归属、规格、数量和金额。更复杂时可用 Store 配合持久化或服务端草稿，但换保存位置不会消除这些检查；sessionStorage 只是当前规模下的恢复方式。

## 追问：用户直接打开确认页，没带任何数据怎么办？

1. 确认页应该识别缺少购买意图，说明需要重新选择商品，再提供回购物车或浏览入口。不能默认购买列表里的第一件商品，也不能凭上一次缓存的商品对象猜用户这次想买什么。

2. 如果键存在但解析失败，或只有 basketIds 字段没有有效 ID，也应当按无效草稿处理。读取时需要捕获异常并检查必要字段，避免一个损坏字符串让整个页面崩溃，错误恢复应让用户重新开始而不是卡住。

3. 测试空存储、损坏 JSON、空数组与过期商品，检查不会发送不完整提交请求。可以清除这个无效键，但不要清空全部 sessionStorage，其他页面可能还有无关状态，处理范围应限制在本次下单数据。

## 追问：为什么不能把订单总价一并缓存后直接使用？

1. 可以保存用于临时展示，但不能作为确认结果。用户离开去选地址期间，运费、优惠或商品可售性可能变化，返回后继续用旧总价会让页面显示的购买条件与后端实际条件不一致。

2. 当前确认页会读取地址后重新请求金额，服务端根据标识恢复真实商品。即使用户手动把缓存金额改成一元，也不应影响最终订单价格，前端缓存只记录选择，不具备定价权限。

3. 如果以后要支持保价或锁价，需要服务端报价标识与有效期，再在提交时验证。存储里一个数字既没有可信来源证明，也没有锁定语义，不能因为刷新后还在就把它当成永久有效报价。
