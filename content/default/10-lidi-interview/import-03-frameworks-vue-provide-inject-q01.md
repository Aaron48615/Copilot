# 注入值为什么有时不更新？

## 核心回答

1. 注入值不更新时，我会先看提供出去的到底是响应式对象还是当时的普通值。比如 provide 一个 count.value，只传出了那个数字，后续 ref 改变不会让已经注入的数字自动变化；应该提供 ref 本身，让双方保留同一响应式连接。

2. 提供 reactive 对象时，后代通过对象访问属性可以跟踪变化，但如果把原始值属性解构为普通变量，再拿它渲染，就可能失去关联。可以保持对象访问，或通过 toRef、toRefs 建立字段引用，不能把“注入成功”与“任何使用方式都响应式”混为一谈。

3. 另一个问题是提供者重新赋值给局部变量。后代拿到的是之前提供的对象，局部变量改指向不会自动让注入重新执行；需要整体替换时，用 ref 包住对象，再更新 value，消费者继续通过同一个 ref 读取当前内容。

4. 我还会检查是否被更近的祖先同名 provide 覆盖，或者 inject 使用默认值掩盖了提供者缺失。大型组件组合更适合使用统一导出的 Symbol key，类型也保持一致，避免两边字符串相同却实际上来自不同环境的误会。

5. 修复时应保持修改责任清楚，提供者可以暴露只读状态与更新方法。后代通过动作更新，由提供者统一校验；测试既确认视图跟随变化，也确认缺少提供者时有明确反馈，不能只用深度 watch 反复复制来补一个本来断开的引用。

## 追问：提供 ref 和提供 ref.value，消费者拿到的有什么不同？

1. 提供 ref 保留了带 value 的响应式容器，消费者读取它时能与后续替换关联。提供 ref.value 则取出当前内容；若是数字就只是一次普通值传递，之后容器变成另一个数字，消费者不会凭空获得通知。

2. 如果 value 本身是响应式对象，提供它仍可能跟踪内部字段修改，但当提供者整体替换 value，消费者仍持有旧对象。这个细节容易导致“改字段能更新，重新加载整个对象就不更新”的表现，需要根据替换需求选择提供形式。

3. 我会在接口中明确注入的是 Ref、只读对象还是普通服务，避免调用方凭经验猜测是否要写 value。测试分别修改内部字段和替换整体对象，能够更直接验证响应式连接是否符合设计。

## 追问：inject 有默认值，为什么有时会掩盖错误？

1. 若某依赖实际必需，默认空对象会让组件继续运行，但调用更新方法或渲染字段时才出现更远的错误。缺少 Provider 的根因被隐藏，调试者看到的只是某个方法不存在，而不知道组件的使用环境不完整。

2. 必需依赖可以封装一个读取函数，注入失败时给出明确开发错误；可选依赖再设计有意义的默认行为，例如没有上层尺寸设置时使用普通尺寸。默认值应符合产品语义，不只是为了让类型检查暂时通过。

3. 测试要分别覆盖提供者存在和缺失，并确认嵌套提供者选择最近值。这样组件单独用于文档展示或测试时，需要什么环境一目了然，也不会因悄悄落到默认状态而误以为集成已经正确。
