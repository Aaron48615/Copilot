# HTTP/1.1、HTTP/2 和 HTTP/3 有什么差别？

## 核心回答

1. HTTP/1.1 支持持久连接，多个请求可以复用连接，但浏览器通常还是要多条连接来提高并发，管线化也没有普遍解决实际等待问题。所以加载很多小资源时，会产生连接管理和排队成本。持久连接不等于多路复用。

2. HTTP/2 用二进制帧和流，在一条连接里交错处理多个请求，并用 HPACK 压缩头部。它减少了不少重复连接开销，但底层还是 TCP。丢失的字节需要补齐后才能继续有序交付，多个流可能一起受影响。

3. HTTP/3 把 HTTP 映射到 QUIC。QUIC 跑在 UDP 上，同时提供可靠传输和 TLS 1.3 安全能力。不同流可以独立交付数据，减少 TCP 层跨流等待。但同一条流内部仍有顺序要求，带宽和拥塞控制也仍然共享。

4. 这会改前端优化思路。过去为 HTTP/1.1 做的大量域名分片，在 HTTP/2 下未必值得留。不过请求并非免费，资源过碎、优先级不合理、重复下载仍有成本。支持多路复用，不等于把所有资源同时预加载。

5. 从 Network 看真实协议，再结合首屏和错误数据判断效果。协议由浏览器与服务端共同协商，HTTP/3 还受网络支持限制。接口处理慢，或大脚本把主线程卡住，单独升级协议解决不了整个页面的性能问题。

## 追问：HTTP/2 头部压缩和 gzip 是一回事吗？

1. 不是。HTTP/2 的 HPACK 处理请求和响应头里的重复字段，比如多次请求重复带着的头信息。gzip、Brotli 这些常用于响应体内容压缩，目标可能是 HTML、CSS 或 JavaScript。两者作用位置不同。

2. 开了 HTTP/2，不代表脚本内容已经被压缩，还要看 `Content-Encoding` 和实际传输大小。反过来，HTTP/1.1 也能传 gzip 压缩的响应体。看见文件下载很小，推断不成一定用了新协议。

3. 分别验证协议、响应头和传输体积，并注意压缩对缓存表示的影响。已经压缩的图片或视频，再压未必更有收益。优化按资源类型判断，别把所有内容机械套同一种处理。还要比较压缩所需的服务端计算成本，确认传输上省下来的量值得这笔额外处理。

## 追问：为什么多路复用后还要合并或拆分资源？

1. 多路复用主要减少连接和传输排队问题，取消不了模块解析、执行和缓存管理成本。一个大文件可能让用户下载很多暂时用不到的代码；很多极小文件又可能增加发现依赖和请求处理的开销。所以还是要平衡。

2. 按使用时机拆分。比如不在首屏的复杂编辑器，放到进入编辑功能时再加载，同时保留合理共享依赖。别为了减少文件数把所有页面都合成一个包，也别为了追求 chunk 多而把简单模块拆得过碎。

3. 判断时看首屏下载和执行量、后续切换延迟，以及缓存复用。协议改变后，旧的拆分经验可能要调。真正目标仍是用户更早看到并操作所需内容，不是让构建报告里的某个数字单独变好。
