# HTTP/1.1、HTTP/2 和 HTTP/3 有什么差别？

## 核心回答

1. HTTP/1.1 支持持久连接，多个请求可以复用连接，但浏览器通常需要多条连接提高并发，管线化也没有普遍解决实际等待问题。因此加载很多小资源时，会产生连接管理和排队成本，不能把持久连接等同于多路复用。

2. HTTP/2 用二进制帧和流在一条连接中交错处理多个请求，并通过 HPACK 压缩头部。它减少了不少重复连接开销，但底层还是 TCP，丢失的字节需要补齐后才能继续有序交付，多个流可能一起受到影响。

3. HTTP/3 把 HTTP 映射到 QUIC，后者运行在 UDP 之上并提供可靠传输和 TLS 1.3 安全能力。不同流可以独立交付数据，减少 TCP 层跨流等待，但同一条流内部仍有顺序要求，也仍然共享带宽与拥塞控制。

4. 这会影响前端优化思路，例如过去为 HTTP/1.1 做的大量域名分片，在 HTTP/2 下未必值得保留。不过请求并非免费，资源过碎、优先级不合理和重复下载仍有成本，不能因为支持多路复用就把所有资源同时预加载。

5. 我会从 Network 查看真实协议，再结合首屏和错误数据判断效果。协议由浏览器与服务端共同协商，HTTP/3 还受网络支持限制；接口处理慢或大脚本执行卡顿时，单独升级协议不能解决整个页面的性能问题。

## 追问：HTTP/2 头部压缩和 gzip 是一回事吗？

1. 不是。HTTP/2 的 HPACK 处理请求和响应头里的重复字段，例如多次请求重复携带的头信息；gzip、Brotli 等常用于响应体内容压缩，目标可能是 HTML、CSS 或 JavaScript，两者作用位置不同。

2. 开启 HTTP/2 不代表脚本内容已经被压缩，仍要检查 Content-Encoding 和实际传输大小。反过来，HTTP/1.1 也能传输 gzip 压缩的响应体，不能看到文件下载很小就推断一定使用了新协议。

3. 我会分别验证协议、响应头和传输体积，并注意压缩对缓存表示的影响。已经压缩的图片或视频未必再压就更有收益，优化要按资源类型判断，而不是把所有内容机械套同一种处理。还要比较压缩所需的服务端计算成本，确认传输节省值得额外处理。

## 追问：为什么多路复用后还要合并或拆分资源？

1. 多路复用主要减少连接与传输排队问题，不取消模块解析、执行及缓存管理成本。一个大文件可能让用户下载很多暂时用不到的代码，很多极小文件又可能增加发现依赖和请求处理的开销，所以仍要平衡。

2. 我会按使用时机拆分，例如把不在首屏的复杂编辑器放到进入编辑功能时加载，同时保留合理共享依赖。不会为了减少文件数把所有页面都合成一个包，也不会为了追求 chunk 多而把简单模块拆得过碎。

3. 判断时看首屏下载和执行量、后续切换延迟以及缓存复用。协议改变后旧的拆分经验可能需要调整，但真正目标仍是用户更早看到并操作所需内容，而不是让构建报告中的某个数字单独变好。
