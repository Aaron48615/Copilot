# 拿智能导购举例，你能讲清哪部分？

## 核心回答

1. 轻购智能导购，能讲清的是用户输入怎么变成前端请求，接口结果怎么呈现在页面上。能顺着代码讲前端怎么调 `/guide/recommend`。从页面效果反推后端一定用了哪种模型、哪种匹配算法，做不到。

2. 可以从 `GuideView.vue` 的提交动作讲到 `getGuideRecommendations`，再到 `GuideResult` 里的意图、商品和条件信息。每一步依赖什么数据，接口没返回结果时页面该停在哪个状态，都能对上。

3. 展示层要把 `matched`、`unmatched` 和 `relaxedConstraints` 分开。用户提了预算和降噪，就按约定展示满足情况和放宽条件。「没有降噪信息」不能加工成「已经证实支持降噪」这种推荐文案。

4. 商品卡片要用接口给的有效商品标识进详情，一段自然语言理由替不了商城商品数据。价格、属性、推荐依据从哪来，得能追溯。服务端给的信息不一致，就定位、反馈，别在前端猜一个结果。

5. 负责的是前端接入、展示和异常处理。模型怎么抽条件、服务端怎么查库和排序，是后端实现。推荐内容和约定对不上，就把这次输入、返回字段、预期结果整理清楚，方便前后端判断问题出在哪。

## 追问：推荐商品超预算时，你先看前端还是后端？

1. 先看这次请求和响应：用户输入有没有正确发出去，页面用的是不是这次返回的数据。旧请求盖住新结果，或者前端读错价格字段，推荐接口本身对，页面也可能显示成超预算。

2. 响应里的商品确实超预算，再看接口有没有明确返回预算放宽信息，业务允不允许这样推。前端漏了提示是展示问题，服务端违反了严格预算约定是接口问题。别不分原因就把商品滤掉。

3. 只有接口访问权限，就把输入、实际响应、预期规则整理给后端定位。别声称已经找到排序算法的错。临时在前端处理，也要说清适用范围，不然可能把接口问题藏起来，后面测试还以为原规则是对的。

## 追问：前端怎样避免把推荐理由显示得过于确定？

1. 接口确认过的信息和未知信息分开说。「符合预算」和「续航资料待确认」不要用同样的肯定语气。理由写得流畅，不代表有商品参数撑着。页面渲染时别额外补出商品能力。

2. 放宽条件的提示要跟对应结果一起出现，别让用户只看到商品卡片，漏掉原需求已经改过这个事实。接口信息不够、说不清放宽了什么，就补约定。前端别靠文案猜服务端意图。

3. 后面要补的话，用固定响应检查未知、部分满足、条件放宽三种展示，再验详情入口。这能验页面是不是忠实表达了响应。商品资料真不真、推荐排序合不合理，还得另有业务证据。
