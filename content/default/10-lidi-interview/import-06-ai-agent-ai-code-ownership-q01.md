# 拿智能导购举例，你能讲清哪部分？

## 核心回答

1. 拿轻购智能导购来说，我能讲清的是用户输入如何变成前端请求，以及接口结果怎样呈现在页面上。我能沿着代码解释前端调用 `/guide/recommend` 的流程，不能从页面效果反推出后端一定用了哪种模型或匹配算法。

2. 具体可以从 `GuideView.vue` 的提交动作讲到 `getGuideRecommendations`，再到 `GuideResult` 里的意图、商品和条件信息。这样能说明每一步依赖什么数据，接口没有返回结果时页面又应当停在哪个状态。

3. 展示层的关键是区分 `matched`、`unmatched` 和 `relaxedConstraints`。例如用户提出预算和降噪要求，我要按约定展示满足情况与放宽条件，不能把“没有降噪信息”加工成“已经证实支持降噪”的推荐文案。

4. 商品卡片还需要使用接口提供的有效商品标识进入详情，不能让一段自然语言理由代替商城商品数据。价格、属性与推荐依据来自哪里应当能追溯；如果服务端给的信息不一致，我会定位并反馈，而不是在前端猜一个结果。

5. 我负责的是前端接入、展示与异常处理，模型如何提取条件、服务端怎样查库和排序属于后端实现。遇到推荐内容与约定不一致时，我会先把具体输入、返回字段和预期结果整理清楚，方便前后端判断问题出在哪里。

## 追问：推荐商品超预算时，你先看前端还是后端？

1. 我会先看这次请求和响应，确认用户输入有没有正确发送、页面是否用了本次返回的数据。如果是旧请求覆盖新结果，或者前端读错价格字段，即使推荐接口本身正确，也可能显示成超预算。

2. 如果响应里的商品确实超预算，再看接口是否明确返回预算放宽信息，以及业务是否允许这样推荐。前端漏掉提示是展示问题，服务端违反严格预算约定是接口问题，不能不分原因地直接过滤掉商品。

3. 若只有接口访问权限，我会整理输入、实际响应和预期规则供后端定位，不会声称已经找到了排序算法的错误。临时前端处理也要说明适用范围，否则可能隐藏接口问题，让后续测试误以为原规则正确。

## 追问：前端怎样避免把推荐理由显示得过于确定？

1. 我会把接口确认的信息与未知信息分开表达，例如“符合预算”和“续航资料待确认”不使用同样的肯定语气。理由写得流畅不代表有商品参数支持，页面不应该在渲染时额外补出商品能力。

2. 对放宽条件，我会让提示与对应结果一起出现，避免用户只看到商品卡片，漏掉原需求已经改变的事实。若接口没有足够信息说明放宽了什么，就需要补约定，前端不能靠文案猜测服务端意图。

3. 如果继续完善，我会用固定响应检查未知、部分满足和条件放宽三种展示，并验证详情入口。这样能验证页面是否忠实表达响应，但商品资料是否真实、推荐排序是否合理，仍需要另外的业务证据。
