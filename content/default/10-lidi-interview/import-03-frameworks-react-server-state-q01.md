# 为什么派生数据不再存一份？

## 核心回答

1. 派生数据是能从现有数据和条件算出的结果，例如商品总价、筛选列表和已选数量。把它再保存成独立 state，就多出一份需要同步的值，任何一次原始数据更新都要记得更新所有副本，遗漏后界面就会自相矛盾。

2. 例如商品数量改变后，购物车明细已经显示三件，总价却还按两件计算。如果总价直接由明细推导，同一次渲染使用的就是同一份输入；如果用 Effect 更新总价，还会先经过一次显示旧总价的渲染。

3. 我会保存最少的事实来源，比如商品数据和选择编号，其他内容在渲染中或 selector 中计算。计算确实昂贵时再用 useMemo 等缓存，依赖包含所有输入；缓存是减少重复工作，不是让派生结果变成另一份可以独立修改的事实。

4. 需要区分真正派生值和有业务意义的快照。订单成交价格、提交时的筛选条件或用户尚未保存的草稿，可能应保持某个时刻的内容，不能随原始数据继续改变；它们需要明确名称和创建时机，不能一概删除。

5. 判断时我会问“原始数据相同，结果是否必然相同”。若答案是肯定的，通常可以直接计算；如果依赖服务端优惠规则、实时库存或独立确认流程，就不能只靠前端推导替代服务端结果，尤其要区分展示估算和最终确认数据。

## 追问：筛选结果很大，直接每次算不是很慢吗？

1. 可以缓存计算，但先确认瓶颈确实在筛选，而不是列表节点太多。useMemo 以原始数组和筛选条件为依赖，输入不变时复用结果，既避免重复过滤，也没有额外增加一条必须手动同步的 state 更新路径。

2. 如果数组每次都被无意义地重新创建，缓存可能频繁失效，需要回到数据来源检查引用。筛选本身改变时仍必须重新算，缓存不会让所有输入变化都免费，大规模数据还可能需要分页或服务端筛选。

3. 我会用真实数据量比较计算耗时，并检查输入体验。必要时把非紧急列表更新延后，或优化算法，但不能为了保持缓存而漏掉筛选依赖，否则性能看似好了，显示的却是上一组条件的结果。

## 追问：编辑表单为什么可以复制一份接口数据？

1. 编辑草稿有独立含义，它允许用户暂时修改而不立即影响已保存数据，因此不只是重复缓存。页面应该能区分服务端当前值和用户草稿，提供保存、取消以及是否已修改的反馈，而不是自动互相覆盖。

2. 初始化通常发生在第一次进入编辑或切换记录时，后台刷新不应无条件重置草稿。若服务器内容已经变化，可以提醒用户重新载入或处理冲突，避免他填写了很久却被一次静默刷新清空。

3. 提交成功后再使用服务端确认的结果更新缓存，并决定是否重新初始化草稿。这样复制有明确的生命周期和用途，与为了显示总价而额外维护一个随时可能过期的 state，是不同的数据设计问题。
