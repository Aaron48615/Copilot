# finally 适合放什么？

## 核心回答

1. 我会把 `finally` 用在这次操作结束时都要做的收尾，例如恢复按钮可点击、关闭对应加载提示、移除临时监听。成功提示或失败提示不适合直接放在这里，因为收尾分支本身不说明业务是否完成，它的职责是整理本次操作留下的资源。

2. 对 Promise 的 `finally`，回调正常返回普通值不会替换前面的结果，返回成功的 Promise 也通常保留原来的成功值或拒绝原因。不过后续链会等待这个 Promise 完成，因此如果清理过程很慢，调用者拿到最终结果的时间也会被推迟。

3. 如果清理回调抛错或返回拒绝的 Promise，后续会收到新的失败，原来的结果就被覆盖了。同步 `try` 配套的 `finally` 还有一个区别：里面直接 `return` 也可能覆盖前面的返回或异常，所以我会避免在这种收尾分支里改变控制流。

4. 收尾还必须对应正确的操作，不能只要有一个请求结束就关闭页面上所有加载提示。假设页面允许并发查询，我会考虑按请求编号判断，或者用计数表示还有多少任务未结束，并单独处理清理失败，避免它掩盖真正需要排查的业务错误，也要防止旧任务释放了新任务正在使用的资源。

## 追问：finally 返回 Promise，会不会影响后续 then 的执行时间？

1. 会影响，后续链需要等待收尾回调返回的 Promise 完成。假设数据已经请求成功，但收尾还在等待临时文件释放，那么接在后面的成功回调要等清理结束才执行，不能认为业务成功后它就一定立即继续。

2. 如果这个 Promise 成功，通常继续传递清理前的值，而不是把清理返回值传给下游。如果它拒绝，下游则会收到清理错误；若它一直没有完成，后续链也会一直等待，这些都会影响调用者看到的状态。

3. 因此我会判断清理是否必须成为操作完成的前提。必须完成的资源释放可以等待，独立统计等非关键工作则可单独安排，但要给它自己的错误处理，不能仅仅省略返回值就把后台失败置之不理。

## 追问：业务请求失败，清理资源也失败，应该保留哪个错误？

1. 我会先区分调用方最需要处理的失败和辅助清理失败，而不是让后发生的错误自然覆盖前一个。假设业务失败导致提交未完成，页面通常仍应围绕提交失败反馈，同时记录清理问题帮助排查资源是否残留。

2. 可以在清理内部单独捕获异常，保留原始错误作为主要原因，再把清理失败作为附加信息记录。如果清理失败意味着资源无法安全继续使用，则应明确提升它的严重性，让调用方知道需要停止相关操作。

3. 具体返回一个组合错误还是保留主要错误，要按照调用约定决定，并避免丢失各自的堆栈和上下文。验证时应覆盖业务成功但清理失败、两者都失败等路径，不能只测成功时加载提示是否关闭。
