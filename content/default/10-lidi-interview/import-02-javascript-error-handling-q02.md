# finally 适合放什么？

## 核心回答

1. `finally` 放这次操作结束时都要做的收尾：按钮恢复可点、关掉对应加载、摘掉临时监听。成功提示或失败提示别直接放这里。收尾分支本身不说明业务成没成，它的职责是收拾这次操作留下的资源。

2. Promise 的 `finally` 里，回调正常返回普通值，不会替换前面的结果；返回成功的 Promise，通常也保留原来的成功值或拒绝原因。不过后续链会等这个 Promise 完成，清理很慢的话，调用者拿到最终结果的时间也会被拖后。

3. 清理回调抛错，或返回拒绝的 Promise，后续会收到新的失败，原来的结果就被盖掉了。同步 `try` 配套的 `finally` 还有一个差别：里面直接 `return`，也可能盖住前面的返回或异常。这种收尾分支里别改控制流。

4. 收尾必须对准正确的那次操作，不能哪个请求一结束就把页面上所有加载都关了。页面允许并发查询，可以按请求编号判断，或者用计数表示还有几件没结束。清理失败要单独处理，别盖住真正要查的业务错误，也别让旧任务把新任务正在用的资源放掉。

## 追问：finally 返回 Promise，会不会影响后续 then 的执行时间？

1. 会。后续链要等收尾回调返回的 Promise 完成。数据已经请求成功，收尾还在等临时文件释放，后面的成功回调就得等清理结束才跑。业务成功了，不等于它马上继续。

2. 这个 Promise 成功，通常继续传递清理前的值，不会把清理返回值传给下游。它拒绝，下游就收到清理错误。它一直完不成，后续链也会一直等。这些都会影响调用者看到的状态。

3. 清理是不是必须成为「操作完成」的前提，要想清楚。必须完成的资源释放可以等；独立统计这类非关键工作可以单独安排，但要给它自己的错误处理。省略返回值，不等于后台失败可以不理。

## 追问：业务请求失败，清理资源也失败，应该保留哪个错误？

1. 调用方最需要处理的失败，和辅助清理失败，要分开，别让后发生的错误自然盖住前一个。业务失败导致提交没完成，页面通常仍应围着提交失败来反馈，同时记下清理问题，方便查资源有没有残留。

2. 清理内部可以单独捕获异常，原始错误当主要原因，清理失败当附加信息记下来。清理失败意味着资源没法安全继续用，就明确抬高它的严重性，让调用方知道相关操作该停。

3. 返回组合错误还是保留主要错误，按调用约定来，各自的堆栈和上下文别弄丢。业务成功但清理失败、两者都失败，都要测。别只测成功时加载提示关没关。
