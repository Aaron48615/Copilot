# 微任务、宏任务和浏览器渲染机会怎么排？

## 核心回答

1. 我会先按浏览器环境回答：通常先执行一个任务的同步代码，然后在规定的检查点处理微任务，浏览器再根据是否有渲染机会更新画面。这里的任务常被叫作宏任务，但不能理解为每执行一个任务就必定绘制一帧。

2. 计时器回调和用户交互处理会通过任务调度，Promise 反应和 `queueMicrotask` 则通过微任务安排。一个任务里注册两类后续工作时，已经入队的微任务通常先处理；不过 Promise 未完成时，其后续还不能拿来参与当前这轮排序。

3. 微任务检查会持续处理队列中新加入的微任务，而不是只处理检查开始时的那一批。因此如果回调不断安排自己，即使每次工作很短，也可能长期挤占主线程，导致点击迟迟不能处理，页面也没有机会展示已经修改的内容。

4. 渲染还取决于刷新节奏、页面可见性和浏览器调度，不应把它当成固定排队的普通回调。`requestAnimationFrame` 适合安排渲染更新阶段的视觉操作，但回调本身在绘制前执行，其中放重计算仍然可能耽误这一帧。

5. 假设要处理大量记录，我会优先分离计算和界面更新，再决定拆成多个任务还是交给 Worker。判断效果要同时看任务耗时和交互表现，不能因为代码用了 Promise 就认为主线程已经让出，更不能把计时器延迟值当成精确执行时刻。

## 追问：requestAnimationFrame 回调执行时页面已经画好了吗？

1. 没有这个保证，它的用途是在一次渲染更新中、绘制之前安排代码。假设在回调中修改元素位置，浏览器可以把这次修改用于后续画面，但回调开始并不意味着先前状态已经被用户看到，不能把它当成绘制完成通知。

2. 如果回调里先设置加载文字，再同步计算很久，文字仍可能要等计算结束才出现在屏幕上。因为这一帧的后续工作仍被当前代码拖住，解决方向是减少回调工作量，而不是把所有耗时代码都搬到这个入口里。

3. 它也不适合作为后台业务的精确计时器，页面不可见时调用节奏可能受到限制。我会把动画进度依据时间计算，把数据处理放在合适的任务中，并避免用回调次数直接代表经过的秒数，否则掉帧就会改变动画速度。

## 追问：把长循环拆成多个 setTimeout 就能保证每片都绘制吗？

1. 拆开后确实给浏览器留下了任务之间的调度机会，但不会强制每片之间绘制。零延时也只是请求尽早安排，实际执行还受其他任务、计时器规则和页面状态影响，所以不能承诺每次回调都对应一个稳定的画面间隔。

2. 假设每片仍然包含大量计算，单次阻塞问题依旧存在。需要按实际耗时控制片段大小，并避免每片都交替读取布局和修改样式，否则拆分后的代码仍可能花很多时间在同步布局上，调度方法并不会自动消除工作成本。

3. 对于只需要最终结果的计算，Worker 可能更合适；对于必须渐进展示的列表，可以分批计算并合并界面更新。我会依据是否访问 DOM、能否接受中间状态和消息传递成本选择方式，再观察响应是否改善，而不是只检查是否出现了计时器。
