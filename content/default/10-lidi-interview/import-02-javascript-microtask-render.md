# 微任务、宏任务和浏览器渲染机会怎么排？

## 核心回答

1. 就浏览器来说，通常先跑完一个任务里的同步代码，再在规定检查点处理微任务，浏览器再根据有没有渲染机会更新画面。这里的任务常被叫作宏任务，但不是每执行一个任务就必定画一帧。

2. 计时器回调和用户交互走任务调度，Promise 反应和 `queueMicrotask` 走微任务。一个任务里注册了两类后续工作，已经入队的微任务通常先处理。Promise 还没完成时，它的后续还不能拿来参与当前这轮排序。

3. 微任务检查会持续处理队列里新加进来的微任务，不是只处理检查开始时的那一批。回调不断安排自己，就算每次工作很短，也可能长期占住主线程。点击迟迟处理不了，页面也没机会把已经改过的内容画出来。

4. 渲染还取决于刷新节奏、页面可见性和浏览器调度，别把它当成固定排队的普通回调。`requestAnimationFrame` 适合安排渲染更新阶段的视觉操作，但回调本身在绘制前执行，里面放重计算仍然可能耽误这一帧。

5. 处理大量记录，优先把计算和界面更新分开，再决定拆成多个任务还是交给 Worker。判断效果要同时看任务耗时和交互表现。代码用了 Promise，不代表主线程已经让出来；计时器的延迟值也不能当成精确执行时刻。

## 追问：requestAnimationFrame 回调执行时页面已经画好了吗？

1. 没有这个保证。它的用途是在一次渲染更新中、绘制之前安排代码。回调里改元素位置，浏览器可以把这次修改用到后续画面上，但回调开始并不等于先前状态已经被用户看到，不能当成绘制完成通知。

2. 回调里先设置加载文字，再同步计算很久，文字仍可能要等计算结束才出现在屏幕上。这一帧后面的活还被当前代码拖着。方向是减少回调工作量，不是把所有耗时代码都搬进这个入口。

3. 它也不适合当后台业务的精确计时器，页面不可见时调用节奏可能被限制。动画进度按时间算，数据处理放在合适的任务里。别用回调次数直接代表经过了几秒，掉帧就会把动画速度带偏。

## 追问：把长循环拆成多个 setTimeout 就能保证每片都绘制吗？

1. 拆开后确实给浏览器留下了任务之间的调度机会，但不会强制每片之间都绘制。零延时也只是请求尽早安排，实际执行还受其他任务、计时器规则和页面状态影响，不能承诺每次回调都对应一个稳定的画面间隔。

2. 每片仍然包含大量计算，单次阻塞问题还在。要按实际耗时控制片段大小，并避免每片都交替读布局、改样式。拆分后的代码仍可能把很多时间花在同步布局上，调度方法不会自动消掉工作成本。

3. 只需要最终结果的计算，Worker 可能更合适；必须渐进展示的列表，可以分批计算再合并界面更新。看是否访问 DOM、能不能接受中间状态、消息传递贵不贵，再观察响应有没有改善。出现了计时器不等于问题已经解决。
