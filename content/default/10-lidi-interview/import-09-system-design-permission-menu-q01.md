# 为什么不能只隐藏按钮？

## 核心回答

1. 隐藏按钮只是不提供操作入口。浏览器里的页面和脚本，当不了可信的授权依据。用户可以改页面、直接打接口地址、重复之前的请求。按钮不见了，不代表对应的数据和操作已经受到保护。

2. 比如普通成员看不到删除按钮，仍可能把记录编号带到删除接口。服务端必须从可信会话识别用户，再检查他能不能删这一条。别相信请求体里自报的角色，也别只判断这个用户已经登录。

3. 前端仍然需要按钮、菜单、路由三处配合，各自解决不同的体验问题。菜单减少无关入口，路由处理直接访问，按钮说明当前页面能做什么。权限标识尽量一致，别菜单藏了，页面上还能点。

4. 权限还可能跟资源归属、数据状态有关，不等于角色名称。同一角色能改自己创建的草稿，却不能改别人的记录，或者已经归档的数据。服务端在实际操作时要重新检查这些条件。

5. 权限被撤销后，旧页面可能暂时还留着按钮，但新的操作请求必须被拒绝。前端收到明确拒绝后再更新权限和页面。已经回到浏览器的数据，靠隐藏按钮收不回来。敏感字段应在响应前过滤，权限缓存也要有失效策略。

## 追问：按钮已经显示可操作，接口却返回 403，怎么办？

1. 把这看成服务端当前的授权结果，停掉这次操作，仍然有权编辑的输入留着。提示说明当前操作没权限，别让用户反复点。涉及敏感数据，页面保留范围也按新的权限重新判断。

2. 随后刷新权限或查询资源状态，区分角色被调整、资源转交、记录状态改变。按钮显示依据可能已经过期，也可能是前后端规则不一致。别一律靠退出登录把问题盖住，更别自动改用另一个接口重试。

3. 权限刷新也失败，就呈现权限暂时无法确认，受保护操作保持不可用。诊断时记必要的请求标识和权限项，方便对照规则。令牌和完整敏感响应别写进日志。也别把所有 403 都当成登录失效。

## 追问：怎么防止把记录 ID 改成别人的 ID 来越权？

1. 服务端把当前用户可访问的数据范围纳入查询或授权判断。比如同时检查记录所属租户，以及当前用户的访问关系。只校验 ID 格式合法，或者换成难猜的随机 ID，替不了这一步授权。

2. 读取、更新、删除、附件下载都要做相应检查，不能只保护列表接口。用户可能从旧链接或其他页面拿到 ID，详情接口必须独立判断。批量操作还要检查每一项，别只看第一条有没有权限。

3. 测试时准备同角色的两个用户，以及相同角色但不同租户的数据，直接交换资源 ID 发请求。预期不只是响应被拒绝，还包括响应不泄露字段、数据没有变化。返回 403 还是隐藏资源存在性，按统一接口约定处理。
