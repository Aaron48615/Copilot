# 为什么不能只隐藏按钮？

## 核心回答

1. 隐藏按钮只是不提供操作入口，浏览器里的页面和脚本并不是可信的授权依据。用户可以修改页面、输入接口地址或重复之前的请求，所以按钮不见了，不代表对应的数据和操作已经受到保护。

2. 比如普通成员看不到删除按钮，但仍可能把记录编号带到删除接口。服务端必须从可信会话识别用户，再检查他能否删除这一条记录，不能相信请求体里自报的角色，也不能只判断这个用户已经登录。

3. 前端仍然需要按钮、菜单和路由三处配合，只是各自解决不同的体验问题。菜单减少无关入口，路由处理直接访问，按钮说明当前页面能做什么；它们最好使用一致的权限标识，避免菜单隐藏了但页面仍出现可点击操作。

4. 权限还可能和资源归属、数据状态有关，不能简单等同于角色名称。比如同一角色能修改自己创建的草稿，却不能修改别人的记录或已经归档的数据，服务端要在实际操作时重新检查这些条件。

5. 权限被撤销后，旧页面可能暂时保留按钮，但新的操作请求必须被拒绝，前端收到明确拒绝后再更新权限和页面。已经返回到浏览器的数据不能靠隐藏按钮收回，所以敏感字段应在响应前过滤，权限缓存也要有失效策略。

## 追问：按钮已经显示可操作，接口却返回 403，怎么办？

1. 我会先把这看成服务端当前授权结果，停止本次操作，并保留仍然有权编辑的输入。提示应说明当前操作无权限，而不是让用户反复点击；若涉及敏感数据，页面保留范围也要按新的权限重新判断。

2. 随后刷新权限或查询资源状态，区分角色被调整、资源转交和记录状态改变。按钮显示依据可能已经过期，但也可能是前后端规则不一致，不能一律靠退出登录掩盖问题，更不能自动改用另一个接口重试。

3. 如果权限刷新也失败，就呈现权限暂时无法确认的状态，受保护操作保持不可用。诊断时记录必要的请求标识和权限项，便于对照规则，但不把令牌或完整敏感响应写进日志，也不把所有 403 都当成登录失效。

## 追问：怎么防止把记录 ID 改成别人的 ID 来越权？

1. 服务端应把当前用户可访问的数据范围纳入查询或授权判断，例如同时检查记录所属租户和当前用户的访问关系。只校验 ID 格式合法，或换成难猜的随机 ID，都不能代替这一步授权。

2. 读取、更新、删除和附件下载都要执行相应检查，不能只保护列表接口。用户可能从旧链接或其他页面拿到 ID，所以详情接口必须独立判断；批量操作还要检查每一项，不能只看第一条记录是否有权限。

3. 测试时准备同角色的两个用户，以及相同角色但不同租户的数据，直接交换资源 ID 发请求。预期不仅是响应被拒绝，还包括响应不泄露字段、数据没有变化；返回 403 还是隐藏资源存在性，应按统一接口约定处理。
