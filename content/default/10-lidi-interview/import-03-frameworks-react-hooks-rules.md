# Hooks 为什么不能写在条件分支里？

## 核心回答

1. 对 useState、useEffect 等常规 Hook，React 需要依靠稳定的调用顺序，把本次调用和组件之前保存的状态对应起来。若某次少调用了一个 Hook，后面的状态位置就可能错位，因此不能放进条件、循环或普通事件回调里。

2. 条件需求应该放到 Hook 内部，或者通过拆组件表达。比如登录后才轮询，可以始终调用 useEffect，在内部检查登录状态后再启动；条件渲染一个包含 Hook 的子组件也合法，因为每个组件分别维护自己的调用顺序。

3. 提前 return 同样需要注意。如果第一次先返回加载界面、下一次才执行后面的 useState，调用序列也不一致；通常把 Hook 放在组件顶层并位于条件返回之前，自定义 Hook 内部也要遵守相同规则。

4. 工程上我会使用 Hooks 的检查规则帮助发现问题，但也会说明版本边界：React 的 use API 是特殊情况，可以在条件和循环中调用，仍必须处于组件或 Hook 内，并不能随意放进 try/catch。不能把这个例外推广到 useState 或 useEffect。

5. 使用规则检查之外，我还会实际切换分支验证生命周期。例如从未登录切到登录再退出，界面应正确显示，轮询只在登录期间存在。调用顺序合法只是起点，分支内部的资源管理和状态重置仍需符合业务，不能只看到检查通过就停止验证。

## 追问：数组长度会变，怎样给每一项使用自己的 Hook？

1. 不能在父组件的 map 回调里直接调用 useState，因为增删项目会改变父组件执行 Hook 的次数。正确做法是把每一项提取成 Item 组件，在 Item 顶层声明它自己的状态，父组件只负责映射出元素。

2. 每个 Item 还需要稳定 key，让状态随业务项而不是数组位置移动。例如任务列表按 task.id 作为 key，重新排序后，某个任务展开的状态仍属于同一个任务，不会转移到占据原位置的另一项。

3. 如果这些项的状态需要统一提交或跨卸载保留，可以把值按 id 存在父级对象中。是否放进子组件应由状态归属决定，拆组件解决调用规则，但并不要求所有数据都变成子组件局部状态。

## 追问：自定义 Hook 里面能不能根据参数决定调不调用 useEffect？

1. 不可以，调用自定义 Hook 并不会让内部常规 Hook 获得条件调用的豁免。如果 enabled 改变后内部 useEffect 有时存在、有时不存在，最终仍会破坏调用它的组件所对应的 Hook 顺序。

2. 可以始终调用 useEffect，把 enabled 放入依赖，在回调开头判断。启用时建立订阅，禁用时上一次清理会释放订阅，新的执行直接返回；这样业务上的开关和生命周期处理都能正常对应。

3. 我会给这种 Hook 验证 false、true、false 的连续切换，而不只测试初次 enabled=true。尤其要确认禁用以后没有残留定时器，重新启用也只建立一份资源，避免规则修好了却留下重复订阅。若任务已经排队，还需要在禁用后让旧结果失效，停止下一次触发与阻止上一轮迟到回写是两个检查点。
