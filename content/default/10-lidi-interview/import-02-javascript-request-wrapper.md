# 如何设计一个带超时、重试和取消的请求函数？

## 核心回答

1. 先约定请求函数的输入和结果，包括请求选项、外部取消信号、单次超时、总时间预算和重试上限。总预算包含等待重试的时间，否则每次都重新计时，看起来设置了超时，用户实际却可能等很久。

2. 每次尝试需要新的取消控制器，再把外部取消与本次超时连起来。已取消的信号不能复用来重新请求。开始前先检查取消状态，结束时清理计时器和监听器。取消发生在退避等待期间，也要能马上结束流程。

3. 错误处理上，要区分网络失败、响应状态异常、数据解析失败和主动取消，因为它们对应的后续动作不同。请求拿到响应不等于业务成功。使用原生请求接口时还要检查状态码，再按接口约定读取响应内容。

4. 只有接口语义允许时才重试暂时故障，并限制次数、增加退避和适量随机等待，避免大量客户端同时重发。写请求尤其要确认幂等能力。超时只表示客户端未确认结果，不能证明服务端没有执行成功。

5. 返回值要让调用方明确知道成功、失败或取消，并保留必要的错误原因，方便展示和排查。验证时重点覆盖请求完成与取消竞争、取消后不再重试、以及总预算耗尽这些容易漏的边界。

## 追问：超时应该覆盖响应体读取吗？

1. 函数承诺返回解析完成的数据，预算就应持续覆盖响应体读取，不是拿到响应头就清计时器。服务端可能很快返回头部，却迟迟传不完正文。过早清理会让调用方仍然卡在读取数据这一步。

2. 下载或流式接口需要单独约定总时长和无数据等待时间，因为长连接本来就可能持续很久。普通接口的短超时不能直接套过去，否则正常下载也会中断。调用方应该能清楚选择适合自身的策略。

3. 计时取消也不是强制打断任何同步代码的工具。较重的同步解析会占住线程，取消回调只能等待执行机会。数据量大到影响交互，可以考虑限制响应规模，或把后续计算移到工作线程，并分别观察耗时。

## 追问：请求已经取消，为什么还要防止旧结果更新页面？

1. 取消和请求完成可能非常接近，旧请求也可能已经进入后续数据转换，这时单靠传输层取消并不稳妥。用户连续搜索两个词，旧词的结果晚到，仍可能把新词对应的列表盖掉，造成输入和结果对不上。

2. 每次查询分配递增标识，在写入列表前确认它仍是当前请求，组件离开后也停止提交结果。取消用来减少无用工作，标识用来判断结果还有没有资格更新页面，两者各自解决不同阶段的问题。

3. 加载状态和错误提示也要做同样的有效性检查，不能让旧请求的结束处理把新请求的加载中状态关掉。验证时可以人为交换两次响应的先后顺序，检查列表、错误和按钮状态始终属于最后一次有效查询。
