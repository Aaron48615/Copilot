# 取消能解决旧响应覆盖吗？

## 核心回答

1. 我不会只靠取消请求来保证页面显示正确，因为取消是通知异步操作停止，并不是把已经发生的事情撤回。比如先搜手机再搜电脑，手机请求可能已完成，或者结果已经进入后续处理，这时仍然需要判断它是否属于当前查询。

2. 我会给每轮查询分配递增序号，在发起请求时保存本轮编号，准备更新页面时与最新编号比较。只有相等才能写入列表，这个判断也要覆盖错误提示和加载状态，否则旧请求的收尾仍可能把新请求的加载动画提前关闭。

3. 新查询开始时可以先取消上一轮请求，减少不必要的网络传输和响应体处理，再创建新的控制器。序号则负责结果是否可以提交，两者解决的问题不同；如果还要异步转换数据，转换结束以后也要重新检查当前轮次。

4. 我更倾向于用轮次而不是只比关键词，因为用户可能先搜手机、再搜电脑、最后又搜手机，第一轮结果并不一定仍然有效。如果要验证方案，我会模拟旧响应晚到、旧请求失败和连续重复查询，分别检查列表、错误与加载状态。

## 追问：旧请求的 finally 为什么也会影响新页面？

1. 假设第一轮请求还没结束，第二轮已经把加载状态设为真，随后第一轮因为取消进入收尾。如果它无条件关闭加载状态，第二轮明明仍在等待，页面却已经允许重复操作，问题就发生在结果列表之外。

2. 我会让收尾逻辑同样携带请求编号，只有当前编号匹配才修改共享的页面状态。旧请求自己的监听器和临时资源仍然应该释放，这种局部清理不必因为它已经过期而跳过，否则可能留下无用引用。

3. 验证时我会控制两轮请求的完成顺序，让旧请求先进入收尾，而新请求继续保持未完成。此时应当继续显示加载提示，等新请求真正结束才关闭，同时确认旧轮错误没有触发新的错误提示。

## 追问：分页加载也能直接丢弃所有旧请求吗？

1. 分页需要先分清查询条件和页码，不能简单地把所有较早发出的请求都当作无效。比如同一筛选条件下第一页和第二页并行获取，它们可能都是需要的结果，只是返回的先后顺序不同。

2. 如果要实现并行分页，我会为整组查询设置版本，同时按页码分别保存结果，展示时按页码组合。筛选条件改变才使旧版本整体失效，这样第二页先返回也不会覆盖第一页，或者错误地打乱记录顺序。

3. 如果只是普通的加载更多，也可以先限制为一次加载一页，让逻辑更容易核对。需要额外处理重复点击、相同记录去重和最后一页判断，取消只负责终止无用请求，并不能自动维护这些分页规则。
