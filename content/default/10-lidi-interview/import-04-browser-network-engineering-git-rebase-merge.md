# merge 和 rebase 有什么区别？

## 核心回答

1. merge 和 rebase 都能把分支变化合进来，但留下的历史不一样。merge 在发生分叉时通常创建一个有两个父节点的合并提交，两条开发线都还在。如果可以快进，也可能只是移动引用，不一定每次都新增合并节点。

2. rebase 会把当前分支的一组提交重新应用到新的基点上，得到新的提交对象。即使代码内容相近，父节点一变，提交标识也会变。所以它是在改写这段分支历史，不是只调整日志显示顺序。

3. rebase 适合整理自己还没共享出去的提交，比如把临时修正合到一起，让一个功能提交表达完整。别人已经基于某段历史继续开发时，优先按团队约定的方式合并，避免逼对方处理被改写的历史。

4. 两者碰到冲突都要读懂双方意图，不能机械选 ours 或 theirs。rebase 按提交重放，相关冲突可能遇到多次。解决之后还要跑跟修改相符的检查。冲突标记消失了，业务逻辑不一定已经对。

5. 如果确实需要改写远端分支，必须先协调并拿到授权，重新核对远端状态。`force-with-lease` 比无条件强推多一层检查，但不等于绝对不会覆盖别人的工作。动手前也确认工作区干净，把恢复依据留好。

## 追问：rebase 时 ours 和 theirs 为什么容易选反？

1. 变基是在新的基点上重放原来的提交。工具呈现的当前一侧和被重放一侧，可能跟日常说的「我的分支」「对方分支」对不上。直接按词语选 ours，不保证留下的是自己原先想留的代码。

2. 看冲突所在提交、两边实际差异和调用上下文，确认每一段改动在解决什么问题。比如一边改校验规则，另一边加字段，两者可能都要留。简单整段选一边，会悄悄丢掉功能。

3. 解决后检查最终 diff，跑对应测试，再继续重放。如果发现理解错了，用 rebase 的中止流程回到操作前状态。继续往上叠修正，历史和工作区会越来越难看清。

## 追问：已经共享的错误提交，怎样撤销更合适？

1. 通常用 revert 生成一条反向提交，原始历史还在，其他人可以继续基于已有提交同步。这样能看清哪次引入问题、哪次撤销，不必让所有协作者重新适应被移走的分支位置。

2. 撤销前仍要检查后续提交是不是依赖它。比如某个新接口已经被其他页面用了，单独回退接口可能引出更多错误。合并提交的撤销还涉及主线选择，不能照搬普通提交的命令却不理解结果。

3. 把撤销当成一项需要验证的代码变更：检查差异、测试关键流程，按团队授权提交。如果只是自己还没共享的临时提交，可以在本地整理，但同样不能丢掉工作区里还没保存的内容。
