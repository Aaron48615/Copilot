# merge 和 rebase 有什么区别？

## 核心回答

1. merge 和 rebase 都可以整合分支变化，但保留的历史不同。merge 在发生分叉时通常创建有两个父节点的合并提交，保留两条开发线；如果可以快进，也可能只是移动引用，不一定每次都会新增合并节点。

2. rebase 会把当前分支的一组提交重新应用到新的基点上，得到新的提交对象。即使代码内容相近，父节点改变后提交标识也会变化，所以它是在改写这段分支历史，而不是只调整日志显示顺序。

3. 我通常把 rebase 用于整理自己尚未共享的提交，例如合并临时修正、让一个功能提交表达完整。别人已经基于某段历史继续开发时，应优先采用团队约定的合并方式，避免迫使对方处理被改写的历史。

4. 两者遇到冲突都需要读懂双方意图，不能机械选择 ours 或 theirs。rebase 按提交重放，可能多次遇到相关冲突；解决后还要运行与修改相符的检查，冲突标记消失不代表业务逻辑已经正确。

5. 如果确实需要改写远端分支，必须先协调并获得授权，重新核对远端状态。force-with-lease 比无条件强推多一层检查，但不等于绝对不会覆盖工作；在开始操作前也应确认工作区干净，保留恢复依据。

## 追问：rebase 时 ours 和 theirs 为什么容易选反？

1. 变基是在新的基点上重放原来的提交，工具呈现的当前一侧与被重放一侧可能和日常理解的我的分支、对方分支不同。直接按词语选择 ours 并不保证保留了自己原先想保留的代码。

2. 我会查看冲突所在提交、两边实际差异和调用上下文，确认每一段改动解决什么问题。比如一边修改校验规则，另一边增加字段，两者可能都需要保留，简单整段选一边会悄悄丢掉功能。

3. 解决后检查最终 diff 并运行对应测试，再继续重放。如果发现理解错了，可以使用 rebase 的中止流程恢复操作前状态，而不是继续叠加修正，让历史和工作区越来越难判断。

## 追问：已经共享的错误提交，怎样撤销更合适？

1. 通常使用 revert 生成一条反向提交，保留原始历史，让其他人继续基于已有提交同步。这样能清楚看到哪次引入问题、哪次撤销，而不需要让所有协作者重新适应被移走的分支位置。

2. 撤销前仍要检查后续提交是否依赖它，例如某个新接口已被其他页面使用，单独回退接口可能引发更多错误。合并提交的撤销还涉及主线选择，不能照搬普通提交的命令而不理解结果。

3. 我会把撤销作为一项需要验证的代码变更，检查差异、测试关键流程并按团队授权提交。若只是自己尚未共享的临时提交，可以考虑本地整理，但同样不能丢弃当前工作区中未保存的内容。
