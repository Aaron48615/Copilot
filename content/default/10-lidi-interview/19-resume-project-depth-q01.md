# 你说 GitHub 年度开发记录近千次，主要做了什么？

## 核心回答

1. 这个记录主要想说明我一直在持续做项目和修改代码，但我不会把贡献数量直接当成能力。贡献图不只统计代码提交，具体年份和口径应该按 GitHub 页面说明；更有代表性的是我实际完成过哪些改动，以及为什么这样改。

2. 比起报总数，我更愿意讲能对应到项目内容的工作。轻购可以展开页面与接口对接、搜索联想、商品卖点、登录跳转、购物车和订单流程，这些可以分别找到入口和行为来说明，比如从用户输入到推荐结果展示，具体讲清数据经过哪些处理。

3. 比如购物车数量修改，我可以讲 `updatingBasketIds` 如何标记正在更新的商品，请求按差值修改数量，数量归零时走删除。讨论重点是为什么重复点击会带来并发问题，以及成功和失败后页面该保持什么状态。

4. 搜索联想则能继续讲输入防抖、请求编号、五分钟缓存和返回数量校验。五分钟是这个功能当前的实现选择，是否适合还要看商品变化频率和用户的重复查询情况。这些具体取舍比单说“接入 AI”更方便讲清我的理解。

5. 我更看重一个问题能不能讲到处理细节，而不是一次改动拆成多少次提交。比如购物车不能只讲成功后数量变化，还要解释请求失败后怎样恢复可操作状态；持续修改的价值应该落在功能是否正确、代码是否更容易维护上。

## 追问：GitHub 的贡献格子为什么不等于提交次数？

1. 贡献图会汇总多种活动，提交、议题和拉取请求等都有各自的计入条件。因此看到某年一个总数，只能先称为该口径下的贡献记录，不能直接把每一次活动都解释成新增功能。

2. 本地 Git 历史与贡献图也可能不同，因为关联邮箱、仓库和分支等条件会影响展示。如果要核对提交，我会另看指定时间范围的历史，并说明合并提交、重复历史是否计入，避免两个数字混用。

3. 就算口径一致，提交大小也不一致，一次改样式和一次修状态问题都可能各算一次。我会用代表性改动解释投入和难点，数字只作为辅助信息，不能代替对代码本身的审查与追问。

## 追问：挑一项改动时，你怎样证明自己参与并理解了？

1. 我会先展示相关差异和上下文，说明原来哪个操作会出问题、改动落在哪个函数。提交记录能够提供时间和作者线索，但不能单独证明理解程度，尤其 AI 参与后还需要讲清楚我做的判断。

2. 拿购物车举例，我会解释为什么标记具体商品，而不是让所有商品都不能操作。再讨论请求失败如何解除标记、保留什么数量，这些分支能检验我是否只记住了一个变量名，还是理解整个交互。

3. 我会用具体操作演示改动，比如连续点击同一商品的加号，再分别观察成功和失败后的数量与按钮状态。面试官还能据此继续追问取消请求或切换页面时怎么办，这比只展示一张运行截图更能说明我是否理解代码。
