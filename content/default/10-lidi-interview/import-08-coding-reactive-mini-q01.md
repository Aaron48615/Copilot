# 这个实现最容易漏什么？

## 核心回答

1. 最容易漏的是依赖会变化，不是建一次就完了。像 `flag ? left : right`，切换分支后要移除 left 的旧订阅。嵌套 effect 还要恢复外层上下文，否则内层结束后的读取会被记错位置。

2. 第二类是对象访问的边界：只代理外层对象，`state.user.name` 的修改不会自动经过外层 set。可以在 get 时懒代理嵌套普通对象，并用 WeakMap 缓存同一原对象对应的代理。直接改原对象仍会绕开拦截。比如持有原始 user 引用的第三方代码，写入时就不会经过新建的代理。

3. 数组和删除操作也不能靠一个 set 全解决。新增数组下标可能影响 length，缩短 length 又会影响被截掉的下标。`delete` 要有删除拦截，`Object.keys` 等遍历读取还需要独立依赖，不能只通知被删除属性。

4. effect 自己读写同一属性时，最直接的问题是递归。运行标记能防止同步重入，但异步调度中两个 effect 相互修改仍可能循环。所以副作用里的反向写入要限制住，调度过程也要给可诊断的循环保护。

5. 最后是生命周期和异常处理：stop 要移除依赖，队列里已经等待的任务也要检查是否仍有效。effect 抛错时用 finally 恢复上下文。WeakMap 只解决对象键的弱引用，不代表订阅、定时器和其他资源都自动释放。

## 追问：数组 push 为什么可能让 length 的依赖漏更新？

1. push 新元素时，会先写入新下标，而这个动作本身就可能改变原数组的 length。之后再拦截 length 赋值，如果只比较当时的新旧长度，看到的可能已经相等，依赖就被错误跳过了。

2. 在设置下标前保存旧长度，判断这次是不是新增有效整数下标。如果下标越过原长度，除了通知该下标，还要通知 length。一次操作命中同一个 effect 时，需要合并执行，避免页面重复计算。

3. 反方向也要处理：把 length 从五改成二，依赖下标四的 effect 应重新读取到 undefined。数组索引识别、遍历依赖和方法内部读取还有额外细节，所以面试最小版可以明确不支持数组，而不能默认它和普通对象完全一样。

## 追问：stop 和暂停一次更新有什么区别？

1. stop 表示结束自动订阅，要把 effect 从所有依赖集合移除，并将它标记为未激活。暂停通常意味着保留关系、暂时不执行，恢复时还要决定是否补一次更新，两者的生命周期约定不同。

2. 对有调度器的版本，stop 发生前任务可能已经进入队列，因此仅删除订阅还不够。队列真正执行时应检查 active 状态，或者同时删除待执行任务，否则组件销毁后仍可能访问已经失效的页面引用。

3. 停止后手动调用 runner 的语义也要明确，比如允许执行原函数，但不重新建立它的自动订阅。若 effect 创建了事件监听或定时器，还需要注册并调用清理函数，删除响应式依赖并不会取消这些外部副作用。
