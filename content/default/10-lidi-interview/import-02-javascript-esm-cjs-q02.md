# 循环依赖会发生什么？

## 核心回答

1. 循环依赖是甲依赖乙、乙又直接或间接依赖甲，形成一条闭合路径。它不等于无限递归，因为模块系统会记下加载状态。但初始化过程中，确实可能读到还没准备好的数据。

2. ESM 里，导入方拿到的是导出变量的绑定，建好关联不代表变量已经初始化。甲导出 `const` 配置，乙在顶层去读甲还没初始化的配置，会触发暂时性死区错误，不是读到空值那么简单。

3. CommonJS 碰到正在加载的模块，会先返回它当时已经提供的导出内容。乙可能只能看到甲已经写入 `exports` 的部分属性，还没加上的属性是 `undefined`。后面能不能看到更新，还取决于手里握的是哪个对象。

4. 同样存在依赖环，把读取放进函数，等全部模块初始化后再调用，有时就能正常跑。关键是实际读取发生的时间。这只说明它为什么暂时可用，不证明以后改入口顺序也没风险。

5. 要调整，先画出最短依赖环，找出双方真正共享的数据或函数。可以抽到独立模块，或让调用方传入依赖。新模块不能再反向导入，不然只是把环藏到更深的位置。

## 追问：为什么把读取放进函数后，循环依赖可能不报错了？

1. 导入关系的建立，和函数体执行，是两个时刻。定义一个函数时，通常不会立刻读取函数体里面引用的导入变量。原来在模块顶层触发的提前访问，被推迟到了后面调用的时候。

2. 甲导出配置，乙导出读取配置的函数，入口等甲乙都初始化完再调用乙，配置绑定已经有值。这个例子依赖明确的调用时机。代码里多了一层函数，不等于问题已经解决。

3. 另一个模块在初始化期间立刻调用这个函数，读取仍然可能过早。分别从不同入口启动，并检查顶层调用链。初始化顺序本身就是业务前提，最好写成明确的启动步骤。

## 追问：CommonJS 循环依赖中，替换导出对象为什么更容易出问题？

1. 乙提前加载甲时，可能握着甲最初的导出对象。甲后来整体赋值，把导出换成另一个对象，乙手里的旧引用不会自动跳到新对象。这跟给原对象加属性是两种操作。

2. 甲只是继续改原对象，乙通过这个对象读属性时可能看到新值。乙要是已经把某个原始值属性解构到局部变量里，局部变量也不会随属性更新。分析时要继续追具体怎么读的。

3. 排查时同时看加载次序、整体替换、解构位置，别只靠调导入顺序碰运气。必须兼容旧模块，可以考虑保持导出对象稳定。长期还是少在初始化阶段双向读数据。
