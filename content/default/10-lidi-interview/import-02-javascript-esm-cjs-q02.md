# 循环依赖会发生什么？

## 核心回答

1. 循环依赖是甲模块依赖乙、乙又直接或间接依赖甲，形成一条闭合的依赖路径。它不等于无限递归，因为模块系统会记录加载状态，但初始化过程中确实可能读到尚未准备好的数据。

2. 对于 ESM，导入方拿到的是导出变量的绑定，建立关联不代表变量已经初始化。例如甲导出 const 配置，乙在顶层读取甲还没初始化的配置，就会触发暂时性死区错误，不能简单理解为读到空值。

3. CommonJS 遇到正在加载的模块，会先返回它当时已经提供的导出内容。因此乙可能只能看到甲已经写入 exports 的部分属性，访问尚未添加的属性会得到未定义值，后续能否看到更新还取决于持有哪个对象。

4. 同样存在依赖环，把读取放进函数并在全部模块初始化后调用，有时就能正常运行。关键是实际读取发生的时间，不过这只是说明它为什么暂时可用，不能证明以后调整入口顺序也没有风险。

5. 如果需要调整，我会先画出最短依赖环，找出双方真正共享的数据或函数。可以考虑抽到独立模块，或让调用方传入依赖，但要保证新模块没有反向导入，否则只是把环藏到了更深的位置。

## 追问：为什么把读取放进函数后，循环依赖可能不报错了？

1. 导入关系的建立和函数体执行是两个时刻。定义一个函数时，通常不会立刻读取函数体里面引用的导入变量，所以原本在模块顶层触发的提前访问，被推迟到了后续调用阶段。

2. 假设甲导出配置，乙导出读取配置的函数，只要入口等甲乙都初始化完再调用乙，配置绑定已经有值。这个例子依赖明确的调用时机，不能只看到代码里多了一层函数就认定问题解决了。

3. 如果另一个模块在初始化期间立即调用这个函数，读取仍然可能过早。验证时我会分别从不同入口启动，并检查顶层调用链；若初始化顺序本身就是业务前提，最好把它写成明确的启动步骤。

## 追问：CommonJS 循环依赖中，替换导出对象为什么更容易出问题？

1. 乙提前加载甲时，可能持有甲最初的导出对象。甲后来执行整体赋值，把导出换成另一个对象，乙手里的旧引用不会自动跳转到新对象，这与给原对象增加属性是两种不同操作。

2. 如果甲只是继续修改原对象，乙通过这个对象读取属性时可能看到新值。但乙如果已经把某个原始值属性解构到局部变量里，局部变量也不会随属性更新，分析时需要继续追踪具体读取方式。

3. 排查时我会同时检查加载次序、整体替换和解构位置，避免只用调整导入顺序碰运气。假如必须兼容旧模块，可以考虑保持导出对象稳定，但长期仍应减少初始化阶段的双向数据读取。
