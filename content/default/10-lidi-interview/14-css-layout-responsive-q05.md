# `rem`、`vw` 和媒体查询怎么选择？

## 核心回答

1. 这三者解决的问题不同，我不会把它们当成必须三选一的适配方案。`rem` 主要表达相对于根字号的长度，`vw` 相对于视口宽度，媒体查询则在条件满足时切换一组样式，既能改尺寸，也能改变页面结构。

2. 字号和阅读间距通常适合 rem，因为可以围绕统一字号体系调整；但 rem 本身不会随屏幕自动变化，只有根字号改变才会缩放。如果把根字号严格绑定屏宽，所有文字也会跟着变化，需要防止大屏过大、小屏难读。

3. vw 适合确实要与视口相关的尺寸，比如横幅留白，但不适合不加限制地控制所有文字。可以用 `clamp()` 给流动尺寸设上下限；如果组件在窄侧栏中，视口仍然很宽，单靠 vw 就反映不出它真正拿到的空间。

4. 媒体查询适合内容放不下时调整结构，例如双栏变单栏、导航换行。我会先使用 Flex 或 Grid 的自然伸缩，再在内容开始拥挤的位置设置断点，并测试中间宽度和字体放大。断点服务于内容，不必围绕几款手机型号逐个写规则。

5. 此外，移动页面先要有正确的视口配置，否则浏览器可能按较宽的布局视口缩小整页，媒体断点也就不是预期效果。我会先确认页面可用宽度，再讨论单位，避免在错误参照上继续调整根字号。

## 追问：clamp() 怎么兼顾缩放和可读性？

1. 它接受最小值、偏好值和最大值，例如 `clamp(1rem, 0.8rem + 1vw, 1.5rem)`。中间值随视口变化，但最终被上下限约束，比纯 vw 字号在超宽屏和窄屏上更可控。

2. 这里的数字只是示例，实际要根据标题层级和正文阅读需求调整。我会让正文保留稳定的阅读大小，对标题或留白使用更明显的流动变化，避免整个界面随着窗口拖动不断改变阅读节奏。

3. 还需要测试浏览器缩放和用户默认字号变化。包含 rem 的表达式有助于响应字体基准，但不代表自动满足所有可访问性要求；仍要检查放大后的换行、按钮高度以及内容有没有被固定尺寸裁掉。

## 追问：为什么桌面页面不一定适合整页 rem 等比缩放？

1. 桌面窗口的宽度变化往往意味着可以增加列数或扩大内容区，不意味着所有按钮和文字都应该同比变大。把一张移动设计稿机械放大，可能得到巨大间距和过长的文字行，空间利用反而更差。

2. 我会让主体容器有最大宽度，侧栏按合理范围取值，内容区使用弹性轨道。窗口较小时再通过媒体查询收起侧栏或改成单栏，正文大小维持可读，结构承担大部分适配工作。

3. 如果同一个组件会出现在不同宽度的区域，还可以考虑容器查询。这样卡片根据所在栏宽切换图片与文字的排列，而不是所有卡片都随着页面级断点同步切换，复用时会更符合真实空间。
