# 弹窗和下拉菜单的焦点管理怎么做？

## 核心回答

1. 我会先区分模态弹窗、操作菜单和普通展开面板，因为它们不应该使用同一套键盘行为。模态弹窗需要暂时限制用户在里面操作；普通导航展开区通常仍然按页面正常 Tab 顺序访问，不能看到“下拉”两个字就全部加 menu 角色和焦点陷阱。

2. 模态弹窗打开时，记录触发入口并把焦点移入，根据内容选择首个输入框、标题或较安全的按钮。背景应不可交互，正反向 Tab 留在弹窗范围内，Escape 和关闭按钮有明确行为。可以优先使用原生 dialog 或成熟组件，再验证业务内容下的表现。

3. 如果是真正的操作菜单，触发按钮要表达展开状态，打开后按对应模式移动到菜单项，方向键帮助逐项选择，Escape 返回触发按钮。若只是几个导航链接，保留链接语义和普通焦点顺序往往更自然，不要为了样子像菜单而让键盘操作突然变复杂。

4. 焦点样式也要可见，可以用 focus-visible 提供清晰轮廓，而不是全局移除 outline。关闭或卸载时恢复合理焦点、清理监听；触发项已删除时选择相邻入口。最后用键盘走完流程，检查动态增删内容和嵌套弹窗，不能只验证点击能打开。

## 追问：普通导航下拉为什么不一定要用 role="menu"？

1. ARIA menu 表达的是一组菜单操作，并配有相应的键盘约定，用户会期待方向键移动等行为。网站导航只是展开若干链接时，使用列表和链接通常已经表达清楚，强加 menu 会带来额外的行为实现责任。

2. 我会用 button 控制展开，用 aria-expanded 表达状态，里面保留真实链接和自然 Tab 顺序。这样用户既能跳转，也能继续遍历页面，不需要进入一个没有完整键盘支持的“伪菜单”后再寻找出口。

3. 如果产品确实需要桌面应用式操作菜单，才按完整菜单模式处理项目焦点、方向键和关闭。判断应由内容用途和用户预期决定，不能仅根据视觉上是一个浮层，就给所有组件套相同的角色。

## 追问：focus-visible 是否意味着鼠标点击永远没有焦点框？

1. 不是，它由浏览器根据输入方式和控件需求判断是否应该展示明显焦点提示，不等同于一个简单的“只用键盘才匹配”开关。文本输入等需要持续输入的控件，即使用鼠标进入，也可能需要显示焦点状态。

2. 我会用它增强清晰的焦点轮廓，同时保留合理的基础样式和目标环境兼容处理。不能先全局 outline: none，再假设所有环境都会被新的选择器覆盖，否则某些用户可能完全看不到自己操作的位置。

3. 验证时交替使用鼠标和键盘，检查按钮、链接、输入框和关闭按钮。轮廓还不能被父容器裁掉，并需要在不同背景上可辨认；它的目标是让用户理解当前焦点，而不是单纯减少截图里的边框。
