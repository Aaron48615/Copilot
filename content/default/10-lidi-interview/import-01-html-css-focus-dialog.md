# 弹窗和下拉菜单的焦点管理怎么做？

## 核心回答

1. 先分清模态弹窗、操作菜单和普通展开面板，键盘行为不该套同一套。模态弹窗要暂时把人留在里面操作；普通导航展开区通常仍按页面正常 Tab 顺序走。看见「下拉」两个字就全部加 `menu` 角色和焦点陷阱，不对。

2. 模态弹窗打开时，记下触发入口，把焦点移进去。按内容选第一个输入框、标题，或比较安全的按钮。背景不可交互，正反向 Tab 留在弹窗范围内，Escape 和关闭按钮行为明确。优先用原生 `dialog` 或成熟组件，再在真实业务内容下验一遍。

3. 真正的操作菜单，触发按钮要表达展开状态，打开后按对应模式移到菜单项，方向键帮着逐项选，Escape 回到触发按钮。如果只是几个导航链接，保留链接语义和普通焦点顺序往往更自然。别为了样子像菜单，让键盘操作突然变复杂。

4. 焦点样式要看得见，可以用 `:focus-visible` 给清楚的轮廓，别全局摘掉 `outline`。关闭或卸载时恢复合理焦点、清监听；触发项已经删了，就选相邻入口。最后用键盘走完流程，动态增删内容、嵌套弹窗都要查，只验证点击能打开不够。

## 追问：普通导航下拉为什么不一定要用 role="menu"？

1. ARIA `menu` 表达的是一组菜单操作，并带着相应的键盘约定，用户会期待方向键移动这类行为。网站导航只是展开若干链接时，列表加链接通常已经说清楚。硬加 `menu`，额外的行为实现责任就来了。

2. 用 `button` 控制展开，`aria-expanded` 表达状态，里面保留真实链接和自然 Tab 顺序。用户既能跳转，也能继续遍历页面，不必钻进一个键盘支持不完整的「伪菜单」再找出口。

3. 产品确实需要桌面应用那种操作菜单，再按完整菜单模式处理项目焦点、方向键和关闭。看内容用途和用户预期，别只因为视觉上是一个浮层，就给所有组件套相同角色。

## 追问：focus-visible 是否意味着鼠标点击永远没有焦点框？

1. 不是。浏览器按输入方式和控件需求判断该不该展示明显焦点提示，它不是一个简单的「只用键盘才匹配」开关。文本输入这类需要持续输入的控件，即使用鼠标点进去，也可能要显示焦点状态。

2. 用它增强清楚的焦点轮廓，同时保留合理的基础样式，目标环境兼容也要处理。别先全局 `outline: none`，再假设所有环境都会被新选择器盖住，否则有的用户可能完全看不到自己操作的位置。

3. 验证时鼠标和键盘交替用，按钮、链接、输入框、关闭按钮都看。轮廓不能被父容器裁掉，不同背景上也要认得出来。目标是让人知道当前焦点在哪，不是单纯减少截图里的边框。
