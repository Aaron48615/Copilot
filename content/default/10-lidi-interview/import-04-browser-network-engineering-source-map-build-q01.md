# 构建缓存失效怎么排查？

## 核心回答

1. 构建缓存问题先分两类。本来可以复用却反复失效，主要影响速度。本来应该失效却错误命中，可能产出旧代码。两者排查方向不同。看到的是构建变慢，还是实际产物跟源码对不上，先说清楚。

2. 接着比较真正影响结果的输入：锁文件、运行时版本、构建配置、插件、环境变量。只按分支名生成缓存键通常不够，配置或依赖变了仍可能拿到旧条目。键过于宽泛，无关改动也会让全部重新构建。

3. 看构建日志和缓存记录，确认哪一层命中了。依赖下载缓存、转译中间产物、完整构建结果是不同东西。清掉包管理器下载缓存，不一定能解决 Webpack 文件缓存的问题。所有叫 cache 的目录不能混为一谈。

4. 现场留下来之后，用相同输入在干净缓存条件下做一次基线构建，比较资源内容和关键行为。只比较文件名不够，生成时间、路径这类信息也可能改 hash。缓存命中本身也不能证明输出正确。

5. 缓存依赖覆盖到额外配置文件，持续集成里保留适当的干净构建验证。修完分别测：输入不变时能复用，重要输入变化时必须失效。既不要每次白做，也不要用旧产物冒充新版本。

## 追问：环境变量改变了，为什么可能仍拿到旧产物？

1. 构建工具可能把环境变量的值直接编译进客户端代码。外层缓存没把这些变量纳入输入，改了变量仍可能复用以前的构建结果。缓存系统不会自动知道所有自定义脚本读了哪些外部状态。

2. 真正影响产物的公开变量和构建参数列出来，纳入缓存依赖或版本摘要，同时避免把秘密原值打到日志里。服务端运行时变量要分开看，它未必影响前端构建。整个环境无差别塞进缓存键，键会又乱又容易误失效。

3. 只改一个明确的功能开关，对比缓存构建和干净构建的实际页面行为。结果一致且符合新配置之后，再检查没有变化时是否正常命中。修复方式如果只是永久关掉缓存，输入归因其实还没解决。

## 追问：删缓存后恢复正常，可以认定根因了吗？

1. 只能说明缓存可能参与了问题，还不能确定哪个输入没被跟踪。删缓存的同时还可能重装依赖、重新生成文件、改变执行顺序。一次恢复正常，证明不了具体错误来自某个缓存键设计。

2. 出问题的构建配置、输入差异、命中记录留下来，尽量重现从正常缓存到错误复用的过程。比如先构建旧配置，再只改某个额外文件，观察工具是否错误命中，才能得到可验证的原因。

3. 修完加上针对这个输入变化的验证，并检查产物行为。清缓存可以当临时恢复。依赖追踪不修，下次相同条件还会再来。让同事以后都手动清缓存，当不了长期方案。
