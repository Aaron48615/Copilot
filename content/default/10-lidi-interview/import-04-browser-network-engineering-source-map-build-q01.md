# 构建缓存失效怎么排查？

## 核心回答

1. 构建缓存问题要先分两类：本来可以复用却反复失效，主要影响速度；本来应该失效却错误命中，可能产出旧代码。两者排查方向不同，我会先明确看到的是构建变慢，还是实际产物与源码不一致。

2. 接着比较影响结果的输入，包括锁文件、运行时版本、构建配置、插件和环境变量。只按分支名生成缓存键通常不够，配置或依赖变化后仍可能取到旧条目；缓存键过于宽泛也会让无关改动导致全部重新构建。

3. 我会查看构建日志和缓存记录，确认哪一层命中。依赖下载缓存、转译中间产物、完整构建结果是不同东西，清掉包管理器下载缓存不一定能解决 Webpack 文件缓存的问题，不能把所有 cache 目录混为一谈。

4. 保留现场后，用相同输入在干净缓存条件下做一次基线构建，比较资源内容和关键行为。不能只比较文件名，因为生成时间或路径等信息也可能改变 hash；缓存命中本身更不能证明输出正确。

5. 如果继续完善，我会让缓存依赖覆盖额外配置文件，并在持续集成中保留适当的干净构建验证。修复后分别测试输入不变时可复用、重要输入变化时必失效，确保既没有每次白做，也没有用旧产物冒充新版本。

## 追问：环境变量改变了，为什么可能仍拿到旧产物？

1. 构建工具可能把环境变量的值直接编译进客户端代码，如果外层缓存没有把这些变量纳入输入，改变变量后仍可能复用以前的构建结果。缓存系统不会自动知道所有自定义脚本读取了哪些外部状态。

2. 我会列出真正影响产物的公开变量及构建参数，将其纳入缓存依赖或版本摘要，同时避免把秘密原值打印到日志。服务端运行时变量则要分开看，它未必影响前端构建，不能把整个环境无差别塞进缓存键。

3. 验证时只改变一个明确的功能开关，对比缓存构建与干净构建的实际页面行为。若结果一致且符合新配置，再检查没有变化时是否正常命中，避免修复方式只是永久关闭缓存而没有解决输入归因。

## 追问：删缓存后恢复正常，可以认定根因了吗？

1. 只能说明缓存可能参与了问题，还不能确定哪个输入没有被跟踪。删除缓存同时可能重装依赖、重新生成文件或改变执行顺序，因此一次恢复正常并不证明具体错误来自某个缓存键设计。

2. 我会保留出问题的构建配置、输入差异和命中记录，尽量重现从正常缓存到错误复用的过程。比如先构建旧配置，再只修改某个额外文件，观察工具是否错误命中，这样才能得到可验证的原因。

3. 修复后加入针对这个输入变化的验证，并检查产物行为。清理缓存可以作为临时恢复措施，但若不修依赖追踪，下次相同条件还会出现，不能把让同事以后都手动清缓存当成长期方案。
