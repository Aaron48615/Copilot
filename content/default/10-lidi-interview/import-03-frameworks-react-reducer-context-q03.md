# Context 性能怎么处理？

## 核心回答

1. 先看 Context 的 `value` 里到底有什么，哪些组件在读它。Provider 的值按引用变了，就会通知这个 Context 的消费者。某个组件只用其中一个字段，也不会自动按字段订阅。

2. 最常见是把变化快慢差很多的数据放一起。主题、用户信息、搜索框文字塞同一个对象，每打一个字，所有消费者都可能被叫到。按用途拆开，主题组件就不必跟着搜索条件刷。

3. 父组件每次渲染都新造一个 `value` 对象，也可能多通知一轮。`useMemo` 可以稳住这个值，回调用 `useCallback`，或者把 Provider 的状态放得更局部。真实状态变了，缓存挡不住消费者拿到新值。

4. 只负责发动作的组件，可以跟读状态的组件用不同 Context。reducer 的 state 和 `dispatch` 拆开，工具栏只发动作，就不必订整份列表。组件自己用了 Context，`memo` 也挡不住这次更新。

5. 拿一次具体操作看哪些消费者更新了，再决定要不要换成能按字段选的状态方案。消费范围本来就小、更新也不贵，拆成很多 Provider 反而更难读。出现重渲染不等于设计一定有问题。

## 追问：用 useMemo 包住 Provider value 就解决了吗？

1. 它主要挡住依赖没变时反复造新对象。父级一个不相关弹窗更新了，主题和用户都没变，缓存让 Provider 继续用原来的引用，消费者就不会只因为对象新建被叫到。

2. `value` 真正依赖的东西变了，缓存结果也该变。搜索词写进依赖，输入照样会更新所有读这个 Context 的组件。漏写依赖来留旧引用，拿到的是过时数据，不是有效的性能优化。

3. 先搞清消费者实际要哪一段数据，再决定拆 Context 还是把状态往下放。同一套输入操作再测提交耗时和更新范围。`useMemo` 写上了，用户感受到的卡顿不一定就少了。

## 追问：状态和 dispatch 拆开有什么实际作用？

1. 任务面板上有数量展示，还有「清空已完成」按钮。数量必须读任务状态；按钮只需要 `dispatch` 一个动作。合在同一个 Context 里，任务内容一变，按钮也会被叫到。

2. `useReducer` 返回的 `dispatch` 身份是稳的，可以单独用一个 Provider 传下去。按钮读动作那个 Context，就不会因为状态 Context 的 `value` 变了被这次订阅直接触发。父级渲染带着更新，还要另外看。

3. 这种拆分适合确实有「只发动作」的消费者，不是每个 Context 都要拆两份。按钮还要根据选中数量显示禁用，它仍然需要那份数据。保留禁用所需的最小订阅，别让没有可清理任务时按钮还能点。
