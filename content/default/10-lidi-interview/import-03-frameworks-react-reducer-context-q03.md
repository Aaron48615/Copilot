# Context 性能怎么处理？

## 核心回答

1. 我会先检查 Context 的 value 实际包含什么，以及哪些组件在读取它。Provider 的值按引用发生变化，会通知这个 Context 的消费者；某个组件即使只使用其中一个字段，也不会自动获得按字段选择的订阅能力。

2. 最常见的问题是把变化频率不同的数据放在一起。比如主题、用户信息和搜索框文字共用一个对象，每输入一个字就可能通知所有消费者；我会按用途拆分，让主题组件不必跟着搜索条件变化。

3. 父组件每次渲染重新创建 value 对象，也可能带来不必要通知。可以用 useMemo 稳定值，回调用 useCallback，或者把 Provider 的状态放得更局部；但真实状态改变时，缓存不能阻止消费者得到新值。

4. 只执行动作的组件，可以与读取状态的组件使用不同 Context。例如把 reducer 的状态和 dispatch 拆开，工具栏只需要发出动作，就不必订阅整份列表。memo 也不能屏蔽组件自己使用的 Context 更新。

5. 我会用一次具体操作查看哪些消费者更新，再决定是否引入支持选择订阅的状态方案。如果消费范围本来很小，更新也不昂贵，拆成很多 Provider 反而增加理解成本，不能仅因出现重渲染就认定设计有问题。

## 追问：用 useMemo 包住 Provider value 就解决了吗？

1. 它主要避免依赖未变时反复创建新对象。例如父级一个不相关弹窗更新，主题和用户都没变，缓存可以让 Provider 继续使用原引用，避免仅由对象新建引起的消费者通知。

2. 只要 value 的真实依赖改变，缓存结果也应该改变。把搜索词列入依赖后，输入仍会更新所有读取该 Context 的组件；如果漏写依赖来保留旧引用，得到的是过时数据，不是有效的性能优化。

3. 我会先明确消费者需要的数据范围，再决定拆 Context 或下放状态。随后重复相同输入操作检查提交耗时和更新范围，不能只看 useMemo 已经写上，就假定用户感受到的卡顿一定减少。

## 追问：状态和 dispatch 拆开有什么实际作用？

1. 比如任务面板包含数量展示和“清空已完成”按钮。数量展示必须读取任务状态，按钮只需要 dispatch 一个动作；合在同一个 Context 时，按钮也会因为任务内容变化收到不必要的通知。

2. useReducer 返回的 dispatch 身份稳定，可以单独通过一个 Provider 传下去。按钮读取动作 Context，就不再因为状态 Context 的 value 变化而被该订阅直接触发，但父级渲染造成的更新仍需另行分析。

3. 这种拆分适合确实存在只发动作的消费者，并不是要求每个 Context 都拆两份。若按钮还要根据选中数量显示禁用状态，它仍然需要相应数据，不能为了少更新把必要的界面依赖隐藏掉。我会保留按钮禁用所需的最小订阅，而不是让按钮在没有可清理任务时仍错误地允许操作。
