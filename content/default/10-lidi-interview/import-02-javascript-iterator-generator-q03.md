# 生成器能提前结束吗？

## 核心回答

1. 生成器可以提前结束，我会区分内部主动返回和外部要求关闭两种情况。内部执行到 `return` 后通常返回完成结果；外部调用迭代器的 `return()`，则是在当前暂停位置发起退出，不必继续消费剩余数据。

2. 例如一个生成器依次产出多条记录，消费者只需要第一条，就可以在拿到结果后关闭它。普通情况下，关闭返回的结果中 `done` 为真，后续再调用 `next()` 也不会重新开始，想重读需要重新创建生成器对象。

3. 资源清理适合放在生成器内部的 `try...finally` 中。已经进入这个区域并暂停后，外部关闭会让它执行清理代码；但如果一次 `next()` 都没调用过，函数体尚未进入，不能指望里面的清理语句执行。

4. 使用 `for...of` 时，在循环体里 `break` 或提前返回，会尝试调用迭代器的关闭方法。因此，如果要封装分批读取记录的逻辑，我会把释放资源和迭代协议配套设计，而不是要求每个调用方都记住额外收尾。

5. 不过，调用 `return()` 不一定当场得到完成状态。如果 `finally` 内又执行了 `yield`，它会再次暂停，清理代码后半段仍未结束；实际写清理逻辑时，我会避免在这里产出业务数据，减少这种难以发现的生命周期问题。

## 追问：为什么调用 return 后还可能得到 done 为假？

1. 可以设想生成器先在 `try` 中产出一条记录，又在 `finally` 中产出一个清理提示。消费者读完第一条再调用 `return()`，执行会先进入清理区域，碰到第二个 `yield` 就暂停，此时返回的仍是一个未完成结果。

2. 这不表示关闭请求丢失，而是退出过程还没有走完。调用方继续执行 `next()`，才有机会让清理区域完成并结束生成器；如果清理中再次返回或抛错，还可能改变原先的退出结果，不能只看第一次调用的方法名。

3. 因此我不会把“收到清理提示”等同于“资源已释放”。如果需要通知进度，可以把通知放在独立回调里，清理区域只负责确定性的收尾，并用提前退出的用例核实关闭后资源状态。

## 追问：直接丢弃迭代器能保证执行 finally 吗？

1. 不能把垃圾回收当成生成器的关闭协议。外部不再保存迭代器，只意味着对象将来可能变得不可达，并不等于语言会主动调用它的 `return()`，所以也不能依靠这种方式完成文件关闭或业务解锁。

2. 手动调用 `next()` 消费数据时，我会让负责消费的一层同时负责退出清理。假设中间处理可能抛错，可以在消费者的 `finally` 中检查并调用关闭方法，这样正常结束、主动放弃和异常路径都有明确的责任人。

3. 使用循环语法也要认识到边界：循环体提前退出会尝试关闭，但这不是所有错误来源的统一保险。尤其是迭代器自己的取值逻辑失败时，资源管理仍应由实现方保证，不能把清理全部寄托在消费者身上。
