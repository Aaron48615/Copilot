# 路由守卫有哪些？怎么用它做登录拦截？

## 核心回答

1. 路由守卫可以按范围理解：全局有 beforeEach、beforeResolve、afterEach，路由记录可以配置 beforeEnter，组件内有进入、更新和离开相关守卫。前置守卫能参与允许、取消或重定向，afterEach 适合标题和统计等后续动作，不能把它当成阻止导航的位置。

2. 登录拦截通常先看目标路由的 meta 是否要求登录，再检查当前身份。没有身份时跳到登录页，并记录经过校验的原目标，成功后恢复访问；登录页本身要避免重复拦截，否则跳到登录页又被重定向到登录页，会形成循环。

3. 本地 token 存在不等于当前会话一定有效，可能已经过期或权限变化。需要根据应用流程确认用户状态，接口继续做真实授权；守卫主要改善前端访问流程，隐藏页面或按钮不能阻止用户绕过界面直接请求敏感资源。

4. Vue Router 4 可以通过返回值表达取消、放行或重定向，异步守卫也可等待必要检查。next 兼容写法要确保每条逻辑路径正确调用，不能一条分支调用后又落到另一次调用；我更倾向用清晰返回减少遗漏和重复的问题。

5. 动态参数变化可能复用组件，单靠 beforeEnter 不一定覆盖同记录参数更新，需要具体字段监听或更新守卫。离开编辑页可以检查未保存内容，重定向后也要处理导航失败与请求取消；测试应包括直接访问、刷新、过期登录和取消离开，而不仅是从首页正常点击。

## 追问：为什么 beforeEnter 没有在每次 query 或 params 变化时执行？

1. beforeEnter 是路由记录的进入守卫，不是这个记录上所有位置变化的通用监听。同一详情记录从一个编号换到另一个编号，或只修改 query，可能复用已有组件，不重新经过预期的进入过程，不能依赖它刷新所有数据。

2. 详情查询可以监听具体参数，也可以使用组件路由更新守卫，根据变化重新获取。若全局守卫承担身份检查，则继续按全局规则工作，页面内部的数据更新和路由级是否允许访问应分清，不必把所有逻辑都集中到一个 beforeEnter。

3. 我会测试同记录参数切换、跳到不同记录和浏览器后退，确认每种变化执行对应动作。尤其请求要处理返回乱序，否则守卫触发正确，旧详情仍可能覆盖新详情，路由生命周期不能代替请求有效性管理。

## 追问：登录后跳回原页面，为什么要校验 redirect？

1. redirect 可能来自 URL，不能默认由可信代码生成。若允许任意外部地址，可能把用户登录后的导航带到不期望的网站；应限定为应用允许的站内目标，并处理格式错误、无权限或循环跳转的情况。

2. 登录成功也不代表所有站内页面都有权限，恢复目标时仍需正常的路由和接口校验。若原页面已删除或当前角色不能访问，可以返回合适首页并解释原因，不能因为“是登录前保存的地址”就绕过检查。

3. 我会使用路由库生成和解析目标，并区分 push 与 replace，避免用户返回时又落到无意义的登录中间页。测试要覆盖空目标、特殊字符和指向登录页自身的目标，确认流程可预测而不会反复重定向。
