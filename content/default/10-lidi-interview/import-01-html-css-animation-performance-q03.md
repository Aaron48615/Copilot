# 移动端为什么更容易卡？

## 核心回答

1. 手机更容易卡，首先是机器差很多。不是所有手机都比电脑慢，但常见中低端机器留给页面的 CPU、GPU、内存余量更小。同样的长列表、复杂动效、脚本计算，更容易把可用时间吃完。

2. 屏幕像素密度也会把成本抬高。CSS 里看着不大的图，解码后可能占很多内存；再叠模糊、阴影、透明动画，绘制和合成更重。文件下载小，不等于解码后的像素少，这两笔账得分开看。

3. 手机还会受温度、电量、别的 App 影响，刚打开和用了一会儿表现可能不一样。手指一滑同时触发很多事件处理或同步布局，跟手性马上掉下来，所以要看真实滑动，别只看首屏加载。

4. 继续优化就先减同时干活的节点和效果，图给合适尺寸，长列表控制渲染范围，再对着记录里最重的那截下手。代表性真机、连续滚动、反复开关弹层都要过。桌面模拟适合初步定位，替不了最终结论。

## 追问：图片已经压缩得很小，为什么仍然占内存？

1. 压缩文件小，省的是网络。显示时图片通常要解码成像素。一张分辨率很高的照片，压缩后体积不大，解码后照样存大量像素。列表里同时亮好几张，成本会叠起来。

2. 按实际显示宽度和像素密度给不同尺寸，别一律下原图。缩略图用缩略资源，详情大图按需加载。设宽高比只能稳住布局，减不了原图解码需要的像素数。

3. 还要看离屏图和轮播预加载是不是太多，别为了「提前准备」把所有大图一起解码。网络、内存、滑动手感一起看，报一个压缩比例说明不了图片性能已经好了。

## 追问：长列表一定要做虚拟列表吗？

1. 不一定。先看条目数量、每项有多复杂、真机滚动怎么样。小列表普通渲染更简单。主要问题是图太大、单项组件反复更新，硬上虚拟列表会把复杂度加上去，主要开销却没动。

2. 节点真的很多，可以只渲染可视区附近，外面留一点预渲染。可变高度、快速滚动、焦点在哪、滚回去位置对不对，都得处理，不然容易空白、跳动，或者键盘够不到内容。

3. 拿最容易卡的那类列表先验收益，再看搜索、打印、读屏怎么用。分页、分段加载也行。按内容怎么被访问来选，别把虚拟化当成所有移动页面的标配。
