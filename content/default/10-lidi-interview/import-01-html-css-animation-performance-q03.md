# 移动端为什么更容易卡？

## 核心回答

1. 移动端更容易卡，首先是目标设备的处理能力和资源限制差异很大。不能把所有手机都看成比电脑慢，但常见中低端设备留给页面的 CPU、GPU 和内存余量较小，同样的长列表、复杂动效和脚本计算更容易超过可用时间。

2. 屏幕像素密度也会影响成本。CSS 中看起来不大的图片，解码后可能占用大量内存；再叠加模糊、阴影和透明动画，绘制与合成的工作会增加。图片下载体积小不代表解码后的像素数量小，两种成本需要分别观察。

3. 手机还会受温度、电量状态和其他应用影响，同一台设备刚打开与连续使用一段时间的表现可能不同。触摸滚动同时触发很多事件处理或同步布局时，用户也更容易直接感受到跟手性下降，所以要看真实交互而不只是首屏加载。

4. 如果继续优化，我会先减少同时工作的节点和效果，为图片提供合适尺寸，控制长列表渲染范围，再针对记录中最重的部分调整。验证应覆盖有代表性的真机、连续滚动和重复开关弹层，桌面设备模拟只适合初步定位，不能代替最终结论。

## 追问：图片已经压缩得很小，为什么仍然占内存？

1. 压缩文件大小是网络传输成本，显示时图片通常需要解码成像素数据。比如一张很高分辨率的照片，即使压缩后文件不大，解码后依然要存储大量像素，列表同时展示多张时成本会累积。

2. 我会根据实际显示宽度和像素密度提供不同尺寸资源，而不是一律下载原图。缩略图用缩略资源，详情大图按需加载；设置宽高比只能稳定布局，并不会减少原始图片解码需要的像素数量。

3. 还要检查离屏图片和轮播预加载是否过多，避免为了“提前准备”把所有大图一起解码。优化时同时观察网络、内存和滑动体验，不能只报告文件压缩比例就认为图片性能问题已经解决。

## 追问：长列表一定要做虚拟列表吗？

1. 不一定。先看条目数量、每项复杂度和真实滚动表现，小列表用普通渲染更简单。若主要问题是图片太大或单项组件反复更新，直接引入虚拟列表可能增加复杂度，却没有解决主要开销。

2. 确实有大量节点时，可以只渲染可视区附近的条目，并保留合理的预渲染范围。但可变高度、快速滚动、焦点位置和滚动恢复都需要处理，否则可能出现空白、跳动或键盘访问不到内容。

3. 我会先拿最容易复现卡顿的一类列表验证收益，再评估搜索、打印和辅助技术的使用需求。分页或分段加载也是可选办法，选择应基于内容访问方式，而不是把虚拟化当成所有移动页面的标准配置。
