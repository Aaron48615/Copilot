# 为什么错误页面要有 resetKey？

## 核心回答

1. 错误边界捕获错误后，通常会在自己的状态里记住失败，并持续显示替代界面。外部路由参数改变不一定会自动清掉这份状态，所以用户从出错商品切到另一商品，仍可能停留在旧错误页，看起来像新页面也坏了。

2. resetKey 或 resetKeys 常是业务封装或边界库提供的接口，不是 React 所有错误边界自带的固定属性。它通常用商品编号等身份值判断何时重置错误；React 自身也可通过改变边界的 key 重新挂载，但两者具体接口不能混称。

3. 重置条件应表达失败上下文改变，例如从商品 A 切换到 B。不能每次 render 都传随机值，否则错误一出现马上重新渲染、再次失败，可能形成反复尝试；同一个资源的手动重试也应有明确按钮和状态反馈。

4. 重置错误状态只是允许重新尝试，必须同时考虑底层问题是否已修复。接口缓存需要失效或重新获取，lazy 的失败 Promise 可能已缓存，单清空边界并不保证重新下载；缺失的发布资源更不是重建组件就会重新存在。

5. 我会测试两个方向：同一对象失败后重试，以及切换到另一个对象能否恢复。同时检查重置是否丢掉周围未保存数据，边界范围尽量对应独立功能，避免为了恢复一个卡片把整页表单和导航状态一起清空。

## 追问：resetKey 和 React 的 key 是一回事吗？

1. 不是，React 的 key 参与元素身份识别，改变后通常会卸载旧实例并创建新实例。resetKey 是组件或第三方库自行定义的普通接口，它可能只重置错误状态，是否重挂载子树要看具体实现和文档。

2. 因此不能凭名字相似就假定所有边界都支持。使用某个库时，我会确认属性名、触发比较方式以及重置回调能做什么；自己实现时则明确把资源身份变化和错误状态清除写成可理解的逻辑。

3. 选择还影响草稿保留。改变较高层的 key 会重置整片局部状态，只清边界可能影响更小；恢复错误时应说明希望保留什么，再决定重置范围，而不是只要页面重新出现就算修好了。

## 追问：重试按钮点击后马上又失败，应该怎样处理？

1. 先判断是否真的重新执行了失败操作。若只是清掉错误状态，而读取的仍是已拒绝的资源或旧缓存，界面可能立刻再次抛错；需要同时提供真正的数据刷新或资源重试机制，按钮才有实际意义。

2. 如果新请求确实发出但仍失败，应展示可理解的失败信息并限制连续自动重试。断网、权限问题和资源不存在的处理不同，不能无限循环点击或自动刷新，把服务器压力和用户等待都不断增加。

3. 发布后脚本文件失效时，可以在确认适用后引导刷新到最新页面，但要考虑未保存输入和重复刷新。如果继续完善，我会检查旧构建资源的保留时间和入口缓存策略，让仍打开旧页面的用户能继续加载对应脚本，并验证更新提示不会造成循环刷新。
