# 为什么错误页面要有 resetKey？

## 核心回答

1. 错误边界抓住错误后，通常在自己的 state 里记住失败了，一直显示替代界面。外面路由参数变了，这份状态不一定会自动清。用户从出错的商品切到另一个商品，可能还停在旧错误页，看起来像新页面也坏了。

2. `resetKey` 或 `resetKeys` 常常是业务封装或边界库给的接口，不是 React 所有错误边界自带的固定属性。一般用商品编号这种身份判断何时重置。React 自己也可以改边界的 `key` 让它重新挂载。两套接口别混着叫。

3. 重置条件应表达失败的上下文变了，比如从商品 A 切到 B。每次 render 都传随机值，错误一出现马上再渲染、再失败，可能反复试。同一资源手动重试，用明确的按钮和状态反馈。

4. 重置错误状态只是允许再试一次，底下的问题修没修好是另一回事。接口缓存可能要失效或重新获取；`lazy` 失败的 Promise 可能已经缓存住了，只清空边界不保证重新下载。发布资源本来就缺失，重建组件也不会变出来。

5. 两个方向都测：同一对象失败后点重试；切到另一个对象能不能恢复。重置会不会把周围没保存的数据清掉也要看。边界范围尽量对应独立功能，恢复一张卡片别把整页表单和导航状态一起清掉。

## 追问：resetKey 和 React 的 key 是一回事吗？

1. 不是。React 的 `key` 参与元素身份，改了通常会卸掉旧实例、建新实例。`resetKey` 是组件或第三方库自己定义的普通接口，可能只重置错误状态。子树重不重新挂，看具体实现和文档。

2. 名字像，不代表所有边界都支持。用某个库时，确认属性名、怎么比较、重置回调能做什么。自己实现就把资源身份变化和错误状态清除写成能读懂的逻辑。

3. 选择还会影响草稿。改比较高那层的 `key` 会重置一大片局部状态；只清边界影响可能更小。恢复错误时说清楚希望留下什么，再决定重置范围。页面重新出现了，不等于修好了。

## 追问：重试按钮点击后马上又失败，应该怎样处理？

1. 先看失败操作有没有真的再执行一遍。只清了错误状态，读的还是已经拒绝的资源或旧缓存，界面可能立刻再抛。按钮要配合真正的数据刷新或资源重试，才有意义。

2. 新请求确实发出去了但仍失败，给出能看懂的失败说明，连续自动重试要收住。断网、没权限、资源不存在，处理不一样。别无限点、也别自动不停刷新，服务器和用户都会被拖住。

3. 发布后旧脚本文件失效，确认是这种情况再引导刷新到最新页面，同时考虑没保存的输入、以及会不会循环刷新。旧构建资源留多久、入口怎么缓存，也要查。还开着旧页面的用户要能加载对应脚本，更新提示不该造成循环刷新。
