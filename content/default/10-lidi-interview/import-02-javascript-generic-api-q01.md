# 泛型约束什么时候需要？

## 核心回答

1. 我会在函数确实依赖某种能力时加泛型约束，比如按编号查找对象时，需要声明 `T extends { id: string }`。这表示传入值至少有字符串编号，同时保留它原本的其他字段，调用者拿到结果后仍能使用自己的具体类型。

2. 约束应该从函数内部的操作倒推，而不是从某个页面的完整数据倒推。如果函数只读取编号，就不必要求名称、头像和创建时间都存在，否则本来能处理的数据也会被拒绝，公共函数反而只能服务一个页面。约束越贴近实际操作，调用者就越容易理解为什么某类输入能传、另一类输入不能传。

3. 如果输入与输出之间没有需要保留的类型关系，我会先考虑普通参数类型。例如只返回编号的函数可以接收带编号的对象，返回字符串就足够；原样返回输入对象时，泛型才更能体现保留具体类型的价值。

4. 泛型约束只参与编译检查，不会在运行时检查服务器返回的数据。假设网络结果需要传入这个函数，我会先验证编号是否存在、是否为字符串，再进入有类型的处理流程，不能用一次类型断言代替实际验证。

## 追问：为什么字段访问函数要写 K extends keyof T？

1. 这里要表达的是两个参数之间的关系：第二个参数必须是第一个对象允许访问的键。只把键写成字符串虽然方便，却会接受拼错的字段名，也无法准确说明读取结果对应哪一种字段类型。

2. 返回类型可以写为 `T[K]`，这样读取名称时得到名称的类型，读取数量时得到数量的类型。如果把结果统一写成字符串或任意类型，就丢掉了这个函数最值得保留的输入输出关系。

3. 这个限制仍然不是外部输入的验证器，用户输入的字符串不能直接视为合法键。如果键来自表单或地址参数，我会先用允许的字段列表进行检查，并明确缺失或可选字段可能返回空值的处理方式。

## 追问：满足约束后，为什么不能随便构造一个对象作为 T 返回？

1. 约束只是最低要求，调用者传入的具体类型可能还有更多必填字段。比如约束只有编号，而具体类型还要求名称，只新建一个带编号的对象并不能满足调用者对完整结果的期待。

2. 因此，函数声明返回泛型时，不能把“满足约束”当成“满足所有可能的具体类型”。如果实际只生产带编号的对象，就应把返回类型写成这个基础结构，让调用方看到真实的能力范围。

3. 如果确实需要生成具体对象，可以让调用方提供负责创建对象的函数，由它补齐特有字段。这是一个可选设计，要根据调用需求决定，不能为了绕过编译错误直接强制断言成泛型类型。
