# 泛型约束什么时候需要？

## 核心回答

1. 函数确实依赖某种能力时才加泛型约束。比如按编号查找对象，声明 `T extends { id: string }`。这表示传入值至少有字符串编号，同时保留它原本的其他字段，调用者拿到结果后仍能用自己的具体类型。

2. 约束从函数内部真正做的操作倒推，别从某个页面的完整数据倒推。函数只读编号，就不必要求名称、头像、创建时间都在，不然本来能处理的数据也会被拒，公共函数反而只能服务一个页面。约束越贴近实际操作，调用者越容易理解为什么这类能传、那类不能传。

3. 输入与输出之间没有需要保留的类型关系，先考虑普通参数类型。只返回编号的函数，接收带编号的对象，返回字符串就够。原样返回输入对象时，泛型更能体现「保留具体类型」的价值。

4. 泛型约束只参与编译检查，不会在运行时检查服务器返回的数据。网络结果要传入这个函数，先验证编号在不在、是不是字符串，再进入有类型的处理流程。一次类型断言替不了实际验证。

## 追问：为什么字段访问函数要写 K extends keyof T？

1. 这里要表达的是两个参数之间的关系：第二个参数必须是第一个对象允许访问的键。只把键写成字符串虽然方便，却会接受拼错的字段名，也说不准读取结果对应哪一种字段类型。

2. 返回类型可以写成 `T[K]`，读名称时得到名称的类型，读数量时得到数量的类型。结果统一写成字符串或任意类型，就丢掉了这个函数最值得保留的输入输出关系。

3. 这个限制仍然不是外部输入的验证器。用户输入的字符串不能直接当成合法键。键来自表单或地址参数，先用允许的字段列表检查，缺失或可选字段可能返回空值，处理方式也要说清。

## 追问：满足约束后，为什么不能随便构造一个对象作为 T 返回？

1. 约束只是最低要求，调用者传入的具体类型可能还有更多必填字段。约束只有编号，具体类型还要求名称，只新建一个带编号的对象，满足不了调用者对完整结果的期待。

2. 函数声明返回泛型时，「满足约束」不等于「满足所有可能的具体类型」。实际只生产带编号的对象，就把返回类型写成这个基础结构，让调用方看到真实能力范围。

3. 确实需要生成具体对象，可以让调用方提供负责创建对象的函数，由它补齐特有字段。这是可选设计，看调用需求。别为了绕过编译错误，直接强制断言成泛型类型。
