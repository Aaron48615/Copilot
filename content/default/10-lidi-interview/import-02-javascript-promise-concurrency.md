# 前端请求并发太多时怎么控制？

## 核心回答

1. 我会先确认请求多是批量任务的正常需求，还是重复触发造成的，因为后者应先做去重或减少调用。对于确实需要执行的大量独立任务，可以维护一个队列，限制同时运行的数量，一个结束后立即补下一个。

2. 队列里保存的是尚未调用的任务函数，而不是已经创建好的请求 Promise。假设要上传一百张图片，可以先尝试较小的并发上限，但具体数值需要结合文件大小和接口限制验证，不能把某个数字当作通用最佳值。

3. 实现时可以启动固定数量的 worker，共享下一个任务的下标，并在 await 之前领取任务。每个 worker 用 try 捕获调用异常和异步拒绝，记录结果后继续领取，避免失败让整个调度链条断开或名额无法释放。

4. 返回结果要按输入下标存放，不要按完成顺序直接追加，否则页面可能把上传结果对应到错误图片。取消、重试和部分失败也要有明确状态，特别是取消时，未启动的任务与正在执行的任务需要分别处理。

5. 并发上限应是正整数，空队列应正常结束，上限大于任务数也不应制造无用工作。它只能约束这一套调度器中的任务，不能自动协调所有标签页，也不能替代服务端限流；存在依赖的任务还需要先保证执行顺序。

## 追问：并发上限该怎样选择和调整？

1. 我会从接口约定和任务性质出发，上传大文件与查询小数据不应该直接共用同一个经验值。假设服务端没有给出明确限制，可以先采用保守配置，再观察完成耗时、错误率和浏览器资源占用，逐步比较不同配置。

2. 如果增加并发后整体完成时间几乎不再缩短，却出现更多超时或限流响应，就说明继续增加可能得不偿失。还要区分网络慢和服务端处理慢，不能仅凭某一次请求变慢，就认定是浏览器连接数达到了某个固定上限。

3. 是否动态调整要看规模，普通页面先保留可配置的固定上限通常更容易维护。若后续确有需求，再考虑遇到限流降低并发、稳定后缓慢恢复，并设置最小值与最大值，避免调整过于频繁导致请求速度来回波动。

## 追问：怎样保证结果顺序并避免重复领取任务？

1. 我会在领取时保存当前下标并马上递增共享游标，然后才执行异步等待，完成后把结果写回对应位置。在同一个 JavaScript 执行环境里，这段同步领取不会被另一个普通回调中途插入，因此不会因响应先后而领取同一项。

2. 失败结果同样占据自己的位置，并带上原任务标识，不能因为失败就跳过数组位置。这样假设第三张图片上传失败，用户仍然能准确重试第三张，而不是在删除失败项后让后面的图片与结果全部错位。

3. 如果加入重试，重试应延续原任务身份，同时防止首次请求的迟到结果覆盖新的尝试。共享游标这个做法只适用于当前运行环境；一旦跨 worker 或多进程分发任务，就需要消息协调，不能把单线程前提照搬过去。
