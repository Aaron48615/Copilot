# IndexedDB 失败时怎么办？

## 核心回答

1. IndexedDB 失败时，先判断它保存的是可重建缓存，还是用户唯一的本地数据。缓存失败可以回到网络去取；离线草稿失败却不能悄悄忽略。否则界面提示保存成功，刷新后内容没了，对用户影响差很多。

2. 初始化可能被权限、存储空间或数据库升级挡住，读取和写入也可能在事务阶段失败。应用应结束等待，给出可恢复状态，别让页面永远转 loading。日志记下错误类型和版本就行，用户保存的正文别完整上报。

3. 对可选缓存，数据库不可用时保持核心网络流程。写入失败不应让已经成功的查询也报错。网络也不可用时，要说明当前没有可读取数据，不能用空列表伪装成服务器真的返回了零条记录。

4. 对草稿或离线队列，事务真正完成之后才标记本地保存成功。失败时把内存里的编辑内容留下，并提供重试或导出办法。重新联网同步还需要幂等键和冲突处理。一串旧请求无条件重放、盖掉服务器新数据，不行。

5. 排查覆盖配额不足、多标签升级、用户清理存储这些条件。删除整个数据库只能作为确认可丢弃数据之后的恢复方式，不能一遇到异常就自动清空。设计时说清楚哪些数据有服务端副本，哪些需要用户主动处理。

## 追问：数据库升级被另一个标签页阻塞，怎么处理？

1. 旧标签页可能还握着旧版本数据库连接，新标签页请求更高版本时就会遇到 blocked。这不一定是数据损坏。先处理连接生命周期，别反复删数据库，也别不停抬版本号试图绕过去。

2. 旧页面应监听 `versionchange`，在合适时机关掉数据库连接并提示更新；新页面说明正在等其他页面释放连接。关闭前还要处理未保存的编辑，别为了升级成功就把用户在另一页的草稿丢掉。

3. 升级逻辑写在版本变更事务里，从旧结构到新结构的迁移说清楚，并验证失败时怎么表现。测试至少同时打开两个标签页，让一个保持旧连接，再启动新版本，确认用户能理解并完成恢复步骤。

## 追问：磁盘配额不足，怎样清理才不会丢草稿？

1. 把可重建缓存和用户草稿分开存，或者明确分类。优先清过期资源、旧查询结果和已经同步的数据。别按最早创建时间一刀切，因为一个很早的未同步草稿，可能仍是用户唯一副本。

2. 清理后有限重试写入，并明确告知有没有保存成功。可以用存储估算信息辅助判断，但配额和可用空间会变，浏览器也可能回收数据。估算结果代替不了事务完成检查，也代替不了服务端持久保存。

3. 如果还是失败，把当前编辑留下来，并提供导出或复制方式，由用户决定怎么处理。验证时模拟写入失败和再次打开页面，确认界面不会显示虚假的已保存提示，也不会在恢复过程中盖掉还没同步的内容。
