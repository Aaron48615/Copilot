# 瀑布流布局怎么实现？

## 核心回答

1. 瀑布流的特点是卡片宽度接近、高度不同，同时尽量减少列之间的空隙。比较直观的 JavaScript 做法是：按容器宽度、列宽和间距算出列数，再记下每一列已经排到的高度，决定下一张卡片放哪。

2. 放卡片时选当前最短的一列，算出横坐标和纵坐标，再把这列高度加上卡片高度和间距。用绝对定位时，还要把容器高度设成最大列高。不然子项脱离普通文档流，后面的内容可能压到卡片上。

3. 图片高度尽量在加载前就确定。可以让接口提供宽高，用宽高比算出展示高度并预留位置。拿不到尺寸时，得在图片加载后再调，但要考虑页面会不会跳。随手给一个高度占位，布局照样可能跳动。

4. 加载更多可以用 `IntersectionObserver` 观察底部哨兵，同时记下请求中、失败、没有更多这些状态。容器尺寸变了要重新算列数，长列表还要考虑虚拟化。首屏关键图片别因为统一懒加载而推迟展示。

5. CSS columns 实现简单，但视觉顺序和阅读顺序要对一下。普通 Grid 也不会自动解决所有瀑布排列问题。按内容顺序、浏览器兼容和交互要求选方案。截图上看着没有空洞，还不够，键盘导航和动态追加后的体验也要看。

## 追问：图片加载失败，会不会把后面卡片的位置算错？

1. 如果布局基于接口给出的宽高比，图片失败时仍可保留原尺寸，换成占位内容，后面的卡片不必全部挪。这样错误处理和布局一致，不会因为一张图失败，这一列突然缩短一大截。

2. 如果卡片高度还受标题或说明影响，就得量完整卡片，不能只算图片高度。文字换行、字体加载、失败提示都可能改高度。必要时用尺寸观察更新布局，并避免观察回调反过来反复触发自己。

3. 正常、失败、慢加载、特别长的标题都要分别验。需要重新布局时，尽量集中计算再应用结果，把当前阅读位置留住。别每完成一张图片就无条件重排全部卡片，页面会连续抖。

## 追问：触底后为什么会重复请求同一页？

1. 哨兵进入可见范围时，回调可能触发多次。内容高度变化，或者重新观察，也会再触发。只加防抖不够：上一个请求还没完成时，新的观察结果仍可能满足触底条件，得有明确的请求中状态。

2. 发请求前同步设上 loading，成功后推进游标，失败则保留原游标供重试。还要判断 `hasMore`，没有数据了就别再请求。切换筛选条件时重置列表，上一轮迟到的结果也要丢掉。

3. 服务端分页可能因为新增内容返回重复项，前端可以按稳定记录标识去重，但不能只靠数组长度推页码。测试时让接口慢一些，再反复滚动、切换筛选，更容易复现，也更容易确认状态处理对不对。
