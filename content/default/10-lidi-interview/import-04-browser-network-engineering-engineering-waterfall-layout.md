# 瀑布流布局怎么实现？

## 核心回答

1. 瀑布流的特点是卡片宽度接近、高度不同，同时尽量减少列之间的空隙。比较直观的 JavaScript 做法是根据容器宽度、列宽和间距计算列数，再记录每一列已经排到的高度，决定下一张卡片的位置。

2. 放卡片时选择当前最短的一列，计算横坐标和纵坐标，再把这列的高度加上卡片高度与间距。使用绝对定位时还要把容器高度设为最大列高，否则子项脱离普通文档流，后面的内容可能压到卡片上。

3. 图片高度要尽量在加载前确定，可以让接口提供宽高，用宽高比计算展示高度并预留位置。拿不到尺寸时需要在图片加载后调整，但要考虑页面位移；不能只给一个随意高度占位就承诺布局不会跳动。

4. 加载更多可以用 IntersectionObserver 观察底部哨兵，同时记录请求中、失败和没有更多等状态。容器尺寸变化时重新计算列数，长列表还要考虑虚拟化；首屏关键图片不要因为统一懒加载而延迟展示。

5. CSS columns 实现简单，但视觉顺序与阅读顺序需要验证，普通 Grid 也不会自动解决所有瀑布排列问题。我会按内容顺序、浏览器兼容和交互要求选方案，不能只看截图没有空洞，就忽略键盘导航和动态追加后的体验。

## 追问：图片加载失败，会不会把后面卡片的位置算错？

1. 如果布局基于接口给出的宽高比，图片失败时仍可保留原尺寸并显示占位内容，后续卡片不必全部移动。这样错误处理与布局一致，不会因为一张图失败就让这一列突然缩短一大截。

2. 如果卡片高度还受标题或说明影响，就需要测量完整卡片，而不是只计算图片高度。文字换行、字体加载和失败提示都可能改变高度，必要时用尺寸观察更新布局，并避免观察回调反复触发自己。

3. 我会分别验证正常、失败、慢加载和特别长的标题。若需要重新布局，尽量集中计算并应用结果，保持当前阅读位置，不要每完成一张图片就无条件重排全部卡片，造成连续抖动。

## 追问：触底后为什么会重复请求同一页？

1. 哨兵进入可见范围时可能多次触发回调，内容高度变化或重新观察也会再次触发。仅添加防抖不够，因为上一个请求尚未完成时，新的观察结果仍可能满足触底条件，需要明确的请求中状态。

2. 我会在发请求前同步设置 loading，成功后推进游标，失败则保留原游标供重试。还要判断 hasMore，避免没有数据后继续请求；切换筛选条件时应重置列表并忽略上一轮迟到的结果。

3. 服务端分页可能因为新增内容返回重复项，前端可以按稳定记录标识去重，但不能只靠数组长度推导页码。测试时让接口慢一些，再反复滚动和切换筛选，更容易复现并确认状态处理是否正确。
