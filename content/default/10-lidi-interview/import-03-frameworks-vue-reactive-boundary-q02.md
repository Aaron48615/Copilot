# shallowRef 什么时候有用？

## 核心回答

1. shallowRef 只让 value 这一层保持响应式，不会像普通 ref 那样把新传入的普通对象深层转换成响应式对象。给 value 替换一个新对象可以触发依赖更新，但对内部普通属性直接赋值，通常不会仅因这个 shallowRef 而触发界面变化。

2. 它适合保存不希望被深层代理的第三方实例，例如图表、编辑器或外部状态容器。组件只需要知道实例是否已经创建或替换，不需要 Vue 跟踪实例内部所有字段；这也能避免某些依赖原始对象身份的库受到代理影响。

3. 大型、按不可变方式更新的数据也可以考虑 shallowRef。比如读取一批结构很深的只读记录，平时只展示，更新时替换整个数组，可以减少深层响应式访问相关开销；但要先确认瓶颈，不是数组稍微大一点就必须换成浅响应式。

4. 代价是调用方必须遵守更新约定。直接修改 rows.value 中某一项的字段，界面可能不会变化；应创建更新后的新数组，或者在确实进行外部深层修改后有意识地使用 triggerRef，不能一会儿依赖自动跟踪、一会儿手动通知却没有统一规则。

5. 我会把这类状态的使用范围和更新入口收拢，避免其他组件误以为里面每个字段都可直接响应。测试要覆盖整体替换和深层修改的区别；如果值本来已经是响应式对象，shallowRef 也不会替我们取消它已有的响应式，仍要检查真实来源。

## 追问：shallowRef 保存大数组后，改一行怎样让界面更新？

1. 最清楚的方式是采用不可变更新，为命中的记录创建新对象，再把新数组赋给 value。外层引用发生变化，依赖这个 shallowRef 的界面就会重新读取；其他记录可以保留原引用，不必深复制整批数据。

2. 如果外部库已经原地修改内部数据，可以在完成修改后调用 triggerRef 通知依赖。但这是一种明确的手动更新协议，遗漏通知就可能不刷新，调用过多又会增加工作，所以不适合让每个组件随意决定何时触发。

3. 我会用同一测试先修改内部字段、再执行规定的替换或通知，确认团队理解两者区别。选 shallowRef 的目的在于明确边界和减少必要成本，不是让原来的随意修改代码不变、只替换一个 API 名称就自动提速。

## 追问：第三方实例放普通 ref 里，一定会出错吗？

1. 不一定，要看实例是否被 Vue 转换、库是否依赖身份，以及内部访问方式。不能把潜在兼容问题说成所有库都会报错；不过对不需要细粒度响应式的复杂实例，深层代理通常没有实际业务收益。

2. 我会优先使用普通局部变量、shallowRef 或合适的 markRaw，选择取决于是否需要在实例建立和替换时更新界面。比如模板要判断编辑器是否就绪，可以浅层保存；完全不参与显示的句柄也不必放进响应式状态。

3. 不管保存方式如何，监听和实例仍要在对应生命周期释放。浅引用只改变跟踪深度，不会自动销毁图表、停止动画或取消网络任务，不能把“不代理”误解成框架已经接管了第三方资源管理。
