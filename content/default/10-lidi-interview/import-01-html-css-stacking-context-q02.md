# 弹窗应该怎么处理层级？

## 核心回答

1. 弹窗层级先确定它属于整个页面还是局部区域。全局模态弹窗通常放在靠近文档根部的统一浮层容器里，少受业务祖先的 `transform`、`opacity`、`overflow` 影响。局部加载遮罩可以留在卡片内部，不必把所有覆盖内容都挂到 `body`。

2. 然后约定少量清楚的层级关系，比如普通内容、固定导航、遮罩、弹窗内容，别让每个组件各自写越来越大的数字。遮罩在背景上面、弹窗在遮罩上面。多层弹窗还得管打开顺序。层级规则要能说清具体关系，别靠谁最后写了 `999999`。

3. 原生 `dialog` 的 `showModal()` 会进顶层，跟普通文档里的 `z-index` 比较不是一回事，适合相应的模态需求。只加 `open` 属性或普通 `show()`，不等于同样的模态行为。原生能力仍要设名称、初始焦点和关闭流程，别只关心是不是盖在最上面。

4. 背景可不可交互、滚动是不是按预期限制、关掉以后焦点能不能恢复，一起查。视觉层级正确只是弹窗能用的一部分。多个弹窗叠着时，关一个不能提前解除最底层的限制；最后一层关完，也不能留下透明遮罩或滚动锁。

## 追问：挂到 body 的弹窗为什么仍然可能有问题？

1. 靠近 `body` 能避开很多业务祖先，但不是绝对保证。根部容器自己可能有影响定位的样式，弹层也可能仍处在不合适的上下文。挂载位置一变，原来依赖祖先的选择器和 CSS 变量继承可能不再一样。

2. 弹层如果是跟着按钮的下拉框，还得把按钮位置换算到所用定位坐标里，并处理滚动和窗口变化。只挪 DOM、不更新定位策略，可能从「被裁掉」变成「位置偏了」。坐标来源和参照方式一起查。

3. 主题、局部样式、点击外部关闭、键盘返回都要测。框架 Portal 或 Teleport 能改挂载位置，具体事件语义和组件状态仍按框架规则理解。移到 `body` 不是层级、定位、交互的一键修复。

## 追问：多层弹窗关闭时怎样避免提前恢复页面滚动？

1. 由统一的弹窗管理逻辑记录当前还开着几层模态，别每个弹窗一关就直接恢复 `body` 样式。内层关了外层还在，页面背景就该继续受限，只有最后一层结束才把原来的状态还回去。

2. 恢复时保存并还原原本的样式和滚动位置，别假定页面开始时 `overflow` 一定是空值。焦点也逐层返回：先回到外层触发入口，最终关闭时再回到页面入口。两套恢复过程要对上。

3. 逐层关闭、一次性关掉全部、路由切换卸载，三条路径都查。异常路径最容易漏计数或残留监听，下一次打开弹窗后页面可能滚不动。验证看完整状态，别只看最上层消没消失。
