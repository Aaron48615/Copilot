# localStorage、IndexedDB 和 Cache Storage 怎么选？

## 核心回答

1. 我会按数据形态和生命周期选择浏览器存储。localStorage 适合少量字符串配置，例如主题偏好，读取简单且同步；但大批量读写或序列化会占用主线程，不适合把大量业务数据当作一个巨大 JSON 反复保存。

2. IndexedDB 适合结构化数据、索引查询和较大的离线内容，读写通过异步事务完成。比如按记录标识保存草稿，比每次读取整份字符串再修改更方便，但要处理数据库升级、事务失败和多个页面同时访问。

3. Cache Storage 面向 Request 与 Response 的缓存，适合静态资源或明确选择的响应。它常和 Service Worker 配合，也可以在页面中使用；它不会像 HTTP 缓存那样自动替我按所有缓存头完成过期策略，需要应用管理。

4. 三者都受同源、安全策略和浏览器存储条件影响，数据可能被用户清理或回收，不应当成永远存在的数据库。用户切换时还要按身份隔离私人数据，不能退出后继续从旧缓存展示上一个账号的信息。

5. 我的原则是配置、小型结构化数据和资源响应各用合适工具，真正业务状态仍明确服务端与本地谁为准。如果继续完善离线能力，会同时设计失败恢复、同步幂等和冲突提示，不能只证明数据能写进去就认为离线功能完成。

## 追问：Cache Storage 会自动遵守 max-age 吗？

1. Cache Storage 是由代码显式管理的缓存空间，不会自动按 HTTP 缓存那套新鲜度规则替你删除过期条目。把响应放进去后，什么时候再取、何时更新或移除，都需要在应用策略中明确处理。

2. 例如缓存接口时，可以记录保存时间并在读取时判断是否需要网络更新，也可以使用网络优先等策略。不能看到响应有 no-store 就假设自定义代码绝对不会把它存入，因此敏感接口应在缓存入口明确排除。

3. 我会将它与浏览器普通 HTTP 缓存分开调试，查看 Application 中的实际条目。验证过期、退出登录和版本切换，确认读取逻辑符合业务，而不是只看 Network 里源站响应头写得正确。

## 追问：多个标签页同时修改本地数据，怎样避免互相覆盖？

1. 首先明确数据更新粒度，避免两个页面各自读取整个对象，修改不同字段后又把整份对象写回，后写入的页面会覆盖前面的变化。IndexedDB 事务可以让同一事务内的读取修改按需要组织，但跨页面业务冲突仍需设计。

2. 可以给记录增加版本号，写入前比较，冲突时重新读取或提示用户；页面之间用 BroadcastChannel 等机制通知变化。通知是帮助同步界面，不应当成绝对可靠的数据库提交凭据，实际结果仍以存储状态为准。

3. 对于用户草稿，我会优先保留冲突内容而不是静默取最后一次写入。测试时开两个标签编辑同一记录，再交错保存，确认能解释哪份生效以及另一份如何恢复，避免只在单标签环境验证。
