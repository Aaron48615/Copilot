# localStorage、IndexedDB 和 Cache Storage 怎么选？

## 核心回答

1. 按数据形态和生命周期选浏览器存储。`localStorage` 适合少量字符串配置，比如主题偏好，读取简单而且同步。但大批量读写或序列化会占主线程，不适合把大量业务数据当成一个巨大 JSON 反复保存。

2. IndexedDB 适合结构化数据、索引查询和比较大的离线内容，读写通过异步事务完成。比如按记录标识保存草稿，比每次读整份字符串再改更方便。但要处理数据库升级、事务失败，以及多个页面同时访问。

3. Cache Storage 面向 Request 与 Response 的缓存，适合静态资源或明确选中的响应。它常和 Service Worker 配合，也可以在页面里用。它不会像 HTTP 缓存那样自动按所有缓存头做完过期策略，需要应用自己管。

4. 三者都受同源、安全策略和浏览器存储条件影响。数据可能被用户清掉或被回收，不能当成永远存在的数据库。用户切换时还要按身份隔离私人数据，退出后别继续从旧缓存展示上一个账号的信息。

5. 配置、小型结构化数据、资源响应，各用合适工具。真正业务状态仍要说清楚服务端和本地谁说了算。如果要完善离线能力，失败恢复、同步幂等和冲突提示要一起设计。数据能写进去，不等于离线功能做完了。

## 追问：Cache Storage 会自动遵守 max-age 吗？

1. Cache Storage 是由代码显式管理的缓存空间，不会自动按 HTTP 缓存那套新鲜度规则替你删过期条目。把响应放进去之后，什么时候再取、何时更新或移除，都要在应用策略里说清楚。

2. 比如缓存接口时，可以记下保存时间，读取时判断要不要网络更新，也可以用网络优先这类策略。看见响应有 `no-store`，不能假设自定义代码绝对不会把它存进去。敏感接口应在缓存入口明确排除。

3. 把它和浏览器普通 HTTP 缓存分开调试，看 Application 里的实际条目。验证过期、退出登录和版本切换，确认读取逻辑符合业务。只看 Network 里源站响应头写得对，不够。

## 追问：多个标签页同时修改本地数据，怎样避免互相覆盖？

1. 先明确数据更新粒度。避免两个页面各自读整个对象，改不同字段后又把整份对象写回去，后写入的页面会盖掉前面的变化。IndexedDB 事务可以让同一事务内的读取修改按需要组织，但跨页面业务冲突仍要设计。

2. 可以给记录加版本号，写入前比较，冲突时重新读取或提示用户。页面之间用 BroadcastChannel 这类机制通知变化。通知是帮着同步界面，不能当成绝对可靠的数据库提交凭据。实际结果仍以存储状态为准。

3. 对用户草稿，优先把冲突内容留下来，别静默取最后一次写入。测试时开两个标签编辑同一记录，再交错保存，确认能解释哪份生效、另一份怎么恢复。只在单标签环境验证，不够。
