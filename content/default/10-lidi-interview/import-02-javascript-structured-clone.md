# structuredClone 能复制什么，不能复制什么？

## 核心回答

1. 结构化克隆适合复制有明确数据约定的状态，例如普通对象、数组、日期、映射集合、集合和二进制缓冲区。它也能处理循环引用，并保留克隆结果内部的共享关系，所以比简单递归赋值更能覆盖实际的数据结构。

2. 不能复制的类型也要提前知道。函数、弱映射、弱集合以及常见的文档节点，都不能直接作为这种数据传递。普通对象可枚举字段里如果藏了函数，通常会导致整个克隆失败，不是只跳过这个字段继续返回其余内容。

3. 自定义类实例需要特别谨慎。它的可枚举数据字段可能复制成功，但原型方法和私有字段不会因此恢复。属性描述符也不是完整照搬，访问器可能在读取时执行。克隆成功不能证明行为、约束和副作用都保持不变。

4. 默认克隆普通缓冲区会复制字节。指定转移则把资源交出去，并让原缓冲区分离，适合发送方不再需要的较大数据。共享缓冲区又是特殊情况，克隆得到的新对象仍可能访问同一块共享内存，不能一概说克隆必然完全隔离。

5. 先列出需要保存的字段和类型，再决定直接克隆还是显式构造数据对象。比如把有方法的实例转换成可传输记录。只修改状态里的一个字段，局部浅复制往往更清楚。要不要深拷贝由隔离需求决定，不是习惯性调用。

## 追问：类实例克隆成功，为什么方法却不见了？

1. 类方法通常定义在原型上，结构化克隆不会把自定义原型链按原样搬过去。一个订单实例有金额字段和计算折扣的方法，结果可能保留金额，却不再具备这个方法。能看到数据，不等于仍然拿到了完整订单实例。

2. 私有字段和构造过程建立的内部约束，同样不能靠复制公开属性还原。直接替换结果原型也未必能修好。方法若访问私有字段，伪装成实例的对象仍会失败。别用改原型来绕过真正需要的初始化过程。

3. 业务需要恢复实例，就提供明确的数据导出与重建过程：先校验记录，再调用构造函数或工厂方法。这样可以有意识地处理版本和默认值，也能把传输数据与对象行为分开，便于判断哪些状态值得保存。

## 追问：克隆失败后可以自动回退到 JSON 吗？

1. 不要无条件回退。两种方式的语义不同，报错本来可能提醒数据里混入了不该出现的函数。直接改用 JSON 可能悄悄删除字段，让调用看似成功，后续使用时才暴露缺失信息，反而更难追查原因。

2. 更稳妥的做法是确认失败类型和数据约定。界面状态中混入了节点引用，就只提取需要保存的编号与显示数据。异常信息可以记录类型和位置，但不应为了定位复制失败，把整份用户数据无筛选地写入日志。

3. 兼容旧环境时，可以选择已明确支持所需类型的实现，或者主动限制输入为可安全序列化的数据。即使采用替代方案，也应测试日期、循环关系和异常字段，公开说明不支持的能力，别让回退悄悄改变调用方的预期。
