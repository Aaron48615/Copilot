# Babel 是怎么把 ES6 转成 ES5 的？

## 核心回答

1. Babel 主要做 JavaScript 源码转换，把目标浏览器还不认的语法改写成能跑的形式。它不是拿字符串替换那么简单。比如箭头函数带着外层的 `this`，只把 `=>` 换成 `function`，意思可能就变了。

2. 流程是解析、转换、再生成。解析得到 AST，插件去访问对应节点、改结构，生成器再吐出代码，需要的话还带 source map。转箭头函数时，必要时会在外层存一个变量，把原来的 `this` 语义留住。

3. 实际配置常用 `preset-env`，按目标环境挑转换插件，不是无差别把所有新语法都降到 ES5。目标来自项目兼容要求和 Browserslist。转得越多，产物和辅助代码可能越大，最后还得在真环境里验行为。

4. 语法转换和运行时 API 补齐是两件事。`Promise`、`includes` 这类能力要有合适的 polyfill，普通 runtime 辅助函数不会自动把所有 API 补齐。Vite 等工具过不过 Babel，看版本和插件，项目用了 Vite 不等于完全没有 Babel。

5. 比如目标浏览器已经认箭头函数，却还不认某个数组方法，就先看生成出来的代码缺哪块运行时能力，别把全部语法都降级。转完还要在目标环境验证，尤其是异步函数、类继承和第三方依赖。构建成功只说明工具能产出文件，运行时能力不一定已经补齐。

## 追问：箭头函数转成普通函数，为什么还要处理 this？

1. 箭头函数没有自己的 `this`，用的是定义位置外层那个。比如对象方法里注册一个箭头回调，回调读的是外层对象。直接改成普通回调后，`this` 可能跟着调用方式走，结果就变了。

2. 转换器会看使用位置，必要时在外层把 `this` 存下来，生成的普通函数再去读这个变量。`arguments`、`super` 这些语义也要单独处理，所以得拿带这些边界的例子看转换结果，别只看一个最简单的加法函数。

3. Babel 也不是把所有代码都翻译成更短的写法。为了语义对得上，产物可能更长。按目标浏览器打开必要的转换，调试用 source map 对着源码看，别直接去改构建后的辅助代码。

## 追问：用了 preset-env，为什么旧浏览器仍报 Promise 未定义？

1. `preset-env` 会不会注入 API 补齐，取决于配置。只转箭头函数，不会凭空给你一个 `Promise`。先分清报错是语法解析失败，还是跑起来缺全局对象，两种问题动手的位置不一样。

2. 应用可以按兼容范围配 `core-js` 和按需注入，同时确认版本、入口、构建目标对得上。异步函数就算已经被转换，生成代码也可能依赖 `Promise`，所以不能只在源码里搜有没有写出这个名字。

3. 如果写的是给别人用的库，还要考虑能不能改宿主的全局环境。该说明所需运行环境，或者选不污染全局的兼容方式，再到实际目标浏览器测。开发服务器能跑，不能当成兼容性已经过关。
