# Babel 是怎么把 ES6 转成 ES5 的？

## 核心回答

1. Babel 主要做 JavaScript 源码转换，可以把目标浏览器不支持的语法改写成兼容形式。它不是简单替换字符串，例如箭头函数涉及词法 this，只把箭头换成 function 就可能改变代码含义。

2. 流程分解析、转换和生成。解析得到 AST，插件访问相应节点并修改结构，生成器输出代码和可选的 source map；例如转换箭头函数时，必要时会通过外层变量保留原来的 this 语义。

3. 实际配置通常用 preset-env 根据目标环境选择转换插件，而不是无差别把所有新语法降到 ES5。目标来自项目兼容要求和 Browserslist，转得越多，产物和辅助代码可能越大，也需要验证最终行为。

4. 语法转换和运行时 API 补齐要分开。Promise、includes 等能力需要合适的 polyfill，普通 runtime 辅助函数并不自动补齐所有 API；Vite 等工具是否经过 Babel 也取决于版本和插件，不能因为项目用 Vite 就说完全没有 Babel。

5. 比如目标浏览器已经支持箭头函数，却不支持某个数组方法，我会先查看生成代码和缺失的运行时能力，避免把全部语法都降级。转换完成后还要在目标环境验证，尤其是异步函数、类继承和第三方依赖；构建成功只说明工具能产出文件，不代表运行时能力已经补齐。

## 追问：箭头函数转成普通函数，为什么还要处理 this？

1. 箭头函数没有自己的 this，而是使用定义位置外层的 this。比如对象方法里注册一个箭头回调，回调读的是外层对象；直接改成普通回调后，this 可能由调用方式决定，结果就变了。

2. 转换器会分析使用位置，必要时在外层保存 this，再在生成的普通函数里访问这个变量。arguments、super 等语义也需要单独处理，因此我会用涉及这些边界的例子理解转换结果，而不只看最简单的加法函数。

3. 这也说明 Babel 不是把所有代码都翻译成更短的写法。为了保持语义，产物可能更长；我会根据目标浏览器启用必要转换，并用 source map 调试源码，不直接修改构建后的辅助代码。

## 追问：用了 preset-env，为什么旧浏览器仍报 Promise 未定义？

1. preset-env 是否注入 API 补齐取决于配置，单纯转换箭头函数不会凭空提供 Promise。需要先看报错属于语法解析失败，还是代码运行时缺少全局对象，两种问题的解决位置不同。

2. 应用可以按兼容范围配置 core-js 和按需注入，同时确认版本、入口及构建目标匹配。异步函数即使已被转换，其生成代码也可能依赖 Promise，因此不能只检查源码里有没有显式使用。

3. 如果写的是给别人使用的库，还要考虑是否允许修改宿主全局环境。我会说明所需运行环境，或选择不污染全局的兼容方式，再在实际目标浏览器测试，不能把开发服务器能运行当成兼容性证明。
