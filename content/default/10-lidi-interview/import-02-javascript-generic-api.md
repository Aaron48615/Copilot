# 泛型在前端 API 封装里怎么用？

## 核心回答

1. 泛型主要用来表达固定响应外壳中的可变数据，例如用 `ApiResponse<T>` 表示状态信息固定、数据类型随接口变化。列表接口可以对应商品数组，详情接口可以对应一个用户对象，公共请求逻辑因此能够复用，同时保留具体字段提示。变化部分用类型参数表示，稳定部分仍然写成普通字段，阅读时比较容易分清各自职责。

2. 我会先约定请求函数返回完整响应还是只返回其中的数据，例如返回完整外壳时可写成 `Promise<ApiResponse<T>>`。调用处应该只按这一层结构取值，避免有些接口取一次数据字段，有些接口取两次，最后依靠猜测和断言使用结果。

3. 请求参数也需要明确类型，但不必把所有参数都放进同一个泛型。比如详情编号和列表筛选有不同含义，可以由各自的接口函数固定下来，让页面调用具体函数，减少路径、参数与响应类型之间随意搭配的机会。

4. 单独写 `request<User>()` 不会检查响应是否真的是用户对象，它只是给编译器一个约定。假设需要更可靠的封装，我会让外部数据先经过检查或解析，再返回具体类型，并把网络失败、业务失败和解析失败的处理约定说明白。

## 追问：调用者把响应泛型填错了，请求函数能发现吗？

1. 如果请求函数只接收路径字符串和一个由调用者指定的泛型，通常发现不了这种错误。编译器不知道某个地址实际返回什么，写成用户类型并不能阻止服务器返回订单数据，提示准确也可能只是表面现象。

2. 一种可选做法是为每个接口提供固定函数，在函数内部关联路径、参数和响应类型。页面调用获取用户的函数时，不再自己随意填写结果类型，可以减少调用阶段的错配，但仍不能证明响应内容正确。

3. 另一种方式是让请求接收解析函数，由解析函数的返回值决定结果类型。这样类型关系来自实际检查，不过解析规则也需要正确覆盖必需字段，不能内部直接强转，否则只是换了一个地方相信输入。

## 追问：网络异常和业务失败应该都放进 ApiResponse 吗？

1. 我会先区分服务端返回的结构与前端请求过程的结果。业务失败可能有正常的响应正文，网络断开则可能根本没有正文，强行把两者当成同一份服务端响应，容易让页面读取不存在的字段。

2. 可以约定网络和解析异常通过异常传递、业务结果通过响应返回，也可以由前端统一转成带明确标记的结果联合。关键是所有接口遵守同一套约定，让调用处知道在哪里处理错误，不能时而抛出、时而悄悄返回空数据。

3. 如果采用抛出异常的方式，还要说明成功结果的泛型不约束拒绝原因。调用处仍需判断捕获到的值是什么，再决定提示或重试，不能仅凭成功返回类型就假定所有错误都有统一的消息和状态码。
