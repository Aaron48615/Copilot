# 泛型在前端 API 封装里怎么用？

## 核心回答

1. 泛型主要用来表达固定响应外壳里可变的那部分数据。比如 `ApiResponse<T>`：状态信息固定，数据类型随接口变。列表接口对应商品数组，详情接口对应一个用户对象。公共请求逻辑能复用，具体字段提示还在。变化部分用类型参数，稳定部分仍写成普通字段，各自职责比较好分。

2. 先约定请求函数返回完整响应，还是只返回其中的数据。返回完整外壳可以写成 `Promise<ApiResponse<T>>`。调用处只按这一层结构取值，别有的接口取一次数据字段，有的取两次，最后靠猜测和断言用结果。

3. 请求参数也要有明确类型，但不必把所有参数都塞进同一个泛型。详情编号和列表筛选含义不同，可以由各自的接口函数固定下来。页面调用具体函数，路径、参数、响应类型就不那么容易随便搭配。

4. 单独写 `request<User>()` 不会检查响应是不是真的用户对象，只是给编译器一个约定。要更可靠的封装，外部数据先经过检查或解析，再返回具体类型。网络失败、业务失败、解析失败怎么处理，约定也要说清楚。

## 追问：调用者把响应泛型填错了，请求函数能发现吗？

1. 请求函数只接收路径字符串，和一个由调用者指定的泛型，通常发现不了这种错误。编译器不知道某个地址实际返回什么。写成用户类型，挡不住服务器返回订单数据。提示看起来准，也可能只是表面现象。

2. 一种做法是每个接口提供固定函数，在函数内部把路径、参数、响应类型绑在一起。页面调用「获取用户」的函数时，不再自己随便填结果类型，调用阶段的错配会少一些，但仍证明不了响应内容正确。

3. 另一种是让请求接收解析函数，由解析函数的返回值决定结果类型。类型关系来自实际检查。解析规则也要正确覆盖必需字段，内部直接强转，只是换了个地方相信输入。

## 追问：网络异常和业务失败应该都放进 ApiResponse 吗？

1. 服务端返回的结构，和前端请求过程的结果，要分开。业务失败可能有正常的响应正文；网络断开则可能根本没有正文。硬把两者当成同一份服务端响应，页面容易去读不存在的字段。

2. 可以约定：网络和解析异常通过异常传递，业务结果通过响应返回；也可以由前端统一转成带明确标记的结果联合。关键是所有接口遵守同一套约定，调用处知道在哪里处理错误。别时而抛出，时而悄悄返回空数据。

3. 采用抛出异常的方式，还要说明成功结果的泛型不约束拒绝原因。调用处仍需判断捕获到的值是什么，再决定提示或重试。不能只凭成功返回类型，就假定所有错误都有统一的消息和状态码。
