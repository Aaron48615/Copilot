# 轻购登录页面的完整流程是什么？

## 核心回答

1. 登录页使用 Vant Form 和 Field 收集用户名、密码，再做表单校验。当前规则是用户名三到十六位字母、数字或下划线，密码六到十六位数字；这是现有项目规则，数字密码限制并不适合作为正式产品的安全设计推荐。

2. 提交时先检查 submitting，避免连续点击造成多个登录请求，再把 userName 和 passWord 交给 loginApi。前端校验帮助用户尽早修正输入，后端仍要重新检查参数和凭据，不能依赖浏览器替自己保证输入合法。

3. 登录成功需要同时满足业务 success 和响应中存在 accessToken，不能只看到 HTTP 200 就跳走。拿到 Token 后调用 setToken 持久保存，再提示成功；如果没有有效凭据，页面应保留错误状态而不是进入受保护页面。

4. 跳转时读取 redirect，没有合适目标就进首页，使用 replace 替换作为中间步骤的登录页。当前字符串判断还不等于完整目标校验，如果继续完善，我会限定站内可访问路径，避免把任意用户修改的参数直接当可信目标。

5. 业务失败与网络异常分别提示，finally 解除 submitting，让用户能够再次尝试。密码只用于本次提交，不应长期保存在浏览器或日志里；演示账号只是体验用途，不能把正式账号凭据写入前端当快捷入口。

## 追问：为什么登录成功还要检查 accessToken？

1. success 是业务声明，但后续请求实际需要凭据。如果响应结构有问题，success 为 true 却没有 accessToken，直接跳到购物车会马上被守卫拦回，用户会看到刚登录成功又需要登录的矛盾反馈。

2. 我会把必要字段检查放在保存状态前，确认是符合约定的非空值，再更新存储与页面身份。检查不通过时说明响应异常，不应写入 undefined 之类字符串，否则存在性判断可能又把它误当作有效凭据。

3. 测试可以固定三种响应：业务失败、业务成功但缺 Token、完整成功。分别看提示、存储和跳转是否一致，这能验证登录状态切换，而不仅是表单按钮点击后有没有调用接口。

## 追问：密码校验规则应该放前端还是后端？

1. 两边都需要，但目的不同。前端告诉用户哪里不符合输入要求，减少无效提交；后端负责真正拒绝不合法请求，因为用户可以直接发送接口调用，绕过 Vant 表单与所有正则。

2. 当前纯数字密码规则要如实说明，不能包装成高强度密码设计。如果正式完善，应和后端统一长度、字符支持与存储策略，同时考虑登录限速等措施，不能只把前端正则写复杂就认为账号更安全。

3. 规则变化还要区分注册与登录。注册可以对新密码提出要求，登录不应随意把原本合法的历史密码挡在前端；修改之前先确认兼容范围，再验证已有用户能否正常登录和修改密码。
