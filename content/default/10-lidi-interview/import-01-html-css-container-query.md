# 容器查询和媒体查询怎么选？

## 核心回答

1. 媒体查询适合根据页面环境调整样式，比如视口宽度、减少动态效果偏好或悬停能力。容器尺寸查询则根据组件祖先容器的可用尺寸调整内部布局，同一张卡片放在主栏和侧栏时，即使浏览器窗口没变，也能呈现不同排列。

2. 做尺寸查询时，需要在合适的祖先上设置 `container-type: inline-size`，再通过 `@container` 判断行内方向尺寸。通常由外层提供宽度，里面的卡片根据这个宽度变化；不能指望元素通过查询自己的尺寸再无限影响自己，尺寸隔离就是为了减少这种循环依赖。

3. 比如商品卡片在宽容器里让图片和文字横排，在窄容器里上下排列，这很适合容器查询。页面整体什么时候收起导航，则仍适合媒体查询。两者可以配合，页面决定空间分配，组件在获得的空间里决定细节，不需要为了复用卡片写很多页面专用类。

4. 我会从内容什么时候挤不下确定断点，并给嵌套容器起清晰的名字，避免查询到错误的祖先。基础样式先保证窄布局可用，支持范围内再启用增强规则，同时测试侧栏收缩、组件单独嵌入等情况，不能只拖动浏览器窗口验证。

## 追问：为什么要查询父容器，而不是卡片自己？

1. 如果卡片根据自己的宽度切换样式，而新样式又改变自身宽度，就容易出现规则互相影响。容器查询通过明确祖先和尺寸约束，让外层先分配空间，内部再根据已获得的空间排版，关系更稳定。

2. 实际结构可以是一个负责占据网格列的外壳，里面放卡片内容，查询条件作用于内容。这个外壳不一定要为每个小元素都新增一层，已有的布局父节点满足条件时就可以使用，避免无意义嵌套。

3. 还要留意收缩包裹的容器。inline-size 尺寸包含会改变内容参与祖先固有尺寸计算的方式，如果外层宽度本来完全靠卡片撑开，应先确定它如何获得宽度，再建立查询，不然可能得到意外的窄容器。

## 追问：如何给不支持容器查询的环境提供可用页面？

1. 先写不依赖查询的基础布局，例如图片在上、文字在下，宽度不超出父容器，按钮可以换行。这样浏览器忽略容器规则后，内容仍完整可读，不会因为增强功能不可用而丢失主要操作。

2. 再按项目支持范围使用 `@supports` 判断相关能力，在支持时加入横向卡片等增强。必要时用媒体查询提供较粗的宽屏调整，但要承认它依据的是视口，无法完全复制组件根据所在栏宽变化的效果。

3. 验证时主动禁用增强规则，检查默认样式和真实内容，尤其是长标题与图片比例。降级不要求每个像素相同，但需要内容顺序合理、操作可达；不能只留一句“旧浏览器走兼容”而没有具体基础样式。
