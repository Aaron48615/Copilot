# 设计一个可访问的 Modal，需要哪些行为？

## 核心回答

1. 我理解可访问的 Modal，首先要让用户知道弹出了什么、当前能操作哪里，以及怎样退出。弹窗需要明确标题和关闭按钮，背景在模态期间不能继续交互；半透明遮罩只是视觉提示，不代表键盘和辅助技术已经被正确处理。

2. 打开前记录触发位置，打开后按内容选择初始焦点。简单输入框可以直接聚焦，长说明适合先聚焦带 tabindex=-1 的标题；删除确认通常优先放到较安全的取消操作，不能机械地选择第一个按钮。

3. 弹窗打开期间，Tab 和反向 Tab 的移动范围应留在内部，背景也不能被鼠标或其他方式操作。自定义实现需要处理动态增加、隐藏和禁用的控件，不能打开时只查一次按钮列表，就认为焦点顺序永远不变。

4. 一般支持 Escape 关闭，并提供可见的取消或关闭按钮；有未保存内容时，可以先确认是否放弃。点击遮罩是否关闭要明确约定，关闭后把焦点还给触发按钮；按钮已经消失时，选择符合后续操作的替代位置。

5. 实现时我会优先评估原生 dialog，用 showModal 打开模态，并补好标题关联和业务关闭逻辑。自定义容器则补充 role、aria-modal、背景隔离和焦点管理，同时处理滚动锁、卸载清理与移动端布局，最后用键盘和读屏实际验证。

## 追问：原生 dialog 的 open、show 和 showModal 有什么区别？

1. 直接添加 open 属性和调用 show 都能让对话框显示，但这属于非模态展示，背景仍然可以交互。showModal 才是模态打开方式，会把对话框放入浏览器顶层，并使同一文档内的其余内容进入惰性状态。

2. 选择原生元素后，我仍会给它可访问名称，明确初始焦点、关闭按钮和关闭后的业务状态。浏览器提供基础行为不代表它知道哪个字段最值得先聚焦，也不会替应用决定未保存表单是否需要确认。

3. 我会让组件状态与原生关闭事件保持一致，避免 DOM 已关闭但框架状态仍认为打开。涉及新增属性或移动端行为时，还要按目标浏览器验证；不能把普通显示方法和模态显示方法混用后，再靠遮罩弥补差异。

## 追问：弹窗里有很长的表单，怎样避免键盘用户迷路？

1. 我会让标题和内容顺序清楚，弹窗高度受可用视口限制，主要内容区可以滚动。初始焦点不应让顶部说明一打开就滚出屏幕，焦点样式也要可见，让键盘用户知道自己当前处于哪一项。

2. 提交失败时保留已填内容，在对应字段说明错误；字段很多时可以增加可聚焦的错误摘要，引导到具体位置。不能只在页面角落显示很快消失的提示，否则用户还需要遍历整个表单才能知道哪里有问题。

3. 移动端要检查软键盘出现后，当前输入项和关键按钮是否仍可到达，不能把所有高度固定死。长内容也不宜整体作为弹窗描述一次播报，我会保留标题、分组和标签，让用户按结构逐步阅读。
