# 设计一个可访问的 Modal，需要哪些行为？

## 核心回答

1. 可访问的 Modal，首先让用户知道弹出了什么、当前能操作哪里、怎样退出。弹窗要有明确标题和关闭按钮，模态期间背景不能继续交互。半透明遮罩只是视觉提示，键盘和读屏不会因此自动处理正确。

2. 打开前记下触发位置，打开后按内容选初始焦点。简单输入框可以直接聚焦，长说明适合先聚焦带 `tabindex=-1` 的标题。删除确认通常优先放到较安全的取消操作，别机械地选第一个按钮。

3. 弹窗打开期间，Tab 和反向 Tab 的移动范围留在内部，背景也不能被鼠标或其他方式操作。自定义实现要处理动态增加、隐藏、禁用的控件。打开时只查一次按钮列表，焦点顺序以后还会变。

4. 一般支持 Escape 关闭，并提供可见的取消或关闭按钮。有未保存内容时，可以先确认要不要放弃。点遮罩关不关要明确约定。关闭后把焦点还给触发按钮；按钮已经没了，就选符合后续操作的替代位置。

5. 实现时优先评估原生 `dialog`，用 `showModal` 打开模态，标题关联和业务关闭逻辑再补上。自定义容器则补 `role`、`aria-modal`、背景隔离和焦点管理，同时处理滚动锁、卸载清理、移动端布局。最后用键盘和读屏实际验一遍。

## 追问：原生 dialog 的 open、show 和 showModal 有什么区别？

1. 直接加 `open` 属性和调用 `show`，对话框都会显示，但这是非模态，背景仍能交互。`showModal` 才是模态打开，对话框进浏览器顶层，同一文档里其余内容进入惰性状态。

2. 选了原生元素，可访问名称、初始焦点、关闭按钮、关闭后的业务状态还是要自己定。浏览器提供基础行为，不等于它知道哪个字段最该先聚焦，也不会替应用决定未保存表单要不要确认。

3. 组件状态要跟原生关闭事件对齐，别 DOM 已经关了，框架状态还认为开着。新增属性、移动端行为，按目标浏览器验。普通显示方法和模态显示方法别混用，再靠遮罩去补差异。

## 追问：弹窗里有很长的表单，怎样避免键盘用户迷路？

1. 标题和内容顺序清楚，弹窗高度受可用视口限制，主要内容区可以滚。初始焦点别让顶部说明一打开就滚出屏幕。焦点样式也要看得见，键盘用户才知道自己当前在哪一项。

2. 提交失败时已填内容留着，在对应字段说明错误。字段很多时可以加可聚焦的错误摘要，引导到具体位置。别只在页面角落闪一下很快消失的提示，用户还得把整个表单走一遍才知道哪有问题。

3. 移动端要看软键盘出来之后，当前输入项和关键按钮还能不能到。高度别全部写死。长内容也不宜整体当作弹窗描述一次播报。标题、分组、标签留着，让用户按结构逐步读。
