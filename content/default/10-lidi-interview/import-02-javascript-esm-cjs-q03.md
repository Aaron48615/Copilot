# tree-shaking 为什么可能失效？

## 核心回答

1. 我会先确认所谓失效指的是未使用导出没有被删除，还是整个包看起来仍然很大。摇树优化依赖构建工具对使用关系和副作用的分析，文件里保留一些代码不一定说明优化完全没有工作。

2. ESM 的静态导入导出让工具比较容易确定哪些成员被使用，如果前面的转换步骤已经把它变成 CommonJS，分析就可能变困难。但也不能说所有 CommonJS 都完全无法优化，具体取决于工具能识别哪些写法。

3. 模块即使没有被使用的导出，执行本身也可能有作用，比如注册插件、修改全局对象或引入样式。工具不能随意删除这些行为，所以需要区分一个导出没被引用和整个模块可以安全跳过。

4. 例如用运行时输入的名称读取模块成员，会让可用成员范围难以静态确定，工具可能保留更多导出。反过来，使用明确的成员名通常更利于分析，但最终能否删除还要结合引用链和具体构建配置判断。

5. 我会在生产构建中检查实际解析到的包入口、模块格式和压缩后的产物，再定位保留原因。如果考虑修改副作用声明，必须先核对初始化代码和样式依赖，不能为了体积好看把有用的行为一起删掉。

## 追问：为什么不能直接给所有依赖加上 sideEffects 为 false？

1. 这个声明是在告诉构建工具，未被使用的模块可以安全跳过，并不是让函数执行得更快。若模块靠顶层执行完成注册，即使没有导出被引用，跳过执行也会改变程序行为。

2. 样式文件尤其容易被遗漏，组件可能通过导入样式才获得正确布局。假如要给一个包补充声明，我会先区分纯工具模块和必须保留的样式、初始化文件，再按实际情况列出有副作用的路径。

3. 验证不能只看产物是否变小，还要用消费这个包的最小页面检查样式和注册功能。开发模式与生产优化路径可能不同，因此开发页面正常，不能直接证明新的声明在发布后也是正确的。

## 追问：按需导入后包还是很大，你会按什么顺序排查？

1. 先看构建实际选择了依赖的哪个入口，而不是只看源码写了几个导入成员。同一个包可能提供多种格式，转译配置或者入口选择会影响工具最终拿到的代码，进而影响静态分析效果。

2. 再查看产物中的模块组成，确认大代码来自目标依赖、共享依赖还是重复版本。如果保留下来的是实际使用路径需要的代码，继续修改导入语法未必有效，应该重新判断功能本身的依赖成本。

3. 最后构造只导入一个功能的最小入口，与当前入口做同配置对照。这样可以区分库本身的限制与项目额外引用；若考虑换库或拆分加载，这只能作为待验证方案，不能先承诺具体缩减比例。
