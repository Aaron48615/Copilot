# tree-shaking 为什么可能失效？

## 核心回答

1. 先确认所谓失效，是没用到的导出没被删，还是整个包看起来仍然很大。摇树优化靠构建工具分析使用关系和副作用。文件里留了一些代码，不一定说明优化完全没工作。

2. ESM 的静态导入导出，工具比较容易确定哪些成员被用到。前面的转换步骤要是已经把它变成 CommonJS，分析就可能变难。也不是所有 CommonJS 都完全优化不了，看工具能认出哪些写法。

3. 模块就算没有被用到的导出，执行本身也可能有作用，比如注册插件、改全局对象、引入样式。工具不能随便删这些行为。一个导出没被引用，和整个模块可以安全跳过，是两件事。

4. 用运行时输入的名称去读模块成员，可用成员范围很难静态确定，工具可能留下更多导出。反过来，用明确的成员名通常更利于分析。最终能不能删，还要结合引用链和具体构建配置。

5. 在生产构建里看实际解析到的包入口、模块格式、压缩后的产物，再定位为什么留下。要改副作用声明，先核对初始化代码和样式依赖。别为了体积好看，把有用的行为一起删掉。

## 追问：为什么不能直接给所有依赖加上 sideEffects 为 false？

1. 这个声明是在告诉构建工具：没被用到的模块可以安全跳过，不是让函数执行得更快。模块靠顶层执行完成注册，即使没有导出被引用，跳过执行也会改程序行为。

2. 样式文件特别容易漏。组件可能就是靠导入样式才有正确布局。给一个包补声明，先分清纯工具模块，和必须留下的样式、初始化文件，再按实际情况列出有副作用的路径。

3. 验证不能只看产物变小没变小，还要用消费这个包的最小页面检查样式和注册功能。开发模式和生产优化路径可能不同。开发页面正常，证明不了新声明发布后也正确。

## 追问：按需导入后包还是很大，你会按什么顺序排查？

1. 先看构建实际选了依赖的哪个入口，别只看源码写了几个导入成员。同一个包可能提供多种格式，转译配置或入口选择会影响工具最终拿到的代码，静态分析效果跟着变。

2. 再看产物里的模块组成，确认大代码来自目标依赖、共享依赖，还是重复版本。留下来的是实际使用路径需要的代码，继续改导入语法未必有效，该重新判断这个功能本身的依赖成本。

3. 最后造一个只导入一个功能的最小入口，跟当前入口用同一套配置对照。这样能分开库本身的限制和项目额外引用。要换库或拆分加载，只能当待验证方案，别先承诺具体能瘦多少。
