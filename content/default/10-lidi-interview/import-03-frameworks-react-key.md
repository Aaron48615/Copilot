# React 的 key 有什么用？为什么不建议用 index？

## 核心回答

1. key 用来标识同一父级下列表项的身份，React 在协调新旧元素时，会结合 key 和组件类型判断哪些内容可以复用。稳定 key 让状态跟着业务对象移动，而不只是跟着当前数组位置移动。

2. index 的问题主要出现在插入、删除和排序。比如每行有一个非受控输入框，删除第一行后，其余项的下标都变了，React 可能把原来第二个位置的局部状态给新的第二行，看起来就像输入内容跑到了另一个人身上。

3. 我会优先使用接口中的稳定 id；前端临时创建的项可以在创建时生成并保存一个编号，而不是每次 render 都随机生成。随机 key 会让 React 不断重建组件，失去输入、焦点和缓存，也可能反复建立订阅。

4. key 只要求同级唯一，不需要全应用唯一，而且不会作为普通 prop 自动传给子组件，需要编号时要另传 id。完全静态、不会重排且不携带局部状态的列表使用 index 风险较低，但仍要根据后续是否可能增加交互来选择。

5. 实际验证可以在某行输入备注，再分别删除前一行和重新排序，确认备注仍属于原记录。只看列表文本是否正确不足以发现身份错误，因为文本会随新属性更新，而局部状态可能已经复用错了；这也是带输入、展开和拖拽的列表更需要稳定标识的原因。

## 追问：改 key 为什么能清空表单？这种方式能随便用吗？

1. key 改变会让 React 把该位置当作新的组件身份，旧组件卸载，新组件从初始状态挂载。因此从编辑用户 A 切换到 B 时，按用户编号设 key 可以明确重置草稿，避免沿用上一用户的输入。

2. 重置不只影响表单值，还会影响焦点、子组件状态和订阅。如果只是更新同一用户的某个字段，不应该随意换 key，否则用户填写到一半可能被清空，第三方编辑器也需要重新初始化。

3. 我会先判断业务上是否真的更换了编辑对象。需要保留多份未提交草稿时，应按对象编号单独存储；key 解决身份切换，不负责草稿保存，更不是用来修补受控状态更新不正确的万能开关。

## 追问：给 map 内部最深的元素加 key，为什么仍然警告？

1. key 必须位于 map 直接返回的那一层，因为 React 正是在这个兄弟集合里对应新旧项。如果返回的是 Row，却只给 Row 内部的 div 加 key，外部 Row 这一层仍然没有身份标识。

2. 一项需要返回多个节点时，可以使用带 key 的 Fragment。短写的空标签 Fragment 不能接收 key，所以这时要使用显式的 Fragment 形式，让整组节点共同对应一条业务记录。

3. 排查时我会先找到产生数组的地方，再看直接返回元素的 key 是否稳定且不重复。只在最里面补 key，或者为了消除警告使用随机数，可能让控制台安静下来，却没有保证实际的状态对应关系。我会再通过插入和删除操作确认整组节点一起移动，尤其一条记录返回多个元素时，要保持它们与同一个业务项对应。
