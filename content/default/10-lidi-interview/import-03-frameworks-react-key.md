# React 的 key 有什么用？为什么不建议用 index？

## 核心回答

1. `key` 用来标明同一父级下列表项是谁。React 协调新旧元素时，拿 key 和组件类型一起判断哪些能复用。key 稳定，状态跟着这笔业务数据走，不会只跟着当前第几项走。

2. `index` 的问题出在插入、删除、排序。每行有一个非受控输入框，删了第一行，后面的下标全变。React 可能把原来第二个位置的局部状态给了新的第二行，输入内容就像跑到另一个人身上。

3. 优先用接口里的稳定 id。前端临时建的项，创建时生成一个编号存下来，别每次 render 都随机一个。随机 key 会让 React 不停拆了再建，输入、焦点、缓存都没了，订阅也可能反复建。

4. key 只要求同一级不重复，不需要全应用唯一。它也不会当普通 prop 自动传到子组件，需要编号就另传 `id`。完全静态、不会重排、也没有局部状态的列表，用 index 风险低一些；后面要加交互，还是尽早换成稳定 id。

5. 验证可以在某一行写备注，再删它前面一行、再排序，看备注还在不在原来那条上。只看列表文字对不对发现不了身份错了：文字会跟着新属性更新，局部状态可能已经复用错了。带输入、展开、拖拽的列表更要稳定标识。

## 追问：改 key 为什么能清空表单？这种方式能随便用吗？

1. key 一变，React 把这个位置当成新组件，旧的卸载，新的从初始状态挂上。编辑用户 A 切到 B，按用户编号设 key，草稿会明确重置，不会沿用上一用户的输入。

2. 重置不止表单值，焦点、子组件状态、订阅都会走。只是更新同一用户的某个字段，别随便换 key，填到一半可能被清空，第三方编辑器也要重新初始化。

3. 先问业务上是不是真的换成另一个编辑对象。要留多份没提交的草稿，按对象编号各自存。key 解决身份切换，不管草稿保存，更不是受控状态更新不对时的万能开关。

## 追问：给 map 内部最深的元素加 key，为什么仍然警告？

1. key 必须在 `map` 直接返回的那一层，React 是在这组兄弟里对新旧项。返回的是 `Row`，却只给 `Row` 里面的 `div` 加 key，外面这层 `Row` 还是没有身份。

2. 一项要返回好几个节点，用带 key 的 `Fragment`。短写的 `<>` 接不了 key，这时写成显式的 `<Fragment key={...}>`，整组节点共同对应一条记录。

3. 排查先找到产生数组的地方，看直接返回的那个元素 key 稳不稳定、有没有重复。只在最里面补、或者为了消警告用随机数，控制台安静了，状态对应关系不一定对。插入删除时看整组节点是不是一起动，一条记录返回多个元素时，它们要跟同一个业务项对应。
