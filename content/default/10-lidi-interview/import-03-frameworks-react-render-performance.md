# React 页面更新慢时怎么定位？

## 核心回答

1. 把「慢」变成能复现的一下：输入搜索词卡住，或者打开详情要等很久。浏览器网络和性能面板分清是请求在等、脚本在算、还是布局绘制。再用 React Profiler 看一次提交里哪些组件耗时。别凭感觉改。

2. 组件更新范围太大，看状态放哪、订了什么。局部输入不必放页面根上。Context 别把所有数据塞进一个高频变化的对象。selector 只返回用到的值。先减少不相干的更新，再谈每个组件怎么缓存。

3. 某一次渲染本身很重，看排序、过滤、格式化、列表行数。贵的纯计算用 `useMemo`；props 稳住再配合 `memo`，可能少做重复活。节点很多就分页或虚拟化。函数引用稳住了，该显示的节点数量不会变少。

4. Effect 是不是反复请求或改 state，是不是因为每次都是新对象依赖，订阅建了又拆。请求太多、图表反复初始化、监听没清，页面也会越来越慢。这是执行行为的问题，不是单纯组件渲染比了几次。

5. 改完用同一份数据量、同一套操作再测，记下具体改善了哪。开发模式额外检查会影响次数，必要时用接近生产的方式看性能。效果以相同数据量和操作的前后对比为准。还要确认少更新之后，列表、按钮、错误提示没有在显示旧数据。

## 追问：Profiler 显示渲染很快，页面为什么还是卡？

1. React 渲染只是整段过程的一块。大量 DOM 的样式计算、同步布局、图片解码、第三方图表绘制，可能发生在浏览器别的阶段。组件函数自己很快，说明不了主线程没被占住。

2. 用浏览器性能面板录同一套操作，看长任务和布局。循环里反复先读元素尺寸再写样式，会逼出强制布局。读写分开批处理，或者别逐行量不必要的节点。修的点不在 `memo` 上。

3. 网络等待和主线程卡住要分开说。接口慢，可以留着旧内容并给加载反馈；脚本堵住了，得少干活或挪出主线程。两件事都叫「React 太慢」，优化手段会对不上真正的问题。

## 追问：什么时候不要加 useMemo 和 useCallback？

1. 计算很便宜，返回值也没人依赖引用稳定，通常就不必。缓存还要比依赖、存结果，读代码的人还得理解依赖关系。简单字符串拼接也缓存，复杂度上去了，体感不一定有。

2. `useCallback` 在函数身份会影响 `memo` 子组件，或者订阅依赖这个引用时，才可能有用。子组件本来就会因为别的 props 更新，单独稳住一个函数不一定少渲染。依赖漏写，事件处理还可能读到旧状态。

3. 没有缓存时逻辑先是对的，再针对测出来的热点加缓存。项目开了 React Compiler，还要看实际编译配置，再决定还要不要手写缓存。React 版本比较新，不等于所有组件已经自动优化好了。
