# React 页面更新慢时怎么定位？

## 核心回答

1. 我先把“慢”变成具体可复现的动作，例如输入搜索词时卡顿，或者打开详情后等待很久。用浏览器网络和性能面板区分请求等待、脚本计算、布局绘制，再用 React Profiler 查看一次提交中哪些组件耗时，避免只凭感觉改代码。

2. 如果组件更新范围过大，就检查状态位置和订阅。局部输入不必放在页面根部，Context 不应把所有数据装进一个高频变化的对象，selector 也应只返回使用到的值；先减少不相关更新，再讨论每个组件如何缓存。

3. 如果某次渲染本身很重，就检查排序、过滤、格式化和列表行数。昂贵纯计算可以用 useMemo，稳定 props 配合 memo 可能减少重复工作；大量节点则考虑分页或虚拟化，不能指望缓存函数引用减少实际需要显示的节点。

4. 我还会查看 Effect 是否反复请求或修改 state，是否因为新对象依赖导致每次重新建立订阅。过多请求、重复初始化图表和未清理监听，也会让页面越来越慢，这些属于执行行为问题，并非单纯的组件渲染比较。

5. 改完后用同一数据量和操作重新测量，记录具体改善点并验证交互正确。开发模式的额外检查会影响执行次数，必要时使用合适的生产性能分析方式；优化效果以相同数据量和操作下的前后测量为准，还应确认没有为了减少更新而让列表、按钮或错误提示显示旧数据。

## 追问：Profiler 显示渲染很快，页面为什么还是卡？

1. React 渲染只是整体过程的一部分。大量 DOM 引起的样式计算、同步布局、图片解码或第三方图表绘制，可能发生在浏览器其他阶段，组件函数本身快并不能证明主线程没有被占用。

2. 我会在浏览器性能面板录制相同操作，查看长任务和布局活动。比如循环中反复先读元素尺寸再写样式，会触发强制布局；可以把读写分批，或避免逐行测量不必要的节点，修复点并不在 memo 上。

3. 网络等待和主线程阻塞也要分开呈现。接口慢可以保留旧内容并显示加载反馈，脚本阻塞则需要减少工作或移出主线程；把两种情况都称为“React 太慢”，会导致优化手段和真正问题对不上。

## 追问：什么时候不要加 useMemo 和 useCallback？

1. 计算很便宜、返回值没人依赖稳定引用时，通常没有必要。缓存还需要比较依赖、保存结果并让读代码的人理解依赖关系，给简单字符串拼接加缓存，可能增加复杂度却没有可感知收益。

2. useCallback 只有在函数身份影响 memo 子组件或订阅等场景时才可能有用。子组件本来就会因其他 props 更新，单独稳定一个函数不一定减少渲染；依赖漏写还可能让事件处理读到旧状态。

3. 我会先保证没有缓存时逻辑也正确，再针对测出的热点加入缓存。如果项目启用了 React Compiler，也要结合实际编译配置评估手动缓存，不能仅凭使用较新 React 版本就假定所有组件已自动优化。
