# keep-alive 下 onUnmounted 会执行吗？

## 核心回答

1. 组件被 KeepAlive 缓存后，从界面上切走通常是停用，不是真正卸载，所以这时不会像普通条件移除那样执行 onUnmounted。实例和局部状态仍然保留，回来时会激活同一份缓存，这也是表单草稿能够留下来的原因。

2. 停用和恢复分别使用 onDeactivated、onActivated 处理。比如列表页离开时暂停轮询，回来时继续刷新；如果只在 onUnmounted 停止定时器，缓存页虽然不可见，轮询仍可能一直发请求，多个缓存页会累计后台工作。

3. 真正被移出缓存、超过 max 被淘汰，或外层 KeepAlive 卸载时，组件仍会进入卸载流程。onDeactivated 在停用和最终卸载时都可能涉及，因此暂停和释放逻辑应能安全重复调用，不要依赖某个回调只出现一次。

4. onActivated 首次挂载也会调用，不能同时在 onMounted 和 onActivated 无条件启动同一个轮询。可以把可恢复的启动逻辑集中到激活处理，启动前检查现有句柄；最终卸载时再释放不会继续复用的第三方实例等资源。

5. 我会按进入、切走、返回和淘汰四个过程验证，检查后台请求数量与界面状态。缓存不会自动冻结所有监听和异步任务，数据仍可能变化；要明确停用时哪些工作暂停、哪些共享更新继续，不能把“页面不见了”当成“组件已经停止运行”。

## 追问：缓存页面里的定时器应该在哪个钩子里清理？

1. 如果页面不可见就不需要执行，应在 onDeactivated 暂停，在 onActivated 恢复。比如消息列表轮询只为了更新当前页面，离开后继续请求没有显示价值，不能等到最终卸载才清理，因为缓存可能保留很久。

2. 我会保存定时器句柄，启动前确认没有已有任务，停止后清空句柄。这样首次激活、重复切换和最终释放都更容易保持一致，避免 mounted 与 activated 各启动一次，让页面看似正常却每轮发送两次请求。

3. 如果任务本来属于整个应用，例如全局会话检查，就不应由一个缓存页面的可见状态决定。应把它放在更合适的生命周期范围，页面只消费结果，避免为了满足全局需求让每个页面各自维护一个定时器。

## 追问：onDeactivated 和 onUnmounted 都释放图表，会不会冲突？

1. 要看释放是什么意思。停用期间希望回来继续复用实例，可以只暂停动画和监听，激活后重新测量尺寸；如果停用就完整 dispose，返回时必须重新创建，否则 ref 还在，实例却已经不能继续操作。

2. 我会把暂停和最终销毁分开，或者把销毁封装成可重复调用且会清空引用的函数。不能第一次销毁后仍保存旧对象，后续卸载再调用一次，或返回时继续向已销毁实例传配置，都可能触发异常。

3. 验证时需要观察首次显示、隐藏后改变容器尺寸、返回和缓存淘汰。只测路由离开时没有报错，不代表资源管理完整，很多问题会在第二次激活时出现，因为代码只考虑了创建和销毁两种状态。
