# keep-alive 下 onUnmounted 会执行吗？

## 核心回答

1. 被 `KeepAlive` 包住的组件，从界面上切走通常是停用，不是卸载。这时 `onUnmounted` 不会跑，实例和里面的草稿、筛选还在，回来用的还是同一份。普通 `v-if` 拿掉就不一样，那个才会走卸载。

2. 切走用 `onDeactivated`，回来用 `onActivated`。比如列表页有轮询，离开就暂停，回来再开。清理只写在 `onUnmounted` 里，页面看不见了定时器还在发请求，多缓存几页后台就越积越多。

3. 真正卸掉还是会走卸载：超出 `max` 被挤掉，或者外面那层 `KeepAlive` 自己没了。`onDeactivated` 在停用和最终卸载时都可能碰到，暂停、释放那套要能重复调用，别默认某个钩子一辈子只进一次。

4. 第一次挂上也会进 `onActivated`。`onMounted` 和 `onActivated` 各开一次轮询，就会变成两份。可恢复的启动集中放到激活里，先看句柄在不在；图表、第三方实例这种回不来的，等真正卸载再 `dispose`。

5. 进页、切走、返回、被淘汰这四步都要看：后台请求停没停、界面状态还在不在。缓存不会把监听和异步任务一起冻住，数据照样可能变。页面不见了不等于组件已经停了。

## 追问：缓存页面里的定时器应该在哪个钩子里清理？

1. 看不见就不该跑的，在 `onDeactivated` 停，在 `onActivated` 再开。消息列表轮询只为当前页刷新，离开还打接口没意义。缓存可能留很久，别等到最终卸载才清。

2. 句柄自己存着，启动前先看有没有旧的，停了就把句柄清掉。第一次进来、来回切、最后释放都能对上。不然 mounted 开一次、activated 再开一次，看起来正常，请求却翻倍。

3. 任务本来是整个应用的，比如全局会话检查，就别绑在某个缓存页显不显示上。放到更合适的地方，页面只消费结果，别每个页自己养一个定时器。

## 追问：onDeactivated 和 onUnmounted 都释放图表，会不会冲突？

1. 看“释放”指什么。停用时还想回来接着用，就先停动画和监听，激活后再量一次尺寸。停用就把实例 `dispose` 掉，回来必须新建；ref 还在、实例已经废了，再往里塞配置会报错。

2. 暂停和最终销毁分开写。销毁做成能重复调用的函数，调完把引用清掉。第一次销毁后还握着旧对象，卸载再调一次，或者回来继续用已销毁的实例，都容易炸。

3. 第一次显示、藏起来改容器大小、再回来、缓存被挤掉，这几步都要过一遍。路由离开没报错，不代表资源管干净了。很多问题第二次激活才露出来，因为代码只想过创建和销毁两种状态。
