# Web Worker 适合解决什么问题？

## 核心回答

1. Web Worker 适合把不需要直接操作 DOM 的计算挪到独立线程，比如大文件解析、复杂数据转换、图像处理。网络请求本身通常已经异步，不为了让 `fetch` 不阻塞就额外建 Worker。值不值得用，看主线程实际耗时。

2. 页面通过 `postMessage` 发任务，Worker 算完回传结果。默认用结构化克隆，不是共享同一个普通对象。函数、DOM 节点这类不能直接传过去。输入输出做成明确的数据结构，少依赖页面上下文。

3. 大数据通信成本不能忽略。合适时可以把 `ArrayBuffer` 当 transferable 转移，避免复制，但发送方的缓冲区会分离，不能再按原来的方式用。复制、转移、共享内存是不同方案，不是没有任何开销的传值。

4. Worker 不能直接改页面 DOM，结果仍要在页面里更新。任务加标识，处理错误、取消、过期响应，并限制实例和消息数量。算得快但回传过多、一次渲染太大，界面照样卡。

5. 先测出计算瓶颈，再用相同任务比较主线程响应、总耗时、内存。Worker 有启动和通信开销，小计算搬过去可能更慢。选一个实际耗时的解析任务做对照，覆盖取消、失败、重启，确认输入输出一致，页面也更容易响应。

## 追问：ArrayBuffer 转移后，原来的数据为什么不能再读？

1. 转移是交出底层资源的所有权，发送方原缓冲区会进分离状态，不是双方同时握着一份可改的共享数组。这样能少复制大数据，但调用方要明确后续谁继续用这份数据。转移后再拿旧引用重试，读不到。

2. 页面还需要原始数据，可以选择复制，保留能重新读取的文件，或重新设计任务输入。为了追求零复制，默认再留一份完整副本，解释时却忽略这部分内存和读取成本，收益要按完整流程算。

3. 转移前后缓冲区状态要查，取消、失败后怎么恢复也要定。共享内存是另一套能力，涉及隔离条件和同步。普通大文件解析未必需要引入。最简单、能保证结果正确的方式，通常更好维护。

## 追问：任务搬到 Worker 后，为什么页面还是卡？

1. 先看耗时部分是不是真的搬过去了。有时主线程仍在发送前做巨大 JSON 序列化，或收到结果后同步生成大量 DOM。Worker 只解决它执行的那部分计算，不会自动减少数据准备、通信、最终渲染。

2. 录完整时间线，输入准备、后台计算、消息接收、渲染分开看。通信数据过大就减少字段或合理转移，渲染过大就分页、虚拟化或分批呈现。只加更多 Worker，希望所有部分一起变快，通常不成立。

3. 实例是不是反复创建、高频进度是不是触发大量更新，也要查。优化后既看页面响应，也看总耗时和内存。只是让主线程空闲，整个任务却大幅变慢，要结合用户需求判断这样取舍值不值。
