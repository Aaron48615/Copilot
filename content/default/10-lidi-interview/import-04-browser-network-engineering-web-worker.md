# Web Worker 适合解决什么问题？

## 核心回答

1. Web Worker 适合把不需要直接操作 DOM 的计算移到独立线程，例如大文件解析、复杂数据转换或图像处理。网络请求本身通常已经异步，不需要为了让 fetch 不阻塞就额外创建 Worker，是否值得使用要看主线程实际耗时。

2. 页面通过 postMessage 发送任务，Worker 计算后回传结果。默认使用结构化克隆，并非共享同一个普通对象；函数和 DOM 节点等不能直接传过去，所以我会把输入输出设计成明确的数据结构，减少对页面上下文的依赖。

3. 大数据通信成本不能忽略。合适时可以把 ArrayBuffer 作为 transferable 转移，避免复制，但发送方的缓冲区会分离，不能再按原来方式使用；复制、转移和共享内存是不同方案，不应混成没有任何开销的传值。

4. Worker 不能直接修改页面 DOM，结果仍需在页面中更新。通常会给任务加标识，处理错误、取消和过期响应，并限制实例与消息数量；否则算得快但回传过多、一次渲染太大，最终界面仍然卡顿。

5. 我会先测出计算瓶颈，再用相同任务比较主线程响应、总耗时和内存。Worker 有启动和通信开销，小计算搬过去可能更慢；如果继续完善，我会选一个实际耗时的解析任务做对照，并覆盖取消、失败与重启，确认输入输出一致且页面更容易响应。

## 追问：ArrayBuffer 转移后，原来的数据为什么不能再读？

1. 转移是交出底层资源的所有权，发送方原缓冲区会进入分离状态，不是双方同时持有一份可修改的共享数组。这样可以减少大数据复制，但要求调用方明确后续谁继续使用这份数据，不能转移后再拿旧引用重试。

2. 如果页面还需要原始数据，可以选择复制、保留可重新读取的文件，或重新设计任务输入。不能为了追求零复制就默认再保留一份完整副本，却在解释中忽略这部分内存和读取成本，收益要按完整流程计算。

3. 验证时检查转移前后缓冲区状态，以及取消、失败后如何恢复。共享内存是另一套能力，涉及隔离条件与同步，普通大文件解析未必需要引入，选择最简单且能保证结果正确的方式通常更容易维护。

## 追问：任务搬到 Worker 后，为什么页面还是卡？

1. 首先看是否真正把耗时部分搬过去，有时主线程仍在发送前做巨大 JSON 序列化，或收到结果后同步生成大量 DOM。Worker 只解决它执行的计算，不会自动减少数据准备、通信和最终渲染工作。

2. 我会录制完整时间线，把输入准备、后台计算、消息接收和渲染分别看。通信数据过大可减少字段或合理转移，渲染过大可分页、虚拟化或分批呈现，不能只增加更多 Worker，希望所有部分一起变快。

3. 还要检查实例是否反复创建、高频进度是否触发大量更新。优化后既看页面响应，也看总耗时和内存；如果只是让主线程空闲但整个任务大幅变慢，需要结合用户需求判断是否值得这样取舍。
