# 超时和用户取消怎么区分？

## 核心回答

1. 超时和用户取消都可能通过中止请求实现，但业务含义不同：前者是超过等待预算，后者是用户主动放弃。请求封装里保存结构化原因，让页面按原因决定提示，别靠错误消息里有没有某个词来猜。

2. 使用标准能力时，AbortSignal.timeout 产生的中止原因是 TimeoutError，无参数调用控制器的 abort 通常使用 AbortError。调用方传入自定义原因，就不能假定所有取消都是同一个名字，封装仍应记下明确的取消来源。

3. 运行环境支持的话，可以把用户信号与超时信号组合，并以最先触发的原因作为这一轮的结论。用计时器做兼容实现时，也应只允许设置一次终态，避免超时和点击取消接连发生，后一个事件盖住最初原因。

4. 页面处理上，主动取消通常结束加载即可，超时可以提示稍后重试，普通网络错误和 HTTP 失败还应分别归类。超时并不证明服务端没有执行写操作，能不能重试要看接口是否允许重复，不能统一弹出自动重试后直接重发。

5. 封装还要覆盖响应体读取阶段，完成后清理自己创建的计时器与监听，防止请求结束后又触发取消逻辑。每轮请求使用新的取消状态，旧请求返回前检查是不是仍是当前这一轮，避免重新搜索后被旧结果盖住。

## 追问：Promise.race 加计时器为什么不够？

1. Promise.race 只决定哪个结果先成为外层结果，计时器赢了不会自动停掉另一个请求。搜索超时后页面已经提示失败，原请求仍可能继续占资源。后面要是还有单独的成功回调，就可能再次更新页面。

2. 所以除了让外层超时，还要把控制器的 signal 传到真实请求里，到期时通知它中止，同时让状态提交检查当前请求身份。不支持取消的任务，只能停止等待并隔离后续结果，外层提前拒绝不等于底层已经终止。

3. 计时器本身也需要收尾。请求先成功时应清掉计时器，避免留下无意义的等待和迟到回调。超时覆盖到哪里也必须约定：还要解析响应体，就把读取和解析放进同一流程，不能收到响应头便宣布整个任务完成。

## 追问：用户取消与超时几乎同时发生时如何分类？

1. 采用先发生且被这一轮记下的原因，并把它保存为不可再覆盖的最终分类。超时先触发、用户随后点击取消，页面仍可按超时收尾；反过来则按主动取消处理，别让回调先后改同一个错误标签。

2. 使用组合信号时可以读它的 reason，标准组合行为会传播触发中止的原因，但自定义封装仍要保留来源信息。输入信号在创建时就已经取消，应在派发前处理，不能等注册一个只监听未来事件的回调才开始判断。

3. 验证时用可控计时器分别覆盖两种先后顺序，以及请求已经成功后的迟到取消，检查只结束一次加载、只提示一次。错误上报也沿用同一分类，否则界面显示主动取消，监控却计为超时，排查结果会对不上。
