# 轻购AI从输入到展示结果的完整流程是什么？

## 核心回答

1. 完整流程从 GuideView 的输入开始。用户填写需求并提交后，函数先 trim，再判断长度是否至少为两个字符；不符合就提示并返回。这样可以拦住只有空格的请求，但不能据此认为所有无意义输入都已经被识别出来。

2. 发请求前，页面把 loading 设为 true，并清除上一次结果，显示正在挑选的提示。这里的结果与本次输入是一组状态，如果输入已经换了却仍把旧商品当作新推荐显示，用户就很难判断推荐对应的是哪次需求。

3. getGuideRecommendations 通过 Axios 向 `/guide/recommend` 发送 `{ query }`。拿到响应后还会检查业务 success，HTTP 返回成功并不一定表示推荐成功；业务失败进入错误处理，页面用提示说明这次请求没有完成。

4. 成功数据写入 result，再展示 relaxedConstraints 和 recommendations。每张卡片显示商品图片、名称、价格、匹配条件和缺少明确依据的条件，让用户能把自己的预算与偏好同实际推荐逐项对照。

5. 用户点击卡片或查看商品时，根据 prodId 跳到商品详情，由详情页加载完整商品与 SKU。请求结束则在 finally 恢复 loading；如果以后允许连续提交，还要增加请求版本检查，不能只因为旧请求结束就关闭新请求的加载状态。

## 追问：为什么 HTTP 200 之后还要检查 success？

1. HTTP 状态描述的是请求在协议层面的处理结果，而项目接口还用 success 表达业务是否完成。例如服务器正常接收了 query，但推荐服务不可用，依然可能返回一个带错误说明的业务对象，不能直接访问其中的商品数组。

2. 当前页面会把业务失败转入错误分支，这样不会把缺少 data 的响应当成正常推荐继续渲染。如果继续完善，再区分业务失败、响应结构错误和成功但列表为空，它们对应的用户提示与重试方式并不相同。

3. 验证时可以分别模拟 HTTP 错误、200 但 success 为 false，以及成功且 recommendations 为空。看页面是否结束加载、是否显示正确提示、能否再次提交，比只测一个正常响应更能说明请求状态处理完整。

## 追问：清掉旧结果是不是最好的交互？

1. 当前实现开始请求时清掉旧结果，优点是结果不会与新输入混淆，逻辑也比较容易理解。代价是网络较慢时用户暂时看不到原来的推荐，如果新请求失败，也失去了上一份可以继续查看的结果。

2. 如果继续优化，可以考虑保留旧结果，但明确标注它对应上一次需求，并在上方显示新请求加载中。不能只是保留卡片不加说明，否则用户改了预算后，很容易误以为旧商品已经按照新预算重新筛选。

3. 选哪种方式要看页面是否支持对比和用户是否经常修改需求。无论采用哪一种，结果都应该绑定提交时的 query，新请求成功后再统一替换；输入框当前值不能直接充当旧结果的标题。
