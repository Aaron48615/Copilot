# 失败的任务怎么处理？

## 核心回答

1. 并发池遇到失败，先明确这一批的语义：独立任务通常记下当前失败后继续处理，必须整体成功的流程才考虑停止派发。这个策略该由调用方选。一个 worker 的异常把整个队列带停，剩余任务就会一直没有结果。

2. 实现上把任务函数的调用也放进 try 里，再 await 返回结果，这样同步抛错和异步拒绝都能被记下。成功或失败都要释放运行名额，并按原任务下标保存状态、结果或原因，方便页面准确定位失败项。

3. 重试前先判断错误能不能恢复。临时网络异常可以考虑有限重试，参数校验失败通常得先改输入。权限错误也不能机械重复发送；有明确的凭证刷新协议，就按协议处理后再决定要不要重新尝试。

4. 还要判断操作允不允许重复。查询和创建记录的风险不同。就算看到超时，也可能只是响应没送到、服务端已经写完。写请求重试应依赖幂等约定或状态核对，不能只凭错误码就自动再执行。

5. 设计重试就要设次数和总耗时上限，等待逐步拉长并带一点随机扰动，等待本身也要能取消。最后返回每项的最终状态和实际尝试次数，让页面只重试失败项，别把已经成功的任务再跑一遍。

## 追问：重试等待期间要不要占用并发名额？

1. 看名额表示什么。表示正在处理的逻辑任务，让 worker 在原地等待更容易实现，也能自然把压力降下来。代价是多个任务同时退避时，新任务就算可以执行也得等着，这种吞吐损失接不接受得事先讲清楚。

2. 名额只限制实际网络请求，可以在失败后释放名额，把重试任务放进带下次执行时间的队列。调度器到时间再派发，期间继续处理其他任务。但要防止同一任务同时存在多个重试副本，造成重复写入。

3. 重试任务要保留原始编号和尝试次数，新任务和重试任务之间也要有公平的取用规则。不然不断到来的新任务可能让重试永远排不到，或者失败任务反复抢占名额，整批看起来一直卡在少数异常项上。

## 追问：如何验证一个失败任务不会卡住队列？

1. 用可手动控制完成的任务来验证：先占满名额，再让其中一个任务拒绝，看下一项会不会开始。这样能直接观察名额释放，不必依赖真实网络快慢，也能发现只有成功分支才补任务的实现缺陷。

2. 还要单独放入一个调用时就同步抛错的任务。它还没有返回 Promise，漏掉外层 try 就可能让 worker 提前退出。验证结果应包含这项失败以及后面任务的完成状态，不能只断言外层捕获到了错误。

3. 最后测连续失败、重试耗尽、取消发生在退避期间这些情况，确认每项只进入一次最终状态。批次结束时应没有悬挂的等待者、残留计时器或仍被统计的运行名额，页面的完成数量也要能和结果列表对上。
