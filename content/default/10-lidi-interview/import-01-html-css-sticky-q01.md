# overflow: hidden 一定会让 sticky 失效吗？

## 核心回答

1. `overflow: hidden` 不一定让 `sticky` 本身失效，但可能改它依赖的滚动参照。`hidden` 会裁剪溢出，并带有滚动容器相关行为。`sticky` 可能因此把这个祖先当成参照，而不是原先预期的页面视口，看起来就跟页面滚动对不上了。

2. 比如卡片外层只是为了裁圆角设了 `hidden`，自己没有可观察的滚动过程，用户滚的是整个文档。里面标题的粘性约束可能一直围着这个外层算，页面移动时就不会按期待停在屏幕顶部。问题不在 `top` 数值太小，而在参照选错了。

3. 沿祖先看计算后的 `overflow-x` 和 `overflow-y`，并核对实际滚动高度。单独设横向 `overflow`，另一轴的计算值也可能跟着变。源码里 `y` 没写，不代表纵向不受影响。有时还有多层嵌套容器，得一层层确认。

4. 目的只是视觉裁剪，可以评估 `overflow: clip`，它不建立滚动容器，但也不等同于 `hidden` 的全部行为。还需要独立块布局，可能要另配 `flow-root`。改之前确认要的是程序滚动、裁剪还是 BFC，按需求拆开职责，别机械替换所有 `hidden`。

5. 检查效果时滚到容器中间和末尾，确认是完全没有粘性，还是已经到达包含块边界而停止保持。后者可能是正确行为。把它误判成隐藏导致失效，就容易删掉本来必须留的裁剪规则。

## 追问：overflow: clip 与 hidden 的关键差别是什么？

1. 两者都可以裁剪溢出，但 `hidden` 仍可以作为滚动容器，内容在适用情况下能通过程序滚动；`clip` 不提供这种滚动能力。对 `sticky` 来说，建不建滚动参照会影响行为，这个差别比「都看不到滚动条」更关键。

2. `clip` 本身也不像某些其他 `overflow` 值那样建立新的块级格式化上下文。原来的 `hidden` 如果同时用来包含浮动，直接替换可能让父容器高度表现变掉，需要按需求另用 `flow-root`。视觉相似，不能完全互换。

3. 先确认这块区域有没有焦点滚动、锚点，或代码里设 `scrollTop` 的需求，再决定用不用 `clip`。只负责裁切装饰时它可能合适，需要可滚动内容时就不该替代。最终按目标环境验证组合表现。

## 追问：只写 overflow-x: hidden 为什么也可能影响纵向 sticky？

1. `overflow` 两个轴的值并非始终独立保留源码里的默认值。一个轴不是 `visible` 或 `clip` 时，另一个轴原本的 `visible` 可能计算成 `auto`。所以只限制横向溢出，祖先也可能变成跟预期不同的滚动容器。

2. 计算样式面板里两个轴一起看，别只搜源码有没有 `overflow-y`。再观察祖先的 `scrollHeight`、`clientHeight` 和滚动行为，确认 `sticky` 实际参照谁。「明明只处理横向，吸顶却变了」往往就能对上。

3. 横向溢出来自某张过宽图片，优先限制那张图片，避免给整页新增滚动边界。确实需要裁剪整个区域，再评估 `clip` 或调整结构。修的是具体原因，别把纵向问题交给额外滚动监听去补。
