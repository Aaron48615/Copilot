# 前端权限菜单和路由保护怎么设计？

## 核心回答

1. 跟接口约定稳定的权限标识，比如订单查看、订单编辑，角色再关联这些权限。前端按服务端返回的有效权限决定展示什么。别在各个组件里反复写管理员、普通用户这种字符串判断，角色一调整就要到处改。

2. 菜单、路由、按钮尽量复用同一份权限声明，职责分开。菜单控制入口，路由拦截直接访问，按钮控制具体操作。父菜单只是分组时，有可见子项就可以保留。别把父页面的权限强加给所有子页。

3. 登录恢复时，先确认会话并加载权限，再进受保护页面，期间显示加载状态。权限加载失败提供重试，默认不放行。公开页面显式标注。动态路由要在首次匹配前协调好，刷新合法地址别误判成不存在。

4. 接口返回 401，按会话过期策略处理，刷新会话失败再清登录状态。403 通常保留会话，提示当前操作没权限。跳回登录前可以记下站内目标地址，恢复跳转时要校验，别直接相信任意外部地址。

5. 真正授权仍由服务端按当前用户、操作、具体资源来做。前端守卫保护不了已经返回的数据。切换账号或租户时，权限、动态路由、相关缓存都清掉。权限变了再检查当前页，新身份别沿用上一身份的入口或内容。

## 追问：权限接口还没返回，路由守卫应该怎么处理？

1. 权限状态分成未加载、加载中、成功、失败。空数组不能同时代表没权限和还没取到。进受保护页面时等加载结果，显示明确的等待状态。别先渲染内容再补一次重定向。

2. 多个路由跳转同时触发，可以共享正在进行的权限请求，但结果要绑到会话或租户版本。用户中途切了账号，旧请求就算成功也不能写入新会话。等待逻辑对了，最终用的却是另一个人的权限。

3. 加载失败给出重试入口，受保护内容不展示。登录页和错误页不该再依赖同一个守卫条件。动态注册路由的话，注册完成后只做必要的重新匹配，别不断跳回原地址形成重定向循环。

## 追问：有子菜单权限但没有父页面权限，菜单树怎么生成？

1. 纯分组节点和真正可访问的父页面要分开。别只看父节点有没有权限就把整棵子树删掉。纯分组只负责组织内容，有可见子项就可以留；父页面链接本身仍按自己的权限判断。

2. 过滤时从子节点结果反推分组要不要显示，稳定的路径和节点标识留着。父页面无权访问、子页可以访问时，分组标题可以不可点击，或者按明确约定指向第一个可访问子页。别链到必然被拒绝的地址。

3. 路由规则跟这个展示约定对齐，嵌套布局别无意中要求用户拥有父业务页权限。菜单隐藏不会改变直接访问的授权结果。子页 URL 还要单独验，别菜单看着对，实际进去却被上层守卫拦住。
