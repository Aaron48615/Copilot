# 异步请求的竞态和取消怎么测试？

## 核心回答

1. 我会先明确竞态的业务规则，比如搜索框采用“最后一次输入对应的结果生效”，而不是“最后返回的请求生效”。然后让每次请求返回可手动完成的 Promise，测试就能准确指定返回顺序，不依赖真实网络延迟碰运气。

2. 基本用例是发出 A、再发出 B，先让 B 成功并确认显示 B，再让 A 成功，页面仍应保留 B。还会让旧请求 A 最后失败，检查它没有覆盖新结果或弹出无关报错，因为过期错误也是一种状态污染。

3. 取消测试分两层：一层检查传给请求的 signal 确实被中止，另一层检查取消后的界面行为。mock 要响应 abort 事件，也要处理接收时已经中止的 signal；只断言调用了 controller.abort，不能证明请求封装和页面正确处理了取消。

4. 我还会故意使用不配合取消的 mock，让旧请求在取消之后照常返回，以验证请求编号等过期检查仍然有效。取消是节省资源的手段，阻止旧结果写入才是页面正确性的要求，两者不能在测试中合成一个断言。

5. 组件卸载、超时和新请求替换旧请求要分别验证，尤其要检查旧请求的 finally 不会提前关闭新请求的 loading。测试会等相关处理完成后再检查无错误提示；取消客户端等待也不能作为服务端业务已经停止的证据。

## 追问：怎么用可控 Promise 复现后发先回？

1. 我会给每个请求一个独立的控制柄，并让 mock 根据请求参数返回对应的 promise。下面是教学用辅助函数，只负责控制完成和失败，不包含 fetch 的 signal 行为，所以取消测试需要额外的 mock 逻辑。

   ```js
   function deferred() {
     let resolve, reject;
     const promise = new Promise((ok, fail) => {
       resolve = ok;
       reject = fail;
     });
     return { promise, resolve, reject };
   }
   ```

2. 测试先通过两次输入发起 A 和 B，确认请求参数都正确，再调用 B.resolve 并等待 B 的结果出现。随后调用 A.resolve，等待旧请求处理结束，断言页面内容没有回退，目标列表仍然对应第二次输入；这样验证的是确实执行过旧响应的场景。

3. 我会再把 A.resolve 换成 A.reject，覆盖过期失败，并把 B 保持 pending 检查 loading。每个用例都重新创建控制柄，结束时处理未完成请求，避免只完成一个 Promise 后把另一个留给后续测试。

## 追问：取消、超时和网络错误需要同样的提示吗？

1. 我会按业务含义区分，用户主动切换搜索或离开页面时取消，通常不需要报错提示。超时说明用户仍在等结果但等待预算已经用完，可以提示重新尝试；真实网络错误则按页面规则说明当前操作没有拿到有效响应。

2. 错误识别不能只靠错误文本里有没有 abort，因为中止可以携带自定义原因，封装库也可能转换错误。我会通过请求上下文和约定的错误类型判断，并测试主动取消与超时产生的不同界面结果，避免把全部中止都静默吞掉。

3. 还要验证错误的归属，旧请求即使是超时也不应覆盖最新一次搜索的成功状态。对写操作则保留结果不确定的可能，页面退出 loading 只代表这次等待结束，不能让测试据此断言服务端一定没有产生业务记录。
