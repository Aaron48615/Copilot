# 异步请求的竞态和取消怎么测试？

## 核心回答

1. 竞态的业务规则先说清。比如搜索框是「最后一次输入对应的结果生效」，不是「最后返回的请求生效」。每次请求返回一个能手动完成的 Promise，测试就能指定返回顺序，不用靠真实网络延迟碰运气。

2. 基本用例：发出 A，再发出 B，先让 B 成功并确认页面显示 B，再让 A 成功，页面仍该留着 B。再让旧请求 A 最后失败，检查它没有盖住新结果，也没有弹出无关报错。过期错误也是一种状态污染。

3. 取消分两层测：一层看传给请求的 signal 确实被中止，另一层看取消之后界面怎么样。mock 要响应 abort 事件，接收时已经中止的 signal 也要处理。只断言调用了 `controller.abort`，证明不了请求封装和页面真处理了取消。

4. 再故意用一个不配合取消的 mock，让旧请求在取消之后照常返回，看请求编号这类过期检查还管不管用。取消是省资源，拦住旧结果写入才是页面正确性。两件事别合成一个断言。

5. 组件卸载、超时、新请求替换旧请求，分开验。尤其看旧请求的 `finally` 会不会提前关掉新请求的 loading。等相关处理走完再检查没有错误提示。取消客户端等待，也不能当成服务端业务已经停了。

## 追问：怎么用可控 Promise 复现后发先回？

1. 每个请求一个独立的控制柄，mock 按请求参数返回对应的 promise。下面这个教学用辅助函数只负责控制完成和失败，不含 fetch 的 signal 行为，取消测试还要另做 mock。

   ```js
   function deferred() {
     let resolve, reject;
     const promise = new Promise((ok, fail) => {
       resolve = ok;
       reject = fail;
     });
     return { promise, resolve, reject };
   }
   ```

2. 测试先通过两次输入发起 A 和 B，确认请求参数都对，再调用 `B.resolve`，等到 B 的结果出现。随后调用 `A.resolve`，等旧请求处理结束，断言页面内容没有回退，目标列表仍对应第二次输入。这样验的是旧响应确实执行过。

3. 再把 `A.resolve` 换成 `A.reject`，覆盖过期失败；B 保持 pending，检查 loading。每个用例重新创建控制柄，结束时把没完成的请求处理掉，别只完成一个 Promise，把另一个留给后面的测试。

## 追问：取消、超时和网络错误需要同样的提示吗？

1. 按业务含义分开。用户主动换搜索词或者离开页面时取消，通常不用报错。超时说明人还在等，但等待预算用完了，可以提示再试一次。真实网络错误按页面规则说明，这次操作没拿到有效响应。

2. 错误识别别只靠错误文本里有没有 abort。中止可以带自定义原因，封装库也可能转换错误。用请求上下文和约定的错误类型来判，主动取消和超时要测出不同的界面结果。别把全部中止都静默吞掉。

3. 错误归属也要验：旧请求哪怕是超时，也不该盖住最新一次搜索的成功状态。对写操作，结果仍可能不确定。页面退出 loading 只代表这次等待结束，测试不能据此断言服务端一定没产生业务记录。
