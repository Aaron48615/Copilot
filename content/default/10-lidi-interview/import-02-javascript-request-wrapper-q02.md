# 重试会不会把写操作执行多次？

## 核心回答

1. 重试确实可能让写操作执行多次，因为客户端没有收到响应，不代表服务端没有完成写入。假设创建订单时响应在回程丢失，前端看到的是超时，数据库里却可能已经有订单，此时重新提交就有重复创建的风险。

2. 我会根据接口实际语义决定是否允许重试，而不是只看请求方法或者状态码。读取一般更容易安全重试，但也要确认没有隐藏副作用；写操作即使使用了看起来幂等的方法，也应核对服务端是否真的按约定实现。

3. 如果要支持创建类接口自动重试，我会先要求服务端提供幂等约定，让同一次业务提交始终使用同一个键。服务端需要原子地识别重复请求，并返回已有结果，前端每次重新生成一个键就失去了去重作用。

4. 重试策略还要限制次数和总等待时间，只处理约定允许的暂时故障，并加入退避。参数错误、权限不足通常应直接交给业务处理，不能靠重复发送解决，用户主动取消后也不应该继续偷偷发出下一次请求。

5. 没有幂等能力时，我会把超时显示为结果待确认，优先按业务编号查询状态，再决定是否再次提交。按钮禁用只能减少当前页面的重复点击，用户刷新或多端操作仍可能重复，因此它不能替代服务端保护。

## 追问：幂等键应该什么时候生成和复用？

1. 我会在一次业务提交确定后生成键，把它和提交内容绑定保存，后续因网络故障发起的重试沿用这个键。比如同一份订单提交重发仍是同一操作，而用户修改商品后重新下单，应被视为新的业务意图。

2. 服务端除了保存键，还应核对请求内容是否一致，避免同一个键被用于不同金额或不同商品。并发收到相同键时，需要通过唯一约束或等效的原子机制处理，不能先查询不存在就让两个请求各自创建。

3. 键的有效期和处理中状态也要约定清楚，过期后重发不一定还具备去重保障。前端遇到处理中应查询或等待，不能直接换键绕过限制；这属于我会提出的接口设计要求，不代表已有项目实现过这套机制。

## 追问：用户取消下单后能直接提示下单失败吗？

1. 不能只根据取消请求就判断下单失败，取消主要结束客户端的等待和相关传输。服务端如果已经接收并处理了请求，订单可能照常创建，所以页面应说明当前尚未确认结果，避免误导用户重复购买。

2. 如果产品要求真正撤销订单，我会把它设计为独立业务操作，由服务端检查订单状态后决定是否允许取消。已付款或已发货的订单可能需要不同流程，这些约束不能靠浏览器里的取消信号替代。

3. 在交互上，我会保留本次业务编号，提供查询结果的入口，并区分关闭页面与撤销业务。恢复连接后先确认服务端状态，再展示成功、失败或可撤销操作，让用户知道下一步该做什么而不必反复点击提交。
