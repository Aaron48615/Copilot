# Promise.all 里一个请求失败了会怎样？

## 核心回答

1. Promise.all 返回一个汇总的 Promise，只要某个输入的拒绝被处理，汇总结果就会拒绝，并采用对应原因。它不会继续等齐成功结果再返回数组，但后续 catch 仍通过微任务执行，不能理解成同步抛错或终止当前代码。

2. 其他已经发出的请求会继续运行，成功的子 Promise 也没有被删除，只是汇总结果不再提供完整成功数组。如果还保存着这些子 Promise，仍然能单独读取结果，所以我不会把它简单说成所有结果都被扔掉。

3. 选哪种组合方式，要看页面是否允许部分成功。必须拿齐的数据可以统一等待 all；独立卡片更适合 allSettled 或分别更新状态，但 allSettled 要等全部结束，逐卡渲染时还需要各自处理完成回调。

4. 工单系统的数据看板包含统计、七日趋势和问题类型分布，三组数据独立拉取，趋势异常时其他卡片仍可展示。这个例子里应保留失败卡片的错误和重试入口，不能随便用空数组兜底，让用户误以为真的没有数据。

5. 如果一个失败后其余结果确实无用，可以显式取消支持 signal 的请求，不过取消不是事务回滚。还要注意 fetch 遇到 HTTP 错误状态通常仍会兑现，需要检查 response.ok 并主动抛错，汇总层才能按失败处理。

## 追问：每个请求先 catch 返回默认值有什么隐患？

1. 子请求 catch 后返回默认值，相当于把这个分支转成成功，外层 all 可能正常兑现。假设库存查询失败却返回零，页面会把接口异常显示成无库存；因此默认值是否安全，要看它会不会改变用户的业务判断。

2. 如果页面允许降级，我会把结果写成带状态的数据，同时保留错误原因，而不是只返回空数组。这样组件能够区分真实空数据与加载失败，成功卡片继续展示，失败卡片可以给出明确提示和单独重试按钮。

3. 必需数据失败时则继续向外抛错，让统一错误界面接管，不为了让 all 成功而吞掉异常。日志可以在统一入口记录，避免每个 catch 都上报一次；用户主动取消也应独立分类，防止把正常离开页面统计成接口故障。

## 追问：一个请求失败后怎样停止其余请求？

1. 假设这些请求属于同一轮加载，我会在启动前创建这一轮专属的控制器，把 signal 传给每个 fetch。汇总捕获失败后调用 abort，让仍在等待的请求尽快结束，但不能把其他页面或下一轮请求共用到同一个控制器里。

2. 取消发出后，已经完成的响应不会被收回，不支持取消的异步任务也可能继续运行。因此页面更新还应检查当前加载编号，过期结果不再覆盖界面，同时保留最初的失败原因，避免被后续取消错误掩盖。

3. 如果请求包含写操作，客户端取消只能说明不再等待，并不能证明服务端没有保存成功。对于提交订单等假设场景，我会通过业务查询或幂等机制确认最终状态，不能因为外层 all 拒绝，就直接重新发送整组写请求。
