# 购物车勾选以后总价是怎么更新的？

## 核心回答

1. 商品项的 checked 是基础状态，selectedBasketIds 用 computed 从选中项取 basketId。接口只需要这次选了哪些购物车行，不需要把前端页面的整个商品对象传过去，后端可以据此重新读取真实数量与价格。

2. allChecked 根据非空且每项 checked 为真计算，避免空购物车被 every 判成全选。点击全选时统一修改所有商品 checked，计算结果随之更新，单项取消后全选自然变为 false，不需要手动维护另一份相互同步的值。

3. 监听 selectedBasketIds 后调用 getCartTotal，拿 totalMoney 更新 totalPrice；没有选中时直接显示零，省去无意义请求。数量修改成功后也要重新计价，因为 basketId 未改变不能代表计价输入没有变化。

4. 当前总价请求还没有独立乱序保护。快速选 A、再选 A 加 B，前一份金额如果后到，就可能覆盖新金额；如果继续完善，我会用编号或输入版本控制写入，清空选择也必须让旧请求失效。

5. 提交栏展示的是金额预览，传给组件前需要核对其金额单位与接口约定，例如统一在接口适配层完成元与分的转换，避免多个组件重复换算。真正结算还要进入订单确认重新计算，前端勾选与展示做得正确，也不意味着优惠、库存或运费在后续步骤不会变化。

## 追问：一件都没选时设零，为什么还会显示回旧金额？

1. 因为此前可能已有计价请求在路上，清空时本地虽然设为零，旧请求随后仍执行赋值。用户操作已经改变，但异步任务不知道自己过期，最终就出现没有勾选却显示应付金额的矛盾界面。

2. 如果继续修复，我会在每次计价输入变化时先递增版本，包括变成空选择的情况，再决定是否发请求。这样旧响应无论成功或失败都不能修改当前金额与加载状态，不必等下一次非空请求才让它失效。

3. 测试先勾选发请求，再全部取消，最后才返回旧金额，最终必须仍为零。这个场景比只测两个非空选中集合更容易暴露遗漏，也说明本地提前赋零与异步失效需要一起做。

## 追问：全选之后删除，为什么要重新加载购物车？

1. 删除影响的不只是商品行，还可能让优惠分组或店铺变为空，相关合计也可能变化。重新请求可以取得服务端当前结构，避免只 splice 一个平面数组却留下空店铺或过期优惠信息。

2. 当前重新加载会重置 checked，这是已有行为，不应描述成自动保留所有选择。如果继续改善，可以先保存未删除项的 basketId，再与新列表求交集恢复，已经不存在的 ID 不能继续出现在结算参数里。

3. 重新加载后计价也要对应恢复后的真实选中集合，不能沿用删除前总价。验证跨店铺删除、仅剩一项和删成空车，检查分组、全选和金额同时合理，不能只看到被删商品消失就结束。
