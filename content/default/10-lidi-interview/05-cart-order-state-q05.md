# 购物车勾选以后总价是怎么更新的？

## 核心回答

1. 商品项的 `checked` 是基础状态，`selectedBasketIds` 用 computed 从选中项取出 `basketId`。接口只要这次选了哪些购物车行，不用把页面上整份商品对象传过去，后端再按这些 ID 去读真实数量和价格。

2. `allChecked` 看列表非空、并且每一项 `checked` 都是真。空购物车如果直接 `every`，会被判成全选，所以要避开。点全选就统一改所有商品的 `checked`，计算结果跟着变；单项取消后全选自然变成 `false`，不用再维护另一份互相同步的值。

3. 监听 `selectedBasketIds` 之后调 `getCartTotal`，拿 `totalMoney` 去更新 `totalPrice`。一件都没选就直接显示零，少发无意义请求。数量改成功也要重新计价，因为 `basketId` 没变，不代表计价输入没变。

4. 现在总价请求还没有独立的乱序保护。很快选 A，再选 A 加 B，前一份金额如果后到，可能把新金额盖掉。要挡住这个，可以用编号或输入版本控制写入；清空选择时，旧请求也得失效。

5. 提交栏展示的是金额预览。传给组件前要对齐金额单位和接口约定，比如在适配层把元和分换好，别让好几个组件各自换一遍。真正结算还得进订单确认重新算。勾选和展示对了，优惠、库存、运费后面照样可能变。

## 追问：一件都没选时设零，为什么还会显示回旧金额？

1. 因为前面可能已经有计价请求在路上。清空时本地先写成零，旧请求随后还是会赋值。用户已经没勾了，那个异步任务不知道自己过期，就出现没选中却显示应付金额。

2. 每次计价输入一变就递增版本，变成空选择也算一次变化，然后再决定发不发请求。旧响应不管成功失败，都不能再改当前金额和加载状态，不用等下一次非空请求才让它失效。

3. 测的时候先勾选发出请求，再全部取消，最后才让旧金额回来，界面还得是零。这比只测两套非空选中集合更容易漏。本地提前赋零，和异步失效，得一起做。

## 追问：全选之后删除，为什么要重新加载购物车？

1. 删除影响的不只是那一行，优惠分组或店铺可能变空，合计也可能变。重新请求能拿到服务端当前结构。只 `splice` 一个平面数组，容易留下空店铺或过期优惠信息。

2. 现在重新加载会把 `checked` 重置，这是已有行为，别说成会自动保住所有选择。要改善的话，可以先记下没删掉的 `basketId`，再和新列表求交集恢复；已经不存在的 ID 不能再出现在结算参数里。

3. 重新加载后，计价也要对上恢复后真正选中的那批，别沿用删除前的总价。跨店铺删除、只剩一项、删成空车都要看：分组、全选、金额是不是一起合理。商品行没了，不等于这一套都对了。
