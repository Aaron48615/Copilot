# 前端如何保护 Token 或 AI API Key？

## 核心回答

1. 我会先区分用户登录 Token 和服务端 API Key。用户 Token 代表当前会话或授权，浏览器可能需要使用；AI 服务的长期密钥属于服务端凭据，不应该打进前端代码或公开环境变量，二者不能用同一种保存方式处理。

2. 服务端密钥由自己的后端或受控函数读取，前端调用自己的业务接口，再由服务端访问外部服务。因为浏览器能执行、解密和发送的内容也能被用户检查，所以混淆或把解密密钥一起放前端，都不能真正保密。

3. 后端代理还要检查登录、权限和请求额度，不能只隐藏 Key 就开放一个任何人都能调用的转发接口。目标地址和允许操作也要受控，避免调用方任意指定第三方目标或参数，造成滥用和意外费用。

4. 登录 Token 的存储取决于认证设计。localStorage 易用但同源脚本可读，内存刷新后丢失，HttpOnly Cookie 限制读取但需考虑自动携带与 CSRF；无论选择哪种，服务端都要处理过期、撤销和资源权限。

5. 如果继续完善，我会减少令牌有效期和权限范围，避免在 URL、日志和错误上报中泄露，并验证退出及账号切换。没有一项前端技巧能保证凭据绝不被滥用，实际方案要覆盖使用、更新、失效和异常处理，而不是只讨论放在哪个变量里。

## 追问：把 API Key 放在 VITE_ 环境变量里为什么不安全？

1. 这类前缀变量用于向客户端暴露配置，构建时可能被替换进 JavaScript。文件叫环境变量并不意味着运行时只存在服务器，浏览器收到产物后可以查看或在请求里观察到它，压缩也不会改变这个事实。

2. 我会先检查变量真正在哪个环境读取，服务端密钥只保留在服务端配置，由后端完成对外调用。前端可以保存公开接口地址和功能开关，但这些值应被当作所有访问者都可能看到的信息。

3. 如果密钥已经发布，应立即按服务商能力撤销或轮换，并检查代码历史、产物和日志中的暴露范围。只是删掉源码变量再重新构建，不代表别人无法继续使用已经拿到的旧凭据。

## 追问：后端代理隐藏 Key 后，还需要限流吗？

1. 需要。攻击者即使不知道 Key，也可能反复调用你的代理接口，让后端替他消耗付费服务。隐藏凭据解决的是直接泄露问题，调用权限和成本控制仍需在自己的服务端实现，不能依赖前端禁用按钮。

2. 我会按账号和业务权限控制可用操作，并设置请求频率、并发和必要的用量上限。上传大小、输入长度和允许模型等参数也应验证，不能把任意客户端参数直接透传给外部服务，扩大原本授权范围。

3. 异常使用要能通过不含敏感正文的记录定位，并给正常用户清楚的限额提示。测试包括未登录、越权和重复请求，确认服务端真正拒绝不允许的调用，而不是前端页面看起来没有提供入口就算完成。
