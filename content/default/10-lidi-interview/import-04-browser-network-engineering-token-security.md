# 前端如何保护 Token 或 AI API Key？

## 核心回答

1. 用户登录 Token 和服务端 API Key 是两回事。用户 Token 代表当前会话或授权，浏览器可能需要用到。AI 服务的长期密钥属于服务端凭据，不该打进前端代码，也不该放进公开环境变量。两种东西不能用同一种保存方式。

2. 服务端密钥由自己的后端或受控函数读，前端调自己的业务接口，再由服务端去访问外部服务。浏览器能执行、解密、发送的内容，用户也能检查。混淆，或者把解密密钥一起放前端，都保不了密。

3. 后端代理还要检查登录、权限、请求额度。只藏 Key，却开放一个谁都能调的转发接口，等于没藏。目标地址和允许操作也要受控，调用方任意指定第三方目标或参数，容易被滥用，费用也会出去。

4. 登录 Token 存哪，取决于认证设计。`localStorage` 好用，但同源脚本能读；内存刷新后就没了；HttpOnly Cookie 限制读取，但要考虑自动携带和 CSRF。不管选哪种，服务端都要处理过期、撤销、资源权限。

5. 令牌有效期和权限范围尽量收小，URL、日志、错误上报里别泄露。退出和切账号要验证。没有一项前端技巧能保证凭据绝不被滥用。实际方案要覆盖使用、更新、失效、异常处理，讨论放在哪个变量里只是其中一小块。

## 追问：把 API Key 放在 VITE_ 环境变量里为什么不安全？

1. 这类前缀变量是用来向客户端暴露配置的，构建时可能被替换进 JavaScript。文件名叫环境变量，不意味着运行时只存在服务器上。浏览器收到产物后可以查看，请求里也能观察到。压缩改变不了这件事。

2. 变量真正在哪个环境读取，要分清。服务端密钥只留在服务端配置，由后端完成对外调用。前端可以保存公开接口地址和功能开关，这些值要当成所有访问者都可能看到的信息。

3. 密钥已经发布出去，按服务商能力立刻撤销或轮换，并检查代码历史、产物、日志里的暴露范围。只是删掉源码变量再重新构建，别人拿到的旧凭据可能还能用。

## 追问：后端代理隐藏 Key 后，还需要限流吗？

1. 需要。攻击者就算不知道 Key，也可能反复打你的代理接口，让后端替他消耗付费服务。隐藏凭据解决的是直接泄露，调用权限和成本控制还得在自己的服务端做。前端禁用按钮挡不住。

2. 按账号和业务权限控制能做什么，再设请求频率、并发、必要的用量上限。上传大小、输入长度、允许的模型这些参数也要验。任意客户端参数直接透传给外部服务，等于把授权范围放大了。

3. 异常使用通过不含敏感正文的记录去定位，正常用户给清楚的限额提示。测未登录、越权、重复请求，确认服务端真正拒绝了不允许的调用。前端页面看起来没有入口，不算完成。
