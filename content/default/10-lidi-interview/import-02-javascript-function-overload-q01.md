# 回调参数为什么有时不能少写？

## 核心回答

1. 这个问题要先区分少写形参和少传实参，回调省略不用的形参通常是允许的。比如数组遍历会传入元素和索引，我只声明元素参数也能正常使用，并不需要为了接收后忽略索引而多写一个变量。

2. 少传实参则是在调用函数时没有提供它要求的数据，例如函数声明需要姓名和年龄，直接只传姓名可能报错。接口承诺会传几个值，与回调作者愿意接收几个值，是两个不同方向的约束，不能混用结论。

3. 参数类型过窄又是另一件事，假设事件接口可能传鼠标事件或键盘事件，回调却只会读取鼠标坐标。即使回调数量完全没变，遇到键盘事件也可能出问题，严格函数类型检查会限制这类不安全赋值。

4. 可选参数表示调用方有权省略该实参，不是表示接收者可以不用它。若索引每次都会传入，就不应仅为了允许作者省略形参而把索引声明成可选，否则真正使用索引的代码反而需要处理不存在的情况。

5. 遇到报错，我会先看它发生在调用处还是赋值处，再核对参数数量、类型范围和可选性。严格函数类型检查对方法声明还有兼容性例外，因此不能用某个方法恰好通过编译来证明窄参数一定安全。

## 追问：遍历回调的索引参数，为什么不该为了方便省略而写成可选？

1. 假设遍历接口内部始终用元素和数字索引调用回调，类型应当把这个事实写清楚。使用者只关心元素时，本来就可以只声明第一个形参，不需要接口把第二个参数改成可能缺失。

2. 一旦索引被声明为可选，接口就允许实现只传元素，接收方看到的索引也可能是 undefined。开启严格空值检查后，直接做数字运算会受到限制，这个麻烦来自错误描述调用约定，而不是检查太严格。

3. 我会对照调用回调的实际代码决定是否可选，再分别检查只用元素和同时使用索引的调用方式。假如某些分支确实不传索引，就应该保留可选性并解释业务含义，不能为了消除提示强行保证它存在。

## 追问：只接受鼠标事件的函数，为什么不能处理任意事件的回调位置？

1. 回调位置声明能收到任意事件，意味着注册方有权传入键盘事件等其他事件。只接受鼠标事件的函数可能直接访问坐标字段，它对输入的要求更高，无法履行这个位置原本承诺的处理范围。

2. 在严格函数类型检查适用的函数赋值场景，这种把参数范围缩窄的替换会被拒绝。反过来，一个能处理一般事件的函数用于只接收鼠标事件的位置，通常没有这个风险，因为实际输入没有超出它的能力。

3. 假如业务确实只注册点击处理，我会让事件名称与回调参数类型建立对应关系，而不是用断言绕过检查。若来源无法保证事件类别，就应在回调内先判断再读取专属字段，把运行时边界也补完整。
