# defer 脚本的执行顺序可靠吗？

## 核心回答

1. 对于文档里由解析器发现的外部经典脚本，defer 会让下载与 HTML 解析并行，等文档解析完成后按文档顺序执行。比如先引入工具库再引入依赖它的业务脚本，两者都使用 defer 时，不会因为业务文件先下载完就先执行。

2. DOMContentLoaded 会等待这些 defer 脚本执行完成，但不等于等待页面中所有异步工作。脚本内部发起一个网络请求后马上返回，浏览器不会自动等那个请求完成才执行后一个脚本，异步依赖仍需明确用 Promise 或事件表达。

3. 这个顺序保证不能直接套到动态插入的 script。通过代码创建并加入页面的外部脚本有自己的执行规则，设置 defer 也不意味着获得文档解析脚本的同样行为；需要有序加载时应显式组织顺序或使用模块依赖。

4. 内联经典脚本上的 defer 没有同样效果，模块脚本默认具有延后执行行为，也不靠再加 defer 生效。如果同时添加 async 和 defer，现代浏览器会按 async 处理，不能把两个属性叠上去当成既有顺序又最快。

5. 我会先明确脚本类型和插入方式，再用依赖例子验证执行时间。defer 避免下载阶段阻塞解析，但执行中的大计算仍在主线程，占用时间依旧会影响渲染与交互，不能把它理解成后台线程执行。

## 追问：前一个 defer 脚本发请求，后一个能直接使用请求结果吗？

1. 不能，defer 保证的是脚本执行顺序，不保证第一个脚本内部启动的异步任务已完成。前一个脚本发起 fetch 后结束，后一个脚本就可能开始，此时全局变量仍未被异步回调赋值，直接使用会出错。

2. 我会把异步初始化包装成明确的 Promise，让真正依赖它的业务等待结果，或者把初始化放进同一个模块流程。不要用固定 setTimeout 猜网络什么时候结束，慢网和失败场景会很容易打破这种假设。

3. 还需要为初始化失败设计可见状态，避免后续页面永远等待一个不会完成的条件。测试时延迟首个请求并模拟错误，确认页面不会因为脚本顺序看似正确，就在数据尚未准备好时继续执行操作。

## 追问：动态加载两个有依赖的脚本，如何保证顺序？

1. 最清楚的方式是先完成第一个脚本加载，再加载依赖它的第二个，并分别处理 onload 和 onerror。这样顺序来自代码的显式控制，而不是假设两个动态 script 标签写得靠前靠后就一定按顺序执行。

2. 合适的情况下可以在插入前设置动态外部脚本的 async 为 false，但仍要理解它与解析器 defer 的区别。若源码可控，我更愿意用 ESM 的 import 表达依赖，让构建与模块系统负责关系，减少全局变量耦合。

3. 加载函数还要处理重复调用、超时和已有脚本，避免多次初始化同一个 SDK。验证时让第二个资源下载更快，再确认仍按预期初始化，同时保证第一个失败后不会继续执行依赖它的功能。
