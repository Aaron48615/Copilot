# defer 脚本的执行顺序可靠吗？

## 核心回答

1. 文档里由解析器发现的外部经典脚本，加了 `defer`，下载可以跟 HTML 解析并行，等文档解析完再按文档顺序执行。先引入工具库，再引入依赖它的业务脚本，两个都 `defer`，不会因为业务文件先下完就先跑。

2. `DOMContentLoaded` 会等这些 defer 脚本执行完，但不会等页面里所有异步工作。脚本里面发了个网络请求就返回了，浏览器不会自动等那个请求完成才执行后一个脚本。异步依赖还得用 Promise 或事件自己说清楚。

3. 这个顺序保证套不到动态插入的 `script` 上。用代码创建再加进页面的外部脚本，有自己的执行规则，设了 `defer` 也不等于拿到文档解析脚本那一套行为。要有序加载，就显式排顺序，或者用模块依赖。

4. 内联经典脚本上的 `defer` 没有同样效果。模块脚本默认就是延后执行，不靠再加一个 `defer`。同时写了 `async` 和 `defer`，现代浏览器按 `async` 处理。两个属性叠上去，不会既保顺序又最快。

5. 脚本类型和插入方式先分清，再用有依赖的例子看执行时间。`defer` 避免下载阶段挡住解析，但执行时的大计算仍在主线程，占用时间照样影响渲染和交互。它不是丢到后台线程去跑。

## 追问：前一个 defer 脚本发请求，后一个能直接使用请求结果吗？

1. 不能。`defer` 保证的是脚本执行顺序，不保证第一个脚本里面启动的异步任务已经完成。前一个脚本发起 `fetch` 就结束了，后一个可能马上开始，这时全局变量还没被异步回调赋值，直接用会出错。

2. 异步初始化包成明确的 Promise，真正依赖它的业务等结果；或者把初始化放进同一个模块流程。别用固定 `setTimeout` 猜网络什么时候结束，网一慢、请求一失败，这种假设就破。

3. 初始化失败要有可见状态，后续页面别永远等一个不会完成的条件。测的时候把首个请求拖慢，再模拟错误。脚本顺序看起来对，数据还没准备好就继续操作，页面会出问题。

## 追问：动态加载两个有依赖的脚本，如何保证顺序？

1. 最清楚的是先等第一个脚本加载完，再加载依赖它的第二个，`onload` 和 `onerror` 分别处理。顺序来自代码里显式控制，两个动态 `script` 标签写得谁前谁后，不保证按那个顺序执行。

2. 插入前把动态外部脚本的 `async` 设成 `false`，有时能用，但仍要分清它跟解析器 `defer` 不是同一套。源码自己能控，更愿意用 ESM 的 `import` 表达依赖，让构建和模块系统管关系，少靠全局变量耦合。

3. 加载函数还要处理重复调用、超时、页面上已经有这份脚本，避免同一个 SDK 初始化多次。让第二个资源下载更快，再确认仍然按预期初始化。第一个失败了，依赖它的功能不要继续跑。
