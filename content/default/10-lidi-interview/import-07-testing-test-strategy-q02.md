# 测试应该断言什么？

## 核心回答

1. 我会先把需求翻译成可以观察的结果，再选择断言。比如表单缺少必填项时，应出现对应提示且不发送提交请求；保存成功时，应展示新内容并退出编辑状态，比断言组件内部某个变量变成 true 更能说明行为正确。

2. 函数测试主要检查输入输出和约定异常，组件测试主要检查渲染、操作结果和必要副作用。请求方法、参数和是否重复提交也可能是重要约定，因此不是完全不看调用记录，而是看这条断言是否真的保护了业务要求。

3. 异步断言要等待结果出现，并确认测试本身返回或 await 了等待过程。例如 Testing Library 的 findBy 可以等待元素，waitFor 里通过会抛错的断言等待条件满足；只返回 false 并不会按我想象的方式要求继续重试。

4. 我会同时检查容易遗漏的错误结果，例如提交失败后错误提示出现，输入内容保留，按钮可以再次操作。否定断言要有正确时机，不能刚点提交就断言没有成功提示，因为请求未结束时这个结果没有什么证明力。

5. 断言精度应跟需求相称，金额和权限结果要准确，随机生成的记录编号则可检查格式及对应关系。大快照只适合辅助观察结构，关键行为仍要明确断言；否则一大段快照被整体更新后，真正的错误可能混在变化里没有被注意到。

## 追问：什么时候需要断言接口被调用了几次？

1. 当调用次数就是约定的一部分时，例如防重复提交要求连续点击只发一次请求，或者输入防抖要求停顿后才查询。我会在受控时间里发起操作、确认请求参数，再断言次数，否则一次发错参数的请求也可能满足数量要求。

2. 只关注最终页面结果的测试，则不一定要固定所有内部调用次数。例如组件换了缓存实现后多一次合法读取，如果需求没有限制，测试不应仅因此失败；我要先区分这是性能要求、业务副作用，还是偶然的实现方式。

3. 对会产生写入的请求，客户端只发一次也不能证明服务端只写了一条，代理重试或接口实现仍有影响。组件测试负责请求行为，幂等效果需要在相应服务测试里验证；我会避免让一个调用次数断言承担超出它能力的结论。

## 追问：快照通过，为什么页面功能仍可能坏了？

1. 快照记录的是某个时刻的结构或图像，按钮看起来存在，不代表点击之后会执行正确操作。比如保存按钮丢了事件处理，初始 DOM 快照可能完全不变，因此还需要真实触发保存，并检查更新结果或约定请求。

2. 大快照包含很多不相关信息，更新时容易把错误一起接受。我会把快照范围缩到有价值的局部，审核变化原因；对提示文字、数量和禁用状态这类明确要求，直接写具体断言更容易让人知道测试失败意味着什么。

3. 视觉回归还能发现布局变化，但会受字体、浏览器和渲染环境影响，所以要固定比较条件并人工确认差异。它与行为测试保护的对象不同，截图一致不能证明接口成功，接口成功也不能证明页面没有遮挡，两种结果需要分别解释。
