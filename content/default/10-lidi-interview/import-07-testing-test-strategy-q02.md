# 测试应该断言什么？

## 核心回答

1. 需求先翻成能观察的结果，再选断言。表单缺必填项，该出现对应提示，并且不发提交请求。保存成功，该展示新内容并退出编辑。断言组件内部某个变量变成 `true`，说明不了行为对。

2. 函数测试主要查输入输出和约定异常。组件测试主要查渲染、操作结果、必要副作用。请求方法、参数、有没有重复提交，也可能是重要约定。不是完全不看调用记录，而是看这条断言是不是真保护了业务要求。

3. 异步断言要等结果出现，测试本身也要返回或 await 这个等待。Testing Library 的 `findBy` 可以等元素，`waitFor` 里通过会抛错的断言等条件满足。只返回 `false`，不会按想象的方式继续重试。

4. 容易漏的错误结果也要查：提交失败后错误提示出现、输入内容还在、按钮能再点。否定断言要有正确时机。刚点提交就断言没有成功提示，请求还没结束，这个结果没什么证明力。

5. 断言精度跟需求相称。金额和权限结果要准，随机生成的记录编号可以查格式和对应关系。大快照只适合辅助看结构，关键行为还是明确断言。一大段快照被整体更新之后，真正的错误可能混在变化里没被注意到。

## 追问：什么时候需要断言接口被调用了几次？

1. 调用次数本身就是约定的一部分时才需要。比如防重复提交要求连续点击只发一次，输入防抖要求停顿后才查询。在受控时间里发起操作、确认请求参数，再断言次数。一次发错参数的请求，数量也可能对。

2. 只关心最终页面结果的测试，不一定要钉死所有内部调用次数。组件换了缓存实现之后多一次合法读取，需求没限制，测试不该只因此失败。先分清这是性能要求、业务副作用，还是偶然的实现方式。

3. 会产生写入的请求，客户端只发一次，也证明不了服务端只写了一条。代理重试、接口实现仍有影响。组件测试负责请求行为，幂等效果要在相应服务测试里验。别让一个调用次数断言承担超出它能力的结论。

## 追问：快照通过，为什么页面功能仍可能坏了？

1. 快照记的是某个时刻的结构或图像。按钮看起来在，不代表点下去会执行正确操作。保存按钮丢了事件处理，初始 DOM 快照可能完全不变。还得真去点保存，再查更新结果或约定请求。

2. 大快照里有很多不相关信息，更新时容易把错误一起接受。快照范围缩到有价值的局部，变化原因要审。提示文字、数量、禁用状态这类明确要求，直接写具体断言，失败时才知道意味着什么。

3. 视觉回归还能发现布局变化，但受字体、浏览器、渲染环境影响，比较条件要固定，差异要人确认。它和行为测试保护的对象不同。截图一致证明不了接口成功，接口成功也证明不了页面没有遮挡，两种结果分开解释。
