# source map、构建缓存和可复现构建怎么做？

## 核心回答

1. source map、缓存和可复现构建分别解决调试、效率与结果可信度的问题，我会把它们连接到同一个发布版本。定位线上错误需要知道用户实际执行哪份代码，再用对应映射回到源码，不能拿当前工作区的行号直接解释压缩堆栈。

2. 生产 map 可以生成后上传到受限平台，公开部署时排除，并记录版本关联。hidden 只影响自动引用，不等于文件不可下载；源码和构建产物本身也不应包含密钥，关闭映射不会让客户端代码中的凭据变得保密。

3. 构建缓存可以复用依赖和中间转换结果，但要明确输入。锁文件、构建配置、工具版本和影响产物的环境变量变化时，应让相应缓存失效；缓存命中只能说明工具选择了复用，不能直接证明最终结果符合新代码。

4. 可复现构建需要固定源码、依赖与工具环境，并减少时间戳、随机数和机器绝对路径等不稳定因素。锁文件很重要，但不是唯一条件；如果构建时从网络下载一份随时变化的数据，同一份源码仍可能生成不同内容。

5. 如果继续完善，我会在干净环境完成发布构建，把产物、版本与映射一起校验，再部署同一份文件。测试兼顾重复构建的一致性和真实页面可用性，不能为了 hash 一致而忽略功能，也不把不同环境的偶然成功当成稳定流程。

## 追问：锁文件一致，为什么两台机器产物仍可能不同？

1. 运行时、包管理器和系统平台可能不同，原生依赖、路径大小写或换行处理都会影响构建。环境变量和构建参数也可能注入不同内容，所以锁文件只固定依赖解析的一部分，不代表所有输入完全相同。

2. 我会比较工具版本、平台、配置和实际安装结果，再检查生成文件是否包含时间戳或绝对路径。构建脚本如果读取外部接口或本机文件，也需要固定或显式记录这些输入，不能只要求同事重新执行安装命令。

3. 验证时在受控环境重复构建并分析具体差异，区分无意义元信息和业务内容变化。目标是理解并控制来源，而不是简单重命名文件让 hash 看起来一样，隐藏真实的不确定性。

## 追问：依赖缓存和完整产物缓存，哪个风险更大？

1. 风险取决于缓存是否正确标识输入，但完整产物缓存离发布结果更近，错误命中可能直接把旧页面部署出去。依赖下载缓存通常只是复用已获取的包，仍会进行后续构建，两者不能用相同的正确性判断。

2. 我会分别记录缓存层和键，避免把下载成功误当成构建已验证。完整产物缓存尤其要涵盖源码、锁文件、工具链和公开配置，并校验产物对应的版本，不能只按分支名或最近一次成功结果复用。

3. 无论选择哪层缓存，都要保留相关测试和必要的干净基线。缓存应减少重复工作，而不是绕开发布验证；出现问题时能够说明哪份产物来自什么输入，比只展示一次构建很快更重要。
