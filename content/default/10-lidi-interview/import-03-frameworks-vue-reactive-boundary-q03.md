# markRaw 会带来什么影响？

## 核心回答

1. `markRaw` 给对象打个标记，之后它再进 Vue 的响应式转换，会保持原始对象。适合复杂第三方实例，或明确不需要代理的数据。它管的是响应式边界，不是给普通业务对象贴一个“更快”的通用标签。

2. 打过标记，直接改这个原始对象内部字段，不会因为这个对象建立正常的代理跟踪。用户资料整份 `markRaw`，再改昵称，界面可能不动。业务要字段实时跟上，别为了少一层代理把通知也拿掉。

3. 它只保证被标记的这个对象，不会自动递归整棵嵌套结构。里面某个普通对象单独放进另一份 `reactive` 状态，仍可能变成代理。同一份业务数据于是同时有原始和代理两种形态，用 `===` 比可能对不上。

4. 已经生成的代理，也不能靠再 `markRaw` 理解成全部撤销。在对象进来的地方就把边界定好。需要原始对象可以用 `toRaw`，别长期一手握原始、一手握代理，还分别改。哪个访问会触发依赖，会变得很难讲。

5. `markRaw` 用在明确的基础设施边界，比如存图表实例。界面通过单独的响应式就绪状态，或外层替换整份引用，来知道变了。实例方法、身份比较、销毁都要测。第一次创建成功不够，也不能说打了标记内存和性能一定更好。

## 追问：为什么同一个嵌套对象可能出现不相等的比较结果？

1. 外层对象被 `markRaw` 了，里面的 `nested` 没有单独标记。把 `nested` 再放进 `reactive` 容器，读出来可能是它的代理。原来的 `nested` 和这个代理严格相等比不过，底层业务内容其实还是那份。

2. 用对象引用当 Map 键、集合成员，或交给第三方库查找，原始对象和代理混用就可能找不到。业务层用稳定编号更稳。必须用原始实例的接口，就始终保持同一种身份形式。

3. 别为了修比较满地散 `toRaw`，边界更难看清。数据进系统时就定哪些保持原始、哪些交给 Vue。对象在不同容器之间传来传去，行为要测。

## 追问：markRaw 和 shallowRef 可以一起用吗？

1. 可以，先看是不是两个都需要。`shallowRef` 本来就不会把保存进去的普通对象再深层转换，单纯存实例可能已经够。`markRaw` 额外表达：这个对象之后进别的响应式容器，也保持原始身份。

2. 两者都不替你管资源生命周期。外层 `ref` 的值被换掉，旧实例不会自动 `dispose`，替换或卸载时要自己放。界面要更新，通过外层引用或单独状态通知，别指望内部字段自动响应。

3. 对象会传到多远，再决定要不要额外标记。命名上说明这是外部实例。没有跨容器需求，不必叠很多响应式工具。工具多不代表边界清，调用方知道怎么更新、怎么释放才算清。
