# markRaw 会带来什么影响？

## 核心回答

1. markRaw 用来标记一个对象，使它在之后进入 Vue 响应式转换时保持原始对象。它适合复杂第三方实例或明确不需要代理的数据，重点是控制响应式边界，不是给普通业务对象加一个“性能更快”的通用标记。

2. 标记后，对这个原始对象内部字段的直接修改，不会因为该对象而建立正常的代理跟踪。比如把用户资料整体 markRaw，随后修改昵称，界面可能不更新；如果业务要求字段实时响应，就不能为了减少代理而把必要通知一起去掉。

3. 它只保证被标记对象本身的处理，不是自动递归标记整棵嵌套结构。内部某个普通对象单独放到另一份 reactive 状态里，仍可能变成代理，同一业务对象因此同时存在原始和代理形式，引用相等判断可能出现意外。

4. 已经产生的代理也不能简单靠 markRaw 理解成全部撤销，使用时应在合适的对象来源处规划。需要获取原始对象可以了解 toRaw，但不宜长期交叉持有原始和代理引用并分别修改，否则很难判断哪个访问触发依赖、哪个不会。

5. 我会把 markRaw 限制在明确的基础设施边界，例如保存图表实例，并让界面通过独立的响应式就绪状态或外层替换获知变化。验证要覆盖实例方法、身份比较和销毁，不只确认第一次创建成功，更不能宣称标记之后内存和性能一定改善。

## 追问：为什么同一个嵌套对象可能出现不相等的比较结果？

1. 假设外层对象被 markRaw，但里面的 nested 没有单独标记；把 nested 再放入 reactive 容器后，读取时可能得到它的代理。原来的 nested 与这个代理用严格相等比较不同，虽然都指向同一份底层业务内容。

2. 如果代码用对象引用作 Map 键、集合成员或第三方库查找依据，原始对象和代理混用就可能查询失败。更稳妥的是在业务层使用稳定编号，在必须使用原始实例的接口处保持明确的一种身份形式。

3. 我会避免为了修复比较就在各处散落 toRaw 调用，因为那会让响应式边界更难追踪。应从数据进入系统的位置决定哪些保持原始、哪些由 Vue 管理，并测试对象在不同容器之间传递时的行为。

## 追问：markRaw 和 shallowRef 可以一起用吗？

1. 可以，但先看是否确实需要两者。shallowRef 本来就不主动深层转换所保存的普通对象，单纯保存实例时可能已经够用；markRaw 还可以表达该对象之后进入其他响应式容器时也保持原始身份的意图。

2. 两者都不替代资源生命周期管理。外层 ref 的值被替换时，旧实例不会因此自动 dispose，需要在替换或卸载时释放；如果还要更新界面，应通过外层引用或单独状态通知，而不是期待内部字段自动响应。

3. 我会按对象的传递范围决定是否额外标记，并在接口文档或命名上说明它是外部实例。没有跨容器需求时，不必叠加很多响应式工具，工具越多不代表边界越清楚，关键是调用者知道怎样更新和释放。
