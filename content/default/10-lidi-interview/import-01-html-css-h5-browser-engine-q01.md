# JavaScript 执行为什么会影响页面流畅度？

## 核心回答

1. JavaScript 会影响页面流畅度，主要因为页面脚本和很多样式、布局工作都要走主线程。一段同步任务跑很久，主线程来不及处理后面的输入、也来不及安排画面更新，按钮就会觉得慢，滚动中的内容也跟不上。

2. 比如点按钮以后立刻同步处理很大一份数据，即便代码先把「加载中」写进 DOM，也不保证用户马上看见。浏览器还要拿到渲染机会才能把变化画出来。当前任务一直不结束，画面可能等到计算做完才一起更新。

3. 微任务也一样。把计算放进 `Promise.then` 不等于丢到后台，持续往外吐微任务仍可能把渲染往后推。另一方面，浏览器还有网络、合成等其他线程或进程，执行 JavaScript 时整个浏览器不会完全停住，有些已经准备好的合成动画仍可能继续。

4. 处理时先定位长任务，再减少重复工作、把能分批的拆开。独立计算必要时交给 Worker。视觉更新可以配合 `requestAnimationFrame`，但回调里的活仍要轻。最终用同一交互下的记录验证。代码改成 `async`，不自动等于不会阻塞。

5. 页面越复杂，一次修改卷进去的范围也可能越大。给列表每个项目连续改样式再量位置，脚本和布局开销会交替出现。既要看工作数量，也要看读写顺序，别只盯某个函数里有没有很长的循环。

## 追问：为什么 await Promise.resolve() 不能可靠地让加载动画先显示？

1. 它把后续代码排到微任务里。微任务通常在当前任务结束后、浏览器下一次渲染机会之前继续跑。后面如果仍是很重的同步计算，主线程可能还是没有先把加载状态画到屏幕上的机会。

2. 要分批工作，得选真正能让出主线程调度机会的方式，并控制每批耗时。跟 DOM 无关的大计算可以转到 Worker。大循环前插一个 `await`，不等于浏览器已经有时间响应用户。

3. 实际录一段交互，看加载提示什么时候出现、输入还能不能响应。`async` 只是函数返回和等待的语言机制，不自动代表并行执行。有没有改善，看任务怎么排、每段执行多久，别只看代码里有没有 `await`。

## 追问：哪些工作适合放到 Web Worker？

1. 比较适合不直接依赖 DOM 的计算，比如较大的数据转换、解析、搜索。Worker 有自己的执行环境，能减轻主线程同步计算。页面元素操作仍得回到主线程完成，整段 UI 更新代码搬不过去。

2. 还要算数据传递成本。大对象复制可能又耗时又占内存；支持的话可以用可转移对象，但转移后原来这边怎么访问会变。任务本来很小，创建和通信的开销可能比计算本身还大。

3. 请求和结果带上标识，用户切换条件以后丢掉旧结果，组件结束时处理取消或终止。迁过去以后，响应性和结果一致性一起验。主线程变轻了，异步返回顺序乱了却显示出过期内容，也不行。
