# JavaScript 执行为什么会影响页面流畅度？

## 核心回答

1. JavaScript 会影响页面流畅度，主要是因为页面脚本和很多样式、布局工作都需要主线程。一个同步任务执行很久时，主线程不能及时处理后续输入和安排画面更新，用户就会感到按钮反应慢或滚动中的内容跟不上。

2. 例如点击按钮后立即同步处理很大的数据集合，即使代码先把“加载中”写进 DOM，也不保证用户马上看到它。浏览器还要获得渲染机会才能把变化画出来，如果当前任务一直不结束，画面可能直到计算做完才一起更新。

3. 微任务也要注意。把计算放进 Promise.then 不等于放到后台，持续产生微任务仍可能推迟渲染。另一方面，浏览器有网络、合成等其他线程或进程，不能说执行 JavaScript 时整个浏览器完全停住，有些已准备好的合成动画仍可能继续。

4. 我的处理思路是先定位长任务，再减少重复工作、拆分可分批任务，独立计算必要时交给 Worker。视觉更新可以配合 requestAnimationFrame，但回调里工作仍要轻量；最终通过相同交互下的记录验证，不能仅凭代码改成 async 就声称已经不会阻塞。

5. 页面越复杂，一次修改涉及的范围也可能越大。例如给列表每个项目连续改样式并测量位置，会让脚本与布局开销交替出现；我会检查工作数量和读写顺序，而不是只关注某个函数内部是否写了很长的循环。

## 追问：为什么 await Promise.resolve() 不能可靠地让加载动画先显示？

1. 它把后续代码安排到微任务中，而微任务通常会在当前任务结束后、浏览器下一次渲染机会之前继续执行。如果后续仍然是很重的同步计算，主线程可能依然没有先把加载状态画到屏幕上的机会。

2. 如果要分批工作，应选择确实能让出主线程调度机会的方式，并控制每批耗时。也可以把与 DOM 无关的大计算转到 Worker，而不是只在大循环前插一个 await，就认为浏览器已经有时间响应用户。

3. 我会实际录制交互，观察加载提示出现时机和输入是否可响应。async 只是函数返回和等待的语言机制，不自动代表并行执行；判断有没有改善，需要看任务安排与每段执行时间，而不是看代码里有没有 await。

## 追问：哪些工作适合放到 Web Worker？

1. 比较适合的是不直接依赖 DOM 的计算，例如较大的数据转换、解析或搜索处理。Worker 有自己的执行环境，可以减少主线程同步计算，但页面元素操作仍需要回到主线程完成，不能直接把整段 UI 更新代码搬过去。

2. 还要考虑数据传递成本。大对象复制可能消耗时间和内存，支持时可以使用可转移对象，但转移后原侧的访问方式会变化；如果任务本来很小，创建和通信的开销可能比计算本身还大。

3. 我会让请求和结果带上标识，用户切换条件后忽略旧结果，并在组件结束时处理取消或终止。迁移后同时验证响应性与结果一致性，不能让主线程变轻了，却因为异步返回顺序不同显示过期内容。
