# 首页点击商品分组后，分类页怎么知道用户想看哪个分类？

## 核心回答

1. 首页和分类页是两个页面，所以用户点了某个分组以后，需要把这次选择带到分类页。当前实现会把分组标题放进路由 query 的 `value`，同时在 `sessionStorage` 写入 `fromHome = '1'`，表示这是一次从首页过来的分类选择。

2. 分类页挂载时读取这两个值，再用 `categoryMap` 把标题映射成左侧分类下标。比如首页显示某个商品分组，分类页要找到对应的分类项，而不是每次都停在第一个分类。这里依赖的是前端事先定义好的标题和下标关系。

3. `fromHome` 的作用是说明这一次要使用 query 里的选择。如果用户之后从普通入口进入分类页，不希望旧参数又让分类改变。处理过后就删除标记，表示这次导航信息已经消费完了；它不是一个需要长期保存的用户偏好。

4. 这个方案对固定分类的小项目比较直接，但也有不足。标题可能改名，分类顺序也可能变化，写死的映射就容易失效。另外 `sessionStorage` 和 URL 是两处信息，直接分享链接时不一定同时带着标记，页面行为就不完全由链接决定。

5. 如果继续改，更倾向传稳定的 `categoryId`，分类数据回来后根据 ID 找到对应项。参数无效时回到默认分类或给出提示，这样刷新、直接打开和分享链接的含义更容易保持一致。这是改进方向，不是说当前代码已经换成了这种实现。

## 追问：为什么不直接把分类下标放进 URL？

1. 下标表示的是当前列表里的位置，不是分类本身的身份。比如今天第三项是运动用品，明天前面新增了一个分类，原来的下标就可能指向另一个内容，但用户保存的链接并没有改变。

2. 稳定的分类 ID 更适合表示“我想看哪个分类”。页面拿到分类列表以后再找这个 ID 对应的位置，排序变化不会改变链接的含义。商品详情同样通常传商品 ID，而不是首页卡片的下标。

3. 当然，拿到 ID 也不能直接相信它一定有效。分类可能已经下架或用户手动改了参数，所以要检查是否存在；查不到就使用明确的默认行为，不能继续用找不到的下标访问数组。

## 追问：sessionStorage 适合存这种信息吗？刷新以后会怎样？

1. 它适合保存当前标签页会话内的临时数据，同一个标签页刷新通常不会马上丢失。这意味着如果 fromHome 还没有消费，刷新后可能还会读到，所以读取后及时删除对一次性标记很重要。

2. 它也不能等同于任意页面之间都共享的全局变量。不同标签页的会话存储通常独立，新窗口可能因打开方式获得初始副本，但之后不是持续同步的。因此不能依赖这个标记让别人打开分享链接时得到完全一样的行为。

3. 如果状态本身应该随链接分享，例如选中的分类，放进 URL 会更清楚；只属于一次操作的临时信息，再考虑会话存储。看这个状态需要活多久、刷新后要不要保留、别人打开链接时要不要相同。
