# 城市视图的仪表盘数据是怎么获取和展示的？

## 核心回答

1. 城市视图仪表盘会加载概览、事件统计、公共设施、交通排行和最新事件五组数据。它们不依赖彼此的响应，所以页面调用请求函数后用 Promise.all 汇总，成功再更新对应卡片、列表与 ECharts 图表，减少串行等待。

2. 当前采用整体成功处理，一个请求失败就进入统一 catch，这一轮其他成功结果也不会按正常成功分支写入。Promise.all 不会自动取消剩余请求，当前各卡片没有独立重试入口，如果要让成功模块继续更新，还需要拆分结果处理和错误状态。

3. 页面既有手动刷新，也每五分钟自动刷新，卸载时清理定时器。现有 loading 主要服务界面，没有完整阻止手动与定时请求重叠；如果继续完善，我会用请求状态控制重入，并在页面隐藏时考虑暂停不必要的刷新。

4. CSV 由后端导出接口生成，前端以 Blob 接收，创建临时下载 URL，触发下载后释放。前端不用再把表格内容逐行拼成文件，前端需要传递正确筛选条件，而编码、字段转义与数据范围主要核对导出端。

5. 登录与主题等共享信息由 Redux Toolkit 管理，单页图表数据与临时交互尽量留在组件。图表拿到有效数据后转换成 option 更新实例，不能在每次请求完成时重新创建图表，也不能把某次缓存统计当成持续实时数据。

## 追问：五分钟刷新会不会和手动刷新撞在一起？

1. 会有这种可能，当前 loading 主要用于展示，没有作为完整互斥条件。定时器触发时上一轮可能仍在等待，用户又点刷新，就可能同时出现多轮请求，增加接口压力并产生旧结果覆盖。

2. 如果继续完善，可以用 ref 记录进行中的任务，未结束时跳过新一轮；也可以在本轮结束后再安排下一次 setTimeout。前者保持计划时间，后者减少重叠但刷新间隔会包含处理耗时，要按实际需求选择。

3. 还要让结果与本轮筛选绑定，并在卸载时取消定时任务、使旧响应失效。验证故意延迟请求超过刷新周期，再触发手动刷新，检查不会重复更新或让过期错误影响新结果，不能只看按钮上的转圈图标。

## 追问：导出文件如何与当前筛选保持一致？

1. 发起导出时要保存当次城市、时间范围等筛选快照并传给后端，不能请求进行中又从变化后的表单读取参数。文件名称或页面提示也应对应这个快照，用户才知道导出的是哪一组数据。

2. 后端需要用同样的筛选与权限范围生成文件，不能列表按用户权限过滤，导出却返回所有数据。前端拿到 Blob 只能证明收到了二进制响应，还应按约定检查错误响应，避免把错误 JSON 下载成 CSV。

3. 验证选择一个容易核对的小范围，对照页面与文件中的城市、时间和记录数量。导出可能覆盖完整筛选结果而页面只显示一页，二者不必逐行相同，但范围与口径要一致，不能把分页差异误判成错误。
