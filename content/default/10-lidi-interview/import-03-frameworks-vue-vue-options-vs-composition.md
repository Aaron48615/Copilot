# Options API 和 Composition API 有什么区别？

## 核心回答

1. Options API 按 data、methods、computed 和生命周期等选项组织组件，结构固定，简单页面容易找到状态和方法。功能复杂后，同一个搜索流程的状态、监听、请求与清理可能分散在多处，修改时需要在几个选项之间来回查看。

2. Composition API 可以按功能把相关状态和行为放在一起，并提取为 composable。例如搜索条件、请求状态和取消逻辑放在同一组代码，弹窗草稿另成一组，读者更容易围绕某个业务需求理解和修改，不必按 API 类型拆散全部逻辑。

3. 组合式主要使用普通变量和函数，不依赖组件 this，类型推断和跨函数组合比较自然。逻辑复用也比 mixin 的隐式属性注入更显式，调用处能看到来源和返回值；但函数抽得太碎或参数过多，仍会增加阅读成本，写法本身不保证可维护。

4. 两套 API 都使用 Vue 的组件和响应式能力，不应把它们说成两个完全不同的运行时框架。Options API 仍适合既有代码和某些简单组件，Composition API 也可以在同一个项目逐步采用，没有必要只为了风格一致就一次性重写所有旧页面。

5. 我的选择会结合组件复杂度、团队约定和测试基础。新增复杂功能倾向组合式，维护稳定的小组件可以延续选项式；迁移时先按行为梳理初始化和清理，验证原有交互，再提取复用部分，避免只把生命周期机械搬进一个很长的 setup 而没有改善组织。

## 追问：composable 比 mixin 更容易看懂，具体体现在哪里？

1. mixin 可能向组件注入同名属性和方法，阅读组件时不容易知道某个字段来自哪里，多个 mixin 还可能产生冲突。composable 在调用处显式导入并接收返回值，来源和命名由调用方掌握，依赖关系更直接。

2. 两个 composable 返回相同字段名时，可以在解构时重命名或保留结果对象，不必依靠合并规则猜最终使用哪一个。它们也能组合普通参数与 ref，使一个行为依赖另一个行为时，用函数调用表达而不是隐式读取组件 this。

3. 但共享状态、监听清理和异步依赖仍需设计，composable 并不会自动避免所有耦合。我会保持每个函数职责具体，避免通过模块单例偷偷共享数据，否则只是换一种形式重新制造不透明来源。

## 追问：把旧组件迁到 Composition API，应该先改什么？

1. 我会先按业务行为列出相关数据、触发条件和资源，而不是逐个选项转换。例如用户编号决定详情请求，窗口变化决定图表尺寸，表单草稿决定校验，这些关系比原来代码属于 methods 还是 watch 更重要。

2. 再把各行为的状态、监听和清理放在一起，保留外部 props、事件和展示结果。纯派生值使用 computed，外部资源在正确生命周期管理，先让行为等价，再决定是否提取 composable，避免迁移和重新设计同时大幅展开。

3. 验证应覆盖首次加载、参数变化、失败和卸载，不只检查页面能打开。迁移后若只是代码更短而清理遗漏或草稿重置错误，就不能算完成；逐个功能稳定下来，通常比一次改变全部结构更容易定位问题。
