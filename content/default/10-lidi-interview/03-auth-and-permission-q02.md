# Token 过期了怎么办？

## 核心回答

1. 轻购当前采用登录失效后重新登录，没有实现刷新 Token。Axios 响应层会检查 HTTP 401 和业务码 A00004，因为有的接口用 HTTP 状态表达失效，有的把失效放在业务响应中，只看一种会漏掉另一种。

2. 确认失效后先 removeToken，避免后续请求继续携带旧凭据，然后跳到登录页。不能只改页面地址不清理存储，否则守卫还会以为有 Token，新的接口也可能继续失败，用户容易在几个页面之间来回跳转。

3. 跳转前记录当前路径、查询参数和 hash 作为 redirect，登录后可以回原位置。已有 Token 也可能过期，所以守卫的存在检查只是提前引导，服务端的失效响应才是这次请求能否继续使用凭据的依据。

4. 多个并行接口可能同时失效，redirectingToLogin 会减少重复跳转，已经在登录或注册页时也不重复跳。这里需要注意状态恢复与错误传播，不能为了只跳一次，把页面所有业务 Promise 都留在未结束状态。

5. 如果后端以后提供刷新接口，我才会设计一个共享刷新任务，让其他请求等待同一结果。刷新失败仍要退出，订单创建等请求能否重放要单独约定；不能把“重新拿 Token”直接等同于所有写请求都可以安全自动重试。

## 追问：三个接口一起返回 401，会有什么问题？

1. 如果每个请求都独立 push 登录页，可能产生多条历史记录、重复 Toast，甚至后来的跳转把 redirect 改成登录页本身。用户再次登录时就丢了原目标，所以登录失效应当作为一次统一动作处理。

2. 当前使用跳转标记避免多次处理，我会同时检查它在登录完成后是否合理恢复。标记不能永远保持真，否则下一次凭据失效可能被忽略；也不能提前恢复导致同一批迟到的 401 又触发退出。

3. 如果继续完善，还要让旧账号请求绑定登录版本，避免新登录成功后，上一轮请求的 401 又清掉新 Token。验证时应故意延迟旧响应，不能只测所有接口几乎同时失败的简单情况。

## 追问：为什么刷新 Token 不能直接写在每个失败请求里？

1. 多个请求同时失效时，每个都刷新会产生多次竞争，后端若轮换刷新凭据，还可能让后到的刷新变成无效。应共享同一个刷新 Promise，其他请求等待结果，而不是各自处理一份登录状态。

2. 需要限制每个原请求最多因刷新重试一次，并排除刷新接口本身，否则刷新失败再次触发刷新，会形成无限循环。成功后也要使用新凭据重建请求，失败则统一清理身份并提示重新登录。

3. 这只是未来有后端协议时的设计。尤其提交订单和支付，原请求可能已经执行，需要幂等或结果查询支持；轻购目前失效后重新登录；要增加自动刷新，还需要先把刷新有效期、失败退出和请求重试的约定确定下来。
