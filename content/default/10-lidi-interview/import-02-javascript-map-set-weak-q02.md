# 用对象去重有什么坑？

## 核心回答

1. 用普通对象当去重表，要先确认按什么判断相同。对象的属性键只能是字符串或 Symbol，其他值当键会发生转换。数字 `1` 和字符串 `"1"` 可能落到同一个位置，这和业务是不是把它们当成同一个编号，不一定一致。

2. 直接把两个普通对象当属性键，它们通常都会变成同样的字符串，内容完全不同也会覆盖。反过来，Set 保存对象时比的是引用身份，两个分别创建、字段相同的对象仍是两项，也不会自动按内容去重。

3. 普通对象还带着原型链。用 `in` 或直接判断属性真假，可能把继承属性当成已经存在。比如输入恰好是 `toString` 就可能误判。用无原型对象、查自有属性能避开这类干扰，但键转换规则不会因此改变。

4. 给商品列表按编号去重，要先约定编号是否必填、数字和字符串要不要统一、重复时留哪条。用 Map 保存编号到商品的映射比较清楚。缺编号要单独处理，不然多条不完整记录会被意外合成一条。

5. 顺序也要讲清楚。重复写入已有键会更新值，但不会把键挪到末尾。「保留最后一条内容」和「按最后出现位置排序」是两件事。用重复编号穿插出现的小样例对一下，免得去重结果对了、展示顺序却错了。

## 追问：怎样实现保留最后一条并按最后出现位置排序？

1. 连续调用 Map 的 `set`，重复编号对应的内容会被替换，位置仍是这个编号第一次插入的位置。比如编号依次是甲、乙、甲，最终内容来自最后一个甲，遍历顺序却还是甲、乙。

2. 要求按最后出现位置排，可以每次写入前先删掉已有编号，再重新插入。例子里就会得到乙、甲，因为重新插入建立了新顺序。这是明确选的业务规则，不是所有去重都该这么做。

3. 处理前还要定无效编号怎么处理，并且别直接改输入数组。页面要留原始列表做撤销，就返回新的结果数组。里面的商品对象仍可能共享引用，去重本身不保证复制所有嵌套内容。

## 追问：为什么不直接用 JSON.stringify 判断两个对象相同？

1. 序列化结果不等于业务上的对象相等。两个对象字段相同、创建时属性顺序不同，可能得到不同字符串。有些值序列化时还会被省略或转换，看起来一样或不一样，都不一定对应业务上的同一条数据。

2. 还有覆盖不了的输入。循环引用会抛错，默认处理 BigInt 也可能失败。待比较对象里有方法、日期或缺失字段，就要逐项约定语义。简单示例能工作，不代表任意对象都能这样去重。

3. 记录有稳定编号，优先按编号比。真要按几个字段判重，先把这些字段标准化，再拼成没有歧义的组合键。只有需求明确要求结构比较时，才上专门的比较逻辑，并补上字段顺序和特殊值的验证样例。
