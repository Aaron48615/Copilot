# 用对象去重有什么坑？

## 核心回答

1. 用普通对象当去重表时，我首先会确认究竟按什么判断相同。对象的属性键只能是字符串或 Symbol，其他值作为键会发生转换，所以数字一和字符串一可能落到同一个位置，这与业务是否把它们看成同一个编号未必一致。

2. 如果直接把两个普通对象作为属性键，它们通常都会变成同样的字符串，内容完全不同也会覆盖。反过来，Set 保存对象时比较的是引用身份，两个分别创建但字段相同的对象仍是两项，也不会自动实现按内容去重。

3. 普通对象还带有原型链，使用 `in` 或直接判断属性真假可能把继承属性误认为已经存在。例如输入恰好是 `toString` 时就可能误判；用无原型对象和自有属性检查能避开这类干扰，但仍不会改变键转换规则。

4. 假设要给商品列表按编号去重，我会先约定编号是否必填、数字和字符串是否统一，以及重复时保留哪条。用 Map 保存编号到商品的映射比较清楚，缺失编号应单独处理，否则多条不完整记录会被意外合并成一条。

5. 顺序也需要明确，重复写入已有键会更新值，但不会把键移动到末尾。因此“保留最后一条内容”和“按最后出现位置排序”是两个要求；我会用重复编号穿插出现的小样例确认预期，避免去重结果正确却展示顺序错误。

## 追问：怎样实现保留最后一条并按最后出现位置排序？

1. 如果直接连续调用 Map 的 `set`，重复编号对应的内容会被替换，但位置仍是这个编号第一次插入的位置。比如编号依次为甲、乙、甲，最终内容虽来自最后一个甲，遍历顺序却仍然是甲、乙。

2. 若要求结果按最后出现位置排列，可以在每次写入前先删除已有编号，再重新插入。这样例子中会得到乙、甲，因为重新插入建立了新的顺序；这是明确选择的业务规则，不是所有去重场景都应采用的默认行为。

3. 我还会在处理前确定无效编号的策略，并且不直接修改输入数组。假设页面需要保留原始列表用于撤销，就返回新的结果数组，同时说明里面的商品对象仍可能共享引用，去重本身不承诺复制所有嵌套内容。

## 追问：为什么不直接用 JSON.stringify 判断两个对象相同？

1. 序列化结果不等于业务定义的对象相等。两个对象字段相同但创建时的属性顺序不同，可能得到不同字符串；某些值在序列化时还会被省略或转换，因此看起来一样或不一样，都未必对应业务上的同一条数据。

2. 它还存在无法直接覆盖的输入，例如循环引用会抛错，默认处理 BigInt 也可能失败。假设待比较对象里包含方法、日期或缺失字段，就要逐项约定语义，不能因为简单示例能工作，就认为任意对象都可以这样去重。

3. 如果记录有稳定编号，我会优先按编号比较；如果确实按几个字段判重，就先标准化这些字段并构造无歧义的组合键。只有需求明确要求结构比较时，才考虑专门的比较逻辑，同时补上字段顺序和特殊值的验证样例。
