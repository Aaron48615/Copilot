# Webpack 热更新（HMR）的原理？

## 核心回答

1. HMR 是在开发时替换发生变化的模块，尽量保留当前页面状态，区别于整页刷新。保存文件后，Webpack 重新编译受影响部分，开发服务器通知浏览器有更新，浏览器的热更新运行时再获取并应用对应的新内容。

2. 通知通常经过开发服务器与浏览器之间的连接，Webpack 热更新运行时会请求更新清单及变化模块。它不是服务器把整个源码目录不断重新发送，也不表示每次只变化一个模块，依赖关系可能让多个模块一起受到影响。

3. 应用更新时要找到能够接受更新的边界。模块或父模块通过相应接口处理替换，框架工具也会参与保存与恢复状态；若没有合适边界或更新无法安全应用，开发环境可能回退到整页刷新，具体由配置和集成决定。

4. 旧模块被替换前还要清理它注册的副作用，例如事件、计时器和外部实例。HMR 不保证任意业务状态都保留，修改组件结构或模块接口可能要求重新初始化，不能把表单偶尔保留就概括为永远不丢状态。

5. 我会用连续修改验证更新效果，检查事件是否重复、页面状态是否合理，以及错误恢复是否正常。Vite 也提供热更新，但其模块服务和更新方式不同；理解共同目标有帮助，不能把 Webpack 的更新文件机制原样套到所有工具上。

## 追问：热更新几次后点击触发多次，通常查什么？

1. 我会先检查模块顶层是否注册了事件、定时器或订阅，每次更新时新模块重新执行，旧副作用却没有清理。这样代码只看到一个监听声明，页面里实际上已累积多份回调，点击一次就会执行多次。

2. 应在模块替换的清理阶段取消旧监听或销毁实例，并使用稳定的引用完成解绑。把匿名函数重新写一遍不等于原回调，无法正确移除；需要保留的状态也应与必须释放的外部资源分别管理。

3. 验证时连续更新多次，再看监听次数、网络请求和内存是否增长。整页刷新后恢复正常只能说明累积状态被清掉，并不是根因修复，不能把开发者每次手动刷新当作解决热更新副作用的办法。

## 追问：HMR 为什么有时会变成整页刷新？

1. 变化可能传到没有接受更新能力的入口，或者模块导出和运行时状态已不适合原地替换。开发工具选择刷新是为了恢复一致状态，而不是每次出现刷新就说明 HMR 连接断了，需要结合控制台原因判断。

2. 我会区分连接通知失败、编译错误和更新边界不支持，分别看开发服务器日志与浏览器运行时信息。修改构建配置或环境变量也可能需要重启，不能期待所有项目设置都像改一行 CSS 一样即时替换。

3. 如果是可支持的业务模块，可以检查 accept 和清理逻辑，或采用框架官方集成。不要为了强行保留页面状态而无条件接受所有更新，否则代码虽然不刷新，界面却可能混用不兼容的新旧状态，调试更困难。
