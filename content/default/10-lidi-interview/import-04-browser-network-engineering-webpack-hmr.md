# Webpack 热更新（HMR）的原理？

## 核心回答

1. HMR 是开发时替换发生变化的模块，尽量留住当前页面状态，跟整页刷新不一样。保存文件后，Webpack 重新编译受影响的部分，开发服务器通知浏览器有更新，浏览器里的热更新运行时再获取并应用对应的新内容。

2. 通知通常走开发服务器和浏览器之间的连接。Webpack 热更新运行时会请求更新清单和变化模块。不是服务器把整个源码目录不断重新发送，也不表示每次只变一个模块。依赖关系可能让多个模块一起受影响。

3. 应用更新时要找到能接受更新的边界。模块或父模块通过相应接口处理替换，框架工具也会参与保存和恢复状态。没有合适边界，或更新没法安全应用，开发环境可能退回整页刷新。具体由配置和集成决定。

4. 旧模块被替换前，它注册过的副作用要清掉，比如事件、计时器、外部实例。HMR 不保证任意业务状态都保留。改了组件结构或模块接口，可能需要重新初始化。表单偶尔还在，概括不成永远不丢状态。

5. 连续修改看更新效果，检查事件会不会重复、页面状态合不合理、错误恢复正不正常。Vite 也提供热更新，但模块服务和更新方式不同。共同目标可以对照，Webpack 那套更新文件机制不能原样套到所有工具上。

## 追问：热更新几次后点击触发多次，通常查什么？

1. 模块顶层是不是注册了事件、定时器或订阅。每次更新新模块重新执行，旧副作用却没清理。代码里只看到一个监听声明，页面里实际已经攒了多份回调，点一次就会执行多次。

2. 在模块替换的清理阶段取消旧监听或销毁实例，用稳定的引用完成解绑。把匿名函数重新写一遍，不等于原来那个回调，没法正确移除。需要保留的状态，和必须释放的外部资源，分开管。

3. 连续更新多次，再看监听次数、网络请求、内存有没有涨。整页刷新后恢复正常，只能说明累积状态被清掉了，不是根因修了。开发时每次手动刷新，当不了解决热更新副作用的办法。

## 追问：HMR 为什么有时会变成整页刷新？

1. 变化可能传到没有接受更新能力的入口，或者模块导出和运行时状态已经不适合原地替换。开发工具选择刷新，是为了恢复一致状态。每次出现刷新就说 HMR 连接断了，不一定对，结合控制台原因看。

2. 分清是连接通知失败、编译错误，还是更新边界不支持。开发服务器日志和浏览器运行时信息两边都看。改构建配置或环境变量，也可能需要重启。不是所有项目设置都能像改一行 CSS 一样即时替换。

3. 如果是可支持的业务模块，检查 `accept` 和清理逻辑，或采用框架官方集成。为了强行留住页面状态而无条件接受所有更新，代码虽然不刷新，界面却可能混用不兼容的新旧状态，调试更难。
