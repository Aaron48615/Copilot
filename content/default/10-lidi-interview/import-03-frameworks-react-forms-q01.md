# 校验应该什么时候发生？

## 核心回答

1. 校验什么时候做，看这时提示对用户有没有帮助。必填、邮箱格式，一般失焦或提交时再说；刚敲一个字符就「邮箱错误」，填写会被打断。密码强度这种边敲边有参考的，可以跟着变。

2. 值和「有没有进过这个字段」「有没有点过提交」、错误文案是分开的。没碰过的字段先别标红；提交之后，该改的都要露出来。已经出错的字段用户又改了，可以马上再验一遍，别让红字一直挂着不消失。

3. 用户名有没有被占用这种远程校验，要控制次数，也要防旧结果盖新输入。本地格式先过了再防抖去查，提交时再确认这轮检查的状态。上一个用户名可用，不能当成现在这个也可用。

4. 前端校验是早点拦住明显错误，服务端照样要完整验。提交过程中显示忙碌，挡住连点；失败了输入留着。字段错误放字段旁边，整表的错误放表单区域，焦点能落到第一个出错的地方。

5. 规则还要跟字段用途对上。密码里的空格可能是有效的，别一律把头尾空白砍掉。结束日期不能早于开始日期这种跨字段规则，任一头变了都要更新错误，单验一个框会漏。

## 追问：用户刚改了用户名，之前的“可用”提示还能保留吗？

1. 不该再当成当前结论。可用不可用是针对那一个输入的。字一改，远程检查就变成未确认或等待。旧结果可以当缓存，但得按用户名分开存，别只有一个全局 `valid` 布尔值。

2. 先做本地格式校验，不合格就不发请求，过了再防抖。请求带上这次输入或一个编号，回来时看当前字段还是不是它。打字很快时，才不会被上一趟结果带偏。

3. 最终提交还是服务端原子地查唯一性。检查通过到按下提交之间，名字可能已经被别人占用。撞了就在用户名字段说明，其他已经填好的留着，别整张表清空让人重填。

## 追问：只有红色边框，为什么不算完整的错误反馈？

1. 红色只说可能有问题，没说怎么改，只靠颜色认的人也看不出。文字写具体一点，比如「请输入包含 @ 的邮箱地址」，别一句「格式错误」完事。

2. 输入框要有能认出来的 label，错误说明用 `aria-describedby` 挂上，出错时设 `aria-invalid`。提交失败后焦点挪到第一个错误字段或错误摘要，键盘用户也知道下一步去哪。

3. 提示时机也要收。每敲一个字就抢焦点、播报全部错误，操作会被打乱。字段错误跟着改正更新；提交失败这种明确节点再集中说一遍。已经填对的内容留着。
