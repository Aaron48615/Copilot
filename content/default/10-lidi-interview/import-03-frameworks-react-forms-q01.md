# 校验应该什么时候发生？

## 核心回答

1. 校验时机要看反馈是否对用户有帮助。必填和邮箱格式通常在失焦或提交时提示，用户刚输入一个字符就显示“邮箱错误”会打断填写；密码强度这种边输入边有参考价值的内容，可以即时反馈。

2. 我会区分值、是否访问过字段、是否尝试提交和错误信息。未触碰的字段通常不立即标红，提交后应显示所有需要修正的问题；用户修改已经出错的字段时，可以及时重新校验，避免错误提示一直不消失。

3. 用户名是否被占用等远程校验需要控制请求次数，也要防止旧结果覆盖新输入。可以在本地格式通过后防抖请求，提交时再确认相关检查状态；不能把上一个用户名校验成功当成当前输入也有效。

4. 前端校验主要帮助用户尽早纠错，服务端仍要执行完整校验。提交期间显示忙碌并防止重复点击，失败后保留输入；字段错误放在字段旁，全局错误放在表单区域，并让焦点能定位到第一个错误位置。

5. 校验规则还应与字段用途一致，例如密码中的空格可能有效，不能统一去掉所有首尾空白。多个字段相关时，例如结束日期不得早于开始日期，需要在任一相关值变化后更新错误，避免只检查单个输入框而遗漏整体约束。

## 追问：用户刚改了用户名，之前的“可用”提示还能保留吗？

1. 不应该继续把它当作当前结论。可用性属于特定输入值，输入改变时就应将远程检查设为未确认或等待状态；可以保留旧结果作为缓存，但必须按用户名区分，不能只有一个全局 valid 布尔值。

2. 我会先做本地格式校验，格式不合格就不发请求，通过后再防抖。请求带上本次输入或编号，返回时检查当前字段是否仍对应它，快速连续输入时才不会被旧结果误导。

3. 最终提交仍由服务端原子地检查唯一性，因为检查通过到点击提交之间，名称可能已被别人使用。遇到冲突应在用户名字段展示明确说明并保留其他输入，而不是清空整张表让用户重填。

## 追问：只有红色边框，为什么不算完整的错误反馈？

1. 红色只能告诉用户可能有问题，不能解释怎么改，也不适合只依赖颜色识别的使用方式。我会给出具体文字，例如“请输入包含 @ 的邮箱地址”，而不是笼统写一个“格式错误”。

2. 输入框需要可识别的 label，错误说明可通过 aria-describedby 关联，出错时设置 aria-invalid。提交失败后把焦点移到第一个错误字段或错误摘要，键盘用户也能知道下一步该去哪里处理。

3. 提示时机也要控制。每输入一个字就强制移动焦点或播报全部错误会干扰操作；通常让字段错误随修正更新，在提交失败这种明确节点集中反馈，并保留用户已经正确填写的内容。
