# `v-for` 的 `key` 为什么重要？

## 核心回答

1. `key` 用来帮助 Vue 识别同级列表节点的身份，使更新时能判断某个旧节点应该复用、移动还是移除。它影响的是数据项与 DOM、组件实例之间的对应关系，不只是为了消除控制台提示，也不是加了就必然更快。

2. 比如列表原来是甲、乙，给第一行输入框填写内容后在前面插入丙，如果按下标作 key，原第一行节点仍可能作为新第一行复用。显示数据变成丙，但原来属于甲的临时输入或子组件内部状态就可能跟错对象。

3. 我会优先使用稳定的业务 ID，例如商品 ID 或工单 ID，而且要在同一组兄弟节点里唯一。ID 不能因为排序或重新请求就改变，也不能在每次渲染时临时生成随机数，否则 Vue 很难复用原有节点。

4. 如果后端没有 ID，前端新建记录时可以生成一次本地标识并随记录保存，而不是每次渲染重新生成。组合字段作 key 时要确认组合确实唯一，不拿会重复的姓名或可能被编辑的标题充当稳定身份。

5. 对完全静态、没有内部状态的简单列表，下标的风险较小，但只要可能插入、删除或排序，就需要重新评估。在 Vue 3 的 `<template v-for>` 中应把 key 放在 template 上，不能只给其中一个子节点加 key 就认为标识了整组。

## 追问：为什么每次渲染都生成随机 key 反而可能更慢？

1. 随机 key 让同一条业务记录在下一次渲染时看起来像全新的节点。Vue 无法按原 key 找到可复用的实例，就可能卸载旧实例再创建新实例，增加初始化和清理开销，具体性能仍需测量。

2. 这种重建还可能丢失输入框焦点、未提交的本地状态，以及子组件内部正在进行的操作。如果组件在挂载时发请求，重建也可能让这些请求重复发生，问题不只是节点移动次数变多。

3. 需要强制重置某个表单时，主动改变特定组件的 key 可以是有意设计，但应该对应明确的重置时机。普通列表刷新应让同一记录保留相同 key，不用随机数制造“每次都是新组件”的效果。

## 追问：用了唯一 ID 后，列表状态就一定不会错吗？

1. 唯一 ID 解决节点身份识别，但数据更新本身也要正确。例如原地修改一个数组时用了错误下标，或者旧请求覆盖了新列表，key 不会替代码判断业务数据是否有效，仍需要检查修改和请求逻辑。

2. 还要核对 ID 的唯一范围，同一个列表混合两种实体时，它们都可能有 ID 一，可以加稳定的类型前缀区分。如果一条业务记录在列表中需要展示多份，也应按实际展示实例定义身份，不能照搬重复 ID。

3. 子组件如果只在初始化时把 prop 复制进本地状态，后续同一 ID 的新数据也不一定同步到这份副本。此时要明确组件是实时展示还是独立编辑草稿，并调整同步策略，不能靠不断改 key 来掩盖状态设计问题。
