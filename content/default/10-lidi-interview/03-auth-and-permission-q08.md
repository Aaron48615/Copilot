# 轻购为什么把轻购AI放进路由白名单？

## 核心回答

1. 当前轻购路由白名单包含 `/login`、`/register` 和 `/guide`。登录注册是身份入口，导购页允许用户先输入需求体验推荐，所以没有 Token 时也能进入，这是当前产品入口的选择。

2. 搜索、商品详情、购物车、地址和订单等页面目前不在白名单。所以匿名用户点开推荐商品后仍可能进入登录页；商品浏览也可以设计为公开，但需要同时拆开详情里的个人收藏等受保护请求。

3. 前端允许进入 guide，并不意味着 `/guide/recommend` 可以无限匿名调用。服务端还需要决定是否允许匿名请求、输入范围和频率上限，尤其模型调用有成本，路由白名单本身不能保护接口额度。

4. 用户从公开推荐点进商品详情时，可能再次被守卫引导登录，登录后通过 redirect 回到目标商品。这个交界处需要说明和验证，不能只测匿名导购能出卡片，就认为整段浏览购买流程都是匿名可用。

5. 如果以后导购要读取收藏、订单或个性化优惠，我会把需要用户数据的部分单独鉴权，或者调整整个入口要求。公开的普通推荐与个人数据推荐不是同一权限范围，不能为了体验方便让匿名请求带任意用户 ID 查询。

## 追问：白名单里的页面能否调用需要登录的接口？

1. 页面公开与某个接口是否公开是两件事。公开导购可以展示通用推荐，但如果同时请求个人收藏，服务端仍应要求有效身份；没有登录时，页面应跳过该请求或展示可登录后使用的入口。

2. 如果不区分，匿名进入公开页就可能立刻收到 401，再被统一拦截器跳走，白名单实际上失去了体验意义。设计时要明确哪些请求匿名执行，哪些依赖会话，而不能只改路由数组就结束。

3. 验证时我会在无 Token、有效 Token 和过期 Token 三种状态下进入 guide，观察请求与跳转。尤其过期凭据不能让公开基础功能陷入重复登录，也不能为了避免跳转而忽略真正的个人数据权限。

## 追问：你会把商品详情也改成公开吗？

1. 从一般购物体验看，先看商品再登录购买通常更顺畅，但这是产品取舍，不是必须照搬的结论。我会先看详情接口是否混合了收藏等个人信息，以及当前项目对匿名访问的后端支持。

2. 如果继续改，可以把公开商品数据与需要登录的收藏状态分开，浏览时只加载可公开内容，加购或查看个人状态时再引导登录。仅把详情路径加入白名单而不调整请求，仍可能因为收藏接口 401 被跳走。

3. 还要验证登录后能保留商品与已选规格的合理上下文，并重新确认库存。如果决定调整当前白名单，前端入口改变需要和接口权限、加载方式一起评估。
