# HTTP/3 为什么用 UDP 还能可靠？

## 核心回答

1. HTTP/3 使用 QUIC，QUIC 运行在 UDP 之上，但可靠性由 QUIC 自己实现。UDP 只负责尽力传递数据报，不提供 TCP 那套确认和重传；不能据此推断建立在它之上的协议也一定是不可靠传输。

2. QUIC 有包编号、确认、丢失检测、拥塞控制和流量控制等机制。发现丢失时会按协议重新传输需要的数据，不是简单把同一个编号的数据包原样再发，因此我会把数据可靠交付与底层数据报是否重发区分开。

3. HTTP 请求和响应通常使用可靠的 QUIC 流，每条流维护自己的字节顺序。某条流缺少数据时，不要求已经完整到达的其他流也等待补齐，减少了 TCP 连接上多个 HTTP/2 流一起被阻塞的问题。

4. 但独立流并不表示完全互不影响，它们仍共享网络带宽和连接级拥塞控制。同一条流内部仍要按序交付，握手和实现资源也会影响性能；HTTP/3 不能保证在任何网络下都比 HTTP/2 更快。

5. QUIC 还结合 TLS 1.3，并利用连接标识支持符合条件的网络路径迁移。如果网络限制 UDP，客户端可能需要回退到其他协议；前端应观察实际协商结果，而不是仅因为服务器宣称支持 HTTP/3 就假设所有用户都在使用。

## 追问：QUIC 消除了所有队头阻塞吗？

1. 没有，它主要避免把不同应用流都绑在一条 TCP 有序字节流上的等待。若某条 QUIC 流缺少前面的字节，这条流自己的有序读取仍需要等待，不能在文件中间缺一段时直接当成完整内容交给应用。

2. 多个流还共享拥塞控制，发生网络丢包可能使发送速率下降，从而影响整个连接。HTTP/3 头部压缩也有自身依赖处理，所以不能把流之间减少阻塞概括成各个请求从此完全独立、永远不相互影响。

3. 我会在回答里明确比较对象是 TCP 层跨流等待，再结合实际网络验证收益。若首屏慢在服务器生成 HTML 或 JavaScript 执行，消除传输层等待也不会自动把这些应用层瓶颈修好。

## 追问：手机从 Wi-Fi 切到移动网络，QUIC 为什么可能更容易保持连接？

1. 传统 TCP 连接通常由地址和端口等信息识别，网络切换可能改变这些信息。QUIC 使用连接标识协助识别同一连接，所以在协议和服务端支持的条件下，可以在新的路径上继续通信，而不必完全按旧方式重建。

2. 迁移并不是直接相信任何新地址，需要验证新路径，并受到部署、客户端策略及 NAT 行为等限制。若网络禁止 UDP 或切换中断很久，连接仍可能失败，所以不能承诺手机切网一定没有断线。

3. 应用层仍要处理重连和重复请求，例如实时消息通过事件标识恢复进度。QUIC 能改善传输条件，但不能代替业务的恢复逻辑；测试时应真实切换网络，而不只依赖开发工具的离线开关模拟。
