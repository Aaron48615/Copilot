# tsconfig 里的 strict 对项目有什么影响？

## 核心回答

1. 我理解 strict 是一组严格类型检查的总开关，主要让代码把原来靠默认假设的条件写清楚。例如参数类型推断不出来、查询结果可能为空、类属性没有初始化，都会更容易在开发阶段暴露，避免等页面运行到那一步才发现问题。

2. 比较常见的是严格空值检查和禁止隐式任意类型，但后者并不禁止所有 any。例如没有上下文可推断的函数参数需要补类型，已经能从数组推断出来的回调参数就不用重复声明，重点是保留检查能力而不是到处写注解。

3. 对可能查不到的用户，我会把结果写成用户对象与空值的联合，并在使用前处理未找到的分支。如果只是补一个非空断言，虽然红线消失了，运行时条件并没有改变，严格模式也就没有真正帮助我发现遗漏。

4. strict 不等于所有检查都打开，数组下标可能越界需要单独考虑 noUncheckedIndexedAccess。它也不能验证服务器返回值或权限是否正确，所以接口入口的运行时检查和真实业务分支仍然要保留，不能拿编译通过代替验证。

5. 假如接手旧项目，我会先按参数、空值和第三方声明分类处理错误，再逐步收紧边界。升级编译器时也会重新执行类型检查，因为 strict 可能随版本增加检查项，迁移成本要结合实际报错评估，不能承诺打开后立刻全部修好。

## 追问：旧项目一开 strict 就大量报错，先修哪些地方？

1. 我会先找被很多页面共用的请求返回类型和工具函数参数，因为这些边界写错会引出一串下游提示。例如返回值实际允许为空，却声明成一定存在，先修源头能让后面的判断有统一依据，避免每个组件各猜一遍。

2. 接着区分真实缺失分支和声明不准确，真实缺失需要补运行逻辑，旧库声明问题可以集中适配。如果只是批量添加断言或把参数改成任意类型，报错数量会下降，但最初希望发现的问题也会被一起遮住。

3. 如果必须分阶段推进，我会明确暂时关闭的子选项、影响范围和恢复条件，并对已修正的路径做验证。不能只看编辑器红线清空，还要确认构建实际检查了对应文件，否则遗漏的目录可能一直没有参与检查。

## 追问：构建成功为什么仍可能存在 TypeScript 类型错误？

1. 有些构建流程只移除类型语法并打包，并没有执行完整的类型检查，因此生成产物成功不代表类型关系正确。我会先看构建脚本和工具配置，确认是否真正运行了编译器检查，不会仅凭命令名称判断它做了什么。

2. 可以把独立的类型检查作为验证步骤，例如执行项目约定的无产物检查命令，再核对配置覆盖的文件范围。如果测试代码或某个子目录被排除了，主应用检查通过也不能说明那些文件没有问题，检查范围需要单独确认。

3. 即便静态检查完整通过，接口结构变化、用户输入不合法和状态竞争仍可能导致运行错误。我会继续验证关键页面行为，把类型检查用来发现结构问题，把运行验证用来确认真实数据和流程，两种证据各有作用。
