# HashRouter 和 BrowserRouter 有什么区别？

## 核心回答

1. HashRouter 把前端路由放在 URL 的片段部分，例如 `/#/products`，片段不会随 HTTP 请求发送给服务器。BrowserRouter 使用浏览器 History API，地址可以直接写成 `/products`，二者都能在站内导航时更新页面而不做整页刷新。

2. 最大的实际区别在直接访问和刷新。BrowserRouter 页面刷新时，服务器会收到 `/products` 请求，需要能够返回应用入口或相应服务端内容；只存在 index.html 的静态部署如果没有配置回退，深层地址就可能返回不存在。

3. 回退规则应只覆盖前端页面路径，不能把接口、脚本和图片请求都返回 HTML。否则资源明明找不到，状态码却是成功，浏览器还可能报脚本 MIME 或解析错误，排查时更难发现真正缺失的文件。

4. HashRouter 对不能修改服务器路由的静态环境比较方便，但地址片段也有自己的使用限制。BrowserRouter 地址更直观，不代表自动获得 SEO；搜索可见性还和真实内容、服务端渲染、元数据及响应状态有关，不能只用 URL 外观判断。

5. 我会根据部署环境和既有路径选型，并验证直接进入详情、刷新、前进后退和子目录部署。使用 basename 等配置时还要与资源基础路径一致，这些测试比只确认首页能通过链接跳到列表更能说明路由部署是否完整。

## 追问：站内点击正常，刷新却 404，应该先查哪里？

1. 先看网络面板中的文档请求。站内点击可能已经由客户端路由处理，刷新则真的请求服务器的深层路径，因此首页正常不能证明服务器认识所有前端地址，问题通常先从托管回退配置排查。

2. 我会确认应用部署在根目录还是子目录，以及服务器返回的是入口 HTML 还是真正的错误页。入口正常但脚本路径不对也会白屏，需要一起检查资源地址，不能只增加一条回退规则就结束验证。

3. 最后验证真实不存在的前端路径和接口路径。应用内部需要自己的未找到页面，接口错误仍应返回接口应有的状态和格式；若所有请求都落到入口，表面上没有 404，实际却掩盖了更多部署错误。

## 追问：pushState 会自动触发 popstate 吗？

1. 直接调用 pushState 或 replaceState 不会因为这次调用本身触发 popstate，浏览器前进后退等历史遍历才会涉及该事件。路由库会自己协调程序化导航后的状态更新，不只是注册一个事件监听就完成全部工作。

2. 因此业务代码通常使用路由库提供的导航 API，而不是随意修改 history 后期待组件自动同步。否则地址变了，路由上下文可能没有按预期更新，界面和 URL 出现不同步，返回操作也更难维护。

3. 我还会区分 push 和 replace：前者新增历史记录，后者替换当前记录。登录跳回、纠正无效参数等场景可能更适合 replace，避免用户按返回键又回到刚被重定向的中间页。
