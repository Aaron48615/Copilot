# ETag、Last-Modified 和 stale-while-revalidate 怎么配合？

## 核心回答

1. 我把这几个机制分成新鲜期和更新验证来理解。Cache-Control 的 max-age 决定资源多久可以直接复用；缓存仍新鲜时通常不发请求，所以 ETag 和 Last-Modified 并不是每次访问都会拿去服务端比较。

2. 需要验证时，客户端可以携带 If-None-Match 对应 ETag，或 If-Modified-Since 对应修改时间。服务端判断表示没变化就返回 304，让客户端使用已有响应体；有变化则返回新内容，并更新验证信息。

3. ETag 是资源表示的验证标识，不要求一定是文件 hash；Last-Modified 是时间，精度和更新时间可靠性可能有限。两种条件同时出现时，If-None-Match 优先，服务端不能只看日期就忽略更准确的验证条件。

4. stale-while-revalidate 允许在指定的过期窗口内先使用旧响应，同时后台更新，适合能容忍短暂旧内容的公开列表。它不保证永远都有缓存，也不适合所有余额、权限数据；我会为入口、静态文件和私有接口分别选择策略。

5. 比如公开文章列表可以允许短时间展示旧顺序，后台更新后供下一次访问使用；提交修改后的详情则可能要求立即重新验证。我会把可容忍的陈旧时间写成业务规则，再选择指令，避免用户刚保存成功却因旧缓存以为内容没有保存。

## 追问：no-cache 和 no-store 到底差在哪里？

1. no-cache 允许保存响应，但复用前要向服务端验证。比如 HTML 希望每次访问确认是否有新版本，可以使用它并配合 ETag，没变化时只返回 304，保留节省响应体传输的机会。

2. no-store 要求缓存不要存储本次请求或响应，适合不应落入 HTTP 缓存的敏感数据。它和清理历史缓存不同，后来加上这个头，不代表之前已存的内容会自动从所有浏览器或中间节点消失。

3. 我会用 Network 观察是否实际发起请求及响应状态，并排除 Service Worker 的单独缓存行为。不能只按选项名字猜效果，也不能把浏览器开发工具显示的缓存结果直接等同于 CDN 的缓存策略，需要分别核对每层配置。

## 追问：304 没有响应体，页面的数据从哪里来？

1. 客户端已有上一份缓存响应体，这次请求只是询问它能否继续使用。服务端返回 304 后，缓存会按规则更新相关元信息并复用旧响应体，因此节省的是内容传输，并没有省掉这次网络往返。

2. 请求里的验证标识必须对应正在验证的资源表示，例如压缩、语言等变化需要正确处理。若服务端不同内容错误共用同一个 ETag，就可能确认了一份已经不适合当前请求的旧内容。

3. 我会同时检查请求条件头、响应头和缓存中的旧版本。若根本没有可用缓存体，却观察到异常的 304，就应检查代理或客户端的验证逻辑，不能在业务代码里简单把 304 当作空数组返回。
