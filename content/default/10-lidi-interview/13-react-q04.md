# 受控组件和非受控组件有什么区别？

## 核心回答

1. 受控和非受控，差在谁保存当前输入值。受控输入由 React 状态决定，文本框传 `value`，复选框传 `checked`，用户操作时通过 `onChange` 更新对应状态，下一次渲染再把新值画出来。输入框显示的内容和业务读到的状态就能对上。

2. 非受控输入由 DOM 保存用户输入。React 可以用 `defaultValue` 或 `defaultChecked` 设初始值。提交时通过 ref 或 FormData 读取，不必每敲一个字就把值同步到组件状态。

3. 输入会影响实时校验、提交按钮能不能点、或另一个字段，受控更容易把这些关系写出来。比如选了配送方式再显示不同表单项，相关值在状态里比较好判断。但这不等于非受控做不了校验。

4. 文本受控值通常初始化成空字符串，避免一开始是 `undefined`，接口回来后又变成字符串，控制模式就切了。`onChange` 里要及时把输入值同步上去。贵的计算和请求可以往后放，别把 `value` 更新本身一起防抖。

5. 文件输入一般由用户选择，读 `files` 拿文件，不能像普通文本框那样随便设本地文件路径。简单提交表单可以考虑非受控，复杂表单还可以借助表单库。看交互和性能需要选。

## 追问：defaultValue 变了，为什么输入框没有跟着变？

1. `defaultValue` 表达的是初始值，不是让当前输入一直跟着这个 prop。用户已经改过了，React 如果每次都用默认值盖 DOM，反而会把用户输入重置，所以不能把它当 `value` 用。默认值和当前值，设计表单时要分开。

2. 异步读取编辑详情，可以等数据到齐再挂载表单，或者从一开始就用受控状态。首次回填和后续刷新要分开，后台数据刷新时别直接盖掉正在编辑的内容。

3. 切换编辑对象时可以明确重置表单。有些情况改 `key` 会重新挂载，但焦点和其他局部状态也会丢。按用户允不允许丢草稿来决定重置行为，别把改 `key` 当成万能修复。

## 追问：受控输入一打字就卡，应该怎么处理？

1. 先判断是输入框本身的问题，还是状态放得太高，整页列表和图表跟着渲染。把输入状态放到合适的小组件，往往比把全部事件处理函数都缓存起来更直接。

2. 输入值要及时更新。搜索请求可以防抖，贵的结果区域可以晚一点再用筛选条件。两者分开以后，用户输入仍然跟手，不必等列表算完或接口回来才看见自己敲的字。

3. 再看每次输入是不是在重复排序大量数据、做复杂同步校验、或创建第三方实例。确认耗时点之后，再选缓存、分批计算或缩小渲染范围。一次卡顿，不等于所有受控表单都慢。
