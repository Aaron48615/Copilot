# 受控组件和非受控组件有什么区别？

## 核心回答

1. 受控和非受控的区别主要是谁保存当前输入值。受控输入由 React 状态决定，文本框传 value，复选框传 checked，用户操作时通过 onChange 更新对应状态，下一次渲染再把新值显示出来。这让输入框显示的内容与业务读取的状态保持一致。

2. 非受控输入由 DOM 保存用户输入，React 可以用 defaultValue 或 defaultChecked 设置初始值。提交时可以通过 ref 或 FormData 读取，不必每输入一个字符就把值同步到组件状态。

3. 如果输入会影响实时校验、提交按钮是否可用或另一个字段，我更容易用受控方式表达这些关系。比如选择配送方式后显示不同表单项，相关值在状态里比较方便判断，但不意味着非受控无法做校验。

4. 文本受控值通常初始化为空字符串，避免一开始是 undefined，接口返回后又变成字符串，造成控制模式切换。onChange 中也要及时同步输入值，昂贵计算和请求可以延后，不能把 value 更新本身一起防抖。

5. 文件输入一般由用户选择，读取 files 获取文件，不能像普通文本框那样随意设置本地文件路径。简单提交表单适合考虑非受控方式，复杂表单还可以借助表单库，选择依据是交互和性能需要。

## 追问：defaultValue 变了，为什么输入框没有跟着变？

1. defaultValue 表达的是初始值，不是让当前输入始终跟随这个 prop。用户已经编辑后，React 如果每次都用默认值覆盖 DOM，反而会把用户输入重置，因此不能把它当成 value 使用。默认值和当前值需要在设计表单时分清。

2. 如果是异步读取编辑详情，我会考虑数据到齐后再挂载表单，或者从一开始使用受控状态。需要区分首次回填与后续刷新，避免后台数据刷新时直接覆盖正在编辑的内容。

3. 切换编辑对象时可以明确重置表单，某些情况下改变 key 会重新挂载，但也会丢掉焦点及其他局部状态。我会按用户是否允许丢弃草稿决定重置行为，不能把改 key 当成通用修复。

## 追问：受控输入一打字就卡，应该怎么处理？

1. 我会先判断是输入框本身的问题，还是状态放得太高，导致整页列表和图表跟着渲染。把输入状态放到合适的小组件，往往比把全部事件处理函数缓存起来更直接。

2. 输入值需要及时更新，搜索请求可以防抖，昂贵结果区域可以考虑延迟使用筛选条件。两者分开以后，用户输入仍然跟手，不必等待列表计算或接口返回才看到自己输入的字符。

3. 我还会检查每次输入是否重复排序大量数据、进行复杂同步校验或创建第三方实例。确认耗时点后再选择缓存、分批计算或减少渲染范围，不能因为一次卡顿就认定所有受控表单都慢。
