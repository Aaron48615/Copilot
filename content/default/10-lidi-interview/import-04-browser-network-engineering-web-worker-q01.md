# Worker 怎么取消？

## 核心回答

1. Worker 取消要区分立即终止和协作停止。页面调用 terminate 可以直接结束对应 Worker，适合一个 Worker 只处理一项独立计算的情况；它不会等待任务执行清理逻辑，因此资源和界面状态要由页面另外处理。

2. 如果希望复用 Worker，可以约定取消消息，但前提是 Worker 有机会处理消息。一个很长的同步循环占住它自己的事件循环时，取消消息也会排队，不会像中断信号一样立刻插进当前计算，这个边界很重要。

3. 协作方式通常把计算拆成批次，在批次之间让出执行并检查任务状态。使用可共享标记还涉及 SharedArrayBuffer 的环境要求和同步规则，不能为了取消一个普通解析任务就默认引入复杂共享内存方案。

4. 页面还要为每次任务加标识，取消或发起新任务后忽略旧结果。结果可能已经发出或正在排队，不能只依赖终止时机保证界面永不更新；进度通知和 finally 清理也应核对当前任务，防止干扰新一轮操作。

5. 我会分别验证立即取消、计算中取消和结果即将返回时取消。若是通过 transfer 转移了 buffer，终止 Worker 也不会自动把所有权还给页面，重试需要保留可重新读取的原文件或重新准备输入，不能让用户点继续时已经没有数据可用。

## 追问：Worker 在大循环里，为什么收不到取消消息？

1. Worker 虽然与页面主线程分开，但它自己的 JavaScript 执行也有事件循环。当前同步任务没有结束或让出时，消息处理回调不能执行，所以在循环外写一个 onmessage 修改取消标记，并不能保证循环中及时看到变化。

2. 我会把处理拆成可恢复的小批次，在适当任务边界继续下一批，让取消消息有机会被处理。仅使用持续的微任务递归也可能不够，因为消息任务仍可能得不到执行时间，需要确认实际调度行为。

3. 如果任务不需要保留中间状态，可以直接 terminate 并重建 Worker，逻辑更简单。测试取消延迟与资源释放，而不只验证按钮状态变成已取消，否则后台计算可能仍在持续消耗资源。

## 追问：terminate 后怎样让用户重新开始计算？

1. 被终止的 Worker 不能继续执行，需要创建新的实例并重新绑定消息和错误监听。我会让页面任务状态回到可启动状态，同时释放旧实例引用，避免按钮重试却仍向已经结束的 Worker 发消息。

2. 输入也要可恢复。如果之前通过 transfer 转移了 ArrayBuffer，页面原来的缓冲区可能已分离，不能再次直接发送；可以从保留的 File 重新读取，或者在设计时决定是否值得保留一份副本。

3. 新任务使用新标识，旧消息即使迟到也不更新结果。验证重复取消和重启时的内存、监听数量与结果一致性，确认不会每重试一次就多留一套监听或把旧进度接到新任务上。
