# 全局捕获能代替局部处理吗？

## 核心回答

1. 全局捕获不能替代局部处理，因为它通常知道哪里出错，却不知道当前业务该如何恢复。假设表单保存失败，页面知道用户输入是否需要保留、按钮能否重试以及错误应该显示在哪里，全局监听很难仅凭一条异常信息做出这些决定。

2. 局部处理应该放在有能力采取行动的位置，例如字段错误显示在输入旁边，列表加载失败保留查询条件。底层只能补充信息时可以继续抛错，让上层决定交互；并不是每一层都要弹提示，否则同一次失败可能连续打断用户好几次。

3. 在浏览器里，全局错误事件和未处理的 Promise 拒绝事件主要用来发现漏掉的异常，还要注意资源加载错误的监听方式。框架的错误边界又有自己的范围，例如 React 错误边界主要处理子树渲染相关错误，普通事件处理函数的错误仍需要单独考虑。

4. 我会把全局处理作为记录和最后兜底的补充，收集必要的页面、版本和堆栈信息，同时避免记录敏感表单内容。若考虑增加监控，还应设计去重和上报失败的处理，不会因为装了一个监听器，就声称所有错误都被覆盖或业务已经恢复。

## 追问：React 错误边界能捕获按钮点击里请求失败吗？

1. 普通点击处理函数中的异常或异步请求拒绝，不会仅仅因为组件外包着错误边界就被统一接住。错误边界主要针对子树渲染相关错误，按钮事件中的业务失败需要在处理函数或调用的请求流程中处理。

2. 假设点击后提交表单，我会等待提交结果，在失败分支保留输入并展示对应提示，同时完成按钮状态恢复。这样处理位置知道用户正在做什么，也不会把一次可恢复的提交失败直接变成整块界面崩溃。

3. 如果请求结果被交给特定的数据加载框架，再由框架在渲染时抛出错误，可能进入它约定的边界机制。面试时我会说明这个前提，不能把框架集成后的表现推广成所有异步错误都会被普通错误边界捕获。

## 追问：同一个错误被局部和全局监控记录，怎样避免重复上报？

1. 我会先明确各层职责：页面负责提示和恢复，请求层补充接口上下文，监控入口负责实际发送。能在设计上集中上报，就比每层都发送一遍更清楚，也容易知道一条记录究竟代表一次失败还是多次失败。

2. 假设存在多个不可避免的捕获入口，可以通过同一错误对象的标记或关联编号识别重复，再结合合理的短时间窗口处理。不能只按错误消息永久去重，否则不同用户操作引发的同类失败也会被错误地合并。

3. 上报信息应保留次数和必要关联，同时对敏感字段做筛选。监控请求自己失败时也要避免再次进入同一上报循环，否则一次网络中断可能制造大量附加错误，反而淹没最先需要排查的问题。
