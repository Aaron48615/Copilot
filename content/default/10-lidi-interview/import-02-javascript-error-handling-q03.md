# 全局捕获能代替局部处理吗？

## 核心回答

1. 全局捕获替不了局部处理。它通常知道哪里出错，却不知道当前业务该怎么恢复。表单保存失败，页面才知道输入要不要留、按钮能不能重试、错误显示在哪。全局监听很难单凭一条异常信息做这些决定。

2. 局部处理放在有能力采取行动的位置：字段错误显示在输入旁边，列表加载失败留着查询条件。底层只能补信息时可以继续抛，让上层决定交互。不是每一层都要弹提示，同一次失败可能连续打断用户好几次。

3. 浏览器里，全局错误事件和未处理的 Promise 拒绝事件，主要用来发现漏掉的异常。资源加载错误的监听方式也不一样。框架错误边界又有自己的范围，比如 React 错误边界主要处理子树渲染相关错误，普通事件处理函数里的错误还得单独管。

4. 全局处理当作记录和最后兜底的补充：收集必要的页面、版本、堆栈，敏感表单内容别记进去。加监控的话，还要设计去重和上报失败怎么处理。装了一个监听器，不等于所有错误都被盖住，更不等于业务已经恢复。

## 追问：React 错误边界能捕获按钮点击里请求失败吗？

1. 普通点击处理函数里的异常，或异步请求的拒绝，不会只因为组件外包着错误边界就被统一接住。错误边界主要针对子树渲染相关错误。按钮事件里的业务失败，要在处理函数或调用的请求流程里处理。

2. 点击后提交表单，等提交结果，失败分支留着输入、展示对应提示，同时把按钮状态恢复。处理位置知道用户正在做什么，一次可恢复的提交失败，不必直接变成整块界面崩溃。

3. 请求结果交给特定数据加载框架，再由框架在渲染时抛错，可能走进它约定的边界机制。这有前提，不能把框架集成后的表现，推广成所有异步错误都会被普通错误边界抓住。

## 追问：同一个错误被局部和全局监控记录，怎样避免重复上报？

1. 各层职责先分清：页面负责提示和恢复，请求层补接口上下文，监控入口负责真正发送。能在设计上集中上报，就比每层都发一遍更清楚，也容易知道一条记录代表一次失败还是多次失败。

2. 多个捕获入口没法避免时，可以用同一错误对象上的标记或关联编号识别重复，再配一个合理的短时间窗口。别只按错误消息永久去重，不同用户操作引发的同类失败也会被错误地合并。

3. 上报信息留下次数和必要关联，敏感字段要筛掉。监控请求自己失败时，别再进同一套上报循环，不然一次网络中断可能制造大量附加错误，最先要查的问题反而被淹没。
