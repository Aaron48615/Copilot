# 为什么不用一个全局状态管理库保存所有购物车数据？

## 核心回答

1. 轻购目前没有用 Pinia 保存购物车，数据由后端接口提供，页面用 ref、computed 和 watch 管理展示与操作。是否需要全局 Store，主要看谁需要这份状态、需要多久，而不是电商项目就必须引入一种库。

2. 购物车页面内部的 checked、加载状态和当前更新项，主要服务本页，放在附近容易找到修改入口。全选和选中 ID 可以从商品状态计算，不需要再存到多个地方，否则删除或刷新时还要同步很多派生值。

3. 到订单确认页只需传本次购买参数，项目用 sessionStorage 保存 confirmOrder，刷新后还能恢复。它承接的是短期流程，不是把所有商品详情与金额都做成全局真相，确认页仍会重新请求后端。

4. 如果以后导航角标、详情页和购物车都需要及时共享数量，Pinia 就有更明确的价值。届时需要统一修改与失效规则，不能只是把当前 ref 搬进 Store，就以为跨页同步和刷新恢复都会自动完成。

5. 无论是否使用状态库，服务端都负责商品可售性、地址归属与订单金额。全局缓存可能过期，浏览器状态也可被修改，所以关键步骤重新确认不能被省略；我选择简单状态方式，是根据当前共享需求控制复杂度。

## 追问：购物车角标需要全局同步时，你怎么迁移？

1. 我会先找出唯一的购物车数量更新入口，把查询、加购成功后的刷新和退出清理集中起来。各页面通过统一状态读取角标，避免详情页自己加一、购物车又单独重新算，产生两种来源。

2. 迁移可以先只共享角标与必要摘要，勾选仍留在购物车页面。全选是当前页面操作，不一定应该在所有入口长期保留，抽 Store 时要重新考虑生命周期，而不是把所有字段原封不动搬过去。

3. 测试加购、删除、重新登录和刷新后数量是否一致，并处理请求失败时的未知状态。即便角标来自 Store，下单确认仍向后端查商品与金额；这个迁移解决展示共享，不是建立可信结算数据。

## 追问：为什么不能把所有页面状态都持久化？

1. 持久化会延长数据生命周期，例如旧 loading 恢复后可能让按钮一直不可用，过期商品或地址也可能被当成最新内容。哪些字段值得保存，应按用户真正需要恢复的操作来决定，而不是一键保存整个对象。

2. 购物车的事实数据可以重新请求，短期购买意图才适合有限暂存。用户切换账号后，原来的 basketIds 也不能自动继续使用，因此还要配合清理、账号标识或服务端归属检查，不能只看刷新后数据还在。

3. 如果继续完善，我会明确持久化白名单与结构版本，读取失败能安全回到重新选择流程。存储只是恢复便利，数据过期、格式变化和账号隔离仍需设计，不能靠状态管理插件自动解决。
