# 列表为什么要用稳定 key？

## 核心回答

1. 稳定 key 首先保证列表项身份正确，其次才是复用效率。React 对同一父级的元素结合 key 和类型进行对应，业务项换了位置仍能保留自己的组件状态，而不是把旧位置上的状态分配给新占据它的数据。

2. 例如联系人列表支持搜索和排序，每行都能编辑备注。若用下标作 key，过滤掉前面一人后，其他人的下标变化，备注草稿或非受控输入就可能跟错人；文本看似刷新正确，也不能证明组件身份没有发生错误对应。

3. 数据库编号或业务唯一编号通常最合适，前端新增记录则在创建时生成一次并保存。不能在渲染过程中随机生成 key，因为每次都变会导致重复卸载挂载，焦点、展开状态和第三方实例都有可能丢失。

4. key 应放在数组直接返回的元素上，且只要求兄弟之间唯一。它不是自动传给子组件的普通参数，如果点击行需要业务编号，还要显式传 id；同样的 key 配上不同组件类型，也不意味着旧实例能够继续使用。

5. 稳定 key 不会自动阻止父组件更新时重新执行子组件，也不解决上万行 DOM 的体量。性能问题还要查看组件计算、订阅和可见行数；静态列表使用下标可以接受，但将来增加拖拽、筛选或输入时需要重新检查假设。

## 追问：有 key 就等于子组件不会重新渲染吗？

1. 不等于，key 用来决定身份是否延续，是否执行组件还取决于父级更新、组件状态、Context 和 memo 等因素。相同 key 的组件完全可能重新渲染，只是不会因此丢掉原来的局部 state。

2. 比如父组件修改筛选面板开关，列表项 key 都没变，但子组件仍可能执行。若这部分确实昂贵，可以先让开关状态更局部，再考虑 memo 和稳定 props，不能靠更换一种 key 方案来跳过计算。

3. 验证时要区分渲染、提交和重新挂载。控制台函数打印次数多不代表 DOM 全部重建，可以结合 Profiler 与挂载清理观察，才能判断是计算重复，还是身份变化造成资源不断释放和创建。如果子组件本身很轻，没有可感知等待，也不必仅为了减少执行次数就引入复杂的手动比较。

## 追问：数据没有后端 id，应该怎样生成 key？

1. 先检查业务字段能否稳定唯一，例如不可变的商品编码，而不是直接拼接可能重复的姓名。key 需要跨更新对应同一项，如果字段会随编辑变化，用它作 key 也可能在改名时重置组件。

2. 纯前端创建的数据，可以在创建那条记录时生成一次编号，并随着记录一起保存。重新渲染、过滤和排序时继续使用它，不要在 map 里临时生成，这样它才真正表达记录身份。

3. 若接口每次返回全新且无法识别的重复数据，需要先明确列表是否有持久交互状态。静态展示可按位置处理，但编辑和拖拽场景最好与数据接口约定稳定标识，不能声称某个随机算法能猜出跨请求的真实身份。
