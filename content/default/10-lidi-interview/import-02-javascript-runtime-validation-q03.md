# 校验失败要不要自动重试？

## 核心回答

1. 校验失败通常不该自动重试。请求已经拿到内容，只是内容不符合约定，重复获取往往还是同一份问题数据。接口把列表字段改成对象，前端继续请求不会把它变回数组，还会增加服务端压力和用户等待。

2. 先分清失败发生在哪一步：网络中断、正文解析失败，还是解析成功后的结构或业务校验失败。就算状态码显示成功，也可能收到登录页或者字段缺失的对象。这些情况要分别记录，不能统统标成网络故障。

3. 对明确的约定错误，停止依赖这份数据的后续操作，向用户展示可理解的异常状态。普通展示字段可以按约定降级，但订单状态或金额不可信时不能补假值继续提交，也不该把异常结果覆盖到正常缓存里。

4. 排查信息应包含接口标识、客户端版本、失败字段路径以及服务端关联标识，方便确认是不是发布后出现的变化。响应全文常含隐私和凭据，只保留经过筛选的摘要，别为定位一个字段问题记下整份用户资料。

5. 只有有证据表明异常是暂时的，并且接口允许安全重试时，才考虑有上限的恢复策略。某个节点仍在运行旧版本，应先定位和修复版本不一致。让所有客户端无限刷新只会掩盖原因，不能当成稳定方案。

## 追问：服务端返回成功状态但正文是登录页，怎么排查？

1. 先看响应内容类型、实际响应地址和跳转记录，确认是否经过了登录跳转或网关页面。成功状态只代表当前响应的状态，并不保证它就是预期的数据接口结果，所以不能直接把解析错误当成用户填写有误。

2. 接着区分身份过期、请求地址写错与代理配置异常。开发环境路径没有匹配代理规则，可能落到了前端页面。定位时记录路径模板和关联标识即可，别把访问令牌或包含敏感查询参数的完整地址暴露到日志。

3. 修复应落在具体原因上：身份过期走约定的登录恢复，地址错误修正配置，网关问题交给服务端排查。前端可以补充响应类型检查并给出清楚的错误类别，但不应通过反复重试来猜下一次会不会碰巧返回正确内容。

## 追问：怎样记录校验错误才方便定位又不泄露数据？

1. 优先记录出错字段的路径、预期类型和实际类型。比如列表第三项的数量应该是数字，却收到字符串。多数结构问题不需要知道真实姓名、地址或令牌内容，字段位置和类型差异就足以帮助复现和寻找变化。

2. 为了串联一次请求，可以记录受控的请求标识、接口模板和前后端版本，必要时采集脱敏后的最小样例。不能把整个响应转成字符串后上传，嵌套字段里也可能有隐私，日志平台本身还会产生存储与访问成本。

3. 重复出现的相同问题应适当合并或采样，并保留发生次数和影响范围，避免一个坏接口刷满日志。采样规则不能让严重问题完全看不见。关键链路失败仍应有明确统计，同时限制日志访问权限和保留时间。
