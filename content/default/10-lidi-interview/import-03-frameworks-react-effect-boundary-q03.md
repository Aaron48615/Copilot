# 请求怎么避免旧结果覆盖新结果？

## 核心回答

1. 我会先承认请求发起顺序和返回顺序不一定相同。用户先搜索手机又搜索耳机，如果手机的请求后返回，无条件 setState 就会把耳机结果覆盖掉；防抖只能减少次数，不能保证最终返回顺序。

2. 在依赖搜索词的 Effect 中，每次执行都建立独立的请求和有效标记，清理时让旧标记失效。结果到达后先判断是否仍属于当前执行，再写入列表，这样旧请求即使成功也不会进入当前界面。

3. 请求支持取消时，再配合 AbortController，并在清理中 abort，减少不必要的网络和处理开销。取消异常通常不需要显示成红色报错，但普通网络错误仍要展示重试入口，不能统一 catch 后全部忽略。

4. 数据、错误和 loading 都要遵守同一套有效性判断。若请求由事件或多个入口触发，我会用递增编号比较当前请求；这个策略适用于“只要最新结果”的搜索，不应照搬到需要保留每个操作结果的订单提交中。

5. 另外我会把当前条件和已经展示的数据是否匹配表现清楚。用户刚换关键词、结果还没回来时，可以保留旧列表并提示正在更新，也可以显示占位，但不能让旧内容看起来已经是新条件的确认结果，否则技术上没有覆盖，体验上仍可能误导。

## 追问：如果旧请求只是在 finally 里关闭 loading，也会出问题吗？

1. 会。假设请求 A 先开始，B 随后开始，A 结束时 B 还在等待；A 的 finally 无条件执行 setLoading(false)，用户就会看到加载提示提前消失，以为页面已经得到了 B 的结果。

2. 我会把请求编号或有效标记同时用于成功、失败和结束处理。只有仍代表当前搜索的一次请求，才能更新当前搜索的状态，不能只保护 setData 而遗漏 setError 和 setLoading。

3. 若页面本来允许多项任务同时进行，则应该按任务分别记录状态，或者维护活动请求集合。单个布尔值难以表达并发任务，不能靠不断加判断修补一个本来就不够用的状态模型。例如同时上传多个文件，每行应展示自己的进度，不能让最快完成的文件决定整张页面是否仍在上传。

## 追问：如何写测试证明旧响应确实被忽略？

1. 我会让两个模拟请求分别返回可手动完成的 Promise，而不是依赖随机延迟。先输入 A 再输入 B，主动让 B 完成，检查界面显示 B，然后才完成 A，确认列表仍然是 B。

2. 除了数据，还要让 A 在 B 等待时失败或结束，检查错误提示和 loading 没被 A 改掉。这样能覆盖“数据没错但加载状态错了”的情况，单纯断言最后一行文本不够全面。

3. 最后补卸载场景：请求未结束就离开组件，随后完成请求，确认没有继续影响当前页面。若封装支持取消，再验证 signal 被触发，但结果隔离仍应单独测试，不能只检查 abort 被调用。请求的成功和失败都使用受控完成顺序，避免随机网络延时让回归用例偶尔通过、偶尔失败。
