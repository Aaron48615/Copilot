# 请求怎么避免旧结果覆盖新结果？

## 核心回答

1. 请求发出去的顺序，和回来的顺序，不一定一样。用户先搜手机再搜耳机，手机那次后到，无条件 `setState` 就会把耳机结果盖掉。防抖只能少发几次，保证不了谁最后回来。

2. 依赖搜索词的 Effect 里，每一次执行自己带一份请求和有效标记，清理的时候把旧标记作废。结果到了先问还是不是这一次的，再写入列表。旧请求成功了也不会画到当前界面上。

3. 请求支持取消，再配 `AbortController`，清理里 `abort`，少做没用的网络和处理。取消抛出来的异常一般别画成红色报错；普通网络错误还是要给重试。别在 `catch` 里一股脑全吞掉。

4. 数据、错误、loading 用同一套「还算不算当前这次」的判断。请求是点击或者好几个入口触发的，可以用递增编号对当前请求。这套适合搜索这种只要最新结果的；下单每个操作都要留结果，别照搬。

5. 当前条件和已经画出来的数据对不对得上，也要让用户看得出。刚换关键词、结果还没回来，可以暂时留着旧列表并提示正在更新，也可以上占位。别让旧内容看起来已经是新条件的最终结果。技术上没覆盖，看着也会误导。

## 追问：如果旧请求只是在 finally 里关闭 loading，也会出问题吗？

1. 会。请求 A 先发出去，B 跟着发出去，A 结束时 B 还在等。A 的 `finally` 无条件 `setLoading(false)`，加载提示提前没了，用户以为 B 已经有结果了。

2. 请求编号或有效标记，成功、失败、结束都要用。只有还代表当前搜索的那一次，才能改当前搜索的状态。只护住 `setData`，`setError` 和 `setLoading` 漏了，照样乱。

3. 页面本来就允许多件事一起跑，就按任务分别记状态，或者维护一组还在活动的请求。一个布尔值说不清并发。同时传好几个文件，每一行应是自己的进度，别让最快完成的那个决定整页还在不在传。

## 追问：如何写测试证明旧响应确实被忽略？

1. 两个模拟请求各自返回能手动完成的 Promise，别靠随机延迟。先输入 A 再输入 B，先让 B 完成，界面应是 B；再让 A 完成，列表还应该是 B。

2. 数据之外，让 A 在 B 还在等的时候失败或结束，错误提示和 loading 不该被 A 改掉。这能盖住「列表对了、加载状态错了」。只断言最后一行文字不够。

3. 再补卸载：请求没结束就离开组件，随后请求完成，不该再动当前页面。封装支持取消，再看 `signal` 有没有被触发。结果隔离开来仍要单独测，光看 abort 被调用了不够。成功失败都按受控顺序完成，别让随机网速把回归测得一会儿过一会儿挂。
