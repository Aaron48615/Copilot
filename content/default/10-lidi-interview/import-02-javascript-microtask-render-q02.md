# 为什么 await 后的代码常常先于 setTimeout？

## 核心回答

1. 这个说法有前提：如果等待的值已经兑现，或者只是普通值，`await` 后续会通过 Promise 反应异步恢复。在同一段常见浏览器脚本中，它通常会在进入计时器任务前执行，所以看起来比零延时计时器更早。

2. 即使等待的是一个普通数字，后续代码也不会直接作为当前同步调用继续执行。比如先启动异步函数，再在外面打印日志，函数会在等待处让出当前执行，外面的同步日志先出现，然后才轮到已排好的恢复逻辑。

3. 但如果等待的是尚未完成的网络请求，后续此时还没有条件恢复，计时器就完全可能先执行。真正要比较的是 Promise 何时完成、恢复工作何时入队，以及当时有哪些可运行任务，而不是看到 `await` 就判定它一定优先。

4. 微任务检查会继续处理期间新加入的微任务，因此链式 Promise 或连续等待已完成值，可能都发生在下一个任务之前。这个过程不会自动给页面一次绘制机会，若恢复逻辑里进行大量同步计算，交互和动画仍然可能受到阻塞。

5. 假设目的是先展示加载状态再开始重计算，我不会把一个立即兑现的等待当作绘制保证。会考虑把计算拆成多个任务或移到 Worker，并用实际页面表现确认加载提示是否出现；控制台日志的先后只能证明执行顺序，不能证明用户已经看到更新。

## 追问：await 一个由计时器完成的 Promise 会怎样排序？

1. 假设先注册计时器甲，它的回调用来兑现正在等待的 Promise，再注册计时器乙打印日志。当甲先作为任务运行时，兑现操作会安排等待后的恢复工作，但恢复不会插进甲回调中间，而要等当前同步代码结束。

2. 到随后进行微任务检查时，恢复逻辑可以先于乙的任务执行。于是常见顺序是甲回调的同步部分、等待后的代码、乙回调；这里体现的是完成操作触发了后续微任务，并不是等待代码一开始就排在所有计时器前面。

3. 如果乙更早到期并先被执行，或者甲尚未满足运行条件，顺序就会不同。我会在题目中先标出计时器注册和 Promise 完成的位置，再推演排队过程，避免忽略等待对象的来源，仅按语法关键字给出固定答案。

## 追问：连续 await Promise.resolve 能让页面保持流畅吗？

1. 不能依靠它保证流畅，因为每次恢复仍然可能接着排入微任务，浏览器需要继续处理这些工作。假设把大循环改成每轮等待一个已兑现 Promise，虽然调用栈被切开，任务和渲染却仍可能长时间得不到推进。

2. 若想让其他任务有机会运行，可以按一定工作量拆分，并在片段间使用合适的任务调度方式。每片多大要依据实际耗时调整，不能只按固定条数推断体验，因为一条数据的处理成本也可能随内容明显变化。

3. 对于不依赖 DOM 的持续计算，我会考虑 Worker，并让主线程只接收必要结果。这个方案仍有消息传递和数据复制成本，所以应先确认卡顿来自计算，再验证拆分后的输入响应；仅仅增加异步语法并不能说明优化有效。
