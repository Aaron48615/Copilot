# 设计一个可配置数据大屏，重点会考虑什么？

## 核心回答

1. 我会先问清楚大屏给谁看、关注哪些指标，以及允许多大的数据延迟。展示型大屏和分析报表的交互需求不同，第一版可以先支持有限的图表和筛选项，避免一开始就做任意拖拽、任意公式的编辑平台。

2. 配置层用可校验的数据结构描述布局、数据源标识、维度、指标和图表类型，并为格式保留版本。比如按天展示订单金额，需要明确求和口径、日期范围和货币单位；配置保存业务含义，不直接保存任意可执行代码。

3. 数据层把配置转换成受约束的查询，服务端负责授权和适合下推的聚合，前端负责展示适配。各卡片独立维护加载、空结果和错误状态，并限制同时请求的数量，避免一张卡失败拖住整个页面。

4. 渲染层可以把折线图、柱状图和数字卡封装成统一入口，复用图表实例更新数据。使用 ECharts 时通过 setOption 更新，容器尺寸变化时调整大小，卸载时销毁实例；大数据量先减少无用点，而不是每次刷新都重建图表。

5. 刷新策略按指标设置，结合缓存、页面可见性和请求版本控制，防止旧条件的结果覆盖新条件。上线前的验证重点会放在口径正确、单卡失败、长时间运行和不同屏幕尺寸上。需要比较性能时，我会保持设备和数据条件一致，再记录加载及交互的实际变化。

## 追问：拖拽布局和图表配置应怎样保存？

1. 我会给每张卡片稳定的标识，分别记录网格位置、尺寸和业务配置。拖动只改变布局字段，不改变查询口径；复制卡片则生成新标识，避免两个组件错误地共用同一个图表实例或编辑状态。

2. 编辑过程中使用草稿，拖拽结束后更新位置，避免鼠标每移动一下就提交服务端。保存前检查卡片重叠、最小尺寸和配置合法性，预览与正式发布的范围也要明确，防止半完成的修改马上影响展示页。

3. 保存请求带当前修订号，服务端发现版本落后时返回冲突信息，并保留本地草稿。简单版本可以让用户比较后选择重载或另行调整，不必一开始就实现多人实时协同，但不能用最后一次写入掩盖冲突。

## 追问：大屏卡顿时，你会先优化哪一部分？

1. 我会先区分接口慢、数据转换慢和图表绘制慢，分别看请求耗时和主线程任务。接口已经返回却迟迟不显示，就不应只调整轮询时间；如果数据本身到得晚，减少动画也解决不了主要等待。

2. 对长时间序列，优先根据屏幕宽度选择聚合粒度或合适的采样方式，并说明展示的是汇总结果。采样不能随意丢掉峰值，否则监控图会误导判断；精确数值查询仍应有对应的数据入口。

3. 对同时刷新的多张图，可以错开更新时机、减少动画，并复用实例和静态配置。虚拟化适合屏幕外的长列表，不能直接减少一个始终可见的画布内部点数，所以我会根据实际瓶颈选择办法。
