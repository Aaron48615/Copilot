# 设计一个可配置数据大屏，重点会考虑什么？

## 核心回答

1. 大屏给谁看、关注哪些指标、允许多大的数据延迟，先问清楚。展示型大屏和分析报表，交互需求不一样。第一版可以先支持有限的图表和筛选项，一开始就做任意拖拽、任意公式的编辑平台，范围太大。

2. 配置层用可校验的数据结构描述布局、数据源标识、维度、指标、图表类型，格式留版本。按天展示订单金额，要求和口径、日期范围、货币单位都要明确。配置保存业务含义，不直接保存任意可执行代码。

3. 数据层把配置转成受约束的查询。服务端负责授权和适合下推的聚合，前端负责展示适配。各卡片自己维护加载、空结果、错误状态，同时发出去的请求数量也要限制。一张卡失败，别拖住整个页面。

4. 渲染层可以把折线图、柱状图、数字卡封成统一入口，复用图表实例更新数据。用 ECharts 时通过 `setOption` 更新，容器尺寸变了再调大小，卸载时销毁实例。数据量大就先减少无用点，别每次刷新都重建图表。

5. 刷新策略按指标设，结合缓存、页面可见性、请求版本控制，旧条件的结果别盖住新条件。上线前重点验口径对不对、单卡失败、长时间跑、不同屏幕尺寸。要比较性能，设备和数据条件保持一致，再记加载和交互的实际变化。

## 追问：拖拽布局和图表配置应怎样保存？

1. 每张卡片一个稳定标识，网格位置、尺寸、业务配置分开记。拖动只改布局字段，不改查询口径。复制卡片生成新标识，两个组件别错误地共用同一个图表实例或编辑状态。

2. 编辑过程用草稿，拖拽结束再更新位置，鼠标每动一下就提交服务端没必要。保存前检查卡片重叠、最小尺寸、配置合不合法。预览和正式发布的范围也说清，半完成的修改别马上影响展示页。

3. 保存请求带当前修订号，服务端发现版本落后就返回冲突信息，本地草稿留着。简单版本可以让用户比较之后选择重载或另行调整，一开始不必做多人实时协同。但不能用最后一次写入把冲突盖掉。

## 追问：大屏卡顿时，你会先优化哪一部分？

1. 接口慢、数据转换慢、图表绘制慢，先分开看请求耗时和主线程任务。接口已经回来了却迟迟不显示，只调轮询时间没用。数据本身到得晚，减动画也解决不了主要等待。

2. 长时间序列，优先按屏幕宽度选聚合粒度或合适的采样，并说明展示的是汇总结果。采样别随便丢掉峰值，监控图会误导判断。精确数值查询仍应有对应的数据入口。

3. 同时刷新的多张图，可以错开更新时机、减少动画，复用实例和静态配置。虚拟化适合屏幕外的长列表，减不了一个始终可见的画布内部点数。按实际瓶颈选办法。
