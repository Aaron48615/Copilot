# useReducer、Context 和 Redux 怎么取舍？

## 核心回答

1. useReducer、Context 和 Redux 解决的问题并不完全相同。useReducer 把一个组件或局部功能的状态变化集中成规则，Context 把某个值传给深层组件，Redux 则提供组件外的状态容器和配套更新、调试机制，不能只按大小排列成升级路线。

2. 少量独立状态使用 useState 就够了。当表单向导有下一步、返回、重置等动作，而且多个字段需要一起变化时，我会考虑 useReducer，让每个动作对应一个明确结果，减少到处散落的 setter 和不合法组合。

3. 如果这个局部状态需要被多个深层组件使用，可以把 state 和 dispatch 通过 Context 提供。这样不用层层传参，但也要注意订阅范围，Context 默认不会自动按某个字段筛选变化，频繁更新的大对象需要拆分。

4. 跨页面共享的数据有较复杂更新规则，或者需要统一异步处理、开发工具和缓存时，Redux Toolkit 会更合适。采用状态库也有学习和组织成本，我会先确认组件关系和需求，不能因为项目用了 React 就默认必须上 Redux。

5. 我还会区分服务端数据与本地交互状态。接口数据需要缓存、过期和重试策略，输入草稿需要及时响应和取消编辑；它们可以在同一项目采用不同方案，关键是每份数据有明确来源，不在多个地方重复维护同一答案。

## 追问：什么时候 useReducer 比多个 useState 更清楚？

1. 当一次动作会同时改变多个字段时更有优势。例如提交表单开始时要设为提交中、清除旧错误并记录本次请求，成功和失败又对应不同组合；动作能够把这些变化放在同一个可阅读的分支里。

2. reducer 可以表达允许的状态转换，避免同时出现 success=true 和 error=true 之类矛盾。对简单开关没必要强行引入 action 类型，但多步骤流程可以用明确阶段替代一组互相制约的布尔值。

3. 我会对关键动作输入和结果做小范围测试，例如提交失败保留草稿，重置回到初始步骤。测试的是业务规则，而不是重复框架行为；副作用仍在 reducer 外部处理，不能把状态集中等同于代码全部集中。

## 追问：已经用了 Redux，页面内部还可以用 useState 吗？

1. 可以，而且通常应该这样组合。只服务于一个弹窗的开关或尚未提交的输入，放本地状态更直接；Redux 保存真正需要共享的业务结果，不需要跟踪每一次光标移动和输入法中间状态。

2. 要注意本地草稿和共享数据的关系。例如编辑用户信息时，从共享数据初始化草稿，提交成功后再更新共享状态；后台刷新时不能无条件复制回来，覆盖用户已经修改但尚未保存的内容。

3. 我会明确重置时机，比如切换用户编号或点击取消时恢复数据。只要状态归属和同步节点清楚，混合使用不会天然混乱；反而把所有局部细节全局化，容易让其他页面形成不必要的依赖。
