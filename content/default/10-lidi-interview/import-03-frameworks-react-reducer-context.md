# useReducer、Context 和 Redux 怎么取舍？

## 核心回答

1. 三件事解决的问题不一样。`useReducer` 把一个组件或一块功能的状态变化收成规则；Context 把某个值传给深层组件；Redux 是组件外面的状态容器，带更新和调试配套。不是按项目变大就一级级升级。

2. 少量互相不太管的状态，`useState` 就够。表单向导有下一步、返回、重置，好几个字段要一起变，再用 `useReducer`。每个动作对应一个明确结果，少一堆散落的 setter，也不容易拼出不合法组合。

3. 这份局部状态还要给很多深层组件用，可以把 state 和 `dispatch` 用 Context 递下去，少层层传参。订阅范围要留意：Context 默认不会按某个字段筛选变化。频繁更新的大对象要拆。

4. 跨页面共享、更新规则比较复杂，或者要统一异步、开发工具、缓存，Redux Toolkit 更合适。状态库有学习成本和组织成本。先看组件关系和真实需求。项目用了 React，不等于必须上 Redux。

5. 服务端数据和本地交互状态也要分开看。接口数据要缓存、过期、重试；输入草稿要跟手、能取消。同一项目可以两套方案。每份数据来源清楚，别多处各维护一份同一答案。

## 追问：什么时候 useReducer 比多个 useState 更清楚？

1. 一次动作会同时改好几个字段时更清楚。提交一开始要设成提交中、清掉旧错误、记下这次请求；成功和失败又是另一组组合。动作能把这些变化放进同一个能读的分支。

2. reducer 可以写出允许的状态转换，别让 `success=true` 和 `error=true` 同时出现。一个简单开关没必要上 action 类型。多步骤流程用明确阶段，比一组互相掐的布尔值好懂。

3. 对关键动作做小范围测试：提交失败草稿还在，重置回到初始步骤。测的是业务规则，不是框架自己会做什么。副作用仍在 reducer 外面处理。状态集中了，不等于所有代码都塞进 reducer。

## 追问：已经用了 Redux，页面内部还可以用 useState 吗？

1. 可以，而且常常就该这么搭配。只服务一个弹窗的开关、还没提交的输入，放本地更直接。Redux 存真正要共享的业务结果，不必跟踪每一次光标移动和输入法中间态。

2. 本地草稿和共享数据的关系要说清。编辑用户信息，从共享数据初始化草稿，提交成功再写回共享状态。后台刷新别无条件复制回来，盖住用户已经改但还没保存的内容。

3. 重置时机说清楚：换用户编号、点取消时恢复。归属和同步节点清楚，混着用不会天然乱。把所有局部细节都全局化，别的页面反而会多出不必要的依赖。
