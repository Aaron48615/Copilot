# 如何处理浏览器兼容性？

## 核心回答

1. 我会先确认目标浏览器、具体版本和设备，再判断问题属于语法、运行时 API、CSS 还是第三方库。兼容性需要有支持范围，否则为了少量未知旧环境加入大量补丁，既增加体积也很难验证。

2. JavaScript 语法转换和 API 补齐是两件事，Babel 可以按配置转换部分新语法，但不会因此自动提供所有浏览器能力。比如可选链属于语法，Promise 属于运行时能力，DOM API 又要检查是否有合适的替代实现。构建工具能做什么，应以实际配置和产物为准。

3. CSS 可以结合目标环境使用 Autoprefixer、回退值和渐进增强，但加前缀不能让浏览器支持所有新布局。对于会影响基本可用性的样式，我会先提供基础方案，再用支持检测启用增强效果。

4. 我更倾向于检测需要的能力，而不是只判断浏览器名字，比如先看是否存在 ResizeObserver。存在 API 也不代表所有参数和行为都完全一致，所以地图、图表、文件上传这类功能还需要实际运行验证。

5. 检查时会覆盖表单输入、布局、滚动、路由、请求和关键交互，并尽量在真实目标浏览器上复现。如果继续完善，我会记录已测环境和仍未覆盖的版本，不能只在开发机 Chrome 通过就宣称全浏览器兼容。

## 追问：配置了 Babel，为什么仍然报某个 API 不存在？

1. Babel 主要负责代码转换，是否加入 polyfill 取决于 preset、targets 和相关配置。把新的函数写法转成旧语法，并不意味着浏览器就拥有 Promise、Array.from 或其他原来没有的运行时对象。

2. 我会核对报错 API 的支持范围、构建目标和产物，再判断需要补齐哪项能力。某些浏览器 API 不是 core-js 的范围，还可能没有完整可行的 polyfill，不能看到缺失就随便安装一个包。否则可能既增加体积，也没有修复目标浏览器中的问题。

3. 补齐也要考虑体积和加载顺序，必须在使用该能力之前生效。验证时用目标浏览器测试实际流程，同时检查第三方依赖是否也符合目标语法要求，不能只看业务源码经过了 Babel 就结束。

## 追问：不支持 ResizeObserver 时，怎么提供基本功能？

1. 我会先通过特性检测决定是否使用 ResizeObserver，避免直接调用不存在的构造函数。对于图表尺寸同步，可以在支持的浏览器观察容器变化，不支持时再选择替代方案。

2. 简单回退可以监听窗口 resize，并在已知的布局切换后主动通知图表调整尺寸。但窗口没有变化时，侧栏展开也可能改变容器大小，所以这个回退与 ResizeObserver 并不完全等价。

3. 如果目标环境确实需要完整能力，可以评估适合的 polyfill，并验证性能和行为差异。无论采用哪种方案，都要在离开页面时移除监听或断开观察，兼容处理不能顺带引入重复回调和资源泄漏。
