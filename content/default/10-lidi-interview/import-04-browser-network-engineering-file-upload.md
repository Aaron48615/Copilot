# 前端文件上传怎么设计？

## 核心回答

1. 文件上传先按文件大小和使用场景选复杂度。头像这类小文件可以用 FormData 直接上传，选择后检查大小和允许类型，并给出提示。浏览器生成 multipart 请求时通常不手写 `Content-Type`，让它正确带上 boundary。

2. 界面状态要覆盖未选择、上传中、成功、失败和取消。需要进度时，选支持相应能力的请求实现。上传完成后还可能有服务端处理阶段，已发送字节数不能直接当成资源已经能用。

3. 大文件可以设计分片上传：创建任务，切分文件，每片带上任务标识和序号，限制并发，服务端记下进度后再合并。续传时查询服务端已确认的分片，只补传缺失部分。重新选择文件时还要核对内容身份，防止同名不同内容的文件错误续接。最后由服务端校验并确认合并结果。

4. 可靠性上要处理取消、有限重试和重复提交，同一分片以及合并操作应有幂等约定。服务端独立检查权限、类型和大小，必要时扫描内容并清理过期分片。前端校验只是帮用户尽早发现问题。

5. 本地预览可以用对象 URL，替换文件或组件销毁时释放，避免一直占着资源。最终业务表单保存的是服务端确认的文件标识，不是本地路径。文件上传成功但表单没提交时，也要有临时资源回收办法。

## 追问：分片越小、并发越高，上传就一定越快吗？

1. 不一定。分片太小会增加请求和服务端管理开销，并发过高会抢带宽、触发限流，甚至让其他页面请求变慢。分片太大又会增加失败重传的成本，所以要按文件大小和真实网络折中。

2. 先设一个有限并发队列，完成一片再启动下一片，失败重试也纳入调度。别一次创建全部请求让浏览器自己排队，否则取消和进度统计更难控，也不容易尊重服务端的吞吐限制。

3. 验证时比较总耗时、失败率和资源占用，覆盖弱网，别只测本机高速网络。可以先固定并发只调分片大小，再固定分片调并发，比较弱网里的重试成本和总耗时，把能解释差异的测试条件留下来。

## 追问：预览用对象 URL，为什么需要手动释放？

1. `URL.createObjectURL` 创建的是浏览器可引用的本地资源地址，它会让关联的 Blob 在需要期间保持可用。即使页面变量换成新文件，旧地址也可能仍留着资源。频繁预览大文件，内存占用就会上去。

2. 替换文件和组件卸载时调用 `revokeObjectURL`，并清掉旧引用。释放不能过早，图片还没用完就撤销地址，预览或后续操作可能失败，所以要跟实际预览生命周期配合。

3. 对象 URL 也不是可以存进数据库的永久下载地址，它只适用于当前浏览器上下文里的本地资源。上传成功后应使用服务端返回的资源信息，本地预览失败和服务端文件访问失败，要分开处理。
