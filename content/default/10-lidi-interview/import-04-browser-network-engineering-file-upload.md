# 前端文件上传怎么设计？

## 核心回答

1. 文件上传我会先按文件大小和使用场景选择复杂度。头像等小文件可以用 FormData 直接上传，选择后检查大小和允许类型并给出提示；浏览器生成 multipart 请求时通常不手写 Content-Type，让它正确附带 boundary。

2. 界面状态要覆盖未选择、上传中、成功、失败和取消。需要进度时选支持相应能力的请求实现，上传完成后还可能有服务端处理阶段，不能把已发送字节数直接当作资源已经可以使用。

3. 大文件可以设计分片上传：创建任务，切分文件，给每片带任务标识和序号，限制并发，服务端记录进度后再合并。续传时查询服务端已确认的分片，只补传缺失部分；重新选择文件时还要核对内容身份，防止同名不同内容的文件错误续接，最后由服务端校验并确认合并结果。

4. 可靠性上要处理取消、有限重试和重复提交，同一分片及合并操作应有幂等约定。服务端独立检查权限、类型和大小，必要时扫描内容并清理过期分片，前端校验只是帮助用户尽早发现问题。

5. 本地预览可以使用对象 URL，替换文件或组件销毁时释放，避免一直持有资源。最终业务表单保存的是服务端确认的文件标识，而不是本地路径；文件上传成功但表单未提交时，也要有临时资源回收办法。

## 追问：分片越小、并发越高，上传就一定越快吗？

1. 不一定。分片太小会增加请求和服务端管理开销，并发过高会竞争带宽、触发限流，甚至让其他页面请求变慢。分片太大又会增加失败重传的成本，所以需要根据文件大小和真实网络选择折中。

2. 我会先设一个有限并发队列，完成一片再启动下一片，并将失败重试也纳入调度。不要一次创建全部请求让浏览器自己排队，否则取消和进度统计更难控制，也不容易尊重服务端的吞吐限制。

3. 验证时比较总耗时、失败率和资源占用，覆盖弱网而不只测本机高速网络。可以先固定并发只调整分片大小，再固定分片调整并发，比较弱网中的重试成本与总耗时，保留能够解释差异的测试条件。

## 追问：预览用对象 URL，为什么需要手动释放？

1. URL.createObjectURL 创建的是浏览器可引用的本地资源地址，它会让关联的 Blob 在需要期间保持可用。即使页面变量换成新文件，旧地址也可能仍保留资源，频繁预览大文件就会增加内存占用。

2. 我会在替换文件和组件卸载时调用 revokeObjectURL，并清理旧引用。释放不能过早，图片尚未完成使用就撤销地址可能导致预览或后续操作失败，因此要与实际预览生命周期配合。

3. 对象 URL 也不是可以保存到数据库的永久下载地址，它只适用于当前浏览器上下文中的本地资源。上传成功后应使用服务端返回的资源信息，并分别处理本地预览失败和服务端文件访问失败。
