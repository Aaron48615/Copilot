# `reset`、`revert` 和 `checkout` 怎么区别？

## 核心回答

1. 我会先区分是在调整本地提交、撤销已共享改动，还是切换分支和恢复文件。reset、revert 和 checkout 能影响不同层面的状态，不能只把它们都记成“回退代码”，执行前要看当前提交、暂存区和工作区。

2. 对提交使用 reset 会移动当前分支的位置，soft 保留暂存区和工作区，默认 mixed 还会重置暂存区但保留工作区。hard 会进一步覆盖工作区，存在丢失未提交内容的风险，不能为了操作方便随意使用。

3. reset 还有按路径恢复暂存区的形式，例如 `git reset HEAD -- file` 可以取消指定文件暂存，但不移动分支。这个区别很重要，否则容易以为所有 reset 都会改变提交历史，或者误把撤销暂存当成删除修改。

4. revert 会根据已有提交生成相反的修改，并通常新增一个提交来记录撤销，适合保留公共历史。它也可能冲突，而且只撤销代码变化，不能自动回滚已经写入的业务数据或外部系统操作。

5. checkout 既能切分支，也能恢复路径或进入分离 HEAD；现在通常用 switch 和 restore 分清用途。恢复文件同样可能覆盖未提交内容，所以我会先看 diff、确认文件范围，不能把看起来熟悉的命令当成没有风险。

## 追问：只想取消暂存，和丢弃工作区修改有什么不同？

1. 取消暂存只是把文件从下一次提交的候选内容中移出，编辑后的文件仍然留在工作区。可以使用 `git restore --staged -- file`，之后再次查看 diff，确认内容仍在，只是没有准备提交。

2. 恢复工作区会改写实际文件，`git restore -- file` 默认从暂存区恢复工作区对应路径。如果暂存区有部分修改，它恢复的也不一定是 HEAD 内容，所以需要先确认要从哪个来源恢复。

3. 我会明确用户是想保留修改稍后提交，还是确实不要这些编辑，再执行相应操作。只取消一个文件暂存就指定那个路径，不应该用整个目录覆盖来省事，尤其在多人并行编辑时容易误伤其他内容。

## 追问：已经推送的错误提交，为什么通常优先 revert？

1. 别人可能已经基于已推送的提交继续开发，revert 在原历史后面增加撤销记录，不需要让所有人重新适应改写后的提交关系。它能清楚保留错误提交与修复动作，便于后来追查原因。

2. 也要确认撤销范围和后续依赖，如果后面的提交已经依赖错误提交中的部分结构，直接反向应用可能产生冲突或新问题。合并提交的 revert 还需要选择主线父提交，不能只凭一个哈希直接操作。

3. 如果提交里包含泄露的密钥，revert 并不会把旧历史里的密钥清掉，需要先使凭据失效，再按授权处理历史。普通功能错误和敏感信息泄露是不同问题，不能把新增反向提交当成所有场景的完整处理。
