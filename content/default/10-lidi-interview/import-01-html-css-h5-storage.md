# cookie、localStorage、sessionStorage 有什么区别？

## 核心回答

1. cookie 和 Web Storage 的主要区别是用途及发送方式。符合域、路径、安全和同站等条件的 cookie 会随相关请求发送，适合服务端需要的小型会话标识；不是所有同源请求都无条件携带，更不是浏览器里所有 cookie 都会一起发往任意接口；还可以通过到期设置控制持久性。

2. localStorage 通常按源保存字符串数据，跨页面会话保留，适合主题偏好等可恢复信息，但用户清理、浏览器策略和存储限制都可能让数据消失。它不会自动发给服务器，也不保证永久可靠，所以不能把唯一的重要业务记录只放在这里。

3. sessionStorage 还按顶层浏览上下文区分，刷新通常保留，主要适合当前标签页的临时状态，关闭标签页通常会结束对应的页面会话。新窗口在某些打开方式下可能获得初始副本，之后各自独立，不能简单说任意新标签页一定从空开始；浏览器恢复会话的行为也需要结合环境看。

4. 安全和性能也要分别考虑。HttpOnly cookie 限制脚本读取，但不消除 XSS 的其他危害；Secure 和 SameSite 各有职责。Web Storage 是同步接口，同源脚本通常能访问，不适合随意存敏感凭据或大量数据；容量和失败情况应以实际环境为准，并处理读写异常。

5. 如果只是表单草稿，我会根据需要选择标签页内保存还是跨会话恢复，并提供明确清除入口。草稿与服务端正式记录应区分，不能读取到本地值就当成提交成功，也要避免在退出账号后继续显示上一个会话的内容。

## 追问：HttpOnly cookie 是否意味着不用再防 XSS 和 CSRF？

1. 不是，HttpOnly 主要阻止脚本直接读取对应 cookie，攻击脚本仍可能借用户当前会话发起操作或窃取页面中的其他数据。防 XSS 还需要正确处理不可信内容、避免危险注入点，不能把一个 cookie 属性理解成整页安全保证。

2. CSRF 与浏览器自动携带身份有关，SameSite 能降低部分跨站请求风险，但具体策略还要结合请求方式和业务场景。敏感操作通常仍应在服务端校验来源、令牌或其他适用条件，不能因为前端按钮隐藏就允许请求。

3. 以服务端会话配合 cookie 的登录为例，退出时我会检查服务端是否使会话失效，响应是否按正确的域和路径清除对应 cookie。然后刷新页面、重试受保护请求，确认旧会话不能继续访问，同时清理当前账号的页面状态；只隐藏用户名，并不等于完成退出。

## 追问：localStorage 读写失败时，页面应该怎么处理？

1. 访问或写入可能因为环境策略、配额等原因抛出异常，读取到的字符串也可能无法正确解析。像主题偏好这种辅助状态，我会用异常处理和默认值保证页面可用，不能让一条损坏的缓存直接阻止整个应用启动。

2. 存储结构可以带版本，解析后检查必要字段，旧格式按明确规则迁移或忽略。不要把任何读出的 JSON 都当成可信业务对象，也不要在解析失败时直接清空所有站点存储，因为其他功能可能仍依赖其中的数据。

3. 如果数据量大、写入频繁或需要结构化查询，可以评估 IndexedDB，而不是每次输入都同步序列化整份对象。无论用哪一种，本地存储都应有失效和恢复策略，重要记录需要与可靠的服务端状态保持清楚的关系。
