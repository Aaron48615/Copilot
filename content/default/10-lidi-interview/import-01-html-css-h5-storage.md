# cookie、localStorage、sessionStorage 有什么区别？

## 核心回答

1. cookie 和 Web Storage 的主要差别是用途和发送方式。符合域、路径、安全、同站等条件的 cookie 会随相关请求带上，适合服务端需要的小型会话标识。不是所有同源请求都无条件携带，更不是浏览器里所有 cookie 都会一起发往任意接口。到期时间也能控制持久性。

2. `localStorage` 通常按源保存字符串，跨页面会话还在，适合主题偏好这类可恢复信息。用户清理、浏览器策略、存储限制都可能让数据消失。它不会自动发给服务器，也不保证永久可靠，唯一的重要业务记录别只放这里。

3. `sessionStorage` 还按顶层浏览上下文区分，刷新通常还在，主要适合当前标签页的临时状态。关掉标签页，对应的页面会话通常就结束了。新窗口在某些打开方式下可能拿到一份初始副本，之后各自独立。别说任意新标签页一定从空开始。浏览器恢复会话的行为也得结合环境看。

4. 安全和性能得分开说。HttpOnly cookie 限制脚本读取，但 XSS 的其他危害还在。Secure 和 SameSite 各管各的。Web Storage 是同步接口，同源脚本通常能访问，敏感凭据或大量数据别随手放。容量和失败情况以实际环境为准，读写异常要处理。

5. 表单草稿按需要选标签页内保存还是跨会话恢复，并给明确的清除入口。草稿和服务端正式记录要分开。读到本地值不等于提交成功。退出账号以后，上一个会话的内容也不该还显示着。

## 追问：HttpOnly cookie 是否意味着不用再防 XSS 和 CSRF？

1. 不是。HttpOnly 主要拦住脚本直接读对应 cookie。攻击脚本仍可能借用户当前会话去操作，或偷页面里别的数据。防 XSS 还得正确处理不可信内容、避开危险注入点。一个 cookie 属性当不了整页安全保证。

2. CSRF 跟浏览器自动携带身份有关。SameSite 能降低一部分跨站请求风险，具体策略还要结合请求方式和业务场景。敏感操作通常仍应在服务端校验来源、令牌或其他适用条件。前端按钮藏了，不等于请求可以放行。

3. 以服务端会话配合 cookie 的登录为例，退出时看服务端有没有让会话失效，响应有没有按正确的域和路径清对应 cookie。然后刷新页面、再打受保护请求，确认旧会话进不去，当前账号的页面状态也清掉。只藏用户名，不等于退出做完了。

## 追问：localStorage 读写失败时，页面应该怎么处理？

1. 访问或写入可能因为环境策略、配额等原因抛错，读到的字符串也可能解析不了。主题偏好这种辅助状态，用异常处理和默认值保证页面还能用，别让一条损坏的缓存把整个应用卡住。

2. 存储结构可以带版本，解析后检查必要字段，旧格式按明确规则迁移或忽略。读出来的 JSON 别都当成可信业务对象。解析失败时也别直接清空站点全部存储，别的功能可能还依赖里面的数据。

3. 数据量大、写得很勤，或需要结构化查询，可以评估 IndexedDB，别每次输入都同步序列化整份对象。不管用哪一种，本地存储都要有失效和恢复策略。重要记录跟可靠的服务端状态，关系得说清楚。
