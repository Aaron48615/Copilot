# 刷新和缓存怎么取舍？

## 核心回答

1. 我会先确认每类指标能接受多大的延迟，再决定刷新方式。当天订单概览和已经结算的月度趋势不需要同一频率，刷新更快也不代表源数据更新更快；页面应说明数据更新时间，避免制造实时的错觉。

2. 变化不频繁的卡片可以轮询，而且等本轮结束后再安排下一轮，避免慢请求持续堆积。页面隐藏时暂停不必要的刷新，恢复可见后检查数据是否过期；确实需要及时推送时，再评估连接维护和断线恢复的成本。

3. 缓存键要包含数据源、指标、筛选条件、时间范围和用户所属的数据范围。比如同样查询本月金额，不同租户的结果不能复用；权限变化或退出登录时也要清理相关缓存，不能只按卡片编号取数据。

4. 用户切换筛选条件时，我会取消旧请求，并通过请求序号阻止旧结果写回。序号要在条件变化时就更新，不能等下一次请求发出才更新；成功、失败和加载结束状态都要检查，避免旧请求把新请求的加载提示关掉。

5. 普通刷新失败可以保留同一查询下最后一次成功的数据，同时展示过期状态和重试入口。首次加载失败则显示错误；切换到新条件后不能无提示地沿用旧条件的数据，否则页面看起来正常，数字却回答了另一个问题。

## 追问：多个卡片查同一份数据，怎么避免重复请求？

1. 我会先把查询条件规范化，再用完整查询键识别相同请求。同一个时间范围要用一致的时区和边界表示，筛选数组也要约定顺序，否则只是字段排列不同，就可能被误当成两次不同查询。

2. 对正在进行的相同请求，可以让多个卡片订阅同一个结果，成功后各自转换成需要的图表数据。某张卡片卸载时只解除它的订阅，不能直接取消所有卡片共用的请求，要等没有订阅者时再考虑取消。

3. 共享应以查询语义和权限范围相同为前提，不能为了省请求把不同口径强行合并。一个接口若返回多个指标，也要约定局部失败如何表示，否则单个指标异常可能让原本独立的卡片一起不可用。

## 追问：实时推送断线以后，怎样判断数据有没有漏？

1. 我会先确认推送的是完整快照还是增量事件。快照可以用最新版本替换旧数据，增量则需要事件标识或连续序号；如果只收到变化量，却不知道中间漏了多少条，直接继续累加会得到错误结果。

2. 重连时优先根据服务端支持的游标补齐事件，并按标识去重，避免重复计算。若服务端不支持补发，或者游标已经过期，就重新获取完整快照，再从与快照对应的位置继续接收更新。

3. 断线期间要显示连接状态和最后更新时间，恢复过程也不能悄悄当成一直在线。重连使用有上限的退避间隔，离开页面后停止连接；没有实际业务需求时，轮询可能比自己维护这套恢复逻辑更合适。
