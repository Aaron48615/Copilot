# 刷新和缓存怎么取舍？

## 核心回答

1. 每类指标能接受多大延迟，先确认，再决定怎么刷新。当天订单概览和已经结算的月度趋势，不需要同一频率。刷新更快，也不代表源数据更新更快。页面应说明数据更新时间，别制造实时的错觉。

2. 变化不频繁的卡片可以轮询，而且等本轮结束再安排下一轮，慢请求别持续堆积。页面隐藏时暂停不必要的刷新，恢复可见后再查数据过没过期。确实需要及时推送，再评估连接维护和断线恢复的成本。

3. 缓存键包含数据源、指标、筛选条件、时间范围，以及用户所属的数据范围。同样查本月金额，不同租户的结果不能复用。权限变了或退出登录，相关缓存也要清。别只按卡片编号取数据。

4. 用户切换筛选条件时，取消旧请求，用请求序号拦住旧结果写回。序号在条件变化时就要更新，别等下一次请求发出才更新。成功、失败、加载结束都要检查，旧请求别把新请求的加载提示关掉。

5. 普通刷新失败，可以保留同一查询下最后一次成功的数据，同时展示过期状态和重试入口。首次加载失败就显示错误。切到新条件之后，别无提示地沿用旧条件的数据。页面看起来正常，数字却在回答另一个问题。

## 追问：多个卡片查同一份数据，怎么避免重复请求？

1. 查询条件先规范化，再用完整查询键识别相同请求。同一个时间范围要用一致的时区和边界表示，筛选数组也约定顺序。只是字段排列不同，别被当成两次不同查询。

2. 正在进行的相同请求，可以让多个卡片订阅同一个结果，成功后再各自转成需要的图表数据。某张卡片卸载只解除它的订阅，别直接取消所有卡片共用的请求。没有订阅者了，再考虑取消。

3. 共享的前提是查询语义和权限范围相同。别为了省请求把不同口径强行合并。一个接口若返回多个指标，局部失败怎么表示也要约定。单个指标异常，别让原本独立的卡片一起不可用。

## 追问：实时推送断线以后，怎样判断数据有没有漏？

1. 推送的是完整快照还是增量事件，先确认。快照可以用最新版本替换旧数据，增量则需要事件标识或连续序号。只收到变化量，却不知道中间漏了多少条，直接继续累加会得到错误结果。

2. 重连时优先按服务端支持的游标补齐事件，并按标识去重，避免重复计算。服务端不支持补发，或者游标已经过期，就重新拿完整快照，再从跟快照对应的位置继续收更新。

3. 断线期间显示连接状态和最后更新时间，恢复过程也不能悄悄当成一直在线。重连用有上限的退避间隔，离开页面后停止连接。没有实际业务需求时，轮询可能比自己维护这套恢复逻辑更合适。
