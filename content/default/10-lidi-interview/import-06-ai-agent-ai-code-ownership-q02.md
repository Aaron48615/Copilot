# 构建通过，就能说明代码没问题吗？

## 核心回答

1. 不能。构建通过只说明这条构建流程没失败，不等于代码行为都对。还要看脚本实际跑了什么。Vite 转 TypeScript 本身不做类型检查，脚本另外接了检查步骤，才包含那一块。

2. 类型检查主要约束代码里的静态关系，业务要求有没有实现，它判不了。预算上限写错、商品详情跳到了另一个商品，类型照样可能过。得给出输入和预期结果，再对实际行为。

3. 网络数据还有运行时边界，接口可能缺字段、给空列表、给不同类型。把响应写成某个 TypeScript 类型，不会自动验证它。页面会不会报错、异常怎么提示，要用实际响应或者受控样例来查。

4. 这次改了什么，就选对应的验证。纯转换看输入输出，组件交互看加载和错误状态，页面流程看真实导航。导购还要把接口失败和正常无商品分开，两者都没展示卡片，处理结果不一定一样。

5. 报结果时，构建、类型检查、哪些业务场景过了，分开说。没跑的步骤别补成已通过。本地构建成功，能确认的是产物生成成功。部署环境、真实接口、推荐质量，各自还要验。

## 追问：为什么预算筛选错了，类型检查仍可能通过？

1. 价格和预算都是数字，代码把「小于等于」写成「大于等于」，类型上看仍然合法。类型系统知道它们能比，但不知道商品必须在预算内，这是另要表达的业务规则。

2. 准备低于预算、恰好等于、高于预算的商品，先明确边界包不包括等号。预期结果按需求手工定，别再调用被测筛选函数去算，不然同一个错会同时进实现和预期。

3. 价格单位和缺失值也要查。一个字段用元、另一个用分，都是数字也会算错。更明确的类型能少误用，接口转换和规则行为还是要验，类型检查当不了业务裁判。

## 追问：没有后端环境时，还能做哪些有效验证？

1. 用固定接口响应验前端的成功、空结果、错误、异常字段，并确认按钮和提示状态。模拟数据要符合已经确认的约定。别为了让页面好看，只造一份永远完整的理想响应。

2. 也可以控制两次响应谁先回来，看旧结果会不会盖住新结果，再验从商品卡片进详情用的标识。前端能控制的行为，在这层就能覆盖，比等到联调才第一次碰到慢请求更容易定位。

3. 模拟接口通过，证明不了真实鉴权、后端预算筛选、线上数据是对的。还要联调的项目单独标出来，后端可用了再用真实请求补。别把「前端模拟验证通过」写成「完整功能已经验证通过」。
