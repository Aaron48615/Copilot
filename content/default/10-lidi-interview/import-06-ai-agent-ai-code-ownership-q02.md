# 构建通过，就能说明代码没问题吗？

## 核心回答

1. 不能，构建通过只能说明相应构建流程没有失败，不等于所有代码行为正确。我还会先看脚本实际执行了什么，例如 Vite 的 TypeScript 转译本身不做类型检查，只有脚本另接了检查步骤，才包含那部分验证。

2. 类型检查也主要约束代码中的静态关系，不能判断业务要求是否实现。比如预算上限写错、商品详情跳到了另一个商品，这些代码完全可能类型正确，所以必须给出输入和预期结果，再核对实际行为。

3. 网络数据还有运行时边界，接口可能返回缺字段、空列表或不同类型的数据。把响应写成某个 TypeScript 类型不会自动验证它，页面是否会报错、怎样提示异常，需要用实际响应或受控样例来检查。

4. 我会按这次改动选择验证层次，纯转换逻辑看输入输出，组件交互看加载和错误状态，页面流程看真实导航。导购功能还要区分接口失败和正常无商品，不能因为两者都没展示卡片，就认为处理结果一样。

5. 报告结果时，我会准确说构建、类型检查和哪些业务场景通过，没运行的步骤不补成已通过。如果只是本地构建成功，我能确认的是产物生成成功，部署环境、真实接口和推荐质量仍然需要各自的验证。

## 追问：为什么预算筛选错了，类型检查仍可能通过？

1. 假设价格和预算都用数字表示，代码把“小于等于”写成“大于等于”，从类型上看仍然合法。类型系统知道它们可以比较，但并不知道商品必须在预算内，这是需要额外表达的业务规则。

2. 我会准备低于预算、恰好等于预算和高于预算的商品，并先明确边界是否包含等号。预期结果要依据需求手工确定，不能再调用被测筛选函数计算，否则同一个错误会同时进入实现和预期。

3. 还要检查价格单位和缺失值，例如一个字段用元、另一个用分，即使都是数字也会算错。能用更明确的类型减少误用当然有帮助，但接口转换和规则行为依然要验证，不能把类型检查当成业务裁判。

## 追问：没有后端环境时，还能做哪些有效验证？

1. 我可以用固定接口响应验证前端的成功、空结果、错误和异常字段分支，并确认按钮与提示状态。模拟数据要符合已经确认的约定，不能为了让页面正常展示，就只构造一个永远完整的理想响应。

2. 也可以控制两次响应的返回顺序，检查旧结果是否覆盖新结果，并验证从商品卡片进入详情的标识。这样的测试覆盖前端可控制的行为，比等到联调时才第一次遇到慢请求更容易定位问题。

3. 但模拟接口通过，不能证明真实鉴权、后端预算筛选或线上数据正确。我会明确标记仍需联调的项目，后端可用后再用真实请求补齐，不能把“前端模拟验证通过”写成“完整功能已经验证通过”。
