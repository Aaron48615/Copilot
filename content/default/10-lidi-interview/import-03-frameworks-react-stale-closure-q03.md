# 请求返回顺序怎么处理？

## 核心回答

1. 请求乱序和闭包旧值有关系，但不是同一件事。每次请求都拿到当时正确的参数，先发出去的仍可能后回来。两个回调各自读的输入都对，无条件写入同一份状态，照样会盖。

2. 先确认业务是不是只要最新结果。搜索、详情切换一般是。每次请求给一个递增编号，回来时只允许当前编号写入。每个操作都必须留结果，比如批量上传，就按任务编号分别管。

3. Effect 驱动的请求，每一次执行自己带有效标记，清理时让旧的失效。支持 `signal` 的再配合取消，少浪费。取消不是把服务器上已经做完的业务撤回。修改类接口还要另一套幂等和状态确认。

4. 成功、错误、loading 都属于同一次请求。旧请求失败不能盖住新请求的成功；旧请求结束也不能提前关掉新请求的加载提示。判断只写在 `setData` 前面，这类问题第一眼不容易看出来。

5. 用能控制完成顺序的模拟请求来验证：先完成新的，再完成旧的；失败和卸载也补上。网络面板里取消成功是证据，还要证明旧回调不会改当前界面。封装库可能在网络完成之后还做异步转换，这一段也要管到。

## 追问：多个文件同时上传，也应该只接受最后一个响应吗？

1. 不该。每个文件是独立任务，早发出去的文件后完成，仍是有用的结果。一个全局最新编号会丢掉其他文件的成功，文件其实已经传上去了，界面却一直在等或显示失败。

2. 每个文件一个任务编号，各自记进度、错误、服务器返回的文件标识。重试某一个时，给这个任务加尝试版本，旧尝试不能盖新尝试。其他任务照样自己完成，不受最后一次点击影响。

3. 测试里让不同文件交错成功、失败，取消只影响对应那一个。并发策略看「哪些结果画在同一个位置」。搜索框只要最新结果，那套不能当所有请求的通用答案。

## 追问：请求取消了，服务器上的修改是不是也取消了？

1. 不一定。浏览器取消等待，保证不了服务器还没收到、还没执行。提交保存后立刻离开页面，客户端显示取消了，服务器仍可能已经保存成功。取消异常不能直接解释成操作一定没发生。

2. 重要修改靠业务接口确认结果，必要时用幂等标识防止重试做成两笔。前端回到页面可以重新查最新状态，把确认过程说清楚。别凭一次断开的连接自己决定恢复成旧数据。

3. 读请求取消和写请求取消，给用户的反馈不一样。搜索取消通常悄悄忽略就行；支付、保存状态不明，要提示去查进度。已经确认失败，和结果还不确定，界面上要能分开。结果没确认时，别让用户不停重复提交。
