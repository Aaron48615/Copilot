# 请求返回顺序怎么处理？

## 核心回答

1. 请求乱序和闭包旧值有关联，但不是同一个问题。即使每次请求都拿到正确的当前参数，先发出的请求也可能后返回；两个回调分别读取了自己的正确输入，仍可能因为无条件写入同一状态而产生覆盖。

2. 我会先确认业务是否只保留最新结果。搜索和详情切换通常符合这个要求，可以给每次请求分配递增编号，返回时只允许当前编号提交；如果每个操作都必须保留，例如批量上传，就应按任务编号分别管理结果。

3. Effect 驱动的请求可以使用每次执行独立的有效标记，清理时让旧执行失效。支持 signal 的请求再配合取消，减少浪费；取消不是撤回服务器上已经完成的业务操作，所以修改类接口还需要另一套幂等和状态确认设计。

4. 成功结果、错误和 loading 都要属于同一个请求上下文。旧请求失败不能盖住新请求的成功，旧请求结束也不能提前关闭新请求的加载提示；判断只放在 setData 前面，会留下这些不容易第一眼发现的问题。

5. 我会用可控制完成顺序的模拟请求验证，先完成新请求再完成旧请求，并补上失败和卸载。网络面板中取消成功是有用证据，但还应证明旧回调不会修改当前界面，尤其是封装库可能在网络完成后继续做异步转换的情况。

## 追问：多个文件同时上传，也应该只接受最后一个响应吗？

1. 不应该，上传的每个文件都是独立任务，早发出的文件后完成仍是有价值的结果。简单使用一个全局最新编号会丢掉其他文件的成功状态，让用户看到文件实际上传了，界面却一直显示等待或失败。

2. 可以给每个文件分配任务编号，分别记录进度、错误和服务器返回的文件标识。重试某个文件时再给该任务增加尝试版本，旧尝试不能覆盖新尝试，而其他任务仍独立完成，不受最后一次点击影响。

3. 我会在测试中安排不同文件交错成功和失败，检查取消只影响对应任务。并发策略应由“哪些结果属于同一显示位置”决定，不能把搜索框的最新结果策略当成所有请求的通用答案。

## 追问：请求取消了，服务器上的修改是不是也取消了？

1. 不一定，浏览器取消等待通常无法保证服务器还没收到或还没执行请求。比如提交保存后立刻离开页面，客户端显示取消，服务器仍可能已经保存成功，因此不能把取消异常直接解释成操作一定没有发生。

2. 重要修改要通过业务接口确认结果，必要时使用幂等标识防止重试造成重复执行。前端返回页面时可以重新查询最新状态，给出明确的确认过程，而不是凭一次断开的连接自行决定恢复旧数据。

3. 我会区分读取取消和写入取消的用户反馈。搜索取消通常静默忽略即可，支付或保存状态不明则需要提示查询进度；我会让界面区分已经确认失败和结果尚不确定，避免用户在没有确认结果时不断重复提交。
