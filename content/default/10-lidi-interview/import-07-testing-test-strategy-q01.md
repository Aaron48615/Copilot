# 为什么不直接写 E2E？

## 核心回答

1. E2E 要留，但不会把所有规则都塞进去。浏览器启动、环境准备、跨服务交互都有成本。金额计算有很多边界，每个输入都先登录、搜索再下单，反馈会慢，也很难一下判断是公式错了，还是准备数据失败。

2. 纯函数适合用单元测试穷举重要输入，组件测试适合验表单错误和按钮变化。环境更小，失败更容易定位。同样是优惠门槛错了，在函数层看到输入输出，通常比回放完整购物流程更直接。

3. E2E 的价值是看不同部分实际能不能配合：路由跳转、登录状态、请求配置接不接得上。这些问题单测全过也可能还在。所以选登录、关键提交这类少量高价值流程，查真正的页面行为和业务结果。

4. 选哪层测试，也看故障发生在哪。浏览器布局挡住按钮，需要真实浏览器交互才能有效复现。服务端接口字段不一致，就要覆盖接口边界。单独 mock 一个永远正确的数据对象不够。

5. 判断依据是能发现什么问题，以及运行和维护要付多少成本，不是强行凑某个数量比例。时间有限，先保护用户最依赖的路径，再把规则分支补到较低层。改一句文案会不会让整套 E2E 失效，还取决于定位和断言怎么设计。

## 追问：一个线上缺陷应该补在哪一层测试？

1. 触发缺陷的最小条件先找出来。价格格式化把零显示成空，可以直接给格式化函数或组件传零。这个最小测试已经能稳定失败，修好之后它就能低成本保护同一问题，不必每次都完整创建订单。

2. 错误来自连接关系，比如组件取错接口字段，只测格式化函数复现不了，就补组件和请求适配的集成测试。先让测试在修复前确实失败，再确认失败原因对得上原缺陷。写出一条无论代码修没修都能过的测试，没有用。

3. 涉及路由守卫、浏览器行为、真实部署配置，再用 E2E 保护相关路径。同一缺陷可以有两层测试，各自覆盖不同风险。完全相同的输入输出重复三遍，通常只增加维护量，发现能力上不去。

## 追问：项目时间紧，只能先写少量测试怎么办？

1. 先列用户最常用、出错影响最大、最近改得勤的功能，从里面挑一条核心流程做冒烟。比如必须登录才能提交的表单，至少确认有权限能提交、没权限不会误进成功状态。覆盖率数字先不追求漂亮。

2. 容易写错、又能独立验证的规则，补小测试。比如分页参数、金额边界、请求错误映射。这类准备成本通常较低，边开发边跑也方便。复杂环境下的非关键分支记成后续补充，别宣称已经全覆盖。

3. 人工验过什么、自动化保护了什么，说清楚，尚未验证的风险也留着。后面要补，优先补实际出现过的缺陷，以及核心流程的失败恢复。再根据维护成本决定要不要扩大 E2E，别一次搭一个很重的测试平台。
