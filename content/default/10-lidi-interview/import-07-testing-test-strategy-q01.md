# 为什么不直接写 E2E？

## 核心回答

1. 我会保留 E2E，但不会把所有规则都放进去，因为浏览器启动、环境准备和跨服务交互都有成本。比如金额计算有很多边界，如果每个输入都要先登录、搜索再下单，反馈会慢，也很难一下判断是公式错了还是准备数据失败。

2. 纯函数适合用单元测试穷举重要输入，组件测试适合验证表单错误和按钮变化。它们提供的环境更小，失败更容易定位；同样是优惠门槛错误，在函数层看到输入和输出，通常比回放完整购物流程更直接。

3. E2E 的价值是检查不同部分实际能否配合，比如路由跳转、登录状态和请求配置是否接得上。这些问题单测即使全部通过也可能存在，所以我会选登录、关键提交等少量高价值流程，检查真正的页面行为和业务结果。

4. 选择哪层测试也要看故障发生在哪里，不能规定所有问题都必须从单测补起。浏览器布局遮挡按钮，需要真实浏览器交互才能有效复现；服务端接口字段不一致，则需要覆盖接口边界，单独 mock 一个永远正确的数据对象不够。

5. 我的判断依据是能发现什么问题，以及运行和维护要付出多少成本，不是强行满足某个数量比例。时间有限时先保护用户最依赖的路径，再把规则分支补到较低层；也不能笼统说改一句文案必然让整套 E2E 失效，那还取决于定位与断言设计。

## 追问：一个线上缺陷应该补在哪一层测试？

1. 我会先找到触发缺陷的最小条件。例如价格格式化把零显示为空，可以直接给格式化函数或组件传零；如果这个最小测试已经能稳定失败，修复后它就能低成本保护同一问题，不必每次都完整创建订单。

2. 如果错误来自连接关系，比如组件取错接口字段，只测格式化函数无法复现，我会补组件与请求适配的集成测试。先让测试在修复前确实失败，再确认失败原因对应原缺陷，避免写出一条无论代码是否修复都能通过的测试。

3. 涉及路由守卫、浏览器行为或真实部署配置时，再用 E2E 保护相关路径。同一缺陷可以有两层测试，但各自应覆盖不同风险；把完全相同的输入输出重复三遍，通常增加维护量，却没有带来同等的发现能力。

## 追问：项目时间紧，只能先写少量测试怎么办？

1. 我会先列用户最常用、出错影响最大且最近改动频繁的功能，选其中一条核心流程做冒烟检查。比如一个必须登录才能提交的表单，至少确认有权限能提交、没权限不会误进入成功状态，不用先追求漂亮的覆盖率数字。

2. 对容易写错又容易独立验证的规则补小测试，例如分页参数、金额边界和请求错误映射。这类测试通常准备成本较低，也方便我边开发边运行；复杂环境下的非关键分支可以记录为后续补充，而不是宣称已经全覆盖。

3. 我会把人工验证过什么、自动化保护了什么说清楚，并保留尚未验证的风险。如果继续完善，我会优先补实际出现过的缺陷和核心流程的失败恢复，再根据维护成本决定是否扩大 E2E，而不是一次搭一个很重的测试平台。
