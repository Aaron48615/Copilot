# 如何验证它真的工作？

## 核心回答

1. 我会先写清楚最小实现的承诺：普通对象、同步执行、相同值不触发，以及动态依赖清理。测试围绕这些可观察行为，使用运行次数和计算结果断言。例如分支切换以后，旧分支的依赖应该解除，接着修改旧分支里的字段不应该让计算再次运行。

2. 第一组验证订阅是否准确：初次 effect 执行一次，修改已读取属性再执行一次，修改未读取属性则保持次数。还要用两个对象的同名属性检查隔离，避免依赖表只按 key 保存而把互不相关的数据绑在一起。

3. 第二组专门验证条件分支，既看当前结果，也看过期属性能否停止触发。只断言最终字符串可能漏掉多余执行，下面的同步用例同时检查两者。

    ```js
    const s = reactive({ ok: true, a: 1, b: 2 });
    let runs = 0, result;
    effect(() => { runs++; result = s.ok ? s.a : s.b; });
    s.ok = false;
    s.a = 9;
    expect(runs).toBe(2);
    expect(result).toBe(2);
    s.b = 3;
    expect(runs).toBe(3);
    expect(result).toBe(3);
    ```

4. 第三组检查执行上下文，包括嵌套 effect 后外层继续读取，以及执行途中抛错后新建 effect 是否正常。递归保护用有次数上限的例子验证，防止错误实现把测试进程卡死；停止订阅则检查 stop 后赋值不再自动执行。

5. 扩展功能应单独增加测试，不能拿同步版次数去要求有批处理的版本。如果加入嵌套代理、数组或 computed，我会分别检查代理身份、长度变化和缓存失效；没有实现的能力应标注边界，不能把跳过的用例当作通过。

## 追问：怎样验证调度器把多次修改合并成一次执行？

1. 我会先确定调度器约定为同一轮同步代码中的任务去重，放到一个微任务里刷新。注册 effect 后连续修改两个依赖，此时先断言结果还没刷新，等待约定的刷新入口后再断言只新增一次运行。

2. 刷新后的结果还要读取到两个属性的最终值，不能只检查次数。比如先改价格、再改数量，最终总价必须由新价格和新数量计算；若调度时错误保存了旧值，次数正确也不能说明行为正确。

3. 还会检查刷新期间加入任务，以及 stop 时已有任务等待执行的情况。测试应等待实现提供的 flush Promise 或明确的微任务机制，不随便睡几十毫秒；若任务会递归入队，就要额外验证终止条件和错误报告。

## 追问：怎样证明嵌套 effect 没有污染外层依赖？

1. 我会设计一个外层 effect，先执行已创建的内层 runner，再读取外层属性。内层只读取另一项数据，改变外层属性应重跑外层；如果 active 被直接清空，内层之后的外层读取就无法完成收集。

2. 随后只改变内层属性，检查内层更新而外层次数不变，这能发现依赖误归属。用预先创建的 runner 是为了避免每次外层执行都新建订阅者，否则测试同时混入了 effect 生命周期问题，很难判断失败原因。

3. 最后让内层在一次执行中抛错，并在外层用 try/catch 接住后继续读取。外层仍应建立自己的依赖，这能检查恢复是否写在 finally；只测正常返回，无法暴露异常路径留下错误执行上下文的问题。
