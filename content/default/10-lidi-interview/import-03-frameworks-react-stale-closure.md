# React 的 stale closure 是什么，怎么处理？

## 核心回答

1. stale closure 是：回调读的还是创建它那一次渲染的值，而这件事实际需要更新之后的值。函数组件每次执行都有自己那份 props 和 state。定时器、事件订阅、Promise 存了旧回调，组件再渲染一次，里面的变量不会自己换成新的。

2. 空依赖 Effect 建一个计数器，回调一直 `setCount(count + 1)`，可能始终用初始的 count。闭包没写错，是我们想持续加一，计算依据却钉在第一次渲染。这种用函数式更新更对。

3. 处理方法看目的。某个值变了就该重新订阅，把 Effect 依赖补全。只根据前一个状态更新，用函数式 setter。外部回调必须保持这份订阅、但又要读最新值，再考虑 ref，或者适用版本里的 Effect Event。别一律写成空数组。

4. `useCallback` 只缓存函数引用，不会自动刷新闭包，依赖漏写一样是旧值。请求竞态还要单独处理：参数都对的两次请求也可能乱序回来。取消加上有效性判断，当前界面只收对得上的那次结果。

5. 先分清这件事该记住当时值，还是必须读最新值。点发送时确定的收件人，往往就该留那一次的快照。一律改成最新 ref，等待期间切了联系人，消息可能发给别人。不是所有旧值都是 bug。

## 追问：异步回调读取当时的 state，什么时候反而是正确的？

1. 它代表一次已经确定的用户操作时，留当时值往往更合理。点了给联系人 A 发提醒，等待时用户切到 B，这次提醒仍该是 A。回调总读最新联系人，操作对象就换了。

2. 在事件里把必要数据抽成操作参数，比如收件人编号和消息内容，再交给异步流程。操作跟页面后面怎么切分开。读代码也能看出这个任务属于谁，不必依赖一个随时在变的全局变量。

3. 要跟着变的是展示归属：A 的结果回来时，页面已经在显示 B，别直接写进 B 的详情。按任务或联系人把结果存起来，再由当前选择决定展示。操作快照和界面竞态分开处理。

## 追问：怎么排查一个偶尔读到旧值的事件监听？

1. 记下监听是哪一次提交后建的、抓住了哪些数据、状态变了有没有换掉。窗口 `keydown` 只在挂载时注册，处理逻辑却读当前选中项，选中变了仍可能操作第一次那一项。

2. 再看清理函数卸的是不是同一个引用。旧监听没删、新的又加上，一次按键会分别用新旧两份状态。最新函数打印是对的还不够，页面上有没有残留回调一起跑也要确认。

3. 修好之后验证：连续改选择、反复进入退出、快速按键。依赖变了重新注册，或由一份稳定订阅读最新信息，都可以。说清楚为什么选这种，以及哪些变化仍必须让外部资源重建。
