# React 的 stale closure 是什么，怎么处理？

## 核心回答

1. stale closure 指回调仍然读取创建它时那次渲染的值，而业务实际需要更新后的值。函数组件每次执行都有自己的 props 和 state，定时器、事件订阅或 Promise 保存了旧回调后，不会因为组件又渲染一次就自动替换其中的变量。

2. 例如空依赖 Effect 建立计数器，回调一直执行 setCount(count + 1)，它可能始终使用初始 count。这里闭包本身没有出错，问题是我们想持续递增，却把计算依据固定在第一次渲染；函数式更新更符合这个需求。

3. 处理方法要根据目的选择。某个值变化应该重新订阅，就补全 Effect 依赖；只根据前一状态更新，就用函数式 setter；外部回调必须保持订阅但读取最新值时，再考虑 ref 或适用版本中的 Effect Event，而不是统一使用空数组。

4. useCallback 只缓存函数引用，不能自动刷新闭包，依赖漏写同样会产生旧值。请求竞态还需要独立处理，因为参数正确的两个请求也可能乱序返回；要通过取消和有效性判断保证当前界面只接受对应结果。

5. 我会先区分“应该记住当时值”还是“必须读取最新值”。点击发送时确定的收件人，可能就应该保留那次操作的快照；如果一律改成最新 ref，等待期间切换联系人反而可能把消息发给别人，不能把所有旧值都当成错误。

## 追问：异步回调读取当时的 state，什么时候反而是正确的？

1. 当它代表一次已确定的用户操作时，保留当时值往往更合理。例如点击给联系人 A 发送提醒，等待期间用户切到 B，这次提醒仍应对应 A；如果回调总读取最新联系人，就改变了原操作的对象。

2. 我会在事件里提取必要数据形成操作参数，例如收件人编号和消息内容，再把参数交给异步流程。这样操作与页面后续变化分开，阅读代码也能清楚知道任务属于谁，而不是依赖某个随时变化的全局变量。

3. 需要变化的是展示归属：A 的结果返回时，如果页面已显示 B，不应直接写进 B 的详情区域。可以按任务或联系人缓存结果，再由当前选择决定展示，分别解决操作快照和界面竞态，避免混为一谈。

## 追问：怎么排查一个偶尔读到旧值的事件监听？

1. 我会记录监听在哪次提交后建立、捕获哪些数据，以及状态变化后是否替换。比如窗口 keydown 监听只在挂载时注册，但处理逻辑读取当前选中项，就很容易在选择变化后仍操作第一次的项目。

2. 再检查清理函数是否移除相同引用，防止旧监听没删而新监听又加上，导致同一次按键分别使用新旧两份状态。只看最新函数打印正确不够，还要确认页面上没有其他残留回调一起执行。

3. 修复后验证连续改变选择、重复进入退出和快速按键。依赖变化时重新注册，或由稳定订阅读取最新信息，都可以是合理方案；我会说明为何选择它，以及哪些变化仍必须导致外部资源重新建立。
