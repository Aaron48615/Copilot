# Vue 组件和异步交互测试怎么写？

## 核心回答

1. 我会优先围绕用户能观察到的行为测试组件，例如输入搜索词、点击提交、显示加载和返回结果，而不是断言某个内部 ref 一定叫什么。这样重构内部实现时，只要接口和交互不变，测试仍然有价值，不会变成代码结构的另一份抄写。

2. 组件测试需要提供必要的 props、插槽和注入环境，接口和不可控外部服务可以替换为可控制的模拟。输入通过 setValue，点击通过 trigger，输出检查文本、属性和 emitted 事件，避免只调用内部方法而漏掉模板绑定错误。

3. 异步等待要分清来源：Vue DOM 更新等 nextTick 或相关挂载工具方法，接口 Promise 先由测试完成并推进回调，定时器使用假时钟。不能用一个固定 setTimeout 覆盖所有情况，机器变慢后这种测试很容易不稳定。

4. 我会覆盖成功、失败、空结果和快速连续操作，尤其让旧请求后返回，确认不会覆盖当前条件。组件卸载时验证监听、轮询和迟到回调停止；KeepAlive 的停用与最终销毁分开测，不能只在普通挂载卸载流程中推断缓存行为。

5. 不同层级的测试各有范围：纯计算适合单元测试，组件集成验证通信，真实浏览器更适合焦点、布局、滚动和路由操作。运行环境模拟不了真实布局时要明确边界，不能因为虚拟 DOM 环境测试通过，就断言弹窗定位或虚拟列表滚动一定正确。

## 追问：为什么不建议只给整个组件做大快照测试？

1. 大快照能记录输出结构，但很多变化只是样式类名或包装层调整，差异过多时评审容易直接更新快照。它也未必解释具体业务哪里出错，例如按钮仍存在，却在提交中没有禁用，读整段快照不如明确断言清楚。

2. 我会对重要行为写针对性断言：提交时按钮不可重复操作，失败后草稿保留，成功后发出正确事件。小而稳定的展示片段可以使用快照补充，但不把全部交互逻辑都交给一次大字符串比较。

3. 测试应该帮助定位问题而不是只提醒“页面变了”。如果重构后大量无关快照一起变化，需要考虑断言是否过度绑定内部结构，保留有意义的用户契约，才能让测试在长期维护中继续被认真阅读。

## 追问：哪些组件行为必须用真实浏览器再验证？

1. 依赖真实布局和绘制的行为需要额外关注，例如元素高度、滚动恢复、拖拽和弹窗位置。模拟 DOM 环境常常没有完整布局计算，读取尺寸可能都是默认值，测试通过只能说明代码路径没有失败，不能证明视觉效果正确。

2. 键盘焦点、输入法组合、原生表单约束和路由前进后退也适合浏览器验证。可以针对关键用户路径写少量测试，而不是把所有单元用例都搬到浏览器中运行，后者成本较高且定位失败可能更慢。

3. 我会让组件测试先覆盖状态和事件，再用浏览器测试确认无法模拟的实际行为，例如关闭弹窗后焦点返回按钮。这样两类证据互补，既能快速发现逻辑回归，也不会对测试环境没有提供的能力作过度承诺。
