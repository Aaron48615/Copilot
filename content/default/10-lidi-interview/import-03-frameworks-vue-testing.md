# Vue 组件和异步交互测试怎么写？

## 核心回答

1. 围着用户能看见的行为测：输入搜索词、点提交、出现加载、返回结果。别断言某个内部 `ref` 一定叫什么。以后内部实现改了，接口和交互还在，测试仍有用，不会变成另一份代码结构抄写。

2. 组件测试把需要的 props、插槽、注入环境备好，接口和不可控的外部服务换成能控制的模拟。输入用 `setValue`，点击用 `trigger`，输出查文本、属性、`emitted` 事件。只调内部方法，模板绑错了测不出来。

3. 异步等待分来源：Vue DOM 更新等 `nextTick` 或挂载工具提供的方法；接口 Promise 由测试完成并推进回调；定时器用假时钟。一个固定 `setTimeout` 盖所有情况，机器一慢测试就飘。

4. 成功、失败、空结果、快速连点都要有，尤其让旧请求后回来，确认盖不住当前条件。组件卸载时看监听、轮询、迟到回调停没停。`KeepAlive` 的停用和最终销毁分开测，不能只从普通挂卸推断缓存行为。

5. 层级不同范围不同：纯计算走单元测试，组件集成看通信，真实浏览器更适合焦点、布局、滚动、路由操作。运行环境模拟不了真实布局时，边界要说清。虚拟 DOM 环境过了，不能据此说弹窗定位、虚拟列表滚动一定对。

## 追问：为什么不建议只给整个组件做大快照测试？

1. 大快照能记下输出结构，很多变化只是样式类名或包一层，差异一多评审容易直接更新快照。它也说不清具体业务哪里错：按钮还在，提交中却没禁用，读整段快照不如明确断言。

2. 重要行为写针对性断言：提交时按钮不能连点，失败后草稿还在，成功后发出正确事件。小而稳的展示片段可以用快照补一眼，别把全部交互逻辑交给一次大字符串比较。

3. 测试该帮人定位，不是只喊“页面变了”。重构后大量无关快照一起变，看看是不是把内部结构绑得太死。留下有意义的用户约定，长期才有人认真看这些测试。

## 追问：哪些组件行为必须用真实浏览器再验证？

1. 依赖真实布局和绘制的，要额外看：元素高度、滚动恢复、拖拽、弹窗位置。模拟 DOM 常常没有完整布局计算，读到的尺寸可能是默认值。测试过了只说明代码路径没炸，证明不了视觉效果。

2. 键盘焦点、输入法组合、原生表单约束、路由前进后退，也适合浏览器验证。关键用户路径写少量就行，别把所有单元用例都搬进浏览器，成本高，失败了定位也更慢。

3. 组件测试先覆盖状态和事件，浏览器测试确认模拟不了的实际行为，比如关弹窗后焦点回到按钮。两类证据互补：逻辑回归能较快发现，也不会对测试环境没有的能力过度承诺。
