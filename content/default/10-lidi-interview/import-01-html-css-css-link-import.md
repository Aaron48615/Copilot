# link 和 @import 引入 CSS 有什么区别？

## 核心回答

1. link 是 HTML 元素，使用 rel="stylesheet" 可以引入样式表；@import 是 CSS 规则，用来从样式中引入另一份样式。两者最终都可能参与样式层叠，但发现资源的时机和组织方式不同，不能简单理解为一个能用、另一个已经失效。

2. 外部样式中的 @import 通常需要浏览器先获得并解析包含它的 CSS，才能发现后续资源，因此容易形成请求依赖链。直接出现在 HTML 中的 link 更容易被解析器或预加载扫描器及早发现；不过 import 并不是一定等整个页面加载完成才开始下载。

3. 加载早晚也不直接决定谁覆盖谁，样式生效仍看层叠规则与源码顺序。@import 还有允许出现的位置等语法限制，需要写在样式表前部合适的位置。首屏关键样式若层层导入，网络往返可能增加，排查时应看请求瀑布而不是只比较语法长短。

4. 工程中还要区分浏览器的 CSS @import 和构建工具处理的模块导入。有些引用会在构建时展开，有些保留到产物中；Sass 也有自己的模块机制。我会检查最终 CSS 和 HTML，确定用户浏览器实际发起哪些请求，再判断是否需要调整组织方式。

5. 资源路径也是检查点，样式中的相对地址通常以该样式表地址为基准。移动或合并文件后，背景图和字体路径可能需要由工具重写，样式文件成功加载并不代表其内部引用的资源也都还能正确找到。

## 追问：CSS 后下载完成就一定覆盖先下载的 CSS 吗？

1. 不是，网络完成顺序不等于层叠顺序。两条普通声明在同一来源和层中竞争时，还要比较选择器优先级，条件相同再看样式表中的顺序；浏览器不会因为某个文件网络更慢，就临时提高它的权重。

2. 我会先查看元素面板中具体哪条规则获胜，再回到 HTML 的 link 顺序和导入位置解释原因。动态插入样式确实可能改变文档中的顺序，但那是插入位置和规则变化导致的，不是下载耗时本身决定。

3. 因此不能依靠人为延迟加载来“保证覆盖”。想明确控制基础样式与业务覆盖，可以整理层叠层、选择器和文件顺序，再用最终产物验证，避免开发环境碰巧正常、打包后顺序不同就出现样式偏差。

## 追问：怎么判断 @import 是否造成了首屏请求瀑布？

1. 我会在网络面板关闭缓存后重新加载，查看关键 CSS 的发起者和开始时间。如果第二份 CSS 由第一份 CSS 发起，而且必须等前者可解析后才被发现，就能看到相应依赖关系，而不只是两条并排请求。

2. 接着确认这些样式是否首屏必需、是否存在多层导入，以及构建后能否合并或提前通过 link 引入。不能看到 import 就全部改写，因为开发源文件里的导入可能已经被工具展开，浏览器并没有实际多发请求。

3. 修改后比较同样条件下的资源发现时间和首屏显示，并检查媒体条件、层叠顺序有没有被改变。减少请求依赖应建立在样式行为保持正确的基础上，不能为了数字更好看把页面所需样式延后到闪烁出现。
