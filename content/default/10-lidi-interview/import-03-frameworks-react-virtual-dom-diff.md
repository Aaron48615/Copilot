# 虚拟 DOM 是什么？diff 是怎么工作的？

## 核心回答

1. 虚拟 DOM 可以理解为用 JavaScript 数据描述界面结构，包含元素类型、属性和子节点。组件根据当前状态产生描述，React 再比较前后结果，把需要的变化提交到真实 DOM；它不是浏览器 DOM 的完整复制，也不是每次直接重建整个页面。

2. React 使用适合界面更新的启发式协调规则，而不是对任意两棵树求理论最优编辑方案。同一位置类型变化时通常重建对应子树，类型相同则继续比较属性和子节点；列表通过 key 区分身份，避免仅按位置复用导致状态跟错数据。

3. 渲染计算和 DOM 提交要分开看。组件函数可以因为更新而重新执行，但最终描述相同就未必产生实际 DOM 修改；并发渲染中部分计算也可能被中断或放弃，所以不能在渲染期间发请求或修改外部对象来表达一次性动作。

4. 虚拟 DOM 的价值是让开发者用声明式方式组织复杂更新，并把组件状态和界面对应起来。它本身也有创建对象和比较的成本，不能说一定比直接 DOM 操作快；非常小而明确的更新，手写 DOM 完全可能更省工作。

5. 优化时我会先查看状态位置、组件计算和节点体量，再考虑 memo、稳定 props 或虚拟列表。稳定 key 保证身份延续，不等于组件绝不重新渲染；只背“差异比较很快”无法解释输入卡顿，仍需要结合真实的更新和浏览器性能记录判断。

## 追问：组件 render 执行了，为什么 DOM 可能完全没变？

1. render 只是计算想要什么界面。比如父组件的某个状态变化，让子组件再次返回相同的文本和属性，React 可以发现最终结果没有需要提交的差别，因此函数执行并不等于浏览器节点被重新创建。

2. 这也是为什么调试不能只用 console.log 次数判断性能。重复计算可能有成本，但实际 DOM 布局绘制是另一部分，应分别用 Profiler 和浏览器面板观察，才能知道优化应该针对哪一个阶段。

3. memo 可以帮助跳过某些不必要的组件计算，但即使没有 memo，React 也并非每次重建整棵 DOM。解释清楚这个关系，才能避免为了减少日志数量过度缓存，反而引入旧 props 或错误比较函数。

## 追问：同一个 key 从 input 换成 select，能保留原节点吗？

1. 通常不能，key 只是身份判断的一部分，元素或组件类型也需要对应。原生 input 和 select 类型不同，React 不能通过保留同一个 key 就把旧节点当作新类型使用，相关子树会按类型变化处理。

2. 如果切换输入方式仍要保留业务值，应把值存在更稳定的状态位置，再分别传给两种控件。不要把数据保留完全寄托在 DOM 复用上，尤其非受控输入和第三方组件重建时可能丢掉局部内容。

3. 我会验证切换后值、焦点和校验提示是否符合业务预期。有些切换本来就要求重置，有些要求转换格式，key 无法替我们决定这些规则，应在状态和事件设计中明确表达。
