# 虚拟 DOM 是什么？diff 是怎么工作的？

## 核心回答

1. 虚拟 DOM 可以理解成用 JavaScript 数据描述界面：类型、属性、子节点。组件按当前状态产出这份描述，React 再比较前后两次，把该改的提交到真实 DOM。它不是浏览器 DOM 的完整拷贝，也不是每次把整页拆了重建。

2. React 用的是适合界面更新的启发式规则，不是对任意两棵树求理论上最短编辑。同一位置类型变了，通常把对应子树重建；类型相同就继续比属性和子节点。列表靠 `key` 认身份，只按位置复用，状态可能跟错数据。

3. 渲染计算和 DOM 提交要分开看。组件函数因为更新可以再跑，最终描述一样，未必真去改 DOM。并发渲染里，一部分计算还可能被打断或放弃。所以渲染期间别发请求、别改外部对象来表达一次性动作。

4. 虚拟 DOM 的价值是用声明式的方式组织复杂更新，让组件状态和界面对上。它自己也有造对象、做比较的成本，不一定比直接操作 DOM 快。非常小、目标很明确的更新，手写 DOM 完全可能更省。

5. 优化先看状态放哪、组件里算了什么、节点有多少，再考虑 `memo`、稳住 props、虚拟列表。稳定 `key` 保证身份还在，不等于组件再也不渲染。只背「差异比较很快」解释不了输入卡顿，还是要结合真实更新和浏览器性能记录。

## 追问：组件 render 执行了，为什么 DOM 可能完全没变？

1. `render` 只是在算想要什么界面。父组件某个状态变了，子组件再次返回同样的文本和属性，React 可以发现最终没什么要提交。函数跑了，不等于浏览器节点被拆了重建。

2. 调试别只用 `console.log` 次数判断性能。重复计算可能有成本，真正的 DOM 布局绘制是另一段。Profiler 和浏览器面板分开看，优化才知道该动计算还是该动绘制。

3. `memo` 可以跳过某些不必再算的组件。就算没有 `memo`，React 也不是每次重建整棵 DOM。少几行日志就加很重的缓存，自定义比较再写漏，反而可能一直用旧 props。

## 追问：同一个 key 从 input 换成 select，能保留原节点吗？

1. 通常不能。`key` 只是身份的一部分，元素或组件类型也要对上。原生 `input` 和 `select` 类型不同，同一个 key 留不住旧节点当新类型用，相关子树会按类型变化来处理。

2. 切换输入方式还要留业务值，把值放在更稳的状态位置，再分别传给两种控件。数据别完全寄托在 DOM 复用上。非受控输入、第三方组件一重建，局部内容可能就没了。

3. 切换之后值、焦点、校验提示是否符合业务，要过一遍。有的切换本来就要重置，有的要转换格式。`key` 决定不了这些规则，在状态和事件里写清楚。
