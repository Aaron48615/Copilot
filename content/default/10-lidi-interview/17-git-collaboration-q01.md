# `merge` 和 `rebase` 有什么区别？

## 核心回答

1. merge 是把两条开发历史合到一起，如果双方已经分叉，通常会产生一个包含两个父提交的合并提交。原有提交关系得到保留，可以看出功能分支从哪里分出、什么时候合入，适合需要保留协作历史的情况。

2. 如果目标提交只是当前提交的后代，merge 默认可以直接快进分支指针，不一定产生新的合并提交。是否要求保留合并节点要看项目策略，所以不能把 merge 简化为“每次都新增一个提交”。

3. rebase 会把当前分支需要保留的提交重新应用到新的基点之后，通常形成一条更线性的历史。因为父提交等内容变了，重新生成的提交哈希通常也会改变，它并不是把原提交原样搬到另一个位置。

4. 比如我在个人功能分支开发期间，主分支又加入了修改，可以按团队规则选择合并主分支，或者把个人提交变基到新的主分支上。两种方式都可能发生冲突，rebase 还可能在重放不同提交时分别要求处理冲突。

5. 已经共享且有人基于它继续工作的分支，不应该为了历史整齐随意 rebase，因为别人仍然保留旧提交关系。我会先检查工作树、分支和协作情况，遵循仓库规则；这里讨论的是选择原则，不代表可以擅自改写远程历史。

## 追问：rebase 时反复冲突，是不是 Git 出问题了？

1. 不一定，rebase 往往按提交逐个重放，同一个文件可能在多个提交里被修改。前一个提交解决过冲突，后一个提交应用到新的上下文时仍可能再次冲突，这与一次性合并最终状态的过程不同。

2. 我会用 status 确认当前停在哪个阶段，再查看正在应用的提交和冲突上下文。解决后只暂存确认好的文件，再继续 rebase，不能因为同一文件反复出现就直接选择覆盖整份文件。

3. 如果发现基点选错或处理方向不清楚，可以按当前操作使用 rebase --abort 返回开始前的状态，再重新判断。skip 会跳过当前提交，可能丢掉需要的功能，不能把它当成通用的跳过冲突按钮。

## 追问：什么时候 merge 比 rebase 更合适？

1. 多人共同使用同一分支时，我会更重视保持已共享提交的稳定性。merge 可以接入另一条历史，同时保留已有提交身份，让其他人的分支不必因为我整理历史而重新对齐。

2. 如果项目希望保留功能合入的节点，合并提交也有价值，能把一组功能的进入时间表达清楚。反过来，个人尚未共享的小分支可以按规范考虑 rebase，减少开发过程中的无意义交叉。

3. 选择还取决于仓库最终合并策略，例如是否采用 squash，不能只按个人喜好决定。无论哪种方式，解决冲突后都要验证最终行为，历史看起来整齐并不能证明两边的功能正确结合。
