# 如何用浏览器工具定位一个接口慢？

## 核心回答

1. 我会先确认“接口慢”指点击后很久才发请求、请求本身耗时长，还是响应结束后页面才迟迟更新。在 Network 中记录目标请求的开始时间、总耗时和 Initiator，再与用户操作时间对齐，避免把前端等待算成服务端耗时。

2. 展开 Timing 后，可以区分排队、DNS、连接、发送请求、等待首字节和内容下载等阶段。连接复用或缓存命中时有些阶段不会出现，所以不能看到没有 DNS 时间就认定测量有问题。

3. 等待首字节时间长，可能涉及网络往返、代理排队和服务端处理，不能直接断定数据库慢。内容下载时间长则要结合响应体大小、压缩情况和网络条件判断，同样大小的数据在不同网络下耗时可能很不一样。

4. 我还会检查同一操作是否重复发请求、前一个请求是否一直挂着，以及业务请求之前是否有 OPTIONS 或其他依赖请求。搜索场景尤其需要看参数和返回顺序，慢的旧请求即使取消了，也要防止其后续处理覆盖新结果。

5. 浏览器证据能帮助缩小范围，但无法单独解释服务端内部耗时。我会整理脱敏的请求标识、时间、参数特点和 Timing，与后端日志或 Server-Timing 对照；如果响应已经结束，则继续用 Performance 检查解析、计算和渲染。

## 追问：Waiting 很长，能直接让后端优化 SQL 吗？

1. 不能，浏览器测到的等待首字节包含多个环节，SQL 只是服务端处理中的一种可能。我会先在相同网络下比较不同请求，确认是个别接口慢，还是所有请求都出现类似延迟。

2. 然后提供具体请求标识和时间，请后端查看网关、应用及数据库的对应记录。如果服务端提供 Server-Timing，也可以作为辅助，但仍要理解各字段覆盖的范围，不能把名字相近的时间简单相减。

3. 只有证据指向查询耗时，才讨论索引、查询结构等后端改进。前端这边可以减少重复请求或提供合理反馈，但这些措施并不等于已经解决服务端计算慢，更不能声称自己完成了数据库优化。

## 追问：Network 显示请求结束了，为什么列表还没出现？

1. Network 结束主要说明响应传输阶段完成，不代表页面已经完成所有处理。我会先检查代码是否还在等待另一条请求，或者在解析结果后执行了大量同步过滤、排序和数据转换。

2. 可以在响应处理开始、状态提交和页面更新附近加临时性能标记，并用 Performance 看主线程任务。若数据量很大，一次创建大量 DOM 或初始化复杂图表，耗时会出现在网络之后。

3. 还要检查条件渲染和状态错误，例如已经拿到列表但 loading 没关闭。确认是计算慢才考虑分批或减少工作，确认是逻辑错误则修状态分支，不能用更长的接口超时配置解决渲染问题。
