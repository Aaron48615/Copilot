# 如何用浏览器工具定位一个接口慢？

## 核心回答

1. 先确认「接口慢」指点击后很久才发请求、请求本身耗时长，还是响应结束了页面才迟迟更新。在 Network 里记下目标请求的开始时间、总耗时和 Initiator，再跟用户操作时间对齐。别把前端等待算成服务端耗时。

2. 展开 Timing 后，可以区分排队、DNS、连接、发送请求、等待首字节、内容下载这些阶段。连接复用或缓存命中时，有些阶段不会出现。没看到 DNS 时间，不等于测量有问题。

3. 等待首字节时间长，可能涉及网络往返、代理排队和服务端处理，不能直接断定数据库慢。内容下载时间长，要结合响应体大小、压缩情况和网络条件看。同样大小的数据，在不同网络下耗时可能差很多。

4. 再看同一操作有没有重复发请求、前一个请求是不是一直挂着，以及业务请求之前有没有 OPTIONS 或其他依赖请求。搜索场景尤其要看参数和返回顺序。慢的旧请求即使取消了，也要防止后续处理盖住新结果。

5. 浏览器证据能缩小范围，但单独解释不了服务端内部耗时。整理脱敏的请求标识、时间、参数特点和 Timing，跟后端日志或 Server-Timing 对照。响应已经结束，就继续用 Performance 查解析、计算和渲染。

## 追问：Waiting 很长，能直接让后端优化 SQL 吗？

1. 不能。浏览器测到的等待首字节包含多个环节，SQL 只是服务端处理里的一种可能。先在相同网络下比较不同请求，确认是个别接口慢，还是所有请求都出现类似延迟。

2. 然后提供具体请求标识和时间，请后端查看网关、应用和数据库的对应记录。服务端如果提供 Server-Timing，也可以当辅助，但仍要理解各字段覆盖的范围。名字相近的时间，别简单相减。

3. 只有证据指向查询耗时，才讨论索引、查询结构这些后端改进。前端这边可以减少重复请求或给出合理反馈，但这些不等于已经解决服务端计算慢，更不能说自己完成了数据库优化。

## 追问：Network 显示请求结束了，为什么列表还没出现？

1. Network 结束主要说明响应传输阶段完成，不代表页面已经做完所有处理。先看代码是不是还在等另一条请求，或者解析结果之后做了大量同步过滤、排序和数据转换。

2. 可以在响应处理开始、状态提交和页面更新附近加临时性能标记，再用 Performance 看主线程任务。数据量很大时，一次创建大量 DOM 或初始化复杂图表，耗时会出现在网络之后。

3. 还要看条件渲染和状态错误，比如已经拿到列表但 loading 没关。确认是计算慢，再考虑分批或减少工作；确认是逻辑错误，就修状态分支。别用更长的接口超时配置去解决渲染问题。
