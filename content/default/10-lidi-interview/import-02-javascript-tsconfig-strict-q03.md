# 什么时候可以用类型断言？

## 核心回答

1. 类型断言是我告诉编译器，这个值应该按某种类型看待，它本身不会做运行时检查。使用前要有独立依据，例如已经验证了节点确实是输入框，而不只是因为访问某个属性报错，就写一个 as 让提示消失。

2. 对 DOM 查询，我会优先检查元素是否存在，并通过 instanceof 判断具体元素类型。仅仅知道节点存在，还不足以断言成输入框；如果选择器或页面结构以后改变，原先默认的前提可能失效，属性访问也会跟着出问题。

3. 有时第三方声明不完整，或者一段动态构造逻辑确实超出了编译器的推断能力，可以在小范围使用断言。我的要求是能解释保证来自哪里，并把它限制在转换位置，避免整个调用链都依赖读者口头相信这个类型。

4. 外部响应、用户输入和本地存储内容不能仅靠断言变可信，这些数据可能缺字段或来自旧版本。应该先以未知类型接收并检查必要字段，再交给业务函数；通过双重断言强行跨过类型差异，会让本来有用的检查失去意义。

5. 非空断言同样需要证据，因为它只是从静态类型中去掉空值，不会在运行时补上对象。若可以通过提前返回、类型守卫或更准确的参数类型解决，我会优先用这些方式，让代码本身说明条件为什么成立。

## 追问：as、satisfies 和显式类型注解分别适合什么情况？

1. 显式类型注解用于规定变量或函数边界，赋进去的值必须满足这个要求。例如配置对象声明为某个接口，编译器会按该接口检查赋值，后续读取也以这个声明的类型为依据，适合统一对外约定。

2. satisfies 用于检查表达式是否符合要求，同时保留表达式自身推导出的类型信息。它适合检查配置键和值，但不能保证完全不影响上下文推断，也不会生成运行时校验，不能拿它检查刚收到的未知接口数据。

3. as 则允许在一定兼容范围内重新解释类型，承担的保证更多落在编写者身上。如果只是想确认一个对象符合接口，我会优先考虑注解或 satisfies；只有已有证据而推断跟不上时，才考虑使用断言。

## 追问：在回调外判断对象非空，为什么回调里仍要考虑失效？

1. 回调可能在稍后执行，外部可变变量在这段时间里有机会被重新赋值。之前的非空检查说明的是检查当时的状态，不一定能证明未来执行回调时的状态，所以不能机械地给回调中的访问补一个感叹号。

2. 如果需要的是当时取得的那个值，可以先保存到一个不会重新赋值的局部变量，再让回调使用它。这样变量绑定更稳定，但对象内部属性仍可能变化；需要某个字段的快照时，还应单独保存那个字段。

3. 如果回调必须使用最新状态，就应该在执行时重新读取和判断，而不是刻意固定旧值。例如界面已经离开时，继续操作旧元素未必有意义，解决方式应符合生命周期，类型断言不能替代这些运行时条件。
