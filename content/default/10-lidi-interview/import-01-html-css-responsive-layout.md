# 移动端适配是怎么做的？

## 核心回答

1. 移动端 H5 项目使用 rem 适配，通过 amfe-flexible 随屏幕宽度调整根字号，再用 postcss-pxtorem 转换样式里的 px。它解决的是设计尺寸如何映射到不同屏宽，不是所有响应式问题；布局仍需要 Flex 等方式安排内容，长文字和极端宽度不能只靠等比缩放。

2. 项目中业务样式与 Vant 使用了不同换算基准，分别是 75 和 37.5。关键是两部分样式采用的设计尺寸基准不同，必须与根字号策略配套，不能把其中一个数字当成任何项目都适用的配置。如果修改方案，我会先核对构建配置和转换后的实际尺寸。

3. 基础还包括正确设置 viewport，让移动浏览器按设备宽度布局。图片预留宽高比，底部操作区域考虑 `env(safe-area-inset-bottom)`，细边框按实际设备效果处理。安全区、键盘和图片加载引起的布局变化是不同问题，不能期待 rem 自动把它们全部解决。

4. 如果继续完善，我会测试窄屏、横屏、字号放大和真实触摸操作，检查按钮是否容易点击、底栏是否遮住输入框。桌面后台则更适合根据内容改列数与区域尺寸，可以通过栅格和图表容器观察适应尺寸变化；我不会把移动端整页缩放方案原样套到后台，具体效果还需要根据检查结果判断。

## 追问：业务样式和 Vant 的换算基准为什么不能随便统一？

1. px 转 rem 本质上是用设计尺寸除以换算基准，再由运行时根字号还原为显示尺寸。如果两套样式原本基于不同设计尺度，机械统一除数，就会让一部分组件被放大或缩小，表面上像组件库样式失效。

2. 我会选一个业务按钮和一个 Vant 按钮，检查 postcss-pxtorem 的 rootValue 如何按文件区分，再把源码 px 除以对应基准，与构建产物里的 rem 对照。最后用 rem 乘以页面计算后的根字号，对比按钮的实际尺寸，这样能分清是转换规则选错、重复转换，还是根字号与预期不一致。

3. 如果后续统一设计基准，应同时调整转换范围和尺寸来源，并检查是否重复转换或漏转。只改一项 rootValue 就提交，容易让表单、弹层和自定义组件大小不一致，验证应覆盖混合使用两套样式的页面。

## 追问：底部安全区 padding 加了，为什么按钮仍可能被键盘挡住？

1. 安全区主要描述屏幕形状和系统界面预留区域，不等于软键盘高度。键盘弹出会影响可视区域，具体视口行为还与平台和浏览器有关，所以补了 safe-area-inset-bottom 并不能自动保证固定按钮始终在键盘上方。

2. 我会在目标真机上打开输入框，观察可视视口、布局视口和底栏位置，再决定让内容滚动、调整底栏布局或在编辑时改变显示策略。若需要使用视口相关 API，也要处理变化事件与清理，避免键盘收起后仍留下错误高度。

3. 我会在真机上聚焦最后一个字段，检查键盘打开后能否看到输入内容和必要按钮，再切换横屏、收起键盘并继续滚动。还要确认底栏回到正确位置、页面没有残留空白，焦点也没有落到被遮住的控件上；这些操作比只看一张键盘打开时的截图更能发现问题。
