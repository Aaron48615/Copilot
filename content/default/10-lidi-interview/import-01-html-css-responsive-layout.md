# 移动端适配是怎么做的？

## 核心回答

1. 移动端 H5 项目用 rem 适配：`amfe-flexible` 随屏幕宽度调根字号，再用 `postcss-pxtorem` 把样式里的 px 转走。它解决的是设计尺寸怎么映射到不同屏宽，不是所有响应式问题。布局还得用 Flex 这类方式安排内容，长文字和极端宽度不能只靠等比缩放。

2. 项目里业务样式和 Vant 用了不同换算基准，分别是 75 和 37.5。关键是两套样式的设计尺寸基准不同，必须跟根字号策略配套。别把其中一个数字当成任何项目都能套的配置。要改方案，先核对构建配置和转换后的实际尺寸。

3. 基础还包括正确设置 viewport，让移动浏览器按设备宽度布局。图片预留宽高比，底部操作区域考虑 `env(safe-area-inset-bottom)`，细边框按真机效果处理。安全区、键盘、图片加载引起的布局变化是不同问题，rem 不会自动全包。

4. 继续完善就测窄屏、横屏、字号放大和真实触摸：按钮好不好点、底栏会不会挡住输入框。桌面后台更适合按内容改列数和区域尺寸，用栅格和图表容器观察尺寸变化。移动端整页缩放这套，别原样套到后台。具体效果还得看检查结果。

## 追问：业务样式和 Vant 的换算基准为什么不能随便统一？

1. px 转 rem，本质上是用设计尺寸除以换算基准，再由运行时根字号还原成显示尺寸。两套样式原本基于不同设计尺度，机械统一除数，一部分组件就会被放大或缩小，表面上像组件库样式坏了。

2. 挑一个业务按钮和一个 Vant 按钮，看 `postcss-pxtorem` 的 `rootValue` 怎么按文件区分，再把源码 px 除以对应基准，跟构建产物里的 rem 对照。最后用 rem 乘以页面算出来的根字号，对比按钮实际尺寸。这样能分清是转换规则选错、重复转换，还是根字号跟预期不一致。

3. 后续要统一设计基准，转换范围和尺寸来源一起调，并检查有没有重复转换或漏转。只改一项 `rootValue` 就提交，表单、弹层和自定义组件大小容易对不上。验证覆盖混合使用两套样式的页面。

## 追问：底部安全区 padding 加了，为什么按钮仍可能被键盘挡住？

1. 安全区主要描述屏幕形状和系统界面预留区域，不等于软键盘高度。键盘弹出会影响可视区域，具体视口行为还跟平台和浏览器有关。补了 `safe-area-inset-bottom`，固定按钮不会自动永远停在键盘上方。

2. 目标真机上打开输入框，观察可视视口、布局视口和底栏位置，再决定让内容滚动、调整底栏布局，还是编辑时改显示策略。用到视口相关 API，也要处理变化事件和清理，键盘收起后别留下错误高度。

3. 真机上聚焦最后一个字段，看键盘打开后能不能看到输入内容和必要按钮，再切横屏、收起键盘、继续滚动。底栏回到正确位置、页面没有残留空白、焦点也没有落到被挡住的控件上。这些比只看一张键盘打开时的截图更能发现问题。
