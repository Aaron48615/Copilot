# Effect 的清理什么时候执行？

## 核心回答

1. Effect 的清理不只在卸载时执行。某次更新提交后，如果依赖相对上次发生变化，React 会先调用上一次 Effect 返回的清理函数，再运行新的 setup，所以旧订阅不会和新订阅一直并存。

2. 清理函数拿到的是建立那次 Effect 时的值。比如 roomId 从 A 变成 B，旧清理应断开 A 的连接，新 setup 再连接 B；我会在 Effect 内部保存连接实例，让创建和释放指向同一个对象。

3. 组件卸载时也会执行清理，用来停止定时器、移除监听或使请求结果失效。不是每次 render 都一定有清理：依赖没变时通常不重新运行，未提交的渲染也不应被当成已经建立了新的外部连接。

4. 开发环境的 Strict Mode 可能额外执行 setup、cleanup、setup 来检查对称性。看到两次请求不能立即认定生产也会重复；我会确认运行模式，同时检查清理是否完整，而不是加一个“只执行一次”的标记掩盖问题。

5. 比如一个详情页先展示商品甲，再切到商品乙，旧请求的清理应使甲的回调失效，而不是清空所有页面数据。乙的请求仍要独立保留加载状态；这样即使甲更晚返回，也不会覆盖乙，清理负责撤销自己建立的工作，而不是任意重置整个组件。

## 追问：清理时为什么不能只写 removeEventListener 就结束？

1. 移除监听需要对应同一个事件类型、函数引用和 capture 配置。如果添加时用了匿名函数，清理时再写一个长得一样的匿名函数，它们也不是同一个对象，旧监听仍可能留在页面上。

2. 资源可能不止一个。一个自动刷新组件既有窗口监听又有轮询定时器，两个都要清理；如果监听回调还安排了延迟任务，也要考虑已经排队的任务是否会在组件离开后继续执行。

3. 我会通过反复进入和离开页面检查行为，例如一次 resize 是否只调用一次处理逻辑。测试中可以观察添加、移除的参数和回调次数，比只看清理函数有没有出现那一行代码更可靠。

## 追问：请求被取消后，为什么仍可能需要有效性判断？

1. 取消请求是尽量减少继续传输和处理，不等于撤回已经完成的所有工作。接口封装可能不支持 signal，响应之后的解析或其他异步处理也可能还在继续，所以不能把安全性完全建立在取消上。

2. 我会为每次 Effect 保存一个有效标志，清理时设为失效，写入数据前再判断。这样即使旧 Promise 最终完成，也不能把上一页的商品详情覆盖到当前页，清理和提交形成明确对应。

3. 同样的判断应覆盖错误和 loading。旧请求的 finally 如果无条件关闭加载状态，也会让新请求尚未完成时转圈消失；取消产生的异常还应单独识别，通常不作为普通接口失败展示给用户。
