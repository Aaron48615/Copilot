# LCP 图片应该怎么处理？

## 核心回答

1. 哪个元素实际成了 LCP 候选，先确认，别默认第一张图或最大的文件就是目标。不同视口、登录状态、内容，候选可能不一样。优化要对上用户真正看到的主要内容。

2. 确认是主图，就让浏览器尽早发现它，尽量直接出现在初始 HTML 里，别等多轮接口或脚本再插入。关键图片通常不设 lazy，必要时用 `fetchpriority` 提示重要性。发现确实太晚，再评估 `preload`。

3. 图片本身选适合显示尺寸的资源，配 `srcset`、`sizes` 这些响应式规则，格式和压缩也要合适。文件越小越好不是唯一目标，压过头画质差，尺寸选错又可能下一张过大的图，传输和解码都会变重。

4. 给图片明确宽高或宽高比，页面能先留位置，布局也不容易跳。宽高本身不保证 LCP 更早。下载完仍可能被样式、脚本或隐藏状态拖住显示。资源完成和实际绘制之间，有没有在等，也要看。

5. LCP 时间拆开看：首字节等待、资源发现、下载、渲染延迟。服务器很慢，只压图片消不掉前面那段等待。预加载过度还可能抢别的关键资源。改完用同类设备和网络再测，看瓶颈有没有真正少。

## 追问：主图已经下载完了，为什么 LCP 仍然很晚？

1. 下载结束只说明字节可用了。图片还可能等解码、等关键样式、等主线程忙完。页面逻辑也可能先把它藏起来，等动画或接口状态变了才显示。资源结束时间，不能直接当 LCP 发生时间。

2. 性能时间线上看，下载结束到候选绘制之间那段，查长任务、样式计算、显隐变化。要是脚本堵住了，继续把图片文件压小几乎没收益，先减少当前帧前那些没必要的工作。

3. 验证时图片版本保持不变，只调确认过的显示或执行问题，看 LCP 会不会前移。也要确认候选元素没有换成另一块内容。数字变了可能来自候选变了，不能自动记到图片下载优化头上。

## 追问：主图设 fetchpriority=high 后，所有图片都加 high 可以吗？

1. 不合适。优先级提示的意义是区分谁更重要。所有图片都设成高优先级，真正关键的那张就没了相对优势，还可能跟样式、脚本抢。浏览器最终也会按自己的规则排请求，不保证完全按提示执行。

2. 只对确认过的关键候选设提示，其余图片按位置正常加载或懒加载。不同视口可能显示不同主图，响应式选择要配合。桌面和移动版本都被提前下载，首屏那点带宽会浪费。

3. Network 里看实际优先级和完成顺序，再比较首屏内容出现时间。提示只是可测量的手段，不是必加属性。浏览器本来就已经很早、高优先级加载主图，新增配置可能没什么收益。
