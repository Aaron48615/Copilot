# LCP 图片应该怎么处理？

## 核心回答

1. 处理 LCP 图片之前，我会先确认哪个元素实际成为 LCP 候选，不默认把第一张图或最大的文件当作目标。不同视口、登录状态和内容可能产生不同候选，优化必须对应用户真正看到的主要内容。

2. 如果确认是主图，就让浏览器尽早发现它，尽量直接出现在初始 HTML 中，不要等多轮接口或脚本插入。关键图片通常不设 lazy，必要时使用 fetchpriority 提示重要性，只有发现确实太晚时再评估 preload。

3. 图片本身要选择适合显示尺寸的资源，配 srcset、sizes 等响应式规则，使用合适格式和压缩。文件越小越好也不是唯一目标，过度压缩会影响质量，选择错误尺寸又可能下载过大的图片，增加传输与解码工作。

4. 给图片明确宽高或宽高比，帮助页面预留位置，同时避免布局位移。宽高本身不保证 LCP 更早，下载完成后仍可能被样式、脚本或隐藏状态延迟显示，所以还要检查资源完成与实际绘制之间的等待。

5. 我会把 LCP 时间拆开看，包括首字节等待、资源发现、下载和渲染延迟。服务器很慢时只压图片无法消除前面的等待，过度预加载还可能抢其他关键资源；改后用同类设备和网络复测，再判断瓶颈有没有真正减少。

## 追问：主图已经下载完了，为什么 LCP 仍然很晚？

1. 下载结束只说明资源字节可用，图片还可能等待解码、关键样式或主线程工作完成。也可能页面逻辑先把它隐藏，等动画或接口状态变化才显示，因此不能把资源结束时间直接当作 LCP 的发生时间。

2. 我会在性能时间线看下载结束到候选绘制之间的区间，检查长任务、样式计算和显隐变化。如果是脚本阻塞，继续降低图片文件大小可能几乎没有收益，应先减少当前帧前的不必要工作。

3. 验证时保持图片版本不变，只调整确认的显示或执行问题，观察 LCP 是否前移。也要确认候选元素没有换成另一块内容，否则数字变化可能来自候选变化，不能自动归功于图片下载优化。

## 追问：主图设 fetchpriority=high 后，所有图片都加 high 可以吗？

1. 不合适，优先级提示的意义是区分重要程度。所有图片都设成高优先级，会让真正关键资源失去相对优势，还可能与样式、脚本竞争；浏览器最终也会结合自己的规则安排请求，不保证完全按提示执行。

2. 我会只对确认的关键候选设置提示，其余图片根据位置正常加载或懒加载。不同视口可能显示不同主图，响应式选择要配合，否则桌面和移动版本都被提前下载，会浪费本就有限的首屏带宽。

3. 检查 Network 中实际优先级和完成顺序，再比较首屏内容出现时间。提示只是可测量的手段，不是必加属性，若浏览器本来已经很早高优先级加载主图，新增配置可能没有明显收益。
