# 为什么搜索页卸载时还要清理定时器和请求？

## 核心回答

1. 联想既有等待中的 300 毫秒定时器，也可能有已发送的请求。用户离开搜索页后，这些任务不再服务当前页面，如果不清理，定时器仍可能继续调用模型，迟到结果也可能触发无意义的状态更新。

2. 当前 onBeforeUnmount 调用 stopSuggestionRequest，清除 timer，abort 当前 controller，再清空引用。停止尚未触发的定时器可以真正避免那次请求发出，取消已发送请求则主要结束客户端这边的等待，两者作用并不一样。

3. 清理时还递增 suggestionRequestId，让旧异步过程失效。即使取消信号没有传到最底层，结果回来时也会发现编号不再对应当前任务，不再写入建议或恢复过期的 loading 状态。

4. 主动取消不能当作服务故障生成本地建议，否则离开或清空后仍会出现旧关键词。清理应覆盖成功、错误与 finally 的后续行为，而不是认为调用了 abort 就不会再有任何 JavaScript 回调执行。

5. 如果组件以后使用 KeepAlive，离开页面可能只是停用而非卸载，需要另外在停用时暂停不必要工作。当前卸载清理能说明资源归属，但不能自动覆盖所有路由缓存策略，生命周期要结合实际页面使用方式判断。

## 追问：取消请求后为什么仍可能进入 catch 和 finally？

1. 取消通常会让等待中的异步操作以取消异常结束，因此 catch 与 finally 正是正常结束路径的一部分。它不等于把整段函数从内存里瞬间删除，后续错误分类和资源恢复逻辑依然会执行。

2. 所以 catch 要识别主动取消，不显示故障或生成备用内容；finally 则确认自己是否仍是当前请求，再更新 loading 与 controller。否则清理一个旧请求，可能反过来破坏已经开始的新请求。

3. 验证时在请求中途离开页面，再立即进入并输入新词，观察旧异常是否影响新页面。取消能力与结果失效检查一起使用，才能把客户端任务的结束解释清楚，不是只靠一句“卸载时 abort”。

## 追问：清理函数被调用两次会不会出问题？

1. 好的清理逻辑应允许重复调用，先检查 timer 和 controller 是否存在，再清理并置空。输入变化和卸载可能接连触发，同一个已经清掉的任务不应导致异常，幂等的清理方式更容易复用。

2. 递增编号多一次通常只是让更旧任务继续失效，但不能误清新任务引用。因此清理函数的调用时机要清楚，必要时对比请求身份，避免旧异步 finally 调用全局停止函数，把新请求也取消。

3. 测试没有请求时离开、等待计时器时离开、请求执行时离开，以及快速返回重新输入。不同阶段都能正常结束，才说明清理覆盖了资源生命周期，不是某个理想状态下恰好能跑。
