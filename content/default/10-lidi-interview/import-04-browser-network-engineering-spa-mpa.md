# 单页应用和多页应用有什么区别？

## 核心回答

1. SPA 的页面切换主要由客户端路由和 JavaScript 更新内容，通常不需要每次整页导航；MPA 则为不同地址提供独立文档，切换时浏览器加载新页面。区别主要是导航和页面组织方式，不是用了某个框架就必然属于其中一种。

2. SPA 适合交互连续的后台和工具页面，状态可以在页面切换间保留，但需要管理前端路由、错误恢复和首次脚本成本。它也可以通过动态导入只加载当前所需代码，不能说每次首屏一定下载整个站点的 JavaScript。

3. MPA 的独立 HTML 便于按页面输出内容和设置元信息，浏览器原生导航也减少了一部分客户端状态管理。它仍可共享静态资源缓存并有局部交互，不能把多页应用理解成每次都重复下载所有资源的老式页面。

4. SEO 与 SPA、MPA 有关联，但不能绝对化。关键还在初始 HTML 是否包含内容、爬虫执行能力、元信息和性能，SSR 或预渲染也能改善 SPA 的内容可发现性；多页应用的内容若全靠晚到接口，照样可能不好抓取。

5. 我的项目以 SPA 为主，会配合路由懒加载和 history 回退。若做内容展示为主的网站，我会进一步评估服务端渲染或静态生成的成本，不只按切换是否流畅来选；刷新深层链接和无脚本时的表现也值得验证。

## 追问：SPA 和 SSR 是互相排斥的吗？

1. 不是，它们描述的侧重点不同。SPA 常讨论页面导航和客户端更新方式，SSR 讨论首次内容由服务端生成；一个应用可以先收到服务端渲染的 HTML，再完成客户端激活，之后用客户端路由切换。

2. 这样可能更早提供可见内容，也方便生成页面元信息，但增加了服务端执行、缓存和激活一致性的要求。不能只加 SSR 名字就保证更快，服务端响应慢或客户端仍执行大量脚本，用户体验仍可能不好。

3. 我会根据公开内容比例、交互需求和部署能力评估。对于登录后后台，SEO 价值通常有限；对于文章或商品展示，初始内容更重要，选型应解释这些差异，而不是说所有 SPA 都应该改成 SSR。

## 追问：SPA 切换页面时，哪些状态应该保留？

1. 需要按业务区分。登录信息和用户偏好可能跨页面共享，列表筛选和滚动位置可以按返回体验保留，但一次编辑中的临时状态不一定应该自动带到另一个新建页面，保留过多同样会造成数据混淆。

2. 我会把可分享或可恢复的查询条件放进 URL，把页面内部临时状态放在合适的组件或状态容器中。缓存路由时还要处理订阅、计时器和过期数据，不能页面不可见了仍持续请求或响应旧事件。

3. 验证前进、后退、刷新和复制链接四种场景，确认用户能理解看到的内容来源。状态只存在内存时，刷新后不一定能恢复，因此不能把应用内返回正常等同于所有导航方式都已经处理完整。
