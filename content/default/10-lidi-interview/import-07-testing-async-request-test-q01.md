# 如何避免测试本身不稳定？

## 核心回答

1. 我会先让每条测试拥有独立的请求 mock、组件实例和缓存，避免上一条留下的数据影响下一条。比如测试搜索结果时，每次都从空输入开始，不依赖另一条测试先登录或先查过某个关键词，这样单独运行和整组运行才有一致的前提。

2. 请求先后顺序交给测试控制，不用网络快慢制造竞态。我会保存两个 Promise 的 resolve 函数，确认两个请求都已发出后，主动让后发请求先成功，再释放旧请求，这样每次执行都会经过同一个危险顺序。

3. 防抖、超时和退避才需要假计时器，普通请求完成可以直接释放 Promise。推进时间后还要等待对应异步步骤和界面更新，不能认为时间跳过去，所有 Promise 回调和组件渲染就已经完成。

4. 断言前等待明确的状态，比如结果列表出现或提交按钮恢复可用，不固定睡一秒。特别是“没有错误提示”这种否定断言，要等失败处理确实走完再检查，否则请求还没结束时它也能通过。

5. 结束时卸载组件、取消未完成操作，并按工具的用途恢复计时器、拦截器和全局替换。清调用记录不等于恢复原实现；偶发失败时我会看请求顺序和状态变化，再判断缺了哪个等待条件，不先靠增加重试次数掩盖问题。

## 追问：假计时器推进后，为什么页面还没有更新？

1. 假计时器主要控制时间相关回调，Promise 的后续处理以及框架安排的更新还有各自的执行时机。例如防抖定时器虽然已经触发，里面的请求 Promise 仍可能处于 pending，所以列表暂时不变是正常的。

2. 我会把这几个阶段拆开检查：先确认时间推进触发了请求，再释放请求结果，最后等待页面出现目标内容。在 Vitest 中遇到异步定时逻辑可以等待异步推进计时器的方法，但不能把它理解成自动完成所有外部请求。

3. 如果点击工具本身依赖定时器，还要按它的接口配置时间推进方式，否则测试可能互相等待。结束前处理自己创建的待执行任务，再恢复真实时间；我不会在不清楚任务用途时直接运行所有计时器，循环定时器可能一直产生新任务。

## 追问：为什么测试单独运行通过，整组运行却失败？

1. 我会优先找跨测试共享的状态，比如模块级缓存、未恢复的 fetch 替换或共用账号的数据。一条测试改了默认响应，下一条没重新设置，就可能拿到错误的数据；把失败测试和前一条一起跑，通常比盲目延长超时更有信息。

2. 接着检查是否有上一条留下的异步任务。测试函数提前返回、断言 Promise 没有 await、卸载时没有取消订阅，都可能让回调进入下一条测试的执行时间，表现成日志串场或计数偶尔多一次。

3. 如果只在并行运行时失败，我会检查数据名称、端口和文件是否冲突，为每条测试分配独立资源。暂时串行运行可以帮助定位，但最终要修复资源共享的原因，并确认清理动作在断言抛错时也能执行。
