# 如何避免测试本身不稳定？

## 核心回答

1. 每条测试自己的请求 mock、组件实例、缓存，上一条留下的数据别影响下一条。测搜索结果，每次从空输入开始，别依赖另一条测试先登录、先查过某个关键词。单独跑和整组跑，前提才一致。

2. 请求先后顺序交给测试控制，不用网络快慢制造竞态。把两个 Promise 的 resolve 存下来，确认两个请求都发出去了，再主动让后发的先成功，然后放旧请求。每次执行都会经过同一个危险顺序。

3. 防抖、超时、退避才需要假计时器，普通请求完成直接释放 Promise 就行。时间推进之后，对应的异步步骤和界面更新还要等。别以为时间跳过去了，所有 Promise 回调和组件渲染就已经做完。

4. 断言前等明确状态，比如结果列表出现，或者提交按钮恢复可用，别固定睡一秒。「没有错误提示」这种否定断言，要等失败处理确实走完再查，请求还没结束时它也能通过。

5. 结束时卸载组件、取消没做完的操作，按工具用途恢复计时器、拦截器、全局替换。清调用记录不等于恢复原实现。偶发失败就看请求顺序和状态变化，判断缺了哪个等待条件，别先靠加重试次数把问题盖住。

## 追问：假计时器推进后，为什么页面还没有更新？

1. 假计时器主要管跟时间有关的回调。Promise 后续处理和框架安排的更新，各有各的时机。防抖定时器已经触发了，里面的请求 Promise 仍可能 pending，列表暂时不变是正常的。

2. 这几个阶段拆开查：先确认时间推进触发了请求，再释放请求结果，最后等页面出现目标内容。Vitest 里碰到异步定时逻辑，可以等异步推进计时器的方法，但它不会自动把所有外部请求做完。

3. 点击工具本身依赖定时器，还要按它的接口配置时间怎么推进，否则测试可能互相等。结束前把自己创建的待执行任务处理掉，再恢复真实时间。不清楚任务用途，别直接跑所有计时器，循环定时器可能一直产生新任务。

## 追问：为什么测试单独运行通过，整组运行却失败？

1. 优先找跨测试共享的状态：模块级缓存、没恢复的 fetch 替换、共用账号的数据。一条测试改了默认响应，下一条没重新设，就可能拿到错数据。把失败测试和前一条一起跑，通常比盲目拉长超时更有信息。

2. 再查有没有上一条留下的异步任务。测试函数提前返回、断言 Promise 没有 await、卸载时没取消订阅，都可能让回调跑进下一条测试的时间里，日志串场，或者计数偶尔多一次。

3. 只在并行跑的时候失败，就查数据名称、端口、文件有没有冲突，给每条测试独立资源。暂时串行能帮忙定位，但最终要修资源共享的原因，断言抛错时清理动作也得执行到。
