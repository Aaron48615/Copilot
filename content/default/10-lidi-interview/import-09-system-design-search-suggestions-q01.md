# 高并发下怎么保护服务端？

## 核心回答

1. 正常输入产生的重复请求，和有人绕过页面直接调接口，要分开。防抖、最小输入长度、取消旧请求，能减轻正常使用的压力。这些逻辑都在客户端，当不了服务端的限流或安全边界。

2. 服务端限制请求频率和同时处理的数量，关键词长度、返回条数、允许的查询方式也要约束。限流可以结合账号、租户、IP。别只按 IP 一刀切，校园网、公司网络里很多正常用户可能共用出口。

3. 查询本身成本可控。常见前缀检索用合适的索引，规模上来再评估专门搜索服务。每个字符都触发全表扫描不行。数据库查询和服务调用设超时，超时之后尽量停掉后面没用的活。

4. 热门查询可以缓存，相同且正在执行的查询合并，减少缓存过期时的重复计算。缓存有容量和有效期，键里包含语言、过滤条件，以及必要的权限范围。个性化结果别只按关键词放进公共缓存。

5. 超限时返回可识别的 429，必要时带 `Retry-After`，让前端提示等待并控制重试。联想不可用时，正常输入和正式搜索入口还留着。客户端取消只表示不再需要结果，说不成它一定取消了服务端已经开始的查询。

## 追问：热门词缓存同时过期，怎样避免请求一起打到数据库？

1. 同一个查询键，只让一个刷新任务真正访问数据源，其他请求等它，或者在业务允许时用标明过期的旧结果。合并范围要说清。单进程里的共享 Promise，只能减少这个进程内的重复查询。

2. 多实例服务如果要进一步合并，由共同的缓存或协调机制控制刷新，刷新者失败、等待超时也要处理。别为了避免重复请求，让所有请求无限等一把锁。等待上限和失败后的响应同样重要。

3. 过期时间可以加一点随机量，减少不同关键词同时失效的概率。这单独解决不了某个热点键的并发刷新。缓存容量也要限制，大量一次性长尾词别把热点挤走。再按实际命中情况调策略。

## 追问：前端收到 429 后，应不应该自动重试？

1. 联想请求通常不值得立即重试，用户可能已经输入了新词。先确认这个请求还对应当前输入，再判断要不要重试。旧关键词已经失效，直接丢掉后续任务，更符合用户当前意图。

2. 响应带 `Retry-After`，就按约定解析等待时长或日期，等待期间别继续密集请求。没有这个字段，也用有次数上限的退避，别每次失败立刻重发。否则客户端还会把拥堵加重。

3. 界面把没有匹配结果和暂时请求过多分开，限流错误别存成长期空结果。用户仍能改输入，合适的时候提供手动重试或正式搜索入口。账号或输入条件变了，原来的重试任务也取消。
