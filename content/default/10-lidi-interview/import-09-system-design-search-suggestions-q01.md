# 高并发下怎么保护服务端？

## 核心回答

1. 我会先区分正常输入产生的重复请求和有人绕过页面直接调用接口。防抖、最小输入长度和取消旧请求能减少正常使用的压力，但这些逻辑都在客户端，不能作为服务端的限流或安全边界。

2. 服务端需要限制请求频率和同时处理的数量，并约束关键词长度、返回条数及允许的查询方式。限流可以结合账号、租户和 IP，不能只按 IP 一刀切，因为校园网或公司网络里的许多正常用户可能共用出口。

3. 查询本身要有可控成本，常见前缀检索可以使用合适的索引，规模上来后再评估专门搜索服务。不能让每个字符都触发全表扫描；数据库查询和服务调用要设置超时，超时后也要尽量停止无用的后续工作。

4. 热门查询可以缓存，并把相同且正在执行的查询合并，减少缓存过期时的重复计算。缓存要有容量和有效期，键里包含语言、过滤条件以及必要的权限范围；个性化结果不能仅按关键词放进公共缓存。

5. 超限时返回可识别的 429，必要时附 Retry-After，让前端提示等待并控制重试。联想不可用时仍可保留正常输入和正式搜索入口，客户端取消只表示不再需要结果，不能声称它一定取消了服务端已经开始的查询。

## 追问：热门词缓存同时过期，怎样避免请求一起打到数据库？

1. 对同一个查询键，只让一个刷新任务真正访问数据源，其他请求等待它或在业务允许时使用标明过期的旧结果。合并的范围需要明确，单进程里的共享 Promise 只能减少这个进程内的重复查询。

2. 多实例服务如果需要进一步合并，可由共同的缓存或协调机制控制刷新，但要处理刷新者失败和等待超时。不能为了避免重复请求，让所有请求无限等待一把锁，等待上限和失败后的响应同样重要。

3. 过期时间可以加入适当随机量，减少不同关键词同时失效的概率，但这并不能单独解决某个热点键的并发刷新。还要限制缓存容量，防止大量一次性长尾词把热点挤走，并按实际命中情况调整策略。

## 追问：前端收到 429 后，应不应该自动重试？

1. 联想请求通常不值得立即重试，因为用户可能已经输入了新词。我会先确认这个请求仍对应当前输入，再判断是否需要重试；旧关键词已经失效时，直接丢弃后续任务更符合用户当前意图。

2. 如果响应带 Retry-After，就按约定解析等待时长或日期，在等待期间避免继续密集请求。没有该字段时也应采用有次数上限的退避策略，而不是每次失败立即重发，否则客户端会进一步增加拥堵。

3. 界面要区分没有匹配结果和暂时请求过多，不能把限流错误存成长期空结果。用户仍可编辑输入，适当时提供手动重试或正式搜索入口；账号或输入条件变化后，原来的重试任务也应取消。
