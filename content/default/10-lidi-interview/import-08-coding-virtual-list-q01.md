# 为什么需要 overscan？

## 核心回答

1. overscan 就是在可见区之外提前渲染一些行，给界面更新争取时间。滚动位置已经变了，但事件处理、框架提交和浏览器绘制还没有完成时，只保留当前视口内的 DOM 就容易露出空白。

2. 固定行高时，可以在可见开始下标前减几行、结束下标后加几行，并限制在数据范围内。它没有改变占位总高度，也不是把所有内容都隐藏渲染，而是让实际存在的节点范围稍微大于视口。

3. 预渲染并非越大越好，每多一行都有组件创建、样式计算和布局成本，复杂卡片还可能触发图片请求。假设视口容纳十行，前后各多三行就是约十六行参与渲染，这个例子只说明成本如何增加，不代表最优配置。

4. 结合行高、内容复杂度和滚动行为调整，而不是照搬统一行数。相同行数对于矮文本行和高卡片提供的像素缓冲不同。向下快速滚动时可以适当增加下方范围，但仍需保留上方缓冲应对突然反向。

5. overscan 只能缓解渲染滞后，不能保证主线程长时间阻塞时不白屏，也不能补出尚未获取的数据。若扩大范围后更卡，就检查单行成本、状态更新频率和数据预取，别把所有问题都归结为预渲染数量不足。

## 追问：怎样根据滚动速度估算预渲染范围？

1. 先用滚动距离除以时间间隔估算速度，再乘一次界面更新的预估耗时，得到可能提前移动的距离。比如每毫秒两像素、更新需要三十毫秒，理论缓冲约六十像素。这只是推导示例，不是测得的项目数据。

2. 固定行高时把距离除以行高并向上取整，再设置最小和最大范围。最低值保证慢速和反向滚动也有余量，最高值避免一次突然拖动滚动条时算出非常大的区间，反而让渲染成本失控。

3. 速度本身会抖动，做适度平滑，或者按几个速度档位调整，减少范围频繁改变。即使这样也需要实际滚动验证，因为图片解码、布局和设备负载会改变延迟。公式只能提供起点，不能当成无白屏保证。

## 追问：预渲染范围和接口预取范围应该相同吗？

1. 不一定。预渲染解决的是数据已有但节点还没准备好，预取解决的是下一段数据尚未到达。网络延迟通常与一帧渲染耗时不同，因此可以提前请求更远的一页，同时只挂载视口附近的少量节点。

2. 分开维护数据缓存和渲染区间，例如接近已加载数据尾部时触发下一页请求，并用游标或页状态去重。快速来回滚动时复用已有数据，不因某页暂时不在 DOM 中就重新请求，也不让滚动事件并发请求同一页。

3. 若用户跳到未加载区域，需要显示对应位置的加载状态并处理失败重试，而不是简单增大 overscan。数据总数未知时，滚动条总高度也只能按产品约定估计或逐步增长，不能假装已经知道整份列表的准确长度。
