# 轻购的 Axios 请求拦截器和响应拦截器分别做什么？

## 核心回答

1. 请求拦截器处理各页面共有的请求准备。轻购创建统一 Axios 实例，配置 baseURL 和五秒 timeout，发请求前读取 getToken，有凭据就加 Authorization Bearer，避免每个业务函数都手动处理一遍身份头。

2. Token 在请求时读取，而不是只在模块初始化时存一份。这样登录或退出后，新请求能使用当前状态；否则应用加载时保存的旧 Token 可能一直留在闭包里，页面明明登录成功，请求却仍没有正确凭据。

3. 响应成功分支通常返回 response.data，让页面拿到后端业务对象，同时检查业务失效码 A00004。这个返回形状是封装约定，业务 API 的类型也要一致，不能有些页面仍把它当完整 AxiosResponse 再多取一层 data。

4. 响应失败分支会检查 HTTP 401，统一清理 Token 并跳登录，跳转标记减少并发失效的重复处理。其他错误继续交给页面，商品加载失败与订单支付结果未知需要不同文案，不适合在拦截器里全部变成同一句提示。

5. 我会让公共层只承担明确共有的规则，业务 success 为 false 并不都意味着退出登录。当前也没有通用自动重试和刷新 Token，尤其支付、订单等写请求不能在没有幂等约定时被拦截器盲目重放。

## 追问：拦截器 catch 里为什么还要继续抛出错误？

1. 如果捕获后只打印日志，没有 reject 或抛出，调用方可能收到 undefined 并继续走成功分支。例如支付页面以为 await 正常结束就跳转，实际请求已经失败，这会把异常处理变成错误的业务状态。

2. 公共层可以把错误整理成稳定结构，保留状态码、业务码和可展示信息，再交给页面判断。页面用 catch 显示业务提示、finally 恢复按钮，但不应该收到后端堆栈或敏感请求内容作为用户文案。

3. 验证时模拟网络错误与 401，检查调用方不会继续执行成功后的动作，同时提交状态仍能恢复。跳转登录属于公共副作用，不意味着 Promise 可以悬空或伪装成成功，这两个责任需要分别处理。

## 追问：为什么不让拦截器统一显示所有 Toast？

1. 公共层不了解页面上下文。同样是超时，商品列表可以显示重试，订单提交却要先判断是否已经创建；统一说“失败，请再试一次”可能误导用户重复产生订单，所以反馈需要业务信息。

2. 页面也可能有局部备用方式，例如商品卖点失败后展示本地内容。如果拦截器已经弹出红色错误，页面又正常显示备用卖点，用户会收到互相矛盾的反馈，多个并行请求还可能连续弹窗。

3. 我会把登录失效等明确全局行为集中处理，其余错误由页面选择提示方式。若以后要统一风格，可以抽取可复用的错误展示组件或映射函数，但不能以统一文案为代价丢掉业务差别。
