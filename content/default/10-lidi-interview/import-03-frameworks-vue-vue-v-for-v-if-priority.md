# v-for 和 v-if 谁的优先级高？

## 核心回答

1. 同一元素上这两个指令，Vue 2 是 `v-for` 优先，Vue 3 是 `v-if` 优先。回答先限定版本。按旧写法迁到 Vue 3，条件可能读不到原来以为已经存在的循环变量。ESLint 的 `vue/no-use-v-if-with-v-for` 两个版本都建议别这么写。

2. 同一个标签既遍历 `item` 又判断 `item.visible`，Vue 3 先处理条件，这时循环别名还不在这个表达式的作用域里，常见会直接报错，这种写法基本等于不能用。条件要是不依赖循环别名，未必报错，仍然不推荐混写。

3. 目的是筛选项目，用 `computed` 先得到符合条件的数组，再 `v-for`。过滤规则可以单独理解和复用，模板只管展示。每行同时承担循环和判断，排序、空状态、数量计算也不容易一致。

4. 目的是整块列表显不显示，`v-if` 放外层，里面再遍历。不需要真实包装元素可以用 `template`。动态列表的 `key` 放在对应的遍历层，稳定唯一。消掉优先级问题却漏了项目身份，输入和状态还会错位。

5. `v-for` 优先说的是编译和作用域规则，不是先创建全部 DOM 再判断。Vue 3 把 `v-if` 提前，语义更直，也能少做“每一项先进入循环再判断”的白功。迁移时核对原模板语义，过滤、空列表、开关变化都要验，用结构清楚的写法，别依赖某个版本碰巧支持的组合顺序。

## 追问：只想隐藏整张列表，为什么要把条件放外层？

1. 整张列表出不出现由一个整体条件决定，跟某一项的属性无关。外层 `v-if` 直接表达这种关系。读模板先看到这块区域展不展示，再看到内部怎么遍历，不必在每个列表项上重复解释同一个开关。

2. 条件为假时，这块区域不会按普通显示方式创建，子组件也少做无意义的初始化。频繁切换还想留内部状态，再考虑 `v-show` 或缓存。那是生命周期选择，跟让 `v-if` 和 `v-for` 抢同一个节点不是一回事。

3. 列表为空时的提示也要单独有。“区域关了”和“区域开着但没有数据”应看起来不一样。条件层次对上真实产品状态，测试也能分开验，不会一个混合指令让所有空白长得一样。

## 追问：computed 过滤之后，用下标当 key 还会有问题吗？

1. 还会。过滤会改变项目位置，下标不是稳定业务身份。原来第三项变成第一项，还用位置当身份，行里草稿、展开、焦点可能复用给另一条数据。过滤写对了，`key` 仍可能错。

2. 优先用原始记录的稳定编号，过滤后的数组继续带着这个编号。没有编号的临时项目，创建时生成并保存。别每次 `computed` 重算再生成随机 `key`，过滤一重算组件会整表重建。

3. 先编辑一行，再改过滤条件让其他行消失，这行应还带着自己的草稿。纯文本刷新很容易把错误身份盖住。加上真实交互，过滤和列表复用两边才验得全。
