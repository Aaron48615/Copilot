# v-for 和 v-if 谁的优先级高？

## 核心回答

1. Vue 2 和 Vue 3 在同一元素上组合这两个指令时优先级不同：Vue 2 是 v-for 优先，Vue 3 是 v-if 优先。回答必须先限定版本，否则迁移时可能沿用旧写法，而条件读取不到原来以为已经存在的循环变量。

2. 例如同一个标签写遍历 item 又判断 item.visible，Vue 3 会先处理条件，此时循环别名还不在该表达式的作用域里，写法就不符合预期。但不能因此说所有同节点组合都必然报错，条件若不依赖别名是另一种情况，仍然不推荐混写。

3. 如果目的是筛选项目，我会通过 computed 先得到符合条件的数组，再用 v-for 渲染。这样过滤规则可以单独理解和复用，模板也只负责展示，避免每行同时承担循环与判断，排序、空状态和数量计算也更容易保持一致。

4. 如果目的是控制整块列表显示，就把 v-if 放在外层，内部再遍历；不需要真实包装元素时可以使用合适的 template。动态列表的 key 要放在对应的遍历层并稳定唯一，不能为了消除优先级问题又遗漏项目身份，造成输入和状态错位。

5. v-for 优先不代表先创建全部 DOM 再判断，这里是编译与作用域规则。迁移时应检查原模板语义，验证过滤、空列表和开关变化，使用结构清楚的写法，而不是依赖某个版本恰好支持的组合顺序。

## 追问：只想隐藏整张列表，为什么要把条件放外层？

1. 整张列表是否出现由一个整体条件决定，与某一项的属性无关，外层 v-if 能直接表达这种关系。读模板时先看到区域是否展示，再看到内部数据如何遍历，不必在每个列表项上重复解释同一开关。

2. 条件为假时对应区域不会按普通显示方式创建，可避免无意义的子组件初始化。若需要频繁切换并保留内部状态，可以再考虑 v-show 或缓存，但这是生命周期选择，与让 v-if 和 v-for 争同一个节点的优先级不同。

3. 我会同时处理列表为空时的提示，让“区域关闭”和“区域打开但没有数据”有不同展示。这样条件层次对应真实产品状态，测试也能分别验证，不会一个混合指令导致所有空白都看起来一样。

## 追问：computed 过滤之后，用下标当 key 还会有问题吗？

1. 仍然可能有问题，过滤会改变项目位置，下标并不代表稳定业务身份。原来第三项变成第一项后，如果沿用位置身份，行内草稿、展开和焦点可能复用给另一条数据，过滤方式正确不等于 key 选择也正确。

2. 应优先用原始记录的稳定编号，过滤后的数组继续保留该编号。没有编号的临时项目可以在创建时生成并保存，不应每次 computed 重新计算时再生成随机 key，否则过滤重算就会重建全部组件。

3. 测试可以先编辑一行，再修改过滤条件让其他行消失，确认这行仍携带自己的草稿。纯文本刷新很容易掩盖错误身份，加入真实交互才能说明 computed 和列表复用两部分同时符合预期。
