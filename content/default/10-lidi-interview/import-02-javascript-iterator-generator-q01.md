# 生成器和 async/await 是什么关系？

## 核心回答

1. 生成器和异步函数都能让函数在某处暂停，但控制方式不同。调用生成器函数先得到迭代器，函数体要在推进时才开始执行；普通生成器遇到 `yield` 交出一个值后，通常由调用者再次调用 `next()`继续运行。

2. 调用异步函数会得到一个 `Promise`，函数体从调用时开始执行，到 `await` 处暂停后，后续代码在等待结果确定后恢复。暂停的是当前函数的后续流程，并不会阻塞整个线程。它适合把异步请求的先后依赖写成顺序代码，不需要业务调用方手动决定每一次怎样推进。

3. 普通生成器即使产出一个 `Promise`，也不会自动等待它完成，要靠执行器接收结果、等待并把值传回生成器。早期异步流程可以这样实现，但不能因此说原生异步函数一定是由生成器实现的，两者有各自的语言规则。

4. 如果目标是逐个产生同步结果，生成器比较合适；如果只要获得一次异步操作的最终结果，我会用异步函数。还有异步生成器，它可以在等待异步数据后继续产出多个值，通过异步迭代消费，适合按需获取连续结果，而不是一次返回所有内容。

## 追问：生成器执行器怎样把 Promise 的结果和异常传回去？

1. 执行器先调用 `next()`取得当前产出的值，然后等待这个值代表的异步结果。成功后把结果作为下一次推进的参数传入，生成器中暂停的产出表达式就能收到该值，继续执行后面的语句。

2. 如果等待失败，执行器应通过迭代器的 `throw(error)` 方法把错误送回暂停位置，而不是只在执行器外部打印日志。这样生成器内部围绕产出表达式写的异常捕获才有机会处理失败，决定恢复执行还是向外传播。

3. 每次推进还要看结束标记，生成器完成后应返回最终结果，并处理推进本身同步抛出的异常。这些都是执行器额外承担的工作，所以普通请求流程直接使用异步函数，通常比自行维护这套推进逻辑更容易解释和排查。

## 追问：异步生成器是否能自动并行请求多页数据？

1. 异步生成器提供暂停、等待和逐个产出的能力，不会自动把分页请求变成并行操作。假如下一页游标依赖上一页响应，逻辑本身就有先后关系，换成生成器语法也不能消除这个依赖。

2. 如果每页参数独立，可以另外设计有限数量的并发请求，再决定按照完成顺序还是页码顺序产出。这个顺序会影响用户看到的数据，因此并发数量、结果缓存和失败处理都需要显式安排，不能归功于生成器自动处理。

3. 消费者提前停止时，还要处理正在进行的请求与资源清理，停止继续迭代不等于取消所有外部工作。若设计了取消信号，应将它传给支持取消的操作，而且取消也不代表服务器已经完成的写入会被撤销。
