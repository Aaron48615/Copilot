# 为什么要定义事件协议？

## 核心回答

1. 我认为事件协议主要是把“收到一段字节”变成“发生了一件能处理的事”。只拼字符串时，很难区分正文、等待提示、错误和结束；明确事件类型后，前端才能决定追加文本、修改状态，还是停止继续等待。

2. 事件需要携带会话、生成任务或消息的标识，让客户端确认它属于哪次回答。再加协议版本和该生成内的序号，才能在重连、重复订阅或切换会话时避免串消息；这些字段的作用不同，不能只拿一个时间戳全部代替。

3. 我会明确文本字段是增量还是快照，比如 text 事件的 delta 只能追加一次，snapshot 的 text 则替换对应版本。下面是一条示意的 SSE 事件，真实发送时最后还必须有空行分隔；其中数字只表示演示序号。

    ```text
    event: text
    id: gen-1:7
    data: {"version":1,"generationId":"gen-1","seq":7,"delta":"你好"}
    ```

4. done、error 和主动停止应有不同语义，并约定是否为终态、终态后能否再接纳文本。传输层关闭、心跳和业务完成也分开处理；例如服务端停止生成但未发送完成事件时，客户端应该核对状态，不能猜测已经成功。

5. 协议也要写明重复事件、缺失事件、未知类型和版本不兼容的处理方式。同一连接里的流有序，序号主要帮助跨重连核对和应用层处理；它只能发现问题，真正补发仍依赖服务端留存，不会凭空恢复丢失的内容。

## 追问：重连收到重复序号或跳号时，客户端应该怎么做？

1. 我会以生成 id 加序号作为事件身份，保存最后连续接纳的位置。收到小于等于该位置的重放事件就跳过，防止把同一段字重复追加；同一身份却出现不同内容应视为协议异常，不能静默当作正常覆盖。

2. 若预期下一条是八，却收到十，不能一边显示十，一边宣称八和九已经处理。可以暂存后续事件并请求补发，或者查询带版本和序号的完整快照；只有完整核对后才推进恢复位置，避免永久跳过缺口。

3. 这些规则要求服务端明确序号作用域和连续性，比如心跳不占业务序号，快照带自己的覆盖位置。若回放记录已过期，就告知无法续传并取最终结果或重生成；无限重连既增加请求，也不能补出已经不存在的数据。

## 追问：以后新增事件类型，怎样兼容旧版客户端？

1. 我会先区分可选提示与必需语义，比如新增排队提示可以允许旧客户端忽略，但改变文本的追加规则就不能静默兼容。协议版本或能力协商要说明客户端能理解哪些行为，避免界面仍在运行却拼出了错误答案。

2. 在同一版本里，新增可选字段通常比删除或改名已有字段更容易兼容，但仍要做结构校验。未知的非关键事件可以不展示，同时按既定序号规则推进接收游标；未知终态或关键事件应停止猜测，并查询状态或报告不兼容。

3. 服务端不应直接把内部调试信息和模型内部过程原样暴露为公共事件，可以转换成稳定的用户状态。设计验证时我会准备旧事件样例、含新增字段的样例以及未知关键事件样例，检查能否按兼容规则处理，而不只测正常文本流。
