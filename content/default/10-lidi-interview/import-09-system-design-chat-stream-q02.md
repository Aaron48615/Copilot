# 为什么要定义事件协议？

## 核心回答

1. 事件协议是把「收到一段字节」变成「发生了一件能处理的事」。只拼字符串，很难分清正文、等待提示、错误、结束。事件类型明确了，前端才知道该追加文本、改状态，还是停止继续等。

2. 事件要带会话、生成任务或消息的标识，客户端才能确认它属于哪次回答。再加协议版本，以及这次生成内的序号，重连、重复订阅、切会话时才不容易串消息。这些字段作用不一样，一个时间戳替不了全部。

3. 文本字段是增量还是快照，要说清。比如 `text` 事件的 `delta` 只能追加一次，`snapshot` 的 `text` 则替换对应版本。下面是一条示意的 SSE 事件，真实发送时最后还必须有空行分隔；里面的数字只是演示序号。

    ```text
    event: text
    id: gen-1:7
    data: {"version":1,"generationId":"gen-1","seq":7,"delta":"你好"}
    ```

4. `done`、`error`、主动停止语义不同，是不是终态、终态之后还能不能再接纳文本，都要约定。传输层关闭、心跳、业务完成分开处理。服务端停了生成但没发完成事件，客户端该去核对状态，别猜已经成功。

5. 协议还要写重复事件、缺失事件、未知类型、版本不兼容怎么处理。同一连接里的流是有序的，序号主要帮跨重连核对、给应用层处理。它只能发现问题，真正补发还得服务端留着，丢了的内容凭空恢复不了。

## 追问：重连收到重复序号或跳号时，客户端应该怎么做？

1. 用生成 id 加序号当事件身份，保存最后连续接纳的位置。收到小于等于这个位置的重放事件就跳过，同一段字别追加两次。同一身份却出现不同内容，当成协议异常，别静默当正常覆盖。

2. 预期下一条是八，却收到十，不能一边显示十，一边宣称八和九已经处理。可以暂存后续事件并请求补发，或者查询带版本和序号的完整快照。完整核对之后才推进恢复位置，缺口别永久跳过。

3. 这些规则要求服务端说清序号作用域和连续性。比如心跳不占业务序号，快照带自己的覆盖位置。回放记录已经过期，就告知无法续传，取最终结果或者重生成。无限重连既增加请求，也补不出已经不存在的数据。

## 追问：以后新增事件类型，怎样兼容旧版客户端？

1. 可选提示和必需语义先分开。新增排队提示，旧客户端可以忽略；改了文本怎么追加，就不能静默兼容。协议版本或能力协商要说明客户端能理解哪些行为，别让界面还在跑，拼出来的答案却是错的。

2. 同一版本里，新增可选字段通常比删除或改名已有字段更容易兼容，结构校验还是要做。未知的非关键事件可以不展示，同时按既定序号规则推进接收游标。未知终态或关键事件就停止猜测，去查状态，或者报告不兼容。

3. 服务端别把内部调试信息、模型内部过程原样暴露成公共事件，可以转成稳定的用户状态。设计验证时准备旧事件样例、带新增字段的样例、未知关键事件样例，看能不能按兼容规则处理。只测正常文本流不够。
