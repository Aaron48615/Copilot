# 状态转换应该放在哪？

## 核心回答

1. 状态谁在用、转换规则复不复杂，决定放哪。只有一个组件用的简单请求，放组件或自定义 hook 里就行。多个地方都能触发转换，或者不同状态下允许的操作不同，适合把规则集中到 reducer 或转换函数里。

2. 转换函数接收当前状态和一个事件，看这一步允不允许，再返回下一个状态。只有失败后才能重试，处理重试事件时就要检查当前状态。事件类型写对了，不等于可以从任意状态直接跳进加载中。

3. 状态计算和网络请求尽量分开：转换函数只算下一个状态，外围负责发请求，成功或失败再当事件交回来。同样的状态和事件能得到可预测的结果，连续点击、失败重试、取消，这些转换规则也好单独核对。

4. 可辨识联合能限制每个状态带着哪些字段，旧请求盖住新请求它管不了。快速切换查询条件时，请求带上编号，收结果时核对当前编号。卸载、取消、重复完成这些事件，还得看它们还有没有资格改页面状态。

## 追问：reducer 已经用了联合类型，为什么还会出现非法状态转换？

1. 状态类型检查的是对象长什么样，比如成功状态必须有数据。它通常没直接写「成功事件只能接在某次加载之后」。空闲状态收到成功事件，造出来的对象类型上可能完全合法，业务流程上却不对。

2. 分支里同时看当前状态和事件，写明哪些组合能处理。只允许加载中接收对应请求的结果，其他组合保持原状或记下异常。别无论当前是什么状态，都直接换成成功对象。

3. 简单流程，清楚的条件判断和转换用例通常就够。规则非常多再考虑更完整的状态机工具。工具名字里有状态机，业务规则也不会自动被证明正确，允许和拒绝的转换还是要一条条对。

## 追问：连续搜索两次，第一次请求最后返回应该怎么处理？

1. 用户先搜甲再搜乙，页面当前要的是乙的结果，不能按响应到达顺序覆盖数据。每次搜索拿到新编号，编号跟加载状态一起存，回来的结果才能对上它属于哪一次请求。

2. 成功和失败都要对编号，不只过滤成功结果。不然甲请求虽然盖不住乙的数据，稍后失败时却可能把乙的成功页变成错误页，甚至靠旧请求的收尾提前关掉乙的加载提示。

3. 取消旧请求能少等一会儿，编号检查仍然有意义，因为响应可能已经到了，或者任务根本不支持取消。目标是让过期结果失去更新页面的资格。取消网络操作只是配合，替不了状态检查。
