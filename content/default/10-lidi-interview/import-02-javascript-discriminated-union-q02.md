# 状态转换应该放在哪？

## 核心回答

1. 我会先看状态由谁使用、转换规则是否复杂，再决定放在哪里。只有一个组件使用的简单请求，可以在组件或自定义 hook 中处理；多个地方都能触发转换，或者不同状态下允许的操作不同，就适合把规则集中到 reducer 或转换函数里。

2. 转换函数接收当前状态和一个事件，判断这一步是否允许，再返回下一个状态。假设只有失败后才能重试，就应该在处理重试事件时检查当前状态，而不是认为事件本身类型正确，就一定可以从任意状态直接进入加载中。

3. 我会尽量让状态计算与网络请求分开：转换函数只计算结果，外围逻辑负责发请求，并把成功或失败作为事件交回来。这样同样的状态和事件能得到可预测的结果，也容易单独检查连续点击、失败重试和取消等情况下的转换规则。

4. 可辨识联合能限制每个状态携带的字段，却不会自动替我解决旧请求覆盖新请求的问题。假设要支持快速切换查询条件，我会为请求附带编号，在接收结果时核对当前编号，并验证卸载、取消和重复完成事件是否仍然能改变页面状态。

## 追问：reducer 已经用了联合类型，为什么还会出现非法状态转换？

1. 状态类型检查的是对象的形状，比如成功状态必须有数据。它通常没有直接表达成功事件只能接在某次加载之后，所以从空闲状态接收成功事件，生成的对象仍可能在类型上完全合法，却不符合业务流程。

2. 我会在分支里同时检查当前状态和事件，明确哪些组合可处理。比如只允许加载中接收对应请求的结果，其他组合保持原状或记录异常，而不是无论当前是什么状态都直接替换成成功对象。

3. 对简单流程，清楚的条件判断和转换用例通常就够了；规则非常多时才考虑更完整的状态机工具。不能因为工具名字里有状态机，就认为业务规则已经被证明正确，仍要核对每条允许和拒绝的转换。

## 追问：连续搜索两次，第一次请求最后返回应该怎么处理？

1. 假设用户先搜索甲再搜索乙，页面当前需要的是乙的结果，不能仅按响应到达顺序覆盖数据。我会让每次搜索获得新的编号，并把编号与加载状态保存起来，让返回结果能说明它属于哪一次请求。

2. 成功和失败都要核对编号，不只过滤成功结果。否则甲请求虽然不会覆盖乙的数据，却可能在稍后失败时把乙的成功页面变成错误页，甚至通过旧请求的收尾逻辑提前关闭乙的加载提示。

3. 取消旧请求可以减少不必要的等待，但编号检查仍然有意义，因为响应可能已经到达或任务并不支持取消。这里的目标是让过期结果失去更新页面的资格，取消网络操作只是配合措施，不能代替状态检查。
