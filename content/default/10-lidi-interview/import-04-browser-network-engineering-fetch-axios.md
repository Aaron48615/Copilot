# fetch 和 axios 有什么区别？

## 核心回答

1. fetch 是浏览器提供的请求 API，Axios 是请求库，额外提供拦截器、超时配置和数据转换等能力。Axios 的底层实现取决于版本、环境和 adapter，不能一直把它定义成只封装 XHR；选型要看项目已经需要哪些能力。

2. fetch 收到 404、500 这类 HTTP 响应通常不会直接 reject，需要检查 response.ok 或状态码。它返回 Response 后还要读取响应体，读取和 JSON 解析也可能失败；Axios 默认对非成功状态拒绝，但这个规则可以配置。

3. 凭据方面，fetch 默认携带同源 Cookie，跨源携带需要设置 credentials 并满足服务端 CORS 和 Cookie 规则。不能说 fetch 默认完全不带 Cookie，也不能认为前端加一个选项就能越过浏览器的跨站限制。

4. 两者都可以结合 AbortController 取消请求。fetch 的超时可以使用受支持的超时 signal 或自行计时，Axios 提供 timeout；取消通常只是客户端停止等待，并不说明服务端已经撤销正在执行的业务操作。

5. 原有项目使用统一 Axios 实例处理 Token 和登录失效。对于流式读取，我会优先考虑 fetch 的 ReadableStream；上传进度要检查具体 adapter 能力，小功能也可用薄封装，团队统一错误约定往往比选择库名更重要。封装后我会分别测空响应、下载、取消和错误状态，确认业务能区分这些结果，而不是把所有响应都解包成同一种对象。

## 追问：fetch 返回 200，为什么 json() 仍会失败？

1. HTTP 成功只表示服务端返回了成功状态，不保证响应体一定是合法 JSON。代理配置错误可能把入口 HTML 当作接口结果返回，空响应或截断的 JSON 也会让解析失败，所以需要继续检查内容类型和实际响应。

2. 我会先看 Network 中的响应体，确认接口地址与反向代理规则。对于 204 这类本来没有内容的响应，应按接口约定直接处理，不要无条件调用 json；文件下载和文本接口也需要采用不同读取方式。

3. 封装层要保留足够的错误信息区分状态错误、解析失败和网络异常，但不要把敏感响应体直接上报。页面才能给出合适提示，排查时也不会把服务器返回 HTML 的问题误判成数据字段缺失。

## 追问：取消搜索请求以后，为什么还需要防止旧结果覆盖？

1. 取消信号到达时，请求可能已经完成，相关回调也可能正在排队，或者某个请求实现并未及时停止。只调用 abort 不能证明旧结果绝不进入状态更新，因此需要在业务层确认结果仍属于当前搜索。

2. 我会为每次查询记录递增标识或查询键，响应回来时与当前值比较，只有最新一轮才更新列表。取消用于减少无用工作，标识校验用于保证界面一致性，两者配合能处理快速输入和切换筛选条件。

3. 还要让旧请求的 finally 不会错误关闭新请求的 loading。测试时故意让较早的请求更晚返回，并覆盖取消、失败和清空输入，才能验证用户最终看到的确实是当前条件对应的数据。
