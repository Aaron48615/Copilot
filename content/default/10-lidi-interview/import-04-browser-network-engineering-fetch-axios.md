# fetch 和 axios 有什么区别？

## 核心回答

1. `fetch` 是浏览器提供的请求 API，Axios 是请求库，额外提供拦截器、超时配置、数据转换这些能力。Axios 底层实现取决于版本、环境和 adapter，不能一直把它定义成只封装了 XHR。选型看项目已经需要哪些能力。

2. `fetch` 收到 404、500 这类 HTTP 响应，通常不会直接 reject，得检查 `response.ok` 或状态码。它返回 Response 之后还要读响应体，读取和 JSON 解析也可能失败。Axios 默认对非成功状态拒绝，但这个规则可以配。

3. 凭据方面，`fetch` 默认携带同源 Cookie，跨源携带需要设 `credentials`，并且满足服务端 CORS 和 Cookie 规则。不能说 `fetch` 默认完全不带 Cookie，也不能认为前端加一个选项就能越过浏览器的跨站限制。

4. 两者都可以结合 `AbortController` 取消请求。`fetch` 的超时可以用受支持的超时 signal，或者自己计时；Axios 提供 `timeout`。取消通常只是客户端停止等待，不说明服务端已经把正在执行的业务操作撤掉了。

5. 原有项目用统一 Axios 实例处理 Token 和登录失效。流式读取优先考虑 `fetch` 的 ReadableStream；上传进度要看具体 adapter 能力。小功能也可以薄封装一层。团队统一错误约定，往往比选哪个库名更要紧。封装之后分别测空响应、下载、取消和错误状态，确认业务能把这些结果分开，别把所有响应都解包成同一种对象。

## 追问：fetch 返回 200，为什么 json() 仍会失败？

1. HTTP 成功只表示服务端回了成功状态，不保证响应体一定是合法 JSON。代理配错可能把入口 HTML 当成接口结果返回，空响应或截断的 JSON 也会让解析失败。所以还要看内容类型和实际响应。

2. 先看 Network 里的响应体，确认接口地址和反向代理规则。对 204 这类本来没有内容的响应，按接口约定直接处理，别无条件调 `json`。文件下载和文本接口也要用不同的读取方式。

3. 封装层要留够错误信息，把状态错误、解析失败、网络异常分开，但别把敏感响应体直接上报。页面才能给出合适提示，排查时也不会把服务器返回 HTML 的问题，误判成数据字段缺失。

## 追问：取消搜索请求以后，为什么还需要防止旧结果覆盖？

1. 取消信号到达时，请求可能已经完成，相关回调也可能正在排队，或者某个请求实现并没有及时停住。只调 abort，不能证明旧结果绝不进入状态更新。业务层还得确认结果仍属于当前这次搜索。

2. 每次查询记一个递增标识或查询键，响应回来时跟当前值比，只有最新一轮才更新列表。取消用来少做没用的活，标识校验用来保证界面一致。两者配合，才能应付快速输入和切换筛选。

3. 旧请求的 `finally` 也不能错误关掉新请求的 loading。测试时故意让较早的请求更晚返回，并覆盖取消、失败、清空输入。用户最终看到的，得是当前条件对应的数据。
