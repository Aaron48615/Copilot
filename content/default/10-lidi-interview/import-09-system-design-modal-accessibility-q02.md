# 如何测试？

## 核心回答

1. 我会先把弹窗行为写成可观察的检查项，再选择测试工具。比如用键盘打开后，焦点应该到约定的输入框或标题；不能只断言弹窗节点存在，因为节点显示正确时，键盘焦点仍可能留在背景。

2. 焦点测试覆盖 Tab 正向、Shift 加 Tab 反向和动态内容变化。到达最后一个控件后应回到弹窗内部起点，禁用或隐藏控件不能参与顺序；弹窗没有普通输入控件时，也要有合适的初始焦点和可用的关闭入口。

3. 关闭测试分别走取消按钮、Escape 和业务允许的遮罩点击，确认焦点恢复及背景状态释放。若触发按钮因删除记录而消失，应移动到相邻记录或列表入口；如果有未保存内容，还要验证关闭确认不会丢掉草稿。

4. 语义检查确认弹窗有可访问名称，标题关联指向真实元素，图标关闭按钮也有明确名称。然后用读屏器实际打开和阅读，检查是否能理解标题、表单标签和错误信息，不能只因为写了 aria 属性就判定通过。

5. 自动化适合稳定回归打开关闭和焦点路径，人工补充读屏、缩放、移动端软键盘和长内容滚动。测试报告要写明浏览器及辅助技术环境，并区分实际运行与计划覆盖；通过一次扫描不代表所有用户都能顺利完成操作。

## 追问：自动化无障碍扫描通过了，还可能漏掉什么？

1. 扫描工具能发现一些缺失名称、无效关联或对比度问题，但不能替用户判断焦点落点是否合理。比如删除确认框打开后直接聚焦删除按钮，结构可能合法，却比先聚焦取消按钮更容易造成误操作。

2. 它也不一定能识别完整操作过程中的时序问题，例如关闭动画结束后又把焦点拉回已隐藏区域。我的人工检查会从打开开始，一直走到提交失败、修正输入和关闭，而不是只检查某一个静态页面状态。

3. 读屏播报是否冗长、错误提示是否出现得及时，也需要实际体验。长说明全部塞进 aria-describedby 可能让首次播报难以理解，我会保留内容本身的阅读结构，并检查用户能否找到下一步操作。

## 追问：怎样稳定测试关闭后的焦点恢复？

1. 测试先通过真实的触发按钮打开弹窗，并记录预期恢复目标，再用用户可用的方式关闭。等待实际关闭状态完成后断言当前活动元素，不能只调用组件内部关闭函数，否则会漏掉事件绑定和默认行为的问题。

2. 我会分别覆盖触发按钮仍存在、被禁用和被删除三种情况。后两种需要预先约定替代目标，例如列表标题或下一条记录；断言只要求焦点不在弹窗内太宽松，因为焦点掉到 body 也可能被误判为成功。

3. 异步提交后关闭要控制接口完成时机，并验证失败时弹窗仍打开且错误可被感知。关闭成功后再触发一个迟到的旧响应，检查它不会重新聚焦输入框；这样才能覆盖视觉关闭后仍被异步任务干扰的问题。
