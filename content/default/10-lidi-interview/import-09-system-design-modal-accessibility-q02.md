# 如何测试？

## 核心回答

1. 弹窗行为先写成能观察的检查项，再选测试工具。用键盘打开之后，焦点该到约定的输入框或标题。只断言弹窗节点存在不够：节点显示对了，键盘焦点仍可能留在背景。

2. 焦点测试覆盖 Tab 正向、Shift 加 Tab 反向，以及动态内容变化。到最后一个控件之后应回到弹窗内部起点，禁用或隐藏的控件不参与顺序。弹窗没有普通输入控件时，也要有合适的初始焦点，以及能用的关闭入口。

3. 关闭分别走取消按钮、Escape、业务允许的遮罩点击，确认焦点恢复、背景状态释放。触发按钮因为删除记录消失了，就移到相邻记录或列表入口。有未保存内容，还要验关闭确认不会丢掉草稿。

4. 语义上确认弹窗有可访问名称，标题关联指向真实元素，图标关闭按钮也有明确名称。再用读屏实际打开和阅读，看能不能理解标题、表单标签、错误信息。写了 aria 属性，不等于通过。

5. 自动化适合稳定回归打开关闭和焦点路径。读屏、缩放、移动端软键盘、长内容滚动，人工补。报告写明浏览器和辅助技术环境，实际跑了什么、计划覆盖什么分开说。一次扫描通过，不代表所有用户都能顺利做完操作。

## 追问：自动化无障碍扫描通过了，还可能漏掉什么？

1. 扫描工具能发现一些缺失名称、无效关联、对比度问题，但替用户判断不了焦点落点合不合理。删除确认框打开后直接聚焦删除按钮，结构可能合法，却比先聚焦取消更容易误操作。

2. 完整操作过程中的时序问题，它也不一定能识别。比如关闭动画结束后又把焦点拉回已隐藏区域。人工检查从打开开始，一直走到提交失败、修正输入、关闭，别只查某一个静态页面状态。

3. 读屏播报是否冗长、错误提示是否出现得及时，也要实际体验。长说明全部塞进 `aria-describedby`，首次播报可能很难理解。内容本身的阅读结构留着，再看用户能不能找到下一步操作。

## 追问：怎样稳定测试关闭后的焦点恢复？

1. 测试先通过真实的触发按钮打开弹窗，记下预期恢复目标，再用用户能用的方式关闭。等实际关闭状态完成后再断言当前活动元素。只调组件内部关闭函数，事件绑定和默认行为上的问题会漏。

2. 触发按钮仍存在、被禁用、被删除，三种分开覆盖。后两种预先约定替代目标，比如列表标题或下一条记录。断言只要求焦点不在弹窗内太松，焦点掉到 `body` 也可能被误判成功。

3. 异步提交后关闭，要控制接口完成时机。失败时弹窗仍打开，错误能被感知。关闭成功后再丢一个迟到的旧响应，检查它不会重新聚焦输入框。视觉关了之后仍被异步任务干扰，这种问题才能盖到。
