# 断线重连会不会重复消息？

## 核心回答

1. 断线重连可能出现重复消息。客户端收到内容、业务处理成功、服务端知道处理成功，不是同一个时刻。网络在任意一步中断后，服务端为了避免漏发，可能重放一段事件。重新连接不等于天然只发全新数据。

2. SSE 可以通过事件 `id` 和 `Last-Event-ID` 帮助恢复位置，但服务端需要真的保留事件，并支持按标识重放。原生 `EventSource` 会参与自动重连。手动 `fetch` 读流则要自己保存位置、构造重连请求。两边的能力不能混着假设。

3. 客户端按稳定事件标识去重，业务写入也要有幂等约定。只按消息正文比较不可靠，两次合法通知可能文本相同。只在内存里存已读集合，也盖不住刷新后的重复。重要业务的最终去重，应有可靠的服务端机制。

4. 恢复还要处理顺序和缺口。比如客户端上次看到某个序号，重连后服务端已经清掉那段历史，就需要重新拉快照，再继续增量。缺消息时只把后续内容接上，界面看起来在线，状态却悄悄少了一段。

5. 中途断网、重复事件、历史过期都要测恢复，登录状态也校验。自行管理重连时用退避。原生 `EventSource` 的重连等待由浏览器和 `retry` 字段控制。实时 UI 展示和真正业务提交分开。连接恢复了就重复落库不行，为了去重误删两条本来不同的消息也不行。

## 追问：Last-Event-ID 能保证消息只处理一次吗？

1. 不能。它表示浏览器记录的事件位置，不等于业务已经成功处理。比如浏览器记录到了 42，本地保存第 42 条却失败了，自动从 42 之后恢复就可能漏掉它。幂等能防重复，补不回这条遗漏。

2. 业务处理成功的位置单独保存。失败事件先重试，或通过恢复接口从已确认位置重放。位置按连续完成的顺序推进。42 失败、43 成功，不能直接确认到 43。无法重放时重新拉快照，把界面恢复到确定状态。

3. 需要持久化的操作再用幂等键，防止重放时重复写入。普通显示按稳定事件 ID 去重。测接收后处理前断线、保存失败、保存成功后断线，分别看有没有漏消息、有没有重复记录。只验证连接重新建立，不够。

## 追问：服务端只保留最近消息，客户端离线很久怎么办？

1. 重连时服务端应能识别客户端位置已经超出历史保留范围，并返回明确的重新同步信号。悄悄从最新事件开始，客户端可能还留着早已过期的状态，看起来正常，数据并不完整。

2. 先拉当前快照，得到跟它对应的增量起点，再继续接收事件。快照和增量之间要有一致的版本约定。拉快照期间发生的新变化可能丢失或重复。先随便请求列表再打开流，对不齐。

3. 界面在同步期间显示合理状态，用户未提交的本地输入要留着。长时间离线、快照获取失败、同步期间再次断线都要测。用户能恢复到确定状态，而不是反复清空页面却一直追不上服务端。
