# 断线重连会不会重复消息？

## 核心回答

1. 断线重连可能出现重复消息，因为客户端收到内容、业务处理成功和服务端知道处理成功之间并不是同一个时刻。网络在任意一步中断后，服务端为了避免漏发可能重放一段事件，因此不能把重新连接理解成天然只发全新数据。

2. SSE 可以通过事件 id 和 Last-Event-ID 帮助恢复位置，但服务端需要真的保留事件并支持按标识重放。原生 EventSource 会参与自动重连，手动 fetch 读流则需要自行保存位置和构造重连请求，二者不能混用能力假设。

3. 客户端按稳定事件标识去重，业务写入也要有幂等约定。只按消息正文比较不可靠，两次合法通知可能文本相同；只在内存保存已读集合也无法覆盖刷新后的重复，因此重要业务的最终去重应有可靠的服务端机制。

4. 恢复还要处理顺序和缺口，例如客户端上次看到某个序号，重连后服务端已清理那段历史，就需要重新拉取快照再继续增量。不能在缺消息时只把后续内容接上，让界面看起来在线却悄悄少了一段状态。

5. 我会用中途断网、重复事件和历史过期测试恢复，并校验登录状态。自行管理重连时采用退避；原生 EventSource 的重连等待由浏览器和 retry 字段控制。实时 UI 展示与真正业务提交应分开，不能因为连接恢复就重复落库，也不能因为需要去重就误删两条本来不同的消息。

## 追问：Last-Event-ID 能保证消息只处理一次吗？

1. 不能，它表示浏览器记录的事件位置，不等于业务已经成功处理。例如浏览器记录到了 42，但本地保存第 42 条失败，自动从 42 之后恢复就可能漏掉它；幂等能防重复，却不能补回这条遗漏。

2. 我会独立保存业务处理成功的位置，失败事件先重试，或通过恢复接口从已确认位置重放。位置应按连续完成的顺序推进，不能 42 失败、43 成功就直接确认到 43；无法重放时重新拉快照，把界面恢复到确定状态。

3. 需要持久化的操作再用幂等键防止重放时重复写入，普通显示则按稳定事件 ID 去重。测试在接收后处理前、保存失败和保存成功后断线，分别检查有无漏消息与重复记录，不能只验证连接重新建立。

## 追问：服务端只保留最近消息，客户端离线很久怎么办？

1. 重连时服务端应能识别客户端位置已经超出历史保留范围，并返回明确的重新同步信号。不能悄悄从最新事件开始，因为客户端可能继续保留早已过期的状态，看起来正常但数据并不完整。

2. 我会先拉取当前快照，得到与它对应的增量起点，再继续接收事件。快照与增量之间要有一致的版本约定，否则拉快照期间发生的新变化可能丢失或重复，不能简单先请求列表再随便打开流。

3. 界面在同步期间显示合理状态，并保留用户未提交的本地输入。验证长时间离线、快照获取失败和同步期间再次断线，确保用户能恢复到确定状态，而不是反复清空页面却一直追不上服务端。
