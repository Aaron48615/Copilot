# 设计一个搜索联想组件，你会怎么拆？

## 核心回答

1. 拆成输入状态、请求调度、结果缓存、建议展示四块。正在输入的文字和已经确认的选项分开。输入商品名时，用户只移动高亮，不该马上改掉原文本。按 Enter 或点候选之后，才确认选择。

2. 输入变化后先处理空值和中文组合输入，再按业务要求判断要不要查询，远程请求做防抖。等待时间和最小长度没有固定标准，看词库和输入习惯。粘贴、清空、输入法确认，都进同一套状态处理。

3. 每次有效输入变化，马上更新查询版本，不再需要的请求取消掉。响应回来之后，只允许当前版本写入状态。防抖等待期间，旧响应也必须失效。成功、错误、加载结束都要检查。只调用 `AbortController` 替不了完整的状态判断。

4. 缓存保存有限数量、有限时间的同条件结果，键包含关键词，以及语言、筛选项、用户范围。展示上把加载、空结果、错误分开。旧关键词的建议不能冒充当前结果。服务端返回的文本按普通文本渲染，高亮时不直接拼不可信 HTML。

5. 交互用适合输入框联想的 combobox：列表支持方向键移动、Enter 选择、Escape 收起，活动项和展开状态同步。服务端另外负责授权、限流、查询成本，前端按接口约定消费候选。排序不符合预期，先核对请求条件和响应顺序，再跟服务端确认排序规则。

## 追问：输入法组合期间，防抖和 Enter 应怎样配合？

1. 中文输入时，拼音和候选词选择会产生中间输入事件。记下 `compositionstart` 到 `compositionend` 的组合状态。组合期间先不发联想查询，结束之后读最终文本，再按正常规则调度。未确认的内容别当成关键词。

2. 组合过程中按 Enter，可能只是确认候选字，不能同时选中联想列表或提交整个表单。键盘处理要结合组合状态和事件信息，浏览器输入法行为留着。别为了方便选第一项，就无条件拦截所有 Enter。

3. `compositionend` 附近还可能有相邻的 input 事件，最终值交给统一调度逻辑，避免重复请求。测试按目标浏览器和输入法验事件顺序。组合结束后马上删除也要覆盖，确认旧建议不会重新冒出来。

## 追问：上下键选择建议时，焦点和高亮怎么保持一致？

1. 对输入框加 listbox 的方案，DOM 焦点留在输入框，用稳定的选项 ID 更新 `aria-activedescendant`。用户还能继续改文字，读屏也知道当前活动建议。只改背景颜色，表达不了选择位置。

2. 活动索引变了，选项状态跟着同步，对应条目滚到可见范围。别出现读屏指一项、视觉高亮另一项。新结果到达后重新校验索引，原选项没了就清掉活动状态，别还引用已经被移除的节点。

3. Enter 只确认当前有效候选。Escape 收起列表，输入按约定保留。左右键这类文本编辑尽量交给浏览器。鼠标选择也复用同一套确认逻辑。失焦和点击的先后顺序要处理，别列表先关了导致点击没效果。
