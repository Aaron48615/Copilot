# 设计一个搜索联想组件，你会怎么拆？

## 核心回答

1. 我会拆成输入状态、请求调度、结果缓存和建议展示四部分，并区分正在输入的文字与已确认的选项。比如输入商品名时，用户只移动高亮不应马上改掉原文本，按 Enter 或点击候选后才确认选择。

2. 输入变化后先处理空值和中文组合输入，再按业务要求判断是否查询，并对远程请求做防抖。等待时间和最小长度不是固定标准，要看词库和输入习惯；粘贴、清空和输入法确认都需要进入同一套状态处理。

3. 每次有效输入变化立即更新查询版本，取消不再需要的请求，响应回来后只允许当前版本写入状态。防抖等待期间旧响应也必须失效，而且成功、错误和加载结束都要检查；仅调用 AbortController 不能代替完整的状态判断。

4. 缓存保存有限数量、有限时间的同条件结果，键包含关键词及语言、筛选项和用户范围。展示明确区分加载、空结果和错误，旧关键词的建议不能冒充当前结果；服务端返回的文本按普通文本渲染，高亮时不直接拼接不可信 HTML。

5. 交互采用适合输入框联想的 combobox 模式，列表支持方向键移动、Enter 选择和 Escape 收起，并同步活动项与展开状态。服务端另外负责授权、限流和查询成本，前端按接口约定消费候选结果。若排序不符合预期，我会先核对请求条件与响应顺序，再与服务端确认排序规则。

## 追问：输入法组合期间，防抖和 Enter 应怎样配合？

1. 中文输入时，拼音和候选词选择会产生中间输入事件，我会记录 compositionstart 到 compositionend 的组合状态。组合期间先不发联想查询，结束后读取最终文本，再按正常规则调度，避免把未确认内容当成关键词。

2. 组合过程中按 Enter 可能只是确认候选字，不能同时选中联想列表或提交整个表单。键盘处理要结合组合状态和事件信息，保留浏览器输入法行为；不能为了方便选择第一项，就无条件拦截所有 Enter。

3. compositionend 附近还可能有相邻 input 事件，所以需要把最终值交给统一调度逻辑，避免重复请求。测试会按目标浏览器和输入法验证事件顺序，并覆盖组合结束后马上删除，确认旧建议不会重新出现。

## 追问：上下键选择建议时，焦点和高亮怎么保持一致？

1. 对输入框加 listbox 的方案，我会让 DOM 焦点留在输入框，用稳定的选项 ID 更新 aria-activedescendant。这样用户还能继续编辑文字，读屏器又能知道当前活动建议；仅改变背景颜色不足以表达选择位置。

2. 活动索引变化时同步选项状态，并把对应条目滚动到可见范围，不能出现读屏指向一项而视觉高亮另一项。新结果到达后重新校验索引，原选项不存在就清理活动状态，避免仍引用已经被移除的节点。

3. Enter 只确认当前有效候选，Escape 收起列表并按约定保留输入，左右键等文本编辑操作尽量交给浏览器。鼠标选择也复用同一确认逻辑，同时处理失焦与点击的先后顺序，防止列表先关闭导致点击没有效果。
