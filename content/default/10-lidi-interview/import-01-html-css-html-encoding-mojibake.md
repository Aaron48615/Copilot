# 浏览器打开网页出现乱码，是什么原因？

## 核心回答

1. 乱码通常是字节在某一步被按错误编码解读，或者内容到达浏览器之前已经坏了。文件实际按一种编码保存，响应头却声明另一种，浏览器按声明解释，中文就可能变形。别先假设原始字节一定没问题，证据一段段核对。

2. 先看网络响应里的内容和 `Content-Type`，再看文档的 charset 声明和实际文件编码。一般统一用 UTF-8，`meta charset` 放在文档前部。编码判断还有 BOM 这类规则，「响应头永远最高」不是完整优先级。只改 meta、不管服务器头，也不够。

3. 页面框架文字正常，只有接口数据乱码，查接口响应和服务端存取过程，别继续改 HTML 模板。重复编码、错误解码后再保存，内容可能已经变坏。这时浏览器端换字体或改声明，无损恢复不了，得从仍正确的原数据重新处理。

4. 还要分清缺字形和乱码。字符编码对了，字体缺对应字形，可能显示方框，这时查后备字体和字体文件。先确定哪一段文本开始异常，再对照传输字节、解码结果和字体呈现，别把不同问题都归成「中文兼容性」。

## 追问：改成 UTF-8 后为什么已经保存的文字仍然乱码？

1. 编码声明只影响后面字节怎么解释，不会自动把以前的错误转换逆回去。服务端已经把错误解码后的字符串写进数据库，现在再统一输出 UTF-8，只会正确传输那串已经损坏的字符，看上去还是乱码。

2. 找最早仍正确的来源，比如原始文件、备份或提交记录，比较从输入、存储到输出的每一步。只有明确知道发生过什么转换，才谈得上可不可逆。别对所有字符串批量猜一套编码转换。

3. 修复先用少量样本验证，包含中文、符号和表情，原数据留着。若出现替代字符、信息已经丢了，就得承认单凭当前字符串完整恢复不了，从可靠源重新导入。反复转码直到「看着像中文」，更危险。

## 追问：如何判断是字体缺字还是字符解码错误？

1. 把这段文本复制到支持相应字符的编辑器，或者直接看实际字符串。复制出去字符是对的，只在页面上方框，缺字体覆盖的可能性更大。复制出去也是无意义字符，继续查数据和解码过程。

2. 接着临时换成已知覆盖该字符的系统后备字体，看自定义字体有没有加载成功、是不是只含部分字形。有的字体按字符集裁过，常用中文正常，不代表生僻字或符号都能显示。多测几个常见汉字不够。

3. 最终拿网络内容和字符串码点当证据，别凭方框外观下结论，替代字符也可能来自解码失败。确定是缺字就补好后备字体；确定是数据错误，就修产生错误的那一步。别用字体变化去盖内容损坏。
