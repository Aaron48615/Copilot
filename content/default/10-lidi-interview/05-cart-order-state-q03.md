# 如果用户连续点击加号怎么办？

## 核心回答

1. 当前用 updatingBasketIds 记录正在修改的购物车项，同一 basketId 发出请求后先限制重复操作，处理函数里也再检查一次。这样慢网下连续点击不会同时给同一项发送多个修改，其他商品仍可以各自操作。

2. 步进器给的是目标数量，而 changeItem 接口要差值。例如原来两件、用户改成三件，就传一，不是三；这需要先理解接口语义，否则后端可能把增加三件理解为最终五件，页面和实际购物车就会不同。

3. 请求成功后才修改本地数量，并刷新相关金额，失败则维持已确认数量。组件自身可能先展示输入值，所以仍要检查受控值与回调时序，不能只说“代码没赋值”就断言屏幕上一定没有短暂错误数量。

4. 减到零会调用删除接口并重新加载购物车，而不是仅隐藏这一行。请求结束后要释放该项锁，即使失败也不能让按钮永久禁用；全局一个 loading 会阻塞所有商品，不符合当前按项控制的做法。

5. 这种策略可能丢掉请求期间额外点击，但当前优先让操作顺序简单明确。如果要保留连续加减意图，需要另外设计目标数量合并；前端锁仍不能覆盖多设备或直接请求，库存和归属必须由后端确认。

## 追问：为什么不直接给加号加一个防抖？

1. 防抖能合并连续点击，但这里接口接收增量，必须准确理解最后想要多少件。如果只保留最后一次“加一”回调，用户点三次可能只增加一次；如果每次都累加，又要处理初始数量是否已被服务端改变。

2. 当前同一件商品要等本次修改完成才能继续点，逻辑简单，但慢网时用户需要等待。如果要支持连续点击，我会先记住最后想要的数量，等本次完成后按接口要求提交剩余差值；失败时重新查询实际数量，库存不足则提示用户调整。

3. 所以我会先选择用户可理解的交互，再决定防抖或队列方案。测试连续点三次、加减交错和接口失败，检查最终数量符合已接受的意图，不能只看请求次数减少就认为实现正确。

## 追问：请求成功但本地数量仍不一致，怎么办？

1. 先检查服务端是否调整了数量，例如库存限制让目标数量没有完全接受。如果接口只返回成功而没有最终数量，直接按本地旧值加差值可能不反映真实状态，需要查看响应契约或重新读取购物车。

2. 还要考虑其他设备同时修改，同一页面的 updatingBasketIds 只能约束本页。服务端应按真实购物车与库存处理，前端重新查询最终数量更可靠，不能把本页的点击限制当成数据库级并发保证。

3. 排查时记录 basketId、旧值、目标值、提交差值与返回结果，避免记录无关个人信息。确认是接口语义、并发还是显示绑定问题后再改，前端只能控制本页的操作顺序，多设备更新仍需要后端处理并发，再将实际结果返回页面。
