# 如果用户连续点击加号怎么办？

## 核心回答

1. 现在用 `updatingBasketIds` 记正在改的那一行。同一个 `basketId` 发出去之后先拦住重复点，处理函数里再查一次。网慢时连点加号，不会同时给同一件发好几个修改；别的商品还能各自点。

2. 步进器给的是目标数量，`changeItem` 要的是差值。比如原来两件，用户改成三件，就传 `1`，不是 `3`。搞反了，后端可能把「加三件」当成最终五件，页面和真实购物车对不上。

3. 请求成功才改本地数量，并刷新相关金额；失败就维持已经确认过的数量。组件自己可能先把输入值画出来，所以还得看受控值和回调谁先谁后。别以为代码没赋值，屏幕上就一定不会闪一下错的数。

4. 减到零会走删除接口，再重新加载购物车，不是只把这一行藏掉。请求结束要把这项锁放开，失败也不能让按钮永远点不了。全局一个 loading 会把所有商品都卡住，现在是按项控制的。

5. 这样请求期间多点的次数可能丢掉，但操作顺序简单清楚。要保留连续加减，得另外记最后想要的数量，再按接口去凑差值。前端这把锁挡不住别的设备或直接打接口，库存和归属还是后端说了算。

## 追问：为什么不直接给加号加一个防抖？

1. 防抖能把连点合成一次，但这边接口吃增量，得搞清楚最后要几件。只留最后一次「加一」，用户点三次可能只加一件；每次都累加，又得面对初始数量是不是已经被服务端改过。

2. 现在同一件要等这次改完才能再点，逻辑简单，网慢时用户得等。要支持连点，可以先记住最后想要的数量，这次完成后按接口再交剩余差值；失败就重新查实际数量，库存不够再提示用户改。

3. 先把交互做成用户能看懂的，再决定防抖还是排队。测连点三次、加减交错、接口失败，看最终数量对不对得上已经接受的意图。请求次数少了，不代表数量对了。

## 追问：请求成功但本地数量仍不一致，怎么办？

1. 先看服务端有没有改过数量，比如库存不够，目标件数没全接住。接口只回成功、没有最终数量，本地拿旧值加差值可能对不上，得看响应约定，或者再拉一遍购物车。

2. 别的设备也可能同时在改。本页的 `updatingBasketIds` 只管这一页。真实购物车和库存由服务端处理，前端再查最终数量更靠谱。本页点不了，不等于数据库级并发已经搞定。

3. 排查时记下 `basketId`、旧值、目标值、交出去的差值和返回结果，别带上无关个人信息。先分清是接口语义、并发还是显示绑定，再动手改。前端只管本页顺序，多设备还得后端处理，再把实际结果送回页面。
