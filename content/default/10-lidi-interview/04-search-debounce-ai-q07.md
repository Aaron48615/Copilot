# 搜索联想拿到 AI 文本后为什么还要解析？

## 核心回答

1. 提示词要求五条短建议，但模型可能添加编号、说明句或把几个词写在同一行。前端不能把整段文本直接作为五个标签，必须先转换成页面期望的字符串数组，否则会出现超长标签或一条里挤着多个建议。

2. parseSuggestions 按换行以及中英文逗号切分，去掉开头编号、短横线等，再 trim 空白。这个规则适合当前短搜索词，但不能推广为解析任意模型输出的通用方法，内容本身有逗号时也可能被切错。

3. 整理后每条限制十个字符，并取前五条，最终不足五条时使用本地备用规则。因此原文多于五条通常会先截取，并非一定触发失败；判断的是清洗后的数组，例如原文有六条有效建议，截取后仍可能正常得到五个标签。

4. 格式校验只能让页面结构可用，不证明建议相关或商品真实存在。模型返回五个无关词也可能通过长度检查，用户点击后仍需执行普通搜索，不能因为标签整齐就认为 AI 已经理解准确。

5. 如果继续完善，我会增加去重、空项与异常说明过滤，并检查截断后是否出现重复。对于中文和表情的长度还要确认按什么单位截取，界面要求与 JavaScript 字符串长度并不总是等价，不能一概说是十个汉字。

## 追问：为什么去重应该在截断之后再检查一次？

1. 两条原文可能不同，但前十个字符相同，截断后就变成重复标签。若只在原始文本阶段去重，页面仍然会出现多个一样的选项，看似返回五条，实际只给用户两三种选择。

2. 我会先做基础清洗，再按展示与提交策略处理长度，随后对最终建议去重。是否保留完整词作为提交值也要明确，不能标签显示一种含义，点击却搜索被截掉重要否定词的另一段内容。

3. 去重后不足要求时应按约定补充可靠备用内容或降低条数，而不是复制已有标签凑满。测试用长词、不同后缀与重复编号的样本，检查最终显示、点击参数和来源是否一致。

## 追问：为什么结构化 JSON 输出也仍然要校验？

1. JSON 只是格式，模型可能返回合法对象却字段名不对，或者数组里混着 null 和数字。JSON.parse 成功只能证明语法可解析，不能证明它符合搜索建议接口约定，也不能直接替代数组与字符串检查。

2. 如果以后改用结构化输出，我会明确 suggestions 的类型、数量和长度，并在服务端与前端必要边界验证。遇到错误仍按业务处理，不把模型返回的额外字段当作可以执行的指令或页面 HTML。

3. 语义相关性也不会由 JSON 自动保证。测试仍要包含格式正确却内容无关、重复或带危险文本的样本；结构化输出能减少解析歧义，但不能让推荐质量、安全渲染和请求状态这些工作消失。
