# TypeScript 在项目里是怎么用的？

## 核心回答

1. 轻购和城市视图使用的是 TypeScript，我日常主要用它描述接口数据、组件属性和页面状态。这些类型直接贴着调用边界写，能让我在传参或改字段时及时发现不一致，比只依赖记忆确认字段名称更方便，但不能因此省掉实际页面验证。

2. 请求层会用泛型统一外层状态码和业务数据的结构，让不同接口保留各自的数据类型。例如列表和详情可以共用外层响应约定，调用方仍然知道里面是数组还是单个对象，不过指定泛型不代表真实响应已经通过了运行时校验。

3. 组件属性会用 interface 描述，状态会用字面量联合类型约束，例如工单从待分配到已完成的几个状态。这样把拼错的字符串传入受检查的函数会报错，但它不能自动保证状态转换合理，也拦不住服务端传来的未知值，不能说非法状态绝对不会出现。

4. 我的使用习惯是对象结构优先用 interface，联合类型和工具类型用 type，通用列表则通过泛型保留行数据类型。这是为了让声明容易理解，并不是两者完全等价；接口可以声明合并，而类型别名还可以直接表达联合等其他形状。

5. 我比较看重重构时的提示，字段变化后编译器能指出参与检查的调用位置，帮助我逐个确认影响。遇到不确定的数据会先考虑 unknown 和收窄，避免让 any 到处传播；也不会为了一次简单传参堆复杂类型，维护者能看懂同样重要。

## 追问：请求函数写了泛型，为什么调用方仍可能拿到错误数据？

1. 泛型表达的是静态约定，调用方写用户类型，编译器就按这个约定提示属性，但服务器并不知道这个参数。例如接口实际返回错误对象，泛型不会自动把它变成用户，也不会在读取名称之前替代码插入检查。

2. 如果进一步完善请求层，我会让原始结果先经过结构校验，再进入泛型描述的业务返回值，这是改进设想。只在解析后直接断言为泛型参数，会把调用方的期望当成事实，封装虽然更短，却没有建立数据正确的依据。

3. 外层业务码和内层数据也应一起考虑，失败响应未必带有成功时的数据字段。可以通过成功与失败的联合结构表达差别，让调用方确认成功之后再取数据，避免为了统一外形而宣称每个响应都拥有完整业务对象。

## 追问：interface 和 type 的选择会影响实际代码组织吗？

1. 两者都能描述很多对象结构，我会先遵循项目约定，避免同一层代码混用得没有规律。组件属性通常用接口容易扩展，状态字符串集合则用类型别名更直接，没有必要为了偏好某个关键字把简单声明绕复杂。

2. 接口允许同名声明合并，这对扩展已有库的声明有用途，但也意味着重复名称可能改变整体结构。类型别名不能按这个方式重新声明，所以我会根据是否真的需要开放扩展来选，而不是简单说两者没有区别。

3. 对组合类型，还要考虑字段冲突后的可读性，例如交叉类型里的同名字段如果要求互相矛盾，结果可能无法构造。我会优先整理清楚共同字段和差异，避免通过复杂组合掩盖模型冲突，让报错留在更靠近声明的位置。
