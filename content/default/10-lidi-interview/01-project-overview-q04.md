# 轻购项目的目录和页面是怎么拆的？

## 核心回答

1. 轻购主要按职责拆目录。拿商品详情举例：页面负责接路由里的商品 ID、发起加载、保存页面状态，再把商品信息交给具体组件展示。这条过程分别放在页面、接口和公共工具里，不会全写进同一个文件。

2. `src/views` 放页面级组件，比如首页、搜索、商品详情、购物车和订单。这里主要处理本页的业务步骤，比如详情加载成功后显示规格选择，订单提交中禁用按钮。页面可以调其他模块，但不用知道每个接口的底层请求配置。

3. `src/api` 按业务放请求函数。页面调用 `getProductDetail` 或 `getCartInfo`，就能看出是要取商品详情还是购物车。接口地址、参数传递集中在这些函数里，后端路径变了，不用去多个页面里逐个找字符串。

4. 公共请求配置放在 `src/utils/request.ts`，处理 Axios 实例、Token 请求头、登录失效和基础请求方法。`token.ts` 只负责 Token 读写，部署恢复放在 `deploymentRecovery.ts`。出问题可以先判断是某个页面的数据，还是所有请求都会碰到的公共问题。

5. AI 也不是全塞在页面里。搜索联想和商品卖点的提示词、请求、解析、缓存和本地备用逻辑放在 `src/ai`；轻购AI页面用的推荐接口在 `src/api/guide.ts`。能复用的界面放进 `src/components`，比如底部导航、骨架屏和 SKU 面板。拆分看职责和复用情况，不是目录越多越好。

## 追问：什么内容该抽成组件，什么内容继续留在页面里？

1. 先看它是不是有比较独立的界面职责，或者已经在多个页面重复出现。底部导航和骨架屏有清楚的输入和展示规则，抽出来后，各个页面只需要传入配置，不必复制同一段模板。

2. 只有一个页面用的部分，也不一定不能拆。比如 SKU 面板包含规格选择、数量和确认动作，放在详情页里可能让页面很长，拆成组件后更容易看清各自做什么。但组件应该通过 props 和事件交换信息，别偷偷依赖很多页面变量。

3. 反过来，一段只有两三行、以后也未必复用的展示，没必要为了“组件化”再拆。拆完以后，页面是不是更容易理解，改一个功能要跳几个文件是不是合理，这个比统计组件数量更有用。

## 追问：公共请求层和业务接口层为什么要分开？

1. 它们处理的问题不同。公共请求层关心基础地址、请求头和通用错误，比如登录失效；业务接口层关心这次请求到底是查商品还是提交订单，以及参数和返回数据是什么。

2. 如果混在一起，公共请求函数里就可能到处判断某个商品页面需要什么字段，改购物车时还会影响到订单。分开以后，页面看到的是业务函数，公共请求配置可以统一调，不用让每个页面重复处理 Token。

3. 不过也不能把所有错误都在公共层直接弹提示。用户主动取消搜索，和订单提交失败，用户要看到的反馈不一样。公共层可以识别错误类型，页面再决定怎么提示，业务上的处理空间还留着。
