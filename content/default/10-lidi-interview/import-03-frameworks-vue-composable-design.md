# Vue 的 composable 应该怎么设计？

## 核心回答

1. 我会让 composable 围绕一件有状态的行为设计，例如 useSearch 管理查询，useEventListener 管理监听。它使用 Vue 的响应式和生命周期能力复用逻辑，但不应顺手决定页面布局、弹窗文案和权限策略，让调用组件仍能清楚表达业务流程。

2. 输入应说明支持普通值、ref 还是 getter，以及变化后是否重新执行。需要响应式跟踪时在监听范围内读取输入；把响应式值先取成普通字符串再传进去，可能只是传了快照，不能期待 composable 自动知道外部后续变化。

3. 返回值通常使用普通对象包含 ref 和方法，调用方解构后仍能保留响应式连接。状态默认在函数内部创建，使每次调用独立；如果需要共享，应明确由模块、祖先提供者或 store 持有，不能无意中让两个表单共享一个草稿对象。

4. 副作用必须有对应清理，例如监听要移除，请求要取消或失效，定时器要停止。使用组件生命周期的函数应在合适的 setup 上下文同步调用，服务端环境也不能直接假设 window 存在；异步延后创建监听可能需要手动管理停止时机。

5. 我会用接口能否解释清楚来判断抽取是否成功，并测试输入变化、失败和离开组件等行为。纯计算保持普通函数，复用尚不明确的小逻辑可以先留在组件；不能为了让页面只剩几行调用，把全部复杂度塞进一个难以阅读的万能 composable。

## 追问：为什么常见返回形式是普通对象里放多个 ref？

1. 调用方可以直接解构结果，如 data、loading 和 error，每个变量仍然是 ref，与内部状态保持连接。若返回一个 reactive 对象，直接解构其中的原始值属性，可能取出当时的值而失去后续响应式关联。

2. 普通对象也能同时返回 reload、cancel 等方法，把状态和可执行动作明确放在一个接口里。组件模板会按适用规则解包 ref，脚本中则通过 value 使用，调用者容易判断哪些是状态、哪些是操作。

3. 这是一种便于组合的约定，不代表 reactive 返回值一律错误。只要接口明确要求整体使用或通过 toRefs 解构，也能正确工作；关键是避免调用方按常见习惯解构后悄悄失去响应式，而不是只追求固定格式。

## 追问：composable 中的监听为什么要考虑调用时机？

1. 组件 setup 中同步建立的监听通常归属于当前组件作用域，卸载时能自动停止。若在 setTimeout 或 await 之后才额外创建监听，它可能不再具有同样的自动绑定关系，调用方离开后仍继续执行，需要明确保存停止函数。

2. 如果只是等待接口数据后才开始工作，可以先同步建立监听，在回调里判断数据是否就绪。这样既保留清晰生命周期，又不会因为异步初始化把资源创建藏到组件管理范围之外，停止行为更容易解释。

3. 不过自动停止监听不等于取消监听回调已经发起的请求和定时任务，那些仍需要清理或有效性判断。我会测试组件很快卸载的情况，确认迟到的初始化不会在页面离开后再创建一份没人管理的资源。
