# Vue 的 composable 应该怎么设计？

## 核心回答

1. composable 围着一件有状态的事来写，比如 `useSearch` 管查询，`useEventListener` 管监听。它用 Vue 的响应式和生命周期复用逻辑，页面布局、弹窗文案、权限策略还是调用组件自己说。业务流程别偷偷藏进工具函数里。

2. 输入要讲清：普通值、`ref` 还是 getter，变了会不会重跑。需要跟踪时，在监听范围内读输入。先把响应式值取出字符串再传进去，传的是当时那张快照，后面外面再变，composable 不会自己知道。

3. 返回常见是普通对象，里面放 `ref` 和方法，调用方解构以后还能跟上变化。状态默认在函数里创建，每次调用各一份。要共享，就明确由模块、祖先 `provide` 或 store 拿着。两个表单别无意中共用一份草稿。

4. 副作用有开就有关：监听要摘，请求要取消或标失效，定时器要停。用到组件生命周期的函数，在合适的 `setup` 上下文里同步调用。服务端别默认有 `window`。`await` 之后才去建监听，停止时机可能要自己管。

5. 抽得好不好，看接口能不能讲清楚。输入变化、失败、离开组件这些行为要测。纯计算保持普通函数；还不明确会不会复用的小逻辑，可以先留在组件。别为了页面只剩几行调用，把复杂度全塞进一个读不动的万能 composable。

## 追问：为什么常见返回形式是普通对象里放多个 ref？

1. 调用方可以直接解构 `data`、`loading`、`error`，每个还是 `ref`，跟内部状态连着。返回一个 `reactive` 对象，把里面的原始值属性解构出来，拿的可能是当时那个数字，后面就跟不上了。

2. 普通对象里还能一起返回 `reload`、`cancel` 这些方法，状态和动作放在一个接口里。模板会按规则解包 `ref`，脚本里用 `.value`。哪些是状态、哪些是操作，一眼能分。

3. 这是方便组合的约定，不是说返回 `reactive` 就一定错。接口要求整份用，或者用 `toRefs` 再解构，也能工作。怕的是调用方按习惯一解构，响应式悄悄没了。

## 追问：composable 中的监听为什么要考虑调用时机？

1. 组件 `setup` 里同步建的监听，通常跟着当前组件，卸载会自动停。放到 `setTimeout` 或 `await` 之后再建，未必还有这层自动绑定。人走了回调还在跑，就要自己存停止函数。

2. 只是等接口数据到了才开始干活，可以先同步建好听，回调里判断数据齐了没有。生命周期还清楚，也不会把资源创建藏到组件管不到的地方，停止行为更好讲。

3. 监听自动停了，不等于回调里已经发出去的请求和定时器也停了，那些还要清或做有效性判断。组件很快卸载也要测，迟到的初始化别在人走了以后再造一份没人管的资源。
