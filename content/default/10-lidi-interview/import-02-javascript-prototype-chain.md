# 原型链是什么？

## 核心回答

1. 原型链描述的是对象读取属性时的查找路径：先找自身，没有就沿内部原型继续找，直到找到属性或者到达 null。并不是每个对象都经过 Object.prototype，使用 Object.create(null) 创建的对象就直接以 null 为原型。

2. 实例的内部原型和构造函数的 prototype 属性需要分开理解，前者是对象的内部关联，后者是函数上的普通属性。普通构造函数通过 new 创建实例时，会把两者连接起来，但并非所有函数都有可用于构造的 prototype。

3. 原型最直观的作用是共享方法，例如数组通常从 Array.prototype 找到 map 和 push，不需要每个数组自己保存一套方法。普通属性读取只是沿链查找，不会顺便把找到的属性复制到实例自身。

4. 对象自身的同名属性会遮住原型属性，删除这个自身属性后，原型上的值可能重新被读到。赋值则还要考虑继承的 setter 和只读属性，不能简单认定所有写入都会在自身创建属性，更不会默认修改原型上的值。

5. 检查原型我会使用 Object.getPrototypeOf，而不依赖历史遗留的 __proto__。constructor 可以被改写，不能证明对象是谁创建的；instanceof 通常查找构造函数原型是否在链上，但自定义判定和跨窗口对象都需要额外注意。

## 追问：修改 prototype 和替换 prototype 有什么不同？

1. 假设先通过普通构造函数创建实例，再给原来的 prototype 对象增加方法，已有实例通常也能找到这个方法。原因是实例保留着对同一个原型对象的关联，而不是在构造时把当时的方法列表拍成一份快照。

2. 如果把构造函数的 prototype 整体替换成新对象，旧实例仍然指向原来的对象，之后创建的实例才采用新原型。此时旧实例对该构造函数的普通 instanceof 检查可能变成 false，因为检查使用的是当前的 prototype。

3. 替换时还可能丢失原型对象默认的 constructor 属性，但手动补回也不能改变旧实例的内部关联。实际维护中我会避免运行期间频繁替换原型；如果只是解释共享机制，用增加方法和整体替换两个例子就能展示区别。

## 追问：怎样区分自身属性、继承属性和不存在的属性？

1. 读取结果是 undefined 不足以区分这几种情况，因为一个真实存在的属性也可以把值设为 undefined。我会用 Object.hasOwn 判断自身是否定义了这个键，再用 in 判断自身或原型链上是否存在，从而避免把空值误判成缺字段。

2. 比如对象自身没有 toString，但普通对象通常可以从原型找到，所以 hasOwn 为假，in 却为真。对于字典类数据，这种继承字段可能干扰判断，因此不能仅凭 key in object 就认定用户提交了这个字段。

3. 我也不会直接相信 obj.hasOwnProperty 可调用，因为同名字段可能覆盖它，空原型对象也没有这个方法。处理外部输入时应先确定是否只接受自身字段，再做值校验，这样原型链不会悄悄参与本来只针对业务数据的判断。
