# JS 垃圾回收是怎么进行的？

## 核心回答

1. JavaScript 的垃圾回收主要由引擎管理，我会先用可达性解释它：从全局对象、活动执行状态等根出发，仍能沿引用找到的数据需要保留。业务已经不用但全局缓存还引用着的对象，对回收器来说仍然可达。

2. 标记阶段识别存活对象，之后可以清理不可达对象占用的空间，但真实实现不只有一句标记清除。以 V8 为例，还会结合分代、整理以及增量或并发工作降低开销，这些是引擎策略，不是语言保证的固定步骤。

3. 两个对象互相引用并不必然泄漏，只要这组对象已经无法从根访问，追踪式回收仍可处理它们。简单引用计数会受循环引用影响，所以判断问题时，我不会只数对象有几个引用，而会追踪这些引用来自哪里。

4. 常见问题是长期存活的监听、定时器或无上限缓存保留了本应结束的数据。假设页面关闭后，挂在全局对象上的监听仍引用页面状态，就应在对应生命周期解除监听，而不是期待回收器理解页面已经不用了。

5. 弱集合不会因为弱持有的对象而单独阻止回收，适合某些随对象生命周期存在的附加数据。它们不保证立即释放，也不能代替容量管理；排查时还应比较重复操作后的保留对象，不能把一次内存上涨直接当成泄漏。

## 追问：对象已经设为 null，为什么堆内存没有马上下降？

1. 给变量赋空值只是断开这一条引用，如果数组、监听回调或其他变量还保存同一个对象，对象仍然可达。假设全局缓存保存了结果，把函数里的临时变量清空，不会同时删除缓存中的那条记录。

2. 即使所有强引用都消失，对象也只是具备了回收条件，实际何时清理由引擎决定。回收后的空间还可能留在引擎堆中供后续分配使用，所以进程占用没有同步下降，也不足以说明对象没有被回收。

3. 我会用重复创建和释放的操作比较堆快照，检查对应对象数量及保留路径是否持续累积。还要避开调试器或控制台额外保存对象的干扰，将对象仍被引用与内存暂时保留给引擎这两种情况分开判断。

## 追问：WeakMap 能不能直接替代 Map，解决缓存无限增长？

1. 不一定，WeakMap 的键需要是可被弱持有的值，包括对象和未注册符号，不能直接使用普通字符串。假设缓存按接口地址字符串索引，它就不能直接替换原来的映射，更不能仅靠改类名解决内存占用问题。

2. 如果键对象还被全局列表长期持有，弱映射也不会使这个键失去可达性，对应缓存不一定释放。它适合为对象附加与其生命周期一致的数据，不适合用来承诺缓存多少条、何时过期等明确业务规则。

3. 弱映射也不提供枚举全部键或查询大小的接口，因此不方便做容量统计和逐项淘汰。假如目标是限制缓存增长，我会考虑有容量和过期策略的普通映射；是否使用弱映射，应先看键的来源和清理需求。
