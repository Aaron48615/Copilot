# JS 垃圾回收是怎么进行的？

## 核心回答

1. JavaScript 的垃圾回收主要由引擎管。从全局对象、活动执行状态这些根出发，还能沿引用找到的数据要留下。业务已经不用了，但全局缓存还引用着，对回收器来说仍然可达。

2. 标记阶段认出还活着的对象，之后可以清理不可达对象占用的空间。真实实现不只有一句「标记清除」。以 V8 为例，还会结合分代、整理，以及增量或并发工作来降低开销。这些是引擎策略，不是语言保证的固定步骤。

3. 两个对象互相引用，不一定泄漏。这组对象已经没法从根访问到，追踪式回收仍能处理它们。简单引用计数会被循环引用卡住。判断问题时，别只数对象有几个引用，要追这些引用来自哪里。

4. 常见问题是长期活着的监听、定时器、无上限缓存，把本该结束的数据留下了。页面关了，挂在全局对象上的监听仍引用页面状态，就该在对应生命周期摘掉监听。回收器不会理解「页面已经不用了」。

5. 弱集合不会因为弱持有的对象而单独阻止回收，适合某些跟着对象生命周期走的附加数据。它们不保证立刻释放，也替不了容量管理。排查时比较重复操作后还留下哪些对象。一次内存上涨，直接当泄漏太早。

## 追问：对象已经设为 null，为什么堆内存没有马上下降？

1. 给变量赋 `null` 只是断开这一条引用。数组、监听回调或其他变量还保存着同一个对象，对象仍然可达。全局缓存保存了结果，把函数里的临时变量清空，不会同时删掉缓存里那条记录。

2. 所有强引用都消失了，对象也只是具备了回收条件，实际何时清理由引擎决定。回收后的空间还可能留在引擎堆里给后续分配用。进程占用没有同步下降，也不足以说明对象没被回收。

3. 用重复创建和释放的操作比较堆快照，看对应对象数量和保留路径是不是持续累积。调试器或控制台也可能额外握着对象，要把「对象仍被引用」和「内存暂时留给引擎」分开看。

## 追问：WeakMap 能不能直接替代 Map，解决缓存无限增长？

1. 不一定。`WeakMap` 的键需要是可被弱持有的值，包括对象和未注册符号，普通字符串不能直接当键。缓存按接口地址字符串索引，就不能直接替换原来的映射，更不能只改个类名解决内存占用。

2. 键对象还被全局列表长期握着，弱映射也不会让这个键失去可达性，对应缓存不一定释放。它适合为对象附加跟它生命周期一致的数据，不适合用来承诺缓存多少条、何时过期这类明确业务规则。

3. 弱映射也不提供枚举全部键或查询大小的接口，容量统计和逐项淘汰不好做。目标是限制缓存增长，考虑带容量和过期策略的普通映射。用不用弱映射，先看键从哪来、清理需求是什么。
