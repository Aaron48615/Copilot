# SSR hydration 不一致通常是怎么造成的？

## 核心回答

1. hydration 是客户端 React 接管服务端生成的 HTML，并建立交互的过程。它要求客户端第一次渲染使用的结构和内容与服务端对应，不能认为已有 HTML 只是一个可以随意不匹配的加载占位。

2. 常见原因是 render 依赖不确定输入，例如 Date.now、随机数、本地时区或浏览器宽度。服务端没有 localStorage，如果服务端显示未登录、客户端首次直接按存储显示头像，两次输出也可能不同。

3. 另一类原因是结构和数据不一致，比如非法标签嵌套被浏览器纠正、服务端数据没有正确传入客户端缓存，或者两侧条件分支不同。我会对比实际返回 HTML、初始数据和首次渲染条件，而不是先把问题归到 React 本身。

4. 修复时优先统一首屏输入，浏览器特有的信息在挂载后读取，确实无法避免的局部才考虑客户端边界或有限使用 suppressHydrationWarning。还要测试直接访问、刷新和不同语言环境，因为客户端导航正常不代表 hydration 一定正确。

5. 我会把首屏一致和后续个性化分成两个阶段。例如主题先使用服务端确定的值，接管完成后再应用浏览器偏好；若切换会引起明显闪动，就继续调整主题初始化方案。消除警告不是唯一目标，还要让用户实际看到的内容稳定、可以正常交互。

## 追问：render 里用 typeof window 判断分支，为什么还会错？

1. 这个判断能避免服务端访问不存在的 window，却不能保证双方输出一致。服务端走“没有 window”的分支，客户端首次走另一分支，如果一个返回占位、另一个返回完整组件，仍然会出现结构差异。

2. 可以让服务端和客户端第一次都显示相同占位，提交后再设置客户端就绪状态，读取屏幕宽度等信息。这样判断的目的从“环境是否存在”变成“是否已完成首次接管”，两侧初始结构能够对应。

3. 如果只是响应式布局，我会优先使用 CSS 媒体查询，通常不必按 window.innerWidth 生成不同首屏树。只有需要不同交互逻辑时再使用 JS，并为客户端更新预留空间，减少明显闪动。

## 追问：为什么合法的 JSX 也可能生成有问题的首屏 HTML？

1. JSX 能编译不代表标签嵌套符合 HTML 规则。例如段落里嵌套某些块级元素，浏览器解析服务端字符串时可能自动关闭段落，实际 DOM 树与 React 预期结构就不一样。

2. 客户端纯渲染与浏览器解析 HTML 字符串的路径不同，所以只看开发时组件能显示，并不能排除服务端接管的问题。我会检查网络里的原始 HTML 和 Elements 中被解析后的 DOM，确认是否发生了浏览器修正。

3. 修复应调整语义结构，例如用合适的容器、正确的表格层级，而不是给外层加忽略警告。测试也要包含服务端输出再 hydration 的流程，普通组件挂载测试未必能覆盖这种差异。
