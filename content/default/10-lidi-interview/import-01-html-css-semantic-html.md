# 怎么理解语义化标签？

## 核心回答

1. 语义化就是用标签准确表达内容和操作的含义，例如导航用 nav，条目集合用列表，触发动作使用 button，页面跳转使用链接。它不是给每个 div 都换一个新标签，而是让读代码的人、浏览器和辅助技术能从结构知道这一块是什么。

2. button 与可点击 div 的区别最直观。原生按钮带有可聚焦、键盘激活等行为，也能表达禁用；div 加点击只实现了鼠标路径，其他行为需要补齐。表单中还要注意 button 的默认提交行为，非提交动作应明确 type，语义正确也需要配合正确配置。

3. 标题层级和页面区域能帮助用户理解内容组织，读屏用户可以按标题或地标导航。section 适合有主题的章节，article 适合相对独立的内容，普通样式容器继续用 div 即可。用标题标签只为了获得大字号，或跳着层级装饰页面，会削弱结构表达。

4. 语义化帮助描述内容含义，服务端渲染或预渲染则影响首个 HTML 响应中是否已有正文，两者解决的问题不同，换成语义标签不会自动让客户端渲染的页面拥有完整首屏 HTML。如果继续完善搜索访问体验，我会检查页面返回的正文和可访问链接，再评估渲染方式；ARIA 仍只补充名称和状态，需要结合键盘与读屏验证。

## 追问：按钮和链接外观一样时，应该根据什么选标签？

1. 我会根据用户操作后的结果选。跳转到一个资源或页面使用带 href 的链接，提交、删除、展开面板等改变当前状态的动作使用按钮；视觉样式可以相同，但语义和浏览器原生行为不同，不能按设计稿颜色决定标签。

2. 链接支持复制地址、在新标签页打开等常见操作，按钮则有对应的键盘激活与表单行为。用 button 模拟所有跳转，可能让用户失去预期操作；用无意义 href 模拟按钮，又可能带来位置变化或错误导航。

3. 在表单中，普通展开按钮要明确 type="button"，避免意外提交。验证时既看点击结果，也检查键盘和上下文菜单是否符合操作含义，只有外观一样不够，用户对两类控件的预期需要得到尊重。

## 追问：一个页面有多个导航区域，怎样让用户分清？

1. 可以保留多个 nav，但要为不同用途提供清楚名称，例如主导航与文章目录，让辅助技术的地标列表里能区分。名称可以关联可见标题，避免都叫“导航”却指向完全不同的一组链接，增加选择成本。

2. 内部仍然使用有意义的链接文字和列表结构，当前页面或当前位置可以通过适当状态表达。不要只用颜色或一个装饰箭头表示当前项，否则看不到颜色或使用读屏的用户可能不知道自己已经在哪个页面。

3. 我会检查地标数量是否过多，只有主要导航区域才需要强调，不必给每一小组链接都包 nav。结构要帮助快速定位，过度标记反而让导航列表变长；最终用标题和地标浏览一次，确认名称真正能说明区域用途。
