# 搜索框里为什么还要取消请求？

## 核心回答

1. 防抖解决的是输入频繁时何时发请求，不能管理已经发出去的请求。比如“手”的请求先发出但返回慢，“手机”的请求后发出却先返回，如果直接更新列表，最后页面反而可能显示旧关键词的结果。

2. 我会在输入一变化时就让旧结果失效，而不是等新请求真正发出后才处理。因为防抖还有等待窗口，旧请求可能在这个窗口内完成；递增输入版本号，并取消旧定时器和旧请求，可以把有效结果对应到当前输入意图。

3. 对支持取消的 `fetch`，每次请求使用新的 `AbortController`，把 `signal` 传进去，输入变化时调用旧控制器的 `abort()`。它能中止相关请求或响应体读取，但不能保证服务端没有处理请求，也不能撤销已经发生的业务写入。

4. 更新页面前还要比较捕获的版本号与当前版本号，成功、失败和结束加载状态都做这个判断。这样即使某个请求封装不响应取消，或者异步解析完成得较晚，旧结果也不会覆盖新列表，旧请求也不会提前关掉新请求的加载提示。

5. 清空关键词和组件卸载同样要使版本失效，并执行防抖取消及请求取消。主动取消通常不需要显示“搜索失败”，真实网络错误才按当前请求展示；因此我会把减少资源消耗与保证页面结果正确分别处理，不能只加一行 abort 就结束。

## 追问：请求序号应该在输入变化还是发送请求时增加？

1. 如果页面要求结果始终对应当前输入，我会在输入变化时增加序号。假设新关键词还在等待防抖，旧请求刚好完成，只在发送时增加序号就会误把这个旧结果认作当前结果，短暂显示不匹配的列表。

2. 调度请求时同时捕获关键词和当时的序号，响应回来再与最新序号比较。清空输入也要增加序号，即便空字符串根本不发请求，否则上一次搜索仍可能在清空后把列表重新填上。

3. 比较不能只放在成功分支，错误提示和 `finally` 里的 loading 更新也需要相同保护。否则旧请求虽然没有写列表，却仍能展示过时错误或隐藏新请求的加载状态，页面表现仍然不符合当前操作。

## 追问：有了 AbortController，为什么还保留版本号判断？

1. AbortSignal 是给具体异步操作的取消通知，不是让任意一段业务代码立即停止。请求库可能没有传递 signal，已有结果后续执行的格式转换也可能不理会它，所以我不会把取消成功当成结果一定不会写入的前提。

2. 版本号判断直接控制是否提交页面状态，即使旧操作继续完成也可以丢弃结果。两者配合时，取消主要减少不需要的工作，版本号主要保证最新输入拥有更新权，职责明确后更容易检查遗漏分支。

3. 我会分别构造“旧请求晚返回”和“取消后仍返回”的模拟场景，观察旧结果是否被忽略。断言需要针对页面最终内容和调用顺序，不能只看 abort 有没有被调用。客户端取消也不能说明服务端操作已经回滚，这是另外的业务保证。
