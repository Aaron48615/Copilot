# 你平时如何使用 AI 和 Agent 开发？

## 核心回答

1. 我通常先自己明确目标，再让 AI 阅读相关代码并提出修改范围。普通问答适合解释概念，能读文件、改代码和执行命令的 Agent 可以协助推进任务，但我仍需要给出当前项目的约束，不能只说“把功能做好”。

2. 以轻购智能导购为例，我会先说明前端要提交选购需求、接收推荐商品和匹配信息，并提供现有接口封装。服务端如何解析与筛选要依据真实约定，不能让工具根据一个页面名称，就自行假设后端功能已经存在。

3. 实现时我倾向于一次完成一个可检查的小范围，比如先接通请求与基本状态，再核对结果展示。这样读差异时容易判断每个修改的目的，也能及时发现工具顺手改动公共代码、增加依赖或偏离原需求的情况。

4. 改完后，我会先看关键逻辑，再按实际改动选择检查和操作场景。导购要看成功、无商品、接口失败和条件放宽提示是否区分，异步入口还要看旧结果是否覆盖新结果，不能把页面首次出现卡片当成全部完成。

5. 最后整理实际修改、验证结果和剩余问题，再决定接受哪些内容。没有执行的测试不会写成通过，未经确认的后端行为不会写成个人成果；AI 帮我提高执行效率，但需求判断、代码理解和结果确认仍要由我负责。

## 追问：Agent 可以连续执行命令，为什么还要限定任务范围？

1. 连续执行提高的是操作能力，不代表它自动知道哪些改动符合项目目标。一个页面问题可能只需要改状态判断，如果范围没写清楚，工具可能重装依赖或修改公共配置，让本来很小的任务变得难以审查。

2. 我会告诉它允许修改的文件、现有代码规范和应该运行的检查，并关注每条命令的目的。读取文件、运行测试与发布服务的影响不同，不能因为允许了前两种操作，就推导出后面的远程变更也获得授权。

3. 发现它开始处理无关问题时，我会要求回到当前目标，先检查已有差异再继续。这样做不是每一步都重新讨论，而是让最终结果的范围可解释，尤其多人协作时，不能覆盖其他人正在修改的文件。

## 追问：AI 连续修了几轮仍然报错，你会怎么调整？

1. 我会先停止继续叠加补丁，重新记录最短复现步骤和当前实际错误，确认还是不是最初的问题。连续修改可能改变了现象，如果一直沿用第一轮的猜测，就容易把新的错误也当成旧原因处理。

2. 接着检查每轮差异与错误变化，把问题缩到最小函数或最少配置，再提出一个可以验证的假设。比如怀疑响应顺序，就明确记录请求编号与返回顺序，而不是再让工具笼统地“优化异步逻辑”。

3. 对与当前任务无关的修改，我会逐项核对归属后处理，不能用清空工作区的方式图省事。如果最终仍无法确认原因，我会保留复现证据并说明阻碍，比不断更换依赖直到偶然不报错更便于继续定位。
