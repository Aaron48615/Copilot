# allSettled 什么时候更合适？

## 核心回答

1. 多个任务相互独立，部分失败也值得留下其他结果时，选 Promise.allSettled。比如一个页面加载几块独立统计区域，某一区域失败不该让其他已成功的数据都没法展示。每块区域都应根据自己的结果展示内容或重试入口，用户还能用已经加载成功的部分。

2. 它在所有输入都 fulfilled 或 rejected 后，按输入顺序返回状态记录。成功项有 status 和 value，失败项有 status 和 reason。先根据 status 分支再取字段，不能因为 value 是 undefined 就认定失败，因为 undefined 也可能是合法成功值。

3. 它不会因为某个普通输入 Promise 拒绝而直接拒绝整个结果，但也不是任何调用都必定成功。输入不可迭代，或同步迭代器在枚举时抛错，返回的组合 Promise 仍可能拒绝。这和某项业务请求失败后被记进结果数组不同。

4. allSettled 会等最慢的任务，如果某项一直 pending，就拿不到完整结果数组。页面若希望一块数据回来就先显示，应让各任务分别更新对应区域，再用 allSettled 汇总最终状态，而不是 await 整组之后才开始渲染所有卡片。

5. 后续操作必须依赖全部数据正确，通常仍选 Promise.all，或在收集结果后显式检查失败项。别把 allSettled 的外层 fulfilled 当成业务全部成功。批量提交尤其要展示哪些成功、哪些失败，并按业务规则决定重试，避免重复处理已成功项。

## 追问：allSettled 返回成功，为什么页面仍可能显示失败？

1. 外层 fulfilled 表示成功收集了每个输入的终态，不表示每个输入都完成了业务目标。结果数组中仍可能包含 rejected 记录，所以页面应该根据每项 status 展示数据或错误，汇总时也要算实际失败项，不能只看最外层 await 是否抛错。

2. 业务错误还可能被封装为 fulfilled 的返回值，比如接口返回 `{ success: false }`，或者 fetch 返回 HTTP 错误状态。需要在请求适配层统一检查业务含义，决定转成拒绝还是保留明确的业务状态，组合器不会自动读懂响应字段。

3. 把结果和原任务的稳定标识对应起来，便于准确提示失败的是哪一项。重试时只挑选允许重试的失败任务，并保留已成功结果。如果重新执行整组可能产生写入副作用，还需要接口具备相应幂等约定。

## 追问：有一个任务一直 pending，怎样避免整页一直等待？

1. allSettled 本身没有超时机制，所以给需要时限的任务单独设超时。超时要让被等待的任务 Promise 进入拒绝状态，才能进入结果数组。只显示一个「超时」提示，却让 Promise 继续 pending，整组仍然结束不了。

2. 用 Promise.race 和计时器可以限制等待时间，但不会自动停止原任务，仍要配合可用的取消机制，并清理计时器。还应禁止超时后的旧结果继续写状态，否则页面虽然已经提示失败，稍后的响应又可能突然盖上来。

3. 互不依赖的区域，分别维护加载和错误状态，让快任务先显示，再汇总全局完成情况。某块内容是关键依赖，就明确展示该区域超时并提供重试，别为了让整体看起来成功而给缺失数据随意填一个业务值。
