# 怎么支持取消？

## 核心回答

1. 并发池的取消要分成停止派发和通知运行任务两部分，因为 Promise 本身没有通用的取消方法。用户点击取消后，我会先标记这一批不再接受新任务，让尚未启动的任务进入取消状态，避免 worker 又取出下一项。

2. 已经运行的请求需要在创建时接收 AbortSignal，由这一批的控制器通知停止。任务如果只是普通计算或不支持 signal 的库，调度器不能强制打断它，只能要求任务主动检查状态，或者忽略它后续提交的结果。

3. worker 取任务之前要检查取消，等待结束之后也要检查结果是否仍然有效。后一个检查是为了处理请求刚完成就取消的竞态；如果页面又开始新的一批，还需要批次编号，避免旧结果覆盖新页面的数据。

4. 取消之后不能只把队列数组清空，调用方等待的 Promise 也必须有明确结局。我会约定返回已成功、失败和取消的逐项结果，或者让批次明确拒绝，并确保所有运行分支都有收尾处理，不留下永久等待的任务。

5. 对用户主动取消，界面一般结束加载并保留已完成进度，不显示成普通网络故障。控制器一旦取消就不能复用，重新运行应新建控制器；对于写请求还要说明取消不会撤销服务端已经提交的内容。

## 追问：取消恰好发生在请求成功的同时怎么办？

1. 我会先定义成功提交到界面的时点，而不是只看网络请求是否完成。假设响应已到但还没更新状态，这时批次已经取消，就跳过更新；如果成功项早已展示，则通常保留它，不因为取消剩余任务而清空已确认结果。

2. 状态变更最好集中在同一处，并检查批次编号和是否已进入最终状态，保证一项不会既统计成功又统计取消。JavaScript 回调虽然逐个执行，但异步回调到达顺序仍可能变化，需要靠状态判断表达规则。

3. 验证时可以让模拟请求先完成，再在界面提交前触发取消，同时覆盖取消后才返回的情况。如果需求是全部结果一次性展示，我会先暂存结果，只有整批仍有效时才提交，避免页面出现半旧半新的内容。

## 追问：任务不支持 AbortSignal 时还能提供取消按钮吗？

1. 可以提供，但要准确约定它代表停止等待或停止后续派发，不能保证底层工作已经终止。比如一个第三方异步计算没有取消接口，按钮点击后页面可以退出加载，计算本身可能仍在后台消耗资源。

2. 如果是自己编写的长任务，我会考虑拆成小段，每段开始前检查 signal，并适当让出执行机会。只有检查点真的得到运行，取消才能被及时处理；一个持续占用主线程的同步循环不会因调用 abort 自动被中断。

3. 对于不能改造的任务，可以隔离其结果写入，让已取消批次不再更新状态，同时继续接住迟到的异常。是否进一步使用可终止的 worker，要根据计算成本再评估，这属于可选改进，不能把忽略结果说成节省了全部资源。
