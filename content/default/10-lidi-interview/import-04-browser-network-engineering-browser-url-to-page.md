# 从输入 URL 到页面展示，中间发生了什么？

## 核心回答

1. 我会从导航开始讲：浏览器解析地址，确认协议和目标，并检查能否复用已有连接或缓存响应。实际流程受重定向、Service Worker、代理和缓存策略影响，不能认为每次输入地址都会完整执行一次 DNS 和握手。

2. 需要连接时，域名解析得到可连接的地址，解析结果可能来自浏览器、系统或递归 DNS 的缓存。DNS 不仅使用 UDP，也可能使用 TCP 或加密 DNS；CDN 还可能参与地址调度，但并不保证选择物理距离最近的节点。

3. 使用 HTTP/1.1 或 HTTP/2 的 HTTPS 通常先建立 TCP，再进行 TLS 协商，验证证书并建立加密通信。HTTP/3 使用 QUIC，路径不同；浏览器随后发出请求，服务端或缓存节点返回状态、响应头和页面内容。

4. HTML 到达后浏览器逐步解析 DOM，获取 CSS、脚本和图片，完成样式计算、布局、绘制与合成。页面显示后还可能继续请求接口和执行交互，连接也可能保留复用；所以我会把首屏展示和所有资源加载完成分开理解。

5. 例如地址返回重定向，浏览器还需访问新的目标，后续可能再次查缓存或建立连接；表面上只输入一次地址，不代表只有一个请求。定位慢页面时，我会先看完整导航瀑布图，确认时间花在最终文档还是前面的跳转与连接阶段。

## 追问：页面已经显示了，为什么加载图标还在转？

1. 页面可以渐进显示，首段 HTML 和关键样式准备好就可能出现内容。load 等待的资源范围与首屏可见内容不同，例如一张非关键图片仍在下载，就可能让加载状态继续存在，但用户已经能阅读文字。

2. 我会区分 DOMContentLoaded、load 和业务自己的完成状态。DOM 可操作不代表图片解码完成，load 结束也不代表后续接口全部完成；无限滚动和轮询页面更不可能用没有网络请求作为唯一完成标准。

3. 定位时在 Network 看仍未结束的请求，再结合页面需求判断是否值得优化。若只是非关键资源，可以降低它对体验的影响；若主内容仍是空白，就应检查数据请求和脚本执行，而不只关注浏览器图标。

## 追问：DNS 很快，网页为什么仍可能很慢？

1. DNS 只是找到目标地址，之后还有连接建立、TLS、服务端处理、内容传输和渲染。比如 HTML 等了很久才返回，或者大脚本执行占住主线程，即使地址解析只花很短时间，用户仍然会等首屏。

2. 我会查看请求 Timing，把连接等待、首字节等待和下载分别看。首字节时间也可能包含网络往返和服务端排队，不能直接把它全部归结为数据库慢，需要结合服务端请求记录继续确认。

3. 资源到齐后再看 Performance 是否存在长任务或大量布局。这样能判断问题在网络前半段还是浏览器执行阶段，避免明明脚本过大，却不断增加 DNS 预解析配置，最后没有实际改善。
