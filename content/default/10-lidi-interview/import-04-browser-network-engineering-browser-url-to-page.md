# 从输入 URL 到页面展示，中间发生了什么？

## 核心回答

1. 从导航开始：浏览器解析地址，确认协议和目标，并看能不能复用已经有的连接，或者直接用缓存响应。中间还可能碰到重定向、Service Worker、代理和缓存策略。输入一次地址，不等于每次都完整走一遍 DNS 和握手。

2. 真要新建连接时，域名解析得到能连的地址。结果可能来自浏览器缓存、系统缓存，或者递归 DNS 的缓存。DNS 不只走 UDP，也可能走 TCP 或加密 DNS。CDN 还可能参与调度地址，但不保证选到物理上最近的节点。

3. 用 HTTP/1.1 或 HTTP/2 的 HTTPS，通常先建 TCP，再做 TLS 协商，验证书、建加密通道。HTTP/3 走 QUIC，路径不一样。随后浏览器发请求，服务端或缓存节点回状态、响应头和页面内容。

4. HTML 到了之后，浏览器逐步解析 DOM，去拉 CSS、脚本和图片，再做样式计算、布局、绘制和合成。页面显示出来以后，还可能继续请求接口、跑交互，连接也可能留着复用。首屏展示和所有资源加载完，是两件事。

5. 比如地址返回重定向，浏览器还得去新目标，后面可能再查缓存或再建连接。表面上只输了一次地址，请求却可能不止一个。页面慢的时候，先看完整导航瀑布图，时间是花在最终文档上，还是前面的跳转和连接阶段。

## 追问：页面已经显示了，为什么加载图标还在转？

1. 页面可以一点点显示，前面一段 HTML 和关键样式准备好，内容就可能出来。`load` 等的资源范围和首屏看得见的内容不是一回事。比如一张不关键的图片还在下，加载状态可能还在转，用户其实已经能读文字了。

2. `DOMContentLoaded`、`load` 和业务自己的完成状态要分开。DOM 能操作了，不等于图片解码完；`load` 结束了，也不等于后面的接口都回来了。无限滚动和轮询页面，更不能拿「没有网络请求」当唯一完成标准。

3. 定位时在 Network 看还没结束的请求，再结合页面需求判断值不值得优化。如果只是非关键资源，可以降低它对体验的影响；主内容还是空白，就该查数据请求和脚本执行，别只盯着浏览器那个图标。

## 追问：DNS 很快，网页为什么仍可能很慢？

1. DNS 只是找到目标地址，后面还有连接建立、TLS、服务端处理、内容传输和渲染。比如 HTML 等了很久才回来，或者大脚本把主线程占住，地址解析哪怕只花一点点时间，用户还是会等首屏。

2. 看请求 Timing，把连接等待、首字节等待和下载分开。首字节时间里也可能含网络往返和服务端排队，不能一股脑算成数据库慢，还得对照服务端请求记录继续确认。

3. 资源到齐后再看 Performance 有没有长任务或大量布局。这样能判断问题在网络前半段，还是浏览器执行阶段。脚本已经很大了，再堆 DNS 预解析配置，往往改善不了多少。
