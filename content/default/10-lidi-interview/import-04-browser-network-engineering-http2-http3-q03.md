# 前端能直接决定使用哪个协议吗？

## 核心回答

1. 普通网页不能通过 `fetch` 选项直接指定必须用 HTTP/2 或 HTTP/3。协议选择主要由浏览器、服务器或 CDN 的支持、协商信息和网络条件决定。前端改一个请求头，并不能把现有 HTTP/1.1 服务变成 HTTP/3。

2. HTTPS 场景会涉及 TLS 的应用协议协商，HTTP/3 还需要发现可用服务以及 QUIC 支持。服务器即使开了新协议，浏览器也可能因为首次发现过程、代理或 UDP 受限而用其他协议。实际结果得观察。

3. 在 Network 面板打开 Protocol 列，看文档和关键资源实际用的是 h2、h3 还是别的。不同资源可能来自不同域名或节点。首页用了 h3，不代表第三方脚本和所有接口都走同样的连接方式。

4. 推进升级时，前端可以提供关键资源清单和测量结果，跟负责服务端、证书和 CDN 的同学配合。验证应覆盖支持和回退场景，并检查缓存、跨源规则和实时连接。某次请求成功，认定不了部署已经完成。

5. 前端能直接控制的，仍是减少无用资源、合理分包、缓存和加载顺序。协议升级有助于减少某些网络开销，但资源体积、服务端耗时和主线程执行仍可能占主要时间。优化要围着用户实际在等的原因转。

## 追问：服务器支持 h3，开发工具却显示 h2，正常吗？

1. 可能正常。浏览器需要知道目标支持 HTTP/3，并且当前网络、客户端和服务端配置都允许用 QUIC。首次访问、代理环境或 UDP 被拦住，都可能导致继续用 HTTP/2。不能只凭这个判断服务器配置无效。

2. 确认目标域名、证书和节点是否一致，检查服务发现信息和客户端支持情况。CDN 不同地区节点也可能行为不同。测一台机器的单次结果，只能说明这条路径，代表不了所有用户的协议分布。

3. 最后比较访问是否正常，以及能不能合理回退。业务功能没问题的话，重点是查为什么没协商到预期协议，别在前端不停重试同一个请求。强行循环请求可能增加负担，也解决不了网络限制。

## 追问：升级协议后如何做前端性能验收？

1. 先记下相同页面在旧协议下的基线，包括关键资源完成时间、LCP 和错误率，并保留缓存及网络条件。协议改变后再按同样方式复测。别把资源内容变化，或 CDN 缓存变热，当成协议收益。

2. 还要区分高延迟、丢包和稳定网络场景，因为协议优势并不均匀。真实用户数据可以按实际协议分组观察，但这些组的设备和网络可能不同，不能直接用平均值差异证明全部收益都来自协议。

3. 验收也包括失败回退和业务兼容，比如下载、流式响应和大文件请求是否正常。没有测到提升就如实说，再继续定位服务器或脚本瓶颈。别因为协议更新就预设性能一定明显变好。
