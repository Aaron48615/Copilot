# 状态放错位置会导致什么？

## 核心回答

1. 状态放得太高，每次更新影响的范围就变大。搜索框每个按键都放在页面根组件，打一个字，图表、侧栏、列表相关组件都可能再跑一遍。它们实际显示没变，计算还是多了。

2. 放得太低也会出问题。兄弟组件各自存一份选中的商品，点了列表，详情不同步，就得靠额外事件或 Effect 去对齐。它们本该读共同父组件那一份，不该各有一份副本。

3. 放在真正需要它的那些组件共同够得着的位置，能局部就局部，要共享再往上提。临时输入和已经生效的查询条件可以分开：输入框即时改草稿，提交或防抖后再改会影响列表的那份，每个按键就不必触发贵的处理。

4. 派生值别再开一份 state 来传。已选数量可以从选中集合直接算。全局 Context 或 Redux 也不适合承接所有局部状态，订阅会变多，数据谁在用、什么时候清也更难判断。

5. 拿一次具体操作看：哪些组件该变，哪些只是被带着跑。必要时用组合、拆 Provider、`memo` 再缩小范围。既看跟不跟手，也看该同步的界面还齐不齐。少渲染把真正要一起变的界面隔开了，也不行。

## 追问：弹窗开关放在页面根组件一定是错误吗？

1. 不一定。看谁决定它显不显示，以及根组件更新实际有多贵。页面简单、下面都是轻组件，放根上可能更清楚。为了理论上最少渲染，把数据流绕很多层或上全局事件，不一定值得。

2. 弹窗里面每敲一个字都把整页昂贵图表带着刷，就把开关和草稿分开。页面管「打开的是哪一条」，弹窗管当前编辑的文字。父级还能控制打开关闭，键盘事件不必更新整个页面。

3. 用 Profiler 看要不要再拆。弹窗关上草稿是清掉还是留着，也要定。状态放哪既影响速度，也在说这份数据活多久。别只按离根节点远近判断对不对。

## 追问：两个组件复制同一份状态，为什么容易越写越复杂？

1. 两份都能改，就要回答冲突时听谁的。列表选中 A，详情内部还记着 B，再用 Effect 互相同步，可能多渲染甚至转圈。代码里会越来越多「要是不相等就再写一次」。

2. 找出真正的事实来源，选中编号放共同父级，其余组件用 props 读、用回调报动作。详情内容由编号和数据表推出来。少一边改了编号、一边忘了换整个对象这种对不齐。

3. 第二份本来就是独立草稿，名字就叫草稿，约定提交和取消。暂时不一样是有理由的。接口刷新也不会理所当然盖掉草稿。这样状态关系更好讲，也好测。
