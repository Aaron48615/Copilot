# 状态放错位置会导致什么？

## 核心回答

1. 状态放得过高，会扩大每次更新影响的范围。比如搜索框的逐键输入放在整个页面根组件，每打一个字都可能重新执行图表、侧栏和列表相关组件，即使它们的实际显示内容并没有变化，也会增加计算工作。

2. 但状态放得过低也会产生问题。兄弟组件各自保存选中的商品，点击列表后详情没有同步，就需要额外事件或 Effect 对齐；这说明它们本来应该读取一份由共同父组件管理的数据，而不是各有一份副本。

3. 我的原则是放在真正需要它的组件共同拥有的位置，优先局部，再按共享需求提升。临时输入和已经应用的查询条件可以分开：输入框即时更新草稿，提交或防抖后再改变影响列表的数据，避免所有按键都触发昂贵处理。

4. 派生值不应靠再建 state 解决传递问题，例如已选数量可以根据选中集合直接计算。全局 Context 或 Redux 也不适合承接所有局部状态，否则不仅增加订阅，还让数据使用范围变得难以判断和清理。

5. 我会按一次具体操作检查哪些组件需要变化、哪些只是被带着执行。必要时通过组合、拆分 Provider 或 memo 进一步缩小范围；验证既看响应时间，也看共享状态是否仍一致，不能为了少渲染把真正需要同步的界面隔离掉。

## 追问：弹窗开关放在页面根组件一定是错误吗？

1. 不一定，要看谁需要决定它的显示，以及根组件更新的实际成本。简单页面只有少量轻组件时，放根组件可能很清楚，不必为了理论上的最少渲染让数据流绕更多层或引入全局事件。

2. 如果弹窗内部每次输入都把整页昂贵图表带着更新，可以让开关与草稿分别归属。页面负责“打开哪个对象”，弹窗负责当前编辑文字；这样保留父级控制能力，又不必让每个键盘事件更新整个页面。

3. 我会通过 Profiler 判断是否需要进一步拆分，并检查弹窗关闭时草稿应清除还是保留。状态位置不仅影响速度，也表达生命周期，不能只按离根节点远近决定正确与否。

## 追问：两个组件复制同一份状态，为什么容易越写越复杂？

1. 一旦两份都能修改，就需要回答冲突顺序。例如列表选中 A，详情内部还记着 B，双方再用 Effect 相互同步，可能产生额外渲染甚至循环；代码逐渐充满“如果不相等再写一次”的补丁。

2. 我会找出真正的事实来源，把选中编号放在共同父级，其余组件通过 props 读取和报告动作。详情内容由编号和数据表推导，能避免一边更新编号、一边忘了替换整个对象的同步漏洞。

3. 如果第二份本来就是独立草稿，则应明确命名并约定提交和取消，而不是把它称为同步副本。这样允许暂时不同有业务理由，接口刷新也不会理所当然覆盖草稿，状态关系更容易解释和测试。
