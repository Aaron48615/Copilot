# useCallback 能解决所有旧值吗？

## 核心回答

1. useCallback 不能解决所有旧值问题，它缓存的是函数引用。依赖未变时返回之前保存的函数，这个函数仍保留创建时的闭包；如果依赖漏写，缓存反而会让读取旧状态的问题持续存在，而不是自动更新函数内部变量。

2. 比如保存按钮的回调读取 title，却用空依赖缓存，用户修改标题后点击仍可能提交初始标题。正确做法是完整写入依赖，或者根据数据流把需要的值作为参数传入，不能只因为函数名叫“回调缓存”就认为它会读最新内容。

3. 如果回调只按旧状态生成新状态，可以用函数式更新减少直接依赖。例如增加数量时把更新规则传给 setter，而不是闭包读取 count；但回调内的其他 props，如商品编号或步长，仍要按实际使用处理。

4. 它的主要价值是让需要稳定函数身份的地方更容易跳过工作，例如配合 memo 子组件，或某些依赖函数引用的订阅。没有这类需求时，普通函数通常更直观，盲目缓存会增加依赖维护和阅读成本。

5. 我会先定位哪个异步回调在哪一次渲染创建、由谁保存和调用。第三方库只在初始化时保存回调，即使组件后来创建了新函数，库也未必替换旧回调；此时要更新订阅接口或使用适当的最新值读取方式，单加 useCallback 不够。

## 追问：依赖写全了，第三方组件为什么还可能执行旧函数？

1. 依赖变化只让 React 返回新的回调引用，不会强制所有外部对象更新内部保存的函数。某个图表库初始化时保存 onClick，之后没有调用它提供的更新方法，就可能继续使用初次传入的处理器。

2. 我会先查该库是支持动态更新回调，还是需要取消旧订阅再重新注册。能更新就按新引用更新，重新订阅时确保移除同一个旧函数，避免新旧处理器同时存在，让一次点击触发两次操作。

3. 若订阅本来应该稳定，可以由回调读取经过同步的 ref，或在适用版本使用 Effect Event 处理 Effect 中的事件。必须明确最新值读取和订阅生命周期是两件事，不能靠关闭依赖检查把差异隐藏起来。

## 追问：为了保持回调稳定，把所有数据放 ref 有什么代价？

1. ref 的修改不会触发渲染，如果把本来驱动界面的值迁进去，视图可能不再跟着变化。还会出现 state 和 ref 两份内容需要同步的问题，忘记更新其中一份，回调和页面就会使用不同数据。

2. 隐藏依赖也可能让应该重建的资源不更新。比如连接地址改变本该重新连接，如果地址只藏在 ref 中，旧连接仍指向原服务器，虽然回调读到新地址，却并没有真正切换连接对象。

3. 我会只把确实需要跨渲染读取、又不驱动该订阅重建的值放 ref，并清楚安排同步时机。能用参数传递或函数式更新表达的逻辑，优先用那些更显式的方式，让后续维护者容易判断何时更新。
