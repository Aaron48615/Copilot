# useCallback 能解决所有旧值吗？

## 核心回答

1. 不能。`useCallback` 缓存的是函数引用。依赖没变，返回的还是之前存的那个函数，闭包也还是创建时那一份。依赖漏写，缓存反而让读旧状态这件事一直在，函数内部的变量不会自己变新。

2. 保存按钮的回调读 `title`，却用空依赖缓存。用户改了标题再点，提交的可能还是一开始的标题。依赖写全，或者按数据流把需要的值当参数传进去。函数名叫回调缓存，不代表它会读最新内容。

3. 回调只按旧状态算出新状态，可以用函数式更新少直接依赖。加数量时把更新规则传给 setter，不必闭包读 `count`。回调里别的 props，比如商品编号、步长，仍按实际用到的处理。

4. 它主要价值是：需要函数身份稳住的地方更好跳过工作，比如配合 `memo` 子组件，或某些按函数引用订阅的地方。没有这种需求，普通函数更直观。盲目缓存会多一份依赖要维护，读起来也更绕。

5. 先搞清这个异步回调是哪一次渲染创建的、谁存着、谁调用。第三方库只在初始化时把回调存下来，组件后来给了新函数，库也未必换。这时要走它的更新接口，或用合适的最新值读取方式。单加 `useCallback` 不够。

## 追问：依赖写全了，第三方组件为什么还可能执行旧函数？

1. 依赖变了只让 React 返回一个新的回调引用，外面对象内部存着的函数不会被强迫换掉。图表库初始化时存了 `onClick`，之后没调它提供的更新方法，就可能一直用第一次传入的那个。

2. 先查这个库是支持动态换回调，还是要取消旧订阅再重新注册。能更新就按新引用更新；重新订阅时把同一个旧函数卸掉，别新旧处理器同时在，一次点击跑两次。

3. 订阅本身该稳住，可以由回调去读已经同步过的 ref，适用版本也可以用 Effect Event 处理 Effect 里的事件。读最新值和订阅活多久是两件事。别关依赖检查把差异藏起来。

## 追问：为了保持回调稳定，把所有数据放 ref 有什么代价？

1. 改 ref 不会触发渲染。本来驱动界面的值迁进去，视图可能不再跟着变。还会出现 state 一份、ref 一份，忘了更新其中一份，回调和页面用的就不是同一份数据。

2. 依赖藏起来，该重建的资源也可能不更新。连接地址变了本该重连，地址只在 ref 里，旧连接还指着原来的服务器。回调读到了新地址，连接对象其实没换。

3. 只把确实要跨渲染读、又不该带动这次订阅重建的值放 ref，同步时机写清楚。能用参数传递或函数式更新说清楚的，优先用那些更看得见的写法，后面才容易判断什么时候该更新。
