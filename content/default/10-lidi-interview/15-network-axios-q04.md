# 什么是 CORS 预检请求？

## 核心回答

1. CORS 预检是浏览器在某些跨源请求之前发送的 OPTIONS 请求，用来确认服务端是否允许后续的请求方法和请求头。不是所有跨域都会预检，也不是所有 POST 都会预检，判断依据是请求是否满足相应的安全列出条件。预检通常由浏览器自动发起，业务代码不需要手动先请求一次 OPTIONS。

2. 常见触发例子是使用 PUT、DELETE，带 Authorization 自定义认证头，或者以 application/json 作为请求内容类型。普通 GET 如果加了不在安全列表中的请求头，同样可能先预检，不能只看方法名称。

3. 预检通常带 Origin、Access-Control-Request-Method，以及需要检查时的 Access-Control-Request-Headers。服务端通过允许源、方法和头等响应信息表明许可，浏览器验证通过后才发送真正的业务请求。

4. 如果 OPTIONS 返回 200 或 204，但许可头缺失或不匹配，预检仍然失败。反过来，预检通过也不等于业务鉴权通过，真正请求可能返回 401 或 500，而且实际响应同样需要符合 CORS 检查。

5. 排查时我会分别看 OPTIONS 和业务请求是否存在，以及是谁返回了响应：应用服务、网关还是代理。普通跨源预检不携带业务请求的 Cookie 等凭据，所以不能要求它先通过依赖登录 Cookie 的鉴权才能返回许可。

## 追问：OPTIONS 返回 204，为什么浏览器还是拦截？

1. 204 只能说明服务器成功处理了这个 OPTIONS，不代表浏览器检查通过。我会比对页面 Origin 和允许源，特别是协议、端口，以及携带凭据时是否错误地返回了通配符。状态成功和访问许可是两个不同的判断。

2. 再检查允许的方法和请求头是否覆盖真实请求，例如业务请求带 Authorization，但 Access-Control-Allow-Headers 没允许它。网关也可能提前返回了一个没有完整许可头的空响应，需要确认配置实际生效的位置。

3. 如果业务请求已经发出，就要继续检查它的响应，而不是反复改 OPTIONS。常见情况是成功响应有 CORS 头，错误响应没有，导致浏览器无法向脚本暴露真正的业务错误内容。

## 追问：能不能减少每次预检带来的开销？

1. 可以由服务端通过 Access-Control-Max-Age 设置预检结果的缓存时间，浏览器在许可仍适用时复用结果。它有浏览器实现限制，也与普通 HTTP 响应缓存不同，不能承诺设置多久就一定缓存多久。

2. 请求设计上可以避免无意义的自定义头，但不应该为了省一次 OPTIONS 把 JSON 伪装成其他类型，或把认证信息搬进 URL。是否满足无需预检的条件，要以真实协议和请求需求为准。

3. 如果部署条件允许，同源反向代理可以避免这类浏览器跨源检查，但需要承担代理配置和运维成本。我会先观察实际预检频率和耗时，再决定优化方式，不会因为看到两个请求就判断系统有故障。
