# CSP 能防所有 XSS 吗？

## 核心回答

1. CSP 不能防住所有 XSS，它是在浏览器端限制资源加载和部分代码执行的一道附加防线。即使输入被拼进页面，严格脚本策略也可能阻止执行，但前提是策略确实生效，而且没有留下过宽的许可。

2. 例如允许任意内联脚本，或者信任了可被攻击者控制内容的域名，就可能让恶意代码进入允许范围。nonce 必须不可预测并随响应生成，不能把固定值写进前端；允许一个脚本来源也不表示其中所有脚本都安全。

3. 根本处理仍是避免把不可信数据当代码执行。普通文字用框架默认转义或 textContent，富文本用合适的清洗方案，URL 还要检查协议和允许范围；同一段输入放进 HTML、属性和脚本上下文，不能用一种转义包办。

4. 我会把 CSP 看成降低注入影响的措施，结合 HttpOnly Cookie、依赖审核和服务端权限校验使用。如果补充 CSP，我会先用 Report-Only 确认合法资源和违规上报，再逐步启用执行策略；同时回归富文本、第三方脚本和登录功能，检查限制没有破坏正常使用。

5. 例如评论区显示普通文字时，优先让它以文本方式进入页面，而不是先拼成 HTML 再指望 CSP 阻止其中脚本。限制脚本执行并不能修复页面结构被注入后造成的伪装按钮、错误链接或内容覆盖，所以内容处理仍然要从入口做对。

## 追问：允许的第三方脚本被篡改，CSP 还能阻止它吗？

1. 如果它符合允许来源或授权条件，CSP 可能允许执行，不能从域名推断代码没有被污染。第三方脚本一旦在页面上下文运行，通常可以读取页面内容和操作界面，所以接入本身需要谨慎评估。

2. 固定版本的静态脚本可以考虑 SRI 校验内容，并配合正确的跨源配置。这样资源内容意外变化时浏览器可以拒绝加载，但频繁动态变化的脚本不容易使用固定完整性值，仍需要控制信任范围。

3. 我会尽量减少不必要的第三方脚本，固定依赖版本并检查更新来源。高风险内容可以放入受限制的 iframe，明确通信消息格式；不过隔离也有功能和维护成本，应按实际需求设计。

## 追问：用了框架默认转义，还需要清洗富文本吗？

1. 需要，因为默认转义通常把输入当普通文本显示，而富文本希望保留部分 HTML。使用 v-html 或 dangerouslySetInnerHTML 等功能时，实际上绕过了普通文本的保护，必须先确定允许哪些标签和属性。

2. 清洗应使用维护中的专门工具和清晰配置，处理事件属性、危险 URL 及嵌套结构等情况。手写几个正则去删除 script 标签不够，浏览器解析 HTML 的规则复杂，攻击也不只通过 script 元素触发。

3. 清洗后还要避免再次拼接不可信属性或让插件重新引入危险内容。我会保存可复现的测试输入，并在升级清洗工具后回归；CSP 可以作为额外限制，但不能成为省略清洗的理由。
