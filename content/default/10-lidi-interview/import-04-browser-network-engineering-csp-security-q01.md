# CSP 能防所有 XSS 吗？

## 核心回答

1. CSP 防不住所有 XSS。它是浏览器端限制资源加载和部分代码执行的一道附加防线。即使输入被拼进页面，严格的脚本策略也可能拦住执行，但前提是策略真的生效，而且没有留过宽的许可。

2. 比如允许任意内联脚本，或者信任了攻击者能往里面塞内容的域名，恶意代码就可能进允许范围。nonce 必须不可预测，并且跟着每次响应生成，不能把固定值写进前端。允许一个脚本来源，也不表示里面所有脚本都安全。

3. 根本处理仍是别把不可信数据当代码执行。普通文字用框架默认转义或 `textContent`，富文本用合适的清洗方案，URL 还要查协议和允许范围。同一段输入放进 HTML、属性和脚本上下文，一种转义包办不了。

4. CSP 是降低注入影响的措施，要跟 HttpOnly Cookie、依赖审核、服务端权限校验一起用。补充 CSP 时，可以先用 Report-Only 确认合法资源和违规上报，再逐步打开执行策略。同时回归富文本、第三方脚本和登录功能，看限制有没有把正常使用弄坏。

5. 比如评论区显示普通文字，优先让它以文本方式进页面，别先拼成 HTML 再指望 CSP 拦住里面的脚本。限制脚本执行，修不了页面结构被注入之后的伪装按钮、错误链接或内容覆盖。内容处理还是要从入口做对。

## 追问：允许的第三方脚本被篡改，CSP 还能阻止它吗？

1. 如果它符合允许来源或授权条件，CSP 可能允许执行，不能从域名推断代码没被污染。第三方脚本一旦在页面上下文里跑，通常能读页面内容、操作界面，接入本身就要谨慎评估。

2. 固定版本的静态脚本可以考虑 SRI 校验内容，并配上正确的跨源配置。资源内容意外变化时，浏览器可以拒绝加载。频繁动态变化的脚本不容易用固定完整性值，信任范围还是得自己控。

3. 尽量少接不必要的第三方脚本，依赖版本固定住，更新来源也要查。高风险内容可以放进受限制的 iframe，通信消息格式说清楚。隔离有功能和维护成本，按实际需求设计。

## 追问：用了框架默认转义，还需要清洗富文本吗？

1. 需要。默认转义通常把输入当普通文本显示，富文本却希望保留一部分 HTML。用 `v-html` 或 `dangerouslySetInnerHTML` 这类能力时，等于绕过了普通文本保护，必须先确定允许哪些标签和属性。

2. 清洗要用还在维护的专门工具，配置也要清楚，处理事件属性、危险 URL、嵌套结构这些情况。手写几个正则去删 `script` 标签不够。浏览器解析 HTML 的规则很复杂，攻击也不只通过 `script` 元素触发。

3. 清洗之后，别再拼接不可信属性，也别让插件把危险内容重新引进来。留一批可复现的测试输入，清洗工具升级后还要回归。CSP 可以当额外限制，但不能拿它当省略清洗的理由。
