# 类型体操能校验运行时数据吗？

## 核心回答

1. 不能，条件类型、类型推断和映射类型都是帮助编译器描述关系的工具，不会自动生成检查接口内容的代码。比如声明列表元素都有名称，只能约束按这个声明使用数据的代码，服务端实际返回空值时，浏览器仍可能在访问属性时报错。

2. 我会把外部数据先当成未知值，经过真实执行的检查以后再交给业务函数，例如检查对象非空、标识字段是字符串、数量是合法数字。未知类型要求先缩小范围才能使用，任意类型却容易让后续检查失效，所以边界不宜一路透传任意类型。

3. 简单结构可以写类型守卫，复杂嵌套结构可以考虑使用项目已有的校验工具，但守卫返回真也必须有足够证据。函数签名里写了某个类型谓词，不代表编译器会证明函数体检查完整，如果只查一个字段却承诺整个对象安全，仍然会留下漏洞。

4. 静态类型和运行时校验可以配合，前者避免内部调用错误，后者拦住接口、缓存和用户输入中的异常内容。如果要改进重复维护问题，可以考虑从同一份结构描述推导内部类型，但业务范围检查仍要执行，不能因为字段是数字就默认价格一定合理。

## 追问：自定义类型守卫写错了会怎样？

1. 编译器会按守卫声明在调用处缩小类型，但不会替你证明每条检查足以支持这个声明。例如只确认对象存在名称，就宣称它还有合法价格，后续金额计算仍然可能拿到未定义值，这是一种错误的安全承诺。

2. 我会让检查逐层对应业务代码实际依赖的字段，先处理空值，再验证基本类型，嵌套数组还要检查元素。可选字段需要明确允许缺省还是允许空值，两者不能凭感觉混用，否则读取时依然可能出错。

3. 验证守卫时不能只放正确样例，还应加入缺字段、字段类型错误、空对象和嵌套坏数据。对边界值也要覆盖，例如非有限数字或负数量，确保返回真之后，后面的业务函数确实可以按承诺使用数据。

## 追问：前端校验通过了为什么服务端还要校验？

1. 前端校验主要改善交互和保护前端处理流程，不能成为服务端信任请求的理由。用户可以绕过页面直接调用接口，也可能使用过期客户端，因此服务端必须独立检查收到的参数，不能假设它经过了最新前端逻辑。

2. 即使双方对字段类型的检查一致，服务端还要核对权限、资源状态和业务限制。比如数量是正整数不代表库存足够，传入某个订单标识也不代表当前用户有权操作，这些判断需要服务端掌握的真实数据。

3. 如果要减少规则重复，可以共享适合两端的基础约束，但权限和交易规则仍应由服务端作最终决定。前端收到拒绝后更新界面并说明原因，不能因为本地校验已通过，就把服务端的业务拒绝认定为程序异常。
