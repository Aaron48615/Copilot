# tree-shaking 为什么有时失效？

## 核心回答

1. tree-shaking 通过分析模块依赖和使用情况，删除不会影响行为的未使用代码。ESM 的静态 import、export 更利于分析，但用了 ESM 也不保证所有没调用的代码都能删掉，工具还要考虑顶层执行和副作用。

2. CommonJS 的动态导出或运行时条件加载可能让分析更保守，不过也不能说所有 CommonJS 内容都绝对无法优化。实际效果取决于工具、插件和依赖写法，我会看最终依赖图，不只根据文件扩展名或导入语法下结论。

3. 副作用常见于注册组件、修改全局对象、导入样式和 polyfill。sideEffects 帮助描述哪些模块执行需要保留，写错可能丢功能；纯调用提示也只能在确实满足条件时使用，不能把未知函数随意标记为可删除。

4. 入口的使用方式同样重要，动态访问导出集合、导入聚合文件和共享依赖都可能让更多代码留下。循环依赖还涉及初始化顺序，但它不等于必然让全部 tree-shaking 失效，需要看具体引用与求值行为。

5. 排查时我会确认生产优化启用、ESM 没被过早转成其他形式，再查看构建分析与实际产物。最后运行最小消费场景验证功能和样式，体积下降只有在行为正确时才有意义，不能以删得越多作为唯一目标。

## 追问：为什么只导入一个函数，仍然带进很多代码？

1. 这个函数可能本身依赖大型模块，或者入口文件在顶层执行了必须保留的初始化。构建器删除的是未使用且可安全省略的部分，不会因为你只写一个导入名称，就把它真实依赖的功能也自动删除。

2. 我会从分析报告沿导入路径查大依赖，确认是否经过聚合入口、动态导出或 CommonJS 转换。有些包提供更细的公开子入口可以使用，但不能直接引用未承诺稳定的内部文件来换取短期体积收益。

3. 修改后检查生产运行和升级兼容，尤其是样式、地区数据和注册行为。若功能确实需要那部分代码，可以再考虑延迟加载或替代实现，而不是继续强行添加无副作用标记，让工具删掉必要逻辑。

## 追问：压缩和 tree-shaking 有什么不同？

1. 压缩主要减少代码表达体积，例如去空白、缩短名称和简化表达式；tree-shaking 重点是从模块关系中找出不需要的代码。两者经常配合，最终移除无用语句也可能由压缩阶段完成，但关注层次并不完全相同。

2. 例如一个从未被使用的导出函数，静态分析可以标记为无用，再由后续优化删除；一个被使用的函数仍需要保留，只能通过压缩减小写法。不能看产物变成一行就断言已经有效删除了未用模块。

3. 我会分别查看导出使用情况和压缩后的传输大小，再用生产测试保证语义没变。若构建配置关闭相关优化或依赖难以分析，即使压缩率很高，包里仍可能包含大量业务暂时不需要的功能。
