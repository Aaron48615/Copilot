# tree-shaking 为什么有时失效？

## 核心回答

1. tree-shaking 通过分析模块依赖和使用情况，删掉不会影响行为的未使用代码。ESM 的静态 `import`、`export` 更利于分析，但用了 ESM 也不保证所有没调用的代码都能删掉。工具还要考虑顶层执行和副作用。

2. CommonJS 的动态导出，或运行时才决定加载什么，会让分析更保守。也不是所有 CommonJS 内容都绝对无法优化。实际效果取决于工具、插件、依赖怎么写。看最终依赖图，别只根据文件扩展名或导入语法下结论。

3. 副作用常见于注册组件、改全局对象、导入样式、polyfill。`sideEffects` 用来描述哪些模块执行需要保留，写错可能把功能弄丢。纯调用提示也只能在确实满足条件时用。未知函数随便标成可删除，运行时会缺逻辑。

4. 入口怎么用同样重要。动态访问导出集合、导入聚合文件、共享依赖，都可能让更多代码留下来。循环依赖还涉及初始化顺序，但它不等于全部 tree-shaking 一定失效，要看具体引用和求值行为。

5. 生产优化开了没有、ESM 有没有过早转成别的形式，这两点先确认，再看构建分析和实际产物。最后跑最小消费场景，功能和样式都对，体积下降才有意义。删得越多当唯一目标，容易把该留的也删了。

## 追问：为什么只导入一个函数，仍然带进很多代码？

1. 这个函数本身可能依赖大型模块，或者入口文件在顶层执行了必须保留的初始化。构建器删的是未使用且能安全省略的部分。只写一个导入名称，不会把它真实依赖的功能也自动删掉。

2. 从分析报告沿导入路径查大依赖，看是不是经过聚合入口、动态导出或 CommonJS 转换。有些包提供更细的公开子入口可以用。直接引用未承诺稳定的内部文件来换短期体积，升级时容易破。

3. 改完检查生产运行和升级兼容，尤其是样式、地区数据、注册行为。功能确实需要那部分代码，再考虑延迟加载或换实现。继续强行加无副作用标记，让工具删掉必要逻辑，页面会缺能力。

## 追问：压缩和 tree-shaking 有什么不同？

1. 压缩主要减少代码怎么写，比如去空白、缩短名称、简化表达式。tree-shaking 重点是从模块关系里找出不需要的代码。两者经常一起用，最终删掉无用语句也可能发生在压缩阶段，但关注的层次不一样。

2. 一个从未被使用的导出函数，静态分析可以标成无用，再由后续优化删掉。一个被使用的函数仍要保留，只能靠压缩减小写法。产物变成一行，不能断言未用模块已经被有效删掉。

3. 分别看导出使用情况和压缩后的传输大小，再用生产测试保证语义没变。构建配置关掉相关优化，或依赖很难分析，就算压缩率很高，包里仍可能带着大量当前业务用不上的功能。
