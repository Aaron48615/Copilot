# Suspense 能自动处理所有请求吗？

## 核心回答

1. Suspense 不会自动观察页面上的所有请求。它处理的是子树在渲染过程中通过受支持方式表达的等待，例如 lazy 组件代码尚未完成加载，或框架、数据方案提供的 Suspense 数据读取；普通 fetch 本身不会通知边界。

2. 在 useEffect 里请求数据时，组件已经完成了一次渲染，Effect 后续设置 loading 和 data，仍需要组件自己表达这些状态。仅在外层加 Suspense，不会自动把这个 Effect 的等待过程变成 fallback，这是很常见的误解。

3. React 的 use 可以读取 Promise 并与 Suspense 配合，但要使用适合该环境、身份稳定的资源。不能每次客户端渲染都随意新建请求 Promise，导致不断重新等待；具体数据缓存和服务端集成应遵循框架支持的方式。

4. 等待和错误是不同状态。等待时 Suspense 显示 fallback，受支持资源失败后通常交给错误边界；普通事件请求失败仍需在对应异步流程处理。加载提示、错误提示和重试动作应该各自有明确责任，不能全部归给同一个边界。

5. 边界范围应与用户可以独立看到的内容对应，例如先显示页面标题，再让推荐列表局部等待。把整页包进一个大边界可能让一个小模块加载就隐藏全部内容；拆得太细又可能满屏转圈，应按展示节奏选择，而不是按组件数量机械分割。

## 追问：为什么 Effect 里请求时外层 fallback 一直不出现？

1. Suspense 需要在渲染时收到“此处还不能完成”的受支持信号，而 Effect 是提交后才运行。组件已经成功返回了某个界面，它不会因为稍后存在一个网络请求就自动变成悬停状态，外层也无法猜测请求用途。

2. 简单页面可以继续使用显式 loading，初次显示占位，成功后显示数据，失败提供重试。这并不意味着写法落后，关键是状态完整；如果确实需要 Suspense，应该选支持它的数据接口，而不是手动到处抛 Promise。

3. 我会先检查项目框架和查询库的实际配置，再决定是否调整请求方式。迁移时还要验证缓存、请求去重和失败恢复，不能只把加载图标搬到 fallback，就认为原来的请求逻辑已经获得了 Suspense 支持。

## 追问：多个模块应该共用一个 Suspense 吗？

1. 如果这些模块必须一起出现才有意义，可以放在同一边界，例如一组紧密关联的详情内容。这样避免用户看到缺了一半的组合，但其中最慢的一块会决定整体何时展示，需要接受这个等待成本。

2. 如果标题、主信息和推荐区可以独立阅读，就可以按区域拆分，先展示已经就绪的部分。占位应尽量接近最终结构并预留尺寸，避免后续加载造成大幅跳动，比简单给每个组件放一个转圈更自然。

3. 我会从真实阅读顺序和失败恢复考虑粒度，并在慢网络下观察。边界只是表达等待范围，不解决数据本身的依赖瀑布；如果后一请求必须等前一请求结束，仍需检查是否能够提前或并行获取。
