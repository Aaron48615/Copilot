# Suspense 能自动处理所有请求吗？

## 核心回答

1. 不能。Suspense 不会去观察页面上每一个请求。它处理的是子树在渲染时用受支持的方式表达「还在等」：比如 `lazy` 组件代码还没加载完，或框架、数据方案提供的 Suspense 数据读取。普通 `fetch` 本身不会通知边界。

2. 在 `useEffect` 里请求，组件已经完成过一次渲染。Effect 后面再设 loading 和 data，还是组件自己表达这些状态。外层加了 Suspense，不会自动把这个 Effect 的等待变成 fallback。这点很容易误会。

3. React 的 `use` 可以读 Promise，并跟 Suspense 配合，但要用适合这个环境、身份稳住的资源。客户端每次渲染都随便 `new` 一个请求 Promise，会不停重新等待。数据缓存、服务端怎么接，跟框架支持的方式走。

4. 等待和错误是两种状态。等待时 Suspense 显示 fallback；受支持的资源失败了，通常交给错误边界。普通事件请求失败，仍在对应的异步流程里处理。加载提示、错误提示、重试各有责任，别全塞给同一个边界。

5. 边界范围跟用户能独立看的内容对齐。标题可以先出来，推荐列表在局部等。整页包一个大边界，一个小模块在加载就把全部藏掉。拆得太细又可能满屏转圈。按展示节奏选，别按组件数量机械切。

## 追问：为什么 Effect 里请求时外层 fallback 一直不出现？

1. Suspense 要在渲染时收到「这里还画不完」这种受支持的信号。Effect 是提交之后才跑。组件已经成功返回了一块界面，稍后有个网络请求，它不会自己变成悬停。外层也猜不到这个请求是干什么的。

2. 简单页面继续用显式 loading 就行：先占位，成功出数据，失败给重试。这不叫写法落后，状态完整更要紧。真要用 Suspense，选支持它的数据接口，别在各处手动抛 Promise。

3. 先看项目框架和查询库实际怎么配，再决定要不要改请求方式。迁移时缓存、请求去重、失败恢复都要过。只把加载图标挪到 fallback，原来的请求逻辑并不会因此就获得 Suspense 支持。

## 追问：多个模块应该共用一个 Suspense 吗？

1. 这些模块必须一起出现才有意义，可以放同一边界，比如一组绑得很紧的详情。用户就不会看到缺一半的组合。最慢的那块会决定整体何时出来，这份等待成本要接受。

2. 标题、主信息、推荐区可以分开读，就按区域拆，已经就绪的先展示。占位尽量接近最终结构，尺寸先留好，后续加载少大幅度跳动。比给每个组件放一个转圈自然。

3. 粒度看真实阅读顺序和失败怎么恢复，慢网络下看一眼。边界只表达等待范围，数据自己的依赖瀑布它解决不了。后一个请求必须等前一个结束，看能不能提前或并行去取。
