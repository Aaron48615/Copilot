# React 为什么说 state 是一次 render 的快照？

## 核心回答

1. state 是一次渲染的快照，意思是组件这次执行获得的状态值在这次执行中固定。setter 请求 React 用新状态安排下一次渲染，而不是像普通局部变量赋值那样直接修改当前函数里的 count，所以更新后紧接着打印通常还是原值。

2. 事件处理器也是这次渲染产生的函数，里面的定时器和 Promise 回调会记住对应的值。例如点击时计数为五，延迟提示可能仍显示五，即使等待期间界面已经变成六；这是闭包和渲染快照共同作用的结果。

3. 多次更新依赖前一结果时，要传入函数式更新。连续三次 count + 1 可能都算出相同目标值，而三次递增函数会按队列依次计算；批处理减少中间工作，但并不会自动把同一个旧表达式理解成三次累加。

4. 对象和数组也应按照快照对待，修改时创建新结构，不能直接改内部字段再期待引用比较识别变化。只复制被修改路径即可，未变化分支可以复用；这样以前的渲染和需要保留的历史数据才不会被后续操作悄悄改写。

5. 实际处理异步任务时，我会明确想要当时值还是最新值。提交时确定的收件人应保留本次操作参数，持续计数则使用函数式更新，稳定订阅读取最新配置可能使用 ref；不同目的选不同方式，不能看到旧值就一律要求“同步更新 state”。

## 追问：setState 后的日志是旧值，怎样确认下一次真的更新了？

1. 可以观察下一次组件渲染的输出，或在依赖该状态的 Effect 中记录已提交状态。事件函数里的日志仍属于旧快照，不应该把它当成 setter 失败的证据，也没有必要为了日志立即引入强制同步提交。

2. 调试时要注明日志属于渲染、事件还是 Effect，开发模式可能额外执行某些过程，单纯数打印次数会误导。界面最终展示以及更新动作所用参数，往往比一串没有标明阶段的日志更容易解释。

3. 如果下一次确实没变，再检查是否传回了同一个对象、条件分支是否执行，以及组件是否已经被卸载。按这些具体原因定位，不能先假设所有问题都来自所谓“异步 setState”，它不是完整的错误解释。

## 追问：函数式更新能让回调里的其他 state 也变成最新吗？

1. 不能，它只为该状态更新函数提供前一份待更新状态。比如 setCount 的参数 c 可以用于正确累加，但同一回调里读取的 selectedUser 或 step，仍然遵循创建回调时的闭包，不会自动被同步刷新。

2. 如果多个值必须作为一个整体转换，可以考虑将相关状态组织在一起或使用 reducer，明确一个动作读取和修改哪些数据。若它们本来无关，就按各自用途处理依赖，不能为获得“最新值”把整个页面都合成一个对象。

3. 我会用步长可调整的计数器验证这个区别：计数能继续增加，不代表变更后的步长已经生效。需要重建回调、传入参数或使用合适的最新值读取方式，取决于步长变化是否应该改变订阅生命周期。
