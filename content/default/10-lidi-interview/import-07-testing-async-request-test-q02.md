# 重试要测几次？

## 核心回答

1. 我会先确认“重试两次”是否表示首次请求之外再试两次，也就是最多三次尝试。测试次数由重试规则和状态分支决定，不是挑一个数字反复跑；参数命名如果含糊，断言请求次数时就容易差一次。

2. 成功路径会测首次成功不重试，以及第一次暂时失败、下一次成功后立即停止。失败路径会让所有尝试都失败，断言总次数恰好达到上限，最终向调用方返回约定错误，页面也能退出等待状态。

3. 错误要分类测试，不能把所有异常都重发。例如查询遇到暂时网络问题可以按策略尝试，但参数错误通常需要用户修改；创建订单之类的写操作还要确认幂等支持，客户端超时不能证明服务端没有执行。

4. 退避测试会固定随机来源，用假计时器检查时间边界。例如约定首次等待一百毫秒，就在九十九毫秒时确认还没发起，在到达一百毫秒后确认下一次尝试开始，再检查等待上限和成功后没有残留定时器。

5. 取消要分别发生在请求中和等待重试时，确认后续尝试不会继续开始。若实现支持 Retry-After 或总耗时预算，还要分别覆盖这些规则；测试中的一百毫秒用于清楚演示时间边界，业务等待时间则要结合接口约定和用户可以接受的等待长度确定。

## 追问：带随机抖动的退避时间怎么测？

1. 我会把随机函数作为可替换依赖，测试时让它返回固定值，这样预期等待时间能算出来。例如采用零到当前退避值之间的随机等待，就分别用靠近下界和上界的输入测试，而不是要求每次运行随机到相同结果。

2. 退避公式可以作为纯函数测试，重点检查次数增加、最大等待时间和非法参数。调度层只保留少量时间边界测试，确认计算结果确实用于安排下次请求，不需要为了每个公式分支都完整运行网络流程。

3. 我还会检查等待期间取消能否清掉定时任务，以及总超时是否会截断下一次重试。抖动是为了分散大量客户端的请求时刻，单个客户端测试只能验证计算和调度规则，不能直接证明真实流量已经被均匀分散。

## 追问：请求超时后，为什么不能直接重试写操作？

1. 超时代表客户端在规定时间内没得到结果，不等于服务端没完成写入。比如创建记录已经成功，只是响应丢失，再发送一次可能创建两条，所以我要先确认接口是否支持幂等键或者业务上的重复提交识别。

2. 如果有幂等键，我会让第一次尝试表现为响应丢失，检查重试是否复用同一个键和同一份业务参数。客户端测试能证明请求构造正确，至于服务端是否真的只创建一次，还需要在相应接口测试中检查持久化结果。

3. 如果接口没有这类保障，我会选择展示状态待确认、查询操作结果或让用户明确处理，不默认自动重发。测试也要覆盖这个分支，确认页面没有用一句“失败”误导用户以为服务端一定未处理，更不能自行宣称写入被回滚。
