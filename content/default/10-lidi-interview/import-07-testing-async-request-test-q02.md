# 重试要测几次？

## 核心回答

1. 「重试两次」是不是表示首次之外再试两次，也就是最多三次，先确认。测几次由重试规则和状态分支决定，不是挑一个数字反复跑。参数命名含糊，断言请求次数就容易差一次。

2. 成功路径：首次成功不重试；第一次暂时失败、下一次成功后马上停。失败路径：所有尝试都失败，总次数恰好到上限，最终按约定错误返回给调用方，页面也能退出等待。

3. 错误要分类测，不是所有异常都重发。查询碰到暂时网络问题，可以按策略再试；参数错误通常得用户改。创建订单这类写操作，还要确认有没有幂等支持。客户端超时，证明不了服务端没执行。

4. 退避测试把随机来源固定住，用假计时器查时间边界。约定首次等一百毫秒，就在九十九毫秒时确认还没发起，到一百毫秒后再确认下一次开始。等待上限、成功后有没有残留定时器，也要查。

5. 取消分别发生在请求中和等待重试时，确认后续尝试不会再开始。实现支持 Retry-After 或总耗时预算，这些规则也分开覆盖。测试里的一百毫秒是为了把时间边界看清楚，业务等待多长，还得结合接口约定和用户能接受的等待。

## 追问：带随机抖动的退避时间怎么测？

1. 随机函数做成可替换依赖，测试时让它返回固定值，预期等待时间就能算出来。零到当前退避值之间随机等，就分别用靠近下界和上界的输入测。别要求每次运行随机到同一个结果。

2. 退避公式可以当纯函数测，重点看次数增加、最大等待、非法参数。调度层只留少量时间边界测试，确认计算结果真用来安排下次请求。每个公式分支都完整跑一遍网络流程，没必要。

3. 等待期间取消能不能清掉定时任务，总超时会不会截断下一次重试，也要查。抖动是为了把大量客户端的请求时刻打散。单个客户端测试只能验计算和调度规则，证明不了真实流量已经被均匀分散。

## 追问：请求超时后，为什么不能直接重试写操作？

1. 超时只说明客户端在规定时间里没拿到结果，不等于服务端没写入。创建记录可能已经成功，只是响应丢了，再发一次可能变成两条。先确认接口支不支持幂等键，或者业务上认不认得出重复提交。

2. 有幂等键，就让第一次尝试表现为响应丢失，检查重试是不是复用同一个键、同一份业务参数。客户端测试能证明请求构造对。服务端是不是真的只创建一次，还要在对应接口测试里查持久化结果。

3. 接口没有这类保障，就展示状态待确认、去查操作结果，或者让用户明确处理，别默认自动重发。这个分支测试也要覆盖：页面别用一句「失败」让用户以为服务端一定没处理，更别自行宣称写入被回滚了。
