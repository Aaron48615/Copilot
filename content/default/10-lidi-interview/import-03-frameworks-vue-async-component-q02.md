# 异步组件失败怎么办？

## 核心回答

1. 异步组件加载失败应区分网络暂时不可用、资源不存在和模块代码异常。defineAsyncComponent 可以配置加载组件、错误组件、延迟和超时，让界面明确表达等待与失败，不能失败后永远保留转圈，也不应直接留下无法解释的空白区域。

2. 可以通过 onError 根据错误和尝试次数决定 retry 或 fail。重试应有上限和合理间隔，短暂断网恢复后可能成功，但文件路径错误或发布资源被删除时，无限重试只会重复失败，用户也不知道该采取什么动作。

3. 超时表示等待超过预期，不应简单等同于底层网络一定已取消。错误界面需要实际可执行的重试或返回方式，重试时确认重新开始了加载流程，避免按钮只清除提示，却再次读取同一个失败结果。

4. 如果新版本发布后旧页面引用的分包不存在，应检查入口与静态资源缓存策略。必要时提示刷新取得新入口，并考虑未保存内容；如果继续完善，我会增加旧版本资源场景验证，不能只在本地网络良好时测试一次组件出现。

5. 异步组件内部业务接口失败也需要自己的数据反馈，不是加载器的错误组件能自动处理所有异常。是否处于 Suspense 下会影响加载状态由谁控制，我会查看具体配置，把组件代码加载、组件渲染和内部请求三个过程分别说明。

## 追问：设置 timeout 后，请求就一定终止了吗？

1. 不一定，timeout 首先是异步组件等待与错误显示的控制，不能直接推断动态 import 的网络传输已经终止。底层加载方式和可取消能力要单独看，页面显示超时不代表服务器或浏览器已经停止所有工作。

2. 因此恢复逻辑需要考虑原加载稍后完成的情况，避免同时启动多份互相干扰的初始化。加载器的 retry、错误状态和组件实例创建应由明确机制协调，不能在每次超时后随意手动插入另一个相同组件。

3. 用户反馈可以写“加载时间较长，请重试”，不要声称操作已经完全取消。测试用可控制的延迟模拟超时后成功和持续失败，确认提示切换正确，没有永久错误状态或重复挂载造成的资源泄漏。

## 追问：什么样的错误不值得自动重试？

1. 确定的路径错误、资源已被删除和模块执行语法异常，通常不会因为立即再请求一次就恢复。反复重试只会增加等待和请求数量，应尽早显示失败，并提供返回、更新页面或联系维护者等适合的动作。

2. 临时网络问题可以有限重试，但也要考虑用户是否离线和组件是否仍需要显示。已经关闭的弹窗不应继续安排无限加载任务，重试时机应与当前交互状态一致，不能为了“自动恢复”在后台持续做无效工作。

3. 我会记录错误类型、资源地址和发布版本等定位信息，避免只统计一个失败总数。区分部署问题和网络波动以后，才能决定修复资源保留策略还是调整等待反馈，而不是给所有错误统一增加更多重试次数。
