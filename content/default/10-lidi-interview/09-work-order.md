# 智服工单的状态机、SLA 和权限是怎么设计的？

## 核心回答

1. 智服工单是给客服、维修人员和管理员使用的售后系统，前端用 Vue 2、Vuex 和 Element UI。主要流程是创建工单、分配、处理、回访再完成，对应待分配、待处理、处理中、待回访和已完成等状态，动作不能任意越级执行。

2. 页面根据当前状态、角色和负责人显示可执行动作，服务端收到请求再判断。比如工程师可以开始处理和提交回访，但不能直接完成工单，还需要确认工单分配给自己；只隐藏完成按钮无法防止直接调用接口。

3. 服务端在事务中用 FOR UPDATE 读取并锁住工单，按最新状态检查，再同时更新状态与操作记录。当前版本条件来自服务端锁后读取，并非前端打开页面时提交的版本，因此某些在最新状态下仍然合法的操作，还不能识别用户是否依据旧页面提交。

4. SLA 是按问题分类的处理时限，在创建时算截止时间存库，查询时与数据库当前时间比较，已完成和已取消排除。前端展示超时标签与筛选，当前没有按秒倒计时，也没有工作日历、暂停计时或自动催办，超时标记需要重新查询后才会更新。

5. 列表支持分页与多条件筛选，详情时间线说明谁在什么时候做了什么，看板用 ECharts 展示统计。独立数据可以并行请求，组件销毁时清理图表与监听；现有状态规则测试也不等于已经完成真实数据库并发测试。

## 追问：两个人同时点开始处理，后端怎样判断？

1. 第一个事务锁住工单，确认是待处理后更新为处理中并提交。第二个事务等到锁释放后读取最新状态，再执行开始处理就不合法，应返回冲突，而不是把页面传来的旧状态直接覆盖进去。

2. 前端收到冲突后需要刷新详情，说明工单已经变化，再根据最新状态显示按钮。不能在 catch 中盲目重新发送同一个动作，因为用户原本看到的业务条件已经不成立，重试可能继续失败或造成误操作。

3. 这能防止同一个状态转换被随意重复，但不代表所有旧页面动作都会被发现。比如重新分配在最新状态下仍合法，若没提交用户看到的版本，服务端未必知道他的依据过期，这需要版本协议与并发集成测试补足。

## 追问：超时数量为什么不能代表所有逾期处理情况？

1. 当前超时标记统计仍未完成、未取消且已过截止时间的工单，表达现在还有多少逾期任务。已经逾期但后来完成的工单会被排除，所以这个指标不等于历史上有多少工单没有按时完成。

2. 如果要统计历史履约，需要比较完成时间与当时截止时间，并明确取消、重新打开和规则调整如何处理。不能直接拿当前超时查询做历史报表，否则完成越多，历史逾期记录反而看起来越少。

3. 前端应使用明确指标名称与时间范围，例如当前未结逾期、期间逾期完成数量。当前超时标签只表达未结工单是否逾期。若要增加历史履约分析，还需要保存和使用完成时刻，并统一期间范围，不能直接复用当前标签的查询条件。
