# 构造函数返回基本类型会怎样？

## 核心回答

1. 普通构造函数，以及没有继承父类的基类构造器，显式返回基本类型通常会被忽略，结果仍是本次创建的实例。比如先给 `this` 设置名称，再返回一个数字，外部拿到的还是带有名称字段的对象，不是那个数字。

2. 这里基本类型也包含 `null` 和 `undefined`。`typeof null` 得到 `"object"`，但不能把它当成对象。普通构造器显式返回真正的对象或函数时，才会用这个返回值替换默认实例。函数值也要纳入判断，不能只检查对象类型。

3. 构造过程可以拆开看：运行时先建立实例及原型关系，再执行初始化代码，最后根据返回结果决定交出哪个对象。默认实例被替换，前面执行过的赋值或其他副作用也不会被撤销。返回规则只决定最终结果。

4. 派生类构造器是单独的边界，不能照搬基本类型一律忽略的结论。它返回非 `undefined` 的基本类型会抛错；返回 `undefined` 时仍要能拿到已初始化的 `this`，通常意味着已经成功调用了 `super()`。

5. 手写 `new` 的简化实现应明确只覆盖普通构造函数，不能说等价于所有构造行为。需要通用地动态构造实例，优先用 `Reflect.construct`。class 不能用普通函数调用模拟，继承、内建对象和构造目标还有更多规则。

## 追问：返回对象后 instanceof 为什么可能变成假？

1. `instanceof` 的常见判断，是看构造器的原型对象是否出现在结果的原型链上。构造函数最后返回一个普通对象字面量，这个对象通常沿着普通对象的原型链查找，并没有连到该构造函数的原型，所以结果可能是假。

2. 就算构造期间曾经往默认实例写入字段，最终返回的另一个对象也不会自动继承那些字段。调用方看到属性丢失，应检查是不是显式返回了替代对象，别只检查赋值语句有没有执行。两件事可以同时发生。

3. 接口本来就是工厂，返回不同对象可以是明确设计，但别让调用方误以为一定得到该类实例。把返回类型和调用方式说清楚。需要稳定的实例身份，就沿着正常构造路径初始化，别随意替换结果对象。

## 追问：手写 new 用 apply 调用构造函数有哪些局限？

1. 常见练习是先按构造函数原型创建对象，再用 `apply` 把这个对象作为 `this` 传入，最后处理显式返回值。它能演示很多普通函数的行为，但 class 不允许这样直接调用，遇到类构造器就无法通用。

2. 某些内建对象还需要由真正的构造过程建立内部状态，光把原型接上不够。构造函数里的 `new.target` 在普通调用和构造调用中也不同。表面字段相同，涉及构造分支的代码仍可能表现不一致。

3. 任务要求接受多种构造器，用 `Reflect.construct`，让运行时走真正的构造流程。手写版本可以留着解释原型和返回规则，但要限定支持范围，并用类构造器等边界例子对照原生行为。
