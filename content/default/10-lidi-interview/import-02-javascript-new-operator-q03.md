# 构造函数返回基本类型会怎样？

## 核心回答

1. 对于普通构造函数，以及没有继承父类的基类构造器，显式返回基本类型通常会被忽略，结果仍是本次创建的实例。比如先给 `this` 设置名称，再返回一个数字，外部拿到的还是带有名称字段的对象，不是那个数字。

2. 这里基本类型也包含 `null` 和 `undefined`，不能因为 `typeof null` 得到字符串 `"object"` 就把它当成对象。普通构造器显式返回真正的对象或函数时，才会用这个返回值替换默认实例，所以函数值也必须纳入手写判断，不能只检查对象类型。

3. 我会把构造过程拆开解释：运行时先建立实例及原型关系，再执行初始化代码，最后根据返回结果决定交出哪个对象。这样即使默认实例被替换，前面执行过的赋值或其他副作用也不会被撤销，返回规则只是决定最终结果。

4. 派生类构造器是需要单独说明的边界，不能照搬基本类型一律忽略的结论。它返回非 `undefined` 的基本类型会抛错；返回 `undefined` 时仍要能够取得已初始化的 `this`，通常意味着已经成功调用了 `super()`。

5. 因此手写 `new` 的教学实现应明确只覆盖普通构造函数，不能宣称等价于所有构造行为。假设需要通用地动态构造实例，我会优先使用 `Reflect.construct`，因为 class 不能用普通函数调用模拟，继承、内建对象和构造目标还有更多规则。

## 追问：返回对象后 instanceof 为什么可能变成假？

1. `instanceof` 的常见判断是看构造器的原型对象是否出现在结果的原型链上。假设构造函数最后返回一个普通对象字面量，这个对象通常沿着普通对象的原型链查找，并没有连接到该构造函数的原型，因此结果可能是假。

2. 即使构造期间曾经往默认实例写入字段，最终返回的另一个对象也不会自动继承那些字段。调用方看到属性丢失时，应该检查是否显式返回了替代对象，而不是只检查赋值语句有没有执行，两件事可以同时发生。

3. 如果接口本来就是工厂，返回不同对象可以是明确设计，但不应让调用方误以为一定得到该类实例。我会把返回类型和调用方式说清楚；若需要稳定的实例身份，就尽量沿着正常构造路径初始化，避免随意替换结果对象。

## 追问：手写 new 用 apply 调用构造函数有哪些局限？

1. 常见练习是先按构造函数原型创建对象，再用 `apply` 把这个对象作为 `this` 传入，最后处理显式返回值。它能演示很多普通函数的行为，但 class 不允许这样直接调用，所以遇到类构造器就无法通用。

2. 某些内建对象还需要由真正的构造过程建立内部状态，光把原型接上并不足够。构造函数里的 `new.target` 在普通调用和构造调用中也不同，因此即使表面字段相同，涉及构造分支的代码仍可能表现不一致。

3. 假设任务要求接受多种构造器，我会使用 `Reflect.construct`，让运行时执行真正的构造流程。手写版本可以保留为解释原型和返回规则的练习，但应在说明中限定支持范围，并用类构造器等边界示例展示它与原生行为的差别。
