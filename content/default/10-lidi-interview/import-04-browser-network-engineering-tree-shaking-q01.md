# sideEffects 写错会怎样？

## 核心回答

1. sideEffects 是向打包器描述模块求值是否会产生必须保留的外部影响。它不是说这个文件导出的函数永远没有副作用，而是帮助工具判断：如果导出没人使用，整个模块能否连同执行一起省略，这个含义必须先分清。

2. 错误地写成 false，可能把仅靠导入触发的 CSS、polyfill 或注册代码删掉。例如组件功能还在，生产页面样式却没了，原因可能不是 CSS 选择器，而是包含样式导入的模块被认为可以安全跳过。

3. 反过来把所有文件都标成有副作用，会让构建器保守保留更多模块，增加体积，但这通常首先是优化问题。两类错误的风险不同，不能为了让报告里的大小变小，就未经核对把整个包设置为无副作用。

4. 我会列出真正需要保留的入口或文件模式，例如样式文件与初始化模块，同时尽量把纯工具函数和初始化行为分开。具体模式还要符合构建器与包目录的匹配规则，不是写一个看起来像路径的字符串就保证生效。

5. 验证要用消费方的生产构建，检查只导入单个组件、只导入样式和执行注册等场景。开发模式可能没有同样的优化，因此热更新正常不能证明声明正确；没有实际运行验证之前，不能只凭类型检查和包体积通过就发布。

## 追问：一个函数内部会发请求，模块还能标无副作用吗？

1. 可以讨论，因为判断重点是模块被加载求值时是否立即产生影响。仅导出一个请求函数，但没有在顶层调用它，未使用的导出有机会被移除；函数在未来被调用时有副作用，并不自动等于模块导入就有副作用。

2. 如果顶层立刻执行请求、注册事件或修改全局，那就不同了。即使它没有任何导出，导入它也会改变程序行为，这类文件不能为了减体积随意标为可跳过，否则初始化可能完全不发生。

3. 我会查看顶层语句和依赖导入，而不只搜索函数名。一个看起来纯的文件也可能导入带副作用的依赖，声明需要反映整个模块执行关系，并通过实际生产产物和初始化行为确认。

## 追问：生产环境样式丢失，怎样确认是 sideEffects 导致的？

1. 先确认 CSS 源文件确实被导入，开发环境能看到相应样式，再检查生产资源清单和产物里是否存在目标规则。如果规则存在只是被覆盖，就应排查层叠优先级，而不是直接修改副作用声明。

2. 如果整个样式模块消失，我会查看所在包的 sideEffects 和导入路径，做一个只消费该组件的最小生产构建。临时保留相应文件后样式恢复，可以缩小问题范围，但仍要找出真正需要保留的文件集合。

3. 修复后覆盖按需导入和全部导入两种方式，确认样式保留同时没有把整个库强行打进去。最后检查发布包中的声明和样式路径，因为仓库配置正确却发布了另一份 package.json，也会造成使用方失败。
