# 什么时候用 requestAnimationFrame 而不是 Worker？

## 核心回答

1. requestAnimationFrame 和 Worker 解决的问题不同。页面的 window.requestAnimationFrame 把回调安排到一次绘制前，适合轻量视觉更新；后者提供独立执行上下文，适合不需要直接操作 DOM 的重计算，不能把两者简单理解成两个异步定时器。

2. 例如拖拽时需要更新元素位置，可以记录最新指针位置，在一次动画帧回调里统一应用，避免同一帧重复改很多次 DOM。这里的页面回调仍在主线程，里面如果排序巨大数组或解析大文件，页面照样会卡，不因为对齐帧就变轻。

3. 大文件解析、复杂数据转换可以放进 Worker，算完再把结果交给页面。Worker 无法直接修改 DOM，但符合条件的 Dedicated Worker 有自己的 requestAnimationFrame，可以配合 OffscreenCanvas 绘图；它要求关联拥有者 window，并需确认浏览器支持，不能把页面动画帧和后台绘图调度混为一谈。

4. 两者可以配合：Worker 分批计算，页面把最新进度或结果安排到合适的帧显示。要限制消息频率和更新范围，否则后台虽然算得快，主线程接收几千条消息并重新渲染大量元素，仍然可能成为新的瓶颈。

5. 动画要根据时间差计算进度，不能假设所有设备都固定每秒六十帧。后台标签页的动画回调也可能被暂停或限频，页面卸载时要取消请求并释放 Worker；选工具先看任务是否必须接触 DOM，再看计算量和通信成本。

## 追问：动画为什么要使用回调时间戳，而不是每帧移动固定距离？

1. 不同屏幕刷新率和运行负载会改变回调频率，每帧固定移动相同像素，会让动画在高刷新率设备上更快，卡顿时又更慢。按经过时间计算位置，可以让动画时长和速度更接近预期，而不是依赖固定帧数。

2. 我会保存起始时间或上次时间戳，用差值推进，并处理长时间暂停后的跳变。比如后台切回时可以按目标进度恢复，或者限制一次模拟步长，具体取决于是在做过渡动画还是需要稳定物理计算。

3. 验证时覆盖不同刷新率、后台切换和主线程忙碌，确认动画不会瞬移到错误状态。requestAnimationFrame 提供的是调度机会，不保证固定帧率，因此业务逻辑不应依赖回调必定以某个频率到达。

## 追问：Worker 每算出一点进度就发消息，会有什么问题？

1. 高频消息会增加结构化克隆、事件派发和主线程状态更新成本。即使每条内容很小，几千次回调也可能让页面忙于显示进度，反而影响真正的交互响应，后台计算收益就被通信开销抵消。

2. 我会按时间或工作批次聚合进度，只保留最新状态，并让页面在合适的帧更新。最终结果和错误不能因为节流被漏掉，因此协议需要区分普通进度与结束事件，结束时及时确认并清理任务。

3. 测试时比较不开进度、逐条进度和聚合进度的交互表现与总耗时。若页面只显示一个百分比，就没有必要传整份中间数据；通信内容应服务界面需求，而不是把 Worker 内部每一步都暴露出来。
