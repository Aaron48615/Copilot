# 什么时候用 requestAnimationFrame 而不是 Worker？

## 核心回答

1. `requestAnimationFrame` 和 Worker 解决的问题不一样。页面的 `window.requestAnimationFrame` 把回调安排到一次绘制前，适合轻量视觉更新。Worker 提供独立执行上下文，适合不需要直接操作 DOM 的重计算。两者不是两个异步定时器。

2. 比如拖拽时要更新元素位置，记下最新指针位置，在一次动画帧回调里统一应用，避免同一帧反复改很多次 DOM。这里的页面回调仍在主线程。里面如果排序巨大数组、解析大文件，页面照样卡。对齐帧不会自动变轻。

3. 大文件解析、复杂数据转换可以放进 Worker，算完再把结果交给页面。Worker 不能直接改 DOM。符合条件的 Dedicated Worker 有自己的 `requestAnimationFrame`，可以配合 OffscreenCanvas 绘图。它要求关联拥有者 window，还要确认浏览器支持。页面动画帧和后台绘图调度，别混成一件事。

4. 两者可以配合：Worker 分批算，页面把最新进度或结果安排到合适的帧显示。消息频率和更新范围要限制。后台虽然算得快，主线程接收几千条消息、再重新渲染大量元素，仍可能成为新瓶颈。

5. 动画按时间差算进度，别假设所有设备都固定每秒六十帧。后台标签页的动画回调也可能被暂停或限频。页面卸载时取消请求、释放 Worker。选工具先看任务是不是必须碰 DOM，再看计算量和通信成本。

## 追问：动画为什么要使用回调时间戳，而不是每帧移动固定距离？

1. 不同屏幕刷新率、不同运行负载会改变回调频率。每帧固定移动相同像素，高刷新率设备上会更快，卡顿时又更慢。按经过时间计算位置，动画时长和速度更接近预期，不依赖固定帧数。

2. 保存起始时间或上次时间戳，用差值推进，长时间暂停后的跳变也要处理。后台切回来时可以按目标进度恢复，也可以限制一次模拟步长。做过渡动画，还是需要稳定物理计算，这两种需求不一样。

3. 覆盖不同刷新率、后台切换、主线程忙碌，确认动画不会瞬移到错误状态。`requestAnimationFrame` 提供的是调度机会，不保证固定帧率。业务逻辑不该依赖回调必定以某个频率到达。

## 追问：Worker 每算出一点进度就发消息，会有什么问题？

1. 高频消息会增加结构化克隆、事件派发、主线程状态更新的成本。每条内容很小，几千次回调也可能让页面忙着显示进度，反而影响真正的交互。后台计算收益就被通信开销抵消了。

2. 按时间或工作批次聚合进度，只留最新状态，页面在合适的帧更新。最终结果和错误不能因为节流被漏掉。协议要区分普通进度和结束事件，结束时及时确认并清理任务。

3. 比较不开进度、逐条进度、聚合进度的交互表现和总耗时。页面只显示一个百分比，没必要传整份中间数据。通信内容服务界面需求，Worker 内部每一步都暴露出来，通常过重。
