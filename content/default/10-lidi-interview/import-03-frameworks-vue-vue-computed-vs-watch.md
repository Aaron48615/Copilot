# computed 和 watch 有什么区别？

## 核心回答

1. computed 适合从已有响应式数据推导一个结果，例如商品总价、筛选列表或是否允许提交。它声明“这些输入对应什么值”，依赖未变化时可以复用计算结果，不需要再存一份 state 然后手动维护同步，这样数据来源更少也更容易理解。

2. watch 适合因为某个数据变化而执行副作用，例如查询详情、写入存储或调用外部组件接口。它明确监听来源，并可取得新旧值；处理异步操作时还要考虑清理和旧结果，不能只写“监听后请求”就认为所有快速变化都正确。

3. 例如根据搜索词过滤已经存在的列表，可以用 computed；搜索词改变后要向服务器请求另一份数据，可以用 watch。两者可以一起使用，但各自负责不同事情，不能把计算总价也写成异步监听，再维护一个可能短暂过时的 total。

4. computed 的 getter 应保持纯粹，不请求接口、不修改其他状态，也不要在里面排序原始数组。需要排序可以返回副本结果；有些场景支持可写 computed，通过 setter 将赋值转换成明确更新，但它仍应有清楚的数据来源和转换规则。

5. 我会根据需要的是“值”还是“动作”选择，而不是按哪种写法更熟悉。watch 的深度、立即执行和刷新时机需要按场景设置，computed 的缓存也依赖正确的响应式读取；读取当前时间等非响应式来源，不会自动获得持续更新的时钟。

## 追问：为什么不在 computed 里直接请求接口？

1. computed 可能在被读取时才重新计算，并根据依赖缓存结果，不适合承担“必须执行几次”的网络动作。请求跟着 getter 首次求值或依赖失效后的重新求值发生，执行时机与展示读取耦合，不适合管理网络流程；依赖不变时重复读取会复用缓存，不会因此重跑 getter。

2. 它也不自动管理 Promise 的加载、失败和取消。可以由 watch 或专门的请求 composable 管理接口结果，再让 computed 从结果中派生展示，这样异步流程和纯计算各自清楚，错误反馈不会藏在一个值计算里。

3. 例如先按用户编号获取订单数组，再 computed 计算未完成数量。快速切换用户时请求层防止旧结果覆盖，数量计算只使用当前结果；比一个 async computed 同时负责请求、过滤和错误提示更容易验证。

## 追问：computed 返回排序数组时，为什么要复制原数组？

1. Array.sort 会原地修改数组，如果在 getter 里直接排序作为输入的响应式数组，就把派生计算变成了数据修改。其他依赖原顺序的组件会被影响，计算过程中还可能触发额外依赖更新，数据关系不再是单向推导。

2. 可以先复制再排序，或在环境支持时使用返回新数组的排序方式。这样原始列表仍代表接口或用户保存的顺序，排序结果只表达当前展示选择，切换排序规则不会悄悄改变其他页面看到的数据。

3. 我会测试原数组在读取 computed 后保持不变，并检查相同依赖下结果合理复用。复制本身也有成本，大数据需要测量，但不能为了省一次复制就牺牲纯计算约定，必要时可以重新设计排序和分页的位置。
