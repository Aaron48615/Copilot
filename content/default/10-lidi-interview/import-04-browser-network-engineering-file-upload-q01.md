# 上传过程中如何取消和重试？

## 核心回答

1. 取消上传我会同时处理请求和任务状态。每个文件或分片关联 AbortController，点击取消后停止仍在运行的请求，并禁止队列继续启动新分片，界面进入已取消状态，不能只把进度条隐藏。

2. 重试前先区分原因，网络中断和明确的临时服务错误可以有限重试，格式不合法、没有权限等错误通常需要先修正。遇到限流还要尊重服务端的等待提示，使用退避和随机扰动，避免大量分片同时重新发出。

3. 分片上传需要稳定的上传任务标识和分片序号。服务端把同一任务的同一分片按幂等方式保存，前端恢复时查询已完成清单，只补缺失部分；不能因为客户端没收到成功就断定服务端一定没存下来。

4. 取消之后仍要防止迟到回调改变界面。我会用任务版本或状态检查，忽略旧任务的成功通知，并确认旧请求的 finally 不会影响新任务；重新上传同名文件也不能误接上之前不同内容的进度。

5. 客户端 abort 不等于服务端删除临时文件，彻底放弃还需要明确的取消接口或过期清理。任务只有在服务端校验、合并完成后才算成功，上传字节到达百分之百也可能仍处于处理阶段，界面应分别展示。

## 追问：取消后点击继续，应该从哪个位置恢复？

1. 我会向服务端查询该上传任务已经确认保存的分片，以这个清单为准恢复，而不是只看本地进度条。最后一个请求可能在取消前已成功保存，只是响应没有到达，完全相信本地状态会重复上传。

2. 恢复还要校验文件身份，例如尺寸和内容标识，确认用户选回的是同一个文件。文件名相同并不够，内容变化后应创建新任务，避免把两个不同文件的分片合并到一起，产生难以发现的数据损坏。

3. 服务端可能已经清理过期任务，这时需要明确提示重新上传。浏览器关闭后也不一定仍能读取原文件，因此界面应允许重新选择并匹配，不能把断点续传理解成任何时候都能自动继续。

## 追问：分片都上传完了，合并接口超时该不该直接再调？

1. 先查询任务状态，因为合并可能已经完成，只是客户端没有收到响应。若立即重新创建合并任务，可能重复写最终文件或生成多个资源记录，因此服务端应让同一上传任务的合并操作具备幂等性。

2. 我会让任务状态区分上传中、合并中、成功和失败，并返回最终资源标识。仍在合并时可以有限轮询，已经成功就读取结果，明确失败后再按可重试错误处理，不把超时一律当作合并未执行。

3. 重试期间界面要说明正在确认处理结果，避免用户不停点击提交。测试应包含响应丢失、重复调用和中途取消，确认最后只得到一份有效文件，并且临时分片能按规则清理。
