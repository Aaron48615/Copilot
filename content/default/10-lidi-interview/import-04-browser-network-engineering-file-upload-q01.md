# 上传过程中如何取消和重试？

## 核心回答

1. 取消上传要同时处理请求和任务状态。每个文件或分片关联 `AbortController`，点取消后停掉还在跑的请求，队列也不许再启动新分片，界面进入已取消状态。只把进度条藏起来不够。

2. 重试前先分清原因。网络中断、明确的临时服务错误，可以有限重试；格式不合法、没有权限，通常得先修正。遇到限流还要尊重服务端的等待提示，用退避和随机扰动，避免大量分片同时重新发出。

3. 分片上传需要稳定的上传任务标识和分片序号。服务端把同一任务的同一分片按幂等方式保存。前端恢复时查询已完成清单，只补缺失部分。客户端没收到成功，不能断定服务端一定没存下来。

4. 取消之后仍要挡住迟到回调改界面。用任务版本或状态检查，忽略旧任务的成功通知，并确认旧请求的 `finally` 不会影响到新任务。重新上传同名文件，也不能误接上之前不同内容的进度。

5. 客户端 abort 不等于服务端删了临时文件。彻底放弃还需要明确的取消接口，或者过期清理。任务只有在服务端校验、合并完成后才算成功。上传字节到了百分之百，也可能还在处理阶段，界面应分开展示。

## 追问：取消后点击继续，应该从哪个位置恢复？

1. 向服务端查询这个上传任务已经确认保存的分片，以这份清单为准恢复，别只看本地进度条。最后一个请求可能在取消前已经成功保存，只是响应没到。完全信本地状态，会重复上传。

2. 恢复还要校验文件身份，比如尺寸和内容标识，确认用户选回来的是同一个文件。文件名相同不够，内容变了应创建新任务，避免把两个不同文件的分片合并到一起，弄出很难发现的数据损坏。

3. 服务端可能已经清掉过期任务，这时要明确提示重新上传。浏览器关了之后，也不一定还能读到原文件，界面应允许重新选择并匹配。断点续传不是任何时候都能自动继续。

## 追问：分片都上传完了，合并接口超时该不该直接再调？

1. 先查询任务状态，因为合并可能已经完成，只是客户端没收到响应。若立刻重新创建合并任务，可能重复写最终文件，或者生成多条资源记录。所以服务端应让同一上传任务的合并操作具备幂等性。

2. 任务状态区分上传中、合并中、成功和失败，并返回最终资源标识。还在合并时可以有限轮询，已经成功就读结果，明确失败后再按可重试错误处理。超时一律当成合并没执行过，不行。

3. 重试期间界面要说明正在确认处理结果，避免用户不停点提交。测试应包含响应丢失、重复调用和中途取消，确认最后只有一份有效文件，临时分片也能按规则清掉。
