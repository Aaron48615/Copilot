# TCP 三次握手和四次挥手讲一下？

## 核心回答

1. TCP 建立连接通常经过三次握手：客户端发送 SYN 和自己的初始序列号，服务端回复 SYN 加 ACK，客户端再确认服务端的序列号。双方由此建立发送和接收状态，为后面的可靠字节传输做准备。

2. 不能只用双方各发一句话就完成建立，因为服务端还需要知道自己的连接信息被对方接收。第三次确认也有助于避免过期连接请求造成错误状态；握手确认的是传输连接，不是用户已经通过登录鉴权。

3. 正常关闭时，TCP 的两个方向可以分别结束。主动方发送 FIN，另一方确认后仍可能有数据要发送，待它也结束时再发 FIN，由主动方确认，所以常见描述是 FIN、ACK、FIN、ACK 四个报文。

4. 报文数量不保证永远等于四，对方没有待发送数据时可以合并确认和关闭，也可能存在同时关闭或 RST 异常中止。FIN 表示这个方向不再发送数据，不是收到它就立刻丢弃另一方向尚未完成的内容。

5. 最后通常由主动关闭方进入 TIME_WAIT，处理最后确认可能丢失和旧报文残留。对于前端，理解这些机制有助于看连接耗时和复用，但 HTTP/3 用的是 QUIC，不能把 TCP 的握手和挥手直接套到所有网页请求上。

## 追问：三次握手后，为什么应用请求仍可能失败？

1. 握手只说明传输连接建立了，不说明 TLS 已成功，也不说明业务服务已经返回有效响应。HTTPS 还可能遇到证书或协议问题，随后 HTTP 请求又可能因为鉴权失败、服务端错误等原因不能完成。

2. 即使建立时网络正常，之后也可能丢包、断开或等待超时。前端需要分别识别网络异常和服务端返回的错误状态，不能把连接成功当作整个业务操作成功，更不能因此省略错误处理。

3. 排查时我会按连接、TLS、首字节和业务响应分层查看信息。保留脱敏的请求时间和标识，让服务端能关联记录，这比把所有失败都描述成接口超时更有助于确定问题发生在哪一步。

## 追问：FIN 和 RST 关闭连接有什么不同？

1. FIN 用于有序结束一个发送方向，已发送的数据仍按协议正常处理，对端也可以继续把剩余数据发完。这适合业务通信完成后的正常关闭，需要双方各自结束自己的发送方向。

2. RST 表示连接被重置或立即拒绝，可能来自异常状态、应用中止或目标端没有对应连接。它不是正常四次挥手的一部分，应用可能直接收到连接重置错误，未完成的数据也不能当成已可靠交付。

3. 看到 RST 时我会结合哪一端发出、发生时间和代理日志判断，不能只凭一个报文断定服务器故障。对写请求尤其要查询业务结果或使用幂等标识，避免因连接重置后盲目重发而重复执行。
