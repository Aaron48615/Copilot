# TCP 三次握手和四次挥手讲一下？

## 核心回答

1. TCP 建连通常经过三次握手：客户端发 SYN 和自己的初始序列号，服务端回 SYN 加 ACK，客户端再确认服务端的序列号。双方由此建立发送和接收状态，给后面可靠的字节传输做准备。

2. 双方各说一句话还建不成。服务端还需要知道自己的连接信息已经被对方收到。第三次确认也有助于避免过期连接请求造成错误状态。握手确认的是传输连接，不是用户已经通过登录鉴权。

3. 正常关闭时，TCP 两个方向可以分别结束。主动方发 FIN，另一方确认后仍可能还有数据要发，等它也结束时再发 FIN，由主动方确认。所以常见描述是 FIN、ACK、FIN、ACK 四个报文。

4. 报文数量不保证永远等于四。对方没有待发数据时，可以把确认和关闭合并；也可能同时关闭，或者用 RST 异常中止。FIN 表示这个方向不再发数据，收到它不等于立刻丢掉另一方向还没完成的内容。

5. 最后通常由主动关闭方进入 TIME_WAIT，处理最后确认可能丢失，以及旧报文残留。对前端来说，理解这些有助于看连接耗时和复用。但 HTTP/3 用的是 QUIC，不能把 TCP 的握手和挥手直接套到所有网页请求上。

## 追问：三次握手后，为什么应用请求仍可能失败？

1. 握手只说明传输连接建好了，不说明 TLS 已经成功，也不说明业务服务已经返回有效响应。HTTPS 还可能碰到证书或协议问题，随后 HTTP 请求又可能因为鉴权失败、服务端错误等原因完不成。

2. 即使建立时网络正常，之后也可能丢包、断开或等到超时。前端要分别认出网络异常，和服务端返回的错误状态。连接成功不等于整个业务操作成功，错误处理也不能因此省掉。

3. 排查按连接、TLS、首字节、业务响应分层看。留下脱敏的请求时间和标识，让服务端能对上记录。把所有失败都说成接口超时，不如说清楚卡在哪一步。

## 追问：FIN 和 RST 关闭连接有什么不同？

1. FIN 用来有序结束一个发送方向，已经发出去的数据仍按协议正常处理，对端也可以继续把剩余数据发完。这适合业务通信完成后的正常关闭，双方各自结束自己的发送方向。

2. RST 表示连接被重置或立刻拒绝，可能来自异常状态、应用中止，或者目标端没有对应连接。它不是正常四次挥手的一部分。应用可能直接收到连接重置错误，没完成的数据也不能当成已经可靠交付。

3. 看到 RST 时，结合哪一端发出、发生时间、代理日志来判断，别只凭一个报文断定服务器故障。对写请求尤其要查业务结果，或者用幂等标识，避免连接重置后盲目重发、操作被执行两遍。
