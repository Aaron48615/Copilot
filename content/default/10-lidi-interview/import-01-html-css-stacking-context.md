# z-index 为什么有时候不生效？

## 核心回答

1. `z-index` 不生效时，先看元素是否参与相应层叠，以及声明有没有被盖掉。普通 `static` 元素通常不能直接靠它调层级，但 Flex 和 Grid 子项有例外。「必须加 `position`」不是完整规则，先看实际布局身份。

2. 真正的重点是层叠上下文。每个上下文内部先排序，再作为整体参加父级比较。较低父容器里的菜单就算写很大的数字，也不能直接越过更高的兄弟上下文。数字只有放在正确的比较范围里才有意义，不是整个文档统一比大小。

3. 常见创建条件包括：`relative` 或 `absolute` 配合非 `auto` 的 `z-index`，`fixed`、`sticky`，以及非 `none` 的 `transform`、低于 1 的 `opacity`、`isolation: isolate` 等。沿双方祖先查到共同的比较位置，再决定抬哪个容器，或改弹层挂载位置。别无意把整块业务区域抬上去。

4. 还要分清被覆盖和被裁剪。`overflow` 把超出部分藏了，层级变大通常解决不了。原生模态 `dialog` 这类顶层元素，也有独立于普通层级的呈现机制。排查先确认上下文、包含块、裁剪各自起什么作用，再改。三类问题别都归成 `z-index` 太小。

5. 相同层级附近还会受具体绘制规则和文档顺序影响。两个元素都写同样的数字，不代表谁都可以稳定盖住谁。必要的前后关系尽量写清楚，免得组件换个挂载顺序，弹层表现就变了。

## 追问：z-index: auto 和 z-index: 0 为什么可能不一样？

1. 以 `relative` 或 `absolute` 元素为例，`auto` 通常不会仅凭这个组合创建新的层叠上下文，明确的 `0` 会建立一个。即便两种情况下当前盒子看起来都在相近位置，后代参与外部层叠的范围也可能已经不同。

2. 所以给某个父容器「随手补个 0」，可能把菜单限制在内部，原本能盖住外部内容的子项突然被挡住。排查不但看目标菜单的数字，还要看祖先是不是从 `auto` 改成了明确值。这种变化常被认为没有视觉影响，容易漏。

3. 用一个外部浮层和内部高层级子项做对照，看改前改后谁盖谁。注意 `fixed`、`sticky` 或已有 `transform` 的元素可能本来就有上下文。`relative` 场景的结论，不能无条件套到所有定位类型上。

## 追问：isolation: isolate 适合在什么情况下使用？

1. 它可以明确建立一个层叠上下文，让组件内部的层级或混合效果在局部范围内处理。比如卡片有背景装饰和内容，内部要安排前后关系，又不希望装饰跟外部区域产生意外层叠关联，这种边界比较清楚。

2. 但边界也会限制子项。卡片里的全局菜单如果需要盖住其他模块，放在隔离范围内可能不合适。装饰属于卡片，跨区域浮层挂到合适的外部容器。别先把所有内容隔离，再给菜单无限加数字。

3. 用之前确认目的，用之后测内部负层级装饰、外部导航和弹层覆盖关系。`isolation` 不是性能优化口令，也不等于创建固定定位包含块。它们都像「隔离」，机制却不是一回事。
