# z-index 为什么有时候不生效？

## 核心回答

1. z-index 不生效时，我会先看元素是否参与相应层叠，以及声明有没有被覆盖。普通 static 元素通常不能直接靠它调整层级，但 Flex 和 Grid 子项有例外，所以不能把“必须加 position”当成完整规则，先看实际布局身份。

2. 真正的重点是层叠上下文。每个上下文内部先排序，再作为整体参加父级比较；比如较低父容器中的菜单即使写很大的数字，也不能直接越过更高的兄弟上下文。数字只有放在正确的比较范围里才有意义，不是整个文档统一比大小。

3. 常见创建条件包括 relative 或 absolute 配合非 auto 的 z-index，fixed、sticky，以及非 none 的 transform、低于 1 的 opacity、isolation: isolate 等。我会沿双方祖先查到共同的比较位置，再决定提升哪个容器或改变弹层挂载位置，避免无意抬高整块业务区域。

4. 还要区分被覆盖和被裁剪，overflow 隐藏了超出部分时，层级变大通常解决不了。原生模态 dialog 等顶层元素也有独立于普通层级的呈现机制。排查时先确认上下文、包含块和裁剪各自起什么作用，再修改，不能把三类问题都归成 z-index 太小。

5. 相同层级附近还会受具体绘制规则和文档顺序影响，所以两个元素都写同样的数字，不代表谁都可以稳定盖住谁。我会尽量让必要的前后关系明确表达，避免组件换个挂载顺序后弹层表现就发生变化。

## 追问：z-index: auto 和 z-index: 0 为什么可能不一样？

1. 以 relative 或 absolute 元素为例，auto 通常不会仅凭这个组合创建新的层叠上下文，而明确的 0 会建立一个。即使两种情况下当前盒子看起来都在相近位置，后代参与外部层叠的范围也可能已经不同。

2. 因此给某个父容器“随手补个 0”可能把菜单限制在内部，让原本能覆盖外部内容的子项突然被遮住。排查时不仅要看目标菜单的数字，还要检查祖先是否从 auto 改成了明确值，这种变化常被认为没有视觉影响而忽略。

3. 我会用一个外部浮层和内部高层级子项做对照，观察修改前后谁覆盖谁。注意 fixed、sticky 或已有 transform 的元素可能本来就有上下文，不能把 relative 场景的结论不加条件地套到所有定位类型上。

## 追问：isolation: isolate 适合在什么情况下使用？

1. 它可以明确建立一个层叠上下文，让组件内部的层级或混合效果在局部范围内处理。比如卡片有背景装饰和内容，需要内部安排前后关系，希望装饰不与外部区域产生意外层叠关联时，这种边界比较清楚。

2. 但边界也会限制子项。卡片里的全局菜单如果需要覆盖其他模块，放在隔离范围内可能不合适；我会让装饰属于卡片，让跨区域浮层挂到合适的外部容器，而不是先隔离所有内容再给菜单无限增加数字。

3. 使用前要确认目的，使用后测试内部负层级装饰、外部导航和弹层覆盖关系。isolation 不是性能优化口令，也不等于创建固定定位包含块，不能因为它们都像“隔离”，就把不同 CSS 机制混为一谈。
