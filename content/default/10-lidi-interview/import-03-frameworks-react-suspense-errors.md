# React 的懒加载失败和错误边界怎么处理？

## 核心回答

1. React.lazy 用于按需加载组件代码，通常配合动态 import，把暂时不需要的模块延后获取。外层 Suspense 在代码等待时显示占位，但网络断开或脚本不存在属于失败，不能指望加载动画自己变成错误提示。

2. lazy 的加载 Promise 拒绝后会把错误交给最近的错误边界。边界应显示可理解的说明和恢复入口，并记录模块、页面和应用版本等必要信息；不要只输出一段堆栈，让用户不知道是继续等、重试还是返回。

3. 我会按功能区布置边界，例如详情区域加载失败时保留导航。普通按钮事件和 Effect 内请求的失败需要自己的处理，边界不是全局 try/catch；服务端渲染也需要框架对应的错误机制，不能把客户端边界的职责扩大到所有环境。

4. 重试要确认是否能重新执行加载。lazy 会缓存加载相关结果，单纯重置边界不保证同一个失败 lazy 重新发请求；可以在加载层设计有限重试，或者使用框架支持的恢复流程，不能在组件 render 里不断创建新的 lazy 类型。

5. 如果发布时删除了旧脚本，仍打开旧 HTML 的用户可能请求一个已经不存在的文件。这时要检查部署与缓存策略，必要时提示刷新并保护未保存内容；如果继续完善，我会验证离线、旧版本资源和恢复联网的场景，而不是宣称有边界就不会白屏。

## 追问：动态 import 失败时，应该自动刷新页面吗？

1. 不能对所有失败都立即刷新。用户断网时刷新不会让文件出现，还可能把原来能使用的部分也丢掉；编辑页面还有未保存内容，应先提供说明和可控重试，让用户理解刷新会带来什么影响。

2. 如果确认是新版本发布导致旧文件不可用，刷新取得新入口可能有效，但要限制自动刷新次数，避免缓存配置错误引发循环。也可以提示用户保存当前内容后更新，不必把一次模块错误变成整页不断重载。

3. 后续应检查构建资源保留与入口缓存策略，减少旧页面引用失效文件的机会。前端边界负责合理反馈，部署策略负责让可引用的资源存在，两者需要分别处理，不能只靠重试按钮掩盖资源发布问题。

## 追问：错误边界放最外层一个就够了吗？

1. 最外层边界能避免未处理渲染错误直接影响整个根，但所有异常都走它，会让一个小部件出错也替换整页。用户可能失去导航和正在填写的内容，恢复范围与实际问题大小并不匹配。

2. 可以围绕独立功能增加局部边界，例如图表、富文本预览或详情区域，各自提供适合的失败提示。公共布局外再保留总边界处理未预期错误，粒度来自业务可独立使用的区域，而不是每个小按钮都套一层。

3. 我会测试边界本身渲染失败和重置行为，确保还有外层可以承接，并避免恢复时清空无关状态。错误记录也要防止多层重复上报同一次异常，否则日志很多，却难以判断真实故障发生了几次。
