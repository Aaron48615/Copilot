# Sass 和 Less 有什么区别？

## 核心回答

1. Sass 和 Less 都是把扩展语法编译成 CSS 的预处理器，常用能力包括变量、嵌套、混入和计算。浏览器最终处理的是产物 CSS，不直接理解这些源码；选择时我会先看现有工程和组件库的配套，再看是否真的需要额外的样式编程能力。

2. 语法上，SCSS 使用美元符号变量和花括号，Less 使用 @ 变量；Sass 还提供缩进语法，SCSS 是它的一种语法形式，不是另一套完全独立的工具。两者都能复用样式逻辑，不能简单说 Less 没有条件或循环，它有守卫、递归混入等表达方式。

3. Sass 的模块系统可以用 @use 和 @forward 组织命名空间和对外接口，适合避免公共变量散落到全局。Sass 的旧 @import 已被官方弃用，新代码应优先理解模块用法；但这不代表现有项目里的所有 import 立即失效，迁移需要结合版本和依赖检查。

4. 原生 CSS 自定义属性和嵌套已经覆盖一部分日常需求，因此没有必要只为写变量就必然引入预处理器。运行时主题可以用自定义属性，构建时批量生成规则可以用预处理器；我会控制嵌套深度和产物大小，避免源码短了，输出的选择器却越来越难覆盖。

## 追问：Sass 的 @use 相比旧 @import 解决什么问题？

1. 旧式导入容易把变量、函数和混入放进共享作用域，名字冲突时不容易判断来自哪里。@use 默认带命名空间，使用公共变量时能看出所属模块，阅读某个组件的样式就不必到处猜定义来源。

2. 模块通常只加载一次，也可以通过配置和转发明确对外暴露的内容。比如设计变量模块只输出允许组件使用的颜色和间距，内部计算细节不必全部暴露，这有助于限制修改影响，但仍需要合理的模块划分。

3. 迁移时我会检查变量覆盖时机、第三方样式和重复输出，不能只把关键词机械替换。先验证构建后的 CSS 和几个关键页面，再逐步清理旧入口；没有检查项目版本和依赖前，不应声称迁移一定没有行为变化。

## 追问：预处理器嵌套太深会有什么实际问题？

1. 嵌套会展开成更长的选择器，常常把样式与 DOM 层级绑定。页面中间新增一层容器或把按钮移到别处，就可能让原样式失效；覆盖时又需要更复杂的选择器，维护成本逐渐增加。

2. 我会尽量围绕组件类和状态类组织规则，而不是完整复刻 HTML 树。比如卡片按钮有独立类名，就不必从页面、列表、卡片一路套到 button，伪类状态可以就近嵌套，结构关系只在确实必要时表达。

3. 还要检查编译后的产物，循环、混入和扩展可能生成大量重复声明或复杂选择器。源文件行数少不等于最终 CSS 小，评估时看实际输出和覆盖难度，才能判断抽象是否真的让项目更容易维护。
