# Sass 和 Less 有什么区别？

## 核心回答

1. Sass 和 Less 都是把扩展语法编译成 CSS 的预处理器，常用能力有变量、嵌套、混入和计算。浏览器最终处理的是产物 CSS，不直接认这些源码。选哪个，先看现有工程和组件库配套，再看是不是真的需要额外的样式编程能力。

2. 语法上，SCSS 用美元符号变量和花括号，Less 用 `@` 变量。Sass 还提供缩进语法，SCSS 是它的一种写法，不是另一套完全独立的工具。两者都能复用样式逻辑，别说 Less 没有条件或循环，它有守卫、递归混入这类表达。

3. Sass 的模块系统用 `@use` 和 `@forward` 组织命名空间和对外接口，公共变量不容易散落到全局。旧的 Sass `@import` 官方已经弃用，新代码优先搞懂模块用法。现有项目里的 import 不会立刻失效，迁移要结合版本和依赖一起查。

4. 原生 CSS 自定义属性和嵌套已经覆盖一部分日常需求，只为写变量不一定非要上预处理器。运行时主题可以用自定义属性，构建时批量生成规则可以用预处理器。嵌套深度和产物大小要管住，源码短了、输出的选择器却越来越难覆盖，就不划算。

## 追问：Sass 的 @use 相比旧 @import 解决什么问题？

1. 旧式导入容易把变量、函数、混入放进共享作用域，名字冲突时很难说清来自哪。`@use` 默认带命名空间，用公共变量时能看出所属模块，看某个组件的样式不必到处猜定义来源。

2. 模块通常只加载一次，也可以通过配置和转发明确对外暴露什么。设计变量模块只输出允许组件用的颜色和间距，内部计算细节不必全亮出来，修改影响面更好控，模块怎么划还是得合理。

3. 迁移时查变量覆盖时机、第三方样式和重复输出，关键词机械替换不够。先验证构建后的 CSS 和几个关键页面，再逐步清旧入口。项目版本和依赖没核对过，迁移后行为不一定还一样。

## 追问：预处理器嵌套太深会有什么实际问题？

1. 嵌套会展开成更长的选择器，常常把样式和 DOM 层级绑死。页面中间多套一层容器，或把按钮挪到别处，原样式就可能失效。覆盖时又得写更复杂的选择器，维护成本慢慢涨。

2. 尽量围着组件类和状态类组织规则，不必完整复刻 HTML 树。卡片按钮有独立类名，就不必从页面、列表、卡片一路套到 `button`。伪类状态可以就近嵌套，结构关系只在确实必要时写。

3. 还要看编译后的产物。循环、混入、扩展可能生成大量重复声明或复杂选择器。源文件行数少不等于最终 CSS 小。评估看实际输出和覆盖难度，才知道这层抽象是不是真让项目更好维护。
