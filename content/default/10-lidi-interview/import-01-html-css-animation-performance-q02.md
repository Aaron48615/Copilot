# 怎么判断是 JS 还是 CSS 卡？

## 核心回答

1. 我不会直接把问题分成“JS 卡”或“CSS 卡”两类，因为脚本修改样式以后，后续布局和绘制也可能是主要开销。首先固定一个能复现的动作，录制包含输入和画面更新的时间段，再看长时间占用发生在哪个阶段。

2. 如果时间线主要是脚本执行，就沿调用栈找重复渲染、计算或事件处理。例如输入一个字符却让整张列表重新过滤和更新，可以先减少重复计算与无关更新；但要结合具体函数耗时，不能只因为页面用了框架就归咎于框架。

3. 如果脚本不长，却有大量样式计算、布局和绘制，我会检查变动范围。动画持续修改宽高、复杂阴影覆盖大区域、每次滚动都测量节点，都可能带来开销。此时应分别尝试改动画属性、缩小绘制区域或调整读写顺序。

4. 验证时我会保留操作步骤和设备条件，修改一个因素后重新录制，比较对应的阶段是否改善。开发模式、扩展程序和调试工具本身也会干扰结果，正式判断要尽量接近用户环境；没有证据时只说怀疑某处，不能直接宣布已经找到根因。

## 追问：发现一段很长的脚本任务后，怎么决定优化哪部分？

1. 我会先看它是否出现在用户交互到下一帧之间，再展开调用栈看自身耗时和子调用耗时。一个外层函数名称出现在栈顶，不代表它的业务逻辑最贵，时间可能实际花在里面触发的渲染或数据处理。

2. 对重复计算可以缓存合适的结果，对不必要的组件更新可以减少依赖变化；可拆分的大工作可以分批让出主线程。如果计算独立于 DOM，再考虑 Worker，同时估计消息传递和数据复制的成本。

3. 优化后需要重复同一个触发动作，并确认结果仍然正确。比如减少筛选次数不能让列表显示旧查询条件，拆分任务也不能让用户快速切换条件后看到旧结果，响应更快与状态正确需要一起验证。

## 追问：动画看起来卡，但主线程没有明显长任务怎么办？

1. 我会继续看每帧是否都有中等开销叠加，而不是只找特别长的一根柱子。高刷新率设备留给每帧的时间更少，多个不算长的布局或绘制组合起来，也可能错过预期的显示时机。

2. 然后检查绘制区域、图层数量、图片尺寸以及合成相关信息。大面积模糊、透明覆盖和高分辨率纹理可能增加图形处理负担，主线程没有长任务不能证明整个渲染过程都很轻。

3. 还要排除动画曲线、资源尚未解码以及屏幕录制等因素造成的视觉感受差异。可以暂时换成纯色块或关闭某个效果做对照，再回到真机验证；这种对照能缩小范围，但不能替代最终页面的测试。
