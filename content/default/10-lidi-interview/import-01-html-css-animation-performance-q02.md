# 怎么判断是 JS 还是 CSS 卡？

## 核心回答

1. 卡顿很少能干净切成「JS 卡」或「CSS 卡」。脚本改完样式，后面的布局和绘制也可能很重。先固定一个能复现的动作，把输入和画面更新那段录下来，看长时间占用落在哪个阶段。

2. 时间线主要是脚本在跑，就顺着调用栈找重复渲染、计算、事件处理。比如敲一个字，整张列表又过滤又更新，先砍重复计算和无关更新。要看具体函数耗时，别因为用了某个框架就把锅扣给框架。

3. 脚本不长，却有大量样式计算、布局、绘制，就看变动范围。动画一直改宽高、大面积复杂阴影、每次滚动都去量节点，都可能贵。这时分别试：换动画属性、缩小绘制区域、调整读写顺序。

4. 操作步骤和设备条件留着，一次改一个因素再录，对比对应阶段有没有改善。开发模式、扩展、调试工具自己也会搅结果，正式判断尽量靠近用户环境。没有记录就说怀疑某处，别直接宣布已经找到根因。

## 追问：发现一段很长的脚本任务后，怎么决定优化哪部分？

1. 先看它是不是卡在用户操作到下一帧之间，再展开调用栈，看自身耗时和子调用耗时。外层函数名字在栈顶，不代表它的业务逻辑最贵，时间可能花在里面触发的渲染或数据处理上。

2. 重复计算可以缓存合适的结果；不必要的组件更新，少让依赖变；能拆的大活分批，把主线程让出来。计算跟 DOM 没关系，再考虑 Worker，同时估一下消息传递和数据复制贵不贵。

3. 优化后再做同一个动作，结果还得对。少筛几次，列表不能还显示旧查询条件；任务拆开了，人快速改条件也不能看到旧结果。更快和状态正确要一起验。

## 追问：动画看起来卡，但主线程没有明显长任务怎么办？

1. 别只找特别长的一根柱子，看每帧是不是都有中等开销叠在一起。高刷新率设备每帧时间更短，几个不算长的布局或绘制加起来，也可能错过该显示的那一帧。

2. 接着看绘制区域、图层数量、图片尺寸、合成相关信息。大面积模糊、透明覆盖、高分辨率纹理会加重图形处理。主线程没有长任务，不等于整段渲染都轻。

3. 动画曲线、资源还没解码完、屏幕录制，都可能让人觉得卡。可以暂时换成纯色块或关掉某个效果对照，再回到真机看。对照能缩小范围，替代不了最终页面上的测试。
