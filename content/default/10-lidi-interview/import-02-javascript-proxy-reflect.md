# Proxy 和 Reflect 通常怎么一起使用？

## 核心回答

1. Proxy 是对象操作的拦截入口，Reflect 是执行对应操作的标准方法。比如读取时先做记录，再通过 Reflect.get 拿结果；写入时先校验，再通过 Reflect.set 执行。自己的逻辑和默认行为比较容易分开。

2. 在 get 和 set 里转发 `receiver` 很关键。它能留住访问器的 `this`，以及继承时谁在被赋值。直接写 `target[key]`，简单字段可能看不出差异，但 getter 里再次读取其他字段时，访问入口可能已经绕过代理，观察就不完整。

3. 不同拦截器也有不同返回要求。set 需要表示操作是否成功，deleteProperty 需要报告删除是否成功。Reflect 的对应方法便于透传这些结果，但不能把所有方法理解成只返回布尔值。读取返回值、获取键列表，各有自己的含义。

4. 设计一个简化响应式对象，可以在读取时记下当前计算用到了哪个字段，在成功修改后通知相关计算。代理只提供拦截能力。怎么存依赖、避免重复通知、清理旧依赖、处理嵌套对象，仍然要自己实现。

5. 代理还要遵守目标对象的约束，不能任意伪造某些不可配置属性的结果。原对象直接修改、集合内部操作这些场景都有边界。用普通对象说明配合方式就够了，这个示例并不覆盖所有对象类型。

## 追问：get 里直接读 target[key] 会漏掉什么？

1. 对象有个 getter 叫姓名，内部读取 `this.first` 和 `this.last`。直接访问 `target[key]` 会让 getter 的 `this` 指向原对象，这两次内部读取也发生在原对象上，代理可能只记录到 name 这一层访问。

2. 通过 Reflect.get 传入原始 `receiver` 后，getter 里的 `this` 可以保持为代理，内部字段读取便能再次进入 get。这样一个简化依赖系统才知道计算实际用到了名和姓，改其中一项时有机会找到需要重新计算的内容。

3. 但在拦截器里把代理本身当成目标，再次读取同一个属性，又可能递归进入相同拦截器，一直循环。通常向 Reflect 传真正的目标，保留 `receiver` 表达谁在被访问。两者职责不同，不能为了让读取经过代理就随意互换。

## 追问：为什么有了 get 和 set 还不等于响应式？

1. 拦截器只能告诉你发生了读取或写入，并不知道哪个页面计算正在用这个字段。要做响应式，还得在执行计算时记下当前订阅者，把对象、键和订阅者关联起来。写入时才能找到该通知谁，不是每次刷新整个页面。

2. 依赖关系也会变。条件为真时读姓名，为假时读编号，重新执行后应去掉上一轮已经不用的依赖。不然姓名后来变了仍然触发无关计算，长期运行还可能留下不再使用的订阅者。光有代理解决不了这个问题。

3. 另外还需要批量调度、避免计算递归触发自身，以及提供停止订阅的入口。删除字段和遍历键也要单独考虑。学习实现时明确只覆盖普通字段的读写，再逐项补这些行为，别把几行拦截代码说成完整框架。
