# catch 之后还能继续执行吗？

## 核心回答

1. 可以继续，但同步异常捕获和 Promise 的错误处理不一样。同步代码在 `try` 里抛错，会跳到匹配的 `catch`，被跳过的语句不会补执行。捕获分支正常结束，又没有 `return` 或重新抛错，后面的代码接着跑。

2. Promise 的 `catch` 返回一个新 Promise。处理函数正常返回普通值，后续链会转向成功分支，并收到这个值。只记日志、不写返回值，也相当于返回了 `undefined`，下游可能以为错误已经恢复，继续去读不存在的数据。

3. 捕获分支再次抛错，后续链继续保持拒绝。返回另一个 Promise，就要等它的结果决定下一步。失败后尝试读缓存，必须把读缓存的 Promise 返回给链条，不然下游不等它，缓存读取的异常也可能脱离原来的处理范围。

4. 能不能恢复，看业务有没有真实可用的替代结果，语法允许继续不等于业务上可以继续。非关键推荐可以降级成空列表；保存操作失败却不能返回假成功。错误处理要让调用者知道结果可不可靠，后面还要做什么，比如要不要留着输入等用户再提交。

## 追问：catch 里只写日志，为什么后面的 then 还会执行？

1. 错误处理函数被调用后，只要正常结束，这一步本身就算成功。没写返回值时返回的是 `undefined`，新 Promise 因此完成，后面的成功回调自然会跑，原来的错误不会自动继续往下传。

2. 后面的代码准备显示保存成功，前面只记了失败日志，就会误导。当前层只能补上下文、恢复不了业务，记完应重新抛出，让真正负责交互的调用方收到失败，别继续走成功路径。

3. 也可以返回明确区分成功和失败的结果对象，后续代码先看标签再动手。用异常还是结果对象，调用约定要一致。别一部分分支抛错，一部分分支偷偷返回没有含义的空值。

## 追问：外层 try 能捕获定时器回调和未等待的异步函数错误吗？

1. 一般不能靠包住调用位置解决。定时器回调之后才执行，外层那次同步调用早就结束了。回调内部直接抛的异常，不在那次 `try` 的执行范围里，得在回调自己处理，或把操作接到可等待的异步结果上。

2. 异步函数抛错会变成拒绝的 Promise。只调用它而不等待，外层同步捕获也收不到这个拒绝。`await` 等上之后，拒绝才会在等待位置变成可捕获的异常，或者走返回链上的 `catch`。

3. 任务必须后台跑，就给它单独安排失败处理，并留下必要上下文。不需要返回值，不等于可以忽略错误。还要确认页面离开后任务还跑不跑，完成时还有没有资格更新页面。
