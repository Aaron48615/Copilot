# catch 之后还能继续执行吗？

## 核心回答

1. 可以继续，但我会先区分同步的异常捕获和 Promise 的错误处理。同步代码在 `try` 中抛错后，会跳到匹配的 `catch`，被跳过的语句不会补执行；如果捕获分支正常结束，且没有返回或重新抛错，程序就继续执行后面的代码。

2. Promise 的 `catch` 返回一个新的 Promise，处理函数正常返回普通值时，后续链会转向成功分支，并收到这个值。即使只记录日志而不写返回值，也相当于返回了 `undefined`，所以下游可能误以为错误已经恢复，继续读取不存在的数据。

3. 如果捕获分支再次抛错，后续链会继续保持拒绝状态；如果返回另一个 Promise，则要等它的结果决定下一步。假设失败后尝试读取缓存，必须把读取缓存的 Promise 返回给链条，否则下游不会等待，缓存读取的异常也可能脱离原来的处理范围。

4. 我认为能否恢复取决于业务有没有真实可用的替代结果，而不只是语法允不允许继续。非关键推荐内容可以考虑降级为空列表，保存操作失败却不能返回假成功；错误处理应该让调用者知道结果是否可靠，并明确后续还需要做什么，例如是否应保留输入等待用户再次提交。

## 追问：catch 里只写日志，为什么后面的 then 还会执行？

1. 错误处理函数被调用后，只要正常结束，就代表这个处理步骤本身成功了。没有写返回值时返回的是 `undefined`，新 Promise 因此完成，后面的成功回调自然会执行，而不是自动继续传播原来的错误。

2. 假设后续代码准备显示保存成功提示，前面只记录失败日志就会产生误导。若当前层只能补充上下文、不能恢复业务，应记录后重新抛出，让真正负责交互的调用方接收到失败，而不是继续走成功路径。

3. 另一种做法是返回明确区分成功和失败的结果对象，由后续代码先判断标签再操作。无论采用异常还是结果对象，都要保持调用约定一致，不能部分分支抛错，部分分支偷偷返回不带含义的空值。

## 追问：外层 try 能捕获定时器回调和未等待的异步函数错误吗？

1. 一般不能靠包住调用位置解决，因为定时器回调会在之后执行，外层同步调用早已结束。回调内部直接抛出的异常不在那次 `try` 的执行范围内，需要在回调自身处理，或把操作接入可等待的异步结果。

2. 异步函数抛错会形成拒绝的 Promise，只调用它而不等待，外层同步捕获也收不到这个拒绝。使用 `await` 等待后，拒绝才会在等待位置表现为可捕获的异常，或通过返回链上的 `catch` 来处理。

3. 假设任务必须后台执行，我会明确给它安排独立的失败处理，并保留必要上下文。不能因为不需要返回值，就忽略错误；还应确认页面离开后任务是否继续，以及它完成时是否仍有资格更新页面。
