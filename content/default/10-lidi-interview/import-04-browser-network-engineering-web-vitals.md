# LCP、INP、CLS 分别怎么理解和优化？

## 核心回答

1. LCP、INP、CLS 分别看主要内容出现、交互响应、布局稳不稳。它们不是同一条加载耗时换了三个名字。页面哪个方面让用户在等或点错，先确认，再用对应指标和时间线定位。只追一个综合分数，容易改偏。

2. LCP 关注视口内主要内容的呈现时间，候选可能是大图或文本块。服务器首字节、资源发现和下载、主线程绘制都可能影响它。优化主图之外，入口返回和渲染阻塞也要查。最大的那个文件，不一定就是 LCP 元素。

3. INP 关注点击、触摸、键盘这类交互，通常取页面最慢的那次。交互很多时按规则排除少量极端值。拆成输入等待、事件执行、下一次呈现。减少长任务、同步布局、大范围更新。请求业务完成时间和下一帧响应时间，要分开看。

4. CLS 关注意外布局位移，取页面各会话窗口里累计位移分数的最大值，不是整次访问无限累加。窗口内相邻位移间隔小于一秒，窗口最长五秒。图片、广告、异步内容先留空间，字体替换也要查，不稳定会少很多。

5. 实验室测试和真实用户数据一起看，按路由、设备、版本比较，采样口径保持一致。当前核心指标用 INP，只看首次输入等待的 FID 替不了。验证要包含真实点击和后续内容更新，记下候选元素和交互路径，前后比较的是同一类体验。

## 追问：实验室测试与真实用户数据不一致，应该信谁？

1. 两者回答的问题不一样。实验室提供可重复的环境，方便定位某次加载或交互。真实用户数据覆盖实际设备、网络、访问路径，但也受样本、采样、用户构成影响。挑更好看的那个当结论，站不住。

2. 路由、登录状态、缓存、版本是否一致，先对上，再按设备等维度拆。某个低端设备群体表现差，实验室默认环境可能漏掉。线上均值变化，也可能来自用户结构变了，不是代码本身变快。

3. 排查用实验室复现原因，验收再看对应真实场景有没有改善。目前只有本地结果，就把验证范围说清楚，测试条件记下来。一次 Lighthouse 高分，不能说成所有线上用户都达到同样体验。

## 追问：优化一个指标，为什么可能让另一个指标变差？

1. 提前加载大量内容，后续等待可能变短，却抢了主图带宽，或加重主线程执行，LCP 或 INP 变差。把所有工作推迟到点击之后，首屏更轻，用户第一次操作却卡住。优化成本没有凭空消失。

2. 关键访问路径说清楚，相关指标和业务完成时间一起观察。比如保留关键主图，非必要图表延后初始化，用户进图表页时给合理加载方式。只围着首页一次测试堆配置，别的路径会付出代价。

3. 改完比较首次访问、后续操作、慢设备表现，发现退化再调。指标是帮着描述体验的。为了降低某个值把主要内容藏起来，或改掉候选，报告好看了，用户完成原来的任务反而更难。
