# 搜索 composable 要处理什么？

## 核心回答

1. 搜索 composable 不只是封装一个 fetch，我会先明确输入和输出。输入包括关键词、筛选条件、页码以及请求函数，输出包括结果、加载、错误和重试方法；条件是否即时生效也要说明，避免调用方不知道传入 ref 后变化会不会重新查询。

2. 可以接收 ref 或 getter，并在监听或 watchEffect 的响应式执行范围内读取，使依赖变化能够被跟踪。若调用方只传 keyword.value 的当前字符串，函数拿到的是当时值，之后输入改变不会自动通知它，这种接口边界应讲清楚。

3. 请求层需要防抖、取消和有效性判断。防抖减少连续输入发起的次数，取消尽量节省工作，请求编号或失效标记保证旧结果不能覆盖新条件；错误和 loading 也应遵守相同归属规则，不能只保护成功数据。

4. 搜索条件改变时通常还要重置页码，清空输入时明确展示全部、空结果还是初始提示。重试应复用当前已确认条件，而不是上次失败时已经过期的闭包，卸载或停用时还要按使用场景处理待执行定时器和请求。

5. 我会让 composable 管理可复用的数据行为，把结果列表布局和具体提示样式留给组件。测试重点是快速变更条件、返回乱序、清空和失败重试，我会用可控制完成顺序的模拟请求验证这些边界，尤其确认清空后没有旧结果重新出现，重试时使用的是当前有效条件。

## 追问：为什么搜索词变化时要同时处理页码？

1. 新条件通常代表一组新的结果，沿用旧页码可能请求到超出范围的位置。例如上一条件在第十页，新关键词只有两页，如果仍请求第十页，界面显示空列表，用户容易误以为完全没有匹配项。

2. 我会把条件确认和页码重置作为同一次明确操作，避免分别监听造成先查新条件旧页码、再查第一页的重复请求。具体实现可以使用组合查询状态，或在生成请求参数前统一处理，但必须保证输入含义一致。

3. 页码是否重置也有业务例外，例如只切换展示样式不应改变结果页。把影响查询集合的条件和纯界面配置区分开，能减少不必要重查；测试时也要验证后退恢复 URL 条件不会被误当成新搜索清掉页码。

## 追问：请求函数由外部传入，对测试有什么帮助？

1. composable 不必固定依赖某个真实接口，测试可以提供返回受控 Promise 的函数。这样能明确安排第二次搜索先成功、第一次后失败，稳定验证竞态处理，比依赖真实网络随机慢快更容易复现边界情况。

2. 还能直接检查传给请求函数的参数，确认筛选变化时页码重置、清空时遵守约定。组件测试则关注用户输入到结果展示的行为，不需要在每个用例里复制底层网络模拟细节，测试关注点更清楚。

3. 注入不意味着暴露一大串内部选项。接口应保留请求取消信号和必要结果类型，同时把防抖和状态转换封装好；如果为了测试把全部内部变量都公开，反而让调用方依赖实现，之后修改会更困难。
