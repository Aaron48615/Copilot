# 搜索 composable 要处理什么？

## 核心回答

1. 搜索 composable 不只是包一层 `fetch`。输入是关键词、筛选、页码，以及真正发请求的函数；输出是结果、加载中、错误、重试方法。条件变了会不会立刻再查，也要说清楚。调用方传进 `ref` 之后，不知道会不会自动重新查询，这个接口就算糊。

2. 可以接收 `ref` 或 getter，在监听或 `watchEffect` 同步执行那段里读，依赖变化才能被跟上。调用方只传 `keyword.value` 这个当时的字符串，函数拿到的是快照，后面输入再变也不会通知它。这种边界要讲开。

3. 请求层要有防抖、取消、以及这次结果还算不算数。防抖少发几次连续输入；取消能省就省；请求编号或失效标记拦住旧结果盖住新条件。`error` 和 `loading` 也按同一套归属来，别只护住成功数据。

4. 搜索条件一变，页码通常要回到第一页。输入清空后，是展示全部、空结果，还是初始提示，得定下来。重试用的是当前已确认的条件，不是失败那次闭包里过期的词。组件卸掉或停用时，待跑的定时器和请求也按场景处理。

5. composable 管可复用的数据行为，列表怎么排、提示用什么样式留给组件。测试重点是条件改得很快、返回乱序、清空、失败再重试。用能控制完成顺序的假请求，确认清空后旧结果不会再冒出来，重试时条件是现在这份。

## 追问：为什么搜索词变化时要同时处理页码？

1. 新条件是另一组结果，还拿着旧页码，可能请求到根本没有的位置。上一条件在第十页，新词只有两页，还去要第十页，界面是空的，人容易以为完全没匹配。

2. 条件确认和页码重置放进同一次操作。分别监听容易先查“新条件 + 旧页码”，再查第一页，多打一次。可以用组合查询状态，或在拼请求参数前统一处理，两边含义要一致。

3. 也有不该重置页码的，比如只换了展示样式。影响查询集合的条件和纯界面配置分开，少查冤枉请求。浏览器后退把 URL 条件带回来，别当成一次新搜索把页码清掉。

## 追问：请求函数由外部传入，对测试有什么帮助？

1. composable 不必写死某个真实接口。测试可以塞一个返回受控 Promise 的函数，安排第二次搜索先成功、第一次后失败，竞态就能稳定复现。真实网络谁快谁慢，不好卡这个点。

2. 传给请求函数的参数也能直接查：筛选变了页码有没有重置、清空时有没有按约定来。组件测试管用户输入到结果展示，不必每个用例都把底层网络模拟再抄一遍。

3. 注入不是把内部选项全摊开。请求取消信号和结果类型留着，防抖和状态转换封装好。为了测试把内部变量全公开，调用方就会绑死实现，以后改更难。
