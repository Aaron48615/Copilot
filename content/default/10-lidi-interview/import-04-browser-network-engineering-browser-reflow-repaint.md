# 重排和重绘的区别？怎么减少？

## 核心回答

1. 重排也叫布局，是浏览器重新计算元素的尺寸和位置，例如改变容器宽度会影响文字换行和后续元素位置。重绘是更新像素外观，例如背景颜色变化通常不需要重新计算几何信息，影响范围还取决于具体页面。

2. 我会先避免循环里交替读写布局。修改宽度后马上读取 offsetHeight，浏览器为了返回准确结果，可能被迫提前布局；如果每个元素都这样处理，就把原本可以合并的工作拆成了很多次。

3. 改进时可以先集中读取所需尺寸，再统一修改样式，或者用一个 class 表达一组状态变化。DocumentFragment 有利于组织离线节点，但不能保证一定更快；框架批量更新也不代表浏览器只布局一次，最后仍要看实际时间线。

4. 做位移动画时通常优先考虑 transform，透明变化考虑 opacity，因为满足图层等条件时它们有机会主要在合成阶段完成。不能承诺永远不绘制，也不能到处加 will-change；我会用性能面板看布局、绘制和图层开销是否真的下降。

5. 比如展开侧栏会改变正文可用宽度，正文重新换行属于必要布局，不能为了完全避免重排而阻止正常排版。我会先区分必须发生的布局和重复触发的布局，再优化后者，避免把性能建议误用成不允许任何几何变化。

## 追问：把代码放进 requestAnimationFrame，就不会强制布局了吗？

1. 不会。requestAnimationFrame 只安排回调在一次绘制前执行，不会改变 DOM API 的语义。如果回调里仍然先改宽度、再读几何信息，浏览器为了给出最新结果，仍可能同步计算布局。

2. 我会把需要的旧尺寸先读出来，再集中写入。若必须读取修改后的尺寸，可以明确接受一次布局，或者拆到合适的后续阶段；重点是减少无意义的往返，而不是机械地给每段代码套一个回调。

3. 验证时录制同一次交互，查看回调内是否出现重复的 Layout，以及哪些读取触发了它。只看代码调用了 requestAnimationFrame，或者动画肉眼偶尔顺畅，都不足以说明布局抖动已经解决，还要确认耗时来源确实发生了变化。

## 追问：will-change 为什么不能给所有元素都加？

1. will-change 是提前告诉浏览器某些属性可能变化，浏览器可以据此准备资源。例如拖拽即将开始时提示 transform，有时能减少动画开始阶段的准备成本，但浏览器并不保证一定按某种方式优化。

2. 让大量元素长期保持独立图层可能增加纹理内存、栅格化和合成成本，移动设备上尤其需要注意。一个很大的列表即使每张卡片都只做简单动画，也不意味着每张卡片都值得长期保留图层。

3. 我会在实际需要前短暂设置，结束后移除，再比较动画帧耗时和图层数量。若瓶颈本来是复杂 JavaScript 或图片解码，添加这个属性不会解决主要问题，应该先处理真正耗时的工作。
