# 重排和重绘的区别？怎么减少？

## 核心回答

1. 重排也叫布局，是浏览器重新算元素的尺寸和位置。比如改容器宽度，文字会换行，后面的元素位置也会跟着动。重绘是更新像素外观，比如改背景色，通常不用再算一遍几何信息，影响范围还得看具体页面。

2. 循环里别交替读写布局。改完宽度马上读 `offsetHeight`，浏览器为了给你准数，可能被迫提前布局。每个元素都这么来一遍，本来能合并的活就被拆成很多次。

3. 改进可以先把要用的尺寸集中读完，再统一改样式，或者用一个 class 表达一组状态变化。`DocumentFragment` 适合组织离线节点，但不保证一定更快。框架批量更新，也不等于浏览器只布局一次，最后还是看实际时间线。

4. 做位移动画通常优先 `transform`，透明变化用 `opacity`，图层等条件满足时，它们有机会主要在合成阶段完成。这不等于永远不绘制，也不能到处加 `will-change`。性能面板里看布局、绘制和图层开销是不是真的下来了。

5. 比如展开侧栏会挤正文可用宽度，正文重新换行是必要布局，不能为了完全躲开重排就把正常排版禁了。先分清必须发生的布局和重复触发的布局，再去优化后者。

## 追问：把代码放进 requestAnimationFrame，就不会强制布局了吗？

1. 不会。`requestAnimationFrame` 只是把回调安排到一次绘制前执行，DOM API 的语义没变。回调里仍然先改宽度、再读几何信息，浏览器为了给出最新结果，照样可能同步算布局。

2. 需要的旧尺寸先读出来，再集中写入。如果必须读修改后的尺寸，就明确接受这一次布局，或者拆到后面合适的阶段。重点是少做无意义的来回，不是每段代码都套一个回调。

3. 验证时录同一段交互，看回调里有没有重复的 Layout，以及哪些读取把它触发了。代码里调用了 `requestAnimationFrame`，或者动画肉眼偶尔顺，都不够。还得确认耗时来源确实变了。

## 追问：will-change 为什么不能给所有元素都加？

1. `will-change` 是提前告诉浏览器某些属性可能要变，浏览器可以据此准备资源。比如拖拽马上开始时提示 `transform`，有时能少掉动画开头那截准备成本。但浏览器不保证一定按某种方式优化。

2. 大量元素长期各自占一层，纹理内存、栅格化和合成成本都会上去，手机上更明显。一个很大的列表，就算每张卡片只做简单动画，也不等于每张都值得长期留图层。

3. 真正要用之前短暂设上，结束了再拿掉，再比较动画帧耗时和图层数量。瓶颈如果本来是复杂 JavaScript 或图片解码，加这个属性解决不了主要问题，得先处理真正耗时的那块。
