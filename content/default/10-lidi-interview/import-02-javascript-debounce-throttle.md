# 防抖和节流的区别？分别怎么实现？

## 核心回答

1. 防抖通常是等待连续触发停止一段时间后再执行，期间再次触发就重新计时，适合搜索联想这类更关心最后输入的场景。节流则控制持续触发时的执行频率，让滚动或拖动过程中仍有更新机会，具体何时执行还取决于首尾触发规则。

2. 实现防抖时，我会用闭包保存定时器，每次调用先清除旧定时器，再保存最新参数并安排新任务，回调也要保留需要的接收者。节流可以保存上次执行时间，或者用定时器控制下一次执行，如果需要结束后补一次，就要保存最后一轮参数。

3. 轻购搜索联想设置了三百毫秒防抖，输入期间重新计时，停下以后再请求，我把它看作减少重复请求和等待感之间的一个取舍。用户点击搜索按钮时应取消等待中的联想任务并按当前关键词立即搜索，组件卸载时也要清理定时器，避免留下延迟执行。

4. 我会明确防抖节流只能减少调用，不会自动取消已经发出的请求，也不能保证响应按发送顺序回来，因此搜索仍需旧结果校验。如果以后要调整等待时间，应结合交互体验验证；拖拽还要检查结束位置是否提交，不能只关注过程中调用变少。

## 追问：用户一直输入会不会让防抖永远不执行？

1. 对于只有尾部触发的普通防抖，只要每次输入都早于等待时间结束，任务就会一直被推迟。搜索联想可能可以接受这种行为，但自动保存如果一直等不到停顿，就可能让大量编辑内容长时间没有保存。

2. 如果需求不允许无限等待，可以考虑增加最大等待时间，同时记录这一轮开始时间和最近触发时间。达到最大等待时间时使用最新参数执行，再开启下一轮，这属于可以补充的设计，不能说原有防抖天然具备这种保证。

3. 我会用连续触发、短暂停顿和停止输入三个序列验证行为，确认不会同时触发两次保存。还要明确手动保存是否应立即执行并清除待执行任务，避免用户已经提交成功，随后旧定时器又发送一次相同内容。

## 追问：拖拽节流如何保证最后位置没有丢失？

1. 只有时间戳判断的简单节流可能丢掉末次事件，因为它发生时尚未达到间隔，之后用户又停止移动。这样画面或保存位置就停在之前的坐标，所以需要明确尾部补执行，或者在拖拽结束事件中主动提交最终位置。

2. 如果选择尾部定时器，我会让等待期间的新事件更新保存的坐标，定时器触发时使用最新值。若拖拽结束时立即提交，还要清掉待执行任务，防止稍后重复处理，或用较旧坐标覆盖已经确认的位置。

3. 测试时可以让最后一次移动恰好发生在节流窗口内，随后立刻松手，检查最终坐标是否一致。视觉更新也可以考虑按动画帧安排，但持久化请求是否需要节流仍要单独决定，不能把绘制频率和网络提交频率混为一谈。
