# 容器查询会带来什么坑？

## 核心回答

1. 最容易踩的是：组件到底在查谁，没说清楚。没建合适的尺寸查询容器，规则可能根本打不中。套了好几层容器，不带名字的查询也可能选到比预期更近的祖先，表现为页面宽度没变，卡片突然换了布局。

2. 第二个问题是尺寸包含改了固有尺寸怎么算。`inline-size` 查行内方向，一般比直接用 `size` 稳。`size` 两个方向都管，容器原来靠内容撑高，高度来源又没安排好，高度就可能对不上预期。

3. 尺寸查询容器会加上相应的尺寸包含，并建立独立格式化上下文，但绝对定位的包含块不会因此自动换掉。卡片角标要相对容器定位，容器上显式 `position: relative`，还要看中间祖先有没有另当参照。普通样式继承也不会被切断。

4. 测的时候改组件实际容器宽度：收侧栏、改网格列、把卡片丢进弹窗，别只拖浏览器窗口。基础样式在没有增强规则时也要能用。出问题就按容器名称、算出来的尺寸、命中了哪条规则往下查，别随手再加一套断点。

## 追问：嵌套容器时怎样确定规则查询的是哪一层？

1. 承担不同职责的容器给明确的 `container-name`，比如页面主体和卡片外壳用不同名字。查询时指定要的那个名字，组件复用时中间多套一层，参照也不容易悄悄换掉。

2. 开发者工具里点被影响的子元素，看祖先的 `container-type`、名称和实际宽度。光看样式表里的阈值不够，还得确认这个尺寸对应的是侧栏、整行还是卡片本身，当前这条为什么生效就清楚了。

3. 调试时可以暂时给不同外壳加轮廓，单独改一层宽度做对照。看清楚以后把临时样式删掉，留下必要的命名。名字也别随便重复，写了名字仍可能匹配到更近的同名容器。

## 追问：为什么加了 container-type: size 后内容像塌了一样？

1. `size` 包含让容器在两个尺寸方向上，不再像普通盒子那样靠内部内容撑出固有尺寸。原来整块区域完全靠子元素撑高，加上这个约束又没有别的高度来源，结果就可能很意外。

2. 只是根据宽度改卡片布局，先改用 `inline-size`，块方向还可以随内容长。真要查高度再用 `size`，并且靠外层布局、明确高度或其他尺寸约束，给容器一块稳定空间。

3. 修好以后测空内容、长内容、窗口变窄，确认高度不是只对当前这个样例合适。直接补一个刚好能放下当前内容的固定高度，问题会被盖住，翻译变长或错误提示出现以后还是会溢出来。
