# 容器查询会带来什么坑？

## 核心回答

1. 容器查询最容易踩的坑是没有明确组件到底在查询谁。没有建立合适的尺寸查询容器时，规则可能根本不命中；嵌套多个容器后，不带名字的查询也可能选择比预期更近的祖先，表现为页面宽度没变但卡片突然切换布局。

2. 第二个问题是尺寸包含改变了固有尺寸计算。`inline-size` 适合查询行内方向，通常比直接使用 size 更稳妥；size 会涉及两个方向，如果容器原本靠内容撑高，又没有安排好高度来源，就可能出现高度不符合预期的情况。

3. 我还会检查尺寸计算和格式化边界，尺寸查询容器会施加相应的尺寸包含，并建立独立格式化上下文，但不能据此认定绝对定位包含块也改变了。如果卡片角标需要相对容器定位，我会在容器上显式设置 `position: relative`，并检查中间祖先是否另有定位参照；普通样式继承也不会因此被切断。

4. 测试时要改变组件实际容器宽度，例如收起侧栏、调整网格列或把卡片放进弹窗，而不只是拖浏览器窗口。基础样式应能在没有增强规则时正常使用；遇到异常就从容器名称、计算尺寸和命中规则依次排查，避免随手增加另一套断点。

## 追问：嵌套容器时怎样确定规则查询的是哪一层？

1. 我会给承担不同职责的容器设置明确的 container-name，例如页面主体和卡片外壳使用不同名称。查询时指定需要的名字，可以减少组件复用后因为新增中间容器而悄悄改变参照的情况。

2. 然后在开发者工具里选中被影响的子元素，查看祖先的 container-type、名称和实际宽度。只看样式表里的阈值不够，还要确认这个尺寸对应的是侧栏、整行还是卡片本身，才能解释为什么当前规则生效。

3. 调试时可以暂时把不同外壳加上轮廓，并单独改变一层宽度做对照。验证清楚后删除临时样式，保留必要命名；名称也不应随意重复，否则虽然写了名字，仍可能匹配到更近的同名容器。

## 追问：为什么加了 container-type: size 后内容像塌了一样？

1. size 包含使容器在两个尺寸方向的计算中不再像普通盒子那样依赖内部内容的固有尺寸。如果原来整个区域完全靠子元素撑高，加入这个约束后又没有其他高度来源，就可能得到意外结果。

2. 如果只是根据宽度改变卡片布局，我会先改用 inline-size，让块方向仍可以随内容增长。只有确实需要查询高度时，才考虑 size，并通过外层布局、明确高度或其他尺寸约束给容器稳定的空间。

3. 修复后要测试空内容、长内容和窗口变窄的情况，确认高度不是只对当前示例合适。直接补一个当前内容刚好能放下的固定高度可能隐藏问题，翻译变长或错误提示出现后仍会溢出。
