# 错误边界能捕获事件处理器里的异常吗？

## 核心回答

1. 普通事件处理器里抛出来的异常，错误边界不会自动抓住。边界主要处理后代组件在渲染、以及相关生命周期里的错误。按钮回调是用户事件里跑的。按钮在边界里面，不等于它的同步、异步错误都有人接。

2. 比如点保存，`await` 接口失败了，应在这条异步流程里抓住，设置表单错误，按钮恢复可点。用户要知道没存上，已经填的内容还在。这种预期中的业务失败，一般别当成整页崩溃。

3. 定时器、普通 Promise 回调里的异常，也不能笼统丢给边界。真要把某次失败交给边界，需要通过状态让后续渲染抛出来，或用边界库提供的明确接口。后台随手 `throw`，不会沿着组件树冒泡。

4. 错误边界仍然有用：某一块渲染出错，别把整个应用带倒。比如详情组件碰到没法处理的数据结构。边界自己出错，要更外层来接。服务端渲染的错误，通常还有框架或服务端自己的处理。

5. 业务错误和界面没法再画下去的错误分开设计。前者给字段提示、重试、修正入口；后者这块换成替代界面，记下必要信息。较新的 React 对部分 Transition 错误有额外支持。上面讲的是普通事件场景，不是「所有异步都抓不到」。

## 追问：try/catch 包住异步函数调用，为什么仍然漏了错误？

1. 调用了一个返回 Promise 的函数却没有 `await`，`try/catch` 只能抓住当前同步跑的时候抛出来的。后面 Promise 拒绝发生在另一个时刻。要 `await`，或者给返回的 Promise 配 `catch`。

2. 加载状态、成功、错误放进同一条清楚的异步流程，`finally` 里恢复这次请求对应的状态。并发时还要问这次请求还算不算数。异常抓住了，旧失败仍可能盖住用户后来一次成功。

3. 再看内部有没有启动了却没返回的异步任务。外层 `await` 一个函数，不等于等它偷偷建的所有 Promise。辅助函数把实际任务返回去，调用方才知道何时完成、错误反馈由谁承担。

## 追问：怎样判断一个错误应显示字段提示还是触发整块错误页？

1. 用户名冲突、必填没填，改输入就能过的，留在字段旁提示，已填内容留着。权限不够是这次操作的问题，说清楚当前做不了，按情况给重新登录、返回、申请权限。别让用户去改无关字段。

2. 组件没法安全继续画，比如关键数据结构完全不对、也降级不了，交给区域错误边界。边界范围尽量对应一块独立功能，侧栏和其他正常部分还能用。一张卡片出错，别把整站清掉。

3. 两类错误都要有恢复路径，该记的记，敏感输入别直接上传到日志。测试里分别模拟接口业务失败和渲染抛错，看它们进各自那套反馈。边界在不在只是其中一项。
