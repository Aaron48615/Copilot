# 错误边界能捕获事件处理器里的异常吗？

## 核心回答

1. 普通事件处理器中抛出的异常，错误边界不会自动捕获。边界主要处理后代组件在渲染和相关生命周期过程中的错误，而按钮回调是在用户事件中执行，不能只因为按钮位于边界里面，就认为它的全部异步和同步错误都有人处理。

2. 例如点击保存时 await 接口调用失败，应在事件对应的异步流程中捕获，设置表单错误并恢复按钮状态。用户需要知道保存未成功，同时保留已经填写的内容；把这类预期业务失败直接当成整页崩溃通常不合适。

3. 定时器和普通 Promise 回调中的异常也不能笼统依赖边界。若确实要把某个失败交给边界，需要通过状态使后续渲染抛出，或使用边界库提供的明确接口，不能以为任意后台 throw 都能沿组件树冒泡。

4. 错误边界仍然有必要，用于阻止一个区域的渲染异常影响整个应用，比如某详情组件遇到无法处理的数据结构。边界自己的错误需要由更外层处理，通常的服务端渲染错误也有框架或服务端对应的处理方式。

5. 我会分别设计业务错误和不可恢复的界面错误：前者给字段提示、重试或修正入口，后者展示区域替代界面并记录必要信息。最新 React 的部分 Transition 错误有特殊支持，回答时限定普通事件场景，避免用一句“所有异步都抓不到”概括全部 API。

## 追问：try/catch 包住异步函数调用，为什么仍然漏了错误？

1. 如果只是调用返回 Promise 的函数却没有 await，try/catch 只能捕获当前同步执行中抛出的异常，后续 Promise 拒绝发生在另一个时刻。需要 await 它，或为返回的 Promise 提供 catch，才能处理这次异步失败。

2. 我会把加载状态、成功处理和错误处理放进同一个清楚的异步流程，finally 恢复对应请求状态。并发情况下还要判断本次请求是否仍有效，否则虽然异常被捕获，旧失败仍可能覆盖用户后来一次成功操作。

3. 也要检查内部是否启动了没有返回的异步任务。外层 await 一个函数，不等于等待它偷偷创建的所有 Promise；辅助函数应该返回实际任务，方便调用方知道何时完成以及哪里需要承担错误反馈。

## 追问：怎样判断一个错误应显示字段提示还是触发整块错误页？

1. 用户名冲突、必填缺失等可以通过修改输入解决的问题，通常留在字段旁提示，并保留已填写内容。权限不足则应作为操作级提示，说明当前无法执行，并按实际情况提供重新登录、返回或申请权限的入口，不应要求用户反复修改无关字段。

2. 组件无法安全继续渲染的异常，例如关键数据结构不符合预期且无法降级，可以交给区域错误边界。边界范围尽量对应独立功能，让侧栏和其他正常部分仍可使用，而不是一个卡片错误就清空整站。

3. 我会让两类错误都具有合理的恢复路径和必要记录，但避免把敏感输入直接上传到日志。测试分别模拟接口业务失败和渲染抛错，确认它们进入各自设计的反馈，而不是只验证边界存在。
