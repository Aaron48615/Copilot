# 两个兄弟元素各自创建 BFC，margin 就不会合并吗？

## 核心回答

1. 不一定，这是 BFC 很容易被过度概括的地方。两个正常流中的块级兄弟即使各自使用 flow-root，它们自身仍参与外部的块布局，相邻的上下外边距在满足条件时仍然可能折叠；内部有独立格式化上下文不代表外部间距规则全部改变。

2. 例如上一个盒子的 margin-bottom 是 20px，下一个盒子的 margin-top 是 30px，如果发生正外边距折叠，实际间距通常是 30px，而不是 50px。只给两个盒子都加 BFC，不能保证得到相加后的结果，要看发生折叠的是哪两个边界。

3. BFC 常说的“阻止合并”，重点是它的内部内容与外部之间的折叠边界。比如把有 margin 的子元素放入独立 BFC 包裹层，可以避免该子元素的 margin 穿出包裹层；但包裹层自己与其他兄弟的 margin 仍要按外层布局判断。

4. 如果只是想稳定安排一组卡片的间距，我会让父级使用 Flex 或 Grid，再用 gap 表达关系，通常比层层加容器更清楚。必须保留普通块布局时，就明确由一侧负责 margin，或用 padding 表达内部留白，不依赖模糊的“创建 BFC 就好了”。

5. 验证这种题时，我会给两个盒子分别画边框，用实际位置差确认间距。只看样式面板里各自都显示了外边距数值，无法判断它们是否已经折叠，因为属性计算值可以保留，最终排版距离却不是简单相加。

## 追问：外边距里有负值时，折叠结果怎么计算？

1. 参与折叠的外边距如果既有正值也有负值，结果可以按最大正值加最小负值理解。例如 30px 与负 10px 折叠，得到 20px；不是总取较大的那个数，正外边距的简单口诀在这里不够用。

2. 如果参与的都是负值，通常取绝对值最大的负值，例如负 10px 与负 20px 得到负 20px。多个外边距可能一起折叠，所以排查时需要看祖先、相邻兄弟和空块，不能只盯着眼前两个数字。

3. 我会用一个最小例子确认当前结构是否发生折叠，再计算结果。负外边距可能用于有意的重叠，但不适合随意修正普通列表间距；用它补偿错误假设，后续改动一个盒子就容易让其他位置跟着错。

## 追问：改成 Flex 后原来的 margin 表现为什么变了？

1. Flex 子项之间的外边距不会像普通块布局那样折叠，因此原来上下各 20px、视觉只有 20px 的间隔，可能变成 40px。这个变化来自布局模型改变，不是浏览器突然把同一条 CSS 算错了。

2. 迁移时我会先清理子项重复承担的间距，再考虑由父容器统一设置 gap。比如纵向列表使用 column 和 gap，首尾不会自动多出同样的外侧留白，容器需要的边缘空间再用 padding 单独表达。

3. 同时检查原来的 margin: auto 是否承担对齐功能，因为 Flex 中自动外边距会吸收剩余空间。不能把全部 margin 批量删除；要区分它用于项目间隔、容器留白还是推开某个操作按钮，再逐项调整，并确认首尾留白符合设计。
