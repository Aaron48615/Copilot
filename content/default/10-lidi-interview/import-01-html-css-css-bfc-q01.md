# 两个兄弟元素各自创建 BFC，margin 就不会合并吗？

## 核心回答

1. 不一定，这是 BFC 很容易被说满的地方。两个正常流里的块级兄弟，就算各自 `flow-root`，它们自己仍参与外面的块布局。相邻的上下外边距满足条件时照样可能折叠。内部有独立格式化上下文，不等于外部间距规则全改了。

2. 比如上一个盒子 `margin-bottom` 是 20px，下一个 `margin-top` 是 30px，正外边距折叠时实际间距通常是 30px，不是 50px。两个盒子都加 BFC，不保证得到相加后的结果，得看折叠的是哪两条边。

3. 常说 BFC「阻止合并」，重点是它内部内容和外部之间那条折叠边界。有 margin 的子元素放进独立 BFC 包裹层，可以避免这个子元素的 margin 穿出包裹层。包裹层自己跟其他兄弟的 margin，还是按外层布局判断。

4. 只是想稳定一组卡片的间距，父级用 Flex 或 Grid，再用 `gap` 说关系，通常比一层层加容器清楚。必须留普通块布局，就明确由一侧负责 margin，或者用 padding 做内部留白，别靠一句「创建 BFC 就好了」。

5. 验证时给两个盒子分别画边框，用实际位置差确认间距。样式面板里各自都显示了外边距数值，判断不了有没有折叠：属性计算值可以还在，最终排版距离却不是简单相加。

## 追问：外边距里有负值时，折叠结果怎么计算？

1. 参与折叠的外边距既有正又有负，结果可以按最大正值加最小负值来理解。比如 30px 和负 10px 折叠，得到 20px。不是总取较大的那个数，正外边距那套口诀在这里不够用。

2. 参与的都是负值，通常取绝对值最大的那个负值，比如负 10px 和负 20px 得到负 20px。多个外边距可能一起折叠，排查时看祖先、相邻兄弟和空块，别只盯眼前两个数字。

3. 用一个最小例子确认当前结构有没有发生折叠，再计算结果。负外边距可以用来有意重叠，不适合拿来随便修普通列表间距。用它去补错误假设，后面改一个盒子，别的位置容易跟着错。

## 追问：改成 Flex 后原来的 margin 表现为什么变了？

1. Flex 子项之间的外边距不会像普通块布局那样折叠。原来上下各 20px、视觉只有 20px 的间隔，可能变成 40px。这是布局模型变了，不是浏览器把同一条 CSS 算错了。

2. 迁过去先清掉子项重复承担的间距，再考虑由父容器统一设 `gap`。纵向列表用 `column` 加 `gap`，首尾不会自动多出同样的外侧留白，容器边缘空间用 padding 单独说。

3. 同时看原来的 `margin: auto` 是不是在做对齐，因为 Flex 里自动外边距会吃剩余空间。别把全部 margin 一键删掉。分清它是项目间隔、容器留白，还是把某个操作按钮推开，再逐项调，首尾留白还要符合设计。
