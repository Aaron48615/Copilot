# 变量环境和词法环境需要背到什么程度？

## 核心回答

1. 先掌握这些概念能解释什么，再记必要的规范名词，别把内部字段当成内存布局图。执行上下文描述代码当前跑到哪、状态是什么；环境记录保存声明产生的名字和值。两者用来解释语言行为。

2. 从当前环境能访问哪些名字、找不到时往哪继续找，靠的是这套查找关系。变量环境跟某些变量声明的处理有关，它们不一定对应两块独立的物理内存，有时还会连着同一份环境记录。

3. 块级声明要能讲清：名字已经占了位置，但还没初始化，所以声明前访问会报错。就算外层有同名变量，内层绑定也已经挡住它，不会因为当前变量没准备好，就自动退回外层取值。

4. `var` 变量和普通函数声明，要分开看声明处理和后面的赋值执行。前者常在执行到赋值前读到 `undefined`；后者在常见函数体场景可以提前调用。函数表达式则要看它被赋给哪一种变量。

5. 更深入时，用一个小例子逐步讲：进入函数、进入代码块、读取标识符。碰到全局脚本、模块、非严格模式块内函数，先明确运行环境再查规则，一个简化口诀盖不住所有情况。

## 追问：为什么 typeof 一个未声明变量不报错，访问暂时性死区却报错？

1. 真正没有可解析绑定的名字，`typeof` 有特殊处理，可以得到表示未定义的字符串。这个规则允许检查某个全局名字在不在，但不代表所有还没得到值的变量都能被安全查询。

2. 暂时性死区里的名字已经能解析到当前作用域的绑定，只是还没初始化。`typeof` 也要读这个绑定，因此仍会抛错。关键差别是：没有这个名字，和有这个名字但还不能读。

3. 代码块末尾声明一个块级变量，块开头对同名变量做类型查询，就属于后一种。把声明移出去，或换个变量名对照，先确定是不是被内层声明挡住了，再判断是不是全局名字根本没有。

## 追问：变量提升是不是引擎把源码移动到了函数开头？

1. 不是真去改写源码。更准确的说法是：某些声明在执行语句之前就已经处理完了。提升是观察到的效果，拿它解释能不能访问很方便，但不能据此认为赋值语句也会提前执行。

2. 函数作用域变量通常先建好绑定并初始化成 `undefined`，执行到赋值处才改内容。块级声明也会提前占位置，但初始化时机不同，声明前访问的结果不能用同一套规则概括。

3. 函数声明和函数表达式也要拆开看。表达式必须执行后才能产生相应的赋值结果。分别预测声明前读取和调用会怎样，再讲原因。碰到特殊块内声明，先限定严格模式和代码类型。
