# 变量环境和词法环境需要背到什么程度？

## 核心回答

1. 我会先掌握这些概念能解释什么，再记必要的规范名词，而不是把内部字段当成内存布局图。执行上下文描述代码当前的执行状态，环境记录负责保存声明产生的绑定，二者用于解释语言行为。

2. 词法环境相关关系帮助说明当前能访问哪些名字，以及找不到时到哪里继续查找。变量环境则与某些变量声明的处理有关，它们并不必然对应两块独立的物理内存，有时还会关联同一环境记录。

3. 对块级声明，我需要能解释绑定已经建立但尚未初始化的阶段，因此声明前访问会报错。即使外层存在同名变量，内层绑定也已经遮蔽了它，不会因为当前变量没准备好就自动退回外层找值。

4. 对 var 变量和普通函数声明，我会区分声明处理与后续赋值执行。前者常在执行到赋值前读到未定义值，后者在常见函数体场景可提前调用；函数表达式则要看它被赋给哪一种变量。

5. 更深入时，我会用一个小例子逐步说明进入函数、进入代码块和读取标识符的过程。涉及全局脚本、模块或非严格模式块内函数时，需要明确运行环境再查规则，避免拿一个简化口诀覆盖所有情况。

## 追问：为什么 typeof 一个未声明变量不报错，访问暂时性死区却报错？

1. 对真正没有可解析绑定的名字，typeof 有特殊处理，可以得到表示未定义的字符串。这个规则允许代码检查某个全局名字是否存在，但不代表所有尚未得到值的变量都能被安全查询。

2. 暂时性死区里的名字已经能解析到当前作用域的绑定，只是该绑定还没有初始化。typeof 也需要读取这个绑定，因此仍会抛错，关键差别在于没有绑定和有绑定但不可读取。

3. 比如在代码块末尾声明一个块级变量，块开头对同名变量做类型查询，就属于后一种情形。我会把声明移出或更换变量名做对照，先确定是否被内层声明遮蔽，再判断是不是全局名字缺失。

## 追问：变量提升是不是引擎把源码移动到了函数开头？

1. 不是实际改写源码，更准确的说法是某些声明在执行语句之前就已经完成相应处理。提升是观察到的效果，用这个说法解释可访问性很方便，但不能据此认为赋值语句也会提前执行。

2. 函数作用域变量通常先建立绑定并初始化为未定义值，执行到赋值处才改变内容。块级声明也会提前建立绑定，但初始化时机不同，所以两者声明前访问的结果不能用同一个规则概括。

3. 函数声明和函数表达式也要拆开看，表达式必须执行后才能产生相应的赋值结果。面试时我会分别预测声明前读取和调用的结果，再说明原因；遇到特殊块内声明，则先限定严格模式和代码类型。
