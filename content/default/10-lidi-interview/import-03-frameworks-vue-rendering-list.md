# Vue 大列表和 v-for 渲染慢时怎么排查？

## 核心回答

1. 先复现慢在哪：第一次打开、输入筛选、滚动，还是改一行。再用网络和性能工具，把数据等待、计算、DOM 成本分开。列表出得慢，可能只是接口在等，不一定是 `v-for` 的问题，也别直接套某个缓存指令。

2. 模板里别对每一行反复跑很重的函数，比如复杂格式化、多次查找。数据提前整理，派生列表用 `computed`，依赖范围要合理。深度 `watch` 整个大数组再排序或复制，改一点点就会带出大量额外工作。

3. 行组件用稳定业务 `key`，传入尽量明确的 props。是不是选中，可以在父级按行算成布尔值，别让每一行都接收整份会变的集合。也要看实际更新关系，为了引用稳定，把该变的行显示成旧状态，也不对。

4. 数据和节点都太多，可以分页、按需取，或虚拟化，只显示人现在要看的那一段。虚拟列表要处理动态行高、草稿、焦点；图片也要有尺寸和加载策略。节点少了，服务器一次返回的体积不一定少，两层分开设计。

5. 用 `v-memo` 这类优化，依赖得写全，还得真有收益，别当默认装饰。改完用同样数据量测筛选、排序、滚动、单行编辑，比耗时。缓存导致内容不更新也要查。身份、数据、交互还得是对的。

## 追问：computed 已经缓存了列表，为什么滚动还会卡？

1. `computed` 缓存的是派生计算，依赖没变就不用重算数组。已经渲染出去的大量节点，布局、绘制、滚动照样要参加。图片、阴影、复杂行布局也会有浏览器成本。计算缓存包不住所有显示阶段。

2. 打开性能面板看布局和绘制，节点是不是太多、是不是在频繁量尺寸、行里是不是塞了很重的第三方控件。节点体量是主因，分页或虚拟列表更对路；行内效果太花，就减样式、少重复实例。

3. 滚动监听里有没有同步跑很重的代码，比如每次滚动都遍历全部记录。优化后再用真实滚动复测。`computed` 回调次数少了，人不一定觉得顺，人感受的是整段交互。

## 追问：v-memo 依赖漏写会有什么具体后果？

1. `v-memo` 按给定依赖决定这块子树能不能复用。漏掉会影响显示的数据，数据已经变了它还可能跳过更新。只记了选中状态，没包含会变的价格，商品降价了那一行还显示旧价。

2. 子树到底依赖哪些数据，先列清楚，再看手动记忆化值不值得维护。普通列表稳定 `key`、props 传合理，往往已经够用。确认大列表某一块重复更新确实很贵，再考虑往下管。

3. 每个会影响界面的字段都单独改一遍测，别只测依赖数组里已经写出来的那些。缓存对不对，比少更新几次更要紧。价格、禁用、操作对象过时，都会误导人。“不再更新”不能直接当性能成功。
