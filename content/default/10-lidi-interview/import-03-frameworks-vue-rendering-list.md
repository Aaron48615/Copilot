# Vue 大列表和 v-for 渲染慢时怎么排查？

## 核心回答

1. 我会先复现哪种列表操作慢，是首次打开、输入筛选、滚动还是修改单行，再用网络和性能工具区分数据获取、计算与 DOM 成本。一个列表出现得慢，可能只是接口等待，不一定是 v-for 本身有问题，也不能直接套用某个缓存指令。

2. 模板里避免对每一行反复执行昂贵函数，例如复杂格式转换或多次查找。可以提前整理数据，派生列表使用 computed，并确认依赖范围合理；深度 watch 整个大数组再排序或复制，会让很小的改动引发大量额外工作。

3. 行组件使用稳定业务 key，传入尽量明确的 props。比如是否选中可以在父级按行算成布尔值，避免每一行都接收整个变化集合；但要根据实际更新关系判断，不应为了稳定引用而使需要变化的行显示旧状态。

4. 数据和节点数量过多时，可以分页、按需获取或虚拟化，只显示用户当前需要的范围。虚拟列表要处理动态行高、草稿和焦点，图片也应有合理尺寸与加载策略；减少节点不等于减少服务器返回体积，这两个层面要分别设计。

5. 如果使用 v-memo 等优化，应确认其依赖完整且真正有收益，不能当成默认装饰。改完后在相同数据量下验证筛选、排序、滚动和单行编辑，比较实际耗时，并检查缓存是否导致内容不更新，优化应同时保持身份、数据和交互正确。

## 追问：computed 已经缓存了列表，为什么滚动还会卡？

1. computed 主要缓存派生计算，依赖没变时避免重复算数组，但已经渲染的大量节点仍会参与布局、绘制和滚动。图片、阴影和复杂行布局也可能产生浏览器成本，所以计算缓存不能解决所有显示阶段的问题。

2. 我会在浏览器性能面板查看布局与绘制，确认是否存在过多节点、频繁测量尺寸或重型第三方控件。若节点体量是主因，分页或虚拟列表更合适；若是行内效果太复杂，可以减少不必要的样式和重复实例。

3. 还要验证是否有滚动监听同步执行昂贵代码，例如每次滚动都遍历全部记录。优化后用实际滚动操作复测，而不是只看 computed 回调执行次数减少，因为用户感受到的是整段交互而非某一个函数。

## 追问：v-memo 依赖漏写会有什么具体后果？

1. v-memo 根据给定依赖判断是否可以复用子树，漏掉影响显示的数据，可能让它在数据已改变时仍跳过更新。例如只记录选中状态，却没包含会变化的价格，商品降价后该行可能继续显示旧值。

2. 我会先明确子树到底依赖哪些数据，再判断手动记忆化是否值得维护。普通列表使用稳定 key 和合理 props 往往已经够用，只有确认大列表某部分重复更新成本明显时，才考虑进一步手动控制。

3. 测试要分别修改每个会影响界面的字段，而不是只测依赖数组里已经写出的字段。缓存正确性比少几次更新更重要，价格、禁用状态或操作对象过时都可能误导用户，不能把“不再更新”直接当性能成功。
