# Axios 请求模块和 Token 鉴权是怎么封装的？

## 核心回答

1. 我会把重复的请求配置放进一个 Axios 实例，例如接口前缀、超时和通用错误处理。页面仍然通过具体的业务函数调用接口，这样列表组件只需要关心查询参数和结果，不需要知道 Token 从哪里读取。

2. 请求拦截器在发送前读取当前 Token，存在时按约定添加 Authorization。不能创建实例时就永久保存一份旧 Token，也不能给任意第三方地址都带上它；下载文件等请求还需要保留不同的响应类型。

3. 响应拦截器区分 HTTP 状态、业务错误和网络失败。登录失效时清除会话，保存原访问地址并跳转登录页；并发请求同时失败时用标记避免重复跳转，登录成功后用 replace 回到原页面。

4. 封装时我会让失败继续以 rejected Promise 传给调用方，页面才能结束 loading 或显示重试。前端守卫只能提前提示，后端还要检查身份和资源权限；如果继续完善刷新 Token，我会先与后端明确刷新接口和失败规则。

5. 例如表单提交遇到字段校验失败，我会把字段错误交给表单，而不是统一跳转或只弹一个网络错误。取消请求也应单独识别，用户主动离开页面时无需报故障；统一封装的目标是提供一致规则，同时保留业务需要的处理空间。

## 追问：多个请求同时遇到 401，如何只刷新一次 Token？

1. 我会共享一个正在执行的刷新 Promise。第一个请求开始刷新，其他请求等待它的结果，成功后再使用新 Token 重发，而不是每个请求各调用一次刷新接口，避免竞争和重复轮换。

2. 刷新接口要使用独立实例或明确跳过刷新逻辑，原请求也要记录已经重试过。否则刷新接口自己返回 401，或者权限配置一直错误，就可能不断进入响应拦截器，形成无限请求。

3. 刷新失败后统一结束会话，并让等待中的请求全部失败。重放写操作前还要确认服务端的幂等约定；仅凭客户端没有收到成功响应，不能断定订单等操作从未执行。

## 追问：登录后返回原页面，要注意哪些细节？

1. 保存地址时应包含业务需要的路径和查询参数，例如列表页的筛选条件。登录成功后使用 replace 可以替换登录页历史，避免用户按返回键又回到已完成的登录流程。

2. redirect 参数不能直接接受任意外部网址。我会解析并限制到本站允许的路径，同时排除登录页自身，防止开放重定向或反复跳转，非法值就返回一个确定的默认页面。

3. 返回地址不等于获得权限，恢复页面后仍可能遇到 403 或资源已删除。页面要分别给出无权访问、内容不存在等提示，并清理旧账号的缓存，避免切换账号后显示上一位用户的数据。
