# Axios 请求模块和 Token 鉴权是怎么封装的？

## 核心回答

1. 重复的请求配置会放进一个 Axios 实例，比如接口前缀、超时、通用错误处理。页面还是通过具体的业务函数调接口，列表组件只管查询参数和结果，不用自己知道 Token 从哪读。

2. 请求拦截器在发出去之前读当前 Token，有的话按约定加上 Authorization。创建实例时不能把当时那份 Token 永久写死，第三方地址也不能随便带上。下载文件这类请求，响应类型还得单独留着，别跟 JSON 接口混成一套。

3. 响应拦截器要分开看 HTTP 状态、业务错误和网络失败。登录失效就清会话，把原来要去的地址存下来，再跳登录页。好几个请求同时失败时，用一个标记挡住，别连着跳好几次。登录成功后用 replace 回到原来那页。

4. 失败还是以 rejected Promise 交给调用方，页面才能收掉 loading 或者给出重试。前端路由守卫只能提前拦一下，身份和资源权限还得后端查。要做刷新 Token，得先跟后端说清楚刷新接口怎么调、失败怎么算。

5. 表单提交如果是字段校验失败，把字段错误交回表单，别一律跳走或者只弹一个网络错误。取消请求也要单独认出来，用户自己离开页面不算故障。统一封装是给一套一致的规则，具体业务该自己处理的还是留给页面。

## 追问：多个请求同时遇到 401，如何只刷新一次 Token？

1. 刷新用一份大家共用的 Promise。第一个请求开始刷新，后面的等它的结果，成功了再用新 Token 重发。别每个请求各自调一遍刷新接口，否则会抢、也会把 Token 轮换乱掉。

2. 刷新接口要用独立实例，或者明确跳过刷新逻辑。原来那个请求也要记下已经重试过。不然刷新接口自己回 401，或者权限一直配错，就会在响应拦截器里转圈，请求停不下来。

3. 刷新失败就统一结束会话，等着的请求全部失败。重放写操作之前，还得确认服务端的幂等约定。客户端没收到成功响应，不能当成订单这类操作一定没执行过。

## 追问：登录后返回原页面，要注意哪些细节？

1. 存地址时要把路径和查询参数一起留下，比如列表页当时的筛选条件。登录成功用 replace 换掉登录页这条历史，用户按返回键才不会又回到已经登完的登录流程。

2. redirect 参数不能直接吃任意外部网址。解析之后只允许本站路径，登录页自己也要排除掉，不然会开放重定向或者来回跳。非法值就落到一个确定的默认页。

3. 能回到那个地址，不等于就有权限。页面恢复之后仍可能 403，或者资源已经删了。无权访问、内容不存在要分开提示。还得清掉旧账号的缓存，免得切账号以后还显示上一个人的数据。
