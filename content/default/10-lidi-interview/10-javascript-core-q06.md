# 事件循环、宏任务和微任务是什么？

## 核心回答

1. 就浏览器主线程来说，JS 一次只能干一件事。一段同步代码在跑的时候，就算定时器到点了也插不进来，得等这段跑完。浏览器可以在别的机制里等网络、等计时，回调再由事件循环安排执行。

2. 面试里说的宏任务，通常对应规范里的任务，比如定时器回调、用户点击。微任务包括 `Promise.then` 和 `queueMicrotask`。它们不是同一个队列，浏览器还可能有多个任务队列，别把所有来源排成一个绝对顺序。

3. 清微任务的时候，已经排上的会一直清，过程中新塞进来的也会接着跑。常见同步脚本例子里：先跑同步输出，再跑已经入队的 Promise 回调，之后才轮到定时器。

4. `setTimeout(fn, 0)` 是说具备条件之后等执行，不保证零毫秒立刻跑。`new Promise` 括号里的函数本身是同步的，`.then` 才进微任务。`await` 后面那截也会异步安排，别把整个 `async` 函数都当成一开始就是异步。

5. 页面不是每跑完一个任务就画一帧，浏览器自己找空隙画。微任务套微任务，输入和渲染可能一直排不上。Node 的阶段和队列划分不一样，别把浏览器这套直接套过去。

## 追问：同步日志、Promise 回调和零延时定时器怎么排顺序？

1. 同一段普通脚本里先输出 `A`，注册输出 `B` 的零延时定时器，再注册输出 `C` 的已兑现 Promise 回调，最后输出 `D`。同步阶段先得到 `A`、`D`，注册回调本身不会把对应日志打出来。

2. 脚本跑完后的微任务检查点会跑 Promise 回调，所以再输出 `C`，定时器之后才有机会输出 `B`。这个例子顺序是 `A`、`D`、`C`、`B`。前提是没有别的代码或其他机制掺进来。

3. `C` 的回调里又注册一个微任务 `E`，它也会在当前检查点接着跑，排在定时器前面。Promise 还没兑现，回调还没入队，就不能只凭代码写在前面就说一定早于定时器。还得看它何时完成、回调何时进队列。

## 追问：为什么 await Promise.resolve() 不能可靠地避免页面卡顿？

1. 这会把后面的代码推进微任务，当前函数可以先退出，但浏览器在检查点会继续把微任务清完。循环里每次只等一个已经完成的 Promise，仍可能一直占着执行机会，界面还是没空画。

2. 所以把大循环改成 `async` 函数，计算量没变少，页面照样可能卡。大量可拆的计算，按时间或数量分批，批次之间用定时器让一让。主线程实际承担的计算，不会因为加了 `async` 就消失。

3. 跟 DOM 无关的重计算，可以丢到 Worker，但来回传数据费不费得算。跟动画相关的更新可以跟 `requestAnimationFrame`。具体方案还得测长任务和交互，调度 API 本身不保证一次工作会变得够短。
