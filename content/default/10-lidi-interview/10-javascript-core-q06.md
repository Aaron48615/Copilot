# 事件循环、宏任务和微任务是什么？

## 核心回答

1. 我会先限定在浏览器主线程讨论：同一段 JavaScript 同步代码通常执行到结束，定时器和事件回调不能随时插进正在运行的函数。浏览器可以在其他机制中等待网络或计时，回调再由事件循环安排执行。

2. 面试里说的宏任务通常对应规范中的任务，例如定时器回调、用户交互等；微任务包括 Promise 的反应回调和 `queueMicrotask` 回调。它们不是同一个队列，而且浏览器可能有多个任务队列，不能把所有来源按一个绝对顺序排列。

3. 在执行微任务检查点时，浏览器会持续处理队列中的微任务，期间新加入的微任务也会继续处理。在常见的同步脚本例子里，先执行同步输出，再运行已经排入队列的 Promise 回调，之后才有机会运行定时器任务。

4. `setTimeout(fn, 0)` 表示达到调度条件后等待执行，不保证零毫秒立即调用。`new Promise` 的执行器会同步运行，`.then` 回调才通过微任务执行；`await` 后面的继续执行也会异步安排，不能把整个异步函数都当成异步开始。

5. 浏览器会在合适的渲染机会更新界面，但不是每个任务后都必定绘制一帧。如果不断追加微任务，可能让输入和渲染一直等待；Node.js 还有自己的阶段和队列，不能直接套用浏览器的简化顺序。

## 追问：同步日志、Promise 回调和零延时定时器怎么排顺序？

1. 假设在同一段普通脚本里先输出 `A`，注册输出 `B` 的零延时定时器，再注册输出 `C` 的已兑现 Promise 回调，最后输出 `D`。同步阶段先得到 `A、D`，注册回调本身并不执行对应日志。

2. 脚本执行结束后的微任务检查点会运行 Promise 回调，所以再输出 `C`，定时器之后才有机会输出 `B`。这个例子的顺序是 `A、D、C、B`，前提是没有额外代码或其他执行机制混入。

3. 如果 `C` 的回调里又注册一个微任务 `E`，它也会在当前检查点继续执行，排在定时器之前。若 Promise 尚未兑现，它的回调还没入队，就不能仅凭代码注册位置断言一定早于定时器，还要看它何时完成，以及回调实际何时进入队列。

## 追问：为什么 await Promise.resolve() 不能可靠地避免页面卡顿？

1. 这会把后续执行安排成微任务，可以让当前函数暂时退出，但浏览器在检查点会继续清空微任务。如果循环里每次都只等待一个已兑现 Promise，仍可能持续占用执行机会，界面得不到及时绘制。

2. 如果是大量可拆分的计算，我会按时间或数量分批，在批次间通过任务调度主动让出执行机会。不能仅把函数加上 `async` 就认为计算移到了后台，主线程实际承担的计算量并没有因此消失。

3. 对与 DOM 无关的重计算，可以考虑 Web Worker，并评估数据传递成本；与动画相关的更新可以结合 `requestAnimationFrame`。具体方案仍要测量长任务和交互表现，调度 API 本身不保证一次工作会变得足够短。
