# E2E 测试怎样写得接近真实用户？

## 核心回答

1. 从一个明确的用户目标开始。比如登录后搜索某件商品，再加入购物车，把输入、操作、最终结果串起来。每条测试有自己的起点和完成条件：目标商品和选定数量正确出现在购物车里。页面弹出成功提示，不够。

2. 操作尽量用界面上的角色、标签、可见名称。按搜索框标签输入，按按钮名称点。列表里先限定到目标商品再点加入，别依赖 CSS 层级或固定行号。稳定业务标识更合适的时候，也可以用 `data-testid`。

3. 等待围着具体行为发生。点完等到购物车数量变了，再查商品名称和数量。工具的自动等待能处理「能不能点」，不代表业务已经完成。还是用可重试的页面断言，别拿固定 sleep 当成功条件。

4. 测试数据能独立准备。这条流程需要明确存在、能买的商品，以及独立购物车。登录功能本身留界面测试，其他业务用例可以复用准备好的登录状态。会改服务端数据时，账号和记录也别互相影响。

5. 正常路径之外，选对用户有影响的异常：搜索为空、登录失效、提交后接口失败，并看恢复操作。失败时结合截图和 trace 看当时页面和请求。重要业务结果还要对后端证据。成功提示本身证明不了数据一定已经持久化。

## 追问：每条 E2E 都从登录页开始，才算真实吗？

1. 不需要。真不真实，看当前测试经过了哪些需要验证的边界。专门的登录用例该填表单、验身份状态。购物车用例可以从合法登录状态开始，大量重复登录只会更耗时，还多出无关失败点。

2. 复用登录状态时，凭据要有效、权限符合场景，每个浏览器上下文独立。浏览器 cookie 隔离，不等于服务端购物车隔离。多条测试共用账号、同时改购物车，照样会互相影响。按修改范围准备账号或数据。

3. 身份过期、权限不足另写针对性用例。多数场景跳过登录，不等于这些行为可以不测。报告里也说明：业务测试用了预置身份，验的是登录之后的操作；登录入口正不正常，由那条完整登录流程负责。

## 追问：一条完整流程里可以写多个断言吗？

1. 可以。一条测试对应一个清楚目标，不等于只能有一个断言。加入购物车后同时查商品、数量、金额，是在证明同一项操作的结果。只查一个成功提示，加错商品也可能漏掉。

2. 关键阶段放少量断言，确认前提成立再往下。先确认搜到了目标商品，再点加入。失败就能指到搜索、交互、结果里的具体阶段，不会所有问题最后都变成购物车数量不对。

3. 注册、改密码、下单、退款、退出全塞进同一条脚本不合适，前面失败会阻断后面所有检查。能独立准备前提的目标就拆成独立用例。留少量跨页面主流程验证连接关系，别依赖上一条用例留下的状态。
