# E2E 测试怎样写得接近真实用户？

## 核心回答

1. 我会从一个明确的用户目标开始，比如登录后搜索某件商品并加入购物车，把输入、操作和最终结果串起来。每条测试应有自己的起点和明确的完成条件，比如目标商品及选定数量正确出现在购物车中，而不只是页面上弹出成功提示。

2. 操作尽量使用界面的角色、标签和可见名称，比如按搜索框标签输入、按按钮名称点击。列表里先限定到目标商品再点加入，避免依赖 CSS 层级或固定行号；如果稳定业务标识更合适，也可以使用 data-testid。

3. 等待围绕具体行为发生，例如点击后等待购物车数量变化，再检查商品名称和数量。工具的自动等待能处理可点击条件，却不代表业务已经完成，所以我仍要使用可重试的页面断言，不用固定 sleep 代替成功条件。

4. 测试数据要能够独立准备，例如为本条流程创建明确存在且可购买的商品和独立购物车。登录功能本身保留界面测试，其他业务用例可以复用准备好的登录状态；会修改服务端数据时，账号和记录也要避免互相影响。

5. 除了正常路径，我会选有用户影响的异常，例如搜索为空、登录失效和提交后接口失败，并检查恢复操作。失败时结合截图和 trace 查看当时页面与请求；重要业务结果还需对应后端证据，成功提示本身不能证明数据一定已持久化。

## 追问：每条 E2E 都从登录页开始，才算真实吗？

1. 不需要，是否真实取决于当前测试经过了哪些需要验证的边界。专门的登录用例应该填写表单并验证身份状态，而购物车用例可以从合法登录状态开始，否则大量重复登录只会增加耗时和无关失败点。

2. 复用登录状态时，我会确认凭据有效、权限符合场景，并且每个浏览器上下文独立。浏览器的 cookie 隔离不等于服务端购物车隔离；多条测试共用账号并同时修改购物车，依然会互相影响，因此要按修改范围准备账号或数据。

3. 身份过期和权限不足应另外写针对性用例，不能因为多数场景跳过登录就漏掉这些行为。测试报告也要说明业务测试使用了预置身份，它验证的是登录后的操作，登录入口是否正常由那条完整登录流程负责证明。

## 追问：一条完整流程里可以写多个断言吗？

1. 可以，一条测试对应一个清晰目标，不等于只能有一个断言。比如加入购物车后同时检查商品、数量和金额，是在证明同一项操作的结果；如果只检查一个成功提示，实际加错商品也可能被漏掉。

2. 我会在关键阶段放少量断言，确认前提成立再继续，例如先确认搜到了目标商品，再点击加入。这样失败能指向搜索、交互或结果中的具体阶段，而不是所有问题最后都表现为购物车数量不对。

3. 不适合把注册、改密码、下单、退款和退出全部塞进同一条脚本，因为前面失败会阻断后面所有检查。能够独立准备前提的目标就拆成独立用例，保留少量跨页面主流程验证连接关系，避免依赖上一条用例留下的状态。
