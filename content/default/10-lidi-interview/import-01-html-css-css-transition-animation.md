# transition 和 animation 的区别？

## 核心回答

1. transition 适合属性从一个状态变成另一个状态时补上中间过程，例如按钮悬浮或面板展开。它需要出现可参与过渡的计算值变化，并设置属性、时长和曲线；只声明 transition 而状态完全没变，并不会自动开始播放。

2. animation 通常配合 @keyframes 描述多个阶段，可以设置次数、方向、延迟和暂停，不要求先发生 hover 这类状态切换。比如持续旋转的加载图标更适合关键帧，普通按钮颜色变化用 transition 就足够，不需要为了简单效果额外维护一套帧定义。

3. 我会根据动作含义选择，而不是认为 animation 天生更流畅。两者如果持续修改布局属性都可能增加开销，transform 和 opacity 通常更容易做成合成动画，但仍要看实际页面。关键帧的 fill-mode 只影响动画效果的保留方式，不会把业务状态自动保存下来。

4. 收尾也要设计。退场结束后隐藏或卸载组件，需要处理快速反向操作、取消和减少动态效果的情况。现代 CSS 对 display 等离散属性有了相关过渡能力，但不能把它当作连续数值插值，目标浏览器和初始显示状态仍需要专门验证。

5. 属性列表最好写清楚，例如只让颜色和变换过渡，而不是默认所有属性都参与。以后增加宽度或位置状态时，过于宽泛的规则可能意外播放布局变化，让一个本来简单的按钮交互变得迟缓且难以定位。

## 追问：为什么加了 transition 后第一次显示没有动画？

1. 浏览器需要能识别开始状态和结束状态。如果元素刚插入就已经带着最终样式，没有建立可用于过渡的前一个状态，就可能直接显示终点；从 display: none 进入显示也涉及特殊的起始样式条件。

2. 可以根据支持范围使用 starting-style 等能力描述进入时的起点，或者让组件先处于初始状态，再在合适时机切换。重点是建立明确的状态变化，不是随便增加一个很长的 setTimeout，依赖碰巧足够的延迟。

3. 排查时同时看属性是否可动画、时长是否被覆盖，以及用户是否启用了减少动态效果。若业务本来允许直接显示，降级应保证组件仍可操作；不能因为动画没播放就让面板一直透明或等待不会触发的结束事件。

## 追问：监听 animationend 或 transitionend 为什么还可能漏清理？

1. 动画可能在结束前被取消，元素被移除、样式被替换或用户快速重新打开都可能改变事件路径。多个属性参与过渡时，还可能有多个结束事件，因此简单收到任意一次事件就卸载也不一定正确。

2. 我会让组件有明确的打开、关闭中和已关闭状态，结束回调只在仍对应当前关闭动作时执行。必要时处理取消事件，并过滤目标元素和属性，避免子元素冒泡的事件提前触发父组件清理。

3. 减少动态效果或零时长场景应能直接完成状态转换，不依赖动画事件。验证时连续快速开关、卸载组件再返回，确认监听、定时器和透明遮罩都没有残留，这些状态边界比单次正常播放更容易暴露问题。
