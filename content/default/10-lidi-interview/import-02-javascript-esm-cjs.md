# ESM 和 CommonJS 有什么区别？

## 核心回答

1. ESM 使用 import 和 export，静态声明让工具在执行前就能建立模块依赖关系。CommonJS 通过函数加载模块，并用导出对象提供内容，require 可以放进条件分支，首次执行到那里才加载对应模块，重复加载通常使用缓存。

2. ESM 的命名导入关联到导出绑定，模块内部修改变量后，导入方再次读取会看到更新。导入方不能直接给这个绑定重新赋值，但如果它指向一个普通对象，仍可能修改对象内部的可写属性。

3. CommonJS 返回模块的导出值，对象也会按引用共享，并不是每次复制一份数据。需要特别区分修改同一个对象、替换整个导出，以及提前解构出原始值，这几种操作对调用方的影响不同。

4. ESM 更方便静态分析和删除未使用代码，但有副作用的模块仍可能保留。两种模块系统也都可能遇到循环依赖，只是提前访问时的表现不同，不能靠更换语法自动消除初始化顺序问题。

5. 混用时我会先确认运行时版本、文件扩展名和包的类型声明，再检查导出形状。现代 Node 可以用 require 加载满足条件的同步 ESM，但带有顶层等待的依赖图不能照此处理，不能沿用一概不支持的旧结论。

## 追问：为什么 CommonJS 解构出的数字不会跟着模块一起变化？

1. 解构是在那一刻读取对象属性，然后把读到的值赋给局部变量。数字属于原始值，后续模块把原对象的数字属性改掉，不会反过来修改调用方已经得到的局部变量，这是普通赋值语义。

2. 如果调用方一直保存导出对象，并在需要时读取它的属性，就能看到同一对象上的后续修改。但如果模块整体替换了导出对象，旧引用仍指向原对象，需要把这两类变化分别判断。

3. ESM 的命名导入则是对导出绑定的关联，不是上述一次性取值过程。面试里我会用一个递增计数的最小例子说明差异，同时补充：导入后再赋给自己的局部变量，也不会让局部变量自动同步。

## 追问：把老项目改成 ESM，只替换导入语法够不够？

1. 不够，首先要确定文件如何被运行环境识别。包的类型声明可能影响同目录下其他脚本，因此假如要迁移，我会先检查应用入口、构建配置和测试配置，避免某个配置文件仍按旧模式编写。

2. 还要核对路径解析、默认导出和原有 CommonJS 专属变量的使用。构建工具能接受某种导入，不代表直接交给 Node 执行也能接受，验证需要覆盖实际部署或运行方式，而不只看编辑器提示。

3. 我会选择一段边界清楚的依赖链试迁移，再验证启动、测试和生产产物。遇到仅支持旧格式的依赖，可以按运行时支持情况做互操作；迁移的理由应是具体维护收益，而不是觉得新语法天然更快。
