# ESM 和 CommonJS 有什么区别？

## 核心回答

1. ESM 用 `import` 和 `export`，静态声明让工具在执行前就能建起模块依赖。CommonJS 通过函数加载模块，用导出对象提供内容。`require` 可以放进条件分支，第一次执行到那里才加载对应模块，重复加载通常走缓存。

2. ESM 的命名导入连着导出那边的绑定，模块内部把变量改了，导入方再读能看到更新。导入方不能把这个名字改成指向别的值；如果它指向一个普通对象，对象里面可写的属性仍可能被改。

3. CommonJS 返回的是模块的导出值，对象按引用共享，不是每次复制一份。改同一个对象、把整个导出换成另一份、提前解构出原始值，这三种对调用方的影响不一样。

4. ESM 更方便静态分析和删掉没用到的代码，但有副作用的模块仍可能留下。两种模块系统都可能碰上循环依赖，提前访问时的表现不同。换语法不会自动把初始化顺序问题消掉。

5. 混用时先确认运行时版本、文件扩展名、包的类型声明，再看导出长什么样。现代 Node 可以用 `require` 加载满足条件的同步 ESM，但依赖图里有顶层 `await` 的不能这么处理。别沿用「一概不支持」的旧结论。

## 追问：为什么 CommonJS 解构出的数字不会跟着模块一起变化？

1. 解构是在那一刻读取对象属性，再把读到的值赋给局部变量。数字是原始值，后面模块把原对象的数字属性改掉，不会反过来改调用方已经拿到的局部变量。这就是普通赋值。

2. 调用方一直握着导出对象，需要时再读它的属性，就能看到同一对象上后来的修改。模块把整个导出对象换成另一份，旧引用仍指向原来那份。这两类变化要分开看。

3. ESM 的命名导入是对导出绑定的关联，不是上面那种一次性取值。可以用一个递增计数的最小例子把差异讲清楚。导入后再赋给自己的局部变量，那个局部变量也不会自动跟着变。

## 追问：把老项目改成 ESM，只替换导入语法够不够？

1. 不够。先确定文件怎么被运行环境认出来。包的类型声明可能影响同目录下其他脚本。要迁的话，先看应用入口、构建配置、测试配置，别某个配置文件还按旧模式写。

2. 路径解析、默认导出、原来 CommonJS 专属变量的用法，都要对一遍。构建工具能接受某种导入，不代表直接交给 Node 执行也能接受。验证要覆盖实际部署或运行方式，编辑器提示过了不算完。

3. 先挑一段边界清楚的依赖链试迁，再验证启动、测试和生产产物。遇到只支持旧格式的依赖，按运行时支持情况做互操作。迁的理由应是具体维护收益，不是觉得新语法天然更快。
