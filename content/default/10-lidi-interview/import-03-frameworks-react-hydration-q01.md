# 为什么不能到处 suppressHydrationWarning？

## 核心回答

1. `suppressHydrationWarning` 是少量实在对不齐时的例外，不是修 SSR 的工具。服务端 HTML 和客户端第一次渲染本应一致。警告压掉，时间、数据、结构对不上更难发现。

2. 它只管用到的那一层，不会递归忽略整棵子树。设了它，React 也不会保证把不一致的文本补好。服务端显示一种状态，客户端逻辑当成另一种，用户仍可能看到错的，或者走进恢复渲染。

3. 先找差异从哪来。服务端按 UTC 格式化，客户端按本地时区；或者 render 里直接 `Math.random()`。优先把同一份时间和初始数据传下去，首屏用确定结果。要按本地显示的，等客户端提交后再改。

4. 局部时间实在对不齐，限制在单个元素上，把原因写清楚。别整页包一层来盖非法 HTML、登录态不一致、数据没注入。这些改输入和结构。直接打开这个地址也要测，客户端跳转测不到 hydration。

5. 登录态、按钮禁用不一样，文字差一点点也不能当没看见。用户拿首屏判断能不能点。两边输入先统一；身份只能在浏览器里确认，就先显示两边一样的等待，确认后再更新那一块。

## 追问：时间显示不同，一定要关闭服务端渲染吗？

1. 不用先把整页改成客户端渲染。服务端定一个时间戳传给客户端，两边先用同一个时区、同一种格式显示。文章、商品这些主体还是能靠服务端 HTML 先出来。

2. 产品要求显示浏览器本地时间，客户端第一次仍复用服务端那串字，挂载后再转。字变长可能把旁边挤开，提前留点空间。

3. 真正依赖浏览器、服务端没什么有意义输出的一小块，再考虑客户端边界。看首屏内容值和等待成本。一个日期格式，不值得把整页已经有的服务端内容扔掉。

## 追问：测试环境没有警告，线上仍可能出现 mismatch 吗？

1. 可能。测试机和服务器常常同一套语言、时区，真实用户不是。日期、数字格式、本地存储都会带来差别。构造不同时区、第一次访问、已经有登录存储这些条件，别只用自己这台浏览器。

2. 服务端直接打开目标地址也要测。客户端路由跳过去，可能根本没走 hydration，首屏差异露不出来。看网络返回的 HTML 和客户端初始输入，比只看跳转后的页面更贴这个问题。

3. 不稳定复现的，可以用框架或 `hydrateRoot` 的可恢复错误入口记下路由、版本、错误类型。别把用户表单内容收进日志。先缩小差异在哪一块，再对着原因改。
