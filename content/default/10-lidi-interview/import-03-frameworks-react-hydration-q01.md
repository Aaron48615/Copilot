# 为什么不能到处 suppressHydrationWarning？

## 核心回答

1. suppressHydrationWarning 是处理少量不可避免差异的例外选项，不是修复 SSR 的工具。服务端 HTML 和客户端首次渲染本应一致，直接压掉警告，只会让时间、数据或结构不一致的问题更难发现。

2. 它只针对使用位置有限的一层差异，不能递归忽略整棵子树。React 也不会因为设置它就保证修补不一致的文本；如果服务端显示一种状态、客户端逻辑认为是另一种，用户仍可能看到错误内容或出现恢复渲染。

3. 我会先找差异来源，例如服务端使用 UTC，客户端按本地时区格式化日期，或者 render 中直接生成随机数。优先传递相同的时间和初始数据，首屏使用确定结果，需要本地化的内容再在客户端提交后更新。

4. 确实无法避免的局部时间展示，可以限制在单个元素并说明原因。不能把整页包上它来掩盖非法 HTML、登录状态不同或数据注入遗漏；这些问题应修正输入和结构，并在直接访问页面的场景中验证，而不是只测客户端跳转。

5. 尤其是登录状态或按钮禁用状态不同，不能因为文字差异不显眼就忽略。用户会依据首屏判断能否操作，服务端和客户端输入应先统一；如果只能在浏览器确认身份，可以先显示双方一致的等待状态，再在确认后更新对应区域。

## 追问：时间显示不同，一定要关闭服务端渲染吗？

1. 不需要先把整个页面改成客户端渲染。可以由服务端确定一个时间戳并传给客户端，双方先用相同的时区和格式显示，这样文章、商品等主体内容仍可以通过服务端 HTML 直接呈现。

2. 如果产品要求显示浏览器本地时间，客户端首次仍复用服务端文本，挂载后再转换。这个过程可能改变文字宽度，可以提前预留空间，避免时间从短文本变成长文本时把周围布局推开。

3. 只有真正依赖浏览器、没有有意义服务端输出的局部组件，才考虑客户端边界。选择时要看首屏内容价值和等待成本，不应为一个日期格式问题牺牲整页已有的服务端内容。

## 追问：测试环境没有警告，线上仍可能出现 mismatch 吗？

1. 可能，测试机和服务器常常使用相同语言、时区，而真实用户不同。日期、数字格式和本地存储会带来环境差异，我会构造不同时区、首次访问和已有登录存储等条件，而不只沿用开发者自己的浏览器。

2. 还需要测试服务端直接打开目标地址。客户端路由跳转可能完全跳过 hydration，无法暴露首屏差异；检查网络返回的 HTML 与客户端初始输入，比只观察跳转后的页面更贴近问题发生位置。

3. 对无法稳定复现的情况，可以利用框架或 hydrateRoot 的可恢复错误入口记录必要上下文，如路由、版本和错误类型。记录时避免收集用户表单内容，先缩小差异位置，再针对原因修复。
