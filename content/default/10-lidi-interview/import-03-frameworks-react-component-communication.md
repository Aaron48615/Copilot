# React 组件之间怎么通信？

## 核心回答

1. 父子之间我优先使用 props 和回调。比如父组件把选中的商品传给详情卡片，同时传 onSelect；子组件点击时调用回调带回商品编号，由父组件决定如何更新，子组件不直接修改收到的数据。

2. 兄弟组件需要同步时，可以把状态提升到最近的共同父组件。搜索框修改条件，列表读取同一份条件，避免两个组件分别保存搜索词后再互相同步；如果只有一个组件使用，就没有必要继续往更高层放。

3. 跨越很多层时，可以用组件组合减少中间层传参，也可以用 Context 提供主题、用户信息等依赖。Context 负责传递值，状态仍需要 useState 或 useReducer 等管理；value 变化会通知读取该 Context 的消费者。

4. 多页面共同修改的数据，如果还涉及复杂更新规则和调试需求，我会考虑 Redux Toolkit 等状态库。事件总线也能通信，但事件来源和订阅清理更难追踪，我不会把它当默认方案，尤其不希望数据只能靠某个事件碰巧触发才能一致。

5. 还要明确共享状态的生命周期。例如退出登录后用户信息需要重置，弹窗关闭后草稿是否保留则由交互决定。通信方式只负责把值和动作送到对应组件，不会自动替我们决定清理与保存规则，这些需要在状态拥有者那里表达清楚。

## 追问：子组件调用回调，算不算违反单向数据流？

1. 不算，因为回调传回的是用户意图或新值，真正的数据仍由拥有它的父组件更新。比如子组件发出“删除编号为 12 的商品”，父组件可以先检查权限、调用接口，再决定是否从列表移除。

2. 我会把回调命名成 onRemove、onChange 这类具体动作，参数尽量只包含必要信息。直接把父组件所有 setter 都传下去，会让子组件知道太多内部结构，以后调整状态形状时双方都要修改。

3. 异步操作还需要明确等待和失败反馈。删除失败后父组件保持列表，向子组件传递错误或忙碌状态；不能子组件先私自删一份数据，父组件另一份又没有更新，最后只能靠刷新恢复一致。

## 追问：层层传 props 一定要改成 Context 吗？

1. 不一定，我会先看中间组件是否真的需要这些数据。若只是为了把用户信息传给一个深层头像，可以由上层直接构造头像作为 children 传入，中间布局只负责摆放，接口反而更简单。

2. 数据只经过两三层、关系也清楚时，props 的显式传递通常便于阅读和测试。Context 会引入隐含的环境依赖，单独展示组件时还要补 Provider，不能只根据层数机械选择。

3. 如果很多分支都需要同一种环境信息，再使用 Context 更合理。Provider 尽量靠近使用范围，并拆开变化频率差异大的数据，例如主题不必和每次按键都改变的搜索词放在同一个 value 里。我也会检查组件单独使用的成本，明确需要哪几项输入，便于以后移动布局和编写独立交互测试。
