# React 组件之间怎么通信？

## 核心回答

1. 父子之间用 props 和回调。父组件把选中的商品传给详情卡片，再传一个 `onSelect`。子组件点了就调回调，把商品编号带回去，由父组件改数据。子组件别直接改收到的那份。

2. 兄弟要一起变，把状态提到最近的共同父组件。搜索框改条件，列表读同一份条件。别两个组件各存一个搜索词再互相同步。只有一边在用，就没必要再往上提。

3. 隔了很多层，可以用组合少传几层，比如上层直接把头像当 `children` 塞进去。主题、当前用户这种环境信息也可以用 Context。Context 负责把值递下去，状态本身还是 `useState` 或 `useReducer` 管。`value` 一变，读这个 Context 的组件都会收到。

4. 好几个页面都要改同一份数据，更新规则又复杂、还要好查，可以上 Redux Toolkit 这类状态库。事件总线也能通，但事件从哪来、订阅清没清更难跟，不当默认做法。别指望数据碰巧靠某个事件打一下就对齐。

5. 共享状态还有生命周期。退出登录，用户信息要清掉；弹窗关了，草稿留不留看交互。通信只是把值和动作送到该去的组件，清不清理、存不存，还是状态拥有者自己说清楚。

## 追问：子组件调用回调，算不算违反单向数据流？

1. 不算。回调带回去的是用户想干什么，或者一个新值，真正改数据的还是拥有这份数据的父组件。比如子组件说「删编号 12 的商品」，父组件可以先看权限、调接口，再决定列表里去不去掉。

2. 回调名字写成 `onRemove`、`onChange` 这种具体动作，参数只带必要的信息。别把父组件所有 setter 一股脑传下去，子组件就会摸到太多内部结构，以后改状态形状两边都得动。

3. 异步还要把等待和失败说清楚。删除失败，父组件列表保持原样，把错误或忙碌状态传给子组件。别子组件自己先删一份，父组件那份没动，最后只能刷新才对得上。

## 追问：层层传 props 一定要改成 Context 吗？

1. 不一定。先看中间那些组件是不是真的要用这份数据。只是把用户信息送到深层一个头像，上层直接把头像当 `children` 传进去，中间布局只管摆位置，接口更简单。

2. 就过两三层、关系也清楚，props 显式传更好读、也好测。Context 是隐含的环境，单独展示这个组件还得补 Provider。别按层数机械换成 Context。

3. 很多分支都要同一种环境信息，再用 Context 更合适。Provider 尽量靠近真正用到的范围。变化快慢差很多的别塞同一个 `value`，主题没必要跟每个按键都变的搜索词绑在一起。单独拿这个组件测交互时，要说清它依赖哪几项输入，以后挪布局也好接。
