# never 在 switch 里怎么用？

## 核心回答

1. `never` 在 `switch` 里主要用来检查联合类型是否处理完整，它表示当前分支理论上不该再有可能的值。一个任务只有等待、执行中和完成三种状态，分别处理后，把剩余值交给参数类型为 `never` 的检查函数，遗漏就会变成编译错误。

2. 这个方法依赖前面的分支真正排除了对应成员。每个分支直接返回结果，后面的值就能逐渐收窄。如果只是执行几行代码后继续往下走，状态仍可能到达检查位置。不能因为写过 `case` 就认定联合已经被排空，要结合实际控制流判断。

3. 以后如果给联合增加失败状态，但忘记补 `switch` 分支，剩余值就不再是 `never`，检查函数的调用会报错。相比默认返回一段通用文字，这更容易提醒补全新状态的行为，尤其适合状态展示、消息分发等需要逐种处理的逻辑。

4. 检查函数可以声明返回 `never`，并在内部抛出错误，表达这条路径不会正常返回。不能把参数先断言成 `never` 再传进去，否则原本应该暴露的遗漏被人为绕过。也不能只写一个没有任何检查的默认分支，然后说已经穷尽。

5. 这仍然是静态保证。外部输入若未经校验，运行时可能传来类型声明之外的状态。因此接口入口应先验证未知状态，内部再依赖完整联合。抛错属于最后防线，页面是否展示兼容提示要按实际需求设计。编译通过不等于永远不会遇到新值。

## 追问：为什么新增联合成员后，普通 default 不一定报错？

1. 普通 `default` 本来就接受其他值，如果里面直接返回「未知」，新增状态自然也能走进去，编译器没有理由认为这违反了返回类型。结果可能是页面可以运行，但本该专门设计的失败提示悄悄变成了通用文字。

2. 把剩余值赋给 `never` 变量，或者交给只接收 `never` 的函数，才是在明确要求此处没有任何成员。新增失败状态后，这个状态无法赋给 `never`，提示会落在未补齐的分发位置，提醒修改者继续完成逻辑。

3. 不过并非所有开关都必须穷尽。开放的第三方状态码可能需要保留未知分支。先确认这是自己控制的有限状态，还是允许扩展的外部输入，再决定报编译错误或兼容显示，不能为了形式统一牺牲业务兼容性。

## 追问：switch 检查应该传状态字符串还是整个联合对象？

1. 输入只是几个状态字符串，就把剩余字符串传给检查函数，写法已经足够清楚。输入是带状态字段的联合对象，优先按对象的判别字段分支，并让检查函数接收剩余对象，检查的就是整个输入模型。

2. 成功对象带数据、失败对象带错误说明，按状态分支后可以分别访问各自字段，而不必把所有字段写成可选。这样分支除了检查是否漏掉一种结果，还能保证处理成功时确实有成功数据，减少无意义的空值判断。

3. 某次重构把状态字段提前拆出后导致收窄不清楚，先保留完整对象观察控制流，而不是马上加断言。重点是让状态和负载的关联保持明确。只有类型模型确实表达这种关联，穷尽检查才能约束想检查的情况。
