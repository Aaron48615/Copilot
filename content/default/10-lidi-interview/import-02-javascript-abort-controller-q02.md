# 一个 signal 能复用多次吗？

## 核心回答

1. 一个还没有取消的信号可以交给多个操作使用，所以复用本身并不是错误，关键在于它们是否应该一起结束。比如详情页同时加载基本信息和相关推荐，如果离开页面时两者都没有价值，就可以让这组请求共享同一个信号。

2. 但信号一旦进入已取消状态就不能恢复，控制器也没有重置方法，之后拿它发起新的请求会直接遇到取消。用户再次打开详情页属于新一轮任务，我会创建新的控制器，不能继续沿用上一次已经取消的实例。

3. 共享信号意味着共享取消范围，并不意味着共享成功或失败的结果，其中一个请求失败也不会自动取消其他请求。如果需求是任一请求失败就停止整组任务，需要在协调逻辑里显式调用取消，并处理每个请求最终的结果。

4. 我会按任务生命周期保存控制器，而不是把它做成整个应用长期共用的单例，否则一个区域的取消可能误伤另一个区域。对于能独立重试的请求，我通常给它单独的控制器，并在重试时重新建立本轮的取消关系。

## 追问：同组请求里只有一个需要重试怎么办？

1. 先检查共享信号是否已经取消，如果没有取消，技术上可以继续把它传给重试请求。还要确认这次重试仍然属于原来的页面任务，否则页面离开时可能找不到正确的取消入口，留下不必要的请求。

2. 如果共享信号已经取消，就必须为新任务创建新的控制器，不能修改已取消标记来恢复它。假设商品信息成功而推荐失败，我会保留成功部分，只为推荐建立新的请求状态，避免让整个页面重新闪烁。

3. 如果后续需要分别取消两部分，我会从任务设计上拆开控制器，而不是在共享实例上补特殊判断。测试时要覆盖重试期间离开页面，以及旧失败回调晚于新成功回调，防止重试结果被旧状态覆盖。

## 追问：自己封装支持 signal 的异步函数要注意什么？

1. 函数开始时先检查信号是否已经取消，因为只注册取消事件会漏掉过去已经发生的取消。对于已取消输入，应立即按约定结束任务并返回对应原因，不要先启动定时器或耗时工作，再等待一个不会重发的事件。

2. 任务运行期间监听取消事件，在回调里停止自己能够停止的资源，例如清除尚未触发的定时器。只让外层 Promise 进入拒绝状态并不会让底层工作自动停止，因此需要明确谁负责实际清理，以及哪些操作本来就不可中断。

3. 任务正常完成或失败后都应移除不再使用的监听器，避免信号长期引用处理函数。即便监听器设置为只触发一次，正常完成而没有取消时它也可能还在，所以仍然需要完成路径上的主动清理。
