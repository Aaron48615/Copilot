# 一个 signal 能复用多次吗？

## 核心回答

1. 还没取消的信号可以交给多个操作，复用本身没错，关键是它们该不该一起结束。比如详情页同时拉基本信息和相关推荐，离开页面时两样都没用了，就可以让这组请求共用同一个信号。

2. 信号一旦取消就不能恢复，控制器也没有重置方法，之后拿它再发请求会直接被取消。用户再次打开详情页是新一轮任务，得建新的控制器，不能继续用上一次已经取消的那个。

3. 共享信号只共享取消范围，成功失败各算各的。其中一个请求失败，不会自动把其他请求也取消掉。真要「一个失败就整组停」，得在协调逻辑里自己调用取消，并且每个请求最终的结果都要处理。

4. 控制器跟着任务生命周期走，别做成整个应用长期共用的单例，不然一个区域取消可能误伤另一个区域。能独立重试的请求，通常给它单独的控制器，重试时再重新接上本轮的取消关系。

## 追问：同组请求里只有一个需要重试怎么办？

1. 先看共享信号取消了没有。还没取消，技术上可以继续传给重试请求。还得确认这次重试仍属于原来的页面任务，不然页面离开时找不到正确的取消入口，请求会继续跑。

2. 共享信号已经取消了，就得给新任务建新控制器，不能改那个已取消标记把它救回来。比如商品信息成功、推荐失败，成功那部分留着，只给推荐开一轮新的请求状态，别让整页重新闪一遍。

3. 后面如果要分别取消这两部分，从一开始就把控制器拆开，别在共享实例上补一堆特殊判断。测试要覆盖：重试期间离开页面，以及旧失败回调比新成功回调还晚到，防止重试结果被旧状态盖住。

## 追问：自己封装支持 signal 的异步函数要注意什么？

1. 函数一开始先看信号是不是已经取消。只注册取消事件，会漏掉已经发生过的取消。已经取消的输入，应按约定马上结束并带上对应原因，别先开定时器或重活，再等一个不会再发的事件。

2. 运行期间监听取消，回调里停掉自己能停的资源，比如清掉还没触发的定时器。外层 Promise 变成拒绝，底层工作不会自动停，得说清楚谁来做实际清理，哪些操作本来就停不了。

3. 任务正常完成或失败后，都要把不用的监听器摘掉，别让信号长期握着处理函数。就算监听器设成只触发一次，正常完成、没发生取消时它也可能还挂着，完成路径上还是要主动清。
