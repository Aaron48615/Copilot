# E2E 如何处理第三方服务？

## 核心回答

1. 我会先明确这条测试要验证自己的页面行为，还是验证第三方真的可以接通。日常回归通常在稳定的接口边界替换第三方响应，少量接入检查使用官方沙箱；两类结果分开解释，mock 成功不能证明真实支付或地图服务可用。

2. 替换位置要跟请求实际经过的地方一致。浏览器直接请求的接口可以用 Playwright 路由拦截；如果是自己的后端调用第三方，浏览器拦截只能替换前后端之间的响应，要验证后端适配逻辑还得在服务端测试环境替换对应依赖。

3. 响应数据不能只有永远成功的一份，我会准备成功、限流、结构异常和等待超时等场景。例如支付状态先是处理中，随后才变成成功，页面应该允许查询结果，而不是收到任意二百状态码就直接显示已支付。

4. 拦截规则要在触发请求前注册，并核对方法、路径和必要参数，避免误拦其他业务请求。需要区分 HTTP 错误与连接失败：返回五百响应和直接中断请求会经过不同处理分支，测试不能把二者混成同一种失败。

5. 如果继续完善真实接入检查，我会使用专门测试账号和沙箱数据，控制调用次数并保留脱敏诊断信息。第三方不可用时要说明失败来自外部接入，不能无限重跑，也不能因为本地 mock 全通过就宣称完整外部流程已经验证。

## 追问：mock 一直通过，怎么发现第三方接口已经变了？

1. 我会把 mock 数据和实际接口约定对应起来，检查字段名称、类型、状态枚举及必要错误响应。比如金额从数字变成字符串，前端固定夹具可能完全察觉不到，只有让真实响应或沙箱响应经过约定检查才有机会发现差异。

2. 少量独立接入用例可以定期请求沙箱，验证鉴权和关键字段，再让适配层把响应转换成内部格式。沙箱不一定完全等同生产，所以通过时只能说明被检查的接口和环境可用，不能扩大为第三方所有能力都没有变化。

3. 修改 mock 时要看变更依据，不能为了让测试变绿就随意补字段。如果出现约定不匹配，我会先判断是接口升级、环境版本不同还是自己的理解错误，并记录需要调整的适配代码和测试样本，让两边使用同一份明确约定。

## 追问：路由拦截没有生效，应该从哪里查？

1. 我先看请求是否真的从当前页面发出，以及 URL、方法和注册时机是否匹配。例如页面加载时已经请求完了才设置 route，或者接口经过后端代理，都会让原本看似正确的拦截规则没有机会执行。

2. 再检查是否存在其他页面、弹窗或 Service Worker。需要覆盖多个页面时可考虑 context 级拦截；被 Service Worker 接管的请求可能不经过预期路由，在专门测试接口响应的场景可按环境要求阻止 Service Worker 后重试定位。

3. 我会记录实际请求并让未匹配的关键请求明确暴露，而不是默默访问外网后仍认为 mock 生效。若测试本身就是验证离线缓存，则不能关闭 Service Worker 来绕过问题，应该调整测试目标，分别验证缓存逻辑和普通网络交互。
