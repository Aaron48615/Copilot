# 怎么避免缓存无限增长？

## 核心回答

1. 每类缓存保存什么、保存多久、最多多少条，要自己定。Cache Storage 不会自动替业务做过期。浏览器可能回收存储，但那是不可预测的资源管理，当不了自己的清理方案。

2. 预缓存可以按应用版本命名，新版本确认可用后再清明确不再需要的旧缓存。删除只动本应用的命名范围，别遍历删掉同源所有缓存。旧页面还在跑，它们是不是还依赖上一版资源，也要考虑。

3. 运行时缓存要有数量、时间或容量约束。比如图片只留有限的近期条目，过期列表在读或写的时候淘汰。查询参数也会把缓存键撑多，每个带时间戳的 URL 都永久存，空间会爆。规范化键之前，先确认这个参数会不会改变内容。

4. 用户数据单独处理。私人接口不该无条件进公共资源缓存。退出、切账号时清相应范围。不可丢的草稿、未同步任务用独立存储策略。为了省空间把用户唯一数据一起删，后面恢复不了。

5. 看存储估算和缓存条目数，长时间使用、升级、空间不足都测一下。写缓存失败按业务决定怎么回退。图片已经从网络加载成功，却因为附带缓存失败让整个页面功能也失败，这个回退就不合适。

## 追问：缓存淘汰用先进先出，还是最近最少使用？

1. 看资源怎么被访问。先进先出实现简单，按写入先后删。最近最少使用要记访问情况，更适合某些热点资源，但额外读写元数据也有成本。名字更复杂，不代表一定更好。

2. 离线帮助文档可能需要固定留着，普通浏览过的图片可以按最近使用淘汰。不同资源不必共用一套规则。哪些能重建、哪些必须保持可用，说清楚，每类设合理上限。

3. 连续浏览大量新内容之后，常用资源还在不在，删除操作会不会拖慢请求，这两项要测。条目数量不是实际字节大小，一张大图可能比很多小文件占得更多。必要时结合大小或总体存储估算。

## 追问：给缓存键去掉全部查询参数，可以减少空间吗？

1. 键能变少，但可能把不同内容错误合成一份。图片宽度、语言、搜索条件都可能由查询参数决定，全部去掉后可能返回错误尺寸或另一种查询结果。省了空间，页面却错了。

2. 按允许名单规范化那些明确不影响内容的参数，业务参数和统计参数分开处理。涉及用户身份和权限的内容，不能靠简单改键共享缓存。先判断允不允许缓存、隔离范围是什么，否则还可能把私人数据漏给别人。

3. 同一路径、不同参数的请求拿来对，该相同的结果相同，该不同的结果不同。某个参数没法证明无关，就留着它，用过期和数量限制控容量。没有依据的合并，命中率上去了，内容可能已经错了。
