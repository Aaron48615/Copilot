# 怎么避免缓存无限增长？

## 核心回答

1. 避免 Service Worker 缓存无限增长，需要明确每类缓存保存什么、保存多久和最多多少条。Cache Storage 不会自动替我实现业务过期规则，浏览器可能回收存储，但那是不可预测的资源管理，不能当作自己的清理方案。

2. 预缓存可以按应用版本命名，在新版本确认可用后清理明确不再需要的旧缓存。删除时只操作本应用的命名范围，不遍历删掉同源所有缓存；如果旧页面仍在运行，还要考虑它们是否继续依赖上一版资源。

3. 运行时缓存需要数量、时间或容量约束，例如图片只保留有限的近期条目，过期列表在读取或写入时淘汰。查询参数也会增加缓存键数量，不能把每个时间戳 URL 都永久保存，但规范化键之前要确认参数是否影响内容。

4. 用户数据要单独处理，私人接口不应无条件进入公共资源缓存。退出和切换账号时清理相应范围，保留不可丢的草稿或未同步任务则需要独立存储策略，不能为了节省空间把用户唯一数据一起删除。

5. 如果继续完善，我会观察存储估算和缓存条目数，并测试长时间使用、升级和空间不足。写缓存失败应按业务决定回退，不能让图片已经从网络成功加载，却因为附带缓存失败使整个页面功能也失败。

## 追问：缓存淘汰用先进先出，还是最近最少使用？

1. 要看资源访问模式。先进先出实现简单，按写入先后删除；最近最少使用需要记录访问情况，更适合某些热点资源，但额外读写元数据也有成本，不应仅因为名字更复杂就认为一定更好。

2. 例如离线帮助文档可能需要固定保留，普通浏览过的图片则可以按最近使用淘汰。不同资源不必共用一套规则，重要的是明确哪些可重建、哪些必须保持可用，并为每类设置合理上限。

3. 我会测试连续浏览大量新内容后，常用资源是否还在，以及删除操作是否拖慢请求。条目数量不是实际字节大小，一张大图可能比很多小文件占用更多，因此必要时还要结合大小或总体存储估算。

## 追问：给缓存键去掉全部查询参数，可以减少空间吗？

1. 能减少键数量，但可能把不同内容错误合并。例如图片宽度、语言和搜索条件都可能由查询参数决定，全部去掉后可能返回错误尺寸或另一种查询结果，节省空间的同时破坏了页面正确性。

2. 我会按允许名单规范化明确不影响内容的参数，并分别处理业务参数与统计参数。涉及用户身份和权限的内容不能靠简单改键共享缓存，必须先判断是否允许缓存以及隔离范围，否则还可能泄露私人数据。

3. 验证用同一路径的不同参数请求，检查应相同与应不同的结果。若无法证明某个参数无关，就保留它并通过过期和数量限制控制容量，不为了提高命中率做没有依据的合并。
