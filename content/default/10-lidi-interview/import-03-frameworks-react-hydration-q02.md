# 客户端数据请求放哪里？

## 核心回答

1. 我会根据数据是否影响首屏、在哪里能安全获取来决定。服务端可以拿到的页面主体数据，适合使用框架的数据加载能力预先获取，让 HTML 和客户端初始化共享同一份输入，减少先看到空壳再请求的等待。

2. 客户端接手时，应正确复用服务端下发的数据或初始化查询缓存。否则服务端刚查完一次，客户端挂载又立刻请求相同内容，可能增加网络开销，还可能因为两次数据不同导致首屏或加载状态发生跳动。

3. 用户交互后的搜索、分页、收藏等通常需要在客户端发起；只存在浏览器中的条件，也要在客户端读取。查询与修改要区别处理，点击提交是事件动作，不能把一次性业务写入藏在可能重新执行的挂载 Effect 里。

4. 无论请求在哪侧，都需要处理失败、权限和缓存范围。服务端可以使用私有凭据，但只能向客户端传递允许展示的结果；按用户区分的数据不能进入不区分身份的共享缓存。SSR 并不意味着后续刷新和账号切换不再需要校验。

5. 例如商品详情的名称和描述可用于首屏，用户点击规格后重新查询可售情况。这样初次阅读不必等待浏览器再启动请求，交互后的信息也能按当前选择更新；同时保留失败提示，不把首屏已经渲染成功误认为后续选择都一定有数据。

## 追问：已有 SSR 数据，客户端是不是可以永远不再请求？

1. 不可以，服务端数据只是某个时间点的结果。库存、消息数量等可能很快变化，客户端要根据业务时效要求决定何时刷新，比如用户重新聚焦页面、执行修改或主动点击刷新时重新确认。

2. 可以设置合适的新鲜度窗口，避免刚完成 hydration 就重复获取，但窗口长短不能统一套用。文章正文和活动余量的更新频率不同，保留旧值的同时提示后台刷新，通常比每次都清空页面更自然。

3. 用户切换身份时必须重新考虑数据归属。上一用户的个人订单即使仍在新鲜度窗口内，也不能直接显示给下一用户；查询键或缓存实例要包含身份范围，退出时处理对应缓存。

## 追问：为什么不把访问接口的密钥直接随初始数据发给客户端？

1. 初始数据最终会进入浏览器，可能出现在 HTML、脚本或网络响应中，不能按服务端私有变量看待。客户端只需要商品列表，就应该下发列表，不应同时暴露用于读取更多资源的服务端凭据。

2. 我会把有权限的访问留在服务端，按当前用户裁剪返回字段。比如管理接口包含内部备注，前台页面并不需要，就不应该先完整下发再通过 JSX 隐藏，隐藏元素并不会删除已经传出的数据。

3. 后续客户端请求也应走经过授权的接口，由服务端重新检查身份和资源范围。不能把 SSR 时通过一次校验理解成浏览器之后都可信，尤其是详情编号和账号发生变化的时候。
