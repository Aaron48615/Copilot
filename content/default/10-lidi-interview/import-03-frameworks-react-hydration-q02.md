# 客户端数据请求放哪里？

## 核心回答

1. 看这份数据管不管首屏，以及哪边能安全拿到。服务端能拿到的页面主体，适合用框架的数据加载预先取好，让 HTML 和客户端初始化用同一份输入。少出现先空壳再请求的等待。

2. 客户端接手时，把服务端下发的数据或初始化查询缓存用上。不然服务端刚查完，客户端一挂载又请求同一份，网络多一趟，两次数据还可能不一样，首屏或加载状态会跳一下。

3. 用户交互之后的搜索、分页、收藏，一般在客户端发。只存在浏览器里的条件，也在客户端读。查询和修改分开：点击提交是事件，一次性业务写入别藏在可能再跑的挂载 Effect 里。

4. 哪边请求都要处理失败、权限、缓存范围。服务端可以用私有凭据，传给客户端的只能是允许展示的结果。按用户分的数据，别进不区分身份的共享缓存。SSR 不等于后面刷新、换账号就不用再校验。

5. 比如商品详情的名称、描述可以上首屏；用户点了规格，再查可售情况。第一次阅读不必等浏览器再发请求，交互后的信息按当前选择更新。失败提示还在。首屏渲染成功，不代表后面每次选择都一定有数据。

## 追问：已有 SSR 数据，客户端是不是可以永远不再请求？

1. 不行。服务端数据只是那个时间点的结果。库存、消息数可能很快变。按业务时效决定何时刷新：页面重新聚焦、用户改了数据、主动点刷新，再确认一遍。

2. 可以设一个新鲜度窗口，刚 hydration 完别立刻再拉。窗口长短不能所有接口一套。文章正文和活动余量更新频率不一样。留着旧值、后台在刷新，通常比每次先清空页面更顺。

3. 用户换身份，数据归属要重算。上一用户的个人订单就算还在新鲜度窗口里，也不能直接给下一用户看。查询键或缓存实例带上身份范围，退出时把对应缓存处理掉。

## 追问：为什么不把访问接口的密钥直接随初始数据发给客户端？

1. 初始数据最后会进浏览器，可能出现在 HTML、脚本、网络响应里，不能当服务端私有变量。客户端只要商品列表，就下发列表，别顺便带上还能去读更多资源的服务端凭据。

2. 有权限的访问留在服务端，按当前用户裁字段。管理接口里的内部备注，前台页用不到，就别完整下发再用 JSX 藏起来。藏住元素，删不掉已经传出去的数据。

3. 后面客户端再请求，也走经过授权的接口，服务端重新查身份和资源范围。SSR 时过了一次校验，不代表浏览器之后都可信，尤其详情编号、账号已经变了的时候。
