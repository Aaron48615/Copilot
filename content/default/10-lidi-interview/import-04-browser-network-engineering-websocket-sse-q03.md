# 鉴权放在哪里？

## 核心回答

1. 实时连接的鉴权应由服务端在建立连接或订阅时完成，不能只依赖前端菜单与路由守卫。身份有效也不代表能订阅任意房间或会话，服务端还要检查资源归属和权限，并在后续操作中维持这个约束。

2. 浏览器原生 WebSocket 构造器不允许像 fetch 那样任意设置 Authorization 头。可以结合受限 Cookie，或者先通过普通接口换取短期连接票据；原生 EventSource 同样不支持随意自定义请求头，需要按实际认证方式选择接入路径。

3. 使用 fetch 读取 SSE 时可以按请求规则设置头和方法，但要自己实现事件解析与恢复。跨源场景还涉及 CORS、凭据和 Cookie 属性，WebSocket 服务端也应校验 Origin，不能认为所有浏览器连接都由同一种 CORS 机制保护。

4. 长期 Token 不宜放进查询参数，因为 URL 可能进入访问日志、监控和其他记录。若使用签名 URL 或一次性票据，应限制有效期、用途和重用范围，并对日志脱敏；建立连接成功后也不能永久忽略令牌过期和撤权。

5. 我会测试无身份、过期身份、越权订阅和重连。原生 EventSource 的 error 是普通事件，拿不到 HTTP 状态，不能直接认定鉴权失败；可独立检查会话、读取已建流的明确业务事件，或用 fetch 状态区分。确认失效后恢复登录，切账号时关闭旧连接并清理消息。

## 追问：WebSocket 建立后，Token 过期了应该怎么办？

1. 握手时验证通过不代表整个连接生命周期永久有效。服务端需要根据业务决定到期断开、周期检查或通过受控消息刷新认证，前端按约定处理，不能只在浏览器本地计时后假设后端已经撤销权限。

2. 如果采用重新连接，我会先完成会话恢复，再带新凭据建立连接，并用事件位置恢复消息。旧连接和新连接可能短暂重叠，客户端应按连接或会话版本过滤旧消息，避免重复展示或混入上个账号的数据。

3. 撤权也应有明确处理，例如用户被移出房间后，服务端停止相关推送。测试不只覆盖自然过期，还要主动注销和权限改变；仅凭连接仍保持打开，不能认定用户仍拥有最初全部访问权。

## 追问：为什么不直接把长期 Token 拼到 WebSocket URL？

1. URL 容易进入代理访问日志、监控记录或截图，长期凭据被复制后可能持续有效。即使传输使用 WSS，也只是保护网络途中，不能阻止服务端及终端记录地址，因此应减少凭据出现在 URL 中的范围和寿命。

2. 更合适的方案可以是先用已有认证接口获取短期、用途受限的连接票据，再用它建立连接。服务端校验并限制重复使用，日志也要屏蔽票据参数；票据短期化降低风险，但不等于允许随意公开记录。

3. 我会与后端明确票据过期、连接失败重试和重复握手的规则，避免一个票据用完后前端不停重连。若采用 Cookie，同样要校验来源和订阅权限，不能只是把风险从 URL 搬到自动携带凭据而不继续检查。
