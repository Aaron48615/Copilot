# 鉴权放在哪里？

## 核心回答

1. 实时连接的鉴权由服务端在建立连接或订阅时完成，前端菜单和路由守卫挡不住。身份有效也不代表能订阅任意房间或会话。服务端还要检查资源归属和权限，后续操作里继续维持这个约束。

2. 浏览器原生 WebSocket 构造器不允许像 `fetch` 那样任意设 `Authorization` 头。可以结合受限 Cookie，或者先通过普通接口换短期连接票据。原生 `EventSource` 同样不支持随意自定义请求头，按实际认证方式选接入路径。

3. 用 `fetch` 读 SSE 时可以按请求规则设头和方法，但事件解析和恢复要自己做。跨源还涉及 CORS、凭据、Cookie 属性。WebSocket 服务端也应校验 Origin。所有浏览器连接都由同一种 CORS 机制保护，这个假设不成立。

4. 长期 Token 不宜放进查询参数，URL 可能进访问日志、监控和其他记录。若用签名 URL 或一次性票据，限制有效期、用途、重用范围，日志脱敏。连接建立成功后，令牌过期和撤权也不能永久忽略。

5. 测无身份、过期身份、越权订阅、重连。原生 `EventSource` 的 `error` 是普通事件，拿不到 HTTP 状态，不能直接认定鉴权失败。可独立检查会话，读已建流的明确业务事件，或用 `fetch` 状态区分。确认失效后恢复登录。切账号时关掉旧连接、清掉消息。

## 追问：WebSocket 建立后，Token 过期了应该怎么办？

1. 握手时验证通过，不代表整个连接生命周期永久有效。服务端按业务决定到期断开、周期检查，或通过受控消息刷新认证，前端按约定处理。只在浏览器本地计时，就假设后端已经撤销权限，两边会对不上。

2. 若采用重新连接，先完成会话恢复，再带新凭据建连接，并用事件位置恢复消息。旧连接和新连接可能短暂重叠。客户端按连接或会话版本过滤旧消息，避免重复展示，或混入上个账号的数据。

3. 撤权也要有明确处理。比如用户被移出房间后，服务端停止相关推送。测试不只覆盖自然过期，还要主动注销和权限改变。连接仍保持打开，不能认定用户还拥有最初全部访问权。

## 追问：为什么不直接把长期 Token 拼到 WebSocket URL？

1. URL 容易进代理访问日志、监控记录或截图，长期凭据被复制后可能持续有效。就算传输用 WSS，也只保护网络途中，挡不住服务端和终端记录地址。凭据出现在 URL 里的范围和寿命尽量收小。

2. 更合适的是先用已有认证接口拿短期、用途受限的连接票据，再用它建连接。服务端校验并限制重复使用，日志屏蔽票据参数。票据短期化能降低风险，不等于允许随意公开记录。

3. 跟后端明确票据过期、连接失败重试、重复握手的规则，避免一个票据用完后前端不停重连。若采用 Cookie，同样校验来源和订阅权限。只是把风险从 URL 搬到自动携带凭据、不再继续检查，不够。
