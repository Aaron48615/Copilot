# unknown、any 和 never 应该怎么选？

## 核心回答

1. 按当前知道多少信息来选择类型。`unknown` 表示值还不确定，需要检查后再使用。外部响应或捕获到的异常可以先接成未知值，确认它是字符串、错误对象或所需结构后再读属性，让没有验证过的假设停在输入边界。

2. `any` 则基本放开了对这个值的类型检查，可以直接访问不存在的属性，错误还容易继续传播到下游。遇到旧库声明缺失时可能需要临时适配，但尽量把它限制在小范围，并尽快返回明确类型。到处无提示，不等于代码更安全。

3. `never` 表示不存在可能的值，适合表达函数不会正常返回，或联合类型已经全部处理后的剩余分支。一个总是抛错的检查函数可以返回 `never`。给状态联合新增成员时，也可以利用它让遗漏处理的位置出现编译提示，提醒补上行为。

4. `never` 和 `void` 不能混用。`void` 更常表示调用方不依赖返回值，并不说明函数无法结束。事件回调正常执行完可以返回控制权，而抛错函数走不到正常返回路径。二者对后续控制流的含义不同，不能都概括成没有结果。

5. 实际写代码时，优先使用能准确表达输入输出的具体类型，只有未知边界才用 `unknown`，不可能分支才用 `never`。为了消除报错把未知值断言成具体类型，或者强行断言为 `never`，都没有增加真实保证，反而绕开了原本希望得到的检查。

## 追问：catch 捕获的异常为什么不一定是 Error？

1. JavaScript 可以抛出字符串、普通对象甚至空值，并没有强制要求必须是 Error 实例。因此捕获后直接读取 `message` 依赖了额外假设。第三方代码或非标准抛错可能让这个假设失效，错误处理本身也可能再次报错。

2. 先按实际类型分支：常规 Error 可以取消息，字符串可以按规则转为提示，其他情况提供通用文案。跨环境对象未必通过当前环境的实例判断。需要读取类似错误对象的字段，还应单独检查字段存在且类型合适。

3. 面向用户的文案与排查信息也需要区分，不能把任意异常对象直接展示出来。进一步完善错误入口时，统一转换成内部错误结构，并对无法识别的值保留安全兜底，让业务代码不用每次重复猜测抛出了什么。

## 追问：返回 void 的回调能接受一个有返回值的函数吗？

1. 在 TypeScript 中，预期返回 `void` 的回调位置可以接受某些有返回值的函数，因为调用方约定不使用它的结果。遍历回调里调用数组追加方法会得到长度，调用方仍可忽略这个数字。这不代表该函数运行时真的没有返回值。

2. 这和明确声明函数自身返回 `void` 后再返回一个数字不是同一件事，后者通常会触发检查。要分清回调赋值的兼容规则与函数声明约束，否则容易把「结果被忽略」误说成「任何位置都能随便返回」。

3. `never` 更强，要求函数不会正常返回，普通返回数字的函数当然不满足这个条件。设计回调接口时，用 `void` 表示不消费结果，需要结果则写准确返回类型。别拿 `never` 代替空返回，让调用约定变得不可能实现。
