# HTTP 和 HTTPS 的区别？HTTPS 是怎么保证安全的？

## 核心回答

1. HTTPS 可以理解为通过 TLS 保护 HTTP 通信，主要提供传输机密性、完整性和对端身份验证。它解决网络途中被窃听、篡改或冒充的问题，但不负责判断业务接口是否允许某个用户删除某条数据。

2. 建立常见的 HTTPS 连接时，客户端和服务端协商 TLS 版本及算法，服务端提供证书。浏览器检查信任链、域名和有效期等信息，并验证对端确实持有相应私钥；并不是看到一张证书就直接相信服务器。

3. 现代 TLS 常用临时密钥交换材料协商共享秘密，再派生通信密钥，证书签名用于身份认证。后续大量数据用对称加密和完整性保护，不能把所有 TLS 版本都说成客户端拿证书公钥直接加密一个会话密钥。

4. TLS 1.3 简化了握手，符合条件的恢复连接还可发送早期数据，但早期数据有重放风险。下单等有副作用的操作不能因为追求少一次等待就随意使用，实际策略由客户端、服务端和协议实现共同决定。

5. 项目中除了启用 HTTPS，还要避免混合内容并正确设置 Cookie 和重定向。浏览器开发工具能看到本机解密后的请求是正常现象，不代表网络明文传输；终端或服务端被攻破，也不是 HTTPS 单独能够解决的。

## 追问：HTTPS 为什么还可能遇到中间人读取内容？

1. 正常情况下，攻击者缺少可信证书和服务器私钥，不能仅靠截获网络流量就冒充服务器。但如果设备安装并信任了某个代理的根证书，代理可能为站点签发浏览器信任的证书，从而建立两段 TLS 连接。

2. 这类情况常见于用户主动配置的调试代理或组织管理环境，信任前提已经改变。浏览器自身和服务端也能看到解密后的数据，因此传输加密从来不表示数据在所有处理位置都保持不可见。

3. 我会通过证书颁发者和信任链确认当前连接情况，不随意忽略证书警告或安装陌生根证书。开发排查也要用受控账号和必要数据，不能把能抓包解释为线上使用 HTTPS 没有价值。

## 追问：TLS 1.3 的 0-RTT 为什么要防重放？

1. 早期数据在完整的新握手确认之前发送，协议对它的重放保护不等同于普通握手后的数据。攻击者可能重放捕获的早期请求，所以即使内容加密了，服务端仍可能重复看到某个操作。

2. 对于查询类请求，可以按实际语义判断是否适合；创建订单、转账等操作不能简单接受重复执行。服务端需要拒绝不合适的早期请求，或者结合可靠的业务幂等设计，而不是只看请求方法的名字。

3. 作为前端，我会把它理解为协议优化有适用边界，不会在 fetch 中随意承诺开启 0-RTT。最终要由基础设施与服务端配置，并验证业务重复请求时的结果，不能只比较一次连接的速度。
