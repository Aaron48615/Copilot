# 城市视图中的地图和 3D 数据柱是怎么实现的？遇到性能问题怎么办？

## 核心回答

1. 地图使用高德 JS API，初始化时加载脚本并创建实例，再根据城市列表绘制 marker、AQI 圆圈和信息窗。实例与覆盖物放 ref，城市或环境模式变化时更新对应对象，卸载再清理，不能在每次 React 渲染中重新创建整张地图。

2. 3D 页面使用 React Three Fiber，以 React 组件方式组织 Three.js 场景。用户切换人口、面积或 GDP，城市柱体根据当前指标改变高度，支持旋转与悬停查看原始值；地图与 3D 是不同展示模块，不能当成同一个地图图层来介绍。

3. 当前柱高用当前值除以最大值，再乘 4.8 加 1.2，控制展示尺度。颜色按排序后的索引从固定数组取色，主要区分柱体，不表示数值渐变；加基础高度后也不是严格零基线比例，准确比较仍应看原始值。

4. 性能问题我会先区分脚本加载、接口、React 更新和 WebGL 绘制。首屏很慢可能是资源或初始化，拖动很卡才更可能涉及渲染；先看 Network 与 Performance 的具体表现，再决定减少标记、复用对象或减少高频更新。

5. 当前城市柱仍是独立组件，未做实例化，也没有完整二维降级。若规模增大，我会先限制同时展示数量，再评估聚合点位、InstancedMesh 与按需渲染；实际效果需要在相同城市数量与设备上比较加载时间、帧率和内存，再决定是否保留优化。

## 追问：地图和三维图都能展示城市，为何保留两种方式？

1. 地图适合看空间位置，例如某个事件在哪座城市、周边环境如何，用户能利用地理位置理解关系。三维柱更偏向展示指标大小与交互观察，两者回答的问题不同，不只是视觉风格不同。

2. 3D 也有遮挡和透视问题，远处柱体可能看起来更小，所以精确比较不一定比二维柱状图方便。当前提供悬停原值帮助核对，我不会把可旋转的效果直接说成更准确或更专业的数据分析。

3. 如果继续设计，我会让用户按任务选择视图，并保留二维图表或表格作为准确比较入口。要证明三维有价值，需要看用户是否更容易完成查看任务，而不是只展示一个动画就认定体验更好。

## 追问：为什么 3D 动画不适合每帧调用 setState？

1. React 状态变化会进入组件更新过程，而柱体缩放这类逐帧变化可以直接修改 Three.js 对象。每帧都 setState 会增加不必要调度，尤其柱体多时容易把动画工作和页面业务更新混在一起。

2. 当前在 useFrame 中根据 delta 推进 group 的缩放，指标切换仍通过正常状态更新。delta 表达上一帧经过的时间，让不同刷新率设备上的动画速度更接近，不应该每帧固定增加同样数值就认为速度相同。

3. 若以后启用按需渲染，还要确保动画期间请求后续帧，直接修改对象不会自动让所有框架状态知道变化。优化不能只改 frameloop 参数，还要验证旋转、动画和悬停是否仍持续更新。
