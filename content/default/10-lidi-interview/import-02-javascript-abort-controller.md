# AbortController 取消 fetch 后 Promise 会怎样？

## 核心回答

1. 我会先创建控制器，把它的信号传给请求，再在离开页面或新查询开始时调用取消。对于还没完成的请求，取消通常会让返回的 Promise 进入拒绝状态，拒绝原因来自取消信号；没有传入自定义原因时，默认原因是名为 AbortError 的异常。

2. 这里要区分拿到响应头和读完响应体两个阶段，不能说调用取消后原来的 Promise一定变成失败。如果请求已经成功返回响应对象，那个 Promise不会再改变状态，但还在进行的响应体读取仍然可能因为取消而失败。

3. 错误处理里我会结合本轮信号与取消原因，区分主动结束、超时和真实网络故障，避免用户正常切换页面却收到报错。也不能把所有异常都吞掉，服务端错误状态还要单独检查响应状态，因为它通常不会让请求自动拒绝。

4. 取消主要影响客户端正在进行的工作，不保证服务器没有收到请求，更不能回滚已经写入的数据。对于搜索，可以配合请求序号过滤旧结果；如果是提交订单，用户取消等待后应查询真实状态，不能直接认定提交失败再重复发送。

## 追问：已经拿到 Response 后再取消会发生什么？

1. 拿到响应对象通常意味着响应头已经可用，并不代表响应体已经全部读取。比如下载较大的数据时，请求的 Promise可以先成功，后面读取正文的 Promise仍然处于等待状态，所以两个阶段要分别观察。

2. 如果正文还在读取，这时取消可能让读取操作拒绝，但不会把先前成功的请求的 Promise改写成失败。若正文早已读取结束，取消也不会删除拿到的数据，我仍需根据任务是否过期决定要不要展示结果。

3. 如果要验证这个边界，我会使用分段发送正文的测试响应，先取得响应对象再触发取消。分别检查请求阶段已经成功、正文读取失败，以及页面没有显示半成品数据，避免只用瞬间返回的小响应测试。

## 追问：取消提交订单后能马上重新提交吗？

1. 不能仅凭客户端收到取消异常就判断订单没有生成，因为服务器可能已经完成写入，只是响应尚未到达。马上重发可能产生重复订单，因此要把取消等待和取消业务操作分开向用户表达，避免给出错误结论。

2. 如果要设计这类流程，我会让一次提交带有稳定的业务标识，并由服务端实施幂等处理。再次查询或重试使用同一标识，而不是每点一次都生成全新的提交身份，这样服务端才能识别同一次操作。

3. 前端可以显示结果确认中的状态，通过订单查询恢复实际进度，再决定是否允许重新提交。真正撤销订单需要独立业务接口并检查订单状态，关闭请求连接只是通信层动作，不能代替撤销流程。
