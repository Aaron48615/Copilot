# AbortController 取消 fetch 后 Promise 会怎样？

## 核心回答

1. 还没完成的 `fetch` 被取消后，返回的 Promise 一般会变成拒绝，原因来自取消信号。没传自定义原因时，默认是名叫 `AbortError` 的异常。控制器要在发请求前建好，把它的 `signal` 传进去，离开页面或新查询开始时再 `abort()`。

2. 拿到响应头和读完响应体是两段。请求已经成功返回 `Response` 对象了，那个 Promise 不会再改成失败；正文还在读的话，取消之后读取仍可能失败。所以不是一点取消，原来那个请求 Promise 就一定失败。

3. 错误要分清主动取消、超时和真的网络故障。用户正常切页面，不该弹报错。也不能把所有异常都吞掉。服务端返回 4xx、5xx 时，`fetch` 往往还是成功拿到响应，得自己看 `response.ok`，不会自动变成拒绝。

4. 取消只管客户端这边正在干的活，不保证服务器没收到请求，更不能把已经写入的数据撤回来。搜索可以靠请求序号丢掉旧结果。提交订单的话，用户取消等待之后，应该去查真实状态，不能直接当成提交失败再点一次。

## 追问：已经拿到 Response 后再取消会发生什么？

1. 拿到 `Response` 通常只说明响应头已经可用，正文未必读完。比如下载比较大的数据，请求那个 Promise 可以先成功，后面 `response.json()` 或读流的 Promise 还在等。两段要分开看。

2. 正文还在读，这时取消可能让读取拒绝，但不会把已经成功的请求 Promise 改写成失败。正文早就读完了，取消也不会把拿到的数据删掉。任务已经过期的话，结果照样不该展示。

3. 要核对这个边界，得用分段往外吐正文的测试响应：先拿到 `Response` 再取消。分别确认请求阶段已经成功、正文读取失败，以及页面没有把半成品数据画出来。瞬间返回的小响应测不出这段。

## 追问：取消提交订单后能马上重新提交吗？

1. 客户端收到取消异常，不能据此认定订单没生成。服务器可能已经写完了，只是响应还没到。马上重发可能做出两单。取消等待和取消这笔业务，对用户要分开说，别给出错误结论。

2. 一次提交带上稳定的业务标识，服务端按这个做幂等。再次查询或重试用同一个标识，别每点一次就生成全新的提交身份，服务端才能认出是同一笔。

3. 前端可以显示「结果确认中」，用订单查询把真实进度找回来，再决定能不能重新提交。真要撤销订单，得走独立业务接口并看订单状态。关掉请求连接只是通信层的动作，替不了撤销流程。
