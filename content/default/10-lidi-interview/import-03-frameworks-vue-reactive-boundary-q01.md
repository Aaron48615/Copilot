# 为什么解构 reactive 会丢响应式？

## 核心回答

1. `reactive` 对象靠代理上的访问来收集依赖。解构一个原始值属性，执行的是当时那一次读取，局部变量里留下普通数字或字符串。之后再用这个变量，不会再走代理，原对象字段变了，它也不会自己跟上。

2. 比如 `state.count` 是 `0`，解构出 `count` 后再给 `state.count` 加一，局部 `count` 还是 `0`。不是整个 `state` 坏了，是新变量已经不再读那个属性。继续写 `state.count`，或用 `toRef` 做出字段引用，关联还在。

3. `toRefs` 把对象现有属性转成对应的 `ref`，解构之后还能跟着原对象。它们不是深拷贝，也不是另一套独立状态，改字段 `ref` 会影响原对象。可选、暂时还不存在的字段，用具体的 `toRef` 或明确的 getter。

4. 解构嵌套对象要看取出了什么。取出来的还是响应式代理，改它内部字段可能仍会更新；父对象把该字段整份换成新对象，局部引用还指着旧的。不是“任何解构都完全不响应”。

5. Vue 3.5 的 `script setup` 对 `defineProps` 解构有编译期响应式转换，这是特定场景。普通 `reactive` 解构不会因此自动修好。先确认版本和来源。跨函数传值时，可能还是要传 getter，别把编译器处理后的局部写法当成普通 JavaScript 规则。

## 追问：toRefs 得到的值是不是可以独立修改而不影响原对象？

1. 不是。`toRefs` 做出的是连着原对象对应属性的 `ref`，不是副本。给 `name.value` 赋值，原对象的 `name` 也会变。它适合解构后还要响应式，不适合做“点取消就丢掉”的独立草稿。

2. 要草稿，按数据结构自己拷一份，初始化、保存、取消时机说清楚。嵌套对象浅拷还可能共享内部引用，草稿编辑照样改到原数据。`toRefs` 解决不了隔离。

3. 用一次具体操作验证：改解构后的字段，原组件该不该立刻变。该变就用引用连着，不该变就建独立草稿。先定业务关系，再选工具，别看哪个写法更短。

## 追问：Vue 3.5 的 props 解构为什么看起来没有这个问题？

1. `script setup` 编译器能认出从 `defineProps` 解构出来的变量，在相应访问里转成对 `props` 的读取。不是普通运行时解构突然有了新能力。普通函数里对 `reactive` 对象解构，还是 JavaScript 的值和引用规则。

2. 这种转换有范围。把解构变量当普通值传给另一个函数，函数拿到的可能只是当前值。要持续跟踪，传 getter，让被调用的逻辑在监听范围内读。编译器不会跨任意函数自动连上。

3. 先看项目实际的 Vue 编译版本。旧项目可以继续写 `props.xxx` 或 `toRef`。迁移时默认值、监听代码也要核对，新文档示例能跑，不代表这个仓库里同一段代码一定跟着更新。
