# 为什么解构 reactive 会丢响应式？

## 核心回答

1. reactive 对象通过代理访问来收集依赖。解构一个原始值属性时，执行的是当时的读取，随后局部变量保存普通数字或字符串；之后使用这个变量不会再次经过代理，所以原对象字段变化不再与它保持自动连接。

2. 例如 state.count 为零，解构得到 count 后再增加 state.count，局部 count 仍是零。这里不是整个 state 失去响应式，而是新变量已经不再读取那个属性；保持 state.count 的访问，或使用 toRef 建立字段引用，都能表达持续关联。

3. toRefs 可以把对象现有属性转换成对应 ref，便于解构后继续跟随原对象。它们不是深复制，也不是另一套独立状态，修改字段 ref 会影响原对象；可选且暂时不存在的字段，需要考虑使用具体 toRef 或明确的 getter。

4. 解构嵌套对象要更细分：如果取出来的本身还是响应式代理，修改它的内部字段仍可能更新，但父对象把该字段整体换成新对象，局部引用仍指向旧对象。不能简单背成“任何解构都会完全不响应”，而应看取出了什么值。

5. Vue 3.5 的 script setup 对 defineProps 解构提供编译期响应式转换，这是特定场景的能力，不代表普通 reactive 解构也自动修复。阅读代码先确认版本和来源，跨函数传值时仍可能需要 getter，避免把编译器处理后的局部写法误当普通 JavaScript 规则。

## 追问：toRefs 得到的值是不是可以独立修改而不影响原对象？

1. 不是，toRefs 生成的是与原对象对应属性连接的 ref，不是副本。给其中 name.value 赋值，会更新原对象的 name；它适合保持响应式的解构，不适合用来建立“点击取消就丢弃”的独立编辑草稿。

2. 如果需要草稿，应按数据结构创建独立副本，并明确初始化、保存和取消时机。嵌套对象还要避免浅复制后共享内部引用，否则草稿编辑仍可能改变原数据，使用 toRefs 并不能解决这种隔离问题。

3. 我会用一个具体操作验证：修改解构后的字段，原组件是否应该立刻变化。应变化就用引用连接，不应变化就建立独立草稿，先决定业务关系，再选择响应式工具，避免只根据哪个写法更简短来判断。

## 追问：Vue 3.5 的 props 解构为什么看起来没有这个问题？

1. script setup 编译器能识别从 defineProps 解构的变量，在相应访问中转换成对 props 的读取，因此不是普通运行时解构突然获得新能力。普通函数中的 reactive 对象解构仍然遵循 JavaScript 的值和引用规则。

2. 这种转换还有使用范围和传参边界。把解构变量直接作为普通值传给另一个函数，函数拿到的仍可能只是当前值；需要持续跟踪时，可以传 getter，并由被调用逻辑在监听范围内读取，不能期待编译器跨任意函数自动连接。

3. 我会确认项目实际 Vue 编译版本，再使用这个写法，旧项目可以保留 props.xxx 或 toRef。迁移时也要检查默认值和监听代码，不能只看到新文档示例就断言原项目里相同代码一定会响应式更新。
