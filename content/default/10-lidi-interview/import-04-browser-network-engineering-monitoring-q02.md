# 监控数据很多时怎么控制成本？

## 核心回答

1. 控制监控成本，我会先把错误、性能和普通行为分开考虑。严重错误和新版本回归需要较高可见度，重复点击或普通性能样本可以采样；如果所有数据都按同一比例丢弃，可能刚好漏掉低频但影响很大的问题。

2. 重复错误可以按规范化堆栈、版本和路由聚合，再保留发生次数与代表样本。不能只记录第一次后把后续都丢掉，否则平台看不出从偶发变成大面积故障；分组也要避免把不同根因的错误粗暴合在一起。

3. 采样最好保留采样率和来源维度，按会话或用户稳定抽样有时更容易理解完整过程。计算错误率时分子分母要采用一致口径，不能拿采样后的错误次数除以全量访问数，让结果看起来异常优秀。

4. 客户端设置单次载荷、批量发送和频率上限，服务端控制存储期限与索引。批量不能无限等待，离开页面时也要考虑发送；但关键错误不宜全依赖退出阶段，浏览器并不保证每次都能完成最后一次网络请求。

5. 如果继续完善，我会观察数据量、有效问题数和告警质量，逐步调整采样，而不先砍掉所有长尾记录。新版本或重点故障可以临时提高采集比例，确认结束后恢复，避免长期诊断开关带来意外费用。

## 追问：错误去重后，怎样保留故障规模信息？

1. 我会把问题分组和发生统计分开。相同根因归到一个问题组里，但持续记录发生次数、受影响会话数、时间分布和版本，这样既不会生成几万个重复工单，也能看出问题是否正在扩散。

2. 每组保留少量具有差异的样本，例如不同浏览器或关键路由，避免所有样本都来自同一环境。错误消息中的动态编号要规范化，但不能去掉决定根因的区别，否则两个不同问题会被合并后误导排查。

3. 验证时模拟同一错误连续发生和两种相似错误，确认聚合数准确且分组合理。告警可以基于影响比例和新增趋势，而不是单纯按样本条数，防止采样配置变化后平台突然误报或漏报。

## 追问：采样会不会让性能分位数失真？

1. 会有这个风险，尤其是只上传慢请求或只采某类设备时，样本就不代表总体。即使随机采样，样本量过少也会让分位数波动，因此需要明确数据代表哪些用户，而不是直接给出一个精确数字。

2. 我会记录采样策略，并按设备、路由和网络条件检查覆盖。若关键路径使用更高采样率，计算总体指标时必须考虑不同层的比例，不能把各组样本直接混合后当成所有访问的真实分布。

3. 调整策略前后保留可比较的口径，必要时用小范围更完整的数据校验。指标突然变好时先看是否改了采样或过滤规则，再判断代码是否改善，避免把采集方式改变当成优化成绩。
