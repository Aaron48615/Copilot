# infer 和条件类型应该解决什么问题？

## 核心回答

1. 条件类型用来描述：输入长什么样，输出就该是什么样。比如输入符合某种结构，就抽出对应字段，否则给另一种结果。它比的是类型能不能赋值，不是浏览器里跑 `if`。适合少写重复声明，替不了真实业务判断。

2. `infer` 是在条件类型匹配结构时，给某一截起个临时类型名字。比如 `T extends Promise<infer U> ? U : T`，抽出一层结果。外面结构变了，依赖它的辅助类型跟着变，不用手工再维护一份具体类型。

3. 用之前先看有没有现成工具，比如提取函数返回类型，或者「等异步结果之后」的类型，通常不必自己再造一套。抽一层，和递归把嵌套等待都展开，不是同一个需求。联合输入、只读数组也要看匹配范围，名字起得很通用、实现很窄，后面会踩。

4. 适合用它的前提是：输入输出关系确实反复出现，别人也能看懂规则。业务对象已经很明确，直接写类型更好维护。多层嵌套、递归的话，拆出有含义的名字，边界用例对着看。别为了少写几行声明，搞得调用报错看不懂。

## 追问：提取一层 Promise 与 Awaited 有什么不同？

1. 简单匹配 `Promise` 结构取出内部类型，只抽一次。里面还是异步结果结构，就不会再往下拆。`Awaited<T>` 描述的是等完之后的类型关系，嵌套还能继续处理。拿一个浅例子就说两者完全一样，不对。

2. `Awaited<T>` 还考虑符合约定的可等待对象，以及联合输入，范围比只检查原生 `Promise` 结构更宽。函数有时直接返回数字，有时返回异步数字，想要最终的数值类型，用现成工具更贴意图。

3. 这些都是静态推导，不会真的等网络请求，也不会验异步结果里字段对不对。同步值、普通 Promise、联合输入分别做类型检查，把工具吃得下哪些输入说清楚，别把类型名当成运行时功能。

## 追问：为什么提取重载函数返回类型可能比预期宽？

1. 从带多条调用签名的函数类型推断返回类型，看的是最后那条签名，不会去模拟某次实际调用选了哪条重载。最后那条通常写得更宽，得到的结果也可能是联合类型。

2. 比如一条重载：字符串进、数字出；另一条：数字进、字符串出；最后再声明一条把两者都包进去的宽签名。提取整个函数的返回类型，可能得到两种结果的联合。用具体参数去调这个函数，调用表达式仍能拿到较窄的那一种。

3. 业务需要按某种输入精确表达输出，就显式写出输入输出对应关系，或者把重载接口写清楚。别用断言把提取结果强行压窄，关系不清楚就被藏起来了，以后多一种输入特别容易漏。
