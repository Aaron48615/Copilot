# infer 和条件类型应该解决什么问题？

## 核心回答

1. 我会把条件类型理解为描述输入类型与输出类型关系的工具，例如输入符合某种结构时提取对应字段，否则给出另一种结果。它比较的是类型能否赋值，不是在浏览器里执行条件判断，所以适合减少重复声明，而不是替代真实业务逻辑。

2. 类型推断关键字可以在条件类型匹配结构时给某个部分起一个临时类型变量，例如 `T extends Promise<infer U> ? U : T` 提取一层结果。这样不必手工维护外部结构里的具体类型，原始类型变化时，依赖它的辅助类型也能跟着变化。

3. 实际使用前我会先查是否已有标准工具，例如提取函数返回类型或者描述等待异步结果后的类型，通常不需要重新造一套。简单提取一层与递归处理等待结果不是同一个需求，遇到联合输入和只读数组时也要检查匹配范围，避免名字通用但实现很窄。

4. 我觉得适合使用它的前提是输入输出关系确实重复出现，而且其他人能看懂规则，业务对象已经很明确时直接写类型更容易维护。如果需要多层嵌套和递归，我会拆出有含义的名字并验证边界，不会为了减少几行声明让调用报错变得难以理解。

## 追问：提取一层 Promise 与 Awaited 有什么不同？

1. 简单匹配 Promise 结构并取出内部类型，只完成一次结构提取，如果内部仍然是异步结果结构，就不会继续展开。Awaited<T> 描述的是等待后的类型关系，能够继续处理嵌套情况，所以不能仅凭简单示例就认为两者完全等价。

2. Awaited<T> 还考虑符合约定的可等待对象以及联合输入等情况，这比只检查原生 Promise 结构的范围更广。假设一个函数有时直接返回数字，有时返回异步数字结果，我希望得到最终数值类型，使用已有工具更符合意图。

3. 这些仍然都是静态推导，不会真的等待网络请求，更不会验证异步结果里字段是否正确。我会用同步值、普通 Promise 和联合输入作类型检查，把工具适用的输入范围说清楚，避免把类型名称误解成运行时功能。

## 追问：为什么提取重载函数返回类型可能比预期宽？

1. 从具有多个调用签名的函数类型推断返回类型时，会依据最后一个签名进行推断，并不会自动模拟某次实际调用的重载选择。最后的签名通常用于描述更宽的输入输出关系，因此得到的结果也可能是联合类型。

2. 例如一个重载接受字符串返回数字，另一个接受数字返回字符串，最后再声明包含两者的宽签名。提取整个函数的返回类型时可能得到两种结果的联合，而用具体参数调用函数时，调用表达式仍能得到对应的较窄结果。

3. 如果业务需要按某种输入精确表达输出，我会考虑显式写出输入输出映射，或者保留清楚的重载接口。不要用断言把提取结果强行压窄，因为那只会隐藏关系不明确的问题，新增一种输入后尤其容易出现遗漏。
