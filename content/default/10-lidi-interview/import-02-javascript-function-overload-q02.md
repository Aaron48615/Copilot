# 重载怎么避免实现和声明不一致？

## 核心回答

1. 我会先把每种公开调用方式写成明确的输入与输出约定，再实现对应分支。比如示例函数接收字符串时返回长度，接收数字时返回文字，两条重载分别描述这两种关系，不能只写成看起来很丰富的提示。

2. 实现签名需要兼容全部重载，可以用联合参数承接这些输入，但它本身不增加外部可调用的形式。假设公开签名只允许一个或三个参数，即使实现中后两个参数可选，外部也不会因此自动获得两个参数的调用方式。

3. 实现体应该通过类型判断、参数数量或明确的标记字段进行分支，确认输入后再处理。不能用 any 隐藏分支缺失，也不能认为写了重载就会生成运行时校验，编译后的函数仍然只有一份普通实现。

4. 编译器会检查签名兼容性，却不一定证明每个输入都对应正确返回类型。假如实现统一标注字符串或数字的联合返回值，把前面两个分支的返回结果写反仍可能通过，因此还需要验证具体分支行为。

5. 我会分别检查合法调用的推断、非法组合是否被拒绝，以及每个分支实际返回的值和边界。新增重载时同步检查这些项目；如果分支已经难以说明，可以考虑拆成职责清楚的函数，这只是需要评估的调整方案。

## 追问：重载可以编译通过，为什么调用方仍可能拿到错误类型？

1. 假设重载承诺字符串输入返回数字，数字输入返回字符串，而实现签名允许两类输入与两类输出。编译器能够检查实现承接这些签名，却未必建立每个条件分支与某条公开签名之间的严格证明。

2. 如果字符串分支误把原字符串直接返回，它仍属于实现允许的联合返回值，调用方却会按重载把结果当数字。调用方接着使用数字专属方法时才暴露问题，因此编辑器提示正确不是实现正确的充分证据。

3. 对这个例子，我会给两类输入分别验证返回值与运行时类型，并检查空字符串等边界。必要时把分支交给返回类型明确的小函数处理，让检查范围更集中，但仍不能省略对公开输入输出关系的验证。

## 追问：一个或三个参数的重载，怎样防止意外接受两个参数？

1. 对外只声明一个参数和三个参数两种签名，内部实现用可选参数接住两种情况。调用者看到的是公开签名列表，因此正常的类型检查应拒绝两个参数，不能拿实现签名来解释为外部也允许省略任意项。

2. 运行时仍可能有普通脚本或绕开类型检查的调用方，所以如果这是公共边界，实现还应检查参数组合。判断时要依据参数是否提供和取值要求，不能简单用真假判断，否则数字零等合法值可能被误判成缺失。

3. 验证时我会同时保留一个参数和三个参数的成功示例，以及两个参数的编译失败示例。运行时非法输入怎样处理要提前约定，再检查抛错或返回错误的行为，避免声明禁止了但实现悄悄按另一种方式执行。
