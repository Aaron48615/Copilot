# 重载怎么避免实现和声明不一致？

## 核心回答

1. 每种公开调用方式先写成明确的输入与输出约定，再实现对应分支。示例函数：收字符串返回长度，收数字返回文字。两条重载分别描述这两种关系，别只写成看起来很丰富的提示。

2. 实现签名需要兼容全部重载，可以用联合参数承接这些输入，但它本身不增加外部可调用的形式。公开签名只允许一个或三个参数，即使实现里后两个参数可选，外部也不会因此自动获得两个参数的调用方式。

3. 实现体通过类型判断、参数数量或明确的标记字段做分支，确认输入后再处理。别用 `any` 把缺失的分支藏起来。写了重载也不会生成运行时校验，编译后的函数仍然只有一份普通实现。

4. 编译器会检查签名兼不兼容，却不一定证明每个输入都对应正确返回类型。实现统一标注「字符串或数字」的联合返回值，前面两个分支返回结果写反了仍可能通过。具体分支行为还得验。

5. 合法调用的推断、非法组合会不会被拒绝、每个分支实际返回的值和边界，分开查。新增重载时这些项目同步过一遍。分支已经说不清楚，可以考虑拆成职责清楚的函数，这只是要评估的调整方案。

## 追问：重载可以编译通过，为什么调用方仍可能拿到错误类型？

1. 重载承诺字符串输入返回数字、数字输入返回字符串，实现签名却允许两类输入与两类输出。编译器能检查实现承接这些签名，未必建立每个条件分支和某条公开签名之间的严格证明。

2. 字符串分支误把原字符串直接返回，它仍属于实现允许的联合返回值，调用方却会按重载把结果当数字。接着用数字专属方法时才暴露问题。编辑器提示正确，不是实现正确的充分证据。

3. 两类输入分别验证返回值和运行时类型，空字符串这些边界也要看。必要时把分支交给返回类型明确的小函数处理，检查范围更集中。公开的输入输出关系，还是不能省略验证。

## 追问：一个或三个参数的重载，怎样防止意外接受两个参数？

1. 对外只声明一个参数和三个参数两种签名，内部实现用可选参数接住两种情况。调用者看到的是公开签名列表，正常的类型检查应拒绝两个参数。别拿实现签名解释成外部也可以省略任意项。

2. 运行时仍可能有普通脚本，或绕开类型检查的调用方。这是公共边界的话，实现还应检查参数组合。判断时看参数有没有提供、取值合不合法。别简单用真假判断，数字零这类合法值可能被误判成缺失。

3. 同时留着一个参数、三个参数的成功示例，以及两个参数的编译失败示例。运行时非法输入怎么处理提前约定，再检查抛错或返回错误的行为。别声明禁止了，实现却悄悄按另一种方式执行。
