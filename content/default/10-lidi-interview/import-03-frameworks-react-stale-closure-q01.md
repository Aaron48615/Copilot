# setInterval 怎么读取最新计数？

## 核心回答

1. 定时器回调是在某次渲染中创建的，它会捕获那次渲染的计数。若空依赖 Effect 里写 setCount(count + 1)，而初始 count 是零，后续每次触发可能都提交一，问题不在定时器停止了，而在它一直计算相同的旧值。

2. 只需要基于上一个计数递增时，最直接的是函数式更新，例如 `setCount(c => c + 1)`。React 处理更新队列时把待更新状态传给函数，所以回调不需要直接读取外层 count，也不必为每次计数改变重建定时器。

3. Effect 建立 interval 后要返回清理函数，卸载时清掉对应编号。如果间隔由 props 决定，间隔仍应作为依赖，变化后清除旧定时器再建立新的；函数式更新并不是把所有依赖都变得不重要。

4. 若回调除了递增还要读取最新配置，比如当前步长，需要再明确读取方式。可以把配置列入依赖重建，也可以根据版本和用途使用 Effect Event 或同步后的 ref，不能认为函数式更新自动刷新了闭包中所有变量。

5. 我会检查暂停、恢复、重置和快速切换间隔的行为，确认没有多个定时器同时运行。计时还不等于精确时钟，后台标签页可能限制定时器；倒计时若有时间准确性要求，应根据截止时间计算剩余量，而非只数回调次数。

## 追问：把 count 加入依赖也能递增，为什么通常不优先这样写？

1. 这样能让新回调捕获新计数，但每次计数变化都会清除并重新安排定时器。对于简单自增，它增加了不必要的建立和释放，也让定时节奏跟组件更新关联，逻辑比函数式更新更难直接看懂。

2. 如果除了 interval 还有按钮频繁修改计数，每次修改都可能重置下一次触发时间。用户不断点击时，自动计数的节奏可能被推迟；函数式更新让定时器生命周期与计数值本身分开，更符合持续计数的目的。

3. 依赖重建并非永远错误，比如业务要求计数变化后重新开始等待，就可能是有意设计。面试时我会先说明需求，再选择方式，而不是把任何有 count 依赖的定时器都认定为错误代码。

## 追问：倒计时用每秒减一，为什么切到后台后时间不准？

1. 浏览器定时器不是严格的实时调度，后台页面可能被节流，主线程忙也会延迟回调。每次执行减一统计的是执行次数，和现实经过的秒数并不始终一致，所以返回页面时可能比真实时间剩得更多。

2. 可以保存服务端或本地确定的截止时刻，每次触发根据当前时间重新计算剩余量。定时器主要负责刷新显示，页面重新可见时也立即重新计算，而不是期待补跑所有错过的 interval 回调。

3. 涉及订单有效期等业务时，最终是否过期仍由服务端判断，客户端时钟也可能不准确。前端倒计时提供提示，提交时需要处理已经过期的响应，不能只因为屏幕还显示几秒就断言操作一定有效。
