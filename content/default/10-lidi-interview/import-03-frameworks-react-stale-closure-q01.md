# setInterval 怎么读取最新计数？

## 核心回答

1. 定时器回调是某一次渲染里创建的，抓住的是那一次的计数。空依赖 Effect 里写 `setCount(count + 1)`，一开始 count 是 0，后面每次触发可能都提交 1。定时器没停，它一直在用同一个旧值做加法。

2. 只要在上一个计数上加一，最直接是函数式更新：`setCount(c => c + 1)`。React 处理更新队列时会把待更新的状态传进这个函数，回调就不必直接读外层的 `count`，也不必每次计数一变就拆掉重建定时器。

3. Effect 建了 interval，要返回清理函数，卸载时把这个编号清掉。间隔由 props 决定，间隔仍要进依赖，变了先清旧的再开新的。函数式更新不是让所有依赖都变得无所谓。

4. 回调除了加一还要读最新配置，比如当前步长，读取方式要另说。配置可以进依赖，变了就重建；也可以按版本用 Effect Event，或同步到 ref 再读。函数式更新不会自动刷新闭包里别的变量。

5. 暂停、恢复、重置、快速改间隔，确认没有好几个定时器同时在跑。计时不等于精确时钟，后台标签页可能限制定时器。倒计时要准，按截止时间算剩余量，别只数回调跑了几次。

## 追问：把 count 加入依赖也能递增，为什么通常不优先这样写？

1. 这样新回调能抓到新计数，但每次计数一变就会清掉定时器再安排一次。简单自增没必要这样建了又拆，节奏还会跟组件更新绑在一起。函数式更新更直。

2. 除了 interval，按钮还在频繁改计数，每次改都可能把下一次触发时间重算。用户连点时，自动计数的节奏会被往后推。函数式更新让定时器活多久跟计数值本身分开，更符合一直在数的目的。

3. 依赖重建不是永远错。业务就是计数一变就要重新等一轮，那可能是有意的。先说清楚需求再选写法。有 `count` 依赖的定时器，不等于一定写错了。

## 追问：倒计时用每秒减一，为什么切到后台后时间不准？

1. 浏览器定时器不是严格按墙上时钟排的。后台页面可能被节流，主线程忙也会把回调往后拖。每次减一统计的是执行次数，跟现实过了几秒不一定对得上。回到前台时，屏幕上剩的可能比真实时间更多。

2. 保存服务端或本地定好的截止时刻，每次触发用当前时间重算剩余量。定时器主要负责刷新显示。页面重新可见时也立刻重算一遍，别指望错过的 interval 会补跑。

3. 订单有效期这类，过没过期最终还是服务端说了算，客户端时钟也可能不准。前端倒计时是提示。提交时要处理已经过期的响应。屏幕上还显示几秒，不能断言这次操作一定有效。
