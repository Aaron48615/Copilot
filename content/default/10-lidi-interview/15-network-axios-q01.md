# 常见 HTTP 状态码怎么理解？

## 核心回答

1. 我会先按状态码类别判断请求处于什么结果：2xx 是成功，3xx 与重定向或缓存验证有关，4xx 表示客户端请求相关的问题，5xx 表示服务端处理失败。具体提示还要结合响应内容和接口约定，不能只按第一位数字统一弹窗。

2. 200 表示请求成功，201 表示创建了资源，204 表示成功但没有响应内容。比如删除操作返回 204 时，前端可以更新列表，但不应该继续按 JSON 响应体读取业务字段。

3. 400 常见于请求格式或参数不符合要求，401 表示缺少有效认证凭据，403 表示服务器理解请求但拒绝执行。403 不保证用户一定已经登录，具体是权限、策略还是其他限制，要结合服务端约定确认。

4. 404 表示未找到资源，也可能用于隐藏资源是否存在；409 常用于状态冲突，比如提交时数据已被别人修改。429 表示请求过于频繁，前端应限制重复操作，并在适用时参考 Retry-After 安排重试。

5. 500 是服务端内部错误，502、503、504 则要进一步区分网关上游响应异常、暂时不可用和等待上游超时。我会保留脱敏后的请求标识及发生时间辅助排查，同时区分 HTTP 失败和“200 但业务失败”，避免把两者都叫网络错误。

## 追问：收到 401 和 403，前端处理有什么不同？

1. 收到 401 时，我会按认证方案判断是否需要重新登录或尝试刷新凭据。刷新接口本身失败就不能无限刷新，多个请求同时过期时也要协调处理，避免短时间弹出多个登录提示。

2. 收到 403 时，不应该默认清除登录信息，因为重新登录未必能解决问题。可以显示无权访问的说明，保留当前有效会话，并根据返回的明确业务信息判断是否需要申请权限。

3. 页面隐藏按钮只能改善交互，真正的操作权限仍要由服务端检查。无论状态码如何约定，我都会确认页面能处理手动输入地址、权限被临时收回等情况，不能只测试从正常菜单进入。

## 追问：接口返回 200，为什么业务仍然可能失败？

1. HTTP 状态表达的是协议层结果，一些接口把业务执行结果放在响应体的 code 字段。比如服务器正常返回 JSON，但内容说明库存不足，前端不能因为请求进入成功分支就提示下单成功。

2. 我会先看接口约定，明确哪些响应体结构代表成功，再在公共请求层或接口适配层统一识别。文件下载或第三方接口不一定有同样的 code 结构，需要允许它们采用自己的解析方式。

3. 排查时要同时记录 HTTP 状态和业务码，但日志不能直接包含密码或完整令牌。业务失败是否重试取决于原因，库存不足通常需要调整商品选择，不应该自动重复提交同一请求。
