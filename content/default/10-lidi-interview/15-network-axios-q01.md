# 常见 HTTP 状态码怎么理解？

## 核心回答

1. 先按类别看请求处在什么结果：2xx 是成功，3xx 跟重定向或缓存验证有关，4xx 表示客户端请求相关的问题，5xx 表示服务端处理失败。具体提示还要结合响应内容和接口约定，别按第一位数字统一弹窗。

2. 200 表示请求成功，201 表示创建了资源，204 表示成功但没有响应内容。比如删除操作返回 204，前端可以更新列表，但不该继续按 JSON 响应体去读业务字段。

3. 400 常见于请求格式或参数不符合要求。401 表示缺少有效认证凭据。403 表示服务器理解请求但拒绝执行。403 不保证用户一定已经登录，具体是权限、策略还是别的限制，得结合服务端约定确认。

4. 404 表示没找到资源，也可能用来隐藏资源在不在。409 常用于状态冲突，比如提交时数据已经被别人改了。429 表示请求过于频繁，前端应限制重复操作，适用时参考 `Retry-After` 安排重试。

5. 500 是服务端内部错误。502、503、504 还要再分：网关上游响应异常、暂时不可用、等上游超时。留下脱敏后的请求标识和发生时间辅助排查。HTTP 失败，和「200 但业务失败」，别都叫网络错误。

## 追问：收到 401 和 403，前端处理有什么不同？

1. 收到 401，按认证方案判断要不要重新登录，或尝试刷新凭据。刷新接口本身失败就不能无限刷。多个请求同时过期时也要协调，别短时间弹出好几个登录提示。

2. 收到 403，别默认清登录信息，因为重新登录未必能解决问题。可以显示无权访问的说明，保留当前有效会话，再根据返回的明确业务信息判断要不要去申请权限。

3. 页面隐藏按钮只能改善交互，真正的操作权限仍要服务端检查。不管状态码怎么约定，手动输入地址、权限被临时收回这些情况，页面都得能处理。别只测从正常菜单进去。

## 追问：接口返回 200，为什么业务仍然可能失败？

1. HTTP 状态表达的是协议层结果。有的接口把业务执行结果放在响应体的 `code` 字段。比如服务器正常返回 JSON，内容却说库存不足。请求进了成功分支，也不能提示下单成功。

2. 先看接口约定，明确哪些响应体结构代表成功，再在公共请求层或接口适配层统一识别。文件下载或第三方接口不一定有同样的 `code` 结构，允许它们用自己的解析方式。

3. 排查时 HTTP 状态和业务码一起记，日志里别直接带密码或完整令牌。业务失败能不能重试看原因。库存不足通常要用户改商品选择，不该自动把同一请求再提交一遍。
