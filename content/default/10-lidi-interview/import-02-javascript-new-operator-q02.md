# class 和手写构造函数有什么关系？

## 核心回答

1. class 和传统构造函数都建立在 JavaScript 的原型机制上。实例通过原型链找到共享方法，类语法让构造、实例方法和继承关系更集中，所以我会说它们底层有关联，但不能说只是把写法替换一下、所有行为都完全相同。

2. 普通构造函数通常通过 `this` 初始化实例，再把共享方法放到它的 `prototype` 上。class 则把初始化写在构造器中，常规实例方法定义在类的原型对象上；假设创建多个商品实例，这些实例通常共享同一个原型方法，而不是每次复制。

3. 差异之一是 class 必须通过构造调用使用，直接当普通函数调用会抛错，而且类体始终按严格模式执行。类声明也不能在初始化前访问，不能因为传统函数声明可以先调用后声明，就假定类声明有同样的可用时机。

4. 类语法定义的原型方法默认不可枚举，而直接给传统原型赋值的方法通常可枚举。实例字段则属于各个实例，静态方法属于类本身；这些放置位置会影响遍历、共享和调用方式，排查字段找不到时要先确认访问的是哪一层。

5. `extends` 会连接实例方法的原型链，也连接构造器之间的继承关系，方便继承静态成员。派生构造器通常需要先调用 `super()` 再使用 `this`；如果手写继承只处理一个原型对象，或简单调用父类函数，就不能完整代替这些构造语义。

## 追问：原型方法和箭头函数字段该如何选择？

1. 普通实例方法放在原型上，多个实例可以共享同一个函数，适合按对象方法形式调用的行为。箭头函数字段则在每个实例初始化时创建，捕获当前实例的 `this`，把它单独传给事件监听器时，也能保留这个接收者。

2. 代价是每个实例都持有自己的函数，而且同名字段会遮蔽从原型链查找的方法。假设需要大量同类对象，我会优先考虑共享方法；若确实频繁把方法作为回调传递，再评估绑定或箭头字段，不能仅因为写法简短就全部替换。

3. 采用显式绑定时也要保存绑定后的函数引用，尤其是事件移除需要同一个监听器。反复调用 `bind` 会产生不同函数，新增和移除时各绑一次就可能移除失败，所以选择方法形式还要结合实际注册与清理流程。

## 追问：为什么子类构造器里必须先 super 再访问 this？

1. 普通派生类构造器进入时，实例接收者还没有完成初始化，`super()` 会执行父类构造流程并绑定返回的实例。因此在这之前读取或写入 `this` 会报错，不能把它理解成只是建议先调用父类，后面再补也一样。

2. 假设父类负责建立必要字段，子类通常在 `super` 返回后再补充自己的状态。基类构造器运行期间，派生类字段还没有完成初始化，所以父类若调用被子类重写的方法，也要小心该方法访问尚不存在的子类字段。

3. 还有一个边界是派生构造器可以显式返回对象，从而不走通常的实例返回路径，但这不适合作为绕开初始化的常规写法。这样返回的对象可能没有预期原型和字段；面试中我会说明这个例外，同时保持普通继承流程的解释清楚。
