# class 和手写构造函数有什么关系？

## 核心回答

1. class 和传统构造函数都建立在 JavaScript 的原型机制上。实例通过原型链找到共享方法，类语法把构造、实例方法和继承关系写得更集中。底层有关联，但不是把写法换一下、所有行为就完全相同。

2. 普通构造函数通常通过 `this` 初始化实例，再把共享方法放到它的 `prototype` 上。class 把初始化写在构造器里，常规实例方法定义在类的原型对象上。创建多个商品实例，这些实例通常共享同一个原型方法，不是每次复制一份。

3. 差异之一是 class 必须通过构造调用使用，直接当普通函数调用会抛错，类体始终按严格模式执行。类声明也不能在初始化前访问。传统函数声明可以先调用后声明，类声明没有同样的可用时机。

4. 类语法定义的原型方法默认不可枚举，直接给传统原型赋值的方法通常可枚举。实例字段属于各个实例，静态方法属于类本身。这些放置位置会影响遍历、共享和调用方式。字段找不到时，先确认访问的是哪一层。

5. `extends` 会连接实例方法的原型链，也连接构造器之间的继承关系，方便继承静态成员。派生构造器通常需要先调用 `super()` 再使用 `this`。手写继承只处理一个原型对象，或简单调用父类函数，不能完整代替这些构造语义。

## 追问：原型方法和箭头函数字段该如何选择？

1. 普通实例方法放在原型上，多个实例可以共享同一个函数，适合按对象方法形式调用的行为。箭头函数字段则在每个实例初始化时创建，捕获当前实例的 `this`。把它单独传给事件监听器时，也能留住这个实例。

2. 代价是每个实例都握着自己的函数，同名字段还会挡住从原型链查到的方法。大量同类对象时，优先考虑共享方法。真的频繁把方法当回调传出去，再评估绑定或箭头字段。写法短，不能当成全部替换的理由。

3. 采用显式绑定时，也要保存绑定后的函数引用，尤其事件移除需要同一个监听器。反复调用 `bind` 会产生不同函数，新增和移除时各绑一次就可能移除失败。选哪种形式，还要看实际注册和清理怎么做。

## 追问：为什么子类构造器里必须先 super 再访问 this？

1. 普通派生类构造器刚进去时，实例还没有完成初始化。`super()` 会执行父类构造流程并绑定返回的实例。这之前读或写 `this` 会报错。不是建议先调父类、后面再补也一样，顺序是硬性的。

2. 父类负责建立必要字段，子类通常在 `super` 返回后再补自己的状态。基类构造器跑的时候，派生类字段还没初始化完。父类若调用被子类重写的方法，该方法去访问还不存在的子类字段，就会出问题。

3. 派生构造器可以显式返回对象，从而不走通常的实例返回路径，但这不适合当成绕开初始化的常规写法。这样返回的对象可能没有预期原型和字段。普通继承还是先 `super`，再碰 `this`。
