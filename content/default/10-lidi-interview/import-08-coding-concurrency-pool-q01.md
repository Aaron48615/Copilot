# 并发上限为什么不能只用 Promise.all？

## 核心回答

1. Promise.all 本身不是负责启动任务的调度器，它接收可迭代对象并聚合结果。像下面这种写法，是 map 调 request 时把请求全发出去了，等 Promise.all 拿到数组，再想限制启动数量已经晚了。

   ```js
   const running = urls.map(url => request(url));
   await Promise.all(running);
   ```

2. Promise.all 没有 limit 参数，也不会等某个输入完成后再调下一个任务函数。把函数数组直接传给它也不行，普通函数会作为普通值留下来。所以并发限制需要额外逻辑决定何时调用函数，不是换一种方式包装已经存在的 Promise。

3. 并发池要接收还没执行的任务，比如 () => request(url)，先启动不超过上限的几个。每当一个任务结束就补一个，才能在资源限制里持续往前推。任务在传入之前就已经开始，池子最多控制等待，控制不了真实执行数量。

4. Promise.all 仍然可以用在池子内部，等固定数量的 worker 全部完成，这时上限来自 worker 数量。它的结果按输入顺序排，拒绝会让聚合 Promise 提前拒绝，但这不会自动取消其他任务，也不会替你实现失败后停止取任务。

5. 并发数和每秒请求数也不是一回事。最多同时跑三个请求，不代表一秒最多三次。并发上限主要控制同时占用资源的数量；接口还有速率要求，就需要额外控制启动时间，两种约束别混成同一个参数。

## 追问：每批执行 limit 个，再 Promise.all，有什么问题？

1. 分批执行通常能守住并发上限，但会等整批最慢的那个，空出来的位置不能马上用。比如三个任务里两个很快结束，一个还要等很久，下一批仍被挡住。worker 方式则会在前两个结束时继续安排后面的任务。

2. 业务要求一组全部成功后才能进下一组，批次等待反而可能就是正确语义。比如后一步需要本批完整数据，就不能只为了吞吐提前启动。所以先确认批次有没有业务依赖，别一律把分批写法判成错误。

3. 彼此独立的上传或查询，更倾向持续补位，并用一个慢任务加多个可控快任务验证它。还要定义本批失败怎么处理，因为 Promise.all 提前拒绝不代表本批其他请求停了，贸然启动下一批可能把原来的数量估计打乱。

## 追问：浏览器已经限制连接数，为什么还需要并发池？

1. 浏览器的连接安排属于传输层行为，不等于业务请求数限制，尤其不同 HTTP 版本和连接复用方式会影响实际传输。即使部分请求在内部排队，应用也可能已经创建了大量请求对象、准备了上传内容并占着内存。

2. 应用层的池子可以在准备昂贵数据和发送请求之前安排任务，表达自己的资源预算。比如上传任务先读文件再请求，就把读取也放进受控任务里；入队前把所有文件读完，并发上限并没有限制那部分内存开销。

3. 池子也不是越小越好，过小会拖慢完成时间，过大可能给服务加压力。结合任务体积、耗时和接口约定选个起点，再靠实际测量调。上传大文件和查询短文本对带宽占用不同，不适合直接照搬同一个上限。调完还要看超时和失败有没有变多，别只看总完成时间。
