# 并发上限为什么不能只用 Promise.all？

## 核心回答

1. 我会先纠正一个常见说法：Promise.all 本身不是负责启动任务的调度器，它接收可迭代对象并聚合结果。像下面的写法，是 map 调用 request 时把请求全部发出，等 Promise.all 拿到数组，再想限制启动数量已经晚了。

   ```js
   const running = urls.map(url => request(url));
   await Promise.all(running);
   ```

2. Promise.all 没有 limit 参数，也不会等某个输入完成后再调用下一个任务函数。把函数数组直接传给它也不行，普通函数会作为普通值保留下来；因此并发限制需要额外逻辑决定何时调用函数，而不是换一种方式包装已有 Promise。

3. 并发池要接收尚未执行的任务，例如 () => request(url)，先启动不超过上限的几个任务。每当一个任务结束就补一个，才能在资源限制内持续推进；如果任务在传入之前就已经开始，池子最多控制等待，控制不了真实的执行数量。

4. Promise.all 仍然可以用在池子内部，等待固定数量的 worker 全部完成；此时上限来自 worker 数量。它的结果按输入顺序排列，拒绝会让聚合 Promise 提前拒绝，但这不会自动取消其他任务，也不会替我实现失败后停止取任务。

5. 我还会区分并发数和每秒请求数，最多同时运行三个请求，不代表一秒最多三次请求。并发上限主要控制同时占用资源的数量，如果接口还有速率要求，就需要额外控制启动时间，不能把两种约束混成同一个参数。

## 追问：每批执行 limit 个，再 Promise.all，有什么问题？

1. 分批执行通常可以守住并发上限，但会等待整批最慢的任务，空出来的位置不能马上利用。比如三个任务里两个很快结束，一个还要等很久，下一批仍被挡住；worker 方式则会在前两个结束时继续安排后面的任务。

2. 如果业务要求一组全部成功后才能进入下一组，批次等待反而可能就是正确语义。例如后一步需要本批完整数据，就不能只为了吞吐提前启动；所以我会先确认批次有没有业务依赖，而不是一律把分批写法判为错误。

3. 对彼此独立的上传或查询，我会更倾向持续补位，并用一个慢任务加多个可控快任务验证它。还要定义本批失败怎么处理，因为 Promise.all 提前拒绝不代表本批其他请求停止，贸然启动下一批可能打破原来的数量估计。

## 追问：浏览器已经限制连接数，为什么还需要并发池？

1. 浏览器的连接安排属于传输层行为，不等于业务请求数限制，尤其不同 HTTP 版本和连接复用方式会影响实际传输。即使部分请求在内部排队，应用也可能已经创建了大量请求对象、准备了上传内容并占用内存。

2. 应用层的池子可以在准备昂贵数据和发送请求之前安排任务，表达自己的资源预算。比如上传任务先读取文件再请求，就应把读取也放进受控任务里；如果在入队前把所有文件读完，并发上限并没有限制那部分内存开销。

3. 不过池子不是越小越好，过小会拖慢完成时间，过大可能增加服务压力。我会结合任务体积、耗时和接口约定选择起点，再通过实际测量调整；例如上传大文件和查询短文本对带宽的占用不同，不适合直接照搬同一个上限。还要观察调整后是否增加超时和失败，而不只看总完成时间。
