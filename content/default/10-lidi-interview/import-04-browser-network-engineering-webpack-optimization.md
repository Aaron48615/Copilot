# Webpack 层面能做哪些优化？

## 核心回答

1. Webpack 优化我会分构建效率与产物体验，先测哪一部分慢。冷启动、增量更新、生产打包和用户首屏不是同一个指标；给构建开缓存可能缩短开发等待，却不一定减少用户下载或执行的 JavaScript。

2. 构建侧先缩小 loader 处理范围，避免对不需要转译的文件重复处理，同时确认某些依赖确实需要兼容转换。文件缓存和合适的 source map 配置可以减少工作，额外并行也有调度成本，不能无条件增加线程就承诺更快。

3. 产物侧检查生产优化、静态导出分析和压缩，并按真实使用时机拆分页面。大型依赖可以合理共享，但全塞进一个 vendor 也可能让首屏下载很多无关代码，手动分包要结合依赖关系与访问路线，不是看到 node_modules 就统一处理。

4. 长期缓存需要内容 hash 和相对稳定的模块组织，发布时保证 HTML 与资源策略匹配。CDN 能改善分发与缓存，但在 HTTP/2 等环境下不能只用绕过单域并发限制解释它的收益，协议和连接复用需要一起考虑。

5. 我的实践更多来自 Vite 侧的路由懒加载与分包，Webpack 选项会按具体版本核对。如果继续优化，会比较构建耗时、初始资源及关键交互，验证错误映射和旧页面加载，避免只让打包报告变小却增加用户点击后的等待。

## 追问：为什么不能把 node_modules 全排除出转译？

1. 很多依赖已经发布兼容目标环境的代码，排除它们可以节省时间；但也有依赖包含目标浏览器不支持的语法。如果全部排除，应用源码虽然被转换，用户仍可能在依赖文件里遇到语法错误，页面无法启动。

2. 我会根据兼容要求和实际错误定位需要处理的包，采用尽量小的包含范围，而不是两个极端：要么所有依赖都转换，要么任何依赖都不管。还要区分语法问题与缺失 API，转译不能自动解决所有运行时能力。

3. 验证用真实生产产物在目标环境执行，并检查新增依赖的发布格式。开发环境浏览器比较新时容易看不出问题，因此构建速度优化必须建立在兼容行为正确之上，不能为了省几步处理牺牲用户可用性。

## 追问：一个很大的 vendor 包，为什么可能降低缓存收益？

1. 如果把稳定框架和频繁变化的业务依赖都合在一起，其中一部分改变就可能让整个文件内容 hash 改变，用户不得不重新下载全部。公共包也可能包含当前页面根本不用的库，首次访问成本因此增加。

2. 我会按稳定性、使用页面和体积分组，但不追求拆得越细越好。共享关系、运行时代码和加载优先级都会影响实际结果，过多碎片同样增加请求和管理开销，需要看浏览器真正加载了哪些内容。

3. 测试一次只改业务代码，再升级一个依赖，比较哪些资源变化及用户需要重下多少。这样的对照比只看分包名字是否叫 vendor 更有意义，也能发现配置看似稳定但内容每次都变化的问题。
