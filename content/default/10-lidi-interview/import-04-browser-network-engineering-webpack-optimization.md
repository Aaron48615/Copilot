# Webpack 层面能做哪些优化？

## 核心回答

1. Webpack 优化分构建效率和产物体验，哪一部分慢先测出来。冷启动、增量更新、生产打包、用户首屏，不是同一个指标。给构建开缓存可能缩短开发等待，却不一定减少用户下载或执行的 JavaScript。

2. 构建侧缩小 loader 处理范围，别对不需要转译的文件重复处理，同时确认某些依赖确实需要兼容转换。文件缓存、合适的 source map 配置可以少干活。额外并行也有调度成本，无条件加线程不承诺更快。

3. 产物侧检查生产优化、静态导出分析、压缩，并按真实使用时机拆分页面。大型依赖可以合理共享，但全塞进一个 vendor，也可能让首屏下载很多无关代码。手动分包要结合依赖关系和访问路线。看到 `node_modules` 就统一处理，常常过粗。

4. 长期缓存需要内容 hash 和相对稳定的模块组织，发布时保证 HTML 和资源策略匹配。CDN 能改善分发和缓存。在 HTTP/2 这类环境下，只用绕过单域并发限制来解释它的收益，不够。协议和连接复用要一起看。

5. 我的实践更多来自 Vite 侧的路由懒加载和分包，Webpack 选项按具体版本核对。比较构建耗时、初始资源、关键交互，验证错误映射和旧页面加载。只让打包报告变小、用户点击后等待变长，这个优化不划算。

## 追问：为什么不能把 node_modules 全排除出转译？

1. 很多依赖已经发布了兼容目标环境的代码，排除它们能省时间。但也有依赖带着目标浏览器不支持的语法。全部排除，应用源码虽然被转换了，用户仍可能在依赖文件里遇到语法错误，页面起不来。

2. 根据兼容要求和实际错误，定位需要处理的包，包含范围尽量小。两个极端都不合适：要么所有依赖都转，要么任何依赖都不管。还要分清语法问题和缺失 API。转译不能自动补上所有运行时能力。

3. 用真实生产产物在目标环境执行，新增依赖的发布格式也要看。开发环境浏览器比较新时，问题容易看不出来。构建速度优化必须建立在兼容行为正确之上。为了少几步处理牺牲用户可用性，不值。

## 追问：一个很大的 vendor 包，为什么可能降低缓存收益？

1. 稳定框架和频繁变化的业务依赖合在一起，其中一部分一变，整个文件内容 hash 就可能变，用户不得不重新下载全部。公共包里也可能带着当前页面根本不用的库，首次访问成本因此增加。

2. 按稳定性、使用页面、体积分组，但不追求拆得越细越好。共享关系、运行时代码、加载优先级都会影响实际结果。碎片太多同样增加请求和管理开销。看浏览器真正加载了哪些内容。

3. 一次只改业务代码，再升级一个依赖，比较哪些资源变了、用户需要重下多少。这种对照比只看分包名字是不是叫 vendor 更有用，也能发现配置看似稳定、内容每次都在变的问题。
