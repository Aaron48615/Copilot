# connect-src 管什么？

## 核心回答

1. `connect-src` 主要限制脚本能连哪些来源，比如 `fetch`、XHR、WebSocket、EventSource、`sendBeacon`。它管的是连接去向，不是脚本从哪加载。`script-src` 允许加载某个 SDK，不代表这个 SDK 请求的接口也自动被允许。

2. 配置从实际请求地址出发。浏览器请求本站 `/api`，再由服务端代理时，浏览器侧只涉及本站地址。如果浏览器直接打第三方服务，就要评估并明确加上那个来源，HTTPS 和 WSS 这些协议差异也要算进去。

3. 没有单独配 `connect-src` 时，通常会回退到 `default-src` 的限制，所以新接口加上去以后可能突然被拦。WebSocket 对 `self` 的匹配还有实现兼容细节，得按目标浏览器验证，必要时把预期的 WSS 来源写明白，别放开全部地址。

4. 它替代不了 CORS 和后端鉴权。CSP 允许连接之后，响应读取仍可能被 CORS 拦住，服务端照样要验身份。业务接口、消息连接、监控上报要分别测，免得策略看着安全，错误收集却被悄悄切断。

5. 比如接入地图时，脚本、瓦片图片、地理查询接口可能来自不同来源，应分别落到正确指令。只放行查询接口，不会自动允许图片和脚本。按浏览器真实请求建对应表，没用到的第三方来源能撤就撤。

## 追问：同一个接口为什么可能同时受 CSP 和 CORS 影响？

1. CSP 来自当前页面的策略，决定这个页面能不能向目标发起相应连接。CORS 来自目标响应，决定浏览器能不能让页面读跨源响应。它们在不同位置配置，解决的也不是同一件事。

2. 比如页面 `connect-src` 只允许 `self`，请求外部接口可能先被 CSP 拦住。把目标放行之后，对方如果没回合适的允许来源头，仍然会出 CORS 错误。改一处配置，不一定能把整个问题解开。

3. 先读控制台说明，再看有没有真实网络请求和预检记录。这样能把页面策略和服务端跨源规则分开查，不会让后端反复加 CORS 头，却一直忽略浏览器根本没允许发起连接。

## 追问：监控上报被 connect-src 拦截，会怎样发现？

1. 普通 `fetch` 或 `sendBeacon` 形式的监控请求也可能被限制。页面用着正常，错误平台却收不到数据。只依赖这个同样被拦截的上报入口，发现不了问题，所以本地 Console 和网络检查很重要。

2. 预发布时主动触发一个能认出来的测试错误，确认采集端请求出现了，平台上也能看到对应版本的事件。页面退出时的发送方式也要覆盖，常规请求和退出阶段用的实现可能不一样。

3. 配置只放行确定的监控来源，并检查 SDK 会不会向别的域名发数据。对 CSP 违规报告的接收也要单独验证，别把没有报告当成没有违规，最后上线一套实际失明的监控。
