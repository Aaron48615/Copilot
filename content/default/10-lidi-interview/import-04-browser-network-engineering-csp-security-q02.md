# connect-src 管什么？

## 核心回答

1. connect-src 主要限制脚本可以连接哪些来源，例如 fetch、XHR、WebSocket、EventSource 和 sendBeacon。它控制的是连接去向，不是脚本从哪里加载；允许 script-src 加载某个 SDK，不代表 SDK 请求的接口也自动被允许。

2. 配置时我会从实际请求地址出发。浏览器请求本站 /api 再由服务端代理时，浏览器侧只涉及本站地址；如果浏览器直接请求第三方服务，就要评估并明确添加那个来源，同时考虑 HTTPS 与 WSS 等协议差异。

3. 没有单独配置 connect-src 时，通常会回退到 default-src 的限制，因此新增接口后可能突然被拦。WebSocket 对 self 的匹配还有实现兼容细节，需要按目标浏览器验证，必要时显式列出预期的 WSS 来源，而不是放开全部地址。

4. 它不替代 CORS 和后端鉴权：CSP 允许连接后，响应读取仍可能被 CORS 阻止，服务端仍要验证身份。如果继续完善，我会分别测试业务接口、消息连接和监控上报，避免策略看似安全却悄悄切断错误收集。

5. 例如接入地图时，脚本、瓦片图片和地理查询接口可能来自不同来源，应分别落入正确指令。只放行查询接口不会自动允许图片和脚本；我会从浏览器真实请求建立对应表，并检查没有使用的第三方来源能否移除。

## 追问：同一个接口为什么可能同时受 CSP 和 CORS 影响？

1. CSP 来自当前页面的策略，决定这个页面是否允许向目标发起相应连接。CORS 来自目标响应，决定浏览器能否让页面读取跨源响应；它们由不同位置配置，解决的也不是同一件事。

2. 例如页面 connect-src 只允许 self，请求外部接口可能先被 CSP 阻止。放行目标后，若对方没有返回合适的允许来源头，仍然会出现 CORS 错误，因此修改一处配置不一定能解决整个问题。

3. 我会先读控制台说明，再检查有没有真实网络请求和预检记录。这样能把页面策略与服务端跨源规则分开排查，不会让后端反复添加 CORS 头，却一直忽略浏览器根本没允许发起连接。

## 追问：监控上报被 connect-src 拦截，会怎样发现？

1. 普通 fetch 或 sendBeacon 形式的监控请求也可能被限制，页面即使正常使用，错误平台却收不到数据。仅依赖这个同样被拦截的上报入口无法发现问题，所以本地 Console 和网络检查很重要。

2. 我会在预发布主动触发一个可识别的测试错误，确认采集端请求出现，并在平台看到对应版本的事件。还要覆盖页面退出时的发送方式，因为常规请求与退出阶段使用的实现可能不同。

3. 配置只放行确定的监控来源，并检查 SDK 是否会向其他域名发送数据。对 CSP 违规报告的接收也应有独立验证，避免把没有报告误认为没有违规，最终上线一套实际失明的监控。
