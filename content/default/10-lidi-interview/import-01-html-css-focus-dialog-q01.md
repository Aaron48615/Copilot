# 焦点陷阱为什么不能只监听 Tab？

## 核心回答

1. 只监听 Tab 最多处理一部分键盘遍历，不能完整保证模态弹窗的焦点范围。焦点还可能被脚本、自动聚焦、点击或辅助技术操作改变；背景如果仍可交互，用户也可能直接点到后面，所以需要同时处理背景状态和焦点进入、恢复。

2. 即使只看 Tab，也不能简单缓存一份按钮数组然后循环索引。弹窗里的控件可能异步增加、隐藏或禁用，当前列表会变化；Shift+Tab 要反向处理，没有可用控件时也应有稳定落点，例如可程序聚焦的标题，而不是访问不存在的数组项。

3. 嵌套弹窗更加明显。只有最上层应该处理当前焦点限制和 Escape，下面一层不能把焦点又抢回自己。实现时需要明确激活和暂停关系，关闭内层后恢复到外层触发位置，整个过程不能靠两个全局 keydown 监听各自强行纠正。

4. 我会优先用原生模态能力或经过验证的组件，再测试动态内容、程序 focus、反向 Tab 和卸载。自己实现时可结合背景 inert、焦点进入检查与当前可聚焦节点计算，但选择器很难覆盖所有 Shadow DOM 和浏览器细节，不能声称几行监听就完整解决。

## 追问：弹窗里没有可聚焦元素时应该怎么办？

1. 先确认是不是漏了必要的关闭入口，模态弹窗通常需要让用户有明确退出方式。如果只是加载中暂时没有输入或按钮，也应让标题或容器能接收程序焦点，避免焦点继续停在已经不可交互的背景上。

2. 静态标题可以使用 tabindex 为负值，让代码能聚焦它而不把它长期加入普通 Tab 顺序。此时要确保有清楚的弹窗名称和加载说明，用户才知道当前位置以及为什么暂时不能继续填写内容。

3. 后续内容出现后再根据任务安排焦点，不能每次渲染都自动跳到第一个按钮。验证时覆盖加载失败和内容为空的情况，确认仍可关闭或重试；没有可操作元素不应该变成键盘用户被困住的状态。

## 追问：两个弹窗的焦点陷阱互相抢焦点怎么解决？

1. 先把弹窗的激活关系明确下来，只有当前最上层模态弹窗负责约束焦点。内层打开时暂停外层的纠正逻辑，而不是让两个 focusin 监听发现焦点离开后各自拉回，形成来回跳转甚至循环。

2. 关闭内层时，先完成它的清理，再把焦点还给外层中打开它的入口，然后恢复外层管理。外层入口已经不存在时选择附近可操作位置，不能无条件使用最早缓存的节点引用，否则恢复可能失效。

3. 我会测试连续打开两层、逐层 Escape、直接关闭全部以及路由卸载。背景不可交互和滚动锁定也要按层数恢复，避免关闭内层就提前解锁整页，或者最后一层关闭后页面仍然无法滚动。
