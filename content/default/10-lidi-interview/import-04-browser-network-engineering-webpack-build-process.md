# Webpack 的构建流程是怎样的？

## 核心回答

1. Webpack 的构建可以按准备配置、建立依赖图、组织产物和输出理解。启动时读取入口与各项选项，创建 compiler 并注册插件；一次具体编译由 compilation 管理，监听模式中后续更新会再次经历相应编译过程。

2. 从入口出发，Webpack 解析模块引用并定位文件，根据规则运行 loader 做内容转换，再分析依赖并继续处理。并不是所有资源都简单转成一段 JavaScript，例如资源模块可以把文件作为独立资产输出，转换方式取决于配置。

3. 模块与依赖组成图后，还需要决定哪些模块进入初始或异步 chunk。动态导入、共享依赖提取和运行时组织都会影响结果，不能认为每个入口或每个 import 都固定只对应一个最终文件，CSS 和其他资源也可能独立输出。

4. 后续按生产配置进行导出使用分析、压缩等优化，生成资源并通过输出文件系统写入。插件在各阶段通过钩子参与，开发服务器可能使用内存文件系统，因此看不到磁盘 dist 不一定代表没有编译产物。

5. 我主要用过 Vite，遇到 Webpack 问题时会先核对版本与配置，再用最小入口复现，区分依赖找不到、转换失败和输出路径错误。排查时沿配置、模块解析、转换和输出逐步定位，关注第一处有效错误；构建成功后还要验证页面资源路径、接口与懒加载，不能止步于编译日志。

## 追问：module、chunk 和最终资源文件是什么关系？

1. module 是构建系统处理的模块单元，可能来自脚本、样式或其他资源；chunk 是组织模块与加载边界的中间概念。多个模块可以进入同一个 chunk，一个模块也可能通过优化安排被多个页面共享，而不是文件一对一复制。

2. 最终输出的是浏览器能请求的资源，包含 JavaScript、CSS、图片和映射等。一个 chunk 不一定只产出一个文件，样式提取和运行时组织都会改变对应关系，因此不能把 chunk 与磁盘上的 bundle 永远当成同义词。

3. 我会看构建统计里的模块、chunk 和 assets 关联，再解释某个大文件包含什么。分析体积时先确定层级，避免把模块源码大小简单相加当作用户实际下载量，压缩、去重和共享都会改变结果。

## 追问：开发服务器没有 dist，浏览器为什么还能加载代码？

1. 开发中构建结果可以写入内存文件系统，再由开发中间件响应请求，不必每次都落到真实磁盘。浏览器只关心对应 URL 能否返回有效资源，不要求这些内容一定以同名文件存在于项目目录里。

2. 我会先看编译是否成功和开发中间件的公开路径，再检查请求状态。如果某个外部工具必须从磁盘读取产物，需要按需求配置写盘，但不能因为暂时看不到 dist 就反复执行生产构建来掩盖开发路径错误。

3. 验证应直接查看浏览器拿到的资源和更新行为，同时区分开发产物与生产产物。内存编译能运行，不代表正式构建的压缩、缓存和公共路径已经正确，部署前仍要独立测试生产输出。
