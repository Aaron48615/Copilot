# 轻购商品详情里的 SKU 选择是怎么实现的？

## 核心回答

1. 商品详情拿到 skuList 后，当前实现默认选择第一条 SKU，并把列表交给 ActionPanel。商品表示一种产品，SKU 表示具体可购买的规格组合，例如同一款鞋的黑色四十二码，加入购物车时只给商品 ID 还不够明确。

2. 面板会解析每条 SKU 的 properties 字符串，按分号拆属性，再按冒号拆属性名和值，整理成颜色、尺码等选项。这样用户看到的是可点选的规格，而不是一段后端编码字符串。

3. 用户点击属性后更新 selectedProps，再拼出当前组合，与 skuList 中的 properties 做完整匹配。匹配到 SKU 后通过 confirm 事件传回详情页，更新 selectedSku，后续加入购物车和立即购买都使用这个 skuId。

4. 当前字符串比较依赖属性顺序一致，例如颜色在前、尺码在后。相同键值换了顺序也可能匹配失败；如果继续完善，我会把属性解析成规范化键值再比较，或按服务端明确提供的组合标识查找，避免把顺序当业务含义。

5. 另外还需要处理不存在的组合、空 SKU 列表和默认第一条不可售等边界。已有第一条默认选择并不证明库存一定有效，页面可以提前禁用无效组合，服务端在加购与确认订单时仍要校验真实 SKU 和可用数量。

## 追问：颜色和尺码都存在，为什么组合可能不存在？

1. 属性选项通常是所有 SKU 的并集。例如黑色只有四十码，白色只有四十二码，页面分别能看到黑色和四十二码，但不代表黑色四十二码这个完整 SKU 在商品列表里真实存在。

2. 如果继续完善，我会根据已经选择的属性筛出候选 SKU，再判断其余选项是否还能组成有效组合。不能简单把每个属性的全部值都当作始终可选，否则用户最后才发现无法购买，会觉得前面选择被浪费了。

3. 即使组合存在，也要区分是否可售或库存不足。前端的禁用只是帮助选择，最终提交仍使用精确 skuId，由后端重新确认；不能因为选项在页面上亮着，就认定库存已经为当前用户保留。

## 追问：怎样验证规格字符串解析没有误匹配？

1. 我会准备顺序不同但含义相同的属性，例如“颜色:黑;尺码:42”和“尺码:42;颜色:黑”。当前完整字符串匹配存在这个限制，改成规范化比较后，两者应当得到相同的组合判断。

2. 还要测试属性缺失、重复属性名、空值和分隔符异常。若后端允许属性值包含冒号，简单 split 可能切坏内容，需要先确认编码约定；不知道格式时不能在前端凭猜测无限修补解析规则。

3. 最后检查回传的是真实列表里的 SKU，而不是仅根据选项临时拼出来的对象。用户点击加购后，网络请求中的 skuId、数量与面板显示必须一致，这才验证了从展示到购买参数的完整对应。
