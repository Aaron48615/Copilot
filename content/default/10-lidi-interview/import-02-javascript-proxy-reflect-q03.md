# Proxy 能监听所有变化吗？

## 核心回答

1. Proxy 不能自动监听所有变化，它只拦截通过代理对象发生的、已有对应内部操作的访问。最直接的反例是同时保留原对象和代理，直接改原对象不会经过拦截器，所以使用方需要统一访问入口，不能混着修改两种引用。

2. 代理默认只覆盖当前这一层，读取到嵌套对象时，如果返回的仍是原对象，后面的字段修改不会被外层 set 捕获。若要支持深层观察，可以在 get 中按需包装嵌套对象，并缓存原对象到代理的映射，避免重复创建不同代理。

3. 数组需要同时理解下标、长度和遍历之间的关系，例如缩短长度会让部分元素消失。目标数组内部调整不等于每个被删除下标都会经过代理删除拦截，因此要按操作影响通知依赖，不能单靠记录陷阱调用次数推断全部变化。

4. Map 和 Set 的内容通过专门的方法访问，不是普通对象同名属性的读写，直接套通用代理可能遇到内部状态校验失败。把方法绑定回原对象可以解决部分调用问题，却不会自动记录集合元素的变化，还需要专门包装方法。

5. 类的私有字段也有类似边界，代理不天然具备原实例的私有字段身份。我的理解是先明确支持普通对象、数组还是集合，再实现对应规则；读取拦截、依赖收集、更新通知和停止订阅缺一部分，都不能称为完整响应式系统。

## 追问：嵌套对象为什么需要缓存代理？

1. 假设每次读取 state.user 都新建一个代理，两次读取即使对应同一个原对象，引用比较也可能不同。这样用对象做缓存键、比较选中项或移除监听时容易对不上，所以深层包装通常需要保证同一原对象对应稳定代理。

2. 我会考虑用 WeakMap 保存原对象与代理的对应关系，读取嵌套对象时先查缓存，再决定是否创建。这里作为键的是对象；弱引用关系可以避免缓存本身无条件留住已经不再使用的原对象，但不等于自动清理所有订阅关系。

3. 循环引用也是缓存的重要用途，例如 user.self 指回 user，重复访问不应不停创建新的包装层。实现时还要识别已经代理过的对象，并明确浅层模式的边界，避免调用方以为所有嵌套修改都会触发更新，实际只有第一层生效。

## 追问：为什么代理 Map 后调用 get 可能报错？

1. Map 的原生方法会检查调用接收者是否具备集合内部状态，普通代理本身不具备目标 Map 的内部槽。默认转发拿到 get 方法后，以代理作为 this 调用就可能失败，这不是键不存在造成的，而是方法接收者不符合要求。

2. 针对这一点，可以给集合方法做专门包装，在原 Map 上执行操作，但还需要识别读取的是哪个键。否则虽然 get 不报错了，响应式系统仍然不知道哪个计算依赖了这个值，后续更新也就无法准确通知使用方。

3. 写入包装还要区分新增键、覆盖值、删除和清空，因为它们影响的依赖范围不同。比如覆盖已有值未必改变 size，新增键却会影响遍历与数量，所以不能把所有方法简单绑定后，就认为集合观察已经与普通对象完全一致。
