# defer、async、preload 和 prefetch 怎么选？

## 核心回答

1. 我会先区分脚本执行策略和资源获取提示。defer、async 主要影响脚本何时执行，preload、prefetch 主要提示浏览器何时获取资源，它们不是四个可以随意替换的同类开关，用错可能反而拖慢首屏。

2. 外部经典脚本使用 defer 时可以并行下载，文档解析完成后按文档顺序执行，适合有依赖的主逻辑。async 下载完成后尽快执行，不保证多个脚本按文档顺序运行，适合确实独立的脚本；执行本身仍会占主线程。

3. preload 适合当前页面很快就要使用、但可能发现得晚的关键资源，例如经确认的首屏字体或背景主图。需要正确的 as、地址和凭据模式，浏览器才能复用；它只预先获取，不会自动执行脚本或把图片放到页面上。

4. prefetch 更偏向提前获取未来可能使用的资源，例如下一页代码，浏览器可以按资源状况调整或忽略。预测不准会浪费流量，所以我会结合用户意图和访问概率，避免打开首页就把所有路由全预取。

5. 模块脚本默认延后执行，模块资源还可以考虑 modulepreload。具体使用要看版本、浏览器和实际请求图，我会先确定关键资源，再测发现时间及竞争情况；不是加越多提示越快，也不能把懒加载误用到关键首屏图片。

## 追问：第三方统计脚本一定应该加 async 吗？

1. 它常常适合 async，因为主页面通常不应等待统计初始化。但需要确认脚本是否依赖其他全局库，或后续代码是否马上调用它；如果存在顺序要求，直接加 async 可能让故障随下载速度偶发出现。

2. 我会使用 SDK 官方建议的初始化方式，例如先建立轻量队列，真正脚本加载后再消费事件，同时保证失败不阻塞核心业务。脚本本身若执行很重，即使 async 下载，执行时仍可能影响主线程响应。

3. 验证时覆盖加载慢、被拦截和重复初始化，确认页面功能仍然可用。还要考虑 CSP 与隐私要求，不会仅因为它被称为统计脚本就无条件放行来源、收集所有输入或无限重试下载。

## 追问：什么时候宁可不做 prefetch？

1. 用户接下来访问哪个页面很不确定，或者资源很大且命中概率低时，预取容易浪费流量。移动网络和带宽紧张时，它还可能与当前关键内容竞争，所以不能把所有候选页面都提前下载当成默认优化。

2. 我会考虑在用户表现出明确意图时触发，例如桌面鼠标停留某个入口后，再预取相关代码。也要避免把可能有副作用的业务请求当成资源预取，预取的目标应安全且适合缓存，不能提前创建订单等数据。

3. 最终比较下一步访问延迟和未使用流量，保留实际有收益的部分。浏览器也可能不执行提示，功能必须在没有预取时正常工作，不能把它当成页面切换时资源一定已准备好的保证。
