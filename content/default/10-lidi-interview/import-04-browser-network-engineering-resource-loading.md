# defer、async、preload 和 prefetch 怎么选？

## 核心回答

1. 脚本什么时候执行，和资源什么时候去拿，是两件事。`defer`、`async` 主要管脚本执行时机，`preload`、`prefetch` 主要提示浏览器何时获取资源。它们不是四个可以随便互换的开关，用错可能把首屏拖慢。

2. 外部经典脚本用 `defer`，下载可以并行，文档解析完再按文档顺序执行，适合有依赖的主逻辑。`async` 是下完尽快执行，多个脚本不保证按文档顺序，适合确实独立的脚本。执行本身仍占主线程。

3. `preload` 适合当前页面很快就要用、但可能发现得晚的关键资源，比如确认过的首屏字体或背景主图。`as`、地址、凭据模式要对，浏览器才能复用。它只是预先获取，不会自动执行脚本，也不会把图片放到页面上。

4. `prefetch` 更偏向提前拿未来可能用的资源，比如下一页代码。浏览器可以按资源状况调整，也可以忽略。预测不准就浪费流量。结合用户意图和访问概率，打开首页就把所有路由全预取，通常过重。

5. 模块脚本默认延后执行，模块资源还可以考虑 `modulepreload`。具体用不用看版本、浏览器、实际请求图。关键资源先定，再测发现时间和竞争情况。提示加得越多不一定越快。关键首屏图片也不该误用成懒加载。

## 追问：第三方统计脚本一定应该加 async 吗？

1. 常常适合 `async`，因为主页面通常不该等统计初始化。但要确认它是否依赖其他全局库，后续代码会不会马上调用它。有顺序要求，直接加 `async`，故障可能随下载快慢偶发出现。

2. 用 SDK 官方建议的初始化方式，比如先建一个轻量队列，真正脚本加载后再消费事件，同时保证失败不堵住核心业务。脚本本身执行很重，就算 `async` 下载，执行时仍可能拖住主线程。

3. 覆盖加载慢、被拦截、重复初始化，确认页面功能还能用。还要看 CSP 和隐私要求。因为它叫统计脚本，就无条件放行来源、收集所有输入、无限重试下载，不行。

## 追问：什么时候宁可不做 prefetch？

1. 用户接下来进哪个页面很不确定，或者资源很大、命中概率低，预取容易浪费流量。移动网络、带宽紧的时候，它还可能跟当前关键内容抢。所有候选页面都提前下载，不是默认优化。

2. 用户表现出明确意图时再触发更合适，比如桌面鼠标在某个入口停一会儿，再预取相关代码。可能有副作用的业务请求，别当成资源预取。预取目标应安全、适合缓存，别提前去创建订单这类数据。

3. 比较下一步访问延迟和没用上的流量，留下真正有收益的部分。浏览器也可能不执行这个提示，没有预取时功能必须还能用。别把它当成切页面时资源一定已经准备好。
