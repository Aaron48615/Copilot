# 页面白屏的具体排查顺序是什么？

## 核心回答

1. 我会先确认白屏的范围：是所有页面都打不开，还是某个路由、账号或浏览器才出现，以及刷新前后是否一致。先保留出错现场和地址，再看 Console 中最早出现的有效错误，避免被后续连带报错带偏。

2. 接着在 Network 检查 HTML、入口脚本和动态 chunk 是否成功加载，同时看响应类型和内容。脚本请求即使返回 200，也可能实际拿到了登录页或 HTML 回退页面，这时单看状态码发现不了问题。

3. 如果资源正常，我会沿错误堆栈检查路由、组件导入和渲染数据，比如接口还没返回就访问嵌套字段。可以临时缩小到最简单的页面或组件，判断是应用没有启动，还是某个组件渲染时抛错。

4. 如果 Console 没有异常，我还会检查 Elements：根节点是否有内容、容器高度是否为零、是否被 loading 遮罩盖住。有 DOM 但看不见可能是 CSS 或状态逻辑问题，不一定是 JavaScript 崩溃。

5. 修复要对应证据，例如资源版本不一致就处理发布和缓存，数据异常就补充明确的加载、空值和失败状态。错误边界可以限制部分渲染错误的影响，但不能捕获所有事件或异步错误，也救不了入口脚本本身没加载的情况。

## 追问：为什么刚发布后容易出现 chunk 加载失败？

1. 一种可能是用户保留了旧页面，里面引用旧构建的 chunk 文件名，而新发布已经删除了这些文件。点击懒加载路由时才开始下载旧 chunk，所以首页能打开不代表后续页面资源都正常。

2. 我会核对失败 URL、HTML 版本、缓存头和服务器实际文件，确认是否真是版本错配。也要排除路径前缀错误、CDN 缓存和网络故障，不能看到动态导入失败就直接判定是缓存问题。

3. 如果继续完善发布方案，我会考虑入口更新策略、保留旧静态资源和发布切换的一致性。页面可提示用户刷新尝试恢复，但要避免无限自动刷新，并提醒保留未提交的输入，防止恢复动作造成额外损失。

## 追问：没有报错，但页面一直 loading，怎么继续排查？

1. 我会看 loading 由哪些状态决定，再查看对应请求是等待中、失败了，还是根本没有发出。比如只在成功分支关闭 loading，失败后界面就可能一直转圈，这属于状态分支遗漏。

2. 如果请求已经完成，我会在状态更新处设置断点，检查返回结构是否符合判断条件，以及是否存在过期请求修改状态。不能只用一个布尔值模糊表示多个并发请求，否则一个请求失败就可能让界面无法正确结束等待。

3. 还要查看初始化是否在等待不会结束的认证恢复或资源加载 Promise。确认原因后补充超时、失败和重试入口，但不能简单用固定定时器强制隐藏 loading，掩盖关键数据实际不可用的问题。
