# Vue 的 provide / inject 适合放什么状态？

## 核心回答

1. provide 和 inject 适合祖先与后代之间传递共同依赖，避免中间组件层层转交自己并不使用的 props。比如一组表单字段共同使用表单状态、尺寸和校验方法，依赖属于这个表单子树，不需要因此提升到全应用的全局 store。

2. 提供者可以传递普通服务、ref 或 reactive 对象，是否更新取决于传递值本身的响应式关系。提供一个当前数字并不会自动获得后续变化，提供 ref 则保留连接；同名依赖由最近的祖先提供者决定，有利于局部覆盖配置。

3. 我会让状态修改尽量留在提供者，后代读取只读状态并调用明确的方法。比如子字段报告新值，表单提供者统一记录和校验，避免任意后代都能直接修改共享对象，导致很难知道某个字段为什么突然改变。

4. 依赖键可以使用集中导出的 Symbol，减少大型组件组合的名称碰撞，并配合类型定义说明输入输出。必需依赖缺失时要给出清晰反馈，可选依赖才使用有意义的默认值，不能用一个空对象把环境问题推迟成运行时异常。

5. 它不是任意组件通信总线，也不会自动提供持久化、调试时间线或服务端缓存管理。跨页面共享业务状态可以考虑 Pinia，父子关系简单时 props 更显式；选择依据是依赖范围和责任，而不是为了少写几行传参就把所有值都藏进注入环境。

## 追问：为什么表单组件库经常使用 provide 和 inject？

1. 表单项可能隔着布局容器、分栏和自定义包装，直接传递校验、尺寸和禁用状态会让每层布局都认识表单协议。提供者把这些依赖放在表单范围内，后代字段按需读取，中间布局只负责展示即可。

2. 表单还可以提供注册、注销和更新方法，让字段参与整体校验，同时保留明确的修改入口。不是所有字段直接拿到一个可随意改动的大对象，而是通过约定动作报告状态，父级更容易集中处理提交和错误定位。

3. 嵌套表单时，最近的提供者能够建立独立范围，避免内层字段误注册到外层。测试需要覆盖嵌套、条件移除和禁用状态变化，这些场景能说明注入解决的是结构中的依赖传递，而不仅是写法更短。

## 追问：provide 状态为什么通常建议同时提供更新方法？

1. 只提供可变对象虽然方便，但后代修改来源会变多。例如选项组件直接改选中集合，另一个组件又删除其中元素，校验和日志很容易遗漏；提供 select、remove 等方法，可以让规则集中在状态拥有者处。

2. 对外可以提供 readonly 包装，让消费者明确以读取为主，真正变化通过动作发生。比如只允许选择可用商品，检查逻辑写在提供者方法里，调用者不必复制相同判断，也不能无意绕开这条组件层约定。

3. 这仍不是服务端权限防线，浏览器中的只读包装主要帮助代码组织。业务授权仍需接口验证；在前端范围内，它的价值是减少隐式修改并让测试可以围绕动作和结果编写，而不是检查所有后代有没有私自赋值。
