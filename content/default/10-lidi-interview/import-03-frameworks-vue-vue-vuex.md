# Vuex 的核心概念和工作流程是什么？

## 核心回答

1. Vuex 通过 store 管理共享状态，state 保存数据，getter 提供派生读取，mutation 描述同步状态修改，action 组织异步或多步骤行为，module 帮助划分业务范围。它的价值是让多个组件围绕明确的更新入口协作，而不是要求页面所有变量都变成全局状态。

2. 一个常见流程是组件 dispatch 加载用户的 action，action 请求接口，成功后 commit mutation 更新 state，依赖这些状态的组件随后更新。同步简单修改也可以直接 commit，不需要为了走完整流程给每一次赋值都再套一个没有额外作用的 action。

3. mutation 应保持同步，因为状态变化需要与明确的动作记录对应，异步结果应到达后再 commit。否则 mutation 返回之后状态才变化，开发工具和阅读代码的人都难以把结果对应到准确步骤，调试和重放的可预测性会变差。

4. getter 适合计算未完成数量、过滤结果等派生数据，避免重复保存副本；按属性访问与返回函数按参数访问的缓存行为应区分，不能笼统说任何 getter 调用都自动缓存每个参数结果。模块命名空间也要明确，避免多个业务动作同名而误触发。

5. 智服工单项目使用 Vuex 管理登录态、用户信息和字典数据，这些确实具有跨组件共享需求。局部草稿和弹窗开关不必全部放进去；如果继续完善，我会检查退出时的状态重置、请求竞态和模块边界，而新项目是否采用 Pinia 则根据既有环境和维护成本判断。

## 追问：为什么不在组件里直接改 store.state？

1. 直接修改可能让界面变化，但绕过了约定的 mutation 入口，开发工具记录和代码搜索都更难找到来源。多个组件各自改同一字段时，规则也容易分散，状态管理原本希望提供的可追踪性就被削弱了。

2. Vuex 严格模式可以在开发中帮助发现 mutation 外的修改，但它有检查成本，不应只靠运行时兜查。组件应发出明确 commit 或 dispatch，由对应入口校验和更新，让数据变化与业务动作形成可以阅读的对应关系。

3. 我会特别检查表单直接绑定 store 对象的情况，输入可能在不经过 mutation 的情况下改共享数据。可以通过可写 computed 转换成 commit，或先使用本地草稿，保存时统一提交，选择取决于是否需要即时共享和取消编辑。

## 追问：action 请求失败后，store 应该怎么变化？

1. 应明确加载、数据和错误的关系。首次请求失败时可以没有数据并显示错误，后台刷新失败时可以保留旧数据并标记未刷新，不能一律设为空数组，否则用户无法区分确实没有记录和请求没有成功。

2. action 可以在开始、成功和失败时分别 commit 对应状态变化，并把必要的错误结果返回给调用方。并发查询还要判断请求归属，旧请求的失败或 finally 不能覆盖新查询状态，集中到 action 并不会自动解决返回乱序。

3. 涉及登录权限失败时，要清理或隔离不再允许展示的数据，重试也应有明确入口。测试可以按动作检查状态转换和保留规则，既验证失败可恢复，也确认组件离开或账号切换后不会被迟到结果重新填入旧信息。
