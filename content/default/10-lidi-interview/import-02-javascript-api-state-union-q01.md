# 为什么不写 loading、error、data 三个字段？

## 核心回答

1. 三个字段本身并不是不能写，问题在于它们如果互相独立，合法组合就只能靠开发者记住。比如上一次失败留下了错误信息，下一次成功只更新数据，页面便可能同时显示错误和新列表，阅读代码时也难判断哪个才是当前状态。

2. 对于简单请求，我会用状态字段区分未开始、加载中、成功和失败，并让数据只跟成功分支放在一起。这样进入成功分支后就能直接访问结果，进入失败分支就读取错误信息，不需要在每个组件里反复猜测可选字段是否存在。

3. 联合类型也有边界，加载时保留旧数据是合理体验，不能把它一律当成冲突。如果需要后台刷新，我会明确建模正在刷新且带旧数据的分支，或者区分数据状态与请求状态，让页面能表达旧内容仍可看但更新还没完成。

4. 我会根据产品允许的状态决定类型，而不是为了使用联合类型强行删除有效场景，同时用一个更新入口整体替换状态。类型可以约束字段搭配，却不会自动保证请求顺序正确，连续搜索时仍然需要防止旧回调把页面切回旧状态。

## 追问：刷新失败时还想保留旧列表怎么设计？

1. 先确认旧列表是否仍然有参考价值，例如普通商品列表通常可以继续展示，但实时库存不能让用户误认为仍然准确。产品允许保留时，我会明确说明这份内容来自上次成功请求，并让失败提示出现在刷新区域。

2. 类型上可以增加带旧数据的刷新失败分支，同时保存错误原因，和首次加载失败分开处理。前者显示列表及重试入口，后者显示错误占位，组件不必通过数据是否碰巧存在来反推用户应该看到什么。

3. 重新刷新时保留旧内容，成功后整体替换，失败则继续停留在有旧内容的失败状态。测试需要覆盖首次失败和刷新失败两条路径，并检查提示是否清楚区分当前结果与旧结果，避免界面看起来像已经更新。

## 追问：联合类型能阻止从 idle 直接变成 success 吗？

1. 一般的状态联合只能限制每个状态对象的字段形状，不能自动限制状态之间如何跳转。只要成功对象结构合法，代码仍然可以直接赋值，因此我不会把使用联合类型等同于已经实现完整状态机。

2. 如果业务对转换顺序有要求，我会集中处理事件，例如只允许加载中的状态接收本轮成功事件。处理函数同时检查当前状态和请求编号，非法或过期事件不更新页面，调用方就不必各自维护同一套规则。

3. 是否允许直接成功也要看具体需求，例如缓存命中时直接展示成功结果可能完全合理。测试应依据这些业务规则覆盖合法和非法路径，而不是机械要求每次都经过加载动画，否则会增加没必要的等待。
