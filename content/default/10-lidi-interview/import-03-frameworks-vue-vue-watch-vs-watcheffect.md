# watch 和 watchEffect 有什么区别？

## 核心回答

1. watch 显式指定监听来源，例如某个 ref、getter 或一组来源，回调可以得到新旧值，默认不立即执行。它适合明确知道哪几个输入应该触发动作的情况，比如用户编号改变后查详情，回调中其他响应式读取不会自动成为新的监听来源。

2. watchEffect 会先执行一次，通过同步执行期间读取的响应式值自动收集依赖，后续相关值变化再执行。多个条件共同决定副作用时写法比较简洁，但依赖藏在回调读取中，需要避免把不相关展示信息顺手读进去，让请求触发范围意外扩大。

3. 异步 watchEffect 只会跟踪第一个 await 之前同步读取到的依赖，等待后才读取的字段不能指望自动被收集。需要明确的异步触发条件时，我通常倾向 watch，把来源写出来；需要初次执行则设置 immediate，而不是只为少写一行选择隐式依赖。

4. 两者都需要考虑副作用清理，例如查询条件变化使旧请求失效。可以使用回调提供的清理注册方式；Vue 3.5 的 onWatcherCleanup 需要在同步执行阶段注册，不能放在 await 之后。监听自动停止也不等于已经发出的网络任务自动取消。

5. 默认回调时机未必适合读取所属组件更新后的 DOM，需要时可以使用 flush: 'post'。setup 中同步建立的监听通常随组件卸载停止，异步延后创建的监听要另行管理；我会根据来源明确性、新旧值需求和资源生命周期选择，而不是把 watchEffect 当成更高级、可以替代所有 watch 的版本。

## 追问：watch 回调里读了另一个 ref，为什么它变化没触发回调？

1. watch 只跟踪声明的来源，不会因为回调顺便读取另一个 ref 就把它加入来源。这种显式性让触发条件容易判断；例如只监听用户编号，回调读取主题用于提示，主题改变不会自动导致重新查询。

2. 如果另一个值确实决定请求结果，就应该把它加入来源或提供相应 getter。也可以在适合的同步副作用场景使用 watchEffect，但不能只为了省声明把所有读取隐式化，否则以后增加一行日志可能意外扩大请求触发范围。

3. 我会逐个改变会影响结果的条件验证，并确认不相关条件不会重查。选择显式或自动收集依赖，目的是匹配业务触发语义，不是哪个 API 能让回调执行得更多，遗漏与过度依赖都可能造成问题。

## 追问：监听器自动停止了，为什么旧请求还会返回？

1. 停止监听主要阻止它因为后续数据变化再次执行，不会自动撤回回调已经发出的所有外部任务。请求属于网络系统，Promise 也可能仍在继续，组件卸载并不等于这些任务自然结束。

2. 需要在清理中取消支持 signal 的请求，并通过本次执行的有效标记保护结果写入。数据、错误和加载状态都应判断归属，否则旧请求虽然不能再被触发，却可能在结束时影响当前页面或共享状态。

3. 我会用手动完成的模拟请求验证先切换条件再返回旧结果，以及卸载后返回两种情况。测试不能只断言 stop 方法被调用，真正目标是旧任务不再提交不属于当前上下文的结果，这与监听停止是相关但不同的保证。
