# watch 和 watchEffect 有什么区别？

## 核心回答

1. `watch` 显式指定听谁，比如某个 `ref`、getter，或一组来源。回调能拿到新旧值，默认不立即执行。适合清楚知道哪几个输入该触发动作，比如用户编号变了查详情。回调里再读别的响应式值，不会自动变成新的监听来源。

2. `watchEffect` 会先执行一次，靠同步执行期间读到的响应式值自动收集依赖，相关值再变就再跑。多个条件共同决定副作用时写法短。依赖藏在回调读取里，别把不相关的展示信息顺手读进去，请求触发范围会意外变大。也拿不到旧值。

3. 异步 `watchEffect` 只跟踪第一个 `await` 之前同步读到的依赖，等待之后才读的字段，别指望自动被收集。异步触发条件要写明白时，倾向 `watch`，来源写出来；需要初次执行就设 `immediate`。少写一行不是选隐式依赖的理由。`watch` 听 `reactive` 对象默认深层，只想盯某个字段，写成 `() => obj.key` 这种 getter。

4. 两者都要考虑副作用清理，比如查询条件变了，旧请求要失效。可以用回调提供的清理注册。Vue 3.5 的 `onWatcherCleanup` 要在同步执行阶段注册，不能放在 `await` 之后。监听自动停了，已经发出去的网络任务也不会自动取消。组件卸载时监听通常会停，一般不用手动调停止函数。

5. 默认回调时机未必适合读所属组件更新后的 DOM，需要时用 `flush: 'post'`。`setup` 里同步建立的监听通常随组件卸载停；异步延后创建的要另行管理。看来源清不清、要不要新旧值、资源怎么收，再选 API。`watchEffect` 不是更高级、可以替换所有 `watch` 的版本。

## 追问：watch 回调里读了另一个 ref，为什么它变化没触发回调？

1. `watch` 只跟踪声明的来源，回调顺便读另一个 `ref`，不会把它加进来。触发条件因此好判断。只听用户编号，回调读主题用来提示，主题变了不会自动再查一次。

2. 另一个值确实决定请求结果，就把它加进来源，或提供相应 getter。适合的同步副作用也可以用 `watchEffect`。别为了少声明把所有读取隐式化，以后多一行日志，请求触发范围可能被带大。

3. 会影响结果的条件逐个改，确认不相关条件不会重查。显式还是自动收集，对的是业务触发语义，不是哪个 API 能让回调跑得更勤。漏听和听太多都可能出事。

## 追问：监听器自动停止了，为什么旧请求还会返回？

1. 停止监听主要是别再因为后续数据变化执行。回调已经发出去的外部任务，不会因此撤回。请求属于网络，Promise 可能还在继续。组件卸载不等于这些任务自然结束。

2. 清理里取消支持 `signal` 的请求，再用这次执行的有效标记保护写入。数据、错误、加载状态都要判断归属。旧请求虽然不会再被触发，结束时仍可能改到当前页面或共享状态。

3. 用手动完成的模拟请求，验证先切换条件再返回旧结果，以及卸载后返回。不能只断言 `stop` 被调用。真正目标是旧任务不再提交不属于当前上下文的结果。这和监听停止相关，但不是同一件事。
