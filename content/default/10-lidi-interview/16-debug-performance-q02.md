# 你会如何优化首屏性能？

## 核心回答

1. 我会先定义首屏要解决什么问题，是内容出现晚、主要图片出现晚，还是显示后仍然不能操作。然后在相近的设备、网络和缓存条件下用 Network、Performance 和 Lighthouse 观察，不能只比较两次条件不同的分数。

2. 如果入口 JavaScript 太大，可以按路由拆包，把非首屏地图、3D 或复杂图表按需加载。拆包后还要看是否出现连续下载多个模块的瀑布，不能把文件切得越碎就当成优化得越好。

3. 图片要选合适的尺寸、格式和压缩程度，并给出稳定的布局空间。非首屏图片可以懒加载，但主要首屏图片尤其是 LCP 元素应尽早被发现和加载，盲目懒加载反而可能让主要内容更晚出现。

4. 对首屏数据，我会先画清请求之间的依赖关系，独立请求可以并行，有依赖的保留正确顺序。页面能独立展示的区域可以分别加载，避免一个非关键接口拖住整页，也要防止一次性并发过多占用资源。

5. 如果下载不慢但页面仍卡，就要看脚本执行、样式布局和渲染任务，例如一次初始化大量图表或处理很大的列表。如果继续完善，我会按瓶颈选择减少计算或延后非关键工作，并重新测量。前后比较要使用相同设备和数据条件，才能判断变化来自优化还是测试环境差异。

## 追问：Lighthouse 分数变高，就能证明用户体验变好了吗？

1. 分数可以作为实验环境下的参考，但会受到设备、限速、缓存和其他运行任务影响。我会保持条件相近并重复测量，先看具体指标改善是否稳定，不能只拿最好的一次结果做结论。

2. 还要看用户实际操作的页面和阶段，例如首页加载变快，但打开地图或输入搜索时更卡，体验并没有全面改善。实验室数据不能直接代替真实用户在不同设备和网络下的表现。

3. 如果具备数据条件，我会结合真实访问中的 LCP、INP 和 CLS 等指标判断，并关注慢设备上的情况。本地测量主要帮助定位原因，线上数据则反映真实用户的设备和网络分布，两者需要结合看，单次高分不能代表所有用户都变快了。

## 追问：独立请求用了 Promise.all，一个失败会怎样？

1. Promise.all 在其中一个输入 Promise 拒绝后就会拒绝，但其他已经发出的请求不会因此自动取消。它适合结果必须一起使用的情况，不能把提前进入 catch 理解成所有网络工作都停止了。

2. 如果首页的公告和商品列表可以独立展示，我会考虑分别处理状态，或用 allSettled 获取各自结果。这样公告失败时列表仍能显示，同时保留局部错误提示，不必整页都进入失败状态。

3. 并行也有成本，低优先级请求可能争抢带宽或服务端资源。我会先保证关键首屏数据，再分配其他请求的时机；需要取消时还要显式传入取消信号，而不是依赖 Promise 聚合方法帮忙处理。
