# 虚拟列表如何保证可访问性？

## 核心回答

1. 先承认可访问性的限制：未渲染的条目通常不在可访问性树中，读屏器不能凭空读出全部内容。虚拟化适不适合要看任务，如果用户主要是连续阅读长文或用浏览器查找全文，分页或普通文档可能更合适。

2. 语义按实际交互选择，普通内容列表优先使用 ul、li，只有确实是选择控件才采用 listbox 等模式。不能为了支持方向键就把所有卡片都标成 option，因为不同角色会改变读屏器预期，也要求相应的键盘操作。

3. 对只挂载部分内容的列表，可以在适用的条目角色上提供 `aria-posinset` 和 `aria-setsize`，说明它在完整集合中的位置与总数。位置从一开始，总数未知时按规范使用未知值。这能补充信息，但不能让隐藏条目自动被读取。

4. 焦点要和稳定业务 id 关联，不能随节点复用跳到另一条数据。键盘要移动到窗口外时，先调整渲染范围、等待目标挂载，再移动焦点。鼠标滚动导致焦点行离开视口时，可以暂时保留该行，避免焦点落回页面主体。

5. 结合键盘实际走一遍进入、移动、操作和离开列表的过程，再检查读屏器能否理解位置、选中态和加载提示。自动检查只能发现部分语义错误，还需要人工验证。继续完善时提供分页或页面内搜索作为必要的替代入口。

## 追问：aria-posinset 和 aria-setsize 应该填写哪一组数据的位置？

1. 应该描述用户当前浏览的逻辑集合，而不是这次 DOM 切片里的位置。假设筛选后的结果共一百条，窗口显示第五十一到第六十条，那么位置应从五十一开始，总数填一百，不能把当前十条报成全部内容。

2. 已加载二十条但服务端确认总共一百条时，总数仍可以填写一百；若接口根本没有提供总数，就不能用猜测数字冒充事实。对于支持这些属性的角色，未知总数可以用负一表示，位置也必须来自已知的顺序信息。

3. 属性通常放在对应条目上，并与角色要求一致。如果用的是表格或网格，应该检查行列相关的计数和索引语义。过滤、排序或删除后还要同步更新，避免视觉顺序改变了，读屏器却继续读出旧位置。

## 追问：方向键移动到尚未渲染的条目时怎么处理焦点？

1. 先确定这个控件的键盘模式，普通内容列表不必强加方向键导航；对于有该约定的选择列表，维护的是逻辑活动项。按下一项时先计算目标 id 和位置，再请求虚拟列表把它滚入可渲染范围。

2. 采用真实 DOM 焦点时，要等框架提交并拿到目标节点后再 focus，不能只更新索引就认定焦点已移动。等待期间若用户继续按键，还应以最新目标为准，防止较早的异步聚焦把焦点又拉回去。

3. 也可以在适用的复合控件中使用 aria-activedescendant，让 DOM 焦点留在容器上，但被引用的活动节点仍须存在且满足关联要求。两种方式都要保证活动项可见、焦点提示清楚，并让 Tab 可以按约定离开控件。
