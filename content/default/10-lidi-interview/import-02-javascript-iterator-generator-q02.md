# for...of 为什么不能直接遍历普通对象？

## 核心回答

1. `for...of` 读取的是可迭代协议，不是看到对象有属性就逐个取出来。普通对象默认没有可调用的 `Symbol.iterator` 方法，所以直接遍历会报错；数组、字符串和集合等提供了这个入口，因此能够按各自规定的顺序产生值。

2. 如果想遍历普通对象的键值，我会使用 `Object.entries` 得到条目数组，再进行循环。它处理的是对象自身可枚举的字符串键属性，不包含继承属性、不可枚举属性和符号键，因此先要确认这些范围符合实际需求。若业务确实要求符号键，就应另外选择能取得这些键的方式，不能假定条目数组已经包含所有属性。

3. `for...in` 是另一种操作，它枚举字符串键，还可能包含原型链上的可枚举属性，不能简单看成前一种循环的对象版本。处理数据字典时，如果使用它，就要考虑是否通过自有属性检查排除继承来的内容。

4. 也可以为对象实现迭代入口，但应该先定义每一步产出什么，例如只产出值还是产出键值对。假如对象只是一次性配置数据，直接取条目更清楚；如果它本来表示一段连续数据，再提供迭代协议会更自然，也需要约定重复遍历和提前结束的行为。

## 追问：自己实现 Symbol.iterator 时需要返回什么？

1. 这个方法需要返回一个迭代器对象，迭代器有可调用的 `next()` 方法，每次正常返回一个对象，通常写成包含值 `value` 和结束状态 `done` 的形式。这两个字段可以省略，省略 `done` 按未结束处理，省略 `value` 得到 undefined，例如结束时只返回 `{ done: true }` 也可以。循环根据结束状态决定继续消费还是停止，所以不能只返回数组元素，也不能把推进结果直接写成原始数字。

2. 如果希望同一个容器能重复遍历，通常应在每次调用迭代入口时创建独立的遍历状态。把下标直接共享在容器上，可能导致第二次遍历接着第一次的位置走，嵌套循环也可能互相影响，行为会很难预测。

3. 需要时可以用生成器方法表达这个过程，让语言帮助维护暂停位置和结束状态。但生成器对象本身通常是一次性消费的迭代器，遍历完后不会自动重置，容器每次返回新的生成器才便于重复遍历。

## 追问：循环提前 break 时，迭代器会收到什么通知？

1. 对正常取得值后通过跳出语句提前结束的循环，语言会尝试调用迭代器提供的 `return()` 方法，让它有机会释放资源。这个方法不是所有迭代器都必须实现，没有实现时也不能假定外部资源已经被自动清理。

2. 对已经进入相关保护区域的生成器，这种结束过程可以触发清理分支，适合释放它管理的资源。但如果清理代码本身又产出值，生成器未必一次就完全结束，因此清理逻辑应尽量直接完成，而不是继续要求消费者推进。

3. 我也不会把结论扩大成任何异常都会执行相同清理，例如获取下一个结果时迭代器自身抛错，就不能笼统保证循环替它调用结束方法。管理资源的实现仍应考虑自身失败路径，不能只依靠消费者正常提前退出。
