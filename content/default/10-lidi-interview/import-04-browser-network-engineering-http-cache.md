# 强缓存和协商缓存的区别？上线后怎么让用户拿到新版本？

## 核心回答

1. 强缓存通常指缓存还新鲜时直接复用响应。比如 `Cache-Control` 的 `max-age` 还没到期，浏览器不必向服务端验证。协商缓存则会发请求带上验证条件，服务端判断内容没变时回 304，客户端继续用已经有的响应体。

2. 两者可以配合，不是互斥。缓存过期后能不能验证，取决于有没有 ETag、Last-Modified 这类信息。没有合适缓存，或者内容已经变了，就需要下载新响应。304 省的是响应体传输，请求这一趟延迟还在。

3. 上线更新时，JS、CSS 用跟内容相关的 hash 文件名，并长缓存。HTML 负责引用资源，应及时验证或短缓存。新入口引用新文件名，浏览器才能发现新版本。固定入口如果也长期不验证，旧内容会一直留下来。

4. 发布顺序也重要：新资源先就绪，再更新入口，旧 chunk 还要留着。旧页面晚些时候可能触发懒加载，立刻清空旧文件会让正常访问失败。更新不生效时，还要查 CDN 和 Service Worker，别只看源站配置。

5. 缓存策略还要区分公开资源和私人数据，`private`、`no-cache`、`no-store` 含义不一样。验证结合响应头、请求状态和真实操作看缓存行为。普通刷新、强制刷新、开发工具禁用缓存，这几种结果不能混为一谈。

## 追问：用户反馈还是旧页面，怎样逐层定位？

1. 先确认用户实际拿到的 HTML 和资源版本，比如看入口引用的 hash，别只问有没有刷新过。随后看 HTML 响应头、Age 和缓存来源，判断来自浏览器、CDN 还是源站，找出哪一层还在提供旧入口。

2. 再检查有没有 Service Worker。它可能从 Cache Storage 把页面返回来，即使 HTTP 缓存已经失效，结果也不一定变。源站、CDN 和客户端的版本要对上。源站已经更新，不能误判成用户操作不对。

3. 修好之后，用新访问和还停着的旧页面分别验证。强制刷新能帮诊断，但不是发布方案。正常用户不该每次升级都被要求清空数据，更不能因为清缓存有效就跳过真正的策略问题。

## 追问：为什么给所有请求加时间戳不是理想更新方案？

1. 时间戳会改变 URL，确实可能绕开按 URL 区分的缓存，但内容没变的资源每次也会重新下载。浏览器和 CDN 很难复用它们，首屏流量和延迟都会上去，也把入口缓存策略没设计好这件事盖住了。

2. 稳定静态内容交给内容 hash 管理，只有内容改变才换地址。接口要不要新数据，按业务设缓存和验证规则。别在请求拦截器里统一加当前时间，把所有接口原本的缓存能力破坏掉。

3. 排查时临时绕缓存可以当实验，验证结束要恢复合理配置。还得知道 Service Worker 或特殊 CDN 规则可能忽略某些参数。加时间戳也不是在任何缓存系统下都保证有效的万能办法。
