# 强缓存和协商缓存的区别？上线后怎么让用户拿到新版本？

## 核心回答

1. 强缓存通常指缓存仍新鲜时直接复用响应，例如 Cache-Control 的 max-age 尚未到期，浏览器不必向服务端验证。协商缓存则会发请求带上验证条件，服务端判断内容未变时返回 304，客户端继续使用已有响应体。

2. 两者可以配合，不是互斥方案。缓存过期后能否验证取决于有没有 ETag、Last-Modified 等信息，没有合适缓存或内容已变时就需要下载新响应；304 节省响应体传输，但仍有一次请求的延迟。

3. 上线更新时，我会让 JS、CSS 使用与内容相关的 hash 文件名并长缓存。HTML 负责引用资源，应及时验证或短缓存；新入口引用新文件名，浏览器才能发现新版本，不能让固定入口也长期保持不验证的旧内容。

4. 发布顺序也重要，新资源先就绪，再更新入口，并保留旧 chunk。旧页面晚些时候可能触发懒加载，立刻清空旧文件会让正常访问失败；遇到更新不生效，还要检查 CDN 和 Service Worker，而不只看源站配置。

5. 缓存策略还要区分公开资源和私人数据，private、no-cache、no-store 含义不同。我的验证方式是结合响应头、请求状态和真实操作看缓存行为，普通刷新、强制刷新及开发工具禁用缓存的结果不能混为一谈。

## 追问：用户反馈还是旧页面，怎样逐层定位？

1. 先确认用户实际得到的 HTML 和资源版本，例如查看入口引用的 hash，而不是只问是否刷新过。随后看 HTML 响应头、Age 和缓存来源，判断来自浏览器、CDN 还是源站，找出哪一层仍在提供旧入口。

2. 再检查是否存在 Service Worker，它可能从 Cache Storage 返回页面，即使 HTTP 缓存已失效也不一定改变结果。源站、CDN 和客户端的版本要对应起来，避免源站已经更新就误判为用户操作不对。

3. 修复后用新访问和停留中的旧页面分别验证。强制刷新可以帮助诊断，但不是发布方案；正常用户不应每次升级都被要求清空数据，更不能因为清缓存有效就跳过真正的策略问题。

## 追问：为什么给所有请求加时间戳不是理想更新方案？

1. 时间戳改变 URL，确实可能绕开按 URL 区分的缓存，但也会让内容未变的资源每次重新下载。浏览器和 CDN 很难复用它们，首屏流量和延迟都会增加，也掩盖了入口缓存策略没有设计好的问题。

2. 我会把稳定静态内容交给内容 hash 管理，只有内容改变才换地址。接口是否需要新数据则按业务设置缓存和验证规则，而不是统一在请求拦截器里加当前时间，破坏所有接口原本的缓存能力。

3. 排查时临时绕缓存可以作为实验，但验证结束要恢复合理配置。还要知道 Service Worker 或特殊 CDN 规则可能忽略某些参数，所以加时间戳也不是在任何缓存系统下都保证有效的万能办法。
