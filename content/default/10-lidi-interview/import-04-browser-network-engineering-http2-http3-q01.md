# HTTP/2 还需要域名分片吗？

## 核心回答

1. HTTP/2 下通常不需要为了绕过旧的单域连接限制而做域名分片。它可以在一条连接上交错传输多个请求的帧，因此把图片分到 a、b、c 多个域名，不一定带来更多有效并行，反而可能增加准备连接的工作。

2. 多个域名可能分别产生 DNS、TCP 和 TLS 成本，还可能分散连接复用和拥塞控制状态。用户首次打开页面时尤其要注意，这些额外握手可能占用关键时间，不能看到请求分散就认为网络一定更快。

3. 某些条件下浏览器能够跨来源复用符合要求的连接，但需要证书、地址和浏览器规则等满足条件。不能因为几个域名指向同一台机器，就断言一定共用连接，也不能只按域名数量猜实际连接数量。

4. 域名分开仍可能有安全隔离、第三方服务或不同缓存配置的需求，例如用户上传内容与主站隔离。这些理由与旧式性能分片不同，我会按业务目的保留，而不是升级 HTTP/2 后把所有域名机械合并。

5. 优化时看真实协议、连接建立、缓存命中和关键请求等待，再做对照验证。HTTP/2 还有 TCP 层丢包影响，也不能代替资源压缩和合理加载顺序；是否分域应以测量为依据，而不是套用旧的并发连接口诀。

## 追问：同一条 HTTP/2 连接上的请求会互相影响吗？

1. 会。不同请求属于不同流，可以交错发送，但它们共享底层 TCP 连接；发生 TCP 丢包时，后续字节的交付可能等待重传，从而影响多个 HTTP/2 流，不是每个流都有完全独立的网络通道。

2. 带宽和拥塞窗口也共享，大资源可能与首屏关键资源竞争。协议允许多路复用，不代表发送任意数量请求都没有代价，前端仍要控制预加载、非关键图片和大脚本的时机，避免让重要内容排在后面。

3. 我会在性能工具里检查实际优先级、下载与等待时间，再结合弱网结果判断。若问题主要是图片过大，先压缩和选合适尺寸，比为了消除所有共享影响而重新创建很多域名更直接。

## 追问：怎样证明删除域名分片真的有收益？

1. 我会在资源内容、缓存状态和网络条件尽量一致的情况下比较，记录 DNS、连接、TLS 与关键资源完成时间。单看请求总数通常不会变化，因此需要看连接准备是否减少以及首屏是否更早呈现。

2. 同时覆盖首次访问与再次访问，因为长连接复用和缓存会改变结果。若只测已经打开很多页面的浏览器，握手成本可能被隐藏；只测本地高速网络，也可能看不出真实用户环境里的差异。

3. 还要验证跨源权限、Cookie、字体和资源完整性配置没有被域名迁移破坏。性能收益只有在功能正确时才成立，发布后可以按实际协议和地区分组观察，避免平均值掩盖某些网络环境的退化。
