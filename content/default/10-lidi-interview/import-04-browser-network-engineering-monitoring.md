# 前端监控怎样形成闭环？

## 核心回答

1. 我会把前端监控理解为发现问题、定位原因和验证修复的连续工作，而不是只装一个 SDK。最基本的是知道哪个版本、哪个页面出了什么错误，影响多少用户，以及修复发布后这个问题有没有继续发生。

2. 采集分错误、性能和必要业务事件。运行时异常、未处理 Promise 拒绝和资源加载失败可以帮助发现问题；接口失败则要区分网络、状态码和业务错误，避免一个请求被多个监听重复上报，形成看似很多故障的噪声。

3. 上报带版本、路由模板、浏览器和脱敏后的关联标识，堆栈通过对应 source map 还原。原始请求体和用户输入不默认收集，性能数据也要保留采样口径，否则既可能泄露隐私，也可能得出错误的影响范围。

4. 收到数据后进行合理分组和告警，优先关注新增严重错误与关键操作失败。定位时结合复现步骤、资源和接口记录，明确问题发生在前端、网络还是服务端，不能看到一个报错名称就直接归给某一方。

5. 如果继续完善，我会把修复版本和问题记录关联，发布后检查相同错误是否下降以及有无新问题。如果错误只是因为采样调整而变少，要先校正比较口径；问题仍在发生时继续排查，确认修复版本真正覆盖受影响用户，而不是关闭告警就结束处理。

## 追问：某个错误只在线上出现，怎样开始定位？

1. 先确认受影响版本和环境，找一条带有效堆栈、路由和时间的脱敏样本，再用对应构建的 source map 还原。版本不匹配时行号可能指向无关代码，继续凭错误文本猜测容易浪费时间。

2. 我会结合前后操作和网络结果复现，检查生产独有条件，例如压缩优化、缓存旧文件、接口权限和第三方脚本。必要时在受控范围增加少量诊断字段，明确时限和隐私边界，不直接打开全量请求正文记录。

3. 修复前先做一个能稳定触发问题的场景，修复后重复验证，并观察新版本同类错误。一次本地无法复现不代表错误不存在，线上样本有限时先记录可确认的现象和待验证的原因，再通过受控复现逐步排除，避免根据单条错误就直接改动不相关逻辑。

## 追问：怎样避免监控告警太多，最后没人看？

1. 告警应基于用户影响和异常变化，而不是每条错误都立即通知。比如新版本关键页面大面积无法加载需要及时处理，一个已有的低频非关键资源失败可以先聚合观察，两者的处理时效应不同。

2. 我会让告警包含问题概要、版本、影响范围和查看入口，并明确由谁处理。重复告警需要合并和冷却，但持续恶化仍应升级，不能为了安静把整类错误永久屏蔽，导致真正故障也消失。

3. 定期看哪些告警产生了有效行动、哪些只是噪声，再调整阈值和分组。修复后验证问题停止或明显下降，若只是告警被关闭而错误仍在发生，就不能把它当成已经解决。
