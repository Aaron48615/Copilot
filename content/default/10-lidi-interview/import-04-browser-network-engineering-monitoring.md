# 前端监控怎样形成闭环？

## 核心回答

1. 前端监控是发现问题、定位原因、验证修复这一串，装一个 SDK 只是开头。最基本要知道哪个版本、哪个页面出了什么错，影响多少用户，修复发布之后这个问题还有没有继续发生。

2. 采集分错误、性能、必要的业务事件。运行时异常、没处理的 Promise 拒绝、资源加载失败，能帮着发现问题。接口失败要分开看网络、状态码、业务错误。同一个请求被多个监听报好几次，看起来故障很多，其实是噪声。

3. 上报带版本、路由模板、浏览器、脱敏后的关联标识，堆栈用对应的 source map 还原。原始请求体和用户输入默认不收。性能数据要留下采样口径，不然可能泄露隐私，算出来的影响范围也会错。

4. 数据进来后合理分组、告警，优先看新增的严重错误和关键操作失败。定位时结合复现步骤、资源、接口记录，分清是前端、网络还是服务端。看到一个报错名称就直接归给某一方，容易走错。

5. 修复版本和问题记录对上，发布后再看相同错误有没有下降、有没有新问题。错误变少如果只是因为采样调了，比较口径要先校正。问题还在发生就继续查，确认修复版本真正覆盖到受影响的用户。关掉告警不算处理完。

## 追问：某个错误只在线上出现，怎样开始定位？

1. 受影响的版本和环境先确认，找一条带有效堆栈、路由、时间的脱敏样本，再用对应那次构建的 source map 还原。版本对不上，行号可能指到无关代码，接着凭错误文本猜，容易耗很久。

2. 结合前后操作和网络结果去复现，看生产独有的条件，比如压缩优化、缓存着旧文件、接口权限、第三方脚本。必要时在受控范围加少量诊断字段，时限和隐私边界说清楚，别直接打开全量请求正文。

3. 修复前先做一个能稳定触发的场景，修完再走一遍，并观察新版本同类错误。本地一次复现不了，不代表错误不存在。线上样本有限时，先记下能确认的现象和待验证的原因，再受控复现逐步排除。别根据单条错误就去改不相关的逻辑。

## 追问：怎样避免监控告警太多，最后没人看？

1. 告警看用户影响和异常变化，不是每条错误立刻通知。新版本关键页面大面积加载不了，要及时处理；一个已经知道的低频非关键资源失败，可以先聚合观察。两者的处理时效不一样。

2. 告警里带问题概要、版本、影响范围、查看入口，并明确谁来处理。重复告警要合并、冷却，但持续恶化还是要升级。为了安静把整类错误永久屏蔽，真正故障也会一起消失。

3. 定期看哪些告警产生了有效行动、哪些只是噪声，再调阈值和分组。修复后验证问题停了或明显下降。只是告警被关掉、错误还在发生，就不能当成已经解决。
