# 为什么这里可以使用 Promise.all？

## 核心回答

1. 这里可以并行，是因为概览、事件统计、设施、交通排行和最新事件都能根据当前页面条件独立请求，没有一个必须先从另一个响应中拿参数。判断是否并行应先画清数据依赖，而不是看到多个接口就全部放进 Promise.all。

2. 请求由 API 函数调用启动，Promise.all 负责等待与组合。串行 await 会让后一个调用等前一个结束才开始，并行通常让等待更接近最慢请求，但并不是创建多个 JavaScript 线程，也不能保证服务器负载下仍有理想加速。

3. 返回数组按照传入 Promise 的顺序排列，与实际完成顺序无关。因此交通最快返回也不会跑到概览结果的位置，解构时保持顺序一致就能分发给对应组件，避免凭谁先到来判断它属于哪个模块。

4. 当前仪表盘全部成功后统一写入，一个 reject 就进入整体错误处理。它适合将一组数据视为一次完整刷新，但独立卡片本来可以容忍局部失败，现有方案的代价就是一个非核心请求也会影响整轮更新。

5. 如果继续完善，我会根据模块重要性分别处理，或使用 allSettled 检查每个结果。还要考虑刷新重叠与取消，Promise.all 自己不限制下一轮请求，也不会在整体失败后自动中止其他网络任务，这些需要另做控制。

## 追问：Promise.all 里传函数而不调用，会发生什么？

1. Promise.all 接受可迭代的值，会把普通值当作已完成结果，而不会主动执行函数。所以传 getOverview 只是得到函数本身，传 getOverview() 才会启动接口调用并把返回 Promise 交给它等待。

2. 这个区别能解释为什么并行不是 Promise.all 的魔法。也可以先分别调用得到几个 Promise，再统一等待；真正影响串行还是并行的是请求调用发生在前一个 await 之前还是之后。

3. 验证时看 Network 的开始时间和最终结果类型，比只看代码外面套了 Promise.all 更可靠。函数引用被当作结果时，后面访问 data 可能才报错，因此 API 调用形态与类型检查都要保持明确。还应检查每个请求只启动一次，没有为了组合结果再重复调用一遍接口。

## 追问：Promise.all 失败后，其他请求会停止吗？

1. 不会，它返回的组合 Promise 会因为其中一个拒绝而拒绝，但其他已经启动的异步操作通常继续执行。比如交通失败后，设施接口仍可能正常完成，不能把进入 catch 理解成网络层全部取消。

2. 若业务确实不再需要剩余结果，需要给底层请求传取消信号并主动取消；如果希望部分结果继续展示，就应该分别处理它们。前者是放弃这一轮工作，后者是保留还能使用的数据，需要根据页面是否允许部分更新来选择。

3. 城市视图当前按整轮更新，暂时没有局部失败处理，单个附加模块出错也可能阻止这一轮展示。验证某一请求立即失败、其他延迟成功，检查页面是否仍显示旧数据与错误提示，并明确它们的更新时间，避免把旧统计误读为新结果。
