# React 表单应该用受控还是非受控？

## 核心回答

1. 受控表单把值放在 React state 中，通过 value 或 checked 传给输入，再在 onChange 中更新。它适合即时预览、字段联动和动态禁用，比如选择地区后更新可选城市，因为当前值始终可以从状态中读取。

2. 非受控表单由 DOM 保存当前输入，React 用 defaultValue 设置初值，提交时通过 FormData 或 ref 读取。简单联系表单不需要每次输入都影响别处时，这种方式比较直接；但重置和外部数据回填要按它自己的方式处理。

3. 我不会认为非受控一定更快、受控一定更规范。字段多且订阅粗时，受控更新可能带来额外渲染，但可以先缩小状态范围；若业务要求边输入边计算总价，全部改成非受控反而会增加同步代码。

4. 同一个输入在存活期间应保持受控或非受控的明确选择，例如受控文本初值使用空字符串而不是 undefined。文件输入由用户选择文件，不能通过普通 value 填入本地文件；无论哪种方案，都需要统一提交状态、校验和错误反馈。

5. 提交数据时还要核对字段名称和转换规则。例如非受控方案依赖表单元素的 name 才能通过 FormData 收集；数字、复选框和空值也需要按接口协议整理。控制方式只是输入管理的一部分，不会自动保证提交结果符合业务要求。

## 追问：接口返回初始值后，为什么 defaultValue 没跟着变？

1. defaultValue 表达的是初始默认值，不是让 React 持续控制用户当前输入。组件挂载后修改它，不能当作可靠的当前值同步方案；如果需要接口返回后持续回填，受控 value 往往更符合这个需求。

2. 非受控表单也可以先等待初始数据再挂载，或使用表单工具提供的 reset 方法明确重置。关键是区分“第一次载入”和“用户已经编辑后后台又刷新”，不能每次请求完成都覆盖正在输入的内容。

3. 若切换的是完全不同的记录，可以按记录编号设置 key 重建表单，但这会丢掉原记录的本地草稿和焦点。需要保留草稿时，应另行按编号保存，再决定切换回来时恢复哪份数据。

## 追问：受控输入为什么会出现从非受控变受控的警告？

1. 常见原因是第一次 value 为 undefined，React 按非受控处理，接口回来后又传入字符串。它意味着同一输入的控制方式发生了变化，我会把文本初值明确设为空字符串，复选框的 checked 设为布尔值。

2. 不能只为了消掉警告随便把所有字段都转成字符串。数字字段可能需要允许输入空值或中间状态，界面值和最终提交的数值可以分开处理，提交时再按字段规则转换并校验。

3. 我会同时检查是否正确处理了 onChange，以及是否在事件里同步回写当前输入。value 已经由 state 控制却不更新 state，输入就会像被锁住；这属于数据流问题，不应通过切换 key 强制重建解决。
