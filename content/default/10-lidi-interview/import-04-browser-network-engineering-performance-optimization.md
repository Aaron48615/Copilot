# 首屏性能优化做过哪些？

## 核心回答

1. 我做首屏优化时会先测量，结合 Lighthouse、Network 和 Performance 看用户在等什么。资源下载慢、接口串行和脚本执行长是不同问题，不能看到首屏慢就同时加缓存、懒加载和各种预加载，最后也不知道哪项真正有效。

2. 我用过路由懒加载和稳定依赖分包，例如把非首屏业务页面延后加载，让 React、ECharts 等依赖更容易复用缓存。但当前首屏所需的页面仍必须加载，不能笼统说懒加载后首屏永远只剩登录和布局代码。

3. 网络方面，静态资源按内容版本缓存，没有依赖关系的接口可以并行。图片选合适尺寸并尽早加载首屏关键内容，非关键图片再懒加载；接口很慢时也需要和后端一起定位，前端分包并不能缩短服务端处理时间。

4. 渲染方面，骨架屏让等待状态更清晰，但不是实际内容更早完成的证明。图表可以复用实例并通过 setOption 更新，减少不必要的重复初始化；同时检查长任务和组件更新范围，避免网络已经结束，页面仍长时间不能操作。

5. 我还会关注发版后的懒加载失败，旧页面可能请求已经删除的旧 chunk，需要保留兼容资源和有限恢复方案。验证时保持页面内容、设备与网络条件一致，比较前后下载和执行时间，再检查旧页面跳转能否恢复，避免只测新版本首次打开而漏掉升级过程。

## 追问：Lighthouse 分数提升了，就代表真实用户更快吗？

1. 它能提供有价值的实验室诊断，但运行设备、网络模拟和测试路线有限，不等于所有真实用户。缓存、登录状态和第三方服务在实验里可能不同，因此分数提升需要结合相同条件复测与线上数据判断。

2. 我会比较具体指标和时间线，而不只看总分。例如 LCP 是否改善、主线程是否更忙、交互有没有退化；一些优化可能让初次加载更快，却把大量工作推迟到用户点击时，造成新的等待。

3. 线上按路由、设备和网络看分布，并保持采样口径一致。没有真实用户数据时就明确说目前只完成实验室验证，不把本机一次较好结果描述为所有用户都获得了同样幅度的改善。

## 追问：已经做了懒加载，首屏脚本为什么仍然很大？

1. 可能有模块仍被入口静态导入，或公共入口文件把大型库一起引入，动态导入只增加了一个文件却没有移走主要代码。也可能所谓懒加载页面本来就是当前首屏路由，因此它仍立即被请求执行。

2. 我会看构建分析和 Network 的实际初始请求，确认大依赖由哪条导入路径进入。共享 chunk、预加载和组件库导入方式也要检查，不能只搜索到 import() 就认为代码已经从首屏消失。

3. 修改后比较初始传输与执行量，再验证后续页面打开延迟。若某个功能用户几乎立即使用，过度延后会增加点击后的等待，可以在明确意图时预取；目标是整体体验合理，不是入口文件越小越好。
