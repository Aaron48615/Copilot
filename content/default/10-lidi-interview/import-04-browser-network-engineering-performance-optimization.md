# 首屏性能优化做过哪些？

## 核心回答

1. 首屏优化从测量开始，Lighthouse、Network、Performance 一起看用户在等什么。资源下载慢、接口串着发、脚本执行很长，是不同问题。看到首屏慢就同时加缓存、懒加载、各种预加载，最后也不知道哪项真有用。

2. 项目里用过路由懒加载和稳定依赖分包。非首屏业务页面往后放，React、ECharts 这类依赖更容易复用缓存。但当前首屏那个页面该加载还是要加载。懒加载之后，首屏永远只剩登录和布局代码，这话太满。

3. 静态资源按内容版本缓存，没有依赖关系的接口可以一起发。图片选合适尺寸，首屏关键内容尽早加载，非关键图再懒加载。接口本身很慢，还得和后端一起查。前端分包缩短不了服务端处理时间。

4. 骨架屏让等待状态更清楚，但不是实际内容更早完成的证明。图表可以复用实例，用 `setOption` 更新，少做没必要的重复初始化。长任务和组件更新范围也要看。网络已经结束，页面还长时间不能点，用户照样觉得慢。

5. 发版后懒加载可能失败，旧页面会去要已经删掉的旧 chunk，需要留兼容资源和有限恢复。验证时页面内容、设备、网络条件对齐，比较前后下载和执行时间，再看旧页面跳转能不能恢复。只测新版本首次打开，升级过程容易漏。

## 追问：Lighthouse 分数提升了，就代表真实用户更快吗？

1. 它能给实验室诊断，但设备、网络模拟、测试路线都有限，不等于所有真实用户。缓存、登录状态、第三方服务在实验里也可能不一样。分数提升了，还要同样条件复测，再看线上数据。

2. 看具体指标和时间线，别只看总分。比如 LCP 有没有改善、主线程是不是更忙、交互有没有变差。有的优化让初次加载更快，却把大量工作推到用户一点击，又变成新的等待。

3. 线上按路由、设备、网络看分布，采样口径保持一致。没有真实用户数据时就说清楚：目前只做完实验室验证。本机一次较好的结果，不能说成所有用户都快了同样幅度。

## 追问：已经做了懒加载，首屏脚本为什么仍然很大？

1. 可能还有模块被入口静态导入，或者公共入口把大型库一起引进来了。动态导入只多了一个文件，主要代码没挪走。也可能所谓懒加载的页面，本来就是当前首屏路由，它仍会马上被请求、执行。

2. 看构建分析和 Network 里实际的初始请求，确认大依赖是从哪条导入路径进来的。共享 chunk、预加载、组件库怎么导入，都要查。搜到 `import()` 就认为代码已经从首屏消失，经常对不上。

3. 改完比较初始传输和执行量，再看后续页面打开会不会更慢。某个功能用户几乎一进就用，过度延后会增加点击后的等待，明确意图时可以预取。目标是整体体验合理，不是入口文件越小越好。
