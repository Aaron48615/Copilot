# 轻购或城市视图的登录鉴权和权限控制是怎么做的？

## 核心回答

1. 以轻购的实际流程为例。登录接口成功返回 accessToken 后，前端通过 setToken 写入 localStorage；后续普通接口经过统一 Axios 实例，每次请求读取当前 Token，并放到 Authorization 的 Bearer 请求头里，页面不用重复拼接认证信息。

2. 路由守卫负责页面入口，当前白名单是登录、注册和轻购AI，其他页面没有 Token 就跳登录。守卫检查的是凭据是否存在，不能证明它有效；例如浏览器里还保存着过期 Token，最终仍要等服务端校验结果。

3. 跳登录时会保存原目标的 fullPath 到 redirect，成功后回到原页面，没有目标则进首页。这样从购物车被拦截后还能继续原来的操作，但恢复路径不等于恢复过期数据，订单与地址仍需要重新读取。

4. 响应拦截器同时处理 HTTP 401 和业务码 A00004，发现失效就清理 Token 并 replace 到登录页。redirectingToLogin 用来减少并行请求同时失效产生的重复跳转，当前没有刷新 Token 流程，失效后需要用户重新登录。

5. 城市视图用 Redux Toolkit 管理用户与登录相关状态，但状态库也只是前端状态来源。真正的身份、角色和数据归属由服务端判断，比如不能让用户通过修改订单 ID 查看他人订单，前端隐藏页面或按钮都不能代替这些检查。

## 追问：有 Token 为什么还可能没有权限？

1. Token 能帮助服务端识别请求身份，但身份有效不代表对所有资源都有访问权。例如用户登录成功，也只能查看自己的地址和订单，订单 ID 存在本身不能成为允许返回详情的条件。

2. 后端应按当前身份校验数据归属与动作权限，前端根据结果给出明确反馈。通常需要区分未登录与权限不足，不能遇到所有失败都退出登录，否则用户重新登录也无法解决真正的权限问题。

3. 测试时可以使用两个测试账号，在允许的测试环境中交叉请求彼此资源，检查列表、详情和更新接口都遵守同一规则。仅看一个账号页面上没显示别人的数据，无法证明接口没有越权问题。

## 追问：退出登录后，除了删除 Token 还应考虑什么？

1. 要检查页面里是否还留着上一位用户的订单、地址或个人信息。删除 Token 只影响后续身份请求，已经加载到局部状态或 Store 的内容不会自动消失，切换账号后继续显示会造成错误甚至信息泄露。

2. 如果继续完善，集中清理用户相关缓存，并让正在执行的旧身份请求失效。否则退出后旧订单响应才返回，仍可能把刚清空的数据重新写回页面，这与搜索乱序类似，但影响的是账号隔离。

3. 跳转到公开页面后，再登录应重新获取身份与资源。临时下单参数也要核对是否属于原用户，不能把 A 账号留下的 basketIds 不加区分交给 B；服务端同时必须拒绝不属于 B 的购物车项。
