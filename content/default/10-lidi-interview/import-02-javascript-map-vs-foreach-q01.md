# forEach 里写 async，外面会等它完成吗？

## 核心回答

1. 不会，`forEach` 只负责依次调用回调，不收集也不等待回调返回的 Promise。回调标记成 `async` 只改变这个回调自己的返回行为，并没有把外层遍历变成异步等待，所以遍历后面的语句可能在请求完成前就执行。

2. 甚至在前面写 `await list.forEach(...)` 也不能补上等待，因为它拿到的是 `undefined`。假设回调要保存多条记录，外层此时提示全部成功就会过早；正确做法应让外层拿到代表这些保存操作的 Promise，再决定何时展示结果。

3. 若每条操作彼此独立，可以用 `map` 生成 Promise 数组，再等待 `Promise.all`。结果按输入顺序排列，不按网络完成顺序排列；但其中一个失败会让整体拒绝，其他已启动操作不会因此自动停止，错误提示不能假装全部都没执行。

4. 若后一条依赖前一条结果，我会用 `for...of` 配合 `await`，把顺序写清楚。这样也更容易决定失败后停止还是继续，不过它会减少并发，独立且耗时的请求全部串行，可能让总等待时间变长，不能机械替换。

5. 数量较大时，还需要限制同时发出的请求，不能默认一次启动全部任务。我会根据接口约束选择分批或固定并发数，并在实际负责等待的那一层捕获错误，避免回调内部拒绝无人接收，界面却已经进入成功状态。

## 追问：Promise.all 失败后其他请求会取消吗？

1. 不会，它只是汇总输入 Promise 的结果，其中一个拒绝就让汇总结果拒绝。其余请求如果已经发出，通常仍在进行，甚至可能已经完成写入，所以捕获汇总异常并不代表这批操作完全没有产生影响。

2. 假设要尽量停止未完成的请求，可以让请求支持同一个取消信号，并在失败时发出取消。但取消只表达客户端不再继续等待或传输的意图，不会把服务端已经提交的记录回滚，界面仍需要重新确认实际执行结果。

3. 如果产品允许部分成功，我会考虑 `Promise.allSettled` 收集每项状态，再让用户重试失败项。对于写操作，还应由接口明确幂等和重复提交规则，否则一次不加区分的整批重试，可能把已经成功的项目又执行一遍。

## 追问：串行循环里如何做到失败后继续处理？

1. 把单条任务的 `try...catch` 放在循环内部，就能记录这一项失败后继续下一项。若捕获放在整个循环外面，第一次异常通常会直接退出循环；这两个位置对应的业务语义不同，不能只看有没有写错误处理。

2. 假设导入多条互不依赖的数据，我会给每项记录编号、成功或失败状态及必要原因，最后返回汇总。这样调用方既能显示部分完成，也能准确选出重试范围，不必靠控制台日志推断哪些操作真正执行过。

3. 但如果下一项依赖上一项生成的结果，失败后继续可能扩大错误。这时我会停止当前依赖链，并把未执行与执行失败分开说明；是否继续是业务决定，不应为了保证循环跑完而吞掉所有异常，把错误变成看似成功的返回。
