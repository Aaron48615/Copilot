# 写过 Webpack 的 Loader 或 Plugin 吗？

## 核心回答

1. 我没有在生产项目里独立编写过 Webpack Loader 或 Plugin，这一点如实说。接口和实现步骤可以讲。判断先看需求：转换单个输入模块适合 loader，处理整次构建的资源或阶段行为更适合 plugin。

2. 写一个 Markdown 转模块的 loader，接收源文本，按明确规则解析，再输出合法的模块代码。选项用当前版本提供的接口读，异步工作用正确回调，必要时传递 source map。只拼字符串却不处理引号、错误位置、输入边界，生成的代码会坏。

3. 转换如果读了额外模板或配置文件，要把依赖告诉构建器，这些文件一变才能触发更新和缓存失效。能缓存的结果保持输入决定输出，别偷偷读未记录的外部状态。否则首次构建正常，增量时可能一直返回旧内容。

4. 写产物清单插件，在 `apply` 里注册编译钩子，通过 `compilation` 的正式资源接口读取和生成内容。Webpack 5 可以按需要选 `processAssets` 的阶段，别沿用旧式直接改资源的写法，把压缩、hash 这些先后关系忽略掉。

5. 用小项目覆盖正常输入、解析失败、配置变化、监听重建，并检查生成文件实际跑起来怎样。单个转换或清单功能先能跑，再改输入和配置看增量结果，错误位置准不准也要看。重复构建不能留下旧资源或重复条目。

## 追问：Markdown loader 怎样避免生成无效 JavaScript？

1. 输出文本模块时，用可靠的字符串序列化处理引号、反斜线、换行，别把原文直接包进一对引号。若要生成组件结构，需要更明确的解析和代码生成规则，内容里的特殊字符会破坏语法。

2. 原样展示文本和渲染 HTML 要分开。后者涉及不可信内容的清洗。构建能生成 JavaScript，不代表最终页面展示安全。错误信息应带文件和可定位位置，方便找到输入问题，不要只抛一个转换失败。

3. 用含中文、多行、代码片段、特殊字符的小样本测输出，再在真实构建里导入运行。结果正确之外，错误路径和 source map 传递也要验证。成功示例正常、复杂文档一进来就失效，这种缺口很常见。

## 追问：产物体积插件应该在哪个阶段统计？

1. 取决于想统计什么。看最终压缩后的资源大小，就选相应处理已经完成的阶段。优化前统计得到的是另一种口径，当不了实际发布大小。原始字节和 gzip 这类传输压缩后的大小，也要分开说。

2. 通过 `processAssets` 这类钩子选合适时机，明确是否包含映射、图片、压缩副本，并排除插件自己刚生成的报告，避免报告不断统计自身。监听模式里每次编译重新算，不累积上一轮资源。

3. 用已知大小的资源和实际产物对照，再修改或删除文件看结果会不会更新。阈值告警也要说明口径。所有文件简单相加称为首屏流量不合适，异步资源和共享缓存不会在每次访问都被下载。
