# 写过 Webpack 的 Loader 或 Plugin 吗？

## 核心回答

1. 我没有在生产项目里独立编写过 Webpack Loader 或 Plugin，这部分会如实说明，但能解释它们的接口和实现步骤。判断先看需求：转换单个输入模块适合 loader，处理整次构建的资源或阶段行为更适合 plugin。

2. 如果写一个 Markdown 转模块的 loader，我会接收源文本，按明确规则解析后输出合法的模块代码。选项使用当前版本提供的接口读取，异步工作用正确回调，必要时传递 source map；不能只拼字符串却不处理引号、错误位置和输入边界。

3. 转换如果读取了额外模板或配置文件，要把依赖告诉构建器，这样文件变化才能触发更新和缓存失效。能缓存的结果保持输入决定输出，避免偷偷读取未记录的外部状态，否则首次构建正常，增量时可能持续返回旧内容。

4. 如果写产物清单插件，我会在 apply 中注册编译钩子，通过 compilation 的正式资源接口读取和生成内容。Webpack 5 可以按需要选择 processAssets 的阶段，避免沿用旧式直接修改资源的写法而忽略压缩、hash 等先后关系。

5. 验证会用小项目覆盖正常输入、解析失败、配置变化和监听重建，并检查生成文件的实际运行结果。我会先让单个转换或清单功能可运行，再修改输入与配置观察增量结果，并检查错误位置是否准确；重复构建也要确认没有留下旧资源或重复条目。

## 追问：Markdown loader 怎样避免生成无效 JavaScript？

1. 如果输出的是文本模块，可以用可靠的字符串序列化处理引号、反斜线和换行，不能把原文直接包进一对引号。若要生成组件结构，则需要更明确的解析与代码生成规则，避免内容中的特殊字符破坏语法。

2. 还要区分原样展示文本与渲染 HTML，后者涉及不可信内容的清洗，构建能生成 JavaScript 不代表最终页面展示安全。错误信息应包含文件和可定位位置，方便使用者找到输入问题，而不是只抛一个转换失败。

3. 我会用含中文、多行、代码片段和特殊字符的小样本测试输出，再在真实构建里导入运行。除了结果正确，还要验证错误路径和 source map 传递，避免成功示例正常而复杂文档一进来就失效。

## 追问：产物体积插件应该在哪个阶段统计？

1. 取决于想统计什么。如果要看最终压缩后的资源大小，就应选择相应处理已经完成的阶段；在优化前统计得到的是另一种口径，不能把它当成实际发布大小。还要区分原始字节与 gzip 等传输压缩后的大小。

2. 我会通过 processAssets 等钩子选择合适时机，明确是否包含映射、图片和压缩副本，并排除插件自己刚生成的报告，避免报告不断统计自身。监听模式中每次编译重新计算，不累积上一轮资源。

3. 验证时用已知大小的资源和实际产物对照，再修改或删除文件看结果是否更新。阈值告警也要说明口径，不能把所有文件简单相加称为首屏流量，因为异步资源和共享缓存不会在每次访问都被下载。
