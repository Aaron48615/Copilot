# 依赖数组能不能故意少写？

## 核心回答

1. 不该故意少写。Effect 里用到了组件的 props、state，或者这次渲染里新造出来的变量，它们就是响应式依赖。少写不是少干活，是告诉 React：这些值变了也不用重新同步。

2. 比如请求里读了 `userId`，依赖却写成 `[]`。换成另一个用户，Effect 可能还拿着第一次的编号去查。页面已经是新用户，请求还在查旧的。问题是依赖和实际读取对不上，关掉检查规则解决不了。

3. 补全依赖之后跑得太勤，先改结构。只在 Effect 里用的配置对象，进 Effect 再造；固定常量挪到组件外面。计数要加一，用 `setCount(c => c + 1)`，就少读当前这次的 count。

4. 有些逻辑本来就是按钮点击，不必为了跑它专门建一个 Effect。真的需要函数引用稳住，再用 `useCallback`，依赖也要写全。把变化的值全塞进 ref，警告没了，该重建的连接也可能一直不更新。

5. 拿实际变化核对依赖。换用户要重新查，只改展示颜色不该再查一遍。依赖数组得跟这些预期对上。要是某个明明用到的字段缺着，只能靠注释解释，多半是把几件不同的事塞进同一个 Effect 了。

## 追问：依赖是对象，为什么每次渲染都重新执行？

1. React 用 `Object.is` 一项项比依赖，不会钻进去比对象内容。组件每次跑都新造一个 `{ roomId }`，`roomId` 没变，新对象和旧对象也不是同一个。拿这个对象当依赖，Effect 就会再跑。

2. Effect 其实只要 `roomId`，就直接依赖这个原始值，连接配置在 Effect 里面再拼。输入框那些无关状态变了，不会重连，也不用为了少重连再套一层缓存。

3. 对象还要传给别处、引用稳住真有用，再考虑 `useMemo`。缓存的依赖照样写全。空数组当「对象永远不变」用，里面可能一直留着第一次的参数。核对时改一个无关开关，不该重连；改真正的连接参数，该重连。少跑几次但该同步的没跟上，也不算对。

## 追问：想读最新主题，但主题变化不该重连聊天室怎么办？

1. 先把触发条件拆开：连哪间房看 `roomId`，提示文字颜色看主题。两件事写在同一段连接逻辑里，换一次皮肤也可能把连接掐了再建。颜色这类事别跟建立连接绑死。

2. 项目 React 版本如果有 `useEffectEvent`，可以把「要读最新值、但不该带动重连」的那段放进 Effect Event。它有调用范围限制，不是拿来随便删依赖的。老版本就另说。

3. 老版本也可以单独一个 Effect 把主题同步到 ref，订阅回调里再读。主题不是连接条件，这一点要说清楚。换房间仍会重新订阅。别为了「只连一次」，把真正该变的依赖也藏起来。
