# 依赖数组能不能故意少写？

## 核心回答

1. 不应该故意少写依赖。Effect 使用了组件里的 props、state 或随渲染产生的变量，就要考虑它们是否是响应式依赖；少写并不是减少工作那么简单，而是告诉 React 这些值变化时不用重新同步。

2. 比如请求里读取了 userId，却把依赖写成空数组，切换用户后 Effect 仍可能使用第一次的编号。此时页面显示新用户、请求却查旧用户，问题来自依赖描述和实际读取不一致，不能靠关闭检查规则解决。

3. 如果补全依赖后执行过于频繁，我会先调整代码结构。仅在 Effect 内使用的配置对象可以放进去创建，固定常量可以移到组件外；计数递增可以用函数式更新，减少对当前计数的直接读取。

4. 有些逻辑本来属于按钮点击等事件，不需要为了执行它创建 Effect。确实需要稳定函数引用时再考虑 useCallback，并完整维护其依赖；把所有变化值塞入 ref 虽然可能让警告消失，却也容易让本应重新建立的连接一直不更新。

5. 我会用实际变化验证依赖是否合理，例如切换用户后重新查询，改变纯展示颜色却不重复查询。依赖数组应和这些预期行为对应；如果只能靠一段注释解释某个明显使用的字段为什么缺失，就需要进一步检查是否把不同职责混进了同一个 Effect。

## 追问：依赖是对象，为什么每次渲染都重新执行？

1. React 按 Object.is 比较各项依赖，不会递归判断对象内容。组件每次运行都创建 `{ roomId }`，即使 roomId 没变，新对象和旧对象引用也不同，因此以这个对象为依赖的 Effect 会重新运行。

2. 如果 Effect 只需要 roomId，我会直接依赖这个原始值，并在 Effect 内创建连接配置。这样输入框等无关状态变化时不会重连，也不必为了避免重连额外维护一层缓存。

3. 只有对象还要传给其他地方且稳定引用确实有价值时，才考虑 useMemo。缓存的依赖仍要完整，不能把空数组当成固定对象的办法，否则对象内部可能长期保存第一次渲染时的参数。验证时可以改变无关开关和真实连接参数，确认前者不重连、后者能重连，避免只减少次数却漏掉必要同步。

## 追问：想读最新主题，但主题变化不该重连聊天室怎么办？

1. 先分清动作的触发条件：连接依赖 roomId，提示文字的颜色依赖主题。把二者全部写在同一段连接逻辑里，很容易让一次换肤也断开并重建连接，应该先拆出不负责建立连接的部分。

2. 在支持 useEffectEvent 的 React 版本中，可以将 Effect 内需要读取最新值但不驱动重连的逻辑放进 Effect Event。它有调用范围限制，不是删除任意依赖的工具，是否可用要看项目实际版本。

3. 老版本也能根据场景使用独立 Effect 同步 ref，再由订阅回调读取。关键是明确主题为何不属于连接条件，并验证切换房间仍会重新订阅，不能因为追求“只连接一次”把真正需要变化的依赖一起藏起来。
