# 为什么直接改对象 state 不行？

## 核心回答

1. React state 应作为当前渲染的只读快照使用。直接写 user.name 再传回同一个 user，不仅修改了之前的对象，也可能因为新旧引用相同而被 React 跳过更新；即使后来别的更新让界面显示新名字，也不能证明这种写法正确。

2. 更新对象时，我会创建新对象保留未变字段，再替换目标字段。例如修改昵称时复制 user 的顶层，改变 name；数组使用 map、filter 或展开等方式生成新数组，避免对原 state 直接执行 push、splice 或原地排序。

3. 嵌套对象需要沿修改路径复制，顶层展开只是浅复制。更新 address.city 时，如果新旧 user 仍共享同一个 address，直接改 city 仍会污染旧快照；不变的其他分支则可以继续复用，不需要每次深复制全部数据。

4. 上一状态可能连续变化时，使用函数式 setter 获取队列中的前值，再返回新结构。这样同时处理不可变更新和更新顺序，避免多个回调各自根据同一个旧对象计算，最后把彼此的修改覆盖掉。

5. Redux Toolkit 等使用 Immer 的环境可以写修改 draft 的形式，但普通 useState 不会自动帮忙转换。我的判断依据是实际使用的状态工具，不是代码看起来有没有赋值；验证时也会检查旧对象是否保持不变，以及无关子项能否继续复用引用。

## 追问：对象展开之后再改嵌套字段，为什么仍然影响旧 state？

1. 展开只复制顶层属性，如果某个属性本身是对象，复制过去的仍然是相同引用。新 user 和旧 user 的 address 指向同一个对象，对新 user.address.city 赋值，实际上也改了旧对象可见的地址。

2. 应在被修改路径上创建新层级，例如新建 user，再新建 address 并更新 city。没有变化的头像配置或其他分支可以保持原引用，这样既保留旧状态，也让依赖未变分支的组件有机会跳过额外工作。

3. 深层更新很多时，可以调整状态结构，或采用明确支持不可变草稿的工具，减少手写复制出错。不能简单用 JSON 序列化作为万能深复制，它会改变某些值的类型，也增加与实际修改规模无关的计算成本。

## 追问：直接修改之后再复制一次数组，为什么也不推荐？

1. 如果已经修改了数组里的旧对象，再复制外层数组，只是让 React 看见新数组引用，之前的对象仍被污染。共享这个对象的详情组件、历史草稿或其他缓存可能在没有明确更新的情况下一起改变。

2. 正确方式是在 map 中为命中的项目返回新对象，其余项保持原对象。例如修改某商品数量时，只创建那一行的新数据，而不是先对原行赋值后再展开整个数组，更新依据和影响范围都更清楚。

3. 我会检查两个方面：当前显示是否正确，以及旧状态是否仍代表更新前的数据。只做界面断言容易漏掉共享引用污染，尤其后续还要实现撤销、对比或乐观回滚时，旧快照被改掉会导致更难定位的问题。
