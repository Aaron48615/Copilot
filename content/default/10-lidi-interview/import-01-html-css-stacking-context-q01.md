# 为什么 transform 会影响 fixed？

## 核心回答

1. `fixed` 通常参照视口，但祖先上非 `none` 的 `transform` 会给固定定位的后代建包含块。这样后代的 `top`、`left` 和尺寸参照可能改成这个祖先，滚动时看起来像绑在某张卡片上。改的是定位参照，光拿 `z-index` 数字解释不通。

2. 就算 `transform` 视觉上是零，比如 `translate` 位移为零，只要计算值不是 `none`，也可能出这个效果。很多页面为了动画或所谓加速留着 `transform`，肉眼看不出父元素在动，后代定位已经变了。排查别只找明显旋转或缩放的祖先。

3. `transform` 还会建立层叠上下文，所以同一个祖先可能同时影响固定定位和覆盖关系，这两件事得分开看。把子元素 `z-index` 调大，视口参照恢复不了。拿掉父级变换，位置和层级可能一起变。验证时知道自己在解决哪一件。

4. 弹窗本来属于全页面，考虑挂到不受该业务祖先影响的浮层容器，或用合适的原生顶层能力。如果只是卡片内部的遮罩，保留局部参照也可能是对的。改之前先明确用途，再测滚动、缩放和开合动画。别为了恢复一个位置，随手删掉必要动效。

## 追问：translateZ(0) 没有视觉位移，为什么也会影响弹窗？

1. 零位移不等于没有 `transform`。浏览器算到的变换属性仍然不是 `none`，相关包含块和层叠规则照样参与。把 `translateZ(0)` 当成完全没有副作用的「加速开关」，预期会错。

2. 开发者工具里暂时禁用这一条，看 `fixed` 后代是不是回到视口边缘、滚动时是不是不再跟着祖先走。现象对上了，再确认这条变换还有没有性能或动画用途，别直接批量删掉所有 `transform`。

3. 父元素确实需要变换，就把全局浮层挪到合适位置，新的坐标和样式继承关系一起处理。优化性能也要用记录验证。为了一个没证明过的加速技巧，让弹窗定位和层级长期难维护，不划算。

## 追问：把 fixed 改成 absolute 能解决参照错误吗？

1. 通常解决不了「希望参照视口」这个目标。`absolute` 同样受包含块规则影响，滚动行为还跟 `fixed` 不一样。改完某张静止截图看着对，证明不了页面滚动时仍然符合需求，只是把问题换了一种表现。

2. 先明确弹层该跟着触发元素、某个面板，还是视口。跟着卡片的提示可以用局部 `absolute`；盖整页的模态层，选合适的外部挂载和定位方式。参照关系得在结构上成立，别靠属性名称碰运气。

3. 改完测父级滚动、整页滚动和窗口缩放，看要不要重新量触发位置。浮动提示的定位策略也可能由成熟组件处理，但仍要查挂载容器和滚动边界。换成组件，不会自动消掉所有参照问题。
