# 为什么 ESM 的 import 不能随便写进 if？

## 核心回答

1. 这里需要先区分静态导入声明和动态导入表达式：`import x from './x.js'` 属于模块声明，只能放在模块顶层。把它直接写进条件块或普通函数会违反语法规则，不是条件没有满足时才跳过，也不是解释器发现文件不存在才报错。

2. 静态导入让模块依赖在执行模块主体前就能被识别，加载器可以建立依赖关系并连接导出绑定。它的路径必须是字符串字面量，不能等到某个运行时分支才决定，这也为构建工具分析依赖提供基础，但不等于工具一定能删除全部未使用代码。

3. 如果需要根据用户操作或条件加载，可以使用 `import('./x.js')`，它是返回 Promise 的表达式，能够放在条件分支或函数里。等待完成后通常拿到模块命名空间对象，因此要处理加载和执行失败，并区分默认导出与命名导出的读取方式。

4. CommonJS 的 `require` 通常在执行到调用处时同步加载，所以条件调用方式不同，但不能简单说它绝对不能加载 ESM。现代 Node 支持满足条件的同步 ESM；是否可用要看运行版本、模块识别规则及依赖中是否存在顶层等待，不能只看文件扩展名。

## 追问：动态 import 一定会产生独立文件并减少首屏体积吗？

1. 不一定，动态导入是语言提供的异步模块加载入口，产物怎样拆分还取决于构建工具和配置。它经常被用作代码分割的位置，但模块可能被合并、提前加载，或者已经通过其他静态依赖进入首屏产物。

2. 假设准备把一个不常用的面板改为按需加载，我会先检查它是否还在入口处被静态引用，再查看构建后的依赖与网络请求。只有确认代码确实延后加载，才能讨论首屏传输是否减少，不能只看源文件多了一行动态导入。

3. 还要考虑首次打开面板会多一次等待，并处理加载失败和重复点击。若路径包含变量，构建工具能分析到哪些候选模块也有限制，所以这种改法属于需要验证的优化方案，不能直接宣称已经提升加载速度。

## 追问：把静态 import 写在模块底部，就会等上面的代码执行完再加载吗？

1. 不会，静态导入是模块依赖声明，不能按普通语句的书写位置理解加载时机。加载器会先处理依赖关系，在正常的无环依赖中先执行所需依赖，再执行当前模块主体，所以放到底部也不是延迟加载。

2. 导入拿到的绑定与导出有关，并不是执行到这一行才复制一次值。若依赖之间形成循环，还可能在某个绑定尚未初始化时访问它而报错，因此调整导入行的位置通常不能真正解决循环依赖带来的时序问题。

3. 假设确实要在按钮点击后才开始加载某个模块，应把动态导入放到点击流程里，并等待其结果。若问题来自循环依赖，则应检查哪些共享定义能独立出来，明确初始化顺序，不能用移动声明来假装控制执行时间。
