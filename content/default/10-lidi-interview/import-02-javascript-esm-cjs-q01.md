# 为什么 ESM 的 import 不能随便写进 if？

## 核心回答

1. 先分清静态导入声明和动态导入表达式。`import x from './x.js'` 是模块声明，只能放在模块顶层。直接写进 `if` 或普通函数会违反语法，不是条件没满足就跳过，也不是解释器发现文件不存在才报错。

2. 静态导入让模块依赖在执行模块主体前就能被认出来，加载器可以建依赖关系、接上导出绑定。路径必须是字符串字面量，不能等到某个运行时分支再决定。构建工具分析依赖也靠这个，但不等于工具一定能删掉全部没用到的代码。

3. 要根据用户操作或条件再加载，用 `import('./x.js')`。它返回 Promise，可以放在条件分支或函数里。等完之后通常拿到模块命名空间对象，加载和执行失败要处理，默认导出和命名导出的读法也不一样。

4. CommonJS 的 `require` 通常执行到调用处才同步加载，所以条件调用方式不同。但这不是说它绝对加载不了 ESM。现代 Node 支持满足条件的同步 ESM。能不能用，看运行版本、模块识别规则、依赖里有没有顶层 `await`，不能只看文件扩展名。

## 追问：动态 import 一定会产生独立文件并减少首屏体积吗？

1. 不一定。动态导入是语言提供的异步模块加载入口，产物怎么拆还取决于构建工具和配置。它常被当作代码分割的位置，但模块可能被合并、提前加载，或者已经通过别的静态依赖进了首屏产物。

2. 把不常用的面板改成按需加载，先看它是不是还在入口被静态引用，再看构建后的依赖和网络请求。确认代码确实延后加载了，才能谈首屏传输有没有减少。源文件多了一行动态导入，说明不了这件事。

3. 第一次打开面板会多一次等待，加载失败和重复点击也要处理。路径里带变量，构建工具能分析到哪些候选模块也有限制。这种改法是要验证的优化，不能直接宣称已经加快了加载。

## 追问：把静态 import 写在模块底部，就会等上面的代码执行完再加载吗？

1. 不会。静态导入是模块依赖声明，不能按普通语句的书写位置理解加载时机。加载器会先处理依赖关系，无环依赖里通常先执行所需依赖，再执行当前模块主体。放到文件底部也不是延迟加载。

2. 导入拿到的绑定跟导出有关，不是执行到这一行才复制一次值。依赖之间形成循环，还可能在某个绑定还没初始化时访问它而报错。挪导入行的位置，通常解决不了循环依赖带来的时序问题。

3. 真要按钮点了才开始加载某个模块，把动态导入放到点击流程里，并等待结果。问题来自循环依赖，就检查哪些共享定义能独立出来，把初始化顺序写明白。挪声明假装能控制执行时间，没用。
