# 校验应该放在哪一层？

## 核心回答

1. 校验放在数据进入应用的边界附近，但最底层请求函数不必承担所有业务规则。网络层负责请求与响应状态，接口适配层负责具体数据结构，业务层再判断这份数据在当前场景下能不能参与操作。

2. 比如订单详情返回后，适配层可以检查编号、金额格式和状态枚举，再转换成内部统一的数据表示。页面就不必每次渲染都判断字段到底是字符串还是数字，接口差异也能集中在较小范围内处理和定位。

3. 取消订单是否允许，依赖状态、用户操作和服务端规则。这类判断属于业务逻辑，不宜写进所有接口共用的拦截器。字段结构正确只说明数据能被理解，不等于用户当前有权取消，也不等于订单状态不会继续变化。

4. 表单输入是另一种边界。输入过程中可以提供即时提示，提交前再检查完整约束，帮助用户准确修改。前端与服务端可以共享部分规则定义，但服务端仍需独立执行验证，因为请求能够绕过页面直接发起。

5. 通过校验的数据应以明确类型返回，失败则带上可定位的字段路径和原因，由调用方决定提示或降级。按接口组织结构校验，把可复用业务判断提取出来，避免组件、缓存和请求层各写一套不同规则。

## 追问：通用请求函数要不要接收一个校验器？

1. 可以把校验器作为参数，让请求函数统一组织读取、校验与错误返回，具体字段规则仍由接口模块提供。这样请求函数只知道调用校验器，不需要知道订单有哪些状态。新增一个业务接口也不用改全局分支。

2. 类型上让成功结果来自校验器的实际输出，而不是调用方随意填一个泛型就相信响应。校验器可能把合法的日期字符串转换成内部表示，所以输入类型和输出类型需要区分，不能默认两者完全一样。

3. 也要保留不同响应形式的入口。文件下载不该先按普通对象解析，空响应也不该强行读取字段。抽象需要大量开关才能覆盖这些情况，就先拆成少量清楚的函数，等出现稳定重复后再考虑合并。

## 追问：缓存数据已经校验过，读取时还要检查吗？

1. 内存中刚刚通过校验、又没有被任意修改的数据，通常不需要在每个组件里重复完整检查。持久化缓存不同，它可能跨应用版本存在，也可能由其他标签页更新，重新进入应用时仍是需要处理的输入边界。

2. 给持久化数据保存版本标识，先检查版本，再按对应规则迁移或丢弃。比如旧版本把用户名称存成单个字符串。不能直接对旧对象加类型断言，否则页面升级后第一次读缓存，就可能出现很难复现的错误。

3. 迁移结果也要检查。失败时优先恢复为可解释的未加载状态，并按条件重新获取数据。权限或登录相关缓存不能成为服务端授权依据。展示了某个按钮也不代表操作必然获准，提交时仍需处理服务端拒绝。
