# 谈谈 Pinia？为什么取代了 Vuex？

## 核心回答

1. Pinia 是 Vue 官方推荐的状态管理方案之一，适合多个组件或页面共同读取和修改的数据。它提供 store 来组织状态、派生值和动作，同时支持开发工具和类型推断；不是每个页面都必须使用，局部弹窗和输入草稿仍可以留在组件里。

2. 与 Vuex 相比，Pinia 没有要求经过 mutation 的单独层次，state 可以通过动作或明确入口更新，action 也能处理异步。常见写法用 defineStore 定义独立 store，选项式包含 state、getters、actions，也支持使用组合式方式组织状态和方法。

3. 多个 store 通常按业务划分，不需要沿用 Vuex 那种嵌套模块结构；类型推断和调用方式也较直接。不过“少一层接口”不意味着不需要更新规范，分散修改共享数据仍可能难追踪，复杂业务变化适合集中在有含义的动作中。

4. 轻购项目的购物车由页面配合接口管理，并未使用 Pinia。若继续完善，多个页面都要同步购物车角标和用户信息时，我会考虑抽成共享 store，明确请求、更新和退出时的重置，而不会为简单页面通信先引入额外全局状态。

5. Vuex 的既有项目不需要因为 Pinia 被推荐就立即迁移，应评估现有模块、测试和改写成本。Pinia 也不自动持久化所有数据，刷新恢复与 SSR 请求隔离需要按需配置；持久化哪些字段、何时清除以及是否涉及个人数据，都要单独决定。

## 追问：直接解构 store 的 state，为什么可能不再更新？

1. store 本身是响应式对象，直接解构原始值字段可能只得到当时的普通值。例如取出 count 后模板使用局部 count，store.count 后续变化不一定继续与它关联，这和普通 reactive 属性解构的边界相似。

2. 需要解构状态和 getter 时，可以使用 storeToRefs 保留响应式引用；action 方法通常可以直接取出调用。不能把整个 store 展开再以为每个新属性都自动保持响应式，应该根据值和方法的不同角色使用接口。

3. 我会测试通过其他组件修改 store 后，本组件是否同步显示，而不是只验证自己点按钮能变。跨组件更新更能暴露解构断开的问题，也能确认 store 中实际保存的是共享来源，而非某个页面又维护了一份副本。

## 追问：Pinia store 里的数据刷新浏览器后会自动保留吗？

1. 默认内存状态会随页面重新加载而重新建立，不能把全局状态管理等同于浏览器持久存储。需要恢复主题或购物车草稿时，应明确使用存储、插件或服务端数据来源，并在初始化时处理恢复流程。

2. 不应无差别保存整个 store，例如临时 loading、错误实例和敏感个人内容未必适合持久化。还要考虑数据版本变化、无效存储和退出清理，旧结构读回来不能直接当作当前版本合法状态使用。

3. 服务端数据通常仍需要重新确认，存储中的商品价格和权限可能已经过时。可以先恢复可接受的界面偏好，再获取当前业务结果，让用户看到的内容与真实状态一致，不能为了避免请求永久相信本地副本。
