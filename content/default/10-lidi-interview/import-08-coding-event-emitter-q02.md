# 怎么避免内存泄漏？

## 核心回答

1. 事件订阅泄漏通常来自生命周期不匹配：全局 emitter 一直存在，里面保存的监听函数又引用组件、DOM 或大数据。页面离开后，如果监听还在，这些对象仍然可达；问题不在有闭包本身，而在不再需要的闭包仍被长期持有。

2. 我会让 on 返回对应这一次订阅的取消函数，组件创建时订阅，卸载时调用它。这样不用在清理时重新寻找匿名函数，也不会因为两次 `bind` 产生不同函数引用而移除失败，订阅和清理可以放在相邻位置检查。

3. 取消函数应可重复调用，移除最后一个监听器后也要删除空事件集合，避免动态事件名一直积累。清理后如果调用方还把取消函数放在长期数组里，闭包仍可能保留相关引用，所以组件自己的清理列表也需要释放，不能只检查 Map 变空。

4. once 只适合确定最多消费一次的业务，不代表永远不用清理。如果它等待的事件一直没有发生，监听仍会留在 emitter 中；页面提前离开、操作取消或等待超时时，仍需要主动退订，也要处理回调已经启动的异步工作。

5. 验证时我会反复进入和退出页面，看监听数量能否回到基线，以及退出后是否仍收到通知。若怀疑实际内存未释放，再用堆快照查看保留路径，不能仅凭浏览器内存一时没下降判定泄漏，也不能把提高监听器数量上限当成修复。

## 追问：为什么 off 传入看起来一样的函数，却没有退订成功？

1. 函数匹配通常按引用身份，不按代码内容。`on('change', () => update())` 和 `off('change', () => update())` 创建了两个函数，即使文本完全一样，后者也找不到前者；我会保存原监听引用，或直接使用订阅返回的取消函数。

2. `bind` 也有相同问题，每次 `handler.bind(this)` 都会返回新函数。订阅前应绑定一次并保存，而不是订阅和退订时各绑定一次；对同一事件有多份独立订阅的情况，返回单次取消句柄更容易准确对应。

3. 我还会检查清理时使用的 emitter 实例和事件名是否与订阅时一致。动态创建实例、拼错字符串或在依赖变化时反复订阅，都可能导致“调用了 off 但没效果”，所以应同时观察监听数量和实际收到的通知次数。

## 追问：能不能用 WeakRef 自动回收所有监听器？

1. 我不会把弱引用当成默认订阅机制，因为监听器通常需要在明确退订前稳定存在。如果 emitter 只弱持有一个匿名回调，而外部没有保存它，垃圾回收可能让它在业务仍需要时消失，事件通知就变得不可预测。

2. WeakRef 和终结回调也不能保证在某个确定时间完成清理，所以不适合负责页面退出时必须停止的行为。即使对象最终可回收，也无法替代取消定时器、关闭资源或中止请求这些具有明确生命周期要求的操作。

3. 如果确有弱订阅需求，我会先约定由谁强持有监听器、对象消失后是否允许漏通知，再考虑实现。普通组件通信采用显式退订更容易检查；定位泄漏时优先找长期 emitter 到闭包的保留路径，而不是先更换引用类型。
