# 如何测试依赖注入组件？

## 核心回答

1. 测试依赖注入组件时，我会先明确依赖契约：注入键是什么，值包含哪些状态和方法，缺少时是否允许默认行为。Vue Test Utils 可以通过挂载选项提供依赖，也可以用一个真实父组件包裹，不能为了测试直接改子组件内部实现。

2. 只测试消费者行为时，可以提供简单替身，例如一个选中值 ref 和记录调用的方法。点击选项后检查方法收到正确编号，再更新提供的 ref 并等待视图刷新，检查子组件显示随之变化，这分别验证输出动作和输入响应式。

3. 需要验证提供者与后代整体协作时，用真实父子组合更有价值。比如表单提供者集中校验，输入子组件注册与注销，只有把它们一起挂载才能发现最近提供者覆盖、重复注册或卸载未解除关系等问题。

4. 每个测试应创建新的响应式状态和替身方法，避免多个用例共享模块单例。Symbol key 必须与组件使用同一个导出对象，重新生成同名 Symbol 不是同一个键；默认值场景也要单独测，不能所有测试都只走正常注入路径。

5. 断言重点是用户可见结果与约定交互，而不是组件读取 inject 的次数。异步动作先等待对应 Promise，再等待需要的 Vue 更新；如果涉及销毁，还应卸载并验证订阅释放，让测试覆盖依赖的整个使用过程，而不只是初次文本出现。

## 追问：模拟提供者时，为什么也要使用 ref？

1. 如果真实接口提供的是 ref，替身也应保持这个形状，否则组件可能因读取 value 得到 undefined，或者测试只验证初始文本而完全遗漏后续更新。模拟应替换数据来源，不应该改变依赖契约本身。

2. 我会先挂载组件确认初值，再修改同一个 ref，等待 Vue 更新并确认文本改变。这样能发现消费者把注入值提前解包成普通变量的问题，单纯每次重新挂载并传一个新值，反而测试不到响应式连接是否持续存在。

3. 方法也可以使用记录调用的替身，但更新规则应按当前测试目的设置。消费者测试可以只断言发出的动作，集成测试则让真实提供者执行状态变化，避免模拟过度复杂，最终只是重复实现了一遍业务代码。

## 追问：什么时候应该用真实父组件，而不是 global.provide？

1. 当问题涉及提供范围和生命周期时，真实组合更合适。例如内层表单应该覆盖外层表单的字段注册服务，仅注入一个固定对象无法验证“最近提供者生效”，也测不出嵌套结构是否放错了位置。

2. 提供者管理的清理同样适合组合测试。输入组件挂载时注册、移除时注销，父级汇总字段状态；如果只模拟一个 register 方法，可能确认调用发生，却没有检查卸载后父级是否仍保留已经不存在的字段。

3. 我会让单元测试聚焦消费者接口，让少量集成测试覆盖实际协作。两者不需要互相取代，关键是每个用例验证一个真实风险，不为了追求某种测试形式把页面所有依赖全部模拟掉或全部一次性装入。
