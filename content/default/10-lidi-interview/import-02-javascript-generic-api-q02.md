# 分页响应怎么写？

## 核心回答

1. 分页结果拆成列表项和分页信息。`PageResult<T>` 里列表是 `T[]`，页码、每页条数、总数各有明确字段。泛型只替换列表项，分页外壳可以复用，具体页面仍能知道每条数据有哪些属性。

2. 写类型之前先确认接口的分页约定：页码从零还是从一开始，总数表示记录数还是页数。这些含义没统一，字段全是数字、编译全部通过，页面仍可能跳错页。类型名和接口说明要一起看。还要确认返回页码是实际处理过的页码，还是原样回传的请求参数，边界页才不会判错。

3. 空数组是正常结果，没有记录不等于请求失败。服务端不提供准确总数，就按实际协议用下一页游标，或「还有没有更多」的标记。别随便填一个总数，让分页组件显示出并不存在的页数。

4. 请求参数和响应类型分开。搜索条件属于请求，列表记录属于响应。筛选条件变了要重置页码，还要防止旧请求盖住新结果。这些是交互上要做的处理，泛型本身不会完成这些工作。

## 追问：删除最后一页的最后一条记录后应该怎么处理？

1. 先确认删除确实成功，再重新获取当前条件下的列表和总数。前端直接把总数减一只能当临时展示。别人可能同时在新增或删除，本地估算当不了服务端的最终状态。

2. 重新请求后当前页为空，且页码大于首页，可以根据有效总数算最后一页，或者回退一页再请求。回退要有明确的结束条件，接口持续异常时别一直请求。首页为空就正常展示空状态。

3. 原来的筛选和排序条件要留着，不然用户删完看到另一组数据会很困惑。删除期间用户已经切了条件，旧操作触发的刷新也不能盖住当前页面，按当前查询状态决定怎么更新。

## 追问：游标分页还需要 page 和 total 吗？

1. 游标分页通常用上一批返回的位置标记请求下一批，不一定有可靠的页码和总数。按接口真实提供的信息建模，比如记录列表加下一游标，别硬套需要任意跳页的分页结构。

2. 这种方式适合连续加载。能不能回到上一批、能不能跳到指定位置，看服务端协议。前端不能把已经加载的批次数当成真实页数，也不能只凭当前记录数量去推整个结果集有多少条。

3. 切换筛选或排序后，通常要清空旧游标，因为游标往往只对原来的查询顺序有效。要支持继续加载，还得按协议处理结束标记、重复记录、加载失败重试。别把网络失败误判成没有更多数据。
