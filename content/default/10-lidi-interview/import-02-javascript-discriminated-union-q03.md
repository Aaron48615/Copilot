# 接口成功但业务失败怎么表达？

## 核心回答

1. 通信结果和业务结果要分开看。接口返回正常的 HTTP 状态，只说明这次响应在协议层面过了。保存接口返回成功状态码，正文却说名称重复，页面仍应进业务失败分支，不能看见请求回来了就提示保存成功。

2. 业务结果可以用 `success` 这样的字面量字段，区分两个对象分支：成功分支要求数据，失败分支要求错误码和能展示的说明。读取时先判断标签，再访问对应字段。比把数据、错误码、消息都定义成可选，更容易发现漏了什么。

3. 请求层检查网络失败、HTTP 状态、响应能不能解析；业务层再按约定解释正文里的结果。浏览器 `fetch` 收到失败状态码，通常仍会得到响应对象，得主动看 `response.ok`。解析成 JSON，也不代表字段结构已经可信。

4. 页面把不同错误转成具体反馈：名称重复提示改输入，暂时不可用则留着内容并给出后续操作。考虑自动重试前，先确认操作允不允许重复，服务端有没有去重。别把所有业务失败都当成网络抖动反复发送。

## 追问：为什么响应写成 ApiResult 类型后还要校验字段？

1. TypeScript 类型在运行时不会替接口检查数据。就算把解析结果断言成 `ApiResult`，服务端仍可能返回缺标签、字段类型错、旧版本结构。后面按成功分支去读，照样可能出错。

2. 外部结果先当未知数据：是不是对象、标签是不是约定的字面量，再检查对应分支必需的字段。成功结果要求记录编号，就不能只确认成功标签在，完全不管编号有没有、对不对。

3. 校验失败按「响应不符合约定」处理，留下必要的接口和版本信息，页面给能看懂的提示。这跟正常的业务拒绝不是一回事，别伪造一个业务错误码把协议问题藏起来，后面排查会找错方向。

## 追问：余额不足和请求超时可以共用一个重试按钮吗？

1. 两种情况用户该做的事不一样。余额不足是明确的业务拒绝，原样再请求通常不会变，应引导用户改操作。超时只说明客户端没及时拿到结果，证明不了服务端没处理。

2. 会产生写入的操作，超时后应先确认怎么查结果、有没有幂等约定，再决定重不重发。不然用户点一次重试，服务端可能又执行一次。页面只显示一条提示，实际业务已经重复了。

3. 按钮文案应对上真实动作：改输入、查询处理结果、重新尝试，别所有失败都同一个入口。错误类型留得越清楚，页面越好做反馈，不同失败路径也好测。
