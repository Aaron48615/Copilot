# 接口成功但业务失败怎么表达？

## 核心回答

1. 我会分开看通信结果和业务结果，接口返回正常的 HTTP 状态，只能说明这次响应在协议层面的情况。假设保存接口返回成功状态码，但正文表示名称重复，页面仍然应该进入业务失败分支，不能看到请求返回就提示保存成功。

2. 业务结果可以用 `success` 这样的字面量字段区分两个对象分支：成功分支要求数据，失败分支要求错误码和可展示的说明。读取时先判断标签，再访问对应字段，比把数据、错误码和消息都定义成可选字段更容易发现遗漏。

3. 请求层负责检查网络失败、HTTP 状态以及响应能否解析，业务层再按约定解释正文中的结果。使用浏览器 fetch 时，收到失败状态码通常仍会得到响应对象，需要主动检查 `response.ok`，而解析到 JSON 也不代表字段结构已经可信。

4. 页面最后把不同错误转换成具体反馈，比如名称重复提示修改输入，暂时不可用则保留内容并提供后续操作。若考虑自动重试，我会先确认操作是否允许重复，以及服务端是否提供去重机制，不会把所有业务失败都当作网络抖动反复发送。

## 追问：为什么响应写成 ApiResult 类型后还要校验字段？

1. TypeScript 类型在运行时不会替接口检查数据。即使把解析结果断言为 `ApiResult`，服务端仍可能返回缺少标签、字段类型错误或旧版本结构的数据，后续按成功分支读取时依然有出错的可能。

2. 我会先把外部结果当作未知数据，检查它是否是对象、标签是否为约定的字面量，再检查对应分支必需的字段。假设成功结果要求记录编号，就不能只确认成功标签存在，却完全忽略编号是否有效。

3. 校验失败应作为响应不符合约定来处理，保留必要的接口和版本信息，页面给出可理解的提示。它和正常的业务拒绝不同，不能伪造一个业务错误码把协议问题隐藏掉，否则后续排查容易找错方向。

## 追问：余额不足和请求超时可以共用一个重试按钮吗？

1. 两种情况需要的用户动作不同。余额不足是明确的业务拒绝，原样重复请求通常不会改变结果，应引导用户调整操作；超时只能说明客户端没有及时拿到结果，并不证明服务端没有处理。

2. 假设这是会产生写入的操作，超时后应先确认结果查询方式和幂等约定，再决定是否重发。否则用户点击一次重试，服务端可能又执行一次，页面虽然只显示一条提示，实际业务却已经发生重复。

3. 按钮文案应反映真实动作，例如修改输入、查询处理结果或重新尝试，而不是所有失败都展示相同入口。错误类型保留得越清楚，页面越容易做出适当反馈，也更容易测试不同失败路径是否处理正确。
