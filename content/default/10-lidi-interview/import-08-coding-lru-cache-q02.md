# 如何测试淘汰顺序？

## 核心回答

1. 先把最旧到最新的顺序写出来，再让测试操作一步步改它。容量设为 3，依次放 A、B、C，顺序是 A、B、C；读取 A 后变成 B、C、A，再放 D 应淘汰 B。这能区分 LRU 和只按插入时间淘汰的 FIFO。

2. 断言时尽量用不改变顺序的 has 或只读快照，避免为了检查 A 在不在而调用 get，让测试本身把 A 刷成最新。下面的伪代码假定 has 只检查存在性，不参与最近使用计算，也不依赖定时等待。

    ```text
    cache = LRU(3)
    put(A, 1); put(B, 2); put(C, 3)
    assert get(A) == 1
    put(D, 4)
    assert has(B) == false
    assert has(A) and has(C) and has(D)
    assert size == 3
    ```

3. 更新已有键要单独测。比如重建容量 2 的缓存，放 A、B，再覆盖 A 的值，最后放 C。应淘汰 B，A 返回新值，数量仍是 2。这个场景同时检查「覆盖会刷新最近使用」和「同键更新不会错误增加容量」。

4. 还要覆盖容量为 1、空缓存未命中、反复读同一键，以及值为 undefined 的情况。若约定容量必须是正整数，0、负数、小数都应明确报错；若选择容量 0 表示禁用缓存，就要按另一套规则验证，两套预期别混在一起。

5. 未命中的 get 不应凭空插入条目或影响淘汰顺序，也值得单独检查。TTL 属于额外功能，题目没有实现就不写过期测试。耗时测量只能观察实现趋势，不能通过一次运行很快就证明复杂度，数据规模、操作分布和运行环境都可能影响这一次耗时，所以正确性断言和性能观察应分开讲。

## 追问：为什么验证缓存内容时，不建议随手调用 get？

1. LRU 的 get 通常既读值，也更新最近访问顺序，所以它不是没有副作用的观察。假设本来要验证下一次写入会淘汰 A，却先调用 get(A) 检查存在，A 已被挪到最新，后面的淘汰结果就被测试自己改了。

2. 优先用约定明确为不刷新顺序的 has，或者测试专用的只读键顺序快照。真实 API 只有 get，可以让每个断言用独立初始化的缓存，或者把断言造成的访问也写入期望序列，不能隐含忽略它。

3. 读取值本身就是测试目标时当然应该调用 get，比如检查覆盖后的新值，只需安排好时机。存在性、值正确性和淘汰顺序可以分开验证，避免一个很长的测试不断改状态，最后失败却看不出是哪一步规则有问题。

## 追问：怎样用一条操作序列区分 LRU 和 FIFO？

1. 容量设为 2，先写 A、B，再读 A，最后写 C，这条序列就够。LRU 会保留最近读过的 A 并淘汰 B；FIFO 只看最初进入的时间，会淘汰 A。所以关键操作是中间那次命中读取。

2. 如果只连续写 A、B、C，两种策略都会淘汰 A，这个用例虽然能验证容量，却说明不了实现了 LRU。测试必须主动制造「插入顺序」和「最近访问顺序」不同的状态，才能发现实现漏掉了读取时的刷新操作。

3. 再用覆盖 A 的序列补充验证，因为有的实现只在 get 时刷新，却在 set 已有键时漏掉刷新。是否把写入视为使用要先约定，本题选择会刷新。其他缓存有不同规则，测试预期也应跟着规则变，不能只凭名称猜。
