# debounce 和 throttle 怎么选？

## 核心回答

1. 先看用户需要的是「停下来再处理」，还是「持续操作时也不断反馈」。防抖会在连续调用时推迟执行，适合减少中间输入造成的搜索请求；节流保留周期性执行机会，适合持续滚动时计算当前区域。

2. 比如搜索框输入一串词，倾向尾部防抖，等输入短暂停顿再查，但输入框本身仍同步显示文字。中文输入还要考虑 composition 状态，不能把拼音组合过程当成每次都已确认的查询内容。

3. 拖拽预览需要跟手，长时间防抖会让拖动期间几乎不更新。优先按动画帧合并视觉更新，把统计或昂贵计算另行节流。requestAnimationFrame 与绘制节奏配合，并不保证一个固定毫秒间隔的业务限频。

4. trailing 开不开，要看最后一个状态能不能丢，比如滚动停止后还需要同步最终位置。持续输入时普通防抖可能一直不触发；产品要求过程里也定期保存，可以采用有明确最长等待时间的防抖，别随意混用两个包装器。

5. 两者都只是减少函数调用次数，解决不了异步请求的先后顺序，也替代不了提交按钮的处理中状态。实际选择时把延迟反馈和减少计算之间的取舍说清楚，再结合操作耗时调整间隔，别把某个固定数值当成通用答案。

## 追问：搜索用了防抖，为什么结果仍可能显示成旧关键词？

1. 防抖只决定何时发出请求，不决定请求何时返回。用户先停顿触发「手机」，随后又输入「手机壳」并触发新请求，如果旧请求更慢，就可能在新结果之后完成，把页面重新写回旧内容。

2. 查询条件实际改变时增加版本号，发请求时捕获该版本，响应回来只接纳仍与当前条件一致的版本。版本在输入变化时就失效很关键，否则旧请求可能趁新一轮防抖尚未发出时写入页面。

3. 同时可以中止上一次请求来减少无用传输，但保留版本校验处理已经完成、无法取消等情况。清空输入框、切换筛选条件也要更新版本，并取消待执行的防抖调用，避免稍后又发出旧关键词的请求。

## 追问：自动保存应该直接使用防抖吗？

1. 文本编辑适合在停顿后保存，但如果用户持续打字，普通尾部防抖会一直等待。根据能接受的数据丢失范围，考虑最长等待时间，并明确页面上「正在保存」和「已保存」分别对应什么状态。

2. 定时触发也不代表保存一定成功，还需要处理失败重试和版本冲突。尤其两次保存并发时，旧内容可能后到服务端。这要通过按文档串行提交或服务端版本校验解决，仅在前端丢弃旧响应并不能修正数据库内容。

3. 离开页面时可以尝试执行待保存任务，但不能把 flush 等同于服务端确认写入。若任务本身返回 Promise，需要等待业务保存结果并提示未保存状态。直接关闭浏览器时还受生命周期限制，应按需求考虑本地草稿恢复。
