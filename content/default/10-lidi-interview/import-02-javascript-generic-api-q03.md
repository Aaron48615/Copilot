# 为什么不直接把所有接口返回都写成 any？

## 核心回答

1. 我不会把所有接口结果都写成 `any`，因为它会让调用处失去很多本来能提前发现的错误。比如金额应是数字，却被当成字符串调用方法，或者名称字段改名后页面仍使用旧名字，编译器都可能不再提醒。准确的类型也能帮助阅读接口，减少在页面代码和响应样例之间反复查找字段的时间。

2. 这种省事会向下传播：接口结果传给组件、工具函数和状态之后，越来越多地方不知道数据形状。之后想修改一个字段，就需要人工搜索并猜测哪些调用受影响，而准确类型能让编译检查帮助定位需要调整的位置。

3. 对真正未知的输入，我会先使用 `unknown`，它允许接收任何值，但要求使用前完成判断。例如先确认结果是对象，再检查列表是否为数组、条目是否有必要字段，通过验证后才把数据交给页面消费。

4. 泛型适合复用响应外壳，具体接口仍应声明自己的数据结构，但它也不能证明网络数据真实可靠。假设要逐步整理旧代码，我会优先补常用接口和容易出错的字段，把暂时保留的任意类型限制在较小范围内，而不是声称一改类型就消除了运行时错误。

## 追问：把 any 改成 unknown 后报错很多，怎样逐步处理？

1. 我会先从数据进入的位置处理，而不是在每个报错的组件里加断言。先明确一个接口真正需要哪些字段，写集中检查，把验证成功的结果交给下游，这样后面的代码可以共同使用可靠的类型。

2. 每个检查都应对应实际使用，例如展示标题就检查标题是字符串，计算数量还要检查数值是否有效。不能只判断结果非空就把整个对象认定为完整业务数据，那样只是把风险藏到了一个函数里。

3. 对暂时无法确认的接口，可以保留一个清楚标记的兼容位置，并限制它的调用范围。后续按接口逐个替换，比全局消除报错后宣布完成更可控，还需要用缺字段和错误字段的样例验证处理结果。

## 追问：后端字段经常变化，写类型是不是增加维护负担？

1. 类型确实需要跟着协议更新，但协议变化本身就可能影响页面，省掉类型不会省掉这些影响。它只是让错误从开发阶段推迟到运行阶段，尤其是字段改名或数字变字符串时，页面未必马上显出异常。

2. 如果接口存在稳定的文档或描述文件，可以考虑由它生成基础类型，再检查生成结果与实际响应是否一致。这只是可选的改进方式，生成工具不能保证服务端实现完全遵守文档，也不能替代关键数据的验证。

3. 我会把服务端原始结构和页面真正需要的结构适当分开，在转换位置处理字段差异。这样一次兼容修改不必散落到每个组件，但只有存在实际差异时才增加转换，避免为简单接口引入多余工作。
