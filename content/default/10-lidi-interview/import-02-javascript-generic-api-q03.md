# 为什么不直接把所有接口返回都写成 any？

## 核心回答

1. 接口结果别都写成 `any`。调用处会丢掉很多本来能提前发现的错误。金额应是数字，却被当成字符串去调方法；名称字段改名了，页面还在用旧名字，编译器都可能不再提醒。准一点的类型也方便阅读接口，少在页面代码和响应样例之间来回找字段。

2. 这种省事会往下传：接口结果进组件、工具函数、状态之后，越来越多地方不知道数据长什么样。以后改一个字段，就得人工搜索、猜哪些调用受影响。类型准的话，编译检查能帮着定位要改的地方。

3. 真正未知的输入，先用 `unknown`。它允许接收任何值，但用之前必须完成判断。先确认结果是对象，再检查列表是不是数组、条目有没有必要字段，过了验证再交给页面消费。

4. 泛型适合复用响应外壳，具体接口仍应声明自己的数据结构。它也证明不了网络数据真实可靠。整理旧代码时，优先补常用接口和容易出错的字段，暂时保留的任意类型限制在较小范围。改了类型，不等于运行时错误消失了。

## 追问：把 any 改成 unknown 后报错很多，怎样逐步处理？

1. 从数据进入的位置处理，别在每个报错的组件里加断言。先明确一个接口真正需要哪些字段，写集中检查，验证成功的结果交给下游。后面的代码可以共同使用比较可靠的类型。

2. 每个检查应对上实际使用：展示标题就检查标题是字符串，计算数量还要检查数值有没有效。不能只判断结果非空，就把整个对象当成完整业务数据。那样只是把风险藏进一个函数。

3. 暂时确认不了的接口，可以留一个清楚标记的兼容位置，并限制调用范围。按接口逐个替换，比全局消报错后宣布完成更可控。缺字段、错字段的样例也要用来验证处理结果。

## 追问：后端字段经常变化，写类型是不是增加维护负担？

1. 类型确实要跟着协议更新，但协议变化本身就可能影响页面，省掉类型省不掉这些影响。只是把错误从开发阶段推迟到运行阶段。字段改名，或数字变成字符串，页面未必马上显出异常。

2. 接口有稳定的文档或描述文件，可以考虑由它生成基础类型，再检查生成结果和实际响应是否一致。这是可选改进。生成工具保证不了服务端实现完全遵守文档，也替不了关键数据的验证。

3. 服务端原始结构和页面真正需要的结构适当分开，在转换位置处理字段差异。一次兼容修改就不必散落到每个组件。只有存在实际差异时才加转换，简单接口别引入多余工作。
