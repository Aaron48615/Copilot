# CSP 能防什么，配置时容易踩哪些坑？

## 核心回答

1. CSP 是网站通过响应头等方式交给浏览器的内容安全策略，用来限制脚本、样式、图片和连接这些来源。它能降低一部分 XSS 注入和数据外传的风险，但前提是限制合理。加上这个头，页面不会自动变安全。

2. 按资源用途来配：`script-src` 管脚本，`connect-src` 管接口连接，`img-src` 管图片。某些资源指令没单独设置时，会回退到 `default-src`。所以先整理页面真实依赖，再定允许范围。

3. 脚本策略里要特别小心内联代码和动态执行。需要保留的内联脚本，可以用每次响应生成的随机 nonce，或者内容对应的 hash 授权。固定 nonce、大范围的 `unsafe-inline`、不受控的第三方来源，都会把保护削弱。

4. 上线可以先用 Report-Only 收集问题，确认登录、懒加载、监控不被误伤，再逐步改成执行。报告要分清正常依赖漏了，还是异常注入。为了消警告把出现过的域名都加进白名单，不行。

5. CSP 还得配合输出编码、富文本清洗和后端权限检查。部署前用 Report-Only 确认合法资源和报告通道，再打开执行策略。随后用受控违规请求验证浏览器确实拦住了执行，并复测登录、懒加载和错误上报，确认合法功能还能用。

## 追问：nonce 与 hash 分别适合什么场景？

1. nonce 是服务端为当前响应生成的不可预测值，同时写进 CSP 和允许执行的脚本标签。它适合每次响应可能变化的内联脚本。生成、模板输出和缓存必须配合，静态代码里写死一个长期值不行。

2. hash 对应脚本的精确内容，适合内容固定的内联片段。脚本哪怕只改了空白，计算结果也可能变，策略要跟着更新。如果每次请求都插入不同数据，维护 hash 会比较麻烦。

3. 按页面生成方式来选，别为了省事同时放开 `unsafe-inline`。CDN 缓存整份 HTML 时，尤其要检查 nonce 有没有被长期复用。必要时改成稳定脚本文件，或者适合静态页面的 hash 策略。

## 追问：能不能只用 meta 标签配置 CSP？

1. meta 能设一部分 CSP，但它要等页面解析到相应位置才生效，而且不是所有能力都支持。比如 Report-Only 不能靠这种方式替代，限制页面被谁嵌入的 `frame-ancestors` 也不能依赖 meta。

2. 能控制服务器的话，优先用 HTTP 响应头，让策略在文档处理一开始就明确存在。静态托管也先看平台允不允许配安全响应头，别默认没有后端就只能靠页面标签。

3. 条件限制必须用 meta，就把它放在合适的靠前位置，并记下它覆盖不到的能力。验证仍以真实浏览器行为为准，尤其检查早期加载资源，以及多份策略同时存在的情况，别只留下虚假的安全感。
