# CSP 能防什么，配置时容易踩哪些坑？

## 核心回答

1. CSP 是网站通过响应头等方式交给浏览器的内容安全策略，用来限制脚本、样式、图片和连接等来源。它能降低部分 XSS 注入和数据外传的风险，但前提是限制合理，不是加上这个头页面就自动安全。

2. 我会先按资源用途配置，例如 script-src 管脚本，connect-src 管接口连接，img-src 管图片。没有单独设置某些资源指令时会使用 default-src 作为回退，所以应先整理页面真实依赖，再确定允许范围。

3. 脚本策略里要特别注意内联代码和动态执行。需要保留的内联脚本可以通过每次响应生成的随机 nonce，或者内容对应的 hash 授权；固定 nonce、广泛的 unsafe-inline 和不受控的第三方来源都会削弱保护。

4. 上线时我会先用 Report-Only 收集问题，确认登录、懒加载及监控不被误伤后再逐步执行。报告要区分正常依赖遗漏与异常注入，不能为了消除警告，把所有出现过的域名都加到白名单里。

5. CSP 仍需配合输出编码、富文本清洗和后端权限检查。部署前先用 Report-Only 确认合法资源与报告通道，再启用执行策略；随后用受控违规请求验证浏览器确实阻止执行，并复测登录、懒加载和错误上报，确认合法功能仍然可用。

## 追问：nonce 与 hash 分别适合什么场景？

1. nonce 是服务端为当前响应生成的不可预测值，并同时写入 CSP 和允许执行的脚本标签。它适合每次响应可能变化的内联脚本，但生成、模板输出和缓存必须配合，不能在静态代码里写死一个长期值。

2. hash 对应脚本的精确内容，适合内容固定的内联片段。脚本哪怕只改了空白，计算结果也可能改变，需要同步更新策略；如果每次请求都插入不同数据，维护 hash 就会比较麻烦。

3. 我会根据页面生成方式选择，不会同时为了方便放开 unsafe-inline。使用 CDN 缓存整个 HTML 时尤其要检查 nonce 是否被长期复用，必要时改用稳定脚本文件或适合静态页面的 hash 策略。

## 追问：能不能只用 meta 标签配置 CSP？

1. meta 能设置部分 CSP，但它在页面解析到相应位置后才生效，而且并非所有能力都支持。比如 Report-Only 不能用这种方式替代，限制页面被谁嵌入的 frame-ancestors 也不能依赖 meta 设置。

2. 如果能控制服务器，我会优先使用 HTTP 响应头，让策略在文档处理开始时就明确存在。静态托管也应先检查平台是否允许配置安全响应头，而不是默认没有后端就只能依赖页面标签。

3. 若受条件限制必须使用 meta，就把它放在合适的靠前位置，并记录它不覆盖的能力。验证仍以真实浏览器行为为准，尤其检查早期加载资源和多份策略同时存在的情况，避免产生虚假的安全感。
