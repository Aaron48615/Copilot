# ResizeObserver 和 window.resize 有什么区别？

## 核心回答

1. `window.resize` 盯的是浏览器视口大小，`ResizeObserver` 盯的是被观察元素的盒子尺寸。不是同一个事件换了写法。窗口没变，侧栏、网格、父容器一变，元素照样可能变宽变高。

2. 城市视图的图表在后台内容区，侧栏展开收起就是窗口没变、容器变了。直接观察图表容器，再调 `ECharts.resize`。不必每个改布局的按钮都去通知所有图表，依赖更简单。

3. `ResizeObserver` 不是盯所有 DOM 属性，内容改了也不一定触发。关键是观察的那个盒子尺寸变没变。只靠 `transform` 缩放，通常不等于布局盒子变了。别拿它代替 `MutationObserver`，也别当成任意视觉变化的监听。

4. 现在回调直接调 `resize`，没有另外限频。拖动布局时如果回调很密，可以用 `requestAnimationFrame` 把同一帧的更新合并。回调里别反复改被观察元素的尺寸，不然可能循环通知，布局也稳不住。

5. 卸载时 `disconnect`，把自己安排的动画帧或延迟任务也取消，再 `dispose` 图表。简单全屏页只听窗口，用 `window.resize` 也行。看容器变化从哪来，别把 `ResizeObserver` 当成所有场景唯一正确的做法。

## 追问：为什么观察器回调里改宽度可能产生循环？

1. 回调是因为尺寸变了才进来的。它又给同一个元素加宽度，尺寸再变，就可能一直转。浏览器对通知循环有保护，出警告不等于布局对了，别靠无视警告过日子。

2. 图表适配让 CSS 先把容器大小定住，回调只让图表去贴已经确定的尺寸。真要写尺寸，先比预期值和当前值，别每次通知都继续改。单纯加个 `setTimeout`，可能只是把循环拖到下一轮。

3. 加了 `requestAnimationFrame` 合并，还得看互相依赖消没消掉，不只是重复次数少了。侧栏过渡、连续拖动时容器最终要稳住，图表别反复抖。

## 追问：观察多个图表时，需要每张一个全局窗口监听吗？

1. 不需要。`ResizeObserver` 可以观察多个目标，也可以每张图表组件自己管一个观察器。前者要维护 DOM 到实例的映射，后者生命周期更局部。图表多少、组件怎么封装，再取舍。

2. 现在组件里自己管更好懂：挂载观察自己的容器，卸载再清，不用一个全局模块握着所有图表引用。以后要集中观察，删图表时目标和实例映射一起拿掉，不然还会留下没用的对象。

3. 优化前先看实际通知次数和 `resize` 开销。有多张图，不等于多个观察器一定是瓶颈。同样改一次布局，看更新次数和画面，选够简单、又能把资源放干净的那种。
