# SSE 为什么要处理残留 buffer？

## 核心回答

1. 手动读取 SSE 时要保留残留 buffer，因为网络流的分块不等于事件边界。一次 read 可能只有半个字段，也可能一次带来几个事件；如果每个 chunk 都直接 JSON.parse，遇到正常分片也会报错，这不是服务端一定发了坏数据。

2. 先处理字节到文本的转换，UTF-8 字符也可能跨两个 chunk。TextDecoder 应以流式方式持续解码，避免中文被切开后出现替换字符；文本解码状态和 SSE 事件残留是两层问题，不能只拼字符串就忽略字节边界。

3. SSE 按行解释字段，以空行分隔完整事件，还可能使用不同换行形式。多条 data 行需要按协议合并，注释、event、id 和 retry 等字段分别处理；只有收集到完整事件后，才按业务约定解析其中的数据。

4. 我会把未完成的行或事件保留到下一次读取，完整部分消费后及时释放，避免 buffer 一直增长。对于超长事件设置合理限制，流结束时检查是否缺少合法终止边界，不能把任意残留文本擅自当成一个完整消息发布。

5. 原生 EventSource 已实现这些协议解析，手动 buffer 主要是使用 fetch 读流等场景需要处理。比如需要自定义 Authorization 或 POST 时可能自行读取，但就要承担解析、取消和重连责任，不应只写一个按两个换行切割的简化示例就认定兼容所有 SSE。

## 追问：中文被拆到两个网络块，怎样保证不乱码？

1. 网络块可能在一个 UTF-8 字符的多字节编码中间结束，如果每块都独立解码，解码器会把不完整字节当成异常。应复用 TextDecoder 并使用流式解码，让它保留未完成的字节，等下一块补齐后再输出字符。

2. 解码后的文本再交给 SSE 行解析器，行尾或事件末尾仍可能跨块，所以字节解码正确不等于事件已经完整。两层状态分别管理，能清楚判断问题是字符解码失败，还是 JSON 数据尚未收齐。

3. 测试时可以把同一段含中文的事件按多个不同字节位置切开，包括一个字节一块的情况，确认最终结果一致。流结束时也要处理解码器收尾和协议完整性，不能默默丢掉坏尾部却显示成正常完成。

## 追问：一次收到多个 data 行，应该怎样处理？

1. SSE 允许一个事件出现多条 data 行，解析时要按协议使用换行连接它们，到空行才派发完整事件。不能看到一行 data 就立刻当成独立消息，否则服务端用多行文本表示一个事件时，客户端会错误拆分。

2. 之后才按业务格式处理合并后的 data，例如约定为 JSON 时再解析。字段分隔后可选空格、注释和不同换行都需要考虑，不能用全局 trim 随便删掉有意义的内容，也不能把所有以冒号开头的行当作业务正文。

3. 我会用多事件同块、单事件多行和事件跨块的样本验证，再加入 event 与 id 字段。原生 EventSource 可作为行为参考，手写解析器的测试应围绕协议边界，而不是只验证服务端恰好一次发一条 JSON 的情况。
