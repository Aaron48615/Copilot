# SSE 为什么要处理残留 buffer？

## 核心回答

1. 手动读 SSE 时要留残留 buffer，因为网络流的分块不等于事件边界。一次 `read` 可能只有半个字段，也可能一次带来几个事件。每个 chunk 都直接 `JSON.parse`，遇到正常分片也会报错。这不一定是服务端发了坏数据。

2. 先处理字节到文本的转换。UTF-8 字符也可能跨两个 chunk。`TextDecoder` 按流式方式持续解码，避免中文被切开后出现替换字符。文本解码状态和 SSE 事件残留是两层问题。只拼字符串、忽略字节边界，中文会乱。

3. SSE 按行解释字段，空行分隔完整事件，还可能遇到不同换行形式。多条 `data` 行要按协议合并。注释、`event`、`id`、`retry` 这些字段分别处理。收集到完整事件之后，再按业务约定解析里面的数据。

4. 未完成的行或事件留到下一次读取，完整部分消费后及时释放，避免 buffer 一直涨。超长事件设合理限制。流结束时检查是不是缺合法终止边界。任意残留文本擅自当成一个完整消息发布，会解析错。

5. 原生 `EventSource` 已经实现这些协议解析。手动 buffer 主要是用 `fetch` 读流这类场景才需要自己处理。需要自定义 `Authorization` 或 POST 时可能自行读，那就要承担解析、取消、重连。只写一个按两个换行切割的简化示例，兼容不了所有 SSE。

## 追问：中文被拆到两个网络块，怎样保证不乱码？

1. 网络块可能在一个 UTF-8 字符的多字节编码中间结束。每块都独立解码，解码器会把不完整字节当成异常。复用 `TextDecoder` 并使用流式解码，让它留下未完成的字节，等下一块补齐后再输出字符。

2. 解码后的文本再交给 SSE 行解析器。行尾或事件末尾仍可能跨块，所以字节解码正确，不等于事件已经完整。两层状态分别管，才能分清是字符解码失败，还是 JSON 数据还没收齐。

3. 把同一段含中文的事件按多个不同字节位置切开，包括一个字节一块，确认最终结果一致。流结束时处理解码器收尾和协议完整性。默默丢掉坏尾部却显示成正常完成，问题会被藏住。

## 追问：一次收到多个 data 行，应该怎样处理？

1. SSE 允许一个事件出现多条 `data` 行。解析时按协议用换行把它们连起来，到空行才派发完整事件。看到一行 `data` 就立刻当成独立消息，服务端用多行文本表示一个事件时，客户端会拆错。

2. 之后才按业务格式处理合并后的 `data`，比如约定是 JSON 再解析。字段分隔后的可选空格、注释、不同换行都要考虑。全局 `trim` 随便删有意义的内容不行，所有以冒号开头的行都当业务正文也不行。

3. 用多事件同块、单事件多行、事件跨块的样本验证，再加入 `event` 和 `id` 字段。原生 `EventSource` 可以当行为参考。手写解析器的测试围着协议边界转，别只验证服务端恰好一次发一条 JSON 的情况。
