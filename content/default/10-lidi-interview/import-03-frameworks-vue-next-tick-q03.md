# watch 里要不要再 nextTick？

## 核心回答

1. watch 里是否需要 nextTick，要看回调要做什么以及监听的刷新时机。只校验数据或发请求时不需要等待 DOM，因为响应式值已经改变；如果要读取由这次变化产生的元素，默认回调时机可能还拿到当前组件更新前的 DOM。

2. 需要读取更新后的 DOM，可以给 watch 设置 flush: 'post'，让回调在所属组件完成更新后执行。比如列表数量变化后读取高度，这个设置直接表达了目的，通常不需要在回调开头再无条件 await nextTick。

3. 如果在 post 回调里又修改了另一个会影响视图的状态，随后要读取由新修改产生的 DOM，则可能还需要等待那一轮更新。不能把“这是 post watcher”理解为从此以后所有后续赋值都立即更新，时机仍对应具体的一轮变化。

4. flush: 'sync' 会在响应式变化时同步触发，适合少量特定同步判断，但没有普通批量调度的同等收益。数组连续修改时可能触发很多次，不能为了读 DOM 更早执行而使用它，因为那时 DOM 反而可能尚未更新。

5. 我会避免“watch 内永远加 nextTick”的固定写法，优先把监听源缩小到实际字段。若监听导致自己依赖再次变化，还应检查是否循环；例如派生错误文本可以直接 computed，不必靠监听复制再等待，等待 API 无法修复不清楚的数据流。

## 追问：post watcher 里改了 v-if，再读 ref 为什么还是空？

1. post 只说明触发本次监听的那轮所属组件更新已经完成。回调内部刚把 visible 改成 true，产生的是下一轮视图更新，新元素还不一定存在，因此当前 ref 仍为空，并不矛盾。

2. 可以在修改 visible 后再 await nextTick，等待这次新修改完成，或把聚焦行为交给被显示组件自己的挂载逻辑。后者在组件封装良好时更清楚，因为输入框自身最知道何时存在以及如何处理焦点。

3. 还要检查 v-if 是否真的变成真、节点是否处于异步组件或过渡流程中。nextTick 只能保证 Vue 对当前已就绪内容的刷新，不会等待异步代码下载或完整动画，必要时使用对应组件的完成接口。

## 追问：深度 watch 加 nextTick，能避免大量更新吗？

1. 不能，nextTick 不会减少深度监听遍历对象的工作，也不会自动优化回调中的昂贵计算。它只是推迟回调里后续操作，若监听整个巨大表单，任何深层修改仍可能触发你不需要的业务处理。

2. 我会先缩小监听源，例如只关注某个字段或明确的几个 getter，派生值使用 computed。确实要处理批量修改时，再看默认调度已合并了哪些工作，避免把同步 watcher 和额外等待混在一起造成更多执行。

3. 性能验证应记录一次操作的监听执行和实际耗时，检查是否存在回调再次修改自身依赖。无论等待多少轮，这种循环或过大依赖范围都不会从根本上消失，需要调整状态关系而不是继续延后执行。
