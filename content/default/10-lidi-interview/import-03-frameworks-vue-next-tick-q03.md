# watch 里要不要再 nextTick？

## 核心回答

1. 看回调干什么，以及监听的刷新时机。只校验数据或发请求，不用等 DOM，响应式值已经变了。要读这次变化长出来的元素，默认回调时机可能还拿到当前组件更新前的 DOM。

2. 要读更新后的 DOM，给 `watch` 设 `flush: 'post'`，回调会在所属组件这轮更新之后跑。列表数量变了再读高度，这个设置就把目的说清楚了，回调开头不必无条件再 `await nextTick`。

3. `post` 回调里又改了另一个会影响视图的状态，接着要读这次新改动长出来的 DOM，那一轮可能还要等。`flush: 'post'` 不等于从此以后所有赋值都立刻更新 DOM，时机还是对着具体那一轮。

4. `flush: 'sync'` 在响应式变化时同步触发，少量特定同步判断才用。数组连续改几下可能触发很多次。为了更早读 DOM 去用它，那时 DOM 往往还没更新，更对不上。

5. 别做成“`watch` 里永远加 `nextTick`”。监听源尽量收到真正相关的字段。监听导致自己依赖再变，要查有没有循环。派生错误文案用 `computed` 就行，不必监听复制再等待。等待 API 修不好不清楚的数据流。

## 追问：post watcher 里改了 v-if，再读 ref 为什么还是空？

1. `post` 只说明触发这次监听的那一轮、所属组件已经更新完。回调里面刚把 `visible` 改成 `true`，那是下一轮视图，新元素这时候不一定在，`ref` 仍是空，说得通。

2. 改完 `visible` 再 `await nextTick`，等这轮新修改；或者把聚焦交给被显示组件自己的挂载逻辑。输入框自己最清楚什么时候存在、焦点怎么处理。

3. 再看 `v-if` 是不是真的变成真、节点是不是还在异步组件或过渡里。`nextTick` 保证的是 Vue 对当前已经就绪内容的刷新，不会等代码下载完或动画演完。那些用对应组件的完成接口。

## 追问：深度 watch 加 nextTick，能避免大量更新吗？

1. 不能。`nextTick` 不会减少深度监听遍历对象的活，也不会自动优化回调里的重计算。它只是把回调里后面的操作往后推。监听整份巨大表单，随便改一个深层字段，不需要的业务处理照样可能跑。

2. 先把监听源缩小，盯某个字段或明确的几个 getter，派生值用 `computed`。真要处理一批修改，再看默认调度已经合并了哪些。同步 watcher 再加额外等待，执行次数可能更多。

3. 记一次操作里监听跑了几次、实际花了多久，看回调有没有再改自己依赖。循环或依赖范围过大，等多轮都消不掉，要改状态关系，不是继续往后拖。
