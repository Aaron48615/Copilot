# watch 深度监听会拖慢吗？

## 核心回答

1. 深度监听可能变慢，因为它需要遍历相关嵌套数据以建立依赖，数据越大、层级越多，成本越明显。不能一概说 deep 很危险，但对几千条记录的完整树形对象，每次只是改一个小字段却监听全部内容，通常值得重新检查需求。

2. watch 一个 reactive 对象会形成隐式深层监听，而监听返回对象的 getter，默认更关注返回引用的变化，是否深层取决于配置。要知道自己实际监听了什么，不能只看到代码没有写 deep 就断言没有深层遍历。

3. 我会优先监听具体字段或 getter 数组，例如只关心分类和页码，就监听这两个值。需要计算过滤结果时用 computed，而不是深度 watch 整个列表再复制结果；缩小来源既能减少工作，也能让人看懂为什么回调会执行。

4. 深层原地修改时，回调里的新旧对象可能是同一个引用，深度监听不会自动给出历史快照。如果需要知道哪个字段变化，可以监听那个字段，或设计明确的更新动作；为了 diff 再不断深复制整棵对象，可能带来更多开销。

5. Vue 3.5 支持以数字限制深度，但实际可用性要看项目版本，限制后也可能不再通知更深层变化。我会用真实操作测量遍历和回调工作，避免把回调里的排序、请求或同步更新成本全部归因于 deep，调度与业务计算也要分别检查。

## 追问：deep watcher 的 oldValue 为什么和 newValue 一样？

1. 深层字段被原地修改时，外层对象没有换引用，新旧参数可能指向同一个对象。watch 的 deep 表达的是深层访问跟踪，并不承诺在每次修改前复制整份历史数据，因此不能直接靠两个对象参数还原之前的全部字段值。

2. 如果只关心数量变化，可以监听具体 getter，这样回调获得原始值的新旧值更直接。需要整体变更记录时，可以由更新动作明确携带修改字段，或者按必要范围保存快照，避免每次都复制整棵大对象。

3. 我会先确认业务为什么需要旧值，例如撤销、比较提示还是发送接口参数，再选择结构。不同目的需要的数据量不同，不能因为发现 oldValue 相同就立刻加入 JSON 深复制，让一个本来简单的字段监听变得昂贵且有类型限制。

## 追问：设置较小的 deep 深度，会不会漏掉业务变化？

1. 会，限制遍历深度就是选择不跟踪更深层访问，并非无损优化。若状态实际变化在更深一层，回调可能不执行，界面上的汇总或保存提示因此遗漏更新，所以必须先明确需要观察的数据范围。

2. 我更倾向对重要字段建立明确监听，或在业务动作后集中处理，而不是仅凭树很深就随意设一个数字。数字深度适合结构已知且边界清楚的情况，项目还需要使用支持该配置的 Vue 版本。

3. 验证应包含恰好位于边界内和边界外的修改，确认不通知的情况确实可接受。性能改善必须与功能完整性一起判断，不能只看到回调次数减少，就认为深度配置已经合理。
