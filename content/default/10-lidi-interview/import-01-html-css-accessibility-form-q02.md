# 弹窗打开后焦点怎么处理？

## 核心回答

1. 弹窗打开后，我会把焦点移到弹窗内合适的位置，并记录打开前的触发元素。普通填写弹窗可以聚焦第一个输入框；内容较长、需要先阅读说明的弹窗，可以让标题临时可聚焦。不是所有弹窗都应该一打开就跳到确认按钮。

2. 模态弹窗打开期间，背景内容应不可交互，Tab 和 Shift+Tab 在当前弹窗范围内移动。优先考虑原生 dialog 的 `showModal()` 和成熟组件提供的行为，再补具体业务需要，避免只画一个遮罩却让键盘继续进入背景表单。

3. 关闭时通常把焦点还给触发按钮，但要确认这个按钮仍然存在。比如弹窗完成删除后，对应列表行已经移除，就应把焦点放到相邻条目或列表操作入口，让用户能接着完成任务，而不是落到不存在的 DOM 上。

4. 我还会处理 Escape、显式关闭按钮和异步内容变化。弹窗没有可聚焦子项时需要有合理的焦点落点，卸载时要清理监听和恢复被修改的页面状态。验证应覆盖打开、正反向切换、关闭和再次打开，不能只测试第一次点击。

5. 焦点移动还应等待弹窗节点真正出现，不能在设置打开状态的同一处假定所有子元素已完成渲染。若有进入动画，也要确保焦点落点不会被滚动到屏幕外，让用户一打开就能看到自己接下来要操作的位置。

## 追问：删除确认弹窗初始焦点应放在哪个按钮？

1. 我会先看操作的风险和说明长度。删除难以恢复时，通常把焦点放在取消等较安全的操作上，避免用户顺手按回车就执行破坏性动作；这属于交互设计选择，不是所有弹窗统一使用同一规则。

2. 如果正文很长，直接聚焦底部按钮可能把前面的说明滚走，可以先聚焦标题或开头说明，让用户从上下文开始阅读。静态节点使用负值 tabindex 获得程序焦点，不必加入日常 Tab 顺序。

3. 验证时我会从触发按钮用键盘打开，观察第一眼看到的内容和读屏宣布的名称，再确认 Tab 能自然到达两个操作。危险按钮的文案要具体说明动作，不能只有模糊的“确定”而缺少删除对象。

## 追问：弹窗内容异步加载时如何避免焦点丢失？

1. 可以先把焦点放到稳定的标题或容器中，让加载状态明确可见。不要立即尝试聚焦尚未挂载的输入框，也不要在每次数据刷新时重复调用 focus，否则用户刚开始操作就会被打断。

2. 加载完成后，根据任务需要决定是否移动到首个字段。如果用户已经主动进入某个控件，就保留当前位置；如果当前只是等待输入，可以在节点确实渲染后完成一次有意的焦点移动。

3. 内容刷新可能移除当前按钮，此时应选择附近的合理落点，并重新计算可聚焦范围。失败状态也应有重试和关闭入口，不能出现只剩加载占位、键盘找不到出口的情况，关闭后的焦点恢复同样要验证。
