# requestAnimationFrame 解决什么问题？

## 核心回答

1. requestAnimationFrame 主要解决更新时机与浏览器渲染节奏配合的问题。自己写拖动或 Canvas 动画时，可以请求在下一次重绘前执行回调，让状态更新更接近浏览器准备画面的时候，比固定间隔的定时器更适合视觉更新。

2. 它是一次性请求，需要继续动画时再预约下一次。回调次数不是固定每秒六十次，会受到屏幕刷新率、设备负载和页面可见性影响；因此我会根据回调时间戳计算进度，而不是每次回调固定移动几像素，否则高刷屏上速度可能不同。

3. 它也不是独立线程，回调里昂贵的计算仍会占用主线程。把大数组排序放进去不会自动变快，修改宽高也仍可能触发布局；实际做法是控制每帧工作量，尽量合并视觉更新，必要时把可分离计算交给 Worker。

4. 停止动画或组件卸载时，我会取消尚未执行的请求，并清理相关状态。后台标签页的回调可能暂停或被限制，恢复时要处理时间跨度，不能把它当作准确计时器。业务倒计时应基于真实截止时间，动画回调只是负责把当前结果显示出来。

## 追问：拖动事件很密集时怎样配合 requestAnimationFrame？

1. 指针事件里只记录最新坐标，如果已经预约了本帧更新，就不再重复预约。回调执行时读取最新位置并更新视觉状态，这样同一帧里多次移动可以合并，避免每个事件都触发一轮 DOM 修改。

2. 拖动过程还要区分视觉位置和最终业务状态。可以用 transform 表达临时偏移，在结束时提交最终位置；如果每次移动都引起整个页面状态更新，即使用了回调，也可能仍然产生大量无关渲染。

3. 松开指针或组件卸载时要结束拖动并取消剩余回调，确认最后位置没有丢失。还应处理指针离开元素和取消事件，必要时使用指针捕获，否则只优化刷新频率，交互仍可能出现拖到一半失控的问题。

## 追问：动画恢复后突然跳很远应该怎么处理？

1. 先检查是否把上次时间戳一直保留到页面重新可见。页面在后台停了一段时间后，下一帧与上一帧的差值可能很大，直接用速度乘时间差就会产生很大的位移，这与普通掉一两帧不同。

2. 装饰性动画可以在重新可见时重设起点，或者限制单次模拟步长，避免突然跳跃。真实倒计时则应该重新根据截止时间计算，不应通过限制时间差把已经过去的业务时间悄悄补回来。

3. 因此恢复策略要由动画含义决定。比如粒子效果可以暂停后接着播，比赛剩余时间必须追上当前时刻；我会分别测试切后台、锁屏和返回，确认显示既流畅又符合真实状态。
