# 半截回答怎么处理？

## 核心回答

1. 我会保留已经收到的文字，但把状态明确标为中断，不能让半截内容看起来像完整答案。还要区分用户主动停止、网络断开和服务端失败，因为三种情况对应的提示与下一步操作不同，重试也不应一律自动进行。

2. 网络断开只说明客户端没有继续收到数据，服务端可能仍在生成，也可能已经完成。我会先按 generationId 查询状态；若服务端有完整快照，就用同一版本的快照核对当前文本，避免把“最后的 done 丢了”误判成必须重生成。

3. 真正恢复同一次生成，需要服务端保存可回放事件或足够的快照，并支持客户端携带最后接纳序号重连。客户端重放时去重，序号缺口则请求补齐；单靠重新建立 SSE 连接，并不能保证模型会从断开的字继续输出。

4. 重新生成属于新的尝试，我会分配新的生成 id，旧的半截回答可作为历史版本保留并由界面切换。是否长期存多版本取决于产品需求和存储成本，不是技术上绝对不能覆盖；但新旧任务不能共享一个可随意追加的缓冲区。

5. 对用户展示已保留内容和明确操作，例如重连获取结果、重新生成或复制当前文字。服务端恢复能力尚未实现时，我会直接说明只能重新生成；如果继续完善，我会增加状态核对和检查点保存，而不把前端缓存说成可靠的服务端持久化。

## 追问：“继续生成”和“断点续传”是不是一回事？

1. 断点续传关注同一个生成任务的数据交付，服务端已经生成但客户端没收到的事件，可以按游标补发。前提是这些事件仍可获取，而且序号、生成 id 和权限匹配；它不需要重新让模型猜测之前输出了什么。

2. “继续生成”通常是把前文作为上下文重新请求模型，属于新的生成行为。模型可能重复上一句话、改变结构或补出不同内容，所以不能向用户保证它与原任务无缝衔接，应明确提示这是接着现有内容继续尝试。

3. 我会把两个入口区分开：能恢复原任务时先恢复，任务已失败且没有后续数据时再提供继续或重新生成。上下文长度、额外调用费用和重复内容处理也需要考虑，不能在每次断网后都自动发起新的模型请求。

## 追问：用户点停止之后，还收到几个片段怎么办？

1. 点击停止后，我会立即改变本地状态并停止接纳该任务的新展示更新，同时取消客户端读取。由于事件可能已进入回调队列，处理函数还要检查当前生成 id 和取消标记，不能只依赖连接已经关闭这一件事。

2. 浏览器 abort 不保证服务端生成同步停止，所以还需要按接口约定请求取消任务，并让服务端尽可能中止上游调用。若取消与完成同时发生，应以服务端确认的最终状态核对，前端不要把自己的取消请求当成已取消成功。

3. 已展示的内容可以保留为主动停止的回答，未展示缓冲要按事先约定处理，避免点击后文字还持续跳动。若用户马上重新生成，新任务必须使用新 id；迟到的旧片段、错误或完成通知都不能改写新回答。
