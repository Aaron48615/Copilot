# 半截回答怎么处理？

## 核心回答

1. 已经收到的文字留着，状态明确标成中断，半截内容别看起来像完整答案。用户主动停止、网络断开、服务端失败要分开，提示和下一步操作不一样，重试也不该一律自动跑。

2. 网络断开只说明客户端没再收到数据，服务端可能还在生成，也可能已经完成。按 `generationId` 去查状态。服务端有完整快照，就用同一版本的快照核对当前文本。别把「最后的 done 丢了」误判成必须重生成。

3. 真要恢复同一次生成，服务端得保存可回放事件或足够的快照，并支持客户端带着最后接纳的序号重连。客户端重放时去重，序号有缺口就请求补齐。单靠重新建立 SSE 连接，保证不了模型会从断开的那个字接着吐。

4. 重新生成是新的尝试，分配新的生成 id。旧的半截回答可以当历史版本留着，界面上能切换。多版本长期存不存，看产品需求和存储成本，技术上不是绝对不能覆盖。新旧任务不能共用一个能随便追加的缓冲区。

5. 给用户看已经留下的内容，以及明确操作：重连拿结果、重新生成、复制当前文字。服务端恢复能力还没做，就直接说目前只能重新生成。后面要补，就加状态核对和检查点保存。前端缓存说不成可靠的服务端持久化。

## 追问：“继续生成”和“断点续传”是不是一回事？

1. 断点续传关心的是同一个生成任务的数据交付。服务端已经生成、客户端没收到的事件，可以按游标补发。前提是这些事件还能拿到，序号、生成 id、权限也对得上。它不需要再让模型猜之前输出了什么。

2. 「继续生成」通常是把前文当上下文，重新请求模型，属于新的生成。模型可能重复上一句话、改结构、补出不同内容。不能向用户保证跟原任务无缝衔接，要明确提示：这是接着现有内容再试一次。

3. 两个入口分开：能恢复原任务就先恢复；任务已经失败、后面没有数据了，再提供继续或重新生成。上下文长度、额外调用费用、重复内容怎么处理，也要考虑。别每次断网都自动发起新的模型请求。

## 追问：用户点停止之后，还收到几个片段怎么办？

1. 点停止之后马上改本地状态，停止接纳这个任务的新展示更新，同时取消客户端读取。事件可能已经进了回调队列，处理函数还要检查当前生成 id 和取消标记。连接已经关了，这一件事不够。

2. 浏览器 abort 保证不了服务端生成同步停。还要按接口约定请求取消任务，让服务端尽量中止上游调用。取消和完成同时发生，以服务端确认的最终状态为准。前端别把自己的取消请求当成已经取消成功。

3. 已经展示的内容可以留着，当成主动停止的回答。没展示的缓冲按事先约定处理，点完之后文字别还在跳。用户马上重新生成，新任务必须用新 id。迟到的旧片段、错误、完成通知，都不能改写新回答。
