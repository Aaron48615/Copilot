# Vue 的 Diff 算法是怎么工作的？

## 核心回答

1. 数据变了不是整页重画。Vue 用虚拟节点在 JS 里描述 DOM，更新后再生成一棵新树，Diff 比较新旧两棵，把需要的改动 `patch` 到真实 DOM。它不做任意两棵树的理论最优解，按类型、层级、`key` 高效对应。组件重新算一遍，不等于整棵 DOM 删掉重建。比较通常只在同一层，实际业务里节点很少跨层搬。

2. 同类型继续比属性和子节点，类型不同一般要替换。列表里的 `key` 是业务身份，稳定 `key` 能让排序后节点和组件状态还对得上原来那条。用下标或随机 `key`，头部插入一条，后面身份全错位，局部输入还可能串到另一项。这首先是对不对，其次才是快不快。

3. Vue 2 带 `key` 的子节点更新常用双端比较，两头找能复用或移动的，对不上的再查找处理。Vue 3 会先处理头尾相同的那段，中间变化建映射，再用最长递增子序列减少某些场景下的移动。

4. Vue 3 还靠编译结果认出静态内容和动态部分：静态提升、补丁标记，减少运行时没意义的比较。这些依赖具体模板和更新路径，不是每次更新都完整跑同一种列表算法，也不能承诺所有操作都严格线性时间。被问 Vue 3 为什么快，常见答案会把 Proxy 和这套编译优化放在一起说。

5. 业务侧给框架正确输入：稳定身份、合理的状态范围、节点别过量。行特别多、模板里计算很重，还是会慢，算法优化替不了分页和合理计算。解释性能结合实际更新场景，别只背“双端”“最长递增子序列”几个词。

## 追问：最长递增子序列为什么能减少移动？

1. 看新顺序里可复用节点对应的旧位置。有一组旧位置保持递增，它们彼此的相对顺序没被打乱，可以尽量留在原来的相对位置。找到较长的这样一组，移动就集中在不属于这组的节点上。

2. 旧顺序甲乙丙丁，新顺序甲丙乙丁，一部分节点相对次序还在，不必全搬。框架再结合插入位置处理剩下的。新增、删除、节点类型对不上，还是要单独认。

3. 这是带 `key` 的子节点那条更新路径上的优化，不是每棵树都先求一次序列。业务提供稳定 `key`，节点才能被对上。随机 `key` 让原节点对不上，移动优化再好也留不住本该复用的身份。

## 追问：Vue 3 编译器知道静态内容，对更新有什么帮助？

1. 模板里有些结构和文本不随状态变，编译器可以标记或提升，运行时不必像完全未知的手写树那样反复做所有工作。旁边计数在变，固定说明区域不必每次把静态属性再比一遍。

2. 动态节点上的补丁标记能指出重点，比如主要查 class、文本或某几个 props。运行时要盯的范围小了，但仍看模板怎么写。动态插槽、复杂结构，不能一律按最理想的静态路径理解。

3. 这是框架实现上的优势，业务模板里该有的数据设计不能省。每行都调很重的函数，或一次渲染成千上万节点，成本还在。编译优化减的是一部分重复工作，任意页面不会因此自动变轻。
