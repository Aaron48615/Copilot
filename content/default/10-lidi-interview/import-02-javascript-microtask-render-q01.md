# MutationObserver 在哪一类？

## 核心回答

1. MutationObserver 的通知通过微任务安排，不是在每次修改 DOM 的语句中同步调用回调。当前同步代码可以先完成多次修改，之后在微任务检查点交付记录，所以回调看到的节点状态可能已经包含这一轮后续修改。

2. 我会区分一次回调和一条变更记录：多次修改可能在同一次通知中交付，但不代表所有修改都被压成一条记录。假设连续插入几个子节点，处理时应查看记录数组里的目标、类型和新增节点，而不能只处理第一条就算完成。

3. 它与 Promise 回调都涉及微任务，先后要看具体排队过程，不能简单背成观察器永远先执行或永远后执行。回调里再修改被观察的内容，还可能安排新的通知，队列持续产生工作时，同样会推迟后面的任务和渲染机会。

4. 观察到 DOM 变化也不等于已经发生屏幕绘制，更不等于所有样式与几何尺寸变化都会触发它。它关注配置范围内的节点、属性和文本变更；假设关心元素尺寸，应评估 ResizeObserver，而不是仅靠 DOM 变更猜测布局结果。

5. 实际使用时我会缩小观察范围，例如只观察目标容器和指定属性，并在不再需要时断开观察。假设回调要补充节点标记，还应先判断标记是否已符合要求，避免自己写入、自己再次收到通知的循环，把一次小变更变成持续工作。

## 追问：在观察器回调里修改 DOM 如何避免循环通知？

1. 先判断写入是否真的有必要，例如目标节点已经带有需要的标记时直接跳过。这样第二次通知即使出现，也不会继续制造同样的修改；关键是让重复处理能够稳定下来，而不是默认浏览器会替业务去掉无意义写入。

2. 还可以收窄观察配置，只关注业务真正依赖的属性，或把自己的展示标记放到不需要观察的位置。假设只关心节点增删，就不必同时订阅所有属性变化，减少无关记录比在回调中反复过滤整棵树更直接。

3. 临时断开再恢复也是一种办法，但暂停期间的变化可能被漏掉，必须接受这个边界。我会优先设计可重复执行且不会继续改动的处理逻辑，只有确实允许忽略中间变化时才暂停观察，并验证外部修改不会因此丢失。

## 追问：disconnect 和 takeRecords 应该怎么配合？

1. `takeRecords()` 会取出并清空尚未交付的记录，但不会自动调用回调，也不会停止后续观察。假设需要在某个同步边界先处理积压变化，可以主动取出记录，交给已有处理逻辑，之后观察仍然继续。

2. `disconnect()` 则停止观察，并清除这个观察器尚未交付的记录。因此如果收尾时不能丢掉这些变化，应先取出记录，再断开并决定如何处理，而不是断开后才去查询，期待原来的队列仍然完整保留。

3. 如果组件已经销毁，业务可能反而希望直接丢弃旧记录，避免更新失效界面。此时就不必为了形式完整再次执行回调；我会先明确收尾是保留最终变更还是取消后续工作，并同时清理自己保存的节点和闭包引用。
