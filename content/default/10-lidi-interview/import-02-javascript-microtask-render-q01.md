# MutationObserver 在哪一类？

## 核心回答

1. MutationObserver 的通知走微任务，不是每次改 DOM 的语句里同步调回调。当前同步代码可以先做完多次修改，之后在微任务检查点再交付记录。所以回调看到的节点状态，可能已经包含这一轮后面的修改。

2. 一次回调和一条变更记录不是一回事。多次修改可能在同一次通知里交付，但不代表所有修改都被压成一条记录。连续插入几个子节点，处理时要看记录数组里的目标、类型和新增节点，只处理第一条不算完。

3. 它和 Promise 回调都涉及微任务，先后要看具体排队过程，不能背成观察器永远先执行或永远后执行。回调里再改被观察的内容，还可能安排新通知。队列一直有活，后面的任务和渲染机会同样会被往后推。

4. 观察到 DOM 变化，不等于屏幕已经画出来，也不等于所有样式和几何尺寸变化都会触发它。它关注配置范围内的节点、属性和文本变更。关心元素尺寸，应评估 ResizeObserver，别只靠 DOM 变更去猜布局结果。

5. 实际用时把观察范围缩小，比如只观察目标容器和指定属性，不再需要时断开观察。回调要补节点标记，先判断标记是不是已经符合要求，免得自己写入、自己再收到通知，把一次小变更变成持续工作。

## 追问：在观察器回调里修改 DOM 如何避免循环通知？

1. 先判断这次写入是不是真有必要。目标节点已经带着需要的标记，就直接跳过。这样第二次通知就算出现，也不会继续制造同样的修改。关键是让重复处理能停下来，浏览器不会替业务去掉无意义写入。

2. 还可以收窄观察配置，只关心业务真正依赖的属性，或把自己的展示标记放到不需要观察的位置。只关心节点增删，就不必同时订阅所有属性变化。少收无关记录，比在回调里反复过滤整棵树更直接。

3. 临时断开再恢复也是一种办法，但暂停期间的变化可能被漏掉，这个边界要接受。优先写成可重复执行、不会继续改动的处理逻辑。只有确实允许忽略中间变化时才暂停观察，并核对外部修改不会因此丢失。

## 追问：disconnect 和 takeRecords 应该怎么配合？

1. `takeRecords()` 会取出并清空尚未交付的记录，但不会自动调回调，也不会停后续观察。某个同步边界要先处理积压变化，可以主动取出记录，交给已有处理逻辑，之后观察仍然继续。

2. `disconnect()` 会停止观察，并清掉这个观察器尚未交付的记录。收尾时不能丢掉这些变化，应先取出记录，再断开并决定怎么处理。断开后再去查，原来的队列不一定还完整留着。

3. 组件已经销毁，业务可能反而希望直接丢掉旧记录，避免去更新已经失效的界面。这时不必为了形式完整再执行一遍回调。先明确收尾是保留最终变更还是取消后续工作，同时清掉自己保存的节点和闭包引用。
