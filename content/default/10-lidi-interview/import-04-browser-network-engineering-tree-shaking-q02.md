# 动态 import 一定能减小首屏吗？

## 核心回答

1. 动态 import 不一定减小首屏成本，它只是提供异步加载边界。只有模块原本在初始路径中，现在确实推迟到后续需要时再加载，才有机会减少首屏传输、解析和执行，例如把大型导出工具延迟到用户点击导出时。

2. 如果页面初始化就立即执行 import，拆成文件后依旧马上下载，可能只增加请求和依赖等待。若同一个库又被其他入口静态导入，它也可能仍留在初始包或共享包中，所以不能只看源码多了一处动态语法。

3. 预加载和预取也影响结果。构建器可能提前提示相关依赖，开发者也可能主动预取，首屏到底减少了多少必须看真实网络；共享依赖的拆分既可能改善缓存，也可能让当前页仍需加载一个很大的公共文件。

4. 延迟加载还把一部分等待转移到用户操作时，应该提供加载和失败状态。对于即将使用的功能可以在合适时机预取，但不能把所有候选页面提前下载又宣称已经节省首屏流量，收益与代价要同时说明。

5. 我会比较改动前后的初始资源、脚本执行和用户首次打开功能的耗时，并检查旧版本 chunk 的可用性。优化目标是整个访问过程合理，不是 chunk 数量更多，也不是入口文件单独变小就算完成。

## 追问：动态 import 放在组件顶层，为什么仍然可能立即加载？

1. 动态导入的触发时机取决于那行代码什么时候执行。如果模块顶层在入口初始化时就调用 import，即使返回 Promise，浏览器也会马上开始获取，并不会自动等组件显示或用户点击才启动。

2. 我会把真正非首屏功能的导入放在明确的触发位置，或者使用框架的懒加载机制，同时检查是否有其他静态导入路径。只把 import 声明改写成函数调用，但仍在启动阶段执行，通常不足以改变关键路径。

3. 验证时用冷缓存看请求发起时间，再打开对应功能确认资源才被需要。也要避免每次交互都重复创建初始化副作用，模块通常会缓存求值结果，但业务实例和事件监听仍需要按功能生命周期管理。

## 追问：懒加载后点击按钮变慢，怎样折中？

1. 先确认等待主要来自文件下载、模块执行还是功能初始化，再选择措施。下载占主导时可以在用户明确表现意图后预取；执行很重时则需要减少初始化工作，单纯提前下载并不会消除主线程计算成本。

2. 界面先给出真实的加载反馈，并允许失败重试，避免用户以为按钮没反应而连续点击。对于大多数用户马上使用的功能，完全延迟也许不合适，可以把基础能力提前加载，重功能再按需准备。

3. 我会同时比较首屏和首次交互体验，记录未使用的预取流量。没有哪个时机对所有访问路径都最优，应该按真实使用概率取舍，不能为了让首屏报告好看，把所有成本都推到关键操作之后。
