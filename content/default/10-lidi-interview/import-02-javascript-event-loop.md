# JavaScript 事件循环是怎样执行的？

## 核心回答

1. 就浏览器主线程来说，JS 一次只能干一件事。一段同步代码在跑的时候，就算定时器到点了也插不进来，得等这段跑完。

2. 当前这段跑完，会先把已经排好的微任务清掉，比如 `Promise.then`。清的过程中新塞进来的微任务也会接着跑，所以微任务套微任务，页面可能一直更新不了。定时器、点击这类算宏任务，要等微任务告一段落才轮到。

3. 一个常写的例子：先 `setTimeout(fn, 0)`，再 `Promise.resolve().then(...)`，最后 `console.log`。一般会先看到 log，再看到 then，最后才是定时器。`new Promise` 括号里的函数本身是同步跑的，不是异步。

4. 页面不是每跑完一个任务就画一帧，浏览器自己找空隙画。定时器、点击、网络回调也不一定排在同一个队里，别当成完全按注册顺序来。Node 的队列划分不一样，别把浏览器这套直接套过去。

## 追问：为什么连续等待已经完成的 Promise，页面仍然可能卡住？

1. `await` 一个已经完成的 Promise，后面的代码会进微任务，但这不等于把时间让给页面去画。要是循环每一圈很快又排出下一个微任务，微任务会一直清，界面还是没机会更新。

2. 所以把大循环改成 `async` 函数，计算量没变少，页面照样可能卡。得看主线程有没有真正空出来给别的任务。

3. 数据量大就分批，中间用定时器让一让，或者把纯计算丢到 Worker。一批多大、来回传数据费不费，得实际测，不能说改成 `async` 就好了。

## 追问：设置零延迟定时器，为什么不代表马上执行？

1. `setTimeout(fn, 0)` 只是说「尽快具备运行条件」，不是「现在立刻跑」。当前脚本还在跑、微任务还没清完，或者前面还有别的活，这个回调就得接着等。

2. 浏览器对嵌套定时器、后台标签页还有额外限制，别拿 0 毫秒当精确计时。用它拆大任务，目的是让出执行机会，不是保证每批刚好隔固定那么久。

3. 做动画更适合跟帧走的 `requestAnimationFrame`，按时间戳算进度。倒计时按目标时间重算剩余量，别默认每次回调都刚好走过了一秒。
