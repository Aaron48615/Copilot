# JavaScript 事件循环是怎样执行的？

## 核心回答

1. 我会先限定在浏览器主线程讨论，事件循环负责协调脚本、事件回调和页面更新。当前同步代码执行时，定时器到期不会把它打断，异步回调要等到适合的调度时机才进入执行过程。

2. 一般面试里的宏任务对应规范中的任务，比如定时器回调或用户交互相关任务。不同来源可以有不同任务队列，因此不能把所有异步事件想成一个严格按注册时间排序的总队列，调度还受宿主规则影响。

3. 当前任务结束后的微任务检查点，会处理已经排队的微任务，包括已经排队的 Promise 回调。处理过程中加入的微任务通常也会继续执行，所以不断追加微任务可能迟迟不让下一项任务获得机会。

4. 例如同一段脚本先注册零延迟定时器，再注册已兑现 Promise 的回调，最后直接打印消息。没有其他干扰时，先看到同步打印，再看到 Promise 回调，最后才是定时器；Promise 的执行器本身则是同步运行的。

5. 浏览器会在合适的渲染机会更新页面，不保证每个任务后都绘制一帧。如果讨论 Node，就要另看它的阶段调度和额外队列，不能把浏览器的简化顺序直接当成所有 JavaScript 环境的规则。

## 追问：为什么连续等待已经完成的 Promise，页面仍然可能卡住？

1. 等待会把后面的继续执行安排到微任务中，但这并不等于把执行机会交给浏览器绘制。假如循环每轮都很快产生下一个微任务，当前检查点就可能持续处理这些工作，界面仍然没有更新机会。

2. 所以把大循环简单改成异步函数，不能保证长计算消失。计算总量没有减少，而且微任务之间接力也可能阻塞交互；判断是否改善，应看主线程是否真正出现可供其他任务执行的空隙。

3. 假如需要处理大量数据，我会考虑分批并通过定时器等任务调度让出主线程，或把适合的纯计算交给工作线程。批次大小和通信成本需要实际验证，不能先声称改用某个异步关键字就解决了卡顿。

## 追问：设置零延迟定时器，为什么不代表马上执行？

1. 延迟参数只影响何时具备运行条件，不代表回调占有主线程的准确时刻。当前脚本还在执行、微任务尚未处理完，或者前面还有其他工作时，定时器回调都可能继续等待。

2. 浏览器还会根据嵌套定时器和页面状态应用相应限制，所以不能拿零延迟做精确计时。假如用它拆分大任务，目的是提供调度机会，而不是保证每一批恰好间隔某个固定毫秒数。

3. 如果需求是动画，我会考虑使用与渲染机会配合的动画帧回调，并根据时间戳计算进度。若是业务倒计时，则应该按目标时间重新计算剩余量，避免把每次定时器回调都当成准确走过了一秒。
