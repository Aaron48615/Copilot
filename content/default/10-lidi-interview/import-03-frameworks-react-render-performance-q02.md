# 大列表怎么优化？

## 核心回答

1. 我会先分清列表慢在获取、处理还是显示。接口返回大量数据可能耗时，前端排序筛选也可能占用主线程，真正挂载大量节点又涉及布局绘制；只看列表行数就立刻加 memo，可能没有碰到主要耗时来源。

2. 如果用户不需要同时查看全部记录，优先考虑分页或按需获取，减少传输和处理量。已经拿到的数据中，筛选条件没变时可以缓存昂贵计算，但要看真实耗时，简单的几条数据没有必要为缓存增加复杂依赖。

3. 当节点数量本身成为问题时，可以使用虚拟列表，只渲染可见区域和少量缓冲行。数据仍可保留在内存中，滚动时替换可见内容；它减少的是 DOM 和渲染负担，不会自动减少首次下载全部数据的流量。

4. 行组件保持稳定 key 和尽量精简的 props，选择状态可按行提供，避免每次只选中一行却让全部行获得新对象。确实昂贵的行再使用 memo，图片尺寸和懒加载也要处理，否则滚动可能因资源加载和布局变化跳动。

5. 虚拟化有动态高度、焦点、查找和无障碍方面的代价，不能默认所有列表都适合。我会用真实滚动、筛选和选中操作比较效果，确认低性能设备上响应改善，也没有因为行卸载而丢失正在编辑的内容。

## 追问：虚拟列表中输入框草稿为什么容易丢失？

1. 离开可视区域的行可能被卸载，行内 useState 和非受控输入的值也随实例一起消失。滚回来创建的是新的行组件，稳定 key 能正确识别项目，但不能保证已经卸载的实例一直保存在内存里。

2. 需要保留的草稿可以按业务 id 存在列表父级或专门的编辑状态中，行只读取自己的值并回传变化。保存的是业务输入，不需要为了草稿而把全部行节点都留在 DOM 中，否则会失去虚拟化的意义。

3. 还要考虑编辑时滚动、校验错误定位和提交数据来源。提交不能只遍历当前可见输入框，因为未显示的项目也可能被修改；测试应让用户改一行、滚远再返回，确认内容和错误状态仍正确。

## 追问：useDeferredValue 能不能替代虚拟列表？

1. 不能，useDeferredValue 主要帮助把昂贵的非紧急更新延后，让输入等紧急交互优先得到响应。最终若仍要渲染上万行，计算和 DOM 成本并没有因此消失，只是调度时机发生了变化。

2. 例如搜索框立即显示新文字，而列表暂时保留上一次结果，可以对列表使用延后的查询值。界面最好说明结果正在更新，避免用户以为当前看到的数据已经匹配最新输入；它也不等于固定时间的请求防抖。

3. 节点过多时仍需分页或虚拟化，纯计算太重时可以优化算法或使用 Worker。不同方法处理不同问题，我会先从性能记录确认主因，再组合使用，不把某个并发 API 当成自动加速开关。
