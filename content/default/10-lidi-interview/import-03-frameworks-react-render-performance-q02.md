# 大列表怎么优化？

## 核心回答

1. 先分清慢在获取、处理还是显示。接口吐大量数据会耗时，前端排序筛选也会占主线程，真把大量节点挂上去还有布局绘制。只看行数就加 `memo`，可能根本没碰到最耗时的那一段。

2. 用户不需要一次性看完全部记录，优先分页或按需取，少传少算。已经拿到的数据，筛选条件没变，贵的计算可以缓存。就几条数据，没必要为缓存搞一套复杂依赖。

3. 节点数量本身成了问题，再用虚拟列表，只渲染看得见的区域加一点缓冲行。数据可以还在内存里，滚动时换可见的那些。它减的是 DOM 和渲染负担，第一次把全部数据下载下来的流量不会自动变少。

4. 行组件用稳定 key，props 尽量精简。选中状态可以按行给，别只选中一行却让所有行都拿到一个新对象。真贵的行再 `memo`。图片尺寸和懒加载也要处理，不然滚动会因为资源加载、布局变化乱跳。

5. 虚拟化在动态高度、焦点、查找、读屏这些地方有代价，不是所有列表都适合。用真实滚动、筛选、选中比一比。低性能设备上跟不跟手，以及行卸掉之后正在编辑的内容还在不在，都要看。

## 追问：虚拟列表中输入框草稿为什么容易丢失？

1. 滚出可视区域的行可能被卸掉，行里的 `useState`、非受控输入的值跟着实例一起没了。滚回来是新的行组件。稳定 key 能认对是哪一项，保证不了已经卸掉的实例还在内存里。

2. 要留的草稿按业务 id 存在列表父级，或专门一份编辑状态里。行只读自己的值，变化回传上去。存的是业务输入，不必为了草稿把全部行节点留在 DOM 里，不然虚拟化就没意义了。

3. 编辑时滚动、校验错误定位、提交时数据从哪来，都要想到。提交别只扫当前看得见的输入框，没显示的项也可能改过。测的时候改一行、滚远再回来，内容和错误状态还在。

## 追问：useDeferredValue 能不能替代虚拟列表？

1. 不能。`useDeferredValue` 主要把不紧急、又比较贵的更新往后放，让输入这种要紧的交互先跟上。最后还是要画上万行，计算和 DOM 成本还在，只是什么时候排到变了。

2. 比如搜索框马上显示新字，列表暂时留着上一回的结果，列表用延后的查询值。界面最好说明结果正在更新，别让用户以为眼前已经对上最新输入。它也不是固定隔多久才发请求的防抖。

3. 节点太多还是分页或虚拟化；纯计算太重就改算法或丢 Worker。不同手段对不同问题。先看性能记录里主因是什么，再组合用。某个并发 API 不是自动加速开关。
