# reducer 里为什么不能请求接口？

## 核心回答

1. reducer 的职责是根据当前 state 和 action 计算下一份 state，应该保持纯粹、同步且可预测。同样输入应得到同样结果，这样才方便测试、重放动作和理解状态变化，而请求接口的结果、时机和失败情况都不满足这个条件。

2. 如果 reducer 直接发请求，它可能在计算状态时产生无法撤销的外部行为。开发检查或重复求值会让问题更明显；异步返回时也已经不属于本次同步状态转换，不能让 reducer 返回一个 Promise 当作新的普通状态。

3. 我会把请求放在事件处理器、自定义 Hook，或 Redux 的 thunk、RTK Query 等适合处理异步的位置。请求开始、成功和失败分别产生动作，reducer 只处理这些动作如何改变 loading、data 和 error。

4. 例如加载列表时先派发开始动作，接口完成后派发成功动作，把结果作为 payload 传入。还要在请求层处理取消、编号和旧结果，不能只拆出三个 action 就假设并发正确；错误信息也尽量整理成适合界面和序列化的数据。

5. 实际排查时可以单独调用 reducer 并传入固定状态和动作，检查得到的结果是否确定、旧状态是否保持不变。如果这一步就需要联网、等待定时器或准备浏览器节点，通常说明状态计算和外部操作混在一起，需要把触发过程移到更合适的位置。

## 追问：随机编号和当前时间能不能在 reducer 里生成？

1. 如果每次执行 reducer 都重新生成随机数或读取当前时间，同样的 action 会得到不同结果，不利于动作回放。比如新增任务重放后编号改变，后续按原编号删除的动作就可能对应不上。

2. 我会在事件处理器、action creator 或准备 payload 的地方生成编号和时间，再作为 action 的内容传入。这样“用户在某时刻新增了哪条任务”成为明确输入，reducer 只把这条记录加入状态。

3. 测试也因此更简单，可以传入固定编号和时间，直接比较结果。不是说项目不能使用随机值，而是随机性应发生在状态计算之外，让每次转换的依据能够被记录和解释。例如重试保存时可以继续携带原任务编号，让状态转换仍能找到同一条记录，而不是每次执行又产生另一条。

## 追问：Redux Toolkit 里 reducer 看起来直接修改 state，不违反纯函数吗？

1. Redux Toolkit 的 createSlice 等封装使用 Immer，传入的是可记录修改的 draft。写 `state.count += 1` 会被转换成不可变更新，不代表直接修改了之前已经保存的 Redux state 对象。

2. 这个便利只针对状态更新写法，不允许在 reducer 里随意产生副作用。发请求、操作 DOM 或写本地存储仍不属于纯状态计算，不能因为代码允许赋值，就认为任何命令式操作都可以放进去。

3. 普通 useReducer 没有自动提供同样的 draft 语义，应自行返回新对象，除非明确使用相应封装。阅读代码时要先看 reducer 由谁创建，避免把 createSlice 的写法直接搬到普通 reducer 中造成原地修改。验证普通 reducer 时，应同时检查新结果和原输入是否保持不变，不能只看返回对象里的目标字段已变，就忽略旧状态被污染。
