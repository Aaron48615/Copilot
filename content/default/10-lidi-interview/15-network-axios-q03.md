# 什么是跨域？怎么解决？

## 核心回答

1. 跨域要先看源，也就是协议、主机和有效端口的组合，其中一项不同就是不同源。浏览器同源策略会限制脚本读取其他源的资源，跨域请求能否发出与响应能否被脚本读取，需要分开判断。

2. 对普通接口，CORS 是服务端通过响应头声明允许哪些源访问，浏览器再检查是否放行。前端不能靠自己添加一个 Access-Control-Allow-Origin 请求头解决，因为许可必须由被访问的服务端返回。

3. 开发环境可以把浏览器请求发到同源的开发服务器，再由 Vite 等工具代理到后端。浏览器看到的是同源地址，服务器之间转发不受浏览器同源策略限制，但开发代理不会自动跟着构建产物部署到线上。

4. 生产环境可以正确配置 CORS，或者用同域反向代理统一入口。需要 Cookie 等凭据时，还要一起检查客户端凭据选项、服务端允许凭据的响应头和 Cookie 属性，不能只配置允许域名就认为完成。

5. 我会在 Network 中核对真实请求地址、OPTIONS 和响应头，再结合 Console 的报错定位。`no-cors` 不能让前端自由读取跨域 JSON，JSONP 也只是受限的脚本加载方式，不适合代替普通接口设计。

## 追问：开发代理正常，部署后为什么又跨域了？

1. dev server 的代理只在开发服务器运行时生效，构建出的静态文件并不自带一个转发服务。上线后如果浏览器直接请求后端域名，就重新进入跨源访问，需要部署环境提供对应支持。

2. 我会先检查生产环境的 API 地址和路径，确认是应该请求同域的 `/api`，还是允许访问独立域名。再检查反向代理的路径重写，避免把本该转发的请求落到前端页面回退规则上。

3. 如果决定使用 CORS，就由服务端允许真实生产源，包括协议和端口，而不是只保留本地开发地址。还要检查错误响应是否也带正确的 CORS 头，否则业务报错可能被浏览器呈现为跨域失败。

## 追问：CORS 配好了，跨站 Cookie 为什么仍然没带上？

1. 我会先区分跨源和跨站，两者判断规则不同。跨源 fetch 默认不发送跨源凭据，Axios 也需要按需求设置 withCredentials，但这个开关不能覆盖浏览器对 Cookie 自身的限制。我会查看浏览器给出的 Cookie 排除原因，区分响应时没有存入、作用范围不匹配和发送时被浏览器拦截。

2. 真正跨站的 Cookie 还受 SameSite、Secure、Domain、Path 和浏览器隐私策略影响。即使设置了 SameSite=None 和 Secure，第三方 Cookie 限制仍可能阻止它，不能保证所有浏览器表现一样。

3. 携带凭据的 CORS 响应需要返回明确的允许源并允许凭据，不能把允许源写成通配符。同时服务端仍需要认证及相应的 CSRF 防护，CORS 允许读取响应并不代表请求本身可信。
