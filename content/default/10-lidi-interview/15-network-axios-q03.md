# 什么是跨域？怎么解决？

## 核心回答

1. 跨域先看源，也就是协议、主机和有效端口的组合，其中一项不同就是不同源。浏览器同源策略会限制脚本读取其他源的资源。跨域请求能不能发出去，和响应能不能被脚本读到，要分开看。

2. 普通接口走 CORS：服务端用响应头声明允许哪些源访问，浏览器再检查放不放行。前端不能靠自己加一个 `Access-Control-Allow-Origin` 请求头解决，许可必须由被访问的服务端返回。

3. 开发环境可以把浏览器请求发到同源的开发服务器，再由 Vite 等工具代理到后端。浏览器看到的是同源地址，服务器之间转发不受浏览器同源策略限制。但开发代理不会自动跟着构建产物部署到线上。

4. 生产环境可以正确配置 CORS，或者用同域反向代理统一入口。需要 Cookie 等凭据时，客户端凭据选项、服务端允许凭据的响应头、Cookie 属性要一起查。只配了允许域名，不等于完成。

5. Network 里核对真实请求地址、OPTIONS 和响应头，再结合 Console 报错定位。`no-cors` 不能让前端自由读取跨域 JSON。JSONP 只是受限的脚本加载方式，代替不了普通接口设计。

## 追问：开发代理正常，部署后为什么又跨域了？

1. dev server 的代理只在开发服务器跑着的时候生效，构建出的静态文件并不自带一个转发服务。上线后如果浏览器直接请求后端域名，就重新进入跨源访问，部署环境得提供对应支持。

2. 先查生产环境的 API 地址和路径，确认该请求同域的 `/api`，还是允许访问独立域名。再查反向代理的路径重写，别把本该转发的请求落到前端页面回退规则上。

3. 如果决定用 CORS，由服务端允许真实生产源，包括协议和端口，别只留着本地开发地址。错误响应是不是也带正确的 CORS 头也要看，不然业务报错可能被浏览器呈现成跨域失败。

## 追问：CORS 配好了，跨站 Cookie 为什么仍然没带上？

1. 跨源和跨站不是一回事，判断规则不同。跨源 `fetch` 默认不发送跨源凭据，Axios 也要按需求设 `withCredentials`，但这个开关盖不住浏览器对 Cookie 自身的限制。看浏览器给出的 Cookie 排除原因，分清是响应时没存入、作用范围不匹配，还是发送时被拦截。

2. 真正跨站的 Cookie 还受 SameSite、Secure、Domain、Path 和浏览器隐私策略影响。就算设了 `SameSite=None` 和 `Secure`，第三方 Cookie 限制仍可能挡住它，不能保证所有浏览器表现一样。

3. 携带凭据的 CORS 响应需要返回明确的允许源并允许凭据，允许源不能写成通配符。同时服务端仍需要认证和相应的 CSRF 防护。CORS 允许读取响应，不代表请求本身可信。
