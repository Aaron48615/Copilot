# Loader 和 Plugin 的区别？

## 核心回答

1. Loader 主要负责模块内容转换，Plugin 主要通过构建钩子参与整个编译过程。比如 Sass 不能直接按普通 JavaScript 处理，可以先由 loader 转换；生成 HTML、统计资源或调整产物，则更适合在插件的构建阶段处理。

2. 配置 loader 时用规则匹配文件，并限定处理范围。多个 loader 的普通转换阶段通常从右往左执行，每一层接收上一层结果；它不是只能返回字符串，也可以配合 source map、异步回调和二进制输入，具体要遵守接口约定。

3. Plugin 通常提供 apply 方法，拿到 compiler 后注册钩子。compiler 对应构建控制，compilation 对应一次具体编译，监听文件变化时会产生新的编译过程，因此插件不能把上一次资源状态随意复用到下一次。

4. 我会按需求的作用范围选扩展点。例如把 Markdown 转为模块属于内容转换，输出资源清单属于处理整次产物；一个功能有时需要 loader 与 plugin 配合，不能因为都能改文件就说两者完全等价。

5. 实现时还要处理依赖追踪、错误和缓存。转换依赖额外文件就告诉构建器，插件选合适时机更新资源；验证不仅看一次构建成功，还要修改输入后观察增量结果，避免热更新或缓存命中时悄悄使用旧内容。

## 追问：Loader 的执行顺序为什么不能只背从右往左？

1. 普通转换阶段常按从右往左执行，但 loader 还有 pitch 阶段，它通常按从左往右经过各个 loader。pitch 如果返回结果，可以改变后续执行过程，所以解释复杂 loader 时不能只用一条方向规则包办。

2. 日常组合 Sass、CSS 和样式注入时，先按普通阶段理解输入输出就足够实用。遇到源码调试或执行顺序异常，再检查是否定义了 pitch，以及它是否提前返回，避免为了记术语而忽略实际内容转换。

3. 我会用很小的输入记录各阶段收到的内容和调用顺序，并确认同步、异步返回没有混用。这样能定位规则匹配、阶段短路和格式不兼容，而不是反复换数组顺序，碰巧构建通过却解释不了原因。

## 追问：写插件时为什么要区分 compiler 和 compilation？

1. compiler 可以理解为整个构建任务的控制对象，包含配置和主要生命周期；compilation 管理某一次编译中的模块、依赖和资源。监听模式下一个 compiler 会经历多次 compilation，二者并不是同一个寿命。

2. 如果插件在外部变量里长期累积本次产物，下次编译可能混入旧数据，出现清单重复或已删除文件仍被记录的问题。我会把每次编译相关的数据放到相应作用域，并在适当钩子处理当次资源。

3. 使用 Webpack 5 处理输出时，会核对 processAssets 等正式接口及阶段，避免沿用不匹配的旧示例。测试除了首次构建，还要覆盖修改、删除和新增模块，确认插件结果随当前编译正确变化。
