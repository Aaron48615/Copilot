# React 里什么时候应该用 useEffect？

## 核心回答

1. 我把 useEffect 理解成组件和外部系统同步的地方。比如组件显示时订阅消息，筛选条件变化后请求对应数据，或者把 React 中的配置同步给图表实例；这些对象不会仅靠 JSX 的重新计算自动更新。

2. 能在渲染阶段算出来的结果通常不需要 Effect。比如根据商品数组和搜索词得到筛选列表，直接计算即可，确实昂贵再使用 useMemo；先存一份筛选结果再用 Effect 更新，会多一次更新，也多一份需要保持一致的数据。

3. 用户明确触发的动作一般放在事件处理器里。点击提交表单时校验和发送请求，比设置一个 submitted 状态再由 Effect 猜测何时提交更直接，也不会因组件重新挂载意外重复执行提交动作。

4. 写 Effect 时，我会同时说明依赖、建立过程和清理过程。依赖变化先撤销旧同步，再按新值建立；请求还要防止旧结果回写。Effect 只在客户端执行，所以依赖它拿首屏数据会有额外等待，SSR 场景要结合框架的数据获取方式。

5. 例如页面同时展示筛选列表和当前筛选数量，数量直接由列表得到；窗口尺寸监听才需要外部同步。把它们分开后，改变列表不会无意义地移除并添加窗口监听，组件离开时也只需释放自己建立的外部资源，逻辑与界面的关系更容易解释。

## 追问：把 props 复制到 state，再用 Effect 同步有什么问题？

1. 这会产生两个来源。例如父组件传入姓名，子组件再保存一个 name，父级更新后子级可能先渲染旧副本，再由 Effect 同步；代码还得回答本地编辑和父级更新冲突时究竟保留哪一份。

2. 纯展示直接用 props，计算字段直接从 props 推导。如果子组件确实需要编辑草稿，应把草稿作为独立概念，说明何时初始化、何时提交和取消，而不是无条件跟随父级覆盖用户输入。

3. 切换编辑对象时，可以按业务编号重建编辑组件，或显式执行重置动作。选择取决于是否需要保留未保存内容，不能为了消除依赖警告就让每次接口刷新都清空已经输入了一半的表单。

## 追问：useEffect 和 useLayoutEffect 应该怎么选？

1. 普通请求、日志或外部订阅通常使用 useEffect，它不要求在用户看到画面之前完成。不要把所有副作用都换成 useLayoutEffect，否则同步工作可能阻塞浏览器绘制，让首次显示更慢。

2. 需要读布局并立即调整界面时，才考虑 useLayoutEffect，例如测量提示框高度后决定放在按钮上方还是下方。它适合避免用户先看到错误位置再跳动，但内部工作仍应尽量短。

3. 我不会简单说 useEffect 永远在绘制后执行，交互触发时实际时机有细节差异。选择依据是是否必须阻止绘制，而不是记一个绝对的先后顺序；服务端也不能依赖这些 Effect 读取 DOM。若定位还取决于图片最终尺寸，挂载后的测量也不够，需要在图片就绪或容器尺寸变化后重新计算。
