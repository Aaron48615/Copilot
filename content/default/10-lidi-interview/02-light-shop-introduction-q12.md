# 轻购AI返回结果为什么要用 TypeScript 类型？

## 核心回答

1. GuideResult 不是一个简单文本，而是包含意图、商品、匹配信息和证据的嵌套对象。如果都用 any，访问字段写错或把数组当字符串，编辑器也可能不提醒，错误就会拖到页面真正拿到响应时才暴露。

2. 项目用 GuideProduct 描述商品，GuideRecommendation 描述一条推荐，GuideResult 描述完整结果。这样卡片读取 product.prodId、页面遍历 recommendations 时有明确约定，改接口也能知道哪些页面和函数需要一起调整。

3. 类型也能表达缺失与可选，但要根据真实接口来定义。例如没有识别预算与预算为零不是一回事，匹配列表为空也可以是正常情况；为了通过编译随意把所有字段标成可选，实际会把判断负担转移到每个模板。

4. TypeScript 类型在编译后不会自动校验服务端 JSON。即使写了响应类型，返回 null 或错误结构依然可能发生，类型断言也只是告诉编译器相信我，不会把字符串价格变成有效数值。

5. 项目已经定义了这些类型，但前端缺少完整运行时校验。如果继续完善，在 API 边界检查数组、商品 ID、有效价格和条件列表，通过后再交给组件；关键字段错误时明确失败，不靠默认零元商品掩盖异常。

## 追问：为什么运行时入口用 unknown 比 any 更合适？

1. unknown 表示暂时不知道外部数据是什么，使用前需要做判断。比如先确认响应是非空对象，再判断 recommendations 是数组，这会提醒我把网络数据当作待检查输入，而不是直接假定所有字段存在。

2. any 则基本跳过检查，写错 product 或对不存在的数组调用 map 也不一定报类型错误。它在临时对接时方便，但会让错误继续扩散到页面，所以更愿意在一个入口完成校验，之后使用明确类型。

3. 不过 unknown 自己也不会验证事实，检查 typeof price 为 number 仍要考虑非有限值和业务范围。类型收窄只是把已做的检查告诉编译器，预算、商品归属和真实价格还需要与接口约定及服务端数据对应。

## 追问：接口少一个图片字段，应当整页失败吗？

1. 按字段影响区分。图片缺失通常可以显示占位图和商品名称，不一定要丢掉整张卡；但缺少商品 ID 时，详情跳转无法确定目标，应阻止这个入口或拒绝该推荐，不能随便取数组索引代替。

2. 价格缺失也不应该补零，因为用户会理解为免费。可以明确显示价格暂不可用，或按接口约定把该条视为异常；决定应统一在数据转换层，避免不同卡片分别猜默认值造成前后不一致。

3. 测试会覆盖可选字段缺失与关键字段错误两类，并检查降级后的交互是否仍安全。如果允许跳详情重新获取数据，就明确卡片信息不完整；不能只是让组件不报错，却把错误内容继续用于下单。
