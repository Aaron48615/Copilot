# 前端表单怎么做得更容易使用？

## 核心回答

1. 我会先把表单的原生结构做好。每个输入框都有可见的 label，通过 for 和 id 对应，提交使用 button，合适的输入类型帮助浏览器提供键盘和基础校验。placeholder 只是输入示例，输入后会消失，不能替代字段名称。

2. 提示要说明用户该怎么填、哪里需要改。例如手机号长度不对，应写清预期格式，而不是只显示红框或“非法输入”。错误文本通过 `aria-describedby` 与字段关联，确定有错误后设置 `aria-invalid`，让视觉和读屏获得一致的信息。

3. 校验时机也影响体验。可以在提交时检查全部字段，在离开已编辑字段后反馈格式问题，避免用户刚输入一个字符就报错。异步检查还要区分正在验证、网络失败和业务不通过，并防止旧请求结果覆盖新输入。

4. 提交失败后，我会保留已填内容，把焦点移到错误汇总或第一个有问题的字段，让用户知道下一步在哪里处理。最后不用鼠标完成输入、修改和提交，检查焦点是否可见、顺序是否合理；这比只确认页面有 ARIA 属性更能说明表单能不能用。

5. 重复提交也需要明确反馈。等待响应时可以限制重复触发，并在按钮附近显示正在提交；失败后恢复操作入口，保留当前输入，不能让按钮一直处于不可用状态，只剩一条很快消失的提示让用户猜是否成功。

## 追问：异步用户名校验怎样避免旧结果覆盖新结果？

1. 用户输入变化时先记录本次值或递增请求序号，返回结果时只接受仍对应当前输入的那次响应。比如先查短名称、再查完整名称，前一个慢请求最后到达，也不能把当前字段标成无效。

2. 可以用防抖减少请求，并在支持时取消旧请求，但取消不是唯一保证。请求可能已经完成或服务端仍在处理，所以响应落地前的身份校验仍需要保留，避免把网络时序当作正确性前提。

3. 提交时还要再次由服务端确认唯一性，因为输入阶段的可用结果可能已经过期。网络失败应提示稍后重试，不应假装用户名已经被占用；不同失败原因要给出不同的文案和可继续操作的路径。

## 追问：一张长表单有多处错误时，焦点放在哪里更合适？

1. 字段很少时，可以直接聚焦第一个错误输入框，并让关联说明被读到。字段很多或分组明显时，我会在顶部提供错误汇总，列出具体字段和修正方向，避免用户不知道还有多少问题需要处理。

2. 汇总中的条目可以链接到相应输入框，点击后既滚动到位置，也把焦点真正放过去。只滚动页面但不移动键盘焦点，会让用户继续按 Tab 时从原来的位置开始，视觉与操作顺序不一致。

3. 错误修正后要更新汇总并保留其他已填内容，不能每改一个字段就强行把焦点拉回顶部。我会测试连续修正两个错误再提交的过程，确认提示随状态变化，而且没有重复、突兀的播报。
