# 前端表单怎么做得更容易使用？

## 核心回答

1. 先把原生结构做对。每个输入框都有看得见的 label，`for` 和 `id` 对上；提交用 `button`；合适的 `type` 能换出手机键盘，浏览器也能先拦一层基础格式。`placeholder` 只是示例，一输入就没了，不能当字段名称。

2. 提示要说怎么填、哪里要改。手机号长度不对，写清预期格式，别只剩红框或一句「非法输入」。错误文本用 `aria-describedby` 挂到字段上，确定有错再设 `aria-invalid`，眼睛看到的和读屏听到的是同一件事。

3. 校验时机也影响体验。可以提交时查全部，离开已经改过的字段再报格式问题，别刚敲一个字就报错。异步检查要分清正在验证、网络失败、业务不通过，旧请求回来也别盖掉新输入。

4. 提交失败后，已填内容留着，焦点移到错误汇总或第一个有问题的字段，让人知道下一步改哪。不用鼠标走完输入、修改、提交，看焦点看不看得见、顺序顺不顺。页面上有几个 ARIA 属性，说明不了这张表能不能用。

5. 重复提交也要有反馈。等响应时限制连点，按钮旁边写正在提交；失败了把操作入口还回来，当前输入别丢。别让按钮一直灰着，只剩一条很快消失的提示，人只能猜成没成功。

## 追问：异步用户名校验怎样避免旧结果覆盖新结果？

1. 用户一改字，先记下这次的值或给请求加序号，回来只认还对应当前输入的那次。比如先查了短名、又查完整名，前面那个慢请求最后到，也不能把当前字段标成无效。

2. 防抖能少打几次，支持的话也可以取消旧请求，但取消不是唯一保证。请求可能已经完成，服务端也可能还在处理，落地前还得对身份，别把网络时序当成正确性前提。

3. 提交时服务端还得再确认一次唯一性，输入阶段说可用，过一会儿可能就被别人占了。网络失败提示稍后重试，别假装用户名已经被占用。不同失败原因，文案和接下来能做什么都不一样。

## 追问：一张长表单有多处错误时，焦点放在哪里更合适？

1. 字段很少时，可以直接聚焦第一个错误输入框，让关联说明被读到。字段很多或分组很明显时，顶部给错误汇总，列出具体字段和怎么改，免得人不知道还有多少问题。

2. 汇总里的条目可以链到对应输入框，点过去既滚动到位，也把键盘焦点真放过去。只滚页面、不移焦点，人再按 Tab 还从原来的位置开始，眼睛和键盘对不上。

3. 改对一处后更新汇总，其他已填内容留着，别每改一个字段就把焦点强拉回顶部。连续改两处再提交走一遍，提示跟着状态变，也别突然连念好几遍。
