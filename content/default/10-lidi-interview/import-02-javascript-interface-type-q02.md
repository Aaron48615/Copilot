# 如何设计可演进的 API 类型？

## 核心回答

1. 类型先反映真实的接口约定：成功条件、字段含义、可能缺失的内容，再考虑以后怎么扩展。缺少昵称，和昵称明确为空，可能不是一回事。别为了让编译通过，把所有字段都改成可选，逼着页面到处猜。

2. 不同结果可以用有明确标记的联合类型：成功分支带数据，失败分支带错误信息。调用处先判断结果类别，再读对应字段，能表达哪些字段会一起出现。一个对象里数据和错误都可选，却不知道当前究竟是哪种状态，就容易漏。

3. 新增字段要同时考虑旧调用方，以及新调用方碰到旧服务端怎么办。昵称是新增展示信息，可以按协议暂时允许缺失，并提供展示兜底。字段含义变了，需要转换或版本区分。单纯改个类型名字，实现不了兼容。

4. 网络输入最终还要经过运行时检查，接口类型不会跟着服务器变化自动更新。原始响应和页面需要的结果，在必要处转换。未知枚举值、解析失败、网络异常怎么处理写清楚，类型和实际行为对上。别把所有异常都伪装成成功的空结果。

## 追问：把新增字段设成可选，就一定向后兼容吗？

1. 可选只表示调用方需要考虑字段缺失，说明不了整个协议兼容。旧字段原本表示金额分，现在改成金额元，就算新增字段都是可选，旧页面照原来的单位算仍然会错。语义变化必须核对。

2. 还要看接收方怎么处理未知字段。有的运行时校验会拒绝多余字段，服务端新增内容就可能让旧客户端解析失败。定兼容策略时确认检查规则。类型系统通常允许额外属性，推不出网络解析也允许。

3. 真正可选的展示字段，可以定义缺失时的文案。执行关键操作所必需的信息，不能随便兜底。缺的是权限或支付相关状态，流程应明确失败或重新获取数据，别编造默认值继续执行。

## 追问：后端新增一个状态枚举值，前端怎样避免展示错误？

1. 编译时已知状态，和运行时收到的字符串，要分开。服务端可能先于前端发布新值。输入解析需要决定：拒绝未知状态，还是保留为明确的未知分支。别直接断言它属于旧联合类型，然后继续执行逻辑。

2. 只影响展示的状态，可以考虑显示中性文案，并留下原始值方便排查。决定能不能操作的状态，按业务约定采取保守处理。别把未知状态归到成功或已完成，用户可能拿到错误反馈。

3. 内部已知状态的分支处理里，可以用穷尽检查，帮助发现新增类型后漏掉的分支。这只能覆盖重新编译时已经更新的类型。外部协议变化仍需运行时检查。两者解决的是不同时间点的问题。
