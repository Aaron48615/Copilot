# 如何设计可演进的 API 类型？

## 核心回答

1. 我会先让类型反映真实的接口约定，包括成功条件、字段含义、可能缺失的内容，再考虑以后如何扩展。比如缺少昵称和昵称明确为空可能表示不同事情，不能为了让编译通过，就把所有字段都改成可选，迫使页面到处猜测。

2. 对不同结果，可以用有明确标记的联合类型，让成功分支带数据、失败分支带错误信息。这样调用处先判断结果类别再读取对应字段，能表达哪些字段会一起出现，避免一个对象里数据和错误都可选，却不知道当前究竟是哪种状态。

3. 新增字段要考虑旧调用方，也要考虑新调用方遇到旧服务端时怎么办。假设昵称是新增展示信息，可以按协议暂时允许缺失并提供展示兜底；如果字段含义发生变化，则需要转换或版本区分，单纯改个类型名字并不能实现兼容。

4. 网络输入最终还要经过运行时检查，接口类型不会随着服务器变化自动更新。我会把原始响应与页面需要的结果在必要处转换，明确未知枚举值、解析失败和网络异常怎样处理，保持类型与实际行为一致，而不是把所有异常都伪装成成功的空结果。

## 追问：把新增字段设成可选，就一定向后兼容吗？

1. 可选只表示调用方需要考虑字段缺失，并不能说明整个协议兼容。假如旧字段原本表示金额分，现在改成金额元，即使新增字段都是可选，旧页面照原来的单位计算仍然会出错，必须核对语义变化。

2. 还要看接收方如何处理未知字段，有的运行时校验会拒绝多余字段，服务端新增内容就可能让旧客户端解析失败。制定兼容策略时应确认检查规则，不能只根据类型系统通常允许额外属性就推断网络解析也允许。

3. 对真正可选的展示字段，可以定义缺失时的文案；对执行关键操作所必需的信息，则不能随便兜底。假如缺少的是权限或支付相关状态，我会让流程明确失败或重新获取数据，而不是编造默认值继续执行。

## 追问：后端新增一个状态枚举值，前端怎样避免展示错误？

1. 我会区分编译时已知状态与运行时收到的字符串，服务端可能先于前端发布新值。输入解析需要决定是拒绝未知状态，还是保留为明确的未知分支，不能直接断言它属于旧联合类型后继续执行逻辑。

2. 对只影响展示的状态，可以考虑显示中性文案并保留原始值用于排查；对决定是否允许操作的状态，则应按业务约定采取保守处理。不能把未知状态归到成功或已完成，否则用户可能获得错误反馈。

3. 在内部已知状态的分支处理中，可以用穷尽检查帮助发现新增类型后遗漏的分支。不过这只能覆盖重新编译时已经更新的类型，外部协议变化仍需运行时检查，两者分别解决不同时间点的问题。
