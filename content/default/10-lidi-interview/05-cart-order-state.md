# 轻购的购物车、价格联动和订单确认状态是怎么处理的？

## 核心回答

1. 购物车数据按店铺、优惠分组和商品项嵌套返回，原结构用来展示店铺与优惠。页面另外用 computed 得到扁平 cartItems，统一处理勾选和数量，里面仍引用原商品对象，所以计算用的列表与展示的商品可以保持同步。

2. 加载商品后补 checked，selectedBasketIds 从中取选中项 ID，allChecked 根据非空且全部选中计算。全选不再单独保存一份容易不同步的布尔状态；没有商品时必须额外判断非空，因为空数组 every 的结果本来是真。

3. 勾选变化会调用 `/p/shopCart/totalPay` 读取 totalMoney，没有选中就显示零。数量修改成功后也需要刷新金额，价格不能只等选中 ID 改变；当前总价请求还缺少独立乱序保护，快速操作仍可能出现旧金额覆盖。

4. 数量接口接收差值，同一 basketId 正在更新时会暂时阻止重复修改，成功再更新本地数量。减到零走删除并重新加载，删除后的选中状态目前也会重置，用户需要重新勾选；若希望保留，应按未删除的 basketId 恢复。

5. 结算时把 basketIds 和地址等参数放进 sessionStorage 的 confirmOrder，确认页重新读取地址并请求金额。服务端负责按真实商品与 SKU 校验；前端重查库存不能单独保证不超卖，后端还需要通过条件扣减或锁定处理并发库存变化。

## 追问：勾选没有变化，数量变化为何也要请求金额？

1. selectedBasketIds 只表达选了哪些购物车行，某行从一件变两件，它的 ID 不变。若金额刷新只依赖这个数组，页面数量已经更新，总价却还停在一件时的结果，用户看到的数据就不一致。

2. 因此数量更新成功后要明确触发重新计价，或者让计价依赖同时包含选中项与数量版本。不能仅因为 computed 会重新求值，就假定 watcher 必然在所有实现中按期望触发，关键依赖需要清楚表达。

3. 验证时固定选中一件商品，连续增减并模拟失败，检查成功才更新数量和对应金额，失败不显示未被接受的数量。金额仍由服务端返回，前端重新触发只是确保展示跟上业务变化。

## 追问：购物车到确认页之间数据变了怎么办？

1. 购物车是用户之前保存的选择，不是对价格和库存的预约。进入确认页后重新查商品、地址与费用，能发现下架、地址删除或优惠变化；不能仅把购物车对象复制过去就跳过这一步。

2. 如果服务端调整数量或金额，前端应清楚展示变化，让用户重新确认。比如库存只剩一件而原来选了两件，不应悄悄减量后直接提交，用户需要知道实际准备购买的内容与最初选择不同。

3. 提交时仍要最终校验，并由后端用事务与库存策略保证写入规则。重新校验只能看到查询当时的库存，真正写入时还需要原子扣减或锁定。例如两个人都查到最后一件，最终只能有一个成功买到，前端确认页无法独自保证这一点。
