# Vuex 和 Pinia 有什么区别？

## 核心回答

1. Vuex 和 Pinia 都用于组织多个组件共享的状态，但 API 约定不同。Vuex 常见结构是 `state`、`getters`、`mutations` 和 `actions`，状态修改通过 mutation 描述，异步流程通常放在 action，再提交同步 mutation。

2. Pinia 保留 state、getter 和 action 等概念，不要求额外写 mutation，可以直接更新状态或使用 `$patch`。action 也能包含异步逻辑，日常代码更少一些，也减少了只负责转交参数的中间函数，但涉及校验和多个字段更新时，我仍会集中到含义明确的方法里。

3. Pinia 使用独立的 store 组织功能，不需要像 Vuex 那样先设计嵌套模块和命名空间，也支持选项式和 Setup Store。它对 TypeScript 的推导比较自然，但抽取状态时仍要注意响应式，不能认为普通解构在所有情况下都安全，状态来源仍需要保持可追踪。

4. 智服工单使用 Vue 2 和 Vuex 管理登录会话及工单相关状态，这类跨页面信息适合集中管理；对于新的 Vue 3 共享状态，我会优先考虑 Pinia。Vuex 也有支持 Vue 3 的版本，当前 Pinia 已不再支持 Vue 2，因此不能简单按库名忽略版本兼容。

5. 选用状态库之前，我会先确定哪些数据确实需要共享，页面临时表单和弹窗开关不一定要进 store。状态库也不自动解决刷新恢复、账号切换清理或服务端权限验证，这些行为需要结合项目需求单独设计。

## 追问：直接解构 Pinia store 为什么可能失去响应式？

1. store 本身是响应式对象，直接写 `const { count } = store`，得到的可能只是当前数字值。后续 store 中的 `count` 变化，并不会让这个普通局部变量自动变成新值，和解构 reactive 基本值属性的问题类似。

2. 如果需要单独使用状态和 getter，可以通过 `storeToRefs(store)` 得到保持连接的 ref，或者直接使用 `store.count`。action 已绑定到 store，可以直接解构调用；不需要把所有成员都机械地变成 ref。

3. 我会检查解构发生的位置以及被提取的成员类型，尤其是组合函数返回值和组件顶部的写法。对 Setup Store，也应正常返回需要由 Pinia 管理的状态，不能为了模拟私有属性就隐藏全部状态，影响开发工具等功能，服务端渲染和插件也可能依赖完整的状态定义。

## 追问：Pinia 刷新后会自动恢复数据吗，退出登录怎样清理？

1. 默认 store 主要保存在当前应用内存中，刷新页面会重新创建，不会自动从浏览器存储恢复。需要保留购物车或筛选条件时，可以显式持久化或选用插件，同时定义保存字段、失效时机和旧格式如何处理。

2. 退出登录时应清理与账号有关的 store、持久化数据和仍在进行的请求，避免下个账号看到旧内容。服务端才是权限与会话有效性的判断依据，前端把按钮隐藏或 store 清空，都不能替代接口鉴权。

3. Pinia 的 Option Store 提供 `$reset`，Setup Store 则需要自己实现重置方法，不能假定所有 store 都能同样调用。若继续完善，我会检查多个账号切换、刷新恢复及旧请求晚返回的场景，而不是只测试一次点击退出按钮。
