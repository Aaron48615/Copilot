# 什么是跨域？你是怎么解决的？

## 核心回答

1. 同源要求协议、主机、端口一致，任意一项不同就不是同一个源。同源策略限制脚本去访问其他源的某些资源和响应，但不等于跨源请求都发不出去。有的请求已经到了服务端，有的会在预检失败后停掉。

2. 开发代理和生产反向代理职责不一样。开发时浏览器请求同源的 `/api`，Vite 服务器再转到后端。生产可以由 Nginx 托管页面并代理接口，浏览器看到的入口还是同源。开发代理那份配置，不会随着构建自动部署上去。

3. 真要跨源读取时，由服务端按业务配 CORS。`Authorization`、非简单内容类型这些条件可能触发 OPTIONS 预检，得允许对应来源、方法和请求头。携带跨源凭据时，允许来源不能写成星号。

4. 先看控制台和 Network，再分清是 CORS、网络失败、代理地址错了，还是登录失效。CORS 代替不了权限校验，也不是 CSRF 防护。`no-cors` 拿到的是受限的 opaque 响应，不能靠它让页面随便读任意接口内容。

5. 比如 JSON 请求带上 `Authorization` 后，可能比简单查询多一次预检。新增的 OPTIONS 不是业务接口又调了一遍。日志里预检和真实操作要分开认。服务端对预检回了许可，真实操作照样要登录、要验权限。

## 追问：OPTIONS 成功，为什么实际请求仍然报跨域？

1. 预检允许把请求发出去，不等于实际响应已经满足 CORS。服务端可能只给 OPTIONS 加了允许来源的头，真正的 GET、POST 或错误响应漏了，浏览器还是不会把响应内容交给页面读。

2. 看真实请求的响应头，以及有没有重定向。尤其是 401、500 是不是走了另一套网关配置。带凭据的请求还要匹配明确来源和允许凭据设置。OPTIONS 回了 200 就停手，不够。

3. 正确的 CORS 规则要覆盖正常响应和异常响应，来源白名单也还在。前端别靠吞掉错误、关掉浏览器安全限制把问题盖住。那样本地看着正常，真实用户还是读不到接口结果。

## 追问：开发代理能否代替生产环境配置？

1. 不能。开发代理跑在本地开发服务器里，负责把浏览器发给它的请求转到目标后端。构建产物通常只是静态文件，里面没有一个持续跑着的代理服务，上传到服务器后这项能力不会自己出现。

2. 生产需要真实的反向代理、同源后端路径，或者让后端正确配 CORS。比如 `/api` 转到业务服务，页面路由才回退到 `index.html`。接口错误地回退成 HTML，JSON 解析就会失败。

3. 在接近生产的地址下测登录、文件上传和错误响应，确认代理前缀、超时、Cookie 属性都对。只测首页能打开不够。首页静态资源成功，证明不了接口转发也对。
