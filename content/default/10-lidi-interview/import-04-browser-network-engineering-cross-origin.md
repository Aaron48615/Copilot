# 什么是跨域？你是怎么解决的？

## 核心回答

1. 同源要求协议、主机和端口一致，任意一项不同就属于不同源。同源策略限制脚本访问其他源的某些资源和响应，但不等于一切跨源请求都发不出去；有些请求已到服务端，有些会在预检失败后停止。

2. 我会区分开发代理和生产反向代理的职责。开发时浏览器请求同源的 /api，Vite 服务器再转发到后端；生产可以由 Nginx 托管页面并代理接口，浏览器看到的入口同源，开发代理配置本身不会随构建自动部署。

3. 确实需要跨源读取时，由服务端按业务配置 CORS。Authorization、非简单内容类型等条件可能触发 OPTIONS 预检，需要允许对应来源、方法和请求头；如果携带跨源凭据，允许来源不能简单写成星号。

4. 我会先检查控制台和 Network，再区分 CORS、网络失败、代理地址错误和登录失效。CORS 不代替权限校验，也不是 CSRF 防护；no-cors 返回受限的 opaque 响应，不能用它让页面随意读取任意接口内容。

5. 例如 JSON 请求带上 Authorization 后可能比简单查询多一次预检，不能把新增的 OPTIONS 当成业务接口重复调用。日志中应分别识别预检与真实操作，服务端对预检返回许可也不代表真实操作免于登录和权限验证。

## 追问：OPTIONS 成功，为什么实际请求仍然报跨域？

1. 预检允许发送请求，不代表实际响应已经满足 CORS。服务端可能只给 OPTIONS 添加允许来源的头，却漏掉实际 GET、POST 或错误响应，浏览器仍不会把响应内容交给页面读取。

2. 我会查看真实请求的响应头以及重定向过程，尤其检查 401、500 是否走了另一套网关配置。带凭据请求还要匹配明确来源和允许凭据设置，不能只看到 OPTIONS 返回 200 就停止检查。

3. 修复应让正确的 CORS 规则覆盖正常和异常响应，同时保持来源白名单。前端不要通过吞掉错误或关闭浏览器安全限制掩盖问题，那样本地似乎正常，真实用户仍然无法读取接口结果。

## 追问：开发代理能否代替生产环境配置？

1. 不能。开发代理运行在本地开发服务器中，负责把浏览器发给它的请求转给目标后端；构建产物通常只是静态文件，并不包含一个持续运行的代理服务，上传到服务器后这项能力不会自然存在。

2. 生产需要部署真实的反向代理、同源后端路径，或者让后端正确配置 CORS。例如 /api 应转发到业务服务，而页面路由才回退到 index.html；把接口错误地回退到 HTML 会造成 JSON 解析失败。

3. 我会在接近生产的地址下测试登录、文件上传和错误响应，确认代理前缀、超时及 Cookie 属性都正确。只测试首页可以打开不够，因为首页静态资源成功，并不能证明接口转发也正确。
