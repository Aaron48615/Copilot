# TCP 三次握手、四次挥手，以及为什么次数不同

## 核心回答

> 沿用你的回答，末尾补充相关解释。

三次握手用于建立连接

客户端向服务端发送SYN，要求建立数据连接

服务端向客户端发送ACK和SYN，告诉他可以连接

客户端向服务端发送ACK，服务器验证后，连接成功

四次挥手用于断开连接，双方是可以分别关闭发送方向的，因为TCP两个方向可以独立结束

客户端给服务端发送FIN，告诉对方我发送完了

服务器发送ACK，表示我收到你的结束信号了，但是服务器可能还没发完

服务器发送FIN，表示服务器的数据也发完了

客户端发送ACK，进入TIME_WAIT等待状态，双方关闭连接

【建立连接时，服务端通常可以把确认客户端的 ACK 和自己的 SYN 合在一条报文里；关闭时，确认收到 FIN 和自己已经发完数据是两件事，所以 ACK、FIN 常常分开发送，形成四次。主动关闭的一方通常会在最后进入 TIME_WAIT 等待，另一方收到最后的 ACK 后可以关闭。两者不是在同一瞬间一起结束，关闭过程也可能合并报文。】

### TCP 三次握手

#### 过程

假设客户端初始序列号为 `x`，服务器为 `y`：

1. **Client → Server**：`SYN=1, seq=x`。客户端请求建立连接并通知自己的初始序列号。
2. **Server → Client**：`SYN=1, ACK=1, seq=y, ack=x+1`。服务器确认客户端序列号，并发送自己的初始序列号。
3. **Client → Server**：`ACK=1, ack=y+1`。客户端确认服务器序列号，连接建立。

SYN 会消耗一个序列号，所以确认号是 `x + 1` / `y + 1`。

#### 为什么不是两次

两次只能让客户端知道“服务器收到了我的 SYN，并给了它的序列号”，服务器还不知道客户端是否收到自己的 SYN 和初始序列号。第三次 ACK 完成这个确认，也能防止已过期的重复 SYN 让服务器误以为有一条有效连接而长时间保留状态。

#### 三次握手的核心目的

- 让双方确认连接路径可用。
- 互换并确认初始序列号。
- 协商 MSS、窗口缩放、SACK 等 TCP 选项。

因此只说“检查双方发送、接收能力正常”可以帮助记忆，但不如“同步并相互确认初始序列号和参数”严谨。

### TCP 四次挥手

#### 过程

TCP 是全双工的，两个方向要分别关闭。假设客户端主动关闭：

1. **Client → Server**：发送 `FIN`，表示客户端没有更多数据要发，进入半关闭。
2. **Server → Client**：回复 `ACK`，但服务器仍可继续发送剩余数据。
3. **Server → Client**：服务器也发完后发送 `FIN`。
4. **Client → Server**：回复最终 `ACK`，随后客户端进入 `TIME_WAIT`。

服务器如果已经没有剩余数据，第二次 ACK 和第三次 FIN 可以合并，抓包中可能只看到三个报文段。“四次”描述的是逻辑上两个方向各自的 FIN 和 ACK。

#### 主动关闭方为什么要 TIME_WAIT

- 如果最后一个 ACK 丢失，被动关闭方会重发 FIN，主动关闭方仍能重发 ACK。
- 让网络中该连接的旧报文超时消失，避免影响同一四元组的新连接。
