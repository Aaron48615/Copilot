# LCP、INP、CLS 分别反映什么问题？

## 核心回答

把它们对应到使用页面时的感受，就比较好理解了。LCP 看主要内容什么时候出现，比如首屏的大图或文本；INP 看点击、输入以后页面响应得怎么样；CLS 看页面有没有突然移位，比如图片出来时把按钮挤走了。

LCP 不好，可以查主图是不是太晚才开始加载，接口或页面返回是不是慢。INP 不好，就看主线程有没有长时间计算、事件处理是不是太重。CLS 就先查图片有没有预留尺寸，异步内容插入时有没有把原来的布局推开。

我比较喜欢把指标和性能面板放在一起看。指标能指出大概是哪种问题，时间线能看到具体卡在哪一步，比只说“感觉慢”或者只盯一个分数更容易找到原因。改完再比较，看看用户等待的地方有没有改善。

### 性能指标

#### 加载与呈现指标

| 指标 | 衡量内容 | 常见瓶颈 |
| --- | --- | --- |
| TTFB | 导航开始到收到响应第一字节 | 重定向、DNS/连接、服务器处理、CDN 缓存 |
| FP | 首次绘制任何像素 | 了解渲染是否开始，业务价值有限 |
| FCP | 首次绘制文本、图片等内容 | 阻塞 CSS/JS、慢 TTFB |
| LCP | 视口中最大内容元素的呈现时间 | 首屏大图、字体、慢服务端、渲染依赖 JS |

FP 只说明“屏幕开始有像素”，FCP 说明“开始有用户能看见的内容”，LCP 更接近“主要内容出来了”。

#### Core Web Vitals

| 指标 | 用户体验 | 良好阈值 |
| --- | --- | ---: |
| LCP | 主要内容加载速度 | `≤ 2.5s` |
| INP | 整个访问期间的交互响应性 | `≤ 200ms` |
| CLS | 意外布局偏移、视觉稳定性 | `≤ 0.1` |

阈值通常看真实用户数据的第 75 百分位，并分开统计移动端和桌面端。

> [!note]
> FID 已被 INP 取代。FID 只关注第一次交互的输入延迟；INP 考察整个页面生命期中的交互，还覆盖事件处理和下一帧呈现等待。

#### 实验室数据和真实用户数据

- **Lab data**：在可控设备和网络条件下重现，适合调试和回归，例如 Lighthouse、DevTools、WebPageTest。
- **Field/RUM data**：真实用户、设备、地域和网络下的数据，适合判断真实影响，例如 CrUX 和自建 RUM。

两者不能互相替代。Lab 快但可能没覆盖低端机和长会话交互；RUM 真实但噪声更大，还要注意版本、路由和用户分群。

### 怎么优化 LCP

1. 先把 LCP 拆成 TTFB、资源发现延迟、下载时间和元素渲染延迟。
2. 让 LCP 资源在初始 HTML 中可发现，不要懒加载。
3. 优化服务端/CDN TTFB，减小图片和字体体积。
4. 减少阻塞渲染的 CSS/JS 和主线程长任务。

### 怎么优化 CLS

- 图片、视频、iframe 和广告预留尺寸。
- 不在已显示内容上方突然插入无预留空间的内容。
- 优化字体加载和 fallback 尺寸差异。
- 动画使用 `transform`，不用改变文档流的属性推动其他元素。
