# WebSocket 和 SSE 怎么选择？

## 核心回答

选择时主要看消息是不是需要频繁双向发送。WebSocket 建立连接以后，客户端和服务端都能主动发消息，像协同编辑这种双方一直在交互的场景比较适合。

SSE 更偏服务端持续往浏览器推文本，比如进度、通知或者逐步返回的文字。浏览器可以用 EventSource 接收，它有事件解析和自动重连能力。如果客户端只是先提交一次，后面主要等服务器推送，我更偏向 SSE 加普通 HTTP 请求，消息方向比较清楚，也能利用 EventSource 已有的能力。

两种方式都得考虑断线、登录失效和重复消息，组件不用了也要关连接。“实时”不一定就要用 WebSocket，还是看消息方向和频率，选适合这个交互的方式。

### 短轮询、长轮询、SSE、WebSocket

| 方案 | 工作方式 | 优点 | 局限 |
| --- | --- | --- | --- |
| 短轮询 | 固定或动态间隔发请求 | 简单、普通 HTTP 即可 | 空请求多，实时性取决于间隔 |
| 长轮询 | 服务端有数据或超时才响应，客户端立即再发 | 比短轮询更及时 | 每次消息仍会重新建立请求，服务端管理复杂 |
| SSE | 服务端通过一个 HTTP 响应持续推送文本事件 | 单向推送简单，浏览器原生支持重连 | 主要是服务端到客户端，不适合任意二进制双向通信 |
| WebSocket | 长连接上的双向帧通信 | 低延迟、全双工 | 要处理心跳、重连、背压、扩容和消息协议 |

选择原则：低频状态查询用普通轮询；服务端单向推送通知、日志或 AI 文本流可考虑 SSE；双方都需频繁主动发送时再考虑 WebSocket。
