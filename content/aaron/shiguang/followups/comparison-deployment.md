# 追问：这个功能上线时做了什么处理？还有哪些可以改进？

## 核心回答

本地开发时可以让 Vite 中间件接请求，上线就不能只依赖开发服务器了。所以线上接到了 Vercel 服务端函数，Key、模型和接口地址从服务端环境变量读，前端还是请求本站的 `/api/compare/advice`。

接口会检查请求方法、JSON、请求体大小、商品 ID 和需求长度，也限制 IP 的请求频率。默认服务端总超时是 55 秒，前端等到 65 秒会停止等待，避免一直转圈。模型或接口失败就给明确提示，保留商品对比，让用户自己选择要不要重试。

我觉得后续最需要补的是资料质量和用量控制。现在所有商品都能用基础对比，但多数商品只有接口提供的字段，专业参数不够，不能硬做很深入的推荐。可以先给常用品类整理统一字段和可靠来源，再逐步补充。限流现在只在单个实例里计数，后面还要做用户鉴权和共享额度。

【同源检查不等于用户鉴权，也不能当作全站费用上限。代码里已有对比数据、流式处理和接口的测试文件，但要说某次发布验证通过，还是要看那次执行记录，真实模型的验证也不能用模拟响应代替。】

## 回答要点

- 本地开发时可以让 Vite 中间件接请求，上线就不能只依赖开发服务器了。
- 接口会检查请求方法、JSON、请求体大小、商品 ID 和需求长度，也限制 IP 的请求频率。
- 我觉得后续最需要补的是资料质量和用量控制。现在所有商品都能用基础对比，但多数商品只有接口提供的字段，专业参数不够，不能硬做很深入的推荐。
